# Amazon Elastic Block Storage (EBS)

## 1. 소개

Amazon Web Services(AWS)는 조직이 클라우드에서 컴퓨팅과 스토리지 리소스를 관리하는 방식을 혁신했습니다. 그중에서도 Amazon Elastic Block Store(EBS)는 Amazon EC2 인스턴스를 사용할 때 데이터 지속성, 성능 최적화, 운영 복원력을 위한 근본적인 구성 요소로 자리잡고 있습니다.

이 장에서는 네트워크 드라이브이자 영속적인 저장 매체로서 EBS의 필수적인 특성을 살펴보며 EBS를 소개합니다. EC2 인스턴스가 종료된 후에도 데이터를 유지하는 능력, 부트 볼륨으로서의 사용, 동적 확장의 유연성이 주는 이점 등 EBS를 사용하는 주요 이유를 논의합니다. 이 장을 진행하면서 EBS 볼륨이 어떻게 동작하는지, 그 기반이 되는 아키텍처 설계가 무엇인지, AWS 고객이 다양한 워크로드 요구 사항을 충족하기 위해 EBS를 어떻게 활용할 수 있는지에 대한 통찰을 얻게 될 것입니다.

## 2. 정의와 기본 개념

### 2.1. 네트워크 드라이브로서의 EBS

EBS 볼륨의 핵심은, EC2 인스턴스를 호스팅하는 물리적 하드웨어와는 독립적으로 존재하는 블록 스토리지 장치입니다. 서버에 물리적으로 연결된 로컬 디스크와 달리, EBS 볼륨은 AWS 내부 네트워크를 통해 접근하는 "네트워크 드라이브"입니다. 이는 한 컴퓨터에서 뽑아 다른 컴퓨터에 연결할 수 있는 USB 스틱과 유사한 개념이지만, 그 연결이 고성능·저지연 네트워크를 매개로 이루어진다는 중요한 차이가 있습니다.

EBS 볼륨은 원격으로 접근하기 때문에 I/O 작업에는 0이 아닌 네트워크 지연 시간이 존재합니다. 하지만 AWS는 이러한 지연을 최소화하도록 서비스를 설계했으며, 그 결과 많은 워크로드가 로컬 연결 스토리지와 비슷한 성능을 경험합니다. 이러한 네트워크 기반 접근 방식은 EBS 볼륨을 한 인스턴스에서 분리해 몇 초 만에 다른 인스턴스에 다시 연결할 수 있는 기능을 포함한 여러 핵심 기능을 가능하게 합니다. 이 유연성은 클라우드 환경에서 동적 확장, 페일오버, 복구 전략을 지원하는 기초적인 특성입니다.

### 2.2. EC2 인스턴스와의 관계

EBS 볼륨은 EC2 인스턴스와 본질적으로 연결되어 있지만, 임시 인스턴스 스토어와는 구별되는 독립성을 유지합니다. EC2 인스턴스를 시작할 때 하나 이상의 EBS 볼륨을 연결해 운영체제 파일, 애플리케이션, 로그, 기타 데이터를 위한 필요한 스토리지를 제공할 수 있습니다. 주목할 점은, EC2 인스턴스에는 임시 스토리지를 제공할 수 있는 로컬 인스턴스 스토어가 있지만, EBS가 AWS에서 영속적 스토리지를 위한 주요 솔루션이라는 것입니다.

### 2.3. 지속성과 데이터 관리

EBS의 핵심 특징 중 하나는 지속성입니다. EBS 볼륨에 저장된 데이터는 연결된 EC2 인스턴스가 종료되어도 그대로 유지됩니다. 이 지속적인 특성 덕분에 EBS는 데이터 내구성이 무엇보다 중요한 애플리케이션에 이상적입니다. 많은 시나리오에서 EC2 인스턴스는 오토 스케일링 그룹의 일부로 또는 소프트웨어 업데이트 도중 재생성되거나 교체되며 단명할 수 있지만, 기반이 되는 EBS 볼륨은 상태를 유지하여 중요한 정보를 잃지 않고 환경을 재구성할 수 있게 합니다.

EBS 볼륨의 지속성은 데이터 관리에서 다음과 같은 상당한 이점을 제공합니다.

- **내구성:** 데이터는 가용 영역(AZ) 내에서 중복 저장되어 구성 요소 장애로부터 보호됩니다.
- **상태 유지 애플리케이션:** 데이터베이스나 파일 시스템처럼 상태가 있는 데이터를 필요로 하는 워크로드는 외부 시스템으로의 지속적인 복제 없이도 EBS를 안정적으로 사용할 수 있습니다.
- **복구와 재프로비저닝:** EC2 인스턴스가 종료된 후, 동일한 EBS 볼륨을 새 인스턴스에 다시 연결할 수 있어 애플리케이션의 매끄러운 복구와 데이터 연속성을 보장합니다.

## 3. EBS 아키텍처와 기술적 세부 사항

### 3.1. 네트워크 드라이브의 특성

네트워크 드라이브로서 EBS 볼륨은 이를 사용하는 EC2 인스턴스와 물리적으로 함께 위치하지 않습니다. 대신 볼륨은 특정 가용 영역 내의 AWS의 매우 중복적인 스토리지 인프라에서 관리되는 리소스입니다. 이 설계는 다음과 같은 여러 이점을 제공합니다.

- **유연성:** 물리적 서버 하드웨어와 관계없이 볼륨을 생성, 연결, 분리, (스냅샷을 통해) 이동할 수 있습니다.
- **확장성:** AWS는 컴퓨팅 리소스와 독립적으로 스토리지를 확장할 수 있어, 사용자가 필요한 정확한 스토리지 용량과 성능을 프로비저닝할 수 있게 합니다.
- **내결함성:** 데이터는 가용 영역 내에서 자동으로 복제되어 하드웨어 장애를 방어합니다.

다만 네트워크 드라이브를 사용하면 네트워크 지연 시간과 같은 고려 사항이 생깁니다. AWS 네트워크는 높은 처리량과 낮은 지연 시간에 최적화되어 있지만, 극도로 지연 시간에 민감한 작업을 수행하는 애플리케이션은 네트워크 전송에 내재된 약간의 지연을 고려해 설계해야 합니다. AWS는 빠른 I/O 작업이 필요한 워크로드조차도 로컬 연결 디스크와 비슷한 성능을 얻을 수 있도록 내부 네트워킹 프로토콜을 지속적으로 개선하고 있습니다.

### 3.2. 가용 영역 제약

모든 EBS 볼륨은 리전 내의 특정 가용 영역(AZ)에 종속됩니다. 이 종속성은 다음과 같은 중요한 운영상의 함의를 갖습니다.

- **영역 종속성:** 한 AZ(예: us-east-1a)에서 생성된 EBS 볼륨은 다른 AZ(예: us-east-1b)에 위치한 EC2 인스턴스에 직접 연결할 수 없습니다. 이 설계는 영역 내에서 고가용성과 데이터 중복성을 보장하는 데 도움이 됩니다.
- **데이터 이동:** 다른 AZ에서 EBS 볼륨의 데이터를 사용하려면 먼저 볼륨의 스냅샷을 생성해야 합니다. 스냅샷은 Amazon S3에 저장되며 다른 AZ나 리전에서 새 EBS 볼륨을 재생성하는 데 사용할 수 있습니다.
- **운영 계획:** 고가용성 아키텍처를 설계할 때는 EBS 볼륨의 영역별 특성을 고려한 계획이 필수적입니다. 각 AZ에 별도의 볼륨을 유지하거나, 장애 발생 시 스냅샷을 사용해 영역 간에 데이터를 전파할 수 있습니다.

이러한 제약은 특히 여러 영역이나 리전에서 고가용성을 요구하는 애플리케이션의 경우 견고한 아키텍처 계획이 필요함을 강조합니다.

### 3.3. 용량과 성능 프로비저닝

EBS 볼륨을 프로비저닝할 때는 스토리지 용량(기가바이트 또는 테라바이트 단위)과 일반적으로 초당 I/O 작업 수(IOPS)와 처리량으로 측정되는 성능 특성이라는 두 가지 핵심 파라미터를 지정해야 합니다. 이 프로비저닝 모델은 저장하려는 데이터의 크기와 애플리케이션의 성능 요구 사항 모두를 사전에 계획해야 함을 의미합니다.

고려해야 할 몇 가지 요소가 있습니다.

- **용량 계획:** EBS 볼륨은 "사전 프로비저닝된" 리소스이므로 생성 시점에 필요한 스토리지 양을 선언해야 합니다. 볼륨은 나중에 크기를 조정할 수 있지만(4절에서 자세히 다룸), 초기 프로비저닝 단계가 사용 가능한 스토리지의 기준선이 됩니다.
- **성능 튜닝:** EBS 볼륨 유형마다 성능 프로필이 다릅니다. 예를 들어 범용 SSD(gp2/gp3) 볼륨은 IOPS와 처리량이 일반적으로 비용 효율적인 성능을 위해 균형을 이루는 반면, 프로비저닝된 IOPS 볼륨(io1/io2)은 까다로운 워크로드를 위해 높고 일관된 성능을 제공합니다.
- **비용 영향:** AWS는 프로비저닝된 용량과 성능 파라미터를 기준으로 EBS 볼륨에 요금을 부과합니다. 즉, 볼륨의 크기와 필요한 IOPS 수준 모두에 직접적인 비용이 연관됩니다. 이 균형을 최적화하는 것은 성능과 비용 효율성을 모두 유지하는 데 매우 중요합니다.

### 3.4. 연결과 분리 프로세스

EC2 인스턴스에 EBS 볼륨을 연결하는 것은 상당한 운영 유연성을 제공하는 동적인 작업입니다. 이 프로세스는 다음을 포함합니다.

- **볼륨 생성:** EBS 볼륨을 생성할 때 AZ, 용량, 성능 특성을 지정합니다. 볼륨은 인스턴스에 연결되기 전까지 독립적으로 존재합니다.
- **연결:** 연결되면 EC2 인스턴스는 볼륨을 마치 로컬 디스크처럼 접근할 수 있습니다.
- **분리:** 볼륨의 데이터 지속성을 방해하지 않으면서 인스턴스에서 분리할 수 있습니다. 이는 인스턴스 교체나 페일오버 전략을 구현할 때 특히 유용합니다. 분리 단계 동안에는 데이터 손상을 방지하기 위해 운영체제가 모든 I/O 작업이 정상적으로 종료되었음을 보장해야 합니다.

## 4. EBS 볼륨 관리

### 4.1. 종료 시 삭제(Delete on Termination) 속성

EBS 볼륨을 생성할 때 제공되는 주요 기능 중 하나는 "종료 시 삭제(DOT)" 속성입니다. 이 속성은 연결된 EC2 인스턴스가 종료될 때 EBS 볼륨이 자동으로 삭제될지 여부를 결정합니다. 기본 동작은 루트 볼륨과 추가로 연결된 볼륨 사이에서 일반적으로 다릅니다.

- **루트 볼륨:** 기본적으로 루트 볼륨은 인스턴스 종료 시 삭제되도록 구성되어 있습니다. 이는 인스턴스가 종료된 후 계정에 임시적인 인스턴스 특정 데이터가 남지 않도록 보장합니다.
- **추가 볼륨:** 루트가 아닌, 추가로 연결된 EBS 볼륨의 경우 기본 설정은 인스턴스 종료 후에도 볼륨을 보존하는 것입니다. 이는 여러 인스턴스 간에 공유되거나 장기 보존이 필요한 데이터를 보존하는 데 특히 유용합니다.

관리자는 시작 시점이나 인스턴스가 실행 중인 상태에서 이 동작을 수정할 수 있습니다. 예를 들어 인스턴스가 종료된 후에도 운영체제 상태나 중요한 로그 파일을 보존하고 싶다면 루트 볼륨의 DOT 속성을 비활성화할 수 있습니다. DOT 속성을 올바르게 이해하고 구성하는 것은 데이터 보존 요구 사항을 충족하는 데뿐만 아니라, 원치 않는 볼륨이 예기치 않은 비용을 초래할 수 있으므로 비용을 관리하는 데에도 필수적입니다.

### 4.2. EBS 볼륨 크기 조정

EBS 볼륨은 스토리지와 성능 요구 사항이 변화함에 따라 크기를 조정할 수 있는 유연성을 제공합니다. EBS 볼륨의 크기를 조정하는 과정은 두 가지 주요 단계로 이루어집니다.

1. **볼륨 수정:** AWS Management Console, CLI, API를 통해 볼륨의 크기(경우에 따라 IOPS 같은 성능 파라미터도)를 수정할 수 있습니다. 볼륨이 수정될 때는 새 파라미터가 적용되는 "modifying" 단계와 볼륨의 데이터 블록이 재구성되는 "optimizing" 단계를 포함한 여러 상태를 거칩니다.
2. **파일 시스템 재파티셔닝:** 볼륨 용량이 증가한 후에도 운영체제의 기존 파티션이 자동으로 새 공간을 채우도록 확장되지 않을 수 있습니다. 이후 관리자는 추가 용량을 애플리케이션에서 사용할 수 있도록 파일 시스템 확장이나 재파티셔닝 작업을 수행해야 합니다(Linux에서는 `growpart`, Windows에서는 디스크 관리 유틸리티 같은 도구를 사용).

EBS 볼륨의 크기를 늘릴 수는 있지만 줄일 수는 없다는 점에 주의해야 합니다. 용량을 줄여야 한다면 더 작은 새 볼륨을 생성하고 그에 맞게 데이터를 마이그레이션해야 합니다.

### 4.4. 크기 조정 후 재파티셔닝

성공적인 크기 조정 작업 후 마지막이자 중요한 단계는 운영체제가 추가된 스토리지 용량을 인식하도록 보장하는 것입니다. 여기에는 일반적으로 다음이 포함됩니다.

- **새 볼륨 크기 감지:** 운영체제는 기반 디스크가 커졌다는 것을 알아야 합니다. Linux에서는 `lsblk`나 `fdisk` 같은 도구를 사용해 새 디스크 크기를 확인할 수 있습니다.
- **파티션 확장:** 파티셔닝 도구를 사용해 관리자는 새로 사용 가능해진 공간을 차지하도록 기존 파티션을 확장합니다. Linux 시스템에서는 `growpart` 명령이 이 목적으로 일반적으로 사용됩니다.
- **파일 시스템 확장:** 파티션이 확장된 후에는 파티션을 채우도록 파일 시스템 자체의 크기를 조정해야 합니다. Linux에서는 `resize2fs`(ext 파일시스템용)나 `xfs_growfs`(XFS용) 같은 명령이 사용됩니다. Windows에서는 디스크 관리 유틸리티가 유사한 역할을 수행합니다.

이 단계들을 완료하면 EC2 인스턴스가 새 용량을 완전히 활용할 수 있게 되어, 크기가 조정된 볼륨이 스토리지 계층에서는 더 커 보이지만 확장되지 않은 파일 시스템 때문에 활용도가 떨어지는 상황을 방지할 수 있습니다.

## 5. EBS 볼륨 유형

Amazon EBS는 비용 효율적인 범용 스토리지부터 고성능 미션 크리티컬 환경까지 각각 특정 워크로드 요구 사항을 다루도록 설계된 다양한 볼륨 유형을 제공합니다. 이 절에서는 각 볼륨 유형의 특성, 일반적인 사용 사례, 선택을 안내해야 할 핵심 요소를 자세히 살펴봅니다.

### 5.1. 범용 SSD(gp2, gp3)

gp2와 gp3로 제공되는 범용 SSD 볼륨은 다양한 워크로드에 대해 가격과 성능의 균형 잡힌 조합을 제공하도록 설계되었습니다. 이 볼륨들은 고급 스토리지 솔루션의 프리미엄 비용을 들이지 않으면서도 낮은 지연 시간과 일관된 성능이 필요한 애플리케이션의 기본 선택으로 자주 사용됩니다.

- **GP2 볼륨:** 전통적으로 gp2 볼륨은 성능(IOPS)을 볼륨 크기와 직접 연결합니다. 볼륨 크기가 커질수록 기준 성능도 증가하며, 짧은 시간 동안 더 높은 IOPS로 버스트할 수 있는 능력도 있습니다. 이 모델은 스토리지 요구가 증가함에 따라 적절한 성능 확장이 허용되는 워크로드에 이상적입니다.
- **GP3 볼륨:** 더 새로운 세대인 gp3 볼륨은 IOPS와 처리량을 볼륨 크기에서 분리합니다. 이러한 분리는 성능 파라미터를 독립적으로 구성할 수 있게 하여 더 큰 유연성과 비용 관리를 제공합니다. gp3에서는 기준으로 3,000 IOPS와 125MB/s의 처리량이 제공되며, 필요에 따라 최대 16,000 IOPS와 1,000MB/s까지 확장할 수 있습니다.

개발과 테스트 환경부터 비용 효율성이 핵심 요소인 프로덕션 워크로드까지, 대부분의 범용 애플리케이션에서 이 SSD 볼륨들은 성능과 가격 사이의 최적의 균형을 제공합니다.

### 5.2. 프로비저닝된 IOPS SSD(io1, io2)

높은 트랜잭션 데이터베이스나 지연 시간에 민감한 엔터프라이즈 애플리케이션처럼 지속적으로 높은 I/O 성능을 요구하는 애플리케이션에는 프로비저닝된 IOPS SSD 볼륨(io1과 io2)이 선호되는 선택입니다. 이 볼륨들은 필요한 정확한 IOPS를 지정할 수 있게 함으로써 예측 가능하고 고성능인 스토리지를 제공하도록 설계되었습니다.

- **IO1 볼륨:** 이 볼륨은 스토리지 크기와 독립적으로 IOPS를 프로비저닝할 수 있게 하여, gp2나 gp3 볼륨에서 제공되는 것 이상의 지속적이고 높은 IOPS가 필요한 워크로드에 적합합니다. 특정 구성에서 최대 64,000 IOPS를 지원하는 io1 볼륨은 미션 크리티컬 시스템을 위해 설계되었습니다.
- **IO2 볼륨:** io1의 개선 버전인 io2 볼륨(IO2 Block Express 변형 포함)은 성능과 확장성을 더욱 확장합니다. 더 큰 용량(최대 64TB)을 지원할 수 있으며, 서브 밀리초 지연 시간과 특정 구성에서 최대 256,000 IOPS에 이르는 최대 IOPS를 제공합니다. IO2 볼륨은 또한 클러스터 환경을 위한 개선된 내구성과 멀티어태치 기능의 혜택도 누릴 수 있습니다.

이 볼륨들은 중요한 데이터베이스 애플리케이션, 대규모 트랜잭션 시스템, 성능 변동성을 허용할 수 없는 워크로드에 이상적으로 적합합니다.

### 5.3. 처리량 최적화 HDD(st1)

빅데이터 애플리케이션, 로그 처리, 데이터 웨어하우징처럼 IOPS보다 처리량을 우선시하는 워크로드에는 처리량 최적화 HDD 볼륨(st1)이 비용 효율적인 솔루션을 제공합니다. St1 볼륨은 SSD 기반 옵션에 비해 기가바이트당 더 낮은 비용을 유지하면서 높은 순차 처리량을 제공하도록 설계되었습니다.

- **주요 특성:** St1 볼륨은 일반적으로 최대 500MB/s의 처리량을 제공하며, 대규모의 순차 데이터 전송이 일반적인 시나리오에 적합합니다.
- **사용 사례:** 배치 처리 시스템이나 로그 집계 플랫폼처럼 대량의 데이터를 스트리밍하는 애플리케이션은 st1 볼륨이 제공하는 비용 효율적인 성능의 혜택을 받을 수 있습니다.

### 5.4. 콜드 HDD(sc1)

콜드 HDD 볼륨(sc1)은 비용 최소화가 주된 관심사인, 자주 접근하지 않는 워크로드를 위해 설계되었습니다. 이 볼륨들은 아카이빙 데이터, 백업 스토리지, 그리고 높은 성능이 필요하지 않은 기타 시나리오에 이상적입니다.

- **주요 특성:** st1 볼륨에 비해 최대 처리량이 약 250MB/s로 낮고 IOPS도 낮은 sc1 볼륨은 성능보다 스토리지 비용에 최적화되어 있습니다.
- **사용 사례:** 장기 데이터 아카이빙, 자주 접근하지 않는 백업, 과거 데이터 저장과 같은 시나리오에 sc1 볼륨 유형이 적합합니다. 비용 절감의 대가로 데이터 검색 시 더 높은 지연 시간이 발생할 수 있습니다.

## 6. Multi-Attach 기능

Amazon EBS가 제공하는 더 정교한 기능 중 하나는 Multi-Attach 기능입니다. 전통적으로 EBS 볼륨은 한 번에 하나의 EC2 인스턴스로 제한됩니다. 하지만 multi-attach를 사용하면 특정 고성능 볼륨(구체적으로 io1과 io2 계열)을 동일한 가용 영역 내에서 최대 16개의 EC2 인스턴스에 동시에 연결할 수 있습니다.

- **기능:** Multi-Attach는 여러 EC2 인스턴스가 하나의 EBS 볼륨에 동시에 읽기·쓰기 접근을 할 수 있게 합니다. 이 기능은 공유 데이터 저장소가 필요한 클러스터 환경에서 특히 유용합니다.
- **운영상의 이점:** multi-attach를 활성화함으로써 조직은 애플리케이션 가용성을 높이고 분산 데이터 처리를 촉진할 수 있습니다. 예를 들어 공유 데이터베이스나 파일 시스템을 실행하는 클러스터형 Linux 환경에서, multi-attach는 여러 노드가 동일한 스토리지에 동시에 접근할 수 있게 하여 다운타임을 최소화합니다.

### 6.1. Multi-Attach의 사용 사례

Multi-Attach는 주로 고가용성과 동시 데이터 접근이 중요한 시나리오를 위한 것입니다. 일반적인 사용 사례는 다음과 같습니다.

- **클러스터형 파일 시스템:** 클러스터형 데이터베이스 시스템이나 컨테이너 오케스트레이션 플랫폼을 위한 공유 파일 스토리지처럼, 여러 클라이언트를 동시에 지원해야 하는 분산 파일 시스템이 필요한 애플리케이션은 multi-attach의 혜택을 받습니다.
- **고가용성 아키텍처:** 페일오버 속도가 필수적인 환경에서, multi-attach는 한 인스턴스가 실패해도 다른 인스턴스가 공유 볼륨에 저장된 중요 데이터에 대한 접근을 즉시 이어받을 수 있도록 보장합니다.
- **분산 애플리케이션:** 빅데이터 분석이나 대규모 시뮬레이션 환경처럼 여러 노드에 걸친 동시 데이터 처리를 포함하는 워크로드는 multi-attach를 활용해 데이터 중복을 줄이고 성능을 개선할 수 있습니다.

### 6.2. 제한 사항과 요구 사항

multi-attach 기능은 많은 가능성을 열어주지만, 중요한 제한 사항과 전제 조건도 함께 따릅니다.

- **볼륨 유형 제한:** Multi-attach는 io1과 io2 볼륨에서만 사용할 수 있습니다. 범용 및 HDD 볼륨은 이 기능을 지원하지 않습니다.
- **가용 영역 제약:** multi-attach 볼륨에 연결된 모든 EC2 인스턴스는 동일한 가용 영역 내에 있어야 합니다.
- **인스턴스 제한:** 하나의 multi-attach 볼륨에는 최대 16개의 EC2 인스턴스를 동시에 연결할 수 있습니다.

### 6.3. 파일 시스템 고려 사항

multi-attach나 다른 고급 볼륨 관리 전략을 구현할 때는 여러 소스로부터의 동시 읽기·쓰기 작업을 처리할 수 있는 파일 시스템을 선택하는 것이 필수적입니다. 클러스터 인식 파일 시스템은 여러 노드로부터의 접근을 관리하도록 설계되어 다음을 제공합니다.

- **데이터 무결성:** 동시 작업이 데이터 손상으로 이어지지 않도록 보장합니다.
- **잠금 메커니즘:** 분산 잠금이나 저널링을 통해 공유 데이터에 대한 접근을 조율합니다.
- **확장성:** 노드 전반에서 메타데이터와 데이터 분산을 효율적으로 관리합니다.

미션 크리티컬 애플리케이션에서 흔히 그렇듯, 성능과 신뢰성이 무엇보다 중요할 때 파일 시스템의 선택은 더욱 중요해집니다.

## 7. EBS 스냅샷

### 7.1. 스냅샷 생성과 관리

EBS 스냅샷은 EBS 볼륨의 특정 시점 백업입니다. 스냅샷은 Amazon S3에 저장되며 새 EBS 볼륨을 생성하는 데 사용할 수 있습니다. 주요 기능은 다음과 같습니다.

- **비파괴적 백업:** 볼륨이 연결되어 사용 중인 상태에서도 스냅샷을 생성할 수 있습니다. 일관성을 보장하기 위해 볼륨을 분리하는 것이 권장되지만, AWS는 라이브 스냅샷도 지원합니다.
- **증분 백업:** 최초 스냅샷 이후의 후속 스냅샷은 증분식이며, 마지막 스냅샷 이후 변경된 데이터 블록만 저장됩니다. 이 방식은 스토리지 비용을 최적화하고 백업 시간을 줄입니다.
- **자동화와 스케줄링:** AWS는 스냅샷의 생성과 관리를 자동화하는 API와 도구를 제공해, 정기 백업과 데이터 보존 정책 준수를 가능하게 합니다.

### 7.2. AZ 간 및 리전 간 기능

EBS 스냅샷의 중요한 이점 중 하나는 이동성입니다. 하나의 가용 영역에 한정된 EBS 볼륨과 달리, 스냅샷은 S3에 저장되어 어떤 AZ에서든, 심지어 다른 AWS 리전에서도 볼륨을 생성하는 데 사용할 수 있습니다. 이러한 유연성은 다음을 지원합니다.

- **재해 복구:** AZ 장애 발생 시 스냅샷을 사용해 다른 AZ나 리전에서 신속하게 데이터를 복원할 수 있습니다.
- **지리적 복제:** 조직은 규제 준수나 전 세계적으로 분산된 애플리케이션의 접근 지연 시간 개선을 위해 리전 전반에 중요한 데이터를 복제할 수 있습니다.
- **운영 유연성:** 스냅샷은 데이터 저장을 물리적 인프라로부터 분리시켜, 필요한 시점과 장소에 볼륨을 동적으로 프로비저닝할 수 있게 합니다.

### 7.3. EBS 스냅샷 아카이브

비용을 더욱 최적화하기 위해 AWS는 EBS 스냅샷을 위한 아카이브 티어를 제공합니다. 자주 접근하지 않는 스냅샷을 아카이브 티어로 이동시킴으로써 스토리지 비용을 최대 75%까지 줄일 수 있습니다. 다만 몇 가지 트레이드오프가 있습니다.

- **복원 지연 시간:** 아카이브 티어의 스냅샷은 완전히 복원되기까지 24~72시간이 걸릴 수 있습니다.
- **사용 사례 고려:** 이 티어는 거의 복원되지 않는 데이터, 예를 들어 과거 로그나 규제 백업의 장기 아카이빙에 이상적입니다.

### 7.4. 스냅샷을 위한 휴지통(Recycle Bin)

스냅샷의 실수로 인한 삭제는 심각한 결과를 초래할 수 있습니다. 이 위험을 완화하기 위해 AWS는 스냅샷용 휴지통 기능을 제공합니다.

- **실수로 인한 삭제 방지:** 삭제된 스냅샷은 즉시 완전히 삭제되지 않고 휴지통으로 이동됩니다.
- **구성 가능한 보존:** 휴지통 내 스냅샷의 보존 기간은 최소 1일부터 최대 1년까지 구성할 수 있어, 중요한 데이터에 대한 안전망을 제공합니다.
- **운영상의 복구:** 삭제가 의도적이지 않았던 경우 관리자는 휴지통에서 스냅샷을 복원할 수 있어 백업 전략의 연속성을 보장합니다.

### 7.5. 빠른 스냅샷 복원

Amazon EBS의 빠른 스냅샷 복원(Fast Snapshot Restore, FSR)은 생성 시점에 완전히 초기화된 볼륨을 스냅샷으로부터 만들 수 있게 하는 기능입니다. 즉, 표준 초기화 프로세스의 성능 영향이나 지연 시간 없이 즉시 완전한 성능을 제공합니다.

스냅샷으로부터 일반적인 EBS 볼륨을 생성할 때, 데이터는 Amazon S3로부터 지연 로딩됩니다. 즉, 블록은 처음 접근될 때만 가져옵니다. 이로 인해 모든 블록이 로드될 때까지 I/O 작업이 더 높은 지연 시간을 경험할 수 있는 "최초 접근 페널티"가 발생합니다.

빠른 스냅샷 복원이 활성화되면:

- 볼륨은 생성 시점에 완전히 초기화됩니다
- 데이터에 처음 접근할 때 성능 영향이 없습니다
- 애플리케이션은 데이터 로딩을 기다리지 않고 즉시 완전한 성능을 달성할 수 있습니다

![S3-Fast Snapshot Restore](@site/docs/Storage/_assets/s3-fast_snapshot_restore.png)

FSR은 특히 다음과 같은 경우에 유용합니다.

- 빠른 인스턴스 시작이 필요한 부트 볼륨
- 일관된 성능이 필요한 데이터베이스 워크로드
- 신속한 복구가 중요한 재해 복구 시나리오

FSR은 스냅샷과 가용 영역 단위로 구성되며, 가격은 일반적으로 FSR이 활성화된 용량-분(capacity minutes)을 기준으로 책정됩니다. 또한 FSR 혜택으로 동시에 생성할 수 있는 볼륨 수에는 제한이 있습니다.

## 8. 성능 최적화

EBS에서 최적의 성능을 얻으려면 IOPS, 처리량, 볼륨 크기, 비용을 신중하게 균형 잡아야 합니다. 이 절에서는 IOPS 관리, 처리량 고려 사항, 볼륨 선택 가이드라인, 성능 모니터링 모범 사례를 포함한 성능 최적화 전략을 살펴봅니다.

### 8.1. IOPS 관리

초당 I/O 작업 수(IOPS)는 특히 데이터베이스와 트랜잭션 처리를 포함하는 많은 애플리케이션에서 중요한 성능 지표입니다. 효과적인 IOPS 관리는 다음을 포함합니다.

- **충분한 IOPS 프로비저닝:** 미션 크리티컬 워크로드의 경우 필요한 성능을 보장하기 위해 프로비저닝된 IOPS 볼륨(io1/io2)을 사용합니다. gp3 볼륨에서는 IOPS를 독립적으로 구성할 수 있는 유연성이 있어 성능을 세밀하게 조정할 수 있습니다.
- **IOPS 사용률 모니터링:** 볼륨의 성능이 예상 임계값 내에 있는지 확인하기 위해 IOPS 사용량을 정기적으로 추적합니다. AWS CloudWatch와 기타 모니터링 도구는 IOPS 트렌드에 대한 인사이트를 제공하고 병목 현상을 감지하는 데 도움을 줄 수 있습니다.
- **성능과 비용의 균형:** IOPS는 요금에 직접 영향을 미치므로 필요한 만큼만 프로비저닝하는 것이 중요합니다. 워크로드 패턴에 맞춰 성능 파라미터를 동적으로 조정함으로써 비용을 최적화합니다.

### 8.2. 처리량 고려 사항

초당 메가바이트(MB/s)로 측정되는 처리량은, 특히 대규모 순차 데이터 전송을 포함하는 워크로드에서 또 다른 중요한 요소입니다.

- **적절한 볼륨 유형 선택:** 데이터 웨어하우징이나 미디어 스트리밍처럼 높은 처리량이 필요한 워크로드는 st1 볼륨(처리량 최적화 HDD)이나 처리량을 독립적으로 구성할 수 있는 gp3 볼륨을 고려해야 합니다.
- **워크로드 패턴 최적화:** 무작위 I/O 작업보다 더 높은 처리량을 달성할 수 있는 순차 I/O를 최대화하도록 애플리케이션을 설계합니다.
- **버스트 기능 활용:** 일부 볼륨 유형(gp2 등)은 짧은 시간 동안 버스트 성능을 제공합니다. 버스트 메커니즘을 이해하고 최대 성능과 기준 성능 요구 사항을 효과적으로 처리할 수 있도록 애플리케이션을 설계합니다.

### 8.3. 볼륨 선택 가이드라인

워크로드에 맞는 적절한 EBS 볼륨 유형을 선택하는 것은 비용, 성능, 신뢰성 사이의 균형을 달성하는 데 매우 중요합니다. 핵심 가이드라인은 다음과 같습니다.

- **워크로드 요구 사항 평가:** 워크로드가 IOPS에 종속적인지, 처리량에 종속적인지, 혹은 둘의 조합인지 이해합니다. 예를 들어 트랜잭션 데이터베이스는 높은 IOPS가 필요할 수 있고, 대용량 파일 전송은 높은 처리량의 혜택을 받습니다.
- **미래 성장 고려:** 데이터가 증가함에 따라 확장할 수 있는 볼륨 유형을 선택합니다. gp3 볼륨을 사용하면 볼륨 크기를 조정할 필요 없이 성능 파라미터를 조정할 수 있습니다.
- **비용 영향 검토:** 볼륨 유형 전반의 기가바이트당, 프로비저닝된 IOPS당 비용을 비교합니다. 많은 경우 성능 요구를 충족하는 약간 더 비싼 볼륨이 성능 병목을 피함으로써 전체 비용을 줄일 수 있습니다.

### 8.4. 성능 모니터링

일관된 성능 모니터링은 건강한 EBS 환경을 유지하는 핵심입니다.

- **AWS 모니터링 도구 활용:** AWS CloudWatch는 EBS 볼륨에 대해 IOPS, 처리량, 지연 시간, 버스트 밸런스 같은 지표를 제공합니다. 알람과 대시보드를 설정하면 성능 문제가 애플리케이션에 영향을 미치기 전에 알림을 받을 수 있습니다.
- **정기적인 검토 시행:** 볼륨 성능과 사용 패턴에 대한 주기적인 검토를 예약합니다. 이 선제적인 접근 방식은 예상되는 성능 저하에 앞서 조정할 수 있게 합니다.
- **벤치마킹과 테스트:** 특히 크기 조정이나 볼륨 유형 전환 같은 중요한 변경 이후에는 시스템이 요구되는 서비스 수준 목표를 충족하는지 확인하기 위해 정기적인 성능 테스트를 수행합니다.

## 9. 결론

Amazon EBS는 현대 애플리케이션이 요구하는 확장성, 내구성, 성능을 제공하는 AWS 내 기초적인 서비스로 자리잡고 있습니다. 이 장에서 설명한 기술적 세부 사항, 아키텍처 제약, 고급 기능을 이해함으로써 AWS 클라우드에서 견고한 스토리지 솔루션을 설계, 배포, 관리할 준비를 더 잘 갖출 수 있습니다.
