# Amazon S3
## 1. 소개

Amazon Simple Storage Service(Amazon S3)는 백업과 아카이빙부터 정적 웹사이트 호스팅과 데이터 레이크 구축까지 다양한 애플리케이션의 기반으로 전 세계 조직에서 사용하는, 매우 확장 가능하고 내구성이 뛰어나며 안전한 오브젝트 스토리지 서비스입니다. 이 장에서는 프로덕션 환경과 자격증 시험 모두에서 광범위하게 채택되는 기반이 되는 Amazon S3의 기본 개념, 기능, 아키텍처 원칙을 소개합니다.

## 2. S3 기본 사항

### 2.1. 주요 기능과 이점

AWS S3는 오브젝트 스토리지로서 선호되는 선택이 되도록 하는 여러 기능을 제공합니다.

- **내구성과 신뢰성:**
    S3에 저장된 모든 오브젝트는 99.999999999%(11 nines)라는 놀라운 내구성 등급의 혜택을 받습니다. 즉, 수백만 개의 오브젝트를 저장하더라도 예상 손실률은 수천 년에 걸쳐 통계적으로 무시할 수 있는 수준입니다.

- **확장성과 성능:**
    S3는 높은 요청률을 처리하도록 자동으로 확장되며, 프리픽스당 초당 수천 건의 요청을 지원하도록 성능이 설계되었습니다. 이 서비스는 낮은 지연 시간과 높은 처리량에 최적화되어 있어, 자주 접근하는 애플리케이션부터 아카이브 스토리지까지 광범위한 워크로드에 적합합니다.

- **비용 효율적인 스토리지:**
    사용한 만큼 지불하는 가격 모델과 다양한 스토리지 클래스를 통해 S3는 데이터 접근 패턴에 맞춰 성능과 비용을 조정할 수 있게 합니다. 라이프사이클 정책은 시간이 지남에 따라 클래스 간 전환을 자동화해 비용을 더욱 최적화하는 데 도움을 줍니다.

- **손쉬운 통합:**
    S3는 간단한 웹 서비스 인터페이스(RESTful API)를 통해 접근할 수 있으며 다른 AWS 서비스와 매끄럽게 통합됩니다. 이는 이벤트 기반 처리(Lambda 사용)와 안전한 콘텐츠 전송(CloudFront 사용) 같은 고급 워크플로를 촉진합니다.

- **보안과 규정 준수:**
    보안을 염두에 두고 구축된 S3는 버킷 정책, (전송 중과 저장 시 모두의) 암호화, 엄격한 규정 준수 요구 사항을 충족하는 데 도움을 주는 접근 제어 메커니즘 같은 기능을 지원합니다.

### 2.2. 버킷과 오브젝트

S3의 설계 핵심에는 버킷과 오브젝트가 있습니다.

![s3-Buckets and Objects](@site/docs/Storage/_assets/s3-buckets_and_objects.png)

- **버킷:**
    버킷은 오브젝트를 담는 S3의 최상위 컨테이너입니다. 주요 특성은 다음과 같습니다.
    - **전역적으로 고유한 이름:** 모든 버킷 이름은 모든 AWS 계정과 리전에 걸쳐 고유해야 합니다. 이는 버킷 이름이 전역 네임스페이스를 형성하도록 보장합니다.
    - **리전별 생성:** 버킷 이름은 전역적으로 고유하지만, 각 버킷은 특정 AWS 리전에서 생성되며 그 리전과 연관됩니다. 이 리전 배치는 지연 시간과 규제 준수에 영향을 미칩니다.
    - **명명 규칙:** 버킷 이름은 특정 규칙을 따라야 합니다.
        - 길이는 3자에서 63자 사이여야 합니다.
        - 소문자, 숫자, 하이픈만 허용됩니다.
        - IP 주소 형식으로 지정할 수 없습니다.
- **오브젝트:**
    오브젝트는 S3에 저장되는 기본 엔티티로 다음으로 구성됩니다.
    - **데이터(오브젝트 본문):** 어떤 유형의 데이터든 될 수 있는 파일의 실제 내용입니다.
    - **키(Key):** 버킷 내에서 오브젝트를 식별하는 고유 식별자입니다. 키는 본질적으로 오브젝트의 전체 "경로"입니다. S3는 진정한 계층적 파일 시스템을 사용하지 않지만, 구분자(일반적으로 슬래시 "/")를 사용하면 폴더처럼 보이는 형태를 만들 수 있습니다.
    - **메타데이터:** 오브젝트에는 시스템 정의 메타데이터(예: Content-Type, Content-Length)가 함께 제공되며 사용자 정의 메타데이터(커스텀 키-값 쌍)도 가질 수 있습니다.
    - **최대 오브젝트 크기:** 개별 오브젝트는 최대 5테라바이트까지 커질 수 있습니다.

### 2.3. S3 스토리지 클래스

AWS S3는 다양한 접근 패턴과 비용 요구 사항에 맞춘 여러 스토리지 클래스를 제공합니다. 각 클래스는 동일한 11 nines의 내구성을 제공하지만 가용성, 검색 시간, 가격에서 차이가 있습니다.

![S3 Storage Classes](@site/docs/Storage/_assets/s3_storage_classes.png)

- **S3 Standard – General Purpose:**
    자주 접근하는 데이터를 위해 설계되었으며 99.99% 가용성 SLA와 함께 낮은 지연 시간과 높은 처리량을 제공합니다. 사용 사례로는 동적 웹사이트, 모바일 및 게임 애플리케이션, 빅데이터 분석이 있습니다.

- **S3 Intelligent-Tiering:**
	이 클래스는 변화하는 접근 패턴에 따라 오브젝트를 티어 간에 자동으로 이동시킵니다. 오브젝트 사용량을 모니터링하고 스토리지 비용을 최적화함으로써 성능 영향 없이 비용을 절감합니다. 소액의 월별 모니터링 비용이 적용되지만 검색 요금은 없습니다.

- **S3 Standard-Infrequent Access(Standard-IA):**
    덜 자주 접근하지만 필요할 때 빠른 접근이 필요한 데이터를 위한 것입니다. Standard 클래스보다 저장 비용이 저렴하지만 검색 요금이 있습니다. 99.9% 가용성 SLA와 함께 재해 복구와 백업에 이상적입니다.

- **S3 One Zone-Infrequent Access(One Zone-IA):**
    비용 절감 측면에서는 Standard-IA와 유사하지만, 데이터가 단일 가용 영역에 저장됩니다. 이는 전체 영역 장애에 대한 복원력을 낮춥니다(99.5% 가용성). 보조 백업이나 쉽게 재생산할 수 있는 데이터에 적합합니다.

- **S3 Glacier 클래스:**
    이 클래스들은 장기 아카이빙과 백업에 최적화되어 있습니다.
    - **Glacier Instant Retrieval:** 거의 접근하지 않는 데이터에 대해 밀리초 단위의 검색 시간을 제공합니다. 최소 90일의 저장 기간이 필요합니다.
    - **Glacier Flexible Retrieval:** 여러 검색 옵션을 제공합니다.
        - **Expedited:** 1~5분 내 검색.
        - **Standard:** 3~5시간 내 검색.
        - **Bulk:** 5~12시간 내 검색(가장 저렴한 비용).
        - 최소 90일의 저장 기간이 적용됩니다.
    - **Glacier Deep Archive:** 거의 접근하지 않고 더 긴 검색 시간(일반적으로 12~48시간)을 감내할 수 있는 데이터를 위한 가장 저렴한 스토리지 옵션이며, 최소 180일의 저장 기간을 갖습니다.

### 2.4. S3 오브젝트 태그와 메타데이터

S3에서 오브젝트를 관리하는 것은 메타데이터와 태그의 사용을 통해 강화됩니다.

- **오브젝트 메타데이터:**
    오브젝트를 업로드할 때 키-값 쌍으로 구성된 메타데이터를 포함할 수 있습니다.
    - **시스템 정의 메타데이터:** S3가 자동으로 설정합니다(예: Content-Length, Content-Type).
    - **사용자 정의 메타데이터:** 사용자가 지정하는 커스텀 메타데이터입니다. 시스템 메타데이터와 구별하기 위해 키에는 `x-amz-meta-` 접두사가 붙어야 합니다.
        메타데이터는 오브젝트와 함께 읽을 수 있는, 오브젝트에 대한 정보(예: 출처, 형식, 커스텀 속성)를 전달하는 데 유용합니다.

- **오브젝트 태그:**
    태그는 오브젝트에 할당할 수 있는 추가적인 키-값 쌍입니다. 메타데이터와 달리 태그는 다음을 위한 것입니다.
    - **세밀한 접근 제어:** 태그를 사용해 태그 값을 기반으로 접근을 제한하는 버킷 정책을 강제할 수 있습니다.
    - **비용 할당과 분석:** 태그는 스토리지 비용을 분류하고 추적하거나 분석을 위해 오브젝트를 그룹화하는 데 도움이 될 수 있습니다.
    - **라이프사이클 관리:** 태그가 라이프사이클 규칙에 영향을 줄 수 있지만, 오브젝트 메타데이터나 태그 모두 S3 내에서 본질적으로 검색 가능하지는 않다는 점에 유의하세요. 메타데이터나 태그를 기반으로 검색을 수행하려면 외부 인덱스(예: DynamoDB 사용)를 유지해야 합니다.

## **3. S3 보안 프레임워크**

### 3.1. 퍼블릭 액세스 차단 설정

퍼블릭 액세스 차단 설정은 의도치 않은 데이터 노출을 방지하는 중요한 안전장치입니다. 이 설정은 버킷 정책이나 ACL이 퍼블릭 접근을 허용하도록 구성되어 있더라도 이를 무효화하기 위해 버킷과 계정 수준 모두에서 적용됩니다.

- **목적:**
    버킷 정책이 퍼블릭 읽기 또는 쓰기 접근을 허용하도록 구성되어 있더라도 버킷이 비공개 상태를 유지하도록 보장함으로써 데이터 유출을 방지하기 위해 설계되었습니다.

- **구성 옵션:**
    개별 버킷 단위로 퍼블릭 액세스 차단 설정을 활성화하거나 비활성화할 수 있으며, 관리자는 계정 내 모든 버킷에 이 설정을 강제할 수 있습니다.

- **모범 사례:**
    민감한 데이터를 저장하는 대부분의 경우, 퍼블릭 접근에 대한 "기본 거부" 태세를 강제하기 위해 이 설정을 활성화된 상태로 유지하는 것이 권장됩니다.

### 3.2. 버킷 정책

버킷 정책은 버킷 수준에서 세밀한 접근 제어를 정의할 수 있게 하는 JSON 기반 리소스 정책입니다. S3 보안의 핵심 구성 요소이며 다양한 조건에 따라 권한을 부여하거나 제한하는 데 사용됩니다.

#### 버킷 정책의 주요 기능

- **리소스 지정:**
    정책은 버킷과 오브젝트의 ARN을 지정해 접근 범위를 정의합니다(예: 버킷 내 모든 오브젝트를 참조하기 위해 `"arn:aws:s3:::example-bucket/*"` 사용).

- **정책 효과:**
    정책 내 명문(statement)은 `"Effect"`로 `"Allow"` 또는 `"Deny"`를 가질 수 있으며, 지정된 작업이 허용되는지 여부를 결정합니다.

- **조건:**
    HTTPS를 강제하기 위한 `aws:SecureTransport`, IP 주소나 VPC 엔드포인트로 접근을 제한하기 위한 `aws:SourceIp`나 `aws:SourceVpce`, 업로드 시 암호화를 강제하기 위한 `s3:x-amz-server-side-encryption` 같은 다른 키 같은 조건 키를 사용합니다.

#### 샘플 S3 버킷 정책

일반적인 버킷 정책 패턴의 몇 가지 예시는 다음과 같습니다.

- **모든 요청에 HTTPS 강제:**

    ```json
    {
        "Version": "2012-10-17",
        "Statement": [
            {
                "Sid": "DenyNonSecureTransport",
                "Effect": "Deny",
                "Principal": "*",
                "Action": "s3:*",
                "Resource": [
                    "arn:aws:s3:::example-bucket",
                    "arn:aws:s3:::example-bucket/*"
                ],
                "Condition": {
                    "Bool": {
                        "aws:SecureTransport": "false"
                    }
                }
            }
        ]
    }
    ```

- **특정 IP 주소로 접근 제한:**

    ```json
    {
        "Version": "2012-10-17",
        "Statement": [
            {
                "Sid": "IPAllow",
                "Effect": "Allow",
                "Principal": "*",
                "Action": "s3:GetObject",
                "Resource": "arn:aws:s3:::example-bucket/*",
                "Condition": {
                    "IpAddress": {
                        "aws:SourceIp": "203.0.113.0/24"
                    }
                }
            }
        ]
    }
    ```

- **SSE-KMS를 위한 특정 KMS 키 사용 강제:**

    ```json
    {
        "Version": "2012-10-17",
        "Statement": [
            {
                "Sid": "EnforceKMSEncryption",
                "Effect": "Deny",
                "Principal": "*",
                "Action": "s3:PutObject",
                "Resource": "arn:aws:s3:::example-bucket/*",
                "Condition": {
                    "StringNotEquals": {
                        "s3:x-amz-server-side-encryption": "aws:kms"
                    }
                }
            }
        ]
    }
    ```

### 3.3. 인가 평가 프로세스

Amazon S3의 인가 프로세스는 S3 요청을 허용할지 거부할지 결정하기 위해 여러 계층의 정책을 평가하는 과정을 포함합니다. 이 프로세스를 이해하는 것은 접근 문제를 해결하고 안전한 아키텍처를 설계하는 데 매우 중요합니다.

#### 다층 평가

1. **사용자 컨텍스트(IAM 정책):**
    요청이 이루어지면 요청 주체(사용자나 역할)에 연결된 IAM 정책이 먼저 평가됩니다. 이 정책들은 S3 작업에 대한 기본 권한을 결정합니다.

2. **버킷 컨텍스트(버킷 정책):**
    다음으로 대상 버킷과 연관된 버킷 정책이 평가됩니다. 이 정책은 추가 권한을 부여하거나 사용자의 IAM 정책을 무효화하는 제한(명시적 거부 등)을 강제할 수 있습니다.

3. **오브젝트 컨텍스트(오브젝트 ACL):**
    마지막으로, 오브젝트가 버킷 소유자와 다른 계정이 소유한 경우 오브젝트의 접근 제어 목록(ACL)이 평가됩니다. 다만 버킷 소유자 강제 설정의 등장으로, 보안 모델을 단순화하기 위해 ACL은 흔히 비활성화됩니다.

#### 추가 고려 사항

- **명시적 거부:**
    어느 단계에서든 명시적 거부가 발견되면 요청은 즉시 거부됩니다.

- **버킷 대 오브젝트 수준 권한:**
    버킷에 대한 작업(예: 오브젝트 목록 조회)은 오브젝트에 대한 작업(예: 파일 검색)과 다릅니다. 버킷 정책은 이러한 차이를 반영하기 위해 리소스 범위를 (뒤에 `/*`를 붙이거나 붙이지 않는 방식으로) 명확하게 구분해야 합니다.

- **인가 단순화:**
    AWS는 복잡성을 최소화하기 위해 버킷 정책을 사용하고 버킷 소유자 제어를 강제하는 것을 권장합니다. 이 접근 방식은 ACL에 대한 의존도를 줄이고 평가 프로세스를 간소화합니다.

### 3.4. 계정 간 접근과 캔드 ACL

S3에서 계정 간 접근은 한 AWS 계정의 사용자가 다른 계정의 버킷이나 오브젝트에 접근할 수 있게 합니다. 이를 안전하게 활성화하는 여러 방법이 있습니다.

#### 계정 간 접근 방법

- **IAM 정책과 버킷 정책:**
    가장 일반적인 방법은 요청 계정의 IAM 정책과 대상 버킷의 버킷 정책을 조합해 접근을 부여하는 것입니다. 버킷 정책은 다른 계정의 주체에 의한 작업을 명시적으로 허용할 수 있습니다.

- **IAM 역할:**
    대상 계정에 IAM 역할을 생성해 외부 사용자가 이를 수임(assume)함으로써 S3 버킷에 대한 임시 접근을 얻을 수 있습니다. 이 방법은 복잡한 버킷 정책을 구성할 필요를 없애줍니다.

#### 오브젝트 소유권과 캔드 ACL

- **오브젝트 소유권 설정:**
    계정 간 접근을 단순화하기 위해, AWS는 이제 버킷 내 모든 오브젝트가 자동으로 버킷 소유자가 소유하도록 하는 버킷 소유자 강제 설정을 사용하는 것을 권장합니다. 이는 오브젝트 수준 ACL로 인한 복잡성을 방지합니다.

- **캔드 ACL:**
    ACL이 여전히 사용되는 경우(예: 버킷 소유자 강제가 비활성화된 경우), "캔드 ACL"은 지름길을 제공합니다. 예를 들어 오브젝트 업로드 시 `x-amz-acl: bucket-owner-full-control` 헤더를 추가하면 해당 오브젝트에 대한 완전한 권한을 버킷 소유자에게 부여합니다. ACL은 레거시 접근 방식으로 간주되지만, 레거시 시스템과 시험 시나리오에서는 여전히 이를 이해하는 것이 중요합니다.

### 3.5. 사전 서명된 URL

사전 서명된 URL(Pre-signed URL)은 버킷의 전체 접근 정책을 변경하지 않고도 비공개 S3 오브젝트에 대한 임시 접근을 부여하는 방법을 제공합니다. 이 URL은 서드파티나 웹 애플리케이션이 안전하게 파일을 다운로드하거나 업로드할 수 있게 하고 싶을 때 특히 유용합니다.

![S3-Pre-signed URLs](@site/docs/Storage/_assets/s3-pre-signed_urls.png)

#### 주요 특성

- **임시 접근:**
    사전 서명된 URL은 만료 시간(기본값은 1시간이지만 SDK나 CLI를 통해 커스터마이징 가능)이 지나면 무효화됩니다.

- **권한 상속:**
    사전 서명된 URL과 연관된 권한은 해당 URL을 생성한 AWS 주체의 권한입니다. 예를 들어 읽기 권한을 가진 사용자가 GET 작업을 위한 사전 서명된 URL을 생성하면, URL을 가진 누구든 동일한 권한을 가진 것처럼 오브젝트에 접근할 수 있습니다.

- **사용 사례:**
    - **다운로드:** 사용자가 비공개 버킷에서 프리미엄 콘텐츠를 임시로 다운로드할 수 있게 허용합니다.
    - **업로드:** 클라이언트가 더 넓은 쓰기 권한을 부여하지 않고 특정 위치에 파일을 업로드할 수 있게 허용합니다.

- **생성:**
    사전 서명된 URL은 AWS SDK, AWS CLI, 또는 S3 콘솔(기간에 제한이 있음)을 통해 생성할 수 있습니다.

### 3.6. S3 접근 로그

S3 접근 로그는 S3 버킷에 대해 이루어진 요청의 상세한 기록을 제공합니다. 이 로그는 감사, 규정 준수, 포렌식 조사에 필수적입니다.

![S3 Access Logs](@site/docs/Storage/_assets/s3_access_logs.png)

#### 접근 로깅의 주요 측면

- **로그 내용:**
	각 로그 레코드에는 요청자의 신원, 요청 시간, 수행된 작업, 반환된 HTTP 상태 코드 같은 요청에 대한 세부 정보가 포함됩니다. 이는 누가 버킷 내 오브젝트에 접근하거나 수정했는지 추적하는 데 도움이 됩니다.

- **전달:**
	접근 로그는 대상 S3 버킷에 파일로 기록됩니다. 대상 로깅 버킷은 리전 간 데이터 전송 문제를 피하기 위해 소스 버킷과 동일한 리전에 있어야 합니다.

- **성능 고려 사항:**
	로깅은 최선 노력(best-effort) 기반으로 수행됩니다. 로그 전달에는 지연(몇 분에서 몇 시간까지)이 있을 수 있으며, 로그가 때때로 불완전할 수 있습니다.

- **모범 사례:**
    - **별도의 로깅 버킷:**
        접근 로그에 사용되는 대상 버킷이 로깅되는 버킷과 동일하지 않도록 보장합니다. 이는 로깅 행위가 추가 로그를 생성하는 로깅 루프를 방지합니다.
    - **분석 도구:**
        접근 패턴과 보안 감사에 대한 인사이트를 위해 로그 데이터를 쿼리하고 분석하는 Amazon Athena 같은 도구를 사용합니다.

## 4. S3의 데이터 보호

### 4.1 S3 암호화 메커니즘

Amazon S3는 저장 데이터를 암호화하는 여러 방법을 제공합니다. 이 메커니즘들은 스토리지 매체가 손상되더라도 적절한 키 없이는 내용을 읽을 수 없도록 보장함으로써 데이터를 보호하는 데 도움을 줍니다.

#### 서버 측 암호화(SSE)

세 가지 주요 서버 측 암호화 옵션이 있습니다.

- **SSE-S3(S3 관리형 키를 사용한 서버 측 암호화):**
    SSE-S3에서는 Amazon S3가 암호화 키를 내부적으로 관리함으로써 전체 암호화 프로세스를 처리합니다. 오브젝트를 업로드할 때 단순히
    `x-amz-server-side-encryption: AES256`
    헤더를 포함하면 S3가 AES-256을 사용해 데이터를 자동으로 암호화합니다. 이 방법은 많은 신규 버킷에서 기본적으로 활성화되어 있으며 키 관리를 위한 고객의 개입이 필요하지 않습니다.

- **SSE-KMS(AWS KMS 관리형 키를 사용한 서버 측 암호화):**
    SSE-KMS는 AWS Key Management Service(KMS)와 통합해 추가적인 제어를 제공합니다. SSE-KMS를 지정하면(헤더
    `x-amz-server-side-encryption: aws:kms`
    를 포함하고 선택적으로
    `x-amz-server-side-encryption-aws-kms-key-id`
    를 통해 특정 키 ID를 지정), S3는 KMS 키를 사용해 오브젝트를 암호화합니다. SSE-KMS의 장점은 다음과 같습니다.

    - **감사 가능성:** KMS 키의 모든 사용은 AWS CloudTrail에 로깅되어 규정 준수와 감사 요구 사항을 지원합니다.
    - **세밀한 접근 제어:** IAM 정책을 사용해 데이터에 대한 접근뿐만 아니라 기반 KMS 키를 사용하는 권한도 통제할 수 있습니다.
    - **추가적인 보안 오버헤드:** 클라이언트는 암호화와 복호화 작업을 수행하기 위해 권한(예: `kms:GenerateDataKey`)을 가지고 있어야 합니다.

    다만 데이터 키를 생성하거나 복호화하는 각 API 호출은 KMS API 할당량에 포함된다는 점에 유의하세요.

- **SSE-C(고객이 제공한 키를 사용한 서버 측 암호화):**
    SSE-C는 자신의 암호화 키를 관리할 수 있게 합니다. 이 모드에서는 각 PUT과 GET 요청(HTTPS를 통해)마다 암호화 키를 제공하고, S3는 사용자의 키를 사용해 오브젝트를 암호화 또는 복호화합니다. S3는 사용자의 키를 저장하지 않으며, 해당 작업 동안에만 일시적으로 사용됩니다. 이 방법은 매 작업마다 키를 안전하게 관리하고 전송해야 합니다.

#### 클라이언트 측 암호화

클라이언트 측 암호화에서는 데이터가 Amazon S3에 업로드되기 전에 클라이언트에서 암호화됩니다. 암호화 키는 전적으로 사용자의 통제 아래 있으며, 다운로드 후 클라이언트 측에서 복호화가 이루어집니다. 이 방법은 AWS 서비스와 독립적으로 암호화 프로세스와 키 관리를 완전히 통제하고자 할 때 유용합니다.

#### 전송 중 암호화

여기서는 저장 데이터에 초점을 맞추고 있지만, Amazon S3도 전송 중 암호화를 지원한다는 점에 유의해야 합니다. S3는 클라이언트와 S3 사이의 데이터가 SSL/TLS를 사용해 암호화되도록 HTTPS 엔드포인트를 제공합니다. 버킷 정책은 (`aws:SecureTransport` 조건을 통해) 모든 요청에 HTTPS 사용을 강제하도록 구성할 수 있습니다.

### 4.2 S3 기본 암호화

기본 암호화는 각 요청마다 암호화 파라미터를 지정할 필요 없이 버킷에 업로드되는 모든 오브젝트가 자동으로 암호화되도록 보장할 수 있게 합니다.

- **기본 동작:**
    버킷에서 기본 암호화가 활성화되면 새 오브젝트마다 자동으로 암호화됩니다. 기본적으로 S3는 SSE-S3 암호화를 적용하지만, 규정 준수나 보안 정책이 AWS KMS를 통해 키를 관리하도록 요구한다면 이 설정을 SSE-KMS로 변경할 수 있습니다.

- **버킷 정책을 통한 강제:**
    기본 암호화 설정 외에도 버킷 정책을 사용해 업로드 시 암호화를 강제할 수 있습니다. 예를 들어 적절한 암호화 헤더(SSE-S3, SSE-KMS, 또는 SSE-C 여부와 관계없이)를 포함하지 않는 모든 PUT 오브젝트 요청을 거부하는 정책을 구성할 수 있습니다. 중요한 점은, 버킷 정책이 기본 암호화 설정보다 먼저 평가되어 적절히 암호화된 오브젝트만 저장되도록 보장한다는 것입니다.

### 4.3 S3 버킷 키

SSE-KMS 암호화 사용을 더욱 최적화하기 위해 Amazon S3는 **S3 버킷 키** 기능을 제공합니다.

![S3 Bucket Key](@site/docs/Storage/_assets/s3_bucket_key.png)

- **목적과 이점:**
	SSE-KMS를 사용할 때, 각 오브젝트 업로드는 일반적으로 데이터 키를 생성하기 위해 AWS KMS에 대한 API 호출이 필요합니다. 처리량이 높은 워크로드의 경우 이는 많은 수의 KMS 요청을 초래해 지연 시간과 비용을 모두 증가시킬 수 있습니다. S3 버킷 키는 Amazon S3가 버킷 수준에서 데이터 키를 생성하고 캐싱할 수 있게 합니다. 이후의 암호화는 매 오브젝트 업로드마다 KMS에 추가 호출을 하지 않고도 이 버킷 키를 사용해 오브젝트를 암호화할 수 있습니다.

- **비용과 성능 최적화:**
    버킷 키를 사용하면 KMS API 호출 수를 최대 99%까지 줄일 수 있어, 비용을 크게 낮추고 KMS 작업과 관련된 CloudTrail 로그 이벤트를 줄일 수 있습니다. 이 접근 방식은 동일한 수준의 보안을 유지하면서도 대규모 암호화 작업의 성능을 최적화합니다.

버킷 키 설정은 버킷 단위로 S3 콘솔에서 활성화하거나 비활성화할 수 있습니다. 활성화되면 S3는 애플리케이션 로직 변경 없이도 버킷 키를 사용한 봉투 암호화(envelope encryption)를 투명하게 처리합니다.

### 4.4 S3 배치 작업을 사용한 배치 암호화

S3에 이미 저장된 다수의 오브젝트를 업데이트하거나 암호화해야 하는 상황을 위해 Amazon S3는 **S3 Batch Operations**를 제공합니다.

- **대량 처리:**
    S3 Batch Operations는 암호화 설정 업데이트 같은 대량 작업을 기존 S3 오브젝트에 대해 수행할 수 있게 합니다. 이는 암호화되지 않은 오브젝트가 있는 레거시 버킷이 있고, 각 오브젝트를 개별적으로 재업로드하지 않고도 암호화를 강제하고 싶을 때 특히 유용합니다.

- **워크플로 개요:**
    1. **인벤토리와 식별:** S3 Inventory를 사용해 암호화 상태를 포함한 메타데이터와 함께 오브젝트 목록을 생성합니다.
    2. **필터링:** Amazon Athena 같은 도구로 인벤토리 보고서를 처리해 암호화 업데이트가 필요한 오브젝트를 식별합니다.
    3. **배치 작업 잡:** 각 오브젝트의 암호화 설정을 업데이트하는(예: SSE-KMS로 다시 암호화) S3 Batch Operations 잡에 오브젝트 목록을 제출합니다.

- **전제 조건:**
    배치 잡은 버킷을 읽고 쓰는 데 적절한 권한을 가지고 있어야 하며, SSE-KMS 암호화가 적용되는 경우 KMS 키를 사용할 권한도 포함해야 합니다.

S3 Batch Operations를 사용하면 다운타임이나 수동 개입 없이 대량의 오브젝트에 대해 암호화를 강제하는 과정을 간소화할 수 있습니다.

### 4.5 S3 오브젝트 잠금과 Glacier Vault Lock

규정 준수와 법적 요구 사항을 위해 Amazon S3는 오브젝트가 저장된 후 삭제나 수정을 방지하는 메커니즘을 제공합니다. 이 기능들은 WORM(Write Once Read Many) 모델을 가능하게 합니다.

#### S3 오브젝트 잠금

- **목적:**
    S3 오브젝트 잠금은 개별 오브젝트에 WORM 정책을 강제할 수 있게 합니다. 오브젝트 잠금이 적용되면 오브젝트 버전은 지정된 보존 기간 동안 덮어쓰기나 삭제로부터 보호됩니다.

- **보존 모드:**
    - **Compliance 모드:** 이 모드에서는 보존 기간이 엄격하게 강제됩니다. 버킷 소유자나 루트 사용자를 포함한 어떤 사용자도 보존 기간이 만료되기 전까지 잠긴 오브젝트 버전을 삭제하거나 변경할 수 없습니다.
    - **Governance 모드:** 이 모드는 더 많은 유연성을 제공합니다. 오브젝트는 대부분의 사용자로부터 삭제 보호를 받지만, 권한이 부여된 사용자(일반적으로 특별한 관리 권한을 가진 사용자)는 필요할 경우 보존 설정을 재정의할 수 있습니다.

- **법적 보류(Legal Hold):**
    또한 오브젝트에 법적 보류를 걸 수 있습니다. 시간 기반 보존과 달리 법적 보류는 설정된 보존 기간과 관계없이 보류가 명시적으로 해제될 때까지 오브젝트를 무기한 보호합니다.

#### Glacier Vault Lock

- **목적:**
    Glacier Vault Lock은 Amazon S3 Glacier 내 아카이브 수준에서 유사한 WORM 개념을 적용합니다. Glacier 볼트에 Vault Lock 정책을 생성하고 잠금으로써, 해당 볼트에 아카이빙된 오브젝트가 변경되거나 삭제될 수 없도록 보장합니다. 정책이 잠기면 수정할 수 없으므로, 장기 보존과 규제 준수를 위한 견고한 메커니즘을 제공합니다.

S3 오브젝트 잠금과 Glacier Vault Lock 모두 엄격한 데이터 보존 정책을 준수해야 하고 데이터가 변조되지 않았음을 증명해야 하는 조직에 중요합니다.

### 4.6 S3 MFA 삭제

특히 버전 관리가 활성화된 버킷에서 오브젝트의 실수로 인한 삭제나 악의적인 삭제에 대한 추가적인 보호 계층을 추가하기 위해 Amazon S3는 **MFA Delete** 기능을 제공합니다.

- **MFA Delete란?**
    MFA(다중 인증) Delete는 특정 파괴적인 작업을 수행할 때 두 번째 형태의 인증(일반적으로 물리적 또는 가상 MFA 장치에서 생성된 일회용 코드)을 제공하도록 요구합니다.

- **MFA Delete는 언제 필요한가?**
    MFA Delete는 다음의 경우 필요합니다.
    - 특정 오브젝트 버전을 영구적으로 삭제할 때.
    - 버킷의 버전 관리 상태를 변경할 때(예: 버전 관리 일시 중지).

- **구현 고려 사항:**
    - MFA Delete는 AWS 루트 계정을 사용하는 버킷 소유자만 활성화하거나 비활성화할 수 있습니다.
    - 영구 삭제에 MFA를 요구함으로써 실수로 인한 데이터 손실과 잠재적인 악의적 작업의 위험을 줄입니다.
    - 활성화되면 영구 삭제나 버전 관리 중지를 초래할 수 있는 모든 API 호출은 유효한 MFA 인증을 포함해야 합니다.

MFA Delete는 데이터 무결성이 무엇보다 중요하고 저장된 데이터의 삭제에 대한 엄격한 통제가 필요한 환경에서 특히 중요합니다.

## 5. 고급 접근 제어

### 5.1. S3 접근 지점

S3 접근 지점(Access Points)은 대규모의 다양한 데이터셋을 포함하는 S3 버킷에 대한 접근 관리를 단순화하도록 설계되었습니다. 모든 오브젝트에 적용되는 하나의 단일화된 버킷 정책을 유지하는 대신, 특정 애플리케이션이나 사용자 그룹에 맞춘 정책을 가진 여러 접근 지점을 만들 수 있습니다.

![S3 Access Points](@site/docs/Storage/_assets/s3_access_points.png)

**주요 기능:**

- **세밀한 접근 제어:**
	각 접근 지점은 종종 프리픽스(예: `/finance/`나 `/sales/`)를 강제함으로써 오브젝트의 부분 집합에 대한 접근을 제한할 수 있습니다. 이는 서로 다른 부서나 애플리케이션이 필요한 데이터만 다룰 수 있게 합니다.

- **단순화된 정책 관리:**
	세부적인 접근 규칙을 버킷 정책에서 개별 접근 지점 정책으로 오프로드함으로써 전체적인 보안 관리가 크게 단순화됩니다. 예를 들어 다음과 같이 구성할 수 있습니다.
	- `/finance` 프리픽스 아래의 오브젝트에 대해서만 배타적으로 읽기·쓰기 권한을 부여하는 _finance 접근 지점_.
	- `/sales` 프리픽스에 대해서만 접근을 허용하는 자체 정책을 가진 _sales 접근 지점_.
	- 여러 데이터셋에 대해 읽기 전용 권한을 가진 _analytics 접근 지점_.

- **고유한 DNS 엔드포인트:**
	각 접근 지점에는 고유한 DNS 이름이 할당됩니다. 클라이언트는 버킷 전체의 정책을 관리할 필요 없이 이 DNS 이름을 사용해 S3 데이터에 접근합니다.

- **VPC 통합:**
	접근 지점은 퍼블릭 인터넷에서 오는 트래픽이나 Virtual Private Cloud(VPC)에서만 오는 트래픽을 받도록 설정할 수 있습니다. VPC 내에서 사용될 때는 데이터가 프라이빗 AWS 네트워크에 남아 있도록 보장하기 위해 VPC 엔드포인트와 함께 사용되는 경우가 많습니다.


S3 접근 지점을 구현함으로써 조직은 최소 권한의 원칙을 효율적으로 강제하고 대규모의 복잡한 버킷 전반에 걸쳐 보안 관리를 확장할 수 있습니다.

### 5.2. S3 Multi-Region 접근 지점

S3 Multi-Region 접근 지점은 서로 다른 AWS 리전에 분산된 여러 S3 버킷에 걸친 단일한 전역 엔드포인트를 제공합니다. 이 아키텍처는 저지연 전역 접근, 강화된 복원력, 단순화된 리전 간 관리가 필요한 애플리케이션에 이상적입니다.

![S3 Multi-Region Access Points](@site/docs/Storage/_assets/s3_multi-region_access_points.png)

**주요 구성 요소와 이점:**

- **통합된 전역 엔드포인트:**
	여러 리전 엔드포인트를 관리하는 대신, 클라이언트는 하나의 전역 엔드포인트와 상호작용합니다. 이 엔드포인트는 요청을 가장 잘 처리할 수 있는 리전의 S3 버킷으로 동적으로 라우팅합니다. 일반적으로 지연 시간이 가장 낮은 리전으로 라우팅됩니다.

- **동적 라우팅과 페일오버:**
	이 시스템은 액티브/액티브와 액티브/패시브 구성을 모두 지원합니다. 액티브/패시브 설정에서는 하나의 버킷이 주(primary)로 지정되고 보조 버킷은 리전 장애 발생 시 백업 역할을 합니다.

- **양방향 복제:**
	S3는 복제 규칙을 통해 리전 전반의 데이터 동기화를 보장합니다. 한 버킷에 작성된 데이터는 다른 버킷으로 비동기적으로 복제되어 다중 리전 접근 지점 전반의 일관성을 유지합니다.

- **단순화된 데이터 관리:**
	통합된 엔드포인트를 사용하면 개발자와 관리자는 여러 버킷 이름과 리전별 구성을 다루는 복잡함을 피할 수 있습니다.

이 솔루션은 데이터 가용성, 지연 시간, 재해 복구가 중요한 전역 애플리케이션에 특히 유용합니다.

### 5.3. S3 Object Lambda

S3 Object Lambda는 동일한 데이터의 여러 버전을 저장할 필요 없이, 검색되는 시점에 S3 오브젝트를 즉석에서 변환할 수 있게 합니다. 이 기능은 AWS Lambda를 활용해 오브젝트 데이터를 요청자에게 반환하기 전에 처리합니다.

**일반적인 사용 사례:**

- **데이터 마스킹:**
    분석 애플리케이션은 민감한 정보를 제거한 문서의 마스킹된 버전에 대한 접근이 필요할 수 있습니다. S3 Object Lambda는 Lambda 함수를 호출해 개인식별정보(PII)를 동적으로 제거할 수 있습니다.

- **데이터 강화:**
    강화된 콘텐츠를 다른 버킷에 중복 저장하는 대신, Lambda 함수를 사용해 (예: 로열티 데이터베이스의 고객 데이터 같은) 정보를 즉석에서 추가함으로써 마케팅 애플리케이션에 강화된 오브젝트를 제공할 수 있습니다.

- **형식 변환과 변환:**
    데이터가 소비되기 전에 오브젝트 형식을 변환(예: XML을 JSON으로)하거나 크기 조정이나 워터마킹 같은 이미지 처리 작업을 수행합니다.


**아키텍처 개요:**

![S3 Object Lambda](@site/docs/Storage/_assets/s3_object_lambda.png)

1. **접근 지점과의 통합:**
    S3 Object Lambda 접근 지점은 기존 S3 버킷 위에 생성되며 Lambda 함수와 연관됩니다.
2. **온디맨드 변환:**
    이 접근 지점을 통해 GET 요청이 이루어지면 Lambda 함수가 요청을 가로채서 원본 오브젝트를 검색하고, 필요한 변환을 수행한 다음, 수정된 오브젝트를 반환합니다.
3. **매끄러운 클라이언트 경험:**
    클라이언트는 여러 저장된 복사본을 관리할 필요 없이 비즈니스 규칙에 따라 동적으로 수정된 버전의 오브젝트를 받습니다.

이 접근 방식은 스토리지 중복을 최소화하면서도 유연하고 실시간에 가까운 데이터 변환 기능을 제공합니다.

### 5.4. VPC 엔드포인트 전략

Virtual Private Cloud(VPC) 내에서 Amazon S3에 안전하고 프라이빗하게 접근하기 위해 AWS는 두 가지 주요 엔드포인트 옵션을 제공합니다: 게이트웨이 엔드포인트와 인터페이스 엔드포인트입니다. 이 엔드포인트들은 데이터 트래픽이 AWS 네트워크 내에 남아 있도록 보장하여 퍼블릭 인터넷에 대한 노출을 줄여줍니다.

**VPC 게이트웨이 엔드포인트:**

- **비용 효율적이고 단순함:**
    게이트웨이 엔드포인트는 무료이며 VPC의 라우팅 테이블과 직접 통합됩니다. 완전히 VPC 내에 위치한 리소스를 위해 설계되었습니다.
- **트래픽 격리:**
    VPC에서 나오는 S3 트래픽이 인터넷을 통과하지 않도록 보장해 보안을 강화합니다.
- **제한 사항:**
    이 엔드포인트는 VPC 내에서만 접근할 수 있으며 온프레미스 환경으로부터의 연결에는 사용할 수 없습니다.

**VPC 인터페이스 엔드포인트(AWS PrivateLink):**

- **강화된 연결성:**
    인터페이스 엔드포인트는 서브넷에 Elastic Network Interface(ENI)를 배포해, VPC 리소스와 온프레미스 네트워크 모두에서 Direct Connect나 VPN을 통해 S3에 안전하게 접근할 수 있게 합니다.
- **보안 제어:**
    ENI에 보안 그룹을 연결하고 엔드포인트 정책을 통해 세밀한 접근을 강제할 수 있습니다.
- **비용 고려 사항:**
    이 엔드포인트는 가용 영역당 시간 요금이 부과되며 게이트웨이 엔드포인트에 비해 추가적인 구성이 필요합니다.

**정책 통합:**
버킷 정책은 `aws:SourceVpc`나 `aws:SourceVpce` 같은 조건을 사용해 특정 VPC나 VPC 엔드포인트에서 시작된 요청으로 접근을 더 세밀하게 제한할 수 있습니다.

올바른 VPC 엔드포인트 전략을 선택하는 것은 네트워크 아키텍처와 연결 요구 사항에 따라 달라지며, S3에 대한 접근이 안전하면서도 효율적이도록 보장합니다.

### 5.5. 잠긴 S3 버킷에 대한 접근 재확보

버킷 정책의 잘못된 구성은 관리자를 포함한 모든 사용자가 S3 버킷에 접근할 수 없도록 실수로 차단할 수 있습니다. 흔한 시나리오로는 모든 주체에 대해 모든 S3 작업을 거부하는 광범위한 거부 규칙을 설정해 버킷과의 모든 상호작용을 효과적으로 차단하는 경우가 있습니다.

**복구 전략:**

- **루트 사용자 활용:**
    제한적인 버킷 정책에도 불구하고 AWS 계정의 루트 사용자는 이러한 거부 대상이 아닙니다. 루트 사용자는 버킷 정책을 수정하거나 삭제할 수 있는 능력을 유지합니다.

- **접근을 재확보하기 위한 단계:**
    1. **루트 사용자로 로그인:**
        계정의 루트 자격 증명을 사용해 AWS Management Console에 접근합니다.
    2. **문제가 되는 정책 수정 또는 제거:**
        접근을 차단하고 있는 과도하게 제한적인 정책을 식별하고 그에 따라 삭제하거나 조정합니다.
    3. **안전하게 재구성:**
        접근을 재확보한 후, 향후 실수로 인한 잠김을 방지하기 위해 모범 사례(예: 특정 조건 사용, 필요한 권한만 부여)를 따르는 수정된 정책을 구현합니다.

- **예방 조치:**
    버킷 정책을 정기적으로 감사하고 테스트하며, 이러한 시나리오를 피하기 위해 변경 알림이나 정책 시뮬레이션 같은 안전장치 구현을 고려합니다.

## 6. 데이터 관리 기능

### 6.1. S3 버전 관리

S3 버전 관리는 동일한 버킷 내에서 오브젝트의 여러 변형을 유지함으로써 데이터를 보호하는 데 도움을 주는 강력한 기능입니다. 버전 관리가 활성화되면, 모든 업데이트나 삭제 작업은 원본을 영구적으로 덮어쓰거나 제거하는 대신 새로운 오브젝트 버전을 생성합니다.

![S3 Versioning](@site/docs/Storage/_assets/s3_versioning.png)

**주요 사항:**

- **의도하지 않은 삭제로부터 보호:**
	버전 관리를 활성화하면 실수로 인한 삭제나 덮어쓰기로부터 데이터를 보호할 수 있습니다. 오브젝트를 삭제하면 Amazon S3는 이전 버전을 제거하지 않고 대신 나중에 제거해 이전 버전을 복원할 수 있는 삭제 마커를 추가합니다.

- **이력 기록과 롤백:**
    오브젝트가 수정될 때마다 새 버전이 생성됩니다. 이를 통해 필요한 경우 오브젝트의 이전 상태로 되돌릴 수 있습니다. 버전 관리가 활성화되기 전에 업로드된 오브젝트는 버전 ID가 `null`입니다.

- **관리 고려 사항:**
	버전 관리는 데이터 보호 계층을 추가하지만 이전 버전의 관리도 필요합니다. 스토리지 비용을 제어하기 위해 버전 관리를 라이프사이클 규칙(6.3절 참고)과 결합해 이전 버전을 만료시키거나 전환할 수 있습니다.

- **모범 사례:**
	버킷을 생성하는 즉시 버전 관리를 활성화하여 이후의 모든 수정 사항이 버전 관리되도록 권장됩니다. 버전 관리가 활성화되면 모든 업데이트나 삭제가 추가 버전을 생성하며, 이전 버전이 무기한 유지되면 요금에 영향을 줄 수 있다는 점을 주의해야 합니다.

### 6.2. S3 복제

S3 복제(Replication)는 동일한 리전 내에서든 다른 리전 간에든 버킷 사이에서 오브젝트를 자동으로 비동기적으로 복사하도록 설계되었습니다. 이 기능은 데이터 가용성을 높일 뿐만 아니라 규정 준수, 재해 복구, 전역 접근 사용 사례도 지원합니다.

**주요 사항:**

- **복제 유형:**
    - **리전 간 복제(CRR):** 오브젝트를 다른 AWS 리전의 버킷으로 복제합니다. 이는 지리적 중복성, 원거리 사용자를 위한 지연 시간 감소, 규제 요구 사항 충족에 유용합니다.
    - **동일 리전 복제(SRR):** 동일한 AWS 리전 내에서 오브젝트를 복제합니다. SRR은 일반적으로 로그를 통합하거나 프로덕션을 그대로 반영하는 테스트 환경을 유지하는 데 사용됩니다.

- **전제 조건:**
    복제는 소스와 대상 버킷 모두에서 버전 관리가 활성화되어야 합니다. 또한 Amazon S3에 소스에서 읽고 대상 버킷에 쓸 수 있는 필요한 IAM 권한을 부여해야 합니다.

- **복제 동작:**
    기본적으로 새 오브젝트만 복제됩니다. 기존 오브젝트를 복제해야 한다면 S3 Batch Replication을 활용해 이미 저장된 오브젝트의 복제를 시작할 수 있습니다.

- **추가 고려 사항:**
    복제 규칙을 구성해 삭제 마커를 포함시키고, 선택적으로 프리픽스나 태그를 기반으로 특정 오브젝트를 제외할 수 있습니다. 이러한 유연성은 특정 비즈니스 요구에 맞춰 복제를 조정할 수 있게 합니다.

#### 6.2.1. S3 Replication Time Control
Amazon S3 Replication Time Control(S3 RTC)은 대부분의 오브젝트를 몇 초 안에 복제하고 99.99%의 오브젝트가 업로드 후 15분 이내에 복제되도록 보장함으로써 예측 가능한 복제 지연 시간을 제공하는 S3 복제 기능입니다. S3 RTC는 데이터 복제 타임라인에 대한 가시성과 제어를 제공함으로써 규정 준수나 비즈니스 요구 사항을 충족하는 데 도움을 주도록 설계되었습니다.

##### 서비스 수준 계약
S3 RTC는 청구 월 동안 99.9%의 오브젝트를 15분 이내에 복제하겠다는 서비스 수준 계약(SLA)의 지원을 받습니다.

##### 내장 모니터링과 알림
- **복제 지표**: 기본적으로 S3 RTC는 S3 복제 지표를 활성화하며, Amazon CloudWatch를 통해 대기 중인 작업, 대기 중인 총 크기, 최대 복제 시간, 실패를 거의 실시간으로 추적할 수 있습니다
- **이벤트 알림**: 두 가지 특별한 S3 이벤트 알림 — `OperationMissedThreshold`(복제가 15분을 초과할 때)와 `OperationReplicatedAfterThreshold`(임계값 이후 복제가 완료될 때) — 을 발생시키며, SQS, SNS, Lambda를 통해 전달됩니다

##### 구성과 전제 조건
- **복제 규칙**: S3 Management Console, AWS CLI, SDK, API에서 복제 규칙에 S3 RTC를 활성화합니다. 규칙은 전체 버킷, 특정 프리픽스, 또는 특정 태그를 가진 오브젝트에 적용할 수 있습니다.
- **버전 관리 요구 사항**: 소스와 대상 버킷 모두 버전 관리가 활성화되어 있어야 합니다. 버전 관리 없이는 복제(따라서 RTC)가 작동할 수 없습니다.
- **권한**: 복제에 사용되는 IAM 역할은 S3에 필요한 권한(예: `s3:GetObject`, `s3:ReplicateObject`, 그리고 오브젝트 잠금 시나리오의 경우 `s3:GetObjectLegalHold`와 `s3:GetObjectRetention`)을 부여해야 합니다

##### 가격 고려 사항
S3 RTC는 표준 복제를 넘어서는 추가 요금이 부과됩니다.
- **데이터 전송 요금**: Replication Time Control 데이터 전송에 대해 GB당 $0.015.
- **지표 요금**: S3 복제 지표는 표준 커스텀 지표 요율로 Amazon CloudWatch 커스텀 지표로 청구됩니다


### 6.3. S3 라이프사이클 규칙

Amazon S3의 라이프사이클 규칙은 시간이 지남에 따른 오브젝트 관리를 자동화합니다. 이 규칙들은 오브젝트를 스토리지 클래스 간에 전환하고 궁극적으로 더 이상 필요하지 않은 오브젝트를 만료(삭제)시켜 스토리지 비용을 최적화하고 데이터 관리를 단순화하는 데 도움을 줍니다.

![S3 Lifecycle Rules](@site/docs/Storage/_assets/s3_lifecycle_rules.png)

**주요 사항:**

- **전환 작업:**
    오브젝트의 나이를 기반으로 한 스토리지 클래스에서 다른 클래스로 자동 전환하는 규칙을 구성할 수 있습니다. 예를 들어 자주 접근하는 데이터는 Standard 클래스에 있다가 60일 후 Standard-Infrequent Access(Standard-IA)로, 또는 아카이빙을 위해 6개월 후 Glacier 티어로 전환될 수 있습니다.

- **만료 작업:**
    라이프사이클 규칙은 지정된 기간이 지나면 오브젝트를 영구적으로 삭제하는 만료 작업도 지원합니다. 이는 임시 파일(예: 로그 파일)이나 오래된 백업을 관리하는 데 특히 유용합니다.

- **불완전한 멀티파트 업로드 중단:**
    남겨진 파트가 스토리지를 소비하는 것을 방지하기 위해, 지정된 일수 내에 완료되지 않은 멀티파트 업로드를 중단하는 규칙을 정의할 수 있습니다.

- **프리픽스나 태그로 필터링:**
    라이프사이클 규칙은 버킷 내 모든 오브젝트에 적용하거나 특정 프리픽스나 특정 태그를 가진 오브젝트로 범위를 좁힐 수 있습니다. 이 세밀함은 동일한 버킷 내의 다양한 데이터 부분 집합에 맞춰 규칙을 조정할 수 있게 합니다.

- **비용 최적화:**
    오브젝트를 더 저비용 스토리지 클래스로 전환하거나 더 이상 필요하지 않을 때 삭제함으로써, 라이프사이클 규칙은 수동 개입 없이 스토리지 비용을 통제하는 데 도움을 줍니다.

### 6.4. S3 Analytics

S3 Analytics는 버킷에 저장된 오브젝트의 사용량 데이터와 접근 패턴을 수집하는 기능입니다. 스토리지 전략을 최적화하고 비용 효율적인 라이프사이클 정책을 설계하는 데 도움이 되는 인사이트를 제공합니다.

**주요 사항:**

- **사용량과 접근 패턴 분석:**
    S3 Analytics는 오브젝트가 얼마나 자주 접근되는지 모니터링하며, 더 저렴한 스토리지 클래스로 전환할 후보인 오브젝트를 식별하는 데 도움을 줄 수 있습니다.

- **보고서 생성:**
    분석 데이터는 매일 업데이트되는 보고서로 집계됩니다. 초기 분석이 나타나는 데는 일반적으로 24~48시간이 걸립니다.

- **시각화 도구와의 통합:**
    S3 Analytics 데이터를 Amazon QuickSight와 통합해 스토리지 사용 패턴에 대한 더 깊은 이해를 제공하는 대시보드와 시각화를 만들 수 있습니다.

- **실행 가능한 인사이트:**
    이 분석은 오브젝트를 전환하기에 "적절한 시점"을 결정하는 데 도움을 줍니다. 이 정보는 성능 요구 사항을 충족하면서도 오브젝트가 비용 효율적으로 저장되도록 라이프사이클 규칙을 설정할 때 매우 유용합니다.

### 6.5. Storage Class Analysis

S3 Analytics와 흔히 혼용되어 언급되는 Storage Class Analysis는 특히 오브젝트 접근 패턴을 평가해 스토리지 클래스 간 오브젝트 전환에 대한 권장 사항을 제공하는 데 초점을 맞춥니다.

**주요 사항:**

- **목적과 이점:**
    Storage Class Analysis는 오브젝트가 얼마나 자주 접근되는지 조사하고, 오브젝트가 Standard 클래스에 남아 있어야 하는지 또는 Standard-IA로 이동해야 하는지 권장할 수 있습니다. 이는 자주 접근하지 않는 데이터를 자동으로 더 저비용 티어로 이동시켜 비용 절감을 달성하는 데 매우 중요합니다.

- **보고서 세부 사항:**
    이 분석은 접근 빈도와 오브젝트 나이 같은 스토리지 지표를 요약한 CSV 보고서를 생성합니다. 이 보고서는 라이프사이클 정책을 세밀하게 조정하고 데이터가 가장 적절하고 비용 효율적인 스토리지 클래스에 저장되도록 보장하는 데 사용할 수 있습니다.

- **범위와 제한 사항:**
    이 분석은 Standard와 Standard-IA 클래스에 저장된 오브젝트에 대해 작동하도록 설계되었습니다. One Zone-IA나 Glacier 같은 스토리지 클래스에는 적용되지 않습니다. 이 제한을 이해하면 현실적인 기대치를 설정하고 데이터 관리 전략을 계획하는 데 도움이 됩니다.

- **실용적인 사용:**
    Storage Class Analysis의 인사이트는 자주 접근되지 않는 데이터를 더 저비용 스토리지 옵션으로 이동시킴으로써 비용을 줄이는 선제적인 라이프사이클 전환을 구현할 수 있게 해줍니다.

## 7. S3 성능 최적화

Amazon S3는 거의 무한한 확장성과 높은 내구성으로 유명합니다. 하지만 사용량이 확장됨에 따라 — 특히 처리량이 높은 애플리케이션에서 — 기준 성능 특성과 워크로드에 맞춰 S3를 최적화하기 위한 모범 사례를 이해하는 것이 중요해집니다. 이 절에서는 S3 성능의 기본 사항을 살펴보고, 주요 성능 모범 사례를 설명하며, KMS 암호화를 사용할 때 대용량 파일 업로드에 대한 특별 고려 사항을 논의하고, 전송 속도를 높이기 위한 S3 Transfer Acceleration의 사용을 검토합니다.

### 7.1. S3 성능 기본 사항

Amazon S3는 대규모 요청률을 자동으로 처리하도록 엔지니어링되어 있습니다. 기본적으로 S3는 다음을 지원하도록 확장됩니다.

- **쓰기 작업:** 프리픽스당 초당 최대 **3,500건의 PUT/COPY/POST/DELETE 요청**.
- **읽기 작업:** 프리픽스당 초당 최대 **5,500건의 GET/HEAD 요청**.

**프리픽스 이해하기:**
S3 오브젝트의 키(전체 이름)는 개념적으로 "프리픽스"와 "오브젝트 이름"으로 나눌 수 있습니다. 프리픽스는 키에서 마지막 구성 요소(예: 폴더 구조) 이전에 오는 부분입니다. S3 성능은 프리픽스별로 확장됩니다. 즉, 오브젝트가 여러 프리픽스에 분산되어 있다면 더 높은 총 요청률을 달성할 수 있습니다. 예를 들어 오브젝트를 `/folder1/sub1/`과 `/folder1/sub2/` 프리픽스 아래에 저장한다면, 각 프리픽스는 독립적인 성능 제한을 갖습니다.

버킷 내 프리픽스 수에는 상한이 없기 때문에, 적절한 키 설계를 통해 프리픽스당 제한을 훨씬 넘어서는 요청 처리량으로 확장할 수 있습니다.

### 7.2. 성능 모범 사례

S3에서 최적의 성능을 달성하려면 다음 모범 사례를 고려하세요.

1. **키 이름을 신중하게 설계:**
    - 어떤 단일 프리픽스도 병목이 되지 않도록 오브젝트를 여러 프리픽스에 분산시킵니다.
    - 데이터를 자연스럽게 "샤딩"하는 명명 규칙을 사용합니다(예: 프리픽스에 날짜나 무작위 구성 요소 포함).

2. **대용량 오브젝트에는 멀티파트 업로드 활용:**
    - 100MB보다 큰 파일의 경우 Amazon은 멀티파트 업로드 사용을 권장합니다.
    - 5GB를 초과하는 파일은 _반드시_ 멀티파트 업로드를 사용해 업로드해야 합니다.
    - **이점:**
        - **병렬 처리:** 파일을 파트로 나누어 동시에 업로드해 사용 가능한 대역폭을 최대화합니다.
        - **복원력:** 한 파트가 실패해도 전체 파일이 아니라 해당 파트만 다시 시도합니다.
        - **재조립:** 모든 파트가 업로드되면 S3가 자동으로 이를 최종 오브젝트로 재조립합니다.

3. **효율적인 다운로드를 위한 바이트 범위 가져오기 활용:**
    - 대용량 오브젝트의 경우 클라이언트는 특정 바이트 범위를 병렬로 요청해 전체 다운로드 시간을 앞당길 수 있습니다.
    - 바이트 범위 요청을 사용하면 필요한 파일 부분만(예: 헤더 정보만) 검색할 수 있어 불필요한 데이터 전송을 줄이고 성능을 개선합니다.

이러한 모범 사례를 신중한 아키텍처 설계와 결합하면 S3 기반 애플리케이션의 처리량과 응답성을 최대화할 수 있습니다.

### 7.3. KMS 키를 사용한 대용량 파일 업로드

보안 요구 사항에 따라 대용량 오브젝트를 AWS KMS를 사용한 서버 측 암호화(SSE-KMS)로 암호화해야 하는 경우, 추가적인 성능 고려 사항이 발생합니다.

1. **멀티파트 업로드에서의 암호화 오버헤드:**
    - SSE-KMS를 사용하면 멀티파트 업로드의 각 파트가 KMS에서 생성된 데이터 키를 사용해 암호화됩니다.
    - S3가 파트를 재조립할 때 최종 오브젝트를 재암호화하기 전에 데이터 키를 복호화하기 위해 KMS를 호출해야 합니다.
    - 이 프로세스는 추가적인 API 호출과 지연 시간을 발생시킵니다.

2. **필요한 권한:**
    - 표준 S3 권한 외에도, 업로드하는 엔티티는 업로드와 재조립 프로세스를 성공적으로 완료하기 위해 적절한 KMS 권한(예: **kms:GenerateDataKey**와 **kms:Decrypt**)을 가지고 있어야 합니다.
    - 이러한 권한을 포함하지 않으면 재조립 중 불완전한 업로드나 오류가 발생할 수 있습니다.

3. **S3 버킷 키를 사용한 최적화:**
    - 빈번한 KMS API 호출과 관련된 성능 영향과 비용을 완화하기 위해 Amazon S3는 **S3 버킷 키**를 제공합니다.
    - 버킷 키를 활성화하면 S3는 보안을 저해하지 않으면서도 KMS에 대한 호출 수를 종종 최대 99%까지 줄여줍니다.
    - 이 접근 방식은 봉투 암호화를 활용하는데, 하나의 S3 버킷 키가 여러 데이터 키를 암호화하는 데 사용되어 대용량 파일 업로드 시 지연 시간과 비용을 낮춥니다.

대규모 파일 업로드에 SSE-KMS를 사용하려면 보안과 성능 목표가 모두 충족되도록 신중한 계획이 필요합니다. IAM 정책을 적절히 설계하고, 대규모로 운영할 때는 S3 버킷 키 활성화를 고려하세요.

### 7.4. S3 Transfer Acceleration

클라이언트가 S3 버킷의 리전에서 지리적으로 멀리 떨어진 애플리케이션의 경우, **S3 Transfer Acceleration**은 AWS의 글로벌 엣지 네트워크를 활용해 지연 시간을 줄이고 전송 속도를 개선하는 방법을 제공합니다.

![S3 Transfer Acceleration](@site/docs/Storage/_assets/s3_transfer_acceleration.png)

1. **동작 방식:**
    - Transfer Acceleration이 활성화되면 데이터는 먼저 클라이언트에서 가까운 AWS 엣지 위치로 전송됩니다.
    - 엣지 위치로부터 데이터는 고속의 프라이빗 AWS 네트워크를 통해 대상 리전의 S3 버킷으로 전달됩니다.
    - 이 프로세스는 데이터가 퍼블릭 인터넷을 통해 이동하는 거리를 줄여, 특히 장거리에서 업로드와 다운로드 성능을 개선합니다.

2. **호환성과 사용 사례:**
    - S3 Transfer Acceleration은 멀티파트 업로드와 호환되어, 대용량, 암호화, 또는 멀티파트 오브젝트에 대한 성능을 동시에 최적화할 수 있습니다.
    - 다양한 지리적 위치의 사용자가 S3 오브젝트에 빠르게 접근해야 하는 전역 애플리케이션에 특히 유용합니다.
    - 일반적인 사용 사례로는 미디어 콘텐츠 전송, 글로벌 백업, 분산된 사용자 기반을 가진 애플리케이션이 있습니다.

3. **비용 고려 사항:**
    - Transfer Acceleration은 전송 성능을 크게 개선할 수 있지만, 엣지 위치를 통해 전송되는 데이터를 기준으로 추가 비용이 발생합니다.
    - 특정 애플리케이션 요구 사항에 대해 비용과 성능 개선 사이의 트레이드오프를 평가하세요.

## 8. 이벤트 기반 S3 아키텍처

이벤트 기반 아키텍처는 시스템이 상태 변화나 특정 이벤트의 발생에 실시간으로 반응할 수 있게 합니다. Amazon S3를 사용하면 버킷을 모니터링해 오브젝트의 생성, 삭제, 복원 같은 이벤트를 감지하고 수동 개입 없이 다운스트림 처리를 트리거할 수 있습니다. 이 기능은 동적 이미지 처리, 메타데이터 인덱싱, 실시간 분석, 자동화된 워크플로 같은 다양한 사용 사례를 가능하게 합니다.

S3 이벤트 알림은 이 아키텍처의 기반입니다. 캡처할 S3 이벤트, (프리픽스나 접미사 필터를 사용해) 오브젝트 키 패턴을 기준으로 이를 필터링하는 방법, 이 알림을 보낼 대상을 지정할 수 있게 합니다. S3 이벤트 알림의 대상으로는 Amazon SNS, Amazon SQS, AWS Lambda, 그리고 Amazon EventBridge와의 통합을 통해 18개 이상의 AWS 서비스 대상이 있습니다. 다음 절에서는 이 메커니즘들을 자세히 살펴봅니다.

### 8.1. S3 이벤트 알림

Amazon S3 이벤트 알림은 버킷을 모니터링하고 특정 이벤트가 발생할 때 자동으로 메시지를 게시하는 메커니즘을 제공합니다. 이 절에서는 핵심 개념, 지원되는 이벤트 유형, 필터링 옵션, 전달 특성을 다룹니다.

#### 지원되는 이벤트와 사용 사례

S3는 다음을 포함한 다양한 이벤트에 대해 알림을 발생시킬 수 있습니다.

- **오브젝트 생성:** 새 오브젝트가 추가될 때 트리거됩니다(예: PUT, POST, COPY 작업을 통해).
    _사용 사례:_ 이미지가 업로드될 때 썸네일을 자동으로 생성합니다.
- **오브젝트 제거:** 오브젝트가 삭제될 때 트리거됩니다.
- **오브젝트 복원:** (Glacier에 저장된 것 같은) 아카이빙된 오브젝트가 복원될 때 발생합니다.
- **복제 이벤트:** 오브젝트가 버킷 간에 복제될 때 생성됩니다.

이 알림들은 변화에 자동으로 반응하는 워크플로를 구축할 수 있게 합니다. 예를 들어 새 파일의 메타데이터를 인덱싱하거나, 바이러스 스캔을 트리거하거나, 데이터 변환을 시작할 수 있습니다.

#### 필터링과 구성

이벤트 알림을 설정할 때는 특정 이벤트만 다운스트림 처리를 트리거하도록 필터를 정의할 수 있습니다. 두 가지 일반적인 필터는 다음과 같습니다.

- **프리픽스 필터링:** 특정 "폴더"나 키 경로(예: `images/`) 내의 오브젝트만 알림을 생성하도록 지정합니다.
- **접미사 필터링:** 특정 파일 확장자(예: `.jpeg`)를 가진 오브젝트로 알림을 제한해, 특정 유형의 파일만 처리를 트리거하도록 보장합니다.

이 알림들은 비동기적으로 전달되도록 설계되어 있으며, 일반적으로 몇 초 내에 전달되지만 경우에 따라 최대 1분까지 걸릴 수 있습니다.

#### 알림 대상

S3 알림은 다음과 같은 여러 대상 서비스 중 하나로 직접 전송될 수 있습니다.

- **Amazon SNS:** 팬아웃 메시징과 브로드캐스트 패턴을 위해.
- **Amazon SQS:** 신뢰할 수 있고 분리된 처리를 위해 이벤트를 대기시킵니다.
- **AWS Lambda:** 즉각적인 처리를 위해 서버리스 함수를 트리거합니다.
- **Amazon EventBridge:** (JSON 규칙을 사용한) 고급 필터링, 재생 기능, 18개 이상의 AWS 서비스 대상과의 통합을 제공합니다.

알림 대상을 SNS, SQS, 또는 Lambda로 구성할 때는 대상 서비스의 리소스 기반 정책이 S3가 이를 호출할 수 있는 권한을 부여하는지 확인해야 합니다.

### 8.2. Lambda와 S3 이벤트 알림

AWS Lambda는 S3 이벤트 알림의 자연스러운 파트너입니다. 이 절에서는 S3 이벤트가 Lambda 함수를 트리거하는 방법, 일반적으로 사용되는 처리 패턴, 오류 처리와 신뢰성을 위한 모범 사례를 살펴봅니다.

#### 통합 개요

S3 이벤트(예: 오브젝트 생성)가 발생하고 알림 필터와 일치하면, Amazon S3는 AWS Lambda 함수를 비동기적으로 호출할 수 있습니다. Lambda에 전달되는 이벤트 페이로드에는 다음과 같은 중요한 메타데이터가 포함됩니다.

- 버킷 이름.
- 오브젝트 키.
- 이벤트 유형(예: 오브젝트 생성 또는 삭제).
- 버전 관리가 활성화된 경우 추가 컨텍스트.

이 페이로드는 Lambda 함수가 다음을 수행할 수 있게 합니다.

- **오브젝트 검색과 처리:** 예를 들어 썸네일 이미지를 생성하거나 파일을 파싱해 메타데이터를 추출합니다.
- **추가 작업 시작:** 데이터베이스 업데이트, 알림 전송, 추가 워크플로 트리거 등.

#### 사용 사례와 패턴

S3 이벤트 알림과 함께 Lambda를 사용할 때의 일반적인 패턴은 다음과 같습니다.

- **미디어 처리:** Lambda 함수가 업로드 시 이미지 크기를 자동으로 조정하거나 비디오를 변환합니다.
- **메타데이터 추출:** 검색이나 분석을 위해 DynamoDB 테이블에 오브젝트 메타데이터를 추출하고 저장합니다.
- **데이터 변환:** Lambda를 사용해 다운스트림 소비자에게 전달하기 전에 오브젝트의 내용을 수정합니다(예: 민감한 정보 마스킹).
- **Object Lambda(고급):** 관련 패턴으로, S3 Object Lambda는 GET 요청을 가로채 Lambda 함수를 사용해 오브젝트를 즉석에서 변환할 수 있게 합니다. 동일한 기반 데이터의 다른 뷰를 제시하고 싶을 때 유용합니다(예: 마스킹된 버전과 강화된 버전).

#### 모범 사례

- **버전 관리 활성화:** 동일한 오브젝트에 대한 여러 쓰기 작업이 올바르게 캡처되도록 보장해 알림 누락을 방지하는 데 도움이 됩니다.
- **데드레터 큐(DLQ) 구성:** Lambda 함수의 실패를 원만하게 처리하기 위해 DLQ를 설정합니다.
- **리소스 정책:** Lambda 함수의 리소스 정책이 S3에 의한 호출 권한을 부여하는지 확인합니다.
- **스테이트리스 설계:** 재시도가 의도치 않은 부작용을 일으키지 않도록 Lambda 함수를 스테이트리스하고 멱등적으로 설계합니다.

### 8.3. 이벤트 기반 애플리케이션 구축

#### 분리와 확장성

이벤트 기반 아키텍처는 각 서비스가 특정 작업을 처리하도록 구성 요소를 분리할 수 있게 합니다.

- **이벤트 소스로서의 S3:** S3에 업로드된 오브젝트는 처리 파이프라인의 시작점 역할을 하는 이벤트를 트리거합니다.
- **처리를 위한 Lambda:** Lambda 함수는 데이터 검증, 변환, 라우팅 같은 작업을 수행할 수 있습니다.
- **다른 서비스와의 통합:** 다운스트림 서비스(SNS, SQS, EventBridge, Step Functions)는 결과를 추가로 처리, 오케스트레이션, 또는 저장할 수 있습니다.

이러한 분리는 아키텍처를 단순화할 뿐만 아니라 확장성도 개선합니다. 예를 들어 시스템은 S3 이벤트가 급증할 때 동시 Lambda 실행 수를 자동으로 확장할 수 있습니다.

#### 아키텍처 예시

1. **썸네일 생성 워크플로:**
    - **이벤트 트리거:** S3에서 이미지 파일에 대한 오브젝트 생성 이벤트.
    - **Lambda 처리:** Lambda 함수가 트리거되어 이미지의 여러 크기를 생성합니다.
    - **저장과 알림:** 크기가 조정된 이미지는 다른 S3 버킷에 저장되고, SNS를 통해 알림이 전송되어 다운스트림 시스템에 처리가 완료되었음을 알립니다.

2. **메타데이터 인덱싱 파이프라인:**
    - **이벤트 트리거:** 새 데이터 파일 업로드에 대한 S3 이벤트.
    - **Lambda 함수:** 파일을 처리해 주요 메타데이터를 추출한 다음 DynamoDB 테이블에 메타데이터를 씁니다.
    - **검색과 분석:** 인덱싱된 메타데이터는 효율적인 검색을 가능하게 하고 분석 대시보드를 구동하거나 추가 워크플로를 트리거하는 데 사용될 수 있습니다.

3. **S3 Object Lambda를 사용한 실시간 데이터 변환:**
    - **이벤트 트리거와 요청 가로채기:** S3 오브젝트에 대한 클라이언트 요청이 S3 Object Lambda 접근 지점에 의해 가로채집니다.
    - **Lambda 변환:** Lambda 함수는 클라이언트에게 반환하기 전에 오브젝트 내용을 즉석에서 수정합니다(예: 민감한 정보 마스킹이나 데이터 형식 변환).
    - **단일 진실 소스:** 원본 오브젝트(한 애플리케이션에서 사용)와 변환된 오브젝트(다른 애플리케이션에서 사용) 모두 동일한 S3 버킷에서 제공되어 데이터 관리를 단순화합니다.

#### EventBridge를 사용한 고급 이벤트 라우팅

S3 이벤트 알림을 Amazon EventBridge와 통합함으로써 다음을 얻을 수 있습니다.

- **고급 필터링:** 이벤트 세부 정보(오브젝트 크기, 메타데이터, 또는 커스텀 속성 등)를 검사해 라우팅을 결정하는 규칙을 만듭니다.
- **다중 대상:** 하나의 S3 이벤트를 워크플로 오케스트레이션을 위한 Step Functions나 실시간 분석을 위한 Kinesis Data Streams 같은 여러 AWS 서비스로 전송합니다.
- **이벤트 재생:** EventBridge는 이벤트를 아카이빙하고 재생할 수 있게 해, 이벤트 기반 워크플로의 감사와 디버깅에 유용합니다.

#### 설계 고려 사항

S3로 이벤트 기반 애플리케이션을 구축할 때는 다음을 고려하세요.

- **신뢰성:** Lambda 함수에서 재시도, DLQ, 멱등적 처리를 사용해 간헐적인 실패를 처리합니다.
- **보안:** 승인된 서비스만 이벤트를 트리거하고 처리할 수 있도록 리소스 정책이 올바르게 구성되어 있는지 확인합니다.
- **모니터링:** CloudWatch 지표와 로그를 활용해 이벤트 알림과 처리 함수의 성능을 모니터링합니다.
- **비용 최적화:** S3 이벤트 알림은 추가 비용 없이 제공되는 내장 기능이므로, 다운스트림 서비스(예: Lambda 실행 시간)를 최적화하는 데 집중해 비용을 통제하세요.

## 9. S3 비용 관리

### 9.1. AWS S3 가격 개요

Amazon S3 가격은 함께 스토리지 솔루션의 전체 비용을 결정하는 여러 핵심 차원을 중심으로 구성됩니다. 이러한 가격 구성 요소를 이해하는 것이 S3 비용을 관리하고 최적화하기 위한 첫걸음입니다.

#### 가격 구성 요소

- **데이터 스토리지 비용:**
    S3는 저장된 데이터의 총량을 기준으로 요금을 부과합니다. 계층형 가격 정책 덕분에 더 많은 데이터를 저장할수록 기가바이트당 비용이 낮아집니다. 가격은 리전별로도 다르므로 한 AWS 리전의 스토리지 비용이 다른 리전과 다를 수 있습니다.

- **요청과 검색 요금:**
    스토리지 외에도 S3에 대한 모든 API 호출마다 비용이 발생합니다. 여기에는 PUT, COPY, POST, DELETE(프리픽스당 초당 약 3,500건으로 그룹화됨)와 GET/HEAD 요청(프리픽스당 초당 최대 5,500건)이 포함됩니다. 1,000건당 기준으로는 낮지만 대규모로는 상당히 누적될 수 있습니다.

- **데이터 전송 비용:**
    S3로 전송되는 데이터는 일반적으로 무료이지만, 데이터 유출(즉, S3에서 나가는 데이터 전송)은 목적지(예: 인터넷, 다른 AWS 리전, 또는 AWS 서비스 간)에 따라 요금이 부과됩니다. 데이터 이동이 많은 애플리케이션의 경우 이러한 비용을 평가하는 것이 중요합니다.

- **암호화와 관리 기능:**
    구성에 따라(예: 서버 측 암호화(SSE-KMS) 사용) 추가 요금이 적용될 수 있습니다. 여기에는 AWS Key Management Service(KMS)에 대한 API 호출 요금이 포함될 수 있습니다.


#### 가격 도구와 리소스

- **AWS Pricing Calculator:**
    AWS Pricing Calculator를 사용하면 스토리지 볼륨, 요청률, 데이터 전송 파라미터를 지정해 S3 사용량을 시뮬레이션할 수 있습니다. 이 도구는 월별 비용을 예측하고 구성에 대한 정보에 기반한 결정을 내리는 데 도움을 줍니다.

- **AWS S3 가격 페이지:**
    가격 페이지는 여러 탭(예: 스토리지 및 요청, 데이터 전송, 관리 및 인사이트)으로 구성되어 있습니다. S3의 가격 모델이 다양한 사용 패턴에 어떻게 맞춰지는지 대략적으로 볼 수 있습니다.

### 9.2. S3 비용 절감 전략

S3의 비용 절감은 올바른 스토리지 클래스 선택, 라이프사이클 정책 구현, 버킷 소유자로부터 비용을 이동시키는 내장 기능 활용의 조합을 통해 달성됩니다.

#### 적절한 스토리지 클래스 선택

Amazon S3는 서로 다른 접근 패턴과 내구성·가용성 요구에 맞춘 여러 스토리지 클래스를 제공합니다.

- **S3 Standard-General Purpose:**
    자주 접근하는 데이터를 위해 설계되었으며 높은 성능과 99.99% 가용성을 제공합니다.

- **S3 Standard-Infrequent Access(Standard-IA):**
    덜 자주 접근하지만 빠른 접근이 필요한 데이터에 적합합니다. 스토리지 비용은 낮지만 검색 요금이 있습니다.

- **S3 One Zone-Infrequent Access(One Zone-IA):**
    단일 가용 영역에 데이터를 저장함으로써 비용을 절감합니다. 보조 백업이나 쉽게 재생산할 수 있는 데이터에 이상적입니다.

- **S3 Intelligent Tiering:**
    변화하는 접근 패턴에 따라 자주 접근/비자주 접근 티어 사이에서 오브젝트를 자동으로 이동시키며, 소액의 월별 모니터링 비용은 있지만 검색 요금은 없습니다.

- **Glacier 스토리지 클래스(Instant Retrieval, Flexible Retrieval, Deep Archive):**
    아카이빙과 장기 백업을 위해 설계되었습니다. 가장 낮은 스토리지 비용을 제공하지만 검색 요금과 접근 시간이 더 길어집니다.

#### 라이프사이클 정책

라이프사이클 규칙은 오브젝트의 스토리지 클래스 전환이나 만료를 자동화합니다.

- **전환 작업:**
    오브젝트를 이동해야 하는 시점을 정의합니다(예: 60일 후 S3 Standard에서 Standard-IA로 전환, 또는 6개월 후 아카이빙을 위해 Glacier로 전환).
- **만료 작업:**
    오브젝트가 삭제되어야 하는 시점을 지정합니다(예: 접근 로그를 365일 후 만료시켜 스토리지 비용을 더욱 줄임).

#### 추가적인 비용 절감 기법

- **오브젝트 압축:**
    업로드 전에 파일을 압축하면 스토리지 사용량이 줄어들어 그에 따른 비용도 줄어듭니다.

- **S3 Requester Pays:**
    이 기능이 활성화되면 데이터 전송 비용을 버킷 소유자가 아닌 요청자가 부담합니다. 이는 대규모 데이터셋을 여러 외부 사용자와 공유할 때 특히 유용합니다.
    ![S3 Requester Pays](@site/docs/Storage/_assets/s3_requester_pays.png)

### 9.3. S3 Storage Lens

S3 Storage Lens는 S3 스토리지 사용량과 활동에 대한 포괄적인 가시성을 제공하는 고급 분석 도구입니다. 트렌드를 모니터링하고, 이상을 감지하며, 비용 최적화 기회를 식별할 수 있게 하여 비용 관리에서 핵심적인 역할을 합니다.

![S3 Storage Lens](@site/docs/Storage/_assets/s3_storage_lens.png)

#### 주요 기능과 지표

- **사용량과 활동 지표:**
	Storage Lens는 총 스토리지 바이트, 오브젝트 수, 평균 오브젝트 크기, 버킷 수 같은 지표를 집계합니다. 어떤 버킷이나 프리픽스가 가장 빠르게 증가하는지에 대한 인사이트를 제공합니다.

- **비용 최적화 인사이트:**
	비현재(non-current) 버전 스토리지와 불완전한 멀티파트 업로드에 대한 지표를 제공해, 더 저비용 클래스로 전환하거나 삭제할 수 있는 오브젝트를 식별하는 데 도움을 줍니다.

- **데이터 보호와 접근 지표:**
	버전 관리, 복제, 접근 관리에 관한 지표는 데이터 보호 조치가 의도치 않게 비용을 증가시키지 않도록 보장하는 데 도움을 줍니다.

#### 대시보드와 보고

- **사전 구성된 대시보드와 커스텀 대시보드:**
    Storage Lens는 계정과 리전 전반의 데이터를 집계하는 기본 대시보드를 제공합니다. 특정 지표나 조직 단위에 초점을 맞춘 커스텀 대시보드를 만들 수도 있습니다.

- **내보내기 옵션:**
    보고서는 CSV나 Parquet 형식으로 내보낼 수 있어, Amazon QuickSight나 Athena 같은 도구에서 추가 분석이 가능합니다.

#### 무료 지표와 고급 지표

- **무료 지표:**
    모든 고객이 사용할 수 있으며 최근 기간(일반적으로 14일)에 대한 기본 사용량 데이터를 포함합니다.
- **고급(유료) 지표:**
    강화된 활동 지표와 비용 최적화 권장 사항 같은 추가적인 상세 인사이트를 제공하며, 데이터는 최대 15개월까지 보관됩니다.

S3 Storage Lens는 스토리지 환경에 대한 중앙화된 뷰를 제공함으로써 정보에 기반한 결정을 내릴 수 있게 하며, 궁극적으로 낭비를 줄이고 비용을 최적화하는 전략을 안내합니다.

### 9.4. Storage Class Analysis를 사용한 비용 최적화

Storage Class Analysis(때때로 S3 Analytics라고도 불림)는 접근 패턴을 기반으로 오브젝트에 대한 최적의 스토리지 클래스를 결정하는 데 도움을 주도록 설계된 기능입니다.

#### Storage Class Analysis의 동작 방식

- **데이터 수집과 보고:**
    Storage Class Analysis는 시간에 따른 접근 패턴과 사용 통계를 모니터링합니다. Standard 스토리지 클래스에 남아 있는 오브젝트와 비용 절감을 위해 Standard-IA로 전환할 수 있는 오브젝트를 상세히 보여주는 CSV 보고서를 생성합니다.

- **보고 빈도:**
    보고서는 매일 업데이트되며, 초기 분석은 활성화 후 일반적으로 24~48시간 후에 확인할 수 있습니다. 이를 통해 데이터가 어떻게 접근되고 있는지 빠르게 파악할 수 있습니다.

- **라이프사이클 정책과의 통합:**
    Storage Class Analysis에서 얻은 인사이트는 S3 라이프사이클 규칙을 수립하거나 세밀하게 조정하는 데 직접 사용할 수 있습니다. 예를 들어 분석 결과 Standard 클래스의 상당 부분의 오브젝트가 30일 동안 접근되지 않았다면, 해당 오브젝트를 Standard-IA로 전환하는 규칙을 만들 수 있습니다.

#### 이점과 제한 사항

- **비용 최적화:**
    자주 접근하지 않는 오브젝트를 식별함으로써, 필요할 때 접근 가능한 데이터의 가용성을 희생하지 않고도 스토리지 비용을 줄일 수 있습니다.
- **자동화:**
    Storage Class Analysis는 라이프사이클 정책을 통해 자동으로 구현할 수 있는 데이터 기반 권장 사항을 제공함으로써 추측을 없애줍니다.
- **분석 범위:**
    Storage Class Analysis는 현재 Standard와 Standard-IA 스토리지 클래스에 초점을 맞추고 있다는 점에 유의하세요. One Zone-IA나 Glacier 티어로는 확장되지 않으므로, 이러한 사용 사례는 별도로 관리해야 합니다.

Storage Class Analysis는 비용 최적화 도구 키트에서 핵심적인 도구입니다. 사용 패턴에 맞는 자동 전환을 구성하는 데 필요한 실행 가능한 인사이트를 제공해, 더 경제적으로 저장될 수 있는 스토리지에 과도하게 비용을 지불하지 않도록 보장합니다.

## 10. S3 웹사이트 호스팅

### 10.1. S3 웹사이트 개요

Amazon S3는 S3 버킷에서 직접 정적 웹사이트를 호스팅할 수 있게 하는 통합 기능을 제공합니다. 주요 측면은 다음과 같습니다.

- **정적 콘텐츠 전달:**
    S3는 회사 랜딩 페이지, 제품 문서, 미디어 에셋처럼 자주 변경되지 않는 콘텐츠를 호스팅하는 데 이상적입니다. S3는 오브젝트를 높은 가용성과 낮은 지연 시간으로 제공하도록 설계되어 있어, 전 세계 사용자에게 웹사이트 에셋을 빠르게 전달할 수 있습니다.

- **웹사이트 엔드포인트:**
    버킷에서 정적 웹사이트 호스팅을 활성화하면 Amazon S3는 전용 웹사이트 엔드포인트 URL을 할당합니다. 이 URL의 형식은 버킷이 위치한 AWS 리전에 따라 다릅니다. 예를 들어 엔드포인트는 `http://bucket-name.s3-website-region.amazonaws.com` 같은 형태일 수 있습니다.

- **접근 요구 사항:**
    웹사이트가 퍼블릭하게 접근 가능하려면 오브젝트가 읽을 수 있어야 합니다. 기본적으로 S3 버킷은 비공개이므로, 웹사이트를 호스팅하려면 필요한 파일에 대한 퍼블릭 읽기 접근을 허용하는 버킷 정책(또는 다른 접근 설정)을 구성해야 합니다. 적절한 권한이 설정되어 있지 않으면 방문자는 오류(예: HTTP 403 Forbidden)를 만날 수 있습니다.

- **매끄러운 통합:**
    정적 웹사이트 호스팅 기능은 다른 AWS 서비스와 통합됩니다. 예를 들어 나중에 향상된 성능, 캐싱, 커스텀 도메인 이름 사용 옵션을 위해 S3에서 호스팅되는 웹사이트 앞에 Amazon CloudFront를 배치할 수 있습니다.

### 10.2. 정적 웹사이트 설정하기

Amazon S3에서 정적 웹사이트를 설정하려면 웹사이트 에셋이 안정적으로 저장, 제공, 업데이트되도록 보장하는 여러 단계가 필요합니다.

1. **S3 버킷 생성:**
    버킷 이름은 전역적으로 고유해야 합니다. S3는 전역 서비스이지만 버킷은 특정 AWS 리전에서 생성됩니다. 정적 웹사이트를 계획할 때는 지연 시간을 줄이기 위해 대상 사용자와 가까운 리전을 선택하세요.

2. **웹사이트 에셋 업로드:**
    정적 웹사이트 파일 — HTML, CSS, JavaScript, 이미지, 기타 리소스 — 을 버킷에 넣습니다. S3는 이 파일들을 오브젝트로 저장합니다. S3가 전통적인 디렉터리를 구현하지는 않지만, 조직화를 위해 논리적인 폴더(또는 키 프리픽스) 구조를 사용하는 것이 권장됩니다.

3. **정적 웹사이트 호스팅 활성화:**
    S3 콘솔에서 버킷의 속성으로 이동해 정적 웹사이트 호스팅 옵션을 활성화합니다. 인덱스 문서(일반적으로 `index.html`로 명명됨)를 지정해야 합니다. HTTP 오류 발생 시 제공되는 오류 문서(예: `error.html`)도 정의할 수 있습니다.

4. **퍼블릭 접근 구성:**
    웹사이트는 브라우저를 통해 접근되므로 오브젝트는 퍼블릭하게 읽을 수 있어야 합니다. 이는 일반적으로 버킷 내 오브젝트에 대해 모든 주체(`"Principal": "*"` 사용)에게 `s3:GetObject` 권한을 부여하는 버킷 정책을 적용해 달성합니다. 퍼블릭하게 공개하려는 콘텐츠를 호스팅할 때만 퍼블릭 접근을 제한적으로 허용하도록 주의하세요.

5. **웹사이트 테스트:**
    위의 설정이 구성되면 제공된 웹사이트 엔드포인트를 사용해 웹사이트에 접근합니다. HTTP 오류(예: 403 Forbidden)가 발생하면 버킷 정책과 오브젝트 권한이 퍼블릭 접근을 허용하도록 올바르게 설정되어 있는지 확인하세요.


### 10.3. CORS 구성

Cross-Origin Resource Sharing(CORS)은 웹 브라우저가 웹 페이지를 제공한 도메인이 아닌 다른 도메인에서 리소스를 요청할 수 있게 허용하는 메커니즘입니다. 이 보안 기능은 S3에서 호스팅되는 정적 웹사이트가 다른 도메인에 요청을 보낼 때(예: AJAX 호출), 심지어 여러 S3 버킷에서 에셋을 제공할 때 특히 관련이 있습니다.

- **동일 출처 정책 이해하기:**
    기본적으로 웹 브라우저는 동일 출처 정책을 강제합니다. 리소스의 "출처(origin)"는 스킴(HTTP 또는 HTTPS), 호스트, 포트로 정의됩니다. 예를 들어 `https://www.example.com`은 단일 출처로 간주됩니다. 웹사이트의 HTML(한 S3 버킷에서 제공됨)이 다른 도메인(또는 정적 웹사이트로 구성된 다른 S3 버킷)에서 이미지나 스크립트를 로드하려 시도하면, 대상 리소스가 명시적으로 이를 허용하지 않는 한 브라우저는 해당 요청을 차단합니다.

- **S3에서 CORS의 역할:**
    크로스 오리진 요청을 허용하려면 S3 버킷에 CORS 규칙을 구성합니다. 여기에는 다음을 지정하는 것이 포함됩니다.

    - **허용된 출처(Allowed Origins):**
        특정 출처(예: `https://www.example.com`)를 허용하거나, 적절하다면 `"*"`를 사용해 모든 출처를 허용할 수 있습니다.

    - **허용된 메서드(Allowed Methods):**
        허용되는 HTTP 메서드를 정의합니다(일반적으로 `GET`, `POST`, `PUT` 등). 정적 웹사이트 호스팅의 경우 `GET`이 가장 일반적입니다.

    - **허용된 헤더와 노출된 헤더:**
        요청에 포함될 수 있는 헤더와 클라이언트에 노출되는 헤더를 지정합니다.

    - **최대 age:**
        브라우저가 CORS 사전 요청(preflight) 응답을 캐시해야 하는 기간을 결정합니다.

- **CORS 사전 요청:**
    사용자 데이터에 영향을 줄 수 있는 크로스 오리진 요청을 보내기 전에, 브라우저는 실제 요청을 보내도 안전한지 확인하기 위해 OPTIONS 요청("사전 요청")을 보냅니다. S3 버킷은 실제 요청을 허용하기 위해 적절한 CORS 헤더 — 특히 `Access-Control-Allow-Origin` — 로 응답해야 합니다.

- **S3에서 CORS 구현:**
    S3 콘솔에서 버킷의 권한 하위에서 XML 형식으로 CORS 구성을 추가할 수 있습니다. 예를 들어:

    ```xml
    <CORSConfiguration>
        <CORSRule>
            <AllowedOrigin>https://www.example.com</AllowedOrigin>
            <AllowedMethod>GET</AllowedMethod>
            <AllowedHeader>*</AllowedHeader>
            <MaxAgeSeconds>3000</MaxAgeSeconds>
        </CORSRule>
    </CORSConfiguration>
    ```

    이 구성은 `https://www.example.com`의 모든 웹 페이지가 이 S3 버킷에서 GET 요청을 수행할 수 있도록 허용하며, 사전 요청 응답은 3000초 동안 캐시됨을 브라우저에 알려줍니다.

## 11. 결론

AWS S3는 단순한 스토리지 서비스를 훨씬 넘어서, 오늘날 데이터 중심 애플리케이션 대부분을 뒷받침하는 포괄적인 플랫폼입니다. 복원력 있고 안전하며 비용 효율적인 클라우드 솔루션을 설계하려면 그 아키텍처와 기능에 대한 깊고 기술적인 이해가 매우 중요합니다.
