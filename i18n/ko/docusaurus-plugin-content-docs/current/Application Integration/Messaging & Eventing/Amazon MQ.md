# Amazon MQ

## 1. 소개

AWS로 마이그레이션하는 조직은 종종 온프레미스 애플리케이션이 MQTT, AMQP, STOMP, Openwire, WSS 같은 개방형 메시징 프로토콜을 사용할 때 어려움에 직면합니다. Amazon Simple Queue Service(SQS)와 Amazon Simple Notification Service(SNS)는 강력한 완전관리형 서비스이지만 독점적인 AWS 프로토콜에 의존합니다. 원래 개방형 프로토콜로 구축된 애플리케이션을 이러한 독점 인터페이스를 사용하도록 재설계하는 것은 시간이 많이 걸리고 비용이 많이 들 수 있습니다. 이를 해결하기 위해 Amazon MQ는 일반적인 오픈소스 브로커를 위한 관리형이고 높은 호환성을 가진 메시징 솔루션을 제공합니다.

## 2. Amazon MQ가 필요한 이유 이해하기

![amazon-mq](@site/docs/Application%20Integration/_assets/amazon-mq.png)

온프레미스 환경은 RabbitMQ나 ActiveMQ가 기본적으로 개방형 메시징 프로토콜을 지원하기 때문에 이들에 자주 의존합니다. 이러한 애플리케이션이 AWS로 마이그레이션되면서 동일한 인터페이스가 필요할 때, Amazon MQ는 메시징 로직을 완전히 재작성할 필요 없이 브로커 호환성을 제공하기 위해 나섭니다.

## 3. 핵심 기능

Amazon MQ는 내부적으로 ActiveMQ나 RabbitMQ를 관리합니다. 단일 관리형 서비스를 통해 (SQS와 유사한) 큐잉과 (SNS와 유사한) 토픽 기반 메시징 패턴 모두를 처리할 수 있습니다. 주요 고려 사항은 다음과 같습니다.

- **관리형 인프라:** AWS가 기본 서버와 네트워크 구성을 자동으로 프로비저닝하고 관리합니다.
- **다중 AZ 페일오버:** 고가용성을 보장하기 위해 여러 가용 영역에 걸친 배포 모드를 선택할 수 있습니다.
- **호환성:** 개방형 프로토콜을 지원하므로 IBM MQ, TIBCO EMS, RabbitMQ, Apache ActiveMQ로 구축된 애플리케이션은 최소한의 리팩토링으로 마이그레이션할 수 있습니다.
- **성능과 확장성 한도:** 사실상 무제한으로 확장되는 SQS와 SNS와 달리 Amazon MQ 브로커는 서버에서 실행되며 실질적인 상한 용량 한계가 있습니다. 따라서 브로커 인스턴스의 적절한 크기 조정이 필수적입니다.

## 4. 아키텍처 고려 사항
서버리스이고 이벤트 기반인 SQS와 SNS에 비해 Amazon MQ는 처리량 한도와 잠재적인 페일오버에 대해 더 많은 직접적인 주의가 필요합니다. 프로덕션 설정에서는 다음을 고려해야 합니다.

- **브로커 유형:** 기존 코드와 기능 요구를 기반으로 ActiveMQ와 RabbitMQ 중에서 결정합니다.
- **배포 모드:** 저비용을 위한 "단일 인스턴스" 또는 고가용성을 위한 액티브/스탠바이 다중 AZ.
- **마이그레이션 단순화:** 기존 메시징 프로토콜을 유지하면서 레거시 환경에서 Amazon MQ로 큐와 토픽을 마이그레이션합니다.

## 5. 결론

Amazon MQ는 인기 있는 개방형 프로토콜에 의존하는 레거시 또는 온프레미스 워크로드를 마이그레이션하기 위한 간단한 경로를 제공합니다. SQS나 SNS만큼 무한정 확장되지는 않지만 ActiveMQ나 RabbitMQ를 위한 관리형 인프라를 제공해, 클라우드 마이그레이션 중에 기존 메시징 API를 유지하고자 하는 조직에게 이상적인 선택이 됩니다. 호환성과 성능의 미묘한 차이를 인지하는 것은 AWS 아키텍처와 마이그레이션 시험을 준비할 때 적절한 서비스를 선택하는 데 도움이 될 것입니다.
