# Amazon SQS

## 1. 소개

Amazon SQS는 마이크로서비스, 서버리스 애플리케이션, 분산 시스템 같은 분산 애플리케이션 구성 요소를 분리하는 완전관리형이고 고도로 확장 가능한 메시지 큐잉 서비스입니다. SQS를 사용하면 자체 메시징 인프라를 프로비저닝하거나 관리할 필요 없이 메시지를 신뢰성 있게 보내고, 저장하고, 받을 수 있습니다. 각각 다른 사용 사례에 최적화된 표준 큐와 FIFO(선입선출) 큐를 모두 지원합니다.

## 2. 핵심 개념

### 2.1. 분리된 아키텍처

SQS의 주요 용도는 메시지 전송(생산자)과 메시지 수신(소비자)이 서로 직접 의존하지 않도록 시스템을 분리하는 것입니다. 이 접근 방식은 각 구성 요소가 시스템의 나머지 부분에 연쇄적인 장애나 병목 현상을 일으키지 않고 자체 수요에 따라 확장할 수 있으므로 마이크로서비스 전반의 복원력과 확장성을 개선합니다.
### 2.2. 표준 큐 vs. FIFO 큐

SQS는 두 가지 큐 유형을 제공합니다.

- **표준 큐**: 거의 무제한의 처리량, 최선의 노력 순서, 최소 한 번 메시지 전달을 제공합니다. 이는 다음을 의미합니다.
    
    - **순서가 보장되지 않음**; 메시지가 보내진 순서와 다른 순서로 전달될 수 있습니다.
    - **높은 처리량**: 프로비저닝 없이 초당 매우 많은 양의 메시지를 처리할 수 있습니다.

- **FIFO 큐**: 메시지 순서("선입선출")를 보존하고 정확히 한 번 처리를 지원합니다. 그러나:
    
    - **감소된 처리량**: 기본적으로 초당 최대 300개 메시지(메시지 배치 처리 시 최대 3000개).
    - **엄격한 순서**: 작업의 정확한 순서가 중요한 워크로드에 적합합니다.
### 2.3. 메시지 크기

각 메시지는 최대 256KB까지 가능합니다. 프로세스가 256KB보다 큰 페이로드(예: 수 메가바이트 크기의 파일)를 보내야 한다면 일반적인 패턴은 다음과 같습니다.

1. 큰 데이터 객체를 Amazon S3에 업로드합니다.
2. SQS를 통해 참조(S3 키)만 보냅니다.
3. 소비자가 S3에서 파일을 검색하고 처리하도록 합니다.

이 패턴은 SQS의 확장성을 유지하면서 대용량 데이터 저장을 S3로 오프로드합니다.

## 3. 데드 레터 큐 이해하기

![sqs-dlq](@site/docs/Application%20Integration/_assets/sqs-dlq.png)

### 3.1. 데드 레터 큐가 중요한 이유

소비자가 "가시성 타임아웃"(메시지를 검색한 후 다른 소비자로부터 숨겨지는 시간) 내에 메시지를 처리하지 못하면 그 메시지는 큐로 돌아갑니다. 특정 메시지가 반복적으로 계속 실패하면 "poison-pill" 루프를 일으킬 수 있습니다.

**데드 레터 큐(DLQ)**는 문제가 있는 메시지의 반복적인 처리 시도를 방지합니다. 원본 큐에 **최대 수신 횟수**를 설정하며, 메시지가 그 임계값 이상으로 실패하면 SQS는 자동으로 그 메시지를 DLQ로 이동시킵니다. 그런 다음 멈춘 메시지를 검사하고, 잠재적인 문제를 디버깅하고, 재처리하기 전에 시정 조치를 결정할 수 있습니다.

### 3.2. 큐 유형 일치시키기

- 표준 큐는 다른 표준 큐만 DLQ로 사용할 수 있습니다.
- FIFO 큐는 다른 FIFO 큐만 DLQ로 사용할 수 있습니다.

### 3.3. 문제 해결을 위한 보존

디버깅을 위한 충분한 시간을 확보하기 위해 DLQ의 보존 기간을 최대 **14일**까지 설정할 수 있습니다. 이는 필요한 경우 문제가 있는 메시지가 분석과 수동 재처리를 위해 계속 사용 가능하도록 보장합니다.

### 3.4. 원본으로 재전송(Redrive)

DLQ에 메시지가 도착한 근본 원인을 수정한 후에는 **Redrive** 기능을 사용해 그 DLQ 메시지를 원본(소스) 큐로 다시 이동시켜 정상 처리할 수 있습니다. 이 워크플로는 소비자를 실패하게 만든 일시적인 로직이나 데이터 형식 오류로부터 우아하게 복구하는 데 도움이 됩니다.

## 4. 멱등성: 안전한 재처리 보장

SQS는 최소 한 번 메시지 전달을 보장하므로 메시지가 가끔 두 번 전달될 수 있습니다. 소비자는 **멱등적**이어야 합니다. 즉 동일한 메시지를 반복 처리해도 의도하지 않은 중복 부작용이 발생하지 않아야 합니다.

예를 들어:

- **비멱등적**: 메시지를 읽을 때마다 새 데이터베이스 레코드를 삽입합니다. 동일한 메시지를 두 번 읽으면 두 개의 중복 레코드가 생성됩니다.
- **멱등적**: 기본 키나 고유 식별자를 사용합니다. 레코드가 이미 존재하면 중복을 생성하는 대신 업데이트하거나 덮어씁니다.

멱등적인 소비자를 설계하는 것은 데이터 손상을 방지하고 분산 시스템에서 일관된 결과를 보장하는 데 중요합니다.

## 5. AWS Lambda와의 통합

![sqs-lambda](@site/docs/Application%20Integration/_assets/sqs-lambda.png)

SQS는 **이벤트 소스 매핑**을 통해 AWS Lambda 함수를 트리거할 수 있습니다. Lambda의 폴러는 SQS 큐에서 자동으로 "롱 폴링"을 사용하고, 배치 단위로 메시지를 가져와 Lambda 함수를 호출합니다. 고려 사항은 다음과 같습니다.

- **배치 크기**: 처리량과 동시성의 균형을 맞춰 1개에서 10개 메시지 사이로 구성합니다.
- **가시성 타임아웃**: 이 타임아웃을 Lambda 함수 타임아웃의 약 6배로 설정합니다. 이는 함수가 재시도가 필요하거나 지연을 겪을 때 메시지가 조기에 큐에 다시 나타나지 않고 충분한 처리 시간을 갖도록 보장합니다.
- **DLQ 설정**: (반복적인 실패로 인한) 처리되지 않은 메시지가 Lambda 함수를 다시 호출하지 않도록 하려면 큐 수준에서 DLQ를 구성합니다. 또는 이벤트를 비동기적으로 처리할 때 Lambda Destinations를 사용할 수 있지만, 이는 SQS 같은 폴링 기반 이벤트 소스에는 적용되지 않습니다.
## 6. 결론

Amazon SQS는 AWS에서 복원력 있고, 확장 가능하고, 분리된 아키텍처를 구축하기 위한 필수적인 구성 요소입니다. 표준 또는 FIFO 큐를 가시성 타임아웃, 데드 레터 큐, 다른 AWS 서비스와의 통합 같은 기능과 함께 사용함으로써 SQS는 최소한의 오버헤드와 최대한의 신뢰성으로 분산된 구성 요소 간의 비동기 통신을 관리하는 데 도움을 줍니다.
