# Amazon SNS

## 1. 소개

Amazon SNS는 분산되고, 분리되고, 확장 가능한 애플리케이션을 구축할 수 있게 해주는 완전관리형 pub-sub 메시징 서비스입니다. 지원되는 여러 프로토콜을 통해 구독자에게 알림을 "푸시"함으로써 애플리케이션 간(A2A) 메시징과 애플리케이션-사람 간(A2P) 메시징을 모두 가능하게 합니다. SNS를 사용하면 자체 메시징 인프라를 관리하고 확장하는 오버헤드 없이 토픽을 신속하게 설정하고, 구독자를 추가하고, 메시지를 전달할 수 있습니다.
## 2. Pub-Sub 패턴

![pub-sub](@site/docs/Application%20Integration/_assets/pub-sub.png)

전통적으로 시스템이 여러 수신자에게 알림을 보내야 할 때 — 예를 들어 이메일을 보내고, 사기 탐지 서비스에 알리고, Amazon SQS 큐에 메시지를 배치하는 것 — 여러 직접적인 통합이 필요했습니다. 새로운 수신자마다 더 많은 코드, 더 많은 엔드포인트, 더 많은 복잡함이 필요했습니다.

발행-구독(pub/sub) 패턴은 메시지 생산자를 소비자로부터 분리합니다. 발행자가 "토픽"에 메시지를 보내면 여러 구독자가 그 메시지를 자동으로 받습니다. 이는 통합 오버헤드를 크게 줄이고 확장을 단순화합니다.

**상위 수준 흐름**:

1. **생산자(발행자):** SNS 토픽에 메시지를 보냅니다.
2. **토픽:** 중앙 "채널" 또는 "허브" 역할을 합니다.
3. **소비자(구독자):** 다양한 형식(예: 이메일, HTTP, AWS Lambda, Amazon SQS)으로 그 토픽으로부터 메시지를 자동으로 받습니다.

이 모델을 사용하면 구독자를 손쉽게 추가하거나 제거할 수 있습니다. 새 소비자를 수용하기 위해 발행자를 수정할 필요가 없습니다. 대신 SNS 토픽을 수신하도록 구성하면 됩니다.

## 3. 아키텍처와 구성 요소

![sns](@site/docs/Application%20Integration/_assets/sns.png)

**토픽**
토픽은 메시지가 게시되는 SNS의 기본 리소스입니다. 메시지가 도착하면 SNS는 모든 구독자에게 자동으로 사본을 배포합니다.

**구독**
구독은 토픽이 소비자에게 메시지를 어떻게 라우팅하는지 정의합니다. 다양한 범위의 구독 엔드포인트를 구성할 수 있습니다.

- **이메일:** SNS는 알림을 이메일 메시지로 직접 보낼 수 있습니다.
- **SMS:** 휴대전화로 문자 메시지를 보냅니다.
- **HTTP/HTTPS:** 구성한 엔드포인트로 요청을 전달합니다.
- **Amazon SQS:** 분리된 처리를 위해 SQS 큐로 알림을 라우팅합니다.
- **AWS Lambda:** 새 메시지가 도착하면 함수를 호출합니다.
- **모바일 푸시 알림:** 모바일 장치를 위해 GCM(Google), APNS(Apple), 또는 ADM(Amazon)과 통합합니다.

**메시지 속성과 필터링:**
메시지는 속성 형태로 추가 메타데이터를 전달할 수 있습니다. 구독자는 필터 정책을 사용해 필요한 메시지만 선택할 수 있습니다.

**확장성**
SNS는 토픽당 수백만 개의 구독을 지원하며, AWS 계정당 많은 수의 토픽을 만들 수 있습니다. 특정 한도 수치는 변경될 수 있지만, 핵심은 SNS가 대규모 팬아웃을 위해 설계되었다는 점입니다.

> **시험 팁:** SNS의 정확한 수치 서비스 한도에 대해 시험을 보지는 않지만, 수백만 명의 구독자로 확장되고 계정당 수십만 개의 토픽을 지원할 수 있다는 것을 아는 것이 중요합니다.

## 4. 신뢰할 수 있는 메시지 전달과 데드 레터 큐

Simple Notification Service(SNS)는 AWS 내에서 유연하고 완전관리형인 메시지 전달 메커니즘을 제공합니다. 그러나 엔드포인트 문제나 네트워크 오류로 인해 메시지 전달이 항상 처음 시도에서 성공하는 것은 아닙니다. 이 섹션에서는 SNS가 메시지 전달 재시도를 어떻게 처리하는지, 그리고 모든 시도가 실패했을 때 중요한 메시지가 손실되지 않도록 데드 레터 큐(DLQ)를 어떻게 활용하는지 살펴봅니다. 이러한 재시도와 실패 처리 프로세스를 이해하는 것은 복원력 있는 시스템을 설계하는 데 핵심입니다.
### 4.1. 관리형 엔드포인트를 위한 기본 전달 정책과 재시도

![sns-retry](@site/docs/Application%20Integration/_assets/sns-retry.png)

SNS가 Kinesis Data Firehose, AWS Lambda, Amazon SQS 같은 AWS 관리형 엔드포인트로 메시지를 보낼 때는 특정한 사전 구성된 전달 정책을 적용합니다. 이 정책은 메시지 전달의 지속성을 최대한 보장하기 위해 뚜렷한 단계로 구성됩니다.

- 지연 없는 3회의 초기 시도.
- 1초 지연으로 구분된 2회의 후속 재시도.
- 재시도 사이에 1초에서 20초 범위의 지수 백오프 시도 10회.
- 각각 20초씩 구분된 100,000회 시도의 "백오프 후" 단계로, 총 최대 23일에 걸쳐 진행됩니다.

이 모든 단계를 합하면 개별 메시지는 최대 100,015회의 총 전달 시도를 볼 수 있습니다. 매우 많은 수의 재시도는 엔드포인트가 복구되면 메시지가 결국 전달될 것이라는 높은 신뢰도를 제공합니다.

### 4.2. HTTP/HTTPS 구독자를 위한 커스텀 전달 정책

AWS 관리형 엔드포인트를 위한 내장 전달 정책 외에도 SNS는 토픽에 구독된 HTTP와 HTTPS 엔드포인트를 위한 커스텀 전달 정책을 제공합니다. 이 정책들을 사용하면 다음을 세밀하게 조정할 수 있습니다.

- 최대 재시도 횟수.
- 연속 시도 사이의 최소 및 최대 지연.
- 지수 백오프 함수.
- 엔드포인트로 전송되는 요청 속도를 제어하는 스로틀링 동작.

이 유연성은 커스텀 애플리케이션 엔드포인트가 특정 처리량이나 동시성 한도를 가지고 있을 때 특히 유용합니다. 맞춤화된 재시도 정책을 설정함으로써 신뢰성(충분한 전달 시도 보장)과 시스템 안정성(복구 중인 서비스에 과부하를 주지 않음) 사이의 균형을 맞출 수 있습니다.

### 4.3. 실패한 전달을 위한 데드 레터 큐 사용

철저한 재시도 정책에도 불구하고 일부 메시지는 여전히 성공적으로 전달되지 못할 수 있습니다. 모든 재시도가 소진되면 데드 레터 큐(DLQ)가 연결되어 있지 않는 한 SNS는 메시지를 폐기합니다. 이 시나리오에서는 전달되지 않은 메시지가 DLQ로 지정된 Amazon SQS 큐로 전송됩니다. 나중에 전달 문제를 해결하기 위해 이 실패한 메시지들을 검사, 재처리, 또는 로깅할 수 있습니다.

### 4.4. 구독 수준 DLQ

SNS의 경우 DLQ는 토픽 자체가 아니라 구독 수준에서 구성됩니다. 이 설계 선택은 실패에 대한 세밀한 처리를 가능하게 합니다. 서로 다른 구독은 처리되지 않은 메시지에 대해 서로 다른 처리가 필요하므로, 필요한 경우 각 구독에 별도의 DLQ를 연결할 수 있습니다. 예를 들면:

- 이메일 구독은 전달에 실패한 메시지를 잡기 위한 자체 DLQ를 가질 수 있습니다.
- 전문화된 오류 처리를 갖춘 HTTP/HTTPS 구독은 자체적인 별도의 DLQ로 구성될 수 있습니다.

구독 수준에서 이 큐들을 분리함으로써 어떤 엔드포인트가 문제를 겪고 있는지 신속하게 파악하고 실패를 더 효율적으로 처리할 수 있습니다.

## 5. 가격 정책과 할당량

- **가격 정책:**
	SNS는 API 요청 수(예: 메시지 게시)와 전달된 알림 수를 기반으로 요금이 청구됩니다. 관대한 무료 티어가 있으며(예를 들어 매월 처음 100만 건의 요청은 무료) 가격 정책은 전달 프로토콜(HTTP/HTTPS, 이메일, SMS 등)에 따라 다릅니다.
    
- **할당량:**
    공식 문서는 계정당 토픽 수, 구독 한도, 메시지 크기(메시지당 최대 256KiB), API 속도 제한 같은 한도를 상세히 설명합니다. 이 할당량들은 대부분의 사용 사례에 충분히 높도록 설계되었으며 종종 요청 시 늘릴 수 있습니다.
## 6. 보안

- **접근 제어:**
    IAM 정책과 SNS 토픽 정책을 사용해 누가 토픽을 게시하거나 구독할 수 있는지 제한합니다.
- **암호화:**
    저장 중인 메시지 데이터를 보호하기 위해 AWS KMS를 사용한 서버 측 암호화를 활성화합니다.
- **VPC 엔드포인트:**
    보안을 강화하기 위해 SNS는 VPC 엔드포인트를 지원해 트래픽이 프라이빗 네트워크 내에 머물 수 있게 합니다.

## 7. 일반적인 통합 패턴

- **애플리케이션 통합:**
    SNS는 마이크로서비스를 분리하는 데 자주 사용됩니다. 일반적인 패턴은 토픽에 메시지를 게시한 다음 병렬 처리를 위해 여러 SQS 큐, Lambda 함수, 또는 다른 엔드포인트로 팬아웃하는 것입니다.
    
- **알림과 통지:**
    (SMS나 이메일을 통한) 운영 알림 전송, 고객 앱을 위한 모바일 푸시 알림, 또는 서비스 간 자동화된 메시지든, SNS는 폴링 없이 실시간, 푸시 기반 전달을 제공합니다.
    
- **팬아웃 아키텍처:**
    SNS는 대량의 구독자에게 효율적으로 메시지를 팬아웃할 수 있어, 단일 이벤트가 여러 작업을 트리거해야 하는 이벤트 기반 시스템에 이상적입니다.
## 8. 결론

Amazon SNS는 애플리케이션 간과 애플리케이션-사람 간 맥락 모두에서 알림과 메시지를 보내는 프로세스를 단순화하도록 설계된 다재다능하고, 고도로 확장 가능하고, 완전관리형인 메시징 서비스입니다. 견고한 보안, 유연한 통합 옵션, 비용 효율적인 가격 정책을 통해 AWS에서 현대적이고, 분산되고, 이벤트 기반인 아키텍처를 구축하기 위한 필수적인 구성 요소입니다.
