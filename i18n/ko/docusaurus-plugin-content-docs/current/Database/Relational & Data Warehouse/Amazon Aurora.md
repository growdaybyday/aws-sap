# Amazon Aurora

## 1. 소개

Amazon Aurora는 Amazon RDS의 일부인 완전관리형 클라우드 네이티브 관계형 데이터베이스 엔진입니다. 고급 상용 데이터베이스의 성능과 가용성을 10분의 1의 비용으로 제공하도록 설계된 Aurora는 MySQL과 호환되는 에디션과 PostgreSQL과 호환되는 에디션, 두 가지로 완전히 호환됩니다. 프로비저닝, 패치, 백업, 복구, 확장 같은 시간이 많이 소요되는 데이터베이스 작업을 자동화하면서 엔터프라이즈급 보안, 신뢰성, 성능을 제공합니다.

Aurora는 관리형 데이터베이스 서비스인 Amazon Relational Database Service(Amazon RDS)의 일부입니다. Amazon RDS는 클라우드에서 관계형 데이터베이스를 더 쉽게 설정, 운영, 확장할 수 있게 합니다.

## 2. Amazon Aurora가 Amazon RDS와 함께 작동하는 방식

다음은 Amazon Aurora가 Amazon RDS에서 제공되는 표준 MySQL과 PostgreSQL 엔진과 어떻게 연관되는지 보여줍니다.

- Amazon RDS를 통해 새로운 데이터베이스 서버를 설정할 때 DB 엔진 옵션으로 Aurora MySQL이나 Aurora PostgreSQL을 선택합니다.

- Aurora는 관리와 운영을 위해 익숙한 Amazon Relational Database Service(Amazon RDS) 기능을 활용합니다. Aurora는 프로비저닝, 패치, 백업, 복구, 장애 감지, 복구 같은 일상적인 데이터베이스 작업을 처리하기 위해 Amazon RDS AWS Management Console 인터페이스, AWS CLI 명령, API 작업을 사용합니다.

- Aurora 관리 작업은 개별 데이터베이스 인스턴스가 아니라, 복제를 통해 동기화되는 전체 데이터베이스 서버 클러스터를 대상으로 하는 경우가 일반적입니다. 자동 클러스터링, 복제, 스토리지 할당은 가장 큰 MySQL과 PostgreSQL 배포를 설정, 운영, 확장하는 것을 간단하고 비용 효율적으로 만듭니다.

- 스냅샷을 생성하고 복원하거나 단방향 복제를 설정함으로써 Amazon RDS for MySQL과 Amazon RDS for PostgreSQL의 데이터를 Aurora로 가져올 수 있습니다. 원클릭 마이그레이션 도구를 사용해 기존 RDS for MySQL과 RDS for PostgreSQL 애플리케이션을 Aurora로 변환할 수 있습니다.

## 3. Amazon Aurora DB 클러스터

Amazon Aurora _DB 클러스터_는 하나 이상의 DB 인스턴스와 해당 DB 인스턴스의 데이터를 관리하는 클러스터 볼륨으로 구성됩니다. Aurora _클러스터 볼륨_은 여러 가용 영역에 걸친 가상 데이터베이스 스토리지 볼륨으로, 각 가용 영역은 DB 클러스터 데이터의 복사본을 가집니다. 두 가지 유형의 DB 인스턴스가 Aurora DB 클러스터를 구성합니다.

- **프라이머리(writer) DB 인스턴스**: 읽기와 쓰기 작업을 지원하며 클러스터 볼륨에 대한 모든 데이터 수정을 수행합니다. 각 Aurora DB 클러스터는 하나의 프라이머리 DB 인스턴스를 가집니다.

- **Aurora 리플리카(reader DB 인스턴스)**: 프라이머리 DB 인스턴스와 동일한 스토리지 볼륨에 연결되지만 읽기 작업만 지원합니다. 각 Aurora DB 클러스터는 프라이머리 DB 인스턴스 외에 **최대 15개의 Aurora 리플리카**를 가질 수 있습니다. Aurora 리플리카를 별도의 가용 영역에 배치함으로써 고가용성을 유지하세요. 프라이머리 DB 인스턴스가 사용할 수 없게 되면 Aurora는 자동으로 Aurora 리플리카로 페일오버합니다. Aurora 리플리카의 페일오버 우선순위를 지정할 수 있습니다. Aurora 리플리카는 프라이머리 DB 인스턴스로부터 읽기 워크로드를 오프로드할 수도 있습니다.

다음 다이어그램은 Aurora DB 클러스터에서 클러스터 볼륨, writer DB 인스턴스, reader DB 인스턴스 간의 관계를 보여줍니다.

![aurora-cluster](@site/docs/Database/_assets/aurora-cluster.png)

Aurora DB 클러스터는 컴퓨팅 용량과 스토리지의 분리를 보여줍니다. 예를 들어 단일 DB 인스턴스만 있는 Aurora 구성도 여전히 클러스터인데, 기반이 되는 스토리지 볼륨이 여러 가용 영역(AZ)에 분산된 여러 스토리지 노드를 포함하기 때문입니다.

## 4. Blue/Green 배포

Blue/Green 배포는 프로덕션 데이터베이스 환경을 별도의 동기화된 스테이징 환경으로 복사합니다. Amazon RDS Blue/Green Deployments를 사용하면 프로덕션 환경에 영향을 주지 않고 스테이징 환경에서 데이터베이스를 변경할 수 있습니다. 예를 들어 스테이징 환경에서 주 또는 부 DB 엔진 버전을 업그레이드하거나, 데이터베이스 파라미터를 변경하거나, 스키마를 변경할 수 있습니다. 준비가 되면 스테이징 환경을 새로운 프로덕션 데이터베이스 환경으로 승격시킬 수 있습니다. 자세한 정보는 [데이터베이스 업데이트를 위한 Amazon Aurora Blue/Green Deployments 사용](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/blue-green-deployments.html)을 참고하세요.

## 5. DB 클러스터 스토리지 구성

Amazon Aurora는 Aurora I/O-Optimized와 Aurora Standard, 두 가지 DB 클러스터 스토리지 구성을 가집니다.

- **Aurora I/O-Optimized**
	I/O 집약적 애플리케이션을 위한 향상된 가격 성능과 예측 가능성을 제공합니다. DB 클러스터의 사용량과 스토리지에 대해서만 비용을 지불하며, 읽기와 쓰기 I/O 작업에 대한 추가 요금은 없습니다.
	Aurora I/O-Optimized는 I/O 비용이 전체 Aurora 데이터베이스 비용의 25% 이상일 때 최선의 선택입니다.

	Aurora I/O-Optimized 클러스터 구성을 지원하는 DB 엔진 버전으로 DB 클러스터를 생성하거나 수정할 때 Aurora I/O-Optimized를 선택할 수 있습니다. 언제든지 Aurora I/O-Optimized에서 Aurora Standard로 전환할 수 있습니다.

- **Aurora Standard**:
	적절한 I/O 사용량을 가진 많은 애플리케이션에 비용 효율적인 가격을 제공합니다. DB 클러스터의 사용량과 스토리지 외에도 I/O 작업에 대해 백만 요청당 표준 요율로 비용을 지불합니다.

	Aurora Standard는 I/O 비용이 전체 Aurora 데이터베이스 비용의 25% 미만일 때 최선의 선택입니다.

	30일에 한 번씩 Aurora Standard에서 Aurora I/O-Optimized로 전환할 수 있습니다. NVMe 기반이 아닌 DB 인스턴스에서 Aurora Standard와 Aurora I/O-Optimized 스토리지 옵션 사이를 전환할 때는 다운타임이 없습니다. 다만 NVMe 기반 DB 인스턴스의 경우 Aurora I/O-Optimized와 Aurora Standard 스토리지 옵션 사이를 전환하려면 데이터베이스 엔진 재시작이 필요해 짧은 다운타임이 발생할 수 있습니다.

## 6. 데이터베이스 활동 스트림

데이터베이스 활동 스트림은 감사, 규정 준수, 보안 분석을 위해 데이터베이스 작업(SQL 쿼리, DML, DDL 등)의 거의 실시간이고 불변인 스트림을 캡처합니다.

활성화되면 Aurora는 프로덕션 워크로드의 성능에 영향을 주지 않으면서 데이터베이스로부터 안전한 대상(Amazon Kinesis나 서드파티 SIEM 솔루션 등)으로 활동 로그를 스트리밍합니다.

## 7. Amazon Aurora DB 클러스터 백업과 복원

Aurora는 클러스터 볼륨을 자동으로 백업하며 _백업 보존 기간_ 동안 복원 데이터를 보존합니다. Aurora 자동 백업은 지속적이고 증분식이므로, 백업 보존 기간 내의 어느 시점으로든 빠르게 복원할 수 있습니다. 백업 데이터가 쓰이는 동안 성능 영향이나 데이터베이스 서비스 중단은 발생하지 않습니다. DB 클러스터를 생성하거나 수정할 때 백업 보존 기간을 1~35일 사이로 지정할 수 있습니다. Aurora 자동 백업은 Amazon S3에 저장됩니다.

백업 보존 기간을 넘어서 데이터를 보존하고 싶다면 클러스터 볼륨의 데이터 스냅샷을 만들 수 있습니다. Aurora DB 클러스터 스냅샷은 만료되지 않습니다. 스냅샷으로부터 새 DB 클러스터를 생성할 수 있습니다.

### 7.1. AWS Backup 사용

AWS Backup을 사용해 Amazon Aurora DB 클러스터의 백업을 관리할 수 있습니다.

AWS Backup이 관리하는 스냅샷은 수동 DB 클러스터 스냅샷으로 간주되지만 Aurora의 DB 클러스터 스냅샷 할당량에는 포함되지 않습니다. AWS Backup으로 생성된 스냅샷은 ``awsbackup:job-`AWS-Backup-job-number` `` 형태의 이름을 가집니다.

AWS Backup을 사용해 Amazon Aurora DB 클러스터의 자동 백업도 관리할 수 있습니다. DB 클러스터가 AWS Backup의 백업 계획과 연관되어 있다면 특정 시점 복구에 그 백업 계획을 사용할 수 있습니다. AWS Backup이 관리하는 자동(지속적) 백업은 ``continuous:cluster-`AWS-Backup-job-number` `` 형태의 이름을 가집니다.

### 7.2. 백업 윈도우

자동 백업은 선호하는 백업 윈도우 동안 매일 발생합니다. 백업이 윈도우에 할당된 시간보다 더 오래 걸리면 백업은 윈도우가 끝난 후에도 완료될 때까지 계속됩니다. 백업 윈도우는 DB 클러스터의 주간 유지보수 윈도우와 겹칠 수 없습니다.

### 7.3. 데이터 복원

Aurora가 보존하는 백업 데이터, 저장해 둔 DB 클러스터 스냅샷, 또는 보존된 자동 백업으로부터 새 Aurora DB 클러스터를 생성해 데이터를 복구할 수 있습니다. 백업 보존 기간 내의 어느 시점으로든 백업 데이터로부터 생성된 DB 클러스터의 새 복사본을 빠르게 복원할 수 있습니다. Aurora 백업은 백업 보존 기간 동안 지속적이고 증분식이기 때문에, 복원 시간을 개선하기 위해 자주 스냅샷을 찍을 필요가 없습니다.

DB 클러스터의 _가장 최근 복원 가능 시점_은 DB 클러스터를 복원할 수 있는 가장 최근 시점입니다. 이는 활성 DB 클러스터의 경우 일반적으로 현재 시간의 5분 이내이며, 보존된 자동 백업의 경우 클러스터 삭제 시점의 5분 이내입니다.

_가장 이른 복원 가능 시점_은 백업 보존 기간 내에서 클러스터 볼륨을 얼마나 과거로 복원할 수 있는지를 지정합니다.

DB 클러스터의 가장 최근 또는 가장 이른 복원 가능 시점을 확인하려면 RDS 콘솔에서 `Latest restorable time`이나 `Earliest restorable time` 값을 확인하세요.

### 7.4. Aurora의 데이터베이스 클로닝

Aurora 클로닝을 사용하면 처음에는 원본과 동일한 데이터 페이지를 공유하지만 별개의 독립적인 볼륨인 새 클러스터를 생성할 수 있습니다. 이 프로세스는 빠르고 비용 효율적으로 설계되었습니다. 연관된 데이터 볼륨을 가진 새 클러스터를 _클론_이라고 합니다. 클론을 생성하는 것은 스냅샷 복원 같은 다른 기법을 사용해 데이터를 물리적으로 복사하는 것보다 빠르고 공간 효율적입니다.

Aurora는 클론을 생성하기 위해 _copy-on-write 프로토콜_을 사용합니다. 이 메커니즘은 초기 클론을 생성하는 데 최소한의 추가 공간을 사용합니다. 클론이 처음 생성될 때 Aurora는 소스 Aurora DB 클러스터와 새로운(클론된) Aurora DB 클러스터가 사용하는 데이터의 단일 복사본을 유지합니다. 추가 스토리지는 소스 Aurora DB 클러스터나 Aurora DB 클러스터 클론에 의해 (Aurora 스토리지 볼륨의) 데이터가 변경될 때만 할당됩니다.

## 8. 클러스터와 스냅샷 데이터를 Amazon S3로 내보내기

이 기능은 Aurora 클러스터에서 Amazon S3로 데이터를 직접 내보낼 수 있게 합니다 — 일반적으로 Parquet 같은 컬럼형 형식으로 내보냅니다. S3에 저장된 후에는 Amazon Athena 같은 서비스로 데이터를 쿼리하거나 분석 처리를 위해 Amazon Redshift에 로드할 수 있습니다.

내보내기 작업은 클러스터의 성능에 최소한의 영향을 미치도록 설계되었으며 빅데이터 분석 워크플로와 통합하는 데 유용합니다.

DB 클러스터를 생성할 때 선호하는 백업 윈도우를 지정하지 않으면 Aurora는 기본 30분 백업 윈도우를 할당합니다. 이 윈도우는 각 AWS 리전에 대한 8시간 블록의 시간 범위 중에서 무작위로 선택됩니다.
### 8.1. 스냅샷 데이터를 Amazon S3로 내보내기

클러스터 데이터를 내보내는 것과 유사하게, 이 기능은 데이터베이스 스냅샷에 포함된 데이터를 Amazon S3로 내보낼 수 있게 합니다. 스냅샷 내보내기는 실시간 데이터베이스에 영향을 주지 않고 과거 데이터를 분석할 수 있게 합니다.

S3에 데이터를 저장하는 것(흔히 효율적인 형식으로)은 모든 과거 데이터를 온라인에 유지하는 것보다 경제적일 수 있습니다.

스냅샷을 내보낼 때 Aurora는 스냅샷 데이터를 쿼리 성능에 최적화된 형식(예: Parquet)으로 변환하며, 이를 다른 AWS 서비스를 사용해 처리하거나 분석할 수 있습니다.

## 9. Aurora Global Database

Amazon Aurora Global Database 기능을 사용하면 여러 AWS 리전에 걸친 여러 Aurora DB 클러스터를 설정할 수 있습니다. Aurora는 프라이머리 DB 클러스터에서 이루어진 모든 변경 사항을 하나 이상의 세컨더리 클러스터로 자동으로 동기화합니다. Aurora 글로벌 데이터베이스는 한 리전에 프라이머리 DB 클러스터를, 다른 리전들에 최대 5개의 세컨더리 DB 클러스터를 가집니다. 이 멀티 리전 구성은 전체 AWS 리전에 영향을 미칠 수 있는 드문 장애로부터 빠른 복구를 제공합니다. 여러 지리적 위치에 모든 데이터의 전체 복사본을 갖는 것은 전 세계 널리 분산된 위치에서 연결하는 애플리케이션을 위한 저지연 읽기 작업도 가능하게 합니다.

다음 다이어그램에서 두 개의 AWS 리전에 걸친 Aurora 글로벌 데이터베이스의 예시를 볼 수 있습니다.

![aurora-global](@site/docs/Database/_assets/aurora-global.png)

**중요한 이유:**

- **전역 읽기 확장성:** 전 세계 사용자가 가까운 리전에 연결해 저지연 읽기 접근을 할 수 있습니다.
- **재해 복구:** 리전 장애가 발생할 경우 세컨더리 리전 중 하나를 몇 분 안에 프라이머리로 승격시켜 비즈니스 연속성을 보장할 수 있습니다.
- **강력한 일관성:** 복제는 일반적으로 1초 미만의 지연 시간으로 이루어져 리전 전반에서 강력한 일관성을 유지합니다.

Aurora Global Database는 복제를 위한 전용 인프라를 사용하기 때문에 세컨더리 리전을 추가해도 프라이머리 클러스터의 성능에 영향을 주지 않습니다.

## 10. IAM 데이터베이스 인증

IAM 데이터베이스 인증을 사용하면 고정된 비밀번호 대신 AWS Identity and Access Management(IAM) 자격 증명을 사용해 Aurora에 연결할 수 있습니다. 활성화되면 애플리케이션은 (AWS SDK나 CLI가 생성한) IAM 인증 토큰을 사용해 Aurora와 안전한 연결을 수립할 수 있습니다.

## 11. Kerberos 인증

Aurora는 Kerberos 인증을 지원해 (Active Directory 같은) 엔터프라이즈 신원 관리 시스템과의 통합을 가능하게 합니다. Aurora의 Kerberos 인증은 IAM 및 다른 보안 기능과 함께 작동해 견고하고 유연한 인증 프레임워크를 제공합니다.

## 12. Aurora Machine Learning

Amazon Aurora machine learning을 사용하면 필요에 따라 다음 AWS 머신 러닝 서비스 중 하나와 Aurora DB 클러스터를 통합할 수 있습니다. 각 서비스는 특정 머신 러닝 사용 사례를 지원합니다.

Amazon Bedrock은 AI 기업들의 선도적인 파운데이션 모델을 API를 통해 사용할 수 있게 하고, 생성형 AI 애플리케이션을 구축하고 확장하는 데 도움이 되는 개발자 도구를 제공하는 완전관리형 서비스입니다.

Amazon Comprehend는 문서에서 인사이트를 추출하는 데 사용되는 _자연어 처리_(NLP) 서비스입니다. Amazon Comprehend와 함께 Aurora machine learning을 사용하면 데이터베이스 테이블의 텍스트 감정을 파악할 수 있습니다.

SageMaker AI는 기능이 풍부한 _머신 러닝_ 서비스입니다. 데이터 과학자는 Amazon SageMaker AI를 사용해 사기 탐지 같은 다양한 추론 작업을 위한 머신 러닝 모델을 구축, 학습, 테스트합니다. SageMaker AI와 함께 Aurora machine learning을 사용하면 데이터베이스 개발자는 SQL 코드에서 SageMaker AI 기능을 호출할 수 있습니다.

## 13. Performance Insights

Performance Insights는 기존 Amazon RDS 모니터링 기능을 확장해 데이터베이스 성능을 시각화하고 분석하는 데 도움을 줍니다. Performance Insights 대시보드를 사용하면 Amazon RDS DB 인스턴스 부하를 시각화하고 대기(wait), SQL 문, 호스트, 사용자별로 부하를 필터링할 수 있습니다.

## 14. Zero-ETL 통합

Zero-ETL 통합은 전통적인 추출, 변환, 로드(ETL) 프로세스 없이도 트랜잭션 데이터를 Aurora에서 Amazon Redshift 같은 데이터 웨어하우스로 매끄럽고 거의 실시간으로 이동시킬 수 있게 합니다. Aurora는 대상 Redshift 클러스터로 변경 사항을 지속적으로 복제해, 복제된 데이터에 대해 직접 분석 쿼리를 실행할 수 있게 합니다.

![aurora-zero-etl](@site/docs/Database/_assets/aurora-zero-etl.png)

## 15. RDS Proxy

RDS Proxy는 애플리케이션과 Aurora 사이에 위치하는 완전관리형 데이터베이스 프록시로, 확장성과 애플리케이션 복원력을 개선하기 위해 연결을 풀링하고 공유합니다. 연결을 열고 닫는 오버헤드를 줄여주며, 서버리스나 마이크로서비스 아키텍처에 특히 유용합니다.

RDS Proxy를 사용하면 예측할 수 없는 데이터베이스 트래픽 급증을 처리할 수 있습니다. 그렇지 않으면 이러한 급증은 연결 과다 신청이나 빠른 속도로 생성되는 새 연결로 인해 문제를 일으킬 수 있습니다. RDS Proxy는 데이터베이스 연결 풀을 수립하고 이 풀 내의 연결을 재사용합니다. 이 접근 방식은 매번 새 데이터베이스 연결을 여는 메모리와 CPU 오버헤드를 피합니다. 데이터베이스를 과다 신청으로부터 보호하기 위해 생성되는 데이터베이스 연결 수를 제어할 수 있습니다.

RDS Proxy는 연결 풀에서 즉시 처리할 수 없는 애플리케이션 연결을 대기시키거나 스로틀링합니다. 지연 시간이 늘어날 수 있지만, 애플리케이션은 갑작스럽게 실패하거나 데이터베이스를 압도하지 않으면서 계속 확장할 수 있습니다. 연결 요청이 지정한 한도를 초과하면 RDS Proxy는 애플리케이션 연결을 거부합니다(즉, 부하를 떨어냅니다). 동시에 사용 가능한 용량으로 RDS가 처리할 수 있는 부하에 대해 예측 가능한 성능을 유지합니다.

RDS Proxy는 페일오버 동안 다운타임을 최소화하고 Aurora 인스턴스의 연결 처리 부담을 줄임으로써 전반적인 성능을 개선합니다.

## 16. Secrets Manager 통합

Aurora는 AWS Secrets Manager와 통합되어 데이터베이스 자격 증명, API 키, 기타 시크릿을 저장하고 관리합니다. Secrets Manager는 시크릿을 자동으로 순환시켜 자격 증명 유출 위험을 줄일 수 있습니다.

Aurora는 연결을 수립할 때 Secrets Manager로부터 최신 자격 증명을 자동으로 검색할 수 있어 안전한 접근을 간소화합니다.

## 17. Aurora Serverless v2

Aurora Serverless v2는 Amazon Aurora를 위한 온디맨드 자동 확장 구성입니다. Aurora Serverless v2는 워크로드를 모니터링하고 데이터베이스의 용량을 조정하는 프로세스를 자동화하는 데 도움을 줍니다. 애플리케이션 수요에 따라 용량이 자동으로 조정됩니다. DB 클러스터가 소비하는 리소스에 대해서만 요금이 부과됩니다. 따라서 Aurora Serverless v2는 예산 내에서 유지하고 사용하지 않는 컴퓨팅 리소스에 대한 비용을 지불하지 않도록 도와줍니다.

이러한 유형의 자동화는 멀티테넌트 데이터베이스, 분산 데이터베이스, 개발 및 테스트 시스템, 그리고 매우 가변적이고 예측할 수 없는 워크로드를 가진 다른 환경에서 특히 유용합니다.

요약하면, 사용 사례는 다음을 포함합니다.

- **예측할 수 없거나 가변적인 워크로드:**
    새 애플리케이션, 개발/테스트 환경, 계절적 수요처럼 트래픽 패턴을 예측하기 어려운 애플리케이션에 이상적이며, 필요에 따라 데이터베이스가 즉시 확장되거나 축소되도록 보장합니다.

- **비용 효율적인 확장:**
    피크 용량에 항상 프로비저닝하는 대신 실제 사용한 초당 비용을 부과함으로써 간헐적이거나 산발적인 급증이 있는 워크로드의 비용을 줄이는 데 도움을 줍니다.

- **고처리량, 저지연 애플리케이션:**
    즉각적이고 세밀한 확장을 통해, 다운타임 없이 트래픽 급증 동안 빠른 응답이 필요한 프로덕션 워크로드를 지원해, 현대적인 웹과 모바일 애플리케이션에 적합합니다.

- **혼합 구성 클러스터:**
    Aurora Serverless v2는 동일한 클러스터 내의 프로비저닝된 인스턴스와 통합할 수 있어, 워크로드의 일부는 일정하고 다른 일부는 가변적일 때 유연성을 제공합니다.


이러한 유연성, 비용 효율성, 완전한 Aurora 기능의 조합은 Serverless v2를 가변적인 수요를 가진 신규 및 기존 애플리케이션 모두에게 훌륭한 선택으로 만듭니다.

## 18. RDS Data API

RDS Data API는 지속적인 연결이나 네이티브 데이터베이스 드라이버 없이 Aurora Serverless 데이터베이스와 상호작용할 수 있는 단순하고 안전한 HTTP 기반 인터페이스를 제공합니다.

**중요한 이유:**
- **사용 편의성:** 지속적인 연결을 유지하기 어려운 웹 및 서버리스 애플리케이션에 이상적입니다.
- **보안:** HTTPS를 사용해 SQL 문을 안전하게 실행하고 결과를 검색합니다.
- **단순화된 통합:** 코드에서 연결 풀링이나 데이터베이스 드라이버를 관리할 필요를 없앱니다.

HTTP 요청을 통해 SQL 명령을 보내면 API가 결과를 반환해, 표준 웹 프로토콜을 사용해 데이터베이스 작업을 애플리케이션에 통합할 수 있습니다.

## 19. 무중단 패칭(ZDP)

무중단 패칭(Zero-Downtime Patching, ZDP)을 사용하면 다운타임 없이 Aurora 데이터베이스 엔진에 보안 패치와 업데이트를 적용할 수 있습니다.

**중요한 이유:**
- **지속적인 가용성:** 업데이트는 롤링 방식이나 라이브 패칭을 통해 적용되어 데이터베이스가 온라인 상태를 유지합니다.
- **보안:** 운영을 방해하지 않고 데이터베이스를 신속하게 업데이트할 수 있도록 보장합니다.
- **운영 효율성:** 유지보수 윈도우를 최소화하고 업데이트 중 위험을 줄입니다.

ZDP는 롤링 업데이트와 페일오버 조율 같은 기법을 활용해 전체 클러스터를 계속 사용 가능하게 유지하면서 인스턴스를 개별적으로 패치합니다.

## 20. Aurora MySQL을 위한 엔진 네이티브 기능

### 20.1. 고급 감사

DML, DDL, 사용자 작업 같은 상세한 데이터베이스 활동을 로깅하는 내장 감사 기능입니다. 서드파티 도구 없이도 포괄적인 감사 로그를 캡처함으로써 규정 준수와 보안 요구 사항을 충족하는 데 도움을 줍니다. 관리자는 캡처되는 세부 수준을 구성할 수 있으며, 로그는 추가 분석을 위해 안전한 대상으로 스트리밍될 수 있습니다.
### 20.2. Backtrack

백업으로부터 복원하지 않고도 Aurora MySQL 클러스터를 특정 시점으로 "되돌릴" 수 있게 하는 기능입니다. 클러스터 상태를 빠르게 되돌림으로써 사용자 오류(예: 실수로 인한 데이터 삭제나 잘못 구성된 쿼리)로부터 신속한 복구를 제공합니다. Aurora는 (사용자가 지정한 보존 윈도우 동안) 변경 이력을 지속적으로 유지해 선택한 시점으로 거의 즉각적인 롤백을 가능하게 합니다.

### 20.3. Fault Injection Queries

데이터베이스에 오류를 의도적으로 주입하거나 장애 시나리오를 시뮬레이션할 수 있는 테스트 도구입니다. 개발자와 DBA가 애플리케이션과 데이터베이스 구성의 복원력과 복구 메커니즘을 검증할 수 있게 합니다. 특정 fault injection 쿼리를 실행함으로써 지연, 오류 조건, 기타 결함을 시뮬레이션한 다음 시스템과 애플리케이션이 어떻게 반응하는지 관찰할 수 있습니다.

### 20.4. In-Cluster Write Forwarding

필요할 때 Aurora 리플리카가 쓰기 쿼리를 프라이머리 writer로 전달할 수 있게 하는 메커니즘입니다. 이는 리플리카에서 실행된 쓰기 집약적 쿼리가 자동으로 프라이머리로 리디렉션되도록 보장함으로써 강력한 일관성을 유지하고 애플리케이션 복잡성을 줄이는 데 도움을 줍니다. (아마도 의도치 않게) 리플리카에 대해 쓰기 요청이 발행되면 시스템은 자동으로 이를 프라이머리 인스턴스로 라우팅해 쓰기가 올바르게 적용되도록 합니다.

### 20.5. Parallel Query

쿼리 처리의 일부(필터링과 집계 등)를 스토리지 계층으로 직접 오프로드하는 성능 강화 기능입니다. 데이터베이스 컴퓨팅 계층에 부담을 주지 않으면서 대규모 데이터셋에 대한 복잡한 분석 쿼리를 가속화합니다. 스토리지 계층은 분산된 노드 전반에서 쿼리의 일부를 병렬로 처리해, 전송되는 데이터 양을 줄이고 쿼리 실행을 가속화합니다.

## 21. Aurora PostgreSQL을 위한 엔진 네이티브 기능

### 21.1. Babelfish

Aurora PostgreSQL이 T-SQL 명령과 SQL Server 와이어 프로토콜을 이해할 수 있게 하는 호환성 계층입니다. 원래 Microsoft SQL Server용으로 개발된 애플리케이션이 최소한의 코드 변경으로 Aurora PostgreSQL에서 실행될 수 있게 하여 마이그레이션을 단순화합니다. Babelfish는 T-SQL 쿼리를 PostgreSQL과 호환되는 SQL로 변환해, 두 환경 사이의 간극을 효과적으로 메웁니다.
### 21.2. Fault Injection Queries(PostgreSQL)

MySQL 버전과 유사하게, 이 기능은 Aurora PostgreSQL 엔진 내에서 결함을 시뮬레이션할 수 있게 합니다. 오류 조건에서 데이터베이스의 동작을 테스트하기 위한 통제된 환경을 제공해, 오류 처리와 복구가 견고한지 확인합니다. 특정 쿼리가 시뮬레이션된 결함이나 지연을 트리거해, 불리한 조건에 대한 시스템의 반응을 관찰하고 최적화할 수 있게 합니다.

### 21.3. Query Plan Management

DBA가 안정적인 쿼리 실행 계획을 캡처, 분석, 강제할 수 있게 하는 도구와 기능의 집합입니다. 데이터나 시스템 조건이 변화하더라도 일관된 성능을 보장함으로써 실행 계획 변경으로 인한 성능 변동성을 완화합니다. DBA는 중요한 쿼리에 대해 선호하는 실행 계획을 "고정"하거나, 쿼리 옵티마이저가 시간이 지나도 알려진 효율적인 계획을 사용하도록 계획 설정을 조정할 수 있습니다.

## 22. Aurora 엔드포인트

Aurora 엔드포인트는 여러 DB 인스턴스(쓰기를 위한 프라이머리와 읽기를 위한 하나 이상의 리플리카)로 구성된 데이터베이스 클러스터에 연결하는 복잡성을 추상화합니다. 이 추상화는 애플리케이션이 개별 인스턴스 호스트 이름을 추적할 필요를 없애고, 연결 관리를 단순화하며, 페일오버 발생 시 연결이 자동으로 재라우팅되도록 보장합니다.

### 22.1. 클러스터 엔드포인트

- **사용법:**
	읽기·쓰기 작업을 위해 Aurora 클러스터의 프라이머리(writer) 인스턴스에 연결합니다.
- **동작:**
	프라이머리 인스턴스가 실패하고 리플리카가 승격되면 클러스터 엔드포인트는 자동으로 새 프라이머리를 가리킵니다.

### 22.2. 리더 엔드포인트

- **사용법:**
	모든 Aurora 리플리카 간에 읽기 전용 쿼리를 균형 있게 분산합니다.
- **동작:**
	Aurora는 로드 밸런싱을 관리하고 사용 가능한 리플리카로 연결을 자동으로 지시해 읽기 확장성을 개선합니다.

### 22.3. 인스턴스 엔드포인트

- **사용법:**
	상세한 모니터링, 문제 해결, 성능 튜닝을 위해 특정 DB 인스턴스(프라이머리나 리플리카)에 직접 연결합니다.
- **동작:**
	클러스터나 리더 엔드포인트와 달리 인스턴스 엔드포인트는 페일오버 시 자동으로 변경되지 않으므로, 일반적으로 진단 목적으로 사용됩니다.

### 22.4. 커스텀 엔드포인트

- **사용법:**
	인스턴스 유형이나 구성에 기반해 DB 인스턴스의 특정 하위 집합으로 연결을 라우팅하는 자체 엔드포인트를 정의할 수 있게 합니다.
- **동작:**
	클러스터에 서로 다른 용량이나 역할을 가진 인스턴스가 포함되어 있고 그에 따라 워크로드를 격리하고 싶을 때 유용합니다.

### 22.5. Aurora Global Database Writer 엔드포인트

- **사용법:**
	Aurora Global Database 설정에서 이 특별한 엔드포인트는 프라이머리 리전에 대해 클러스터 엔드포인트처럼 작동합니다.
- **동작:**
	멀티 리전 배포에서 페일오버가 발생하면 자동으로 새 프라이머리를 가리키도록 업데이트되어, 리전 간 연결 관리를 단순화합니다.

## 23. 마이그레이션과 비용 이점

Aurora는 MySQL과 PostgreSQL의 드롭인 대체품으로 설계되었습니다. 높은 호환성으로 대부분의 기존 도구와 애플리케이션은 네이티브 덤프/복원 도구, 스냅샷, 또는 AWS DMS를 사용해 최소한의 변경으로 마이그레이션할 수 있습니다. Aurora의 비용 모델은 (서버리스의 경우) 사용량 기반이거나 온디맨드/예약 인스턴스를 기반으로 하며, 데이터가 여러 AZ에 복제되더라도 데이터의 한 복사본에 대해서만 비용을 지불하기 때문에 전체 비용은 상용 데이터베이스에 비해 매우 경쟁력을 유지합니다.
