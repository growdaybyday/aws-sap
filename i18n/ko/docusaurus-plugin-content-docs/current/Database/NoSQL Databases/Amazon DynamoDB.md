# Amazon DynamoDB

## 1. 소개

Amazon DynamoDB는 AWS가 제공하는 완전관리형 NoSQL 데이터베이스 서비스입니다. 어떤 규모에서든 낮은 지연 시간이 필요한 애플리케이션을 위해 설계된 DynamoDB는 하드웨어 프로비저닝, 구성, 복제, 확장 같은 관리 작업을 자동으로 처리하면서 빠르고 예측 가능한 성능을 제공합니다. 서버리스 서비스이기 때문에 서버와 인프라를 관리하는 부담을 없애주어 애플리케이션 구축에 집중할 수 있습니다.

## 2. DynamoDB의 특성

DynamoDB의 주요 특성과 설명은 다음과 같습니다.

1. **완전관리형 서비스**
	DynamoDB는 AWS가 완전히 관리합니다. 즉, 하드웨어 프로비저닝, 소프트웨어 패치, 설정, 구성, 복제, 확장을 걱정할 필요가 없습니다 — AWS가 이 모든 운영 측면을 처리하므로 애플리케이션 로직에 집중할 수 있습니다.

2. **높은 성능과 낮은 지연 시간**
	한 자릿수 밀리초 응답 시간을 제공하도록 설계된 DynamoDB는 읽기와 쓰기 작업 모두에서 빠르고 예측 가능한 성능을 보장합니다. 이 일관되게 낮은 지연 시간은 어떤 규모에서든 신속한 데이터 접근이 필요한 애플리케이션에 매우 중요합니다.

3. **매끄러운 확장성**
	DynamoDB는 애플리케이션 워크로드의 변화에 따라 처리량 용량을 자동으로 확장합니다. 트래픽이 갑자기 급증하든 대량의 데이터를 저장해야 하든, DynamoDB는 다운타임 없이 증가(또는 감소)할 수 있어 성능이 일관되게 유지됩니다.

4. **유연한 데이터 모델**
	키-값과 문서 데이터 구조를 모두 지원하는 DynamoDB는 구조화되거나 반구조화된 데이터를 저장하고 쿼리할 수 있게 합니다. 데이터는 테이블에 조직화되며, 항목(행과 유사)과 속성(열과 유사)으로 구성되고, 접근 패턴에 맞춰 단순 또는 복합 기본 키를 정의할 수 있습니다.

5. **고가용성과 내구성**
	DynamoDB의 데이터는 AWS 리전 내 여러 가용 영역(일반적으로 세 개의 복제본)에 자동으로 복제됩니다. 이 복제는 내구성을 향상시킬(데이터 손실 방지) 뿐만 아니라 하나 이상의 영역에 문제가 발생해도 고가용성을 보장합니다.

6. **강력한 보안**
	DynamoDB는 세밀한 접근 제어를 위해 AWS Identity and Access Management(IAM)와 통합됩니다. 또한 저장 시(AWS Key Management Service 사용)와 전송 중(HTTPS를 통해) 암호화를 제공해 데이터를 안전하게 유지합니다.

7. **내장된 백업과 복원 기능**
	DynamoDB는 온디맨드 백업과 특정 시점 복구 같은 기능을 제공합니다. 이 내장 도구들은 실수로 인한 데이터 손실을 방지하고 수동 개입 없이 테이블을 특정 시점으로 복원할 수 있게 합니다.

8. **DAX를 사용한 선택적 인메모리 캐싱**
	훨씬 더 빠른 읽기 성능이 필요한 애플리케이션을 위해 DynamoDB Accelerator(DAX)는 완전관리형 인메모리 캐시를 제공합니다. DAX는 응답 시간을 밀리초에서 마이크로초로 줄여, 읽기가 많은 워크로드에 이상적입니다.

## 3. 테이블, 항목, 속성

![dynamodb-table-items](@site/docs/Database/_assets/dynamodb-table-items.png)

다음은 DynamoDB의 기본 구성 요소입니다.

- **테이블**: 다른 데이터베이스 시스템과 마찬가지로 DynamoDB는 데이터를 테이블에 저장합니다. _테이블_은 데이터의 모음입니다.

- **항목**: 각 테이블은 0개 이상의 항목을 포함합니다. _항목_은 다른 모든 항목과 구별되는, 고유하게 식별 가능한 속성들의 그룹입니다. DynamoDB의 항목은 다른 데이터베이스 시스템의 행, 레코드, 튜플과 여러 면에서 유사합니다. DynamoDB에서는 테이블에 저장할 수 있는 항목 수에 제한이 없습니다. **항목의 최대 크기는 400킬로바이트입니다.**

- **속성**: 각 항목은 하나 이상의 속성으로 구성됩니다. _속성_은 더 이상 세분화할 필요가 없는 기본적인 데이터 요소입니다. 예를 들어 _People_ 테이블의 항목은 _PersonID_, _LastName_, _FirstName_ 등의 속성을 포함합니다. DynamoDB의 속성은 다른 데이터베이스 시스템의 필드나 열과 여러 면에서 유사합니다.
## 4. 기본 키

테이블을 생성할 때는 테이블 이름 외에도 테이블의 기본 키를 지정해야 합니다. 기본 키는 테이블 내의 각 항목을 고유하게 식별해, 두 항목이 동일한 키를 가질 수 없도록 합니다.

DynamoDB는 두 가지 종류의 기본 키를 지원합니다.

- **파티션 키**:
	_파티션 키_라고 불리는 하나의 속성으로 구성된 단순 기본 키입니다.

	DynamoDB는 파티션 키의 값을 내부 해시 함수의 입력으로 사용합니다. 해시 함수의 출력은 항목이 저장될 파티션(DynamoDB 내부의 물리적 스토리지)을 결정합니다.

    파티션 키만 있는 테이블에서는 두 항목이 동일한 파티션 키 값을 가질 수 없습니다.

- **파티션 키와 정렬 키**:
	_복합 기본 키_라고 불리는 이 키 유형은 두 개의 속성으로 구성됩니다. 첫 번째 속성은 _파티션 키_이고 두 번째 속성은 _정렬 키_입니다.

    DynamoDB는 파티션 키 값을 내부 해시 함수의 입력으로 사용합니다. 해시 함수의 출력은 항목이 저장될 파티션(DynamoDB 내부의 물리적 스토리지)을 결정합니다. 동일한 파티션 키 값을 가진 모든 항목은 정렬 키 값에 따라 정렬된 순서로 함께 저장됩니다.

    파티션 키와 정렬 키를 모두 가진 테이블에서는 여러 항목이 동일한 파티션 키 값을 가질 수 있습니다. 다만 그 항목들은 서로 다른 정렬 키 값을 가져야 합니다.

## 5. 보조 인덱스

테이블에 하나 이상의 보조 인덱스를 생성할 수 있습니다. _보조 인덱스_는 기본 키에 대한 쿼리 외에도 대체 키를 사용해 테이블의 데이터를 쿼리할 수 있게 합니다. DynamoDB가 인덱스 사용을 요구하지는 않지만, 인덱스를 사용하면 데이터를 쿼리할 때 애플리케이션에 더 많은 유연성을 제공할 수 있습니다. 테이블에 보조 인덱스를 생성한 후에는 테이블에서 하는 것과 거의 같은 방식으로 인덱스에서 데이터를 읽을 수 있습니다.

DynamoDB는 두 종류의 인덱스를 지원합니다.

- **글로벌 보조 인덱스:** 테이블과 다를 수 있는 파티션 키와 정렬 키를 가진 인덱스입니다. 글로벌 보조 인덱스의 기본 키 값은 고유할 필요가 없습니다. **테이블 생성 후에 생성할 수 있습니다.**
- **로컬 보조 인덱스:** 테이블과 동일한 파티션 키를 가지지만 다른 정렬 키를 가진 인덱스입니다. **테이블 생성 시 정의해야 합니다.**

DynamoDB에서 글로벌 보조 인덱스(GSI)는 전체 테이블에 걸치는 인덱스로, 모든 파티션 키에 걸쳐 쿼리할 수 있게 합니다. 로컬 보조 인덱스(LSI)는 기본 테이블과 동일한 파티션 키를 가지지만 다른 정렬 키를 가진 인덱스입니다.

DynamoDB의 각 테이블은 20개의 글로벌 보조 인덱스(기본 할당량)와 5개의 로컬 보조 인덱스 할당량을 가집니다.

## 6. 읽기 용량 단위(RCU)

1 RCU는 4KB 크기까지의 항목에 대해 초당 하나의 강력한 일관성 읽기를 수행하는 용량을 나타냅니다. 최종 일관성 읽기를 사용하는 경우 1 RCU는 동일한 크기의 항목에 대해 초당 최대 두 번의 읽기를 지원할 수 있습니다.

4KB보다 큰 항목의 경우 DynamoDB는 항목 크기를 다음 4KB 증분으로 올림합니다. 예를 들어 강력한 일관성으로 8KB 항목을 읽는 것은 2 RCU를 소비합니다.

최종 일관성 읽기는 강력한 일관성 읽기의 절반의 RCU를 소비합니다. 이 옵션은 데이터 신선도에서 약간의 지연이 허용될 때 자주 사용되어, 높은 처리량을 제공하면서 비용을 낮춥니다.

## 7. 쓰기 용량 단위(WCU)

1 WCU는 1KB 크기까지의 항목에 대해 초당 한 번의 쓰기를 수행하는 용량을 나타냅니다. 1KB보다 큰 항목의 경우 DynamoDB는 항목 크기를 다음 1KB 증분으로 올림합니다.

2KB 크기의 항목을 쓰는 것은 2 WCU가 필요합니다. 하나의 작업에서 더 많은 데이터를 쓸수록 더 많은 용량 단위가 소비됩니다.

WCU는 테이블이 초당 특정 볼륨의 쓰기 작업을 처리할 수 있도록 보장하며, 예상 워크로드에 기반해 프로비저닝하거나 온디맨드 모드를 사용해 자동으로 확장할 수 있습니다.
## 8. DynamoDB 처리량 용량

테이블의 처리량 모드는 테이블의 용량이 관리되는 방식을 결정합니다. 처리량 모드는 또한 테이블에 대한 읽기·쓰기 작업에 대해 어떻게 요금이 부과되는지도 결정합니다. Amazon DynamoDB에서는 다양한 워크로드 요구 사항을 수용하기 위해 테이블에 대해 **온디맨드 모드**와 **프로비저닝된 모드** 중에서 선택할 수 있습니다.

- **프로비저닝된 용량:**
  애플리케이션에 필요한 RCU와 WCU 수를 지정하면 DynamoDB가 그에 맞춰 처리량을 할당합니다. 예측 가능한 성장을 가진 안정적인 워크로드가 있고 애플리케이션의 용량 요구 사항을 신뢰성 있게 예측할 수 있다면 프로비저닝된 용량을 사용할 수 있습니다.
- **온디맨드 용량(기본값):**
  DynamoDB는 실제 트래픽 패턴에 따라 용량을 자동으로 조정하며 요청당 요금이 부과되어, 예측할 수 없는 워크로드의 확장을 단순화할 수 있습니다.

RCU와 WCU를 이해하고 올바르게 프로비저닝하는 것은 DynamoDB 애플리케이션에서 예측 가능한 성능을 유지하고 비용을 관리하는 데 매우 중요합니다.

## 9. DynamoDB 읽기 일관성

DynamoDB는 일관성과 용량 사용에 영향을 미치는 두 가지 데이터 읽기 옵션을 제공합니다.

- **최종 일관성 읽기(기본값):**
    최종 일관성 읽기(GetItem과 Query 같은 작업의 기본 동작)를 수행하면 읽기가 가장 최근의 쓰기를 즉시 반영하지 않을 수 있습니다. 즉, 쓰기가 방금 승인되었다면 이어지는 최종 일관성 읽기가 이전 버전의 데이터를 반환할 수 있습니다. 다만 새로운 업데이트가 발생하지 않으면 모든 복제본은 짧은 시간 내에 동일한 상태로 수렴합니다. 최종 일관성 읽기는 강력한 일관성 읽기에 비해 절반의 읽기 용량 단위를 소비합니다.

- **강력한 일관성 읽기:**
    ConsistentRead 파라미터를 true로 설정하면 강력한 일관성 읽기를 요청할 수 있습니다. 이 유형의 읽기는 항상 최신 데이터를 반환해, 읽기 이전의 모든 성공한 쓰기를 반영하도록 보장합니다. 강력한 일관성 읽기는 리더 노드(또는 유사한 메커니즘)와의 조율이 필요하기 때문에 더 많은 용량을 소비하고 약간 더 높은 지연 시간을 초래할 수 있습니다. 강력한 일관성 읽기는 데이터와 동일한 AWS 리전에서만 사용할 수 있다는 점에 유의하세요. 글로벌 테이블의 경우 읽기는 항상 최종 일관성입니다.

이 옵션들은 애플리케이션의 요구 사항에 따라 성능, 비용, 최신 데이터의 필요성 사이의 균형을 맞출 수 있게 합니다.

## 10. ACID 트랜잭션

Amazon DynamoDB는 여러 작업을 하나의 전부 아니면 전무(all-or-nothing) 액션으로 그룹화할 수 있는 ACID 트랜잭션을 지원합니다. 이 기능은 서비스에 내장되어 있어, 분산 트랜잭션을 직접 관리할 필요 없이 여러 항목을(경우에 따라 여러 테이블에 걸쳐) 원자성, 일관성, 격리성, 내구성(ACID)이 보장되는 방식으로 업데이트하거나 읽을 수 있습니다. 공식 문서를 기반으로 DynamoDB의 ACID 트랜잭션에 대한 핵심 사항은 다음과 같습니다.

1. **원자성**
    DynamoDB 트랜잭션(쓰기에는 `TransactWriteItems` API, 읽기에는 `TransactGetItems` API 사용)을 사용하면 트랜잭션 내 모든 작업이 성공하거나 아무것도 성공하지 않습니다. 조건이 실패하거나 충돌이 감지되면 전체 트랜잭션이 취소되어 데이터가 일관된 상태로 유지되도록 보장합니다.

2. **일관성**
    DynamoDB의 트랜잭션은 트랜잭션 API에서 작동할 때 직렬화 가능한 격리 수준을 제공합니다. 즉, 동시 트랜잭션의 결과는 마치 하나씩 순차적으로 실행된 것과 같습니다. 예를 들어 트랜잭션을 사용해 여러 항목을 업데이트할 때, 시스템은 트랜잭션 내의 각 읽기가 최신 커밋된 데이터를 보도록 보장하며, 트랜잭션 이전 또는 이후 상태 모두를 보게 됩니다.

3. **격리성**
    DynamoDB 트랜잭션은 트랜잭션의 중간 상태가 다른 작업에 절대 노출되지 않도록 보장합니다. 트랜잭션이 진행 중이더라도, 비트랜잭션 읽기는 트랜잭션 완료 이전이나 이후의 상태를 볼 수는 있지만 부분적으로 적용된 상태를 볼 수는 없습니다. 여러 항목에 걸친 일관된 스냅샷이 필요한 복잡한 워크플로의 경우, 격리되고 원자적인 읽기를 위해 `TransactGetItems`를 사용할 수 있습니다.

4. **내구성**
    트랜잭션이 성공적으로 커밋되면 모든 변경 사항은 디스크에 내구적으로 기록되고 여러 가용 영역에 걸쳐 복제됩니다. 이 복제는 DynamoDB의 기반이 되는 설계(SSD와 자동화된 백업 메커니즘 사용)와 결합되어, 하드웨어 장애가 발생하더라도 데이터가 안전하게 유지되도록 보장합니다.

## 11. 글로벌 테이블

글로벌 테이블은 Amazon DynamoDB의 완전관리형 멀티 리전, 멀티 액티브 기능으로, 테이블을 여러 AWS 리전에 걸쳐 자동으로 복제합니다. 이 복제는 전역적으로 분산된 애플리케이션이 낮은 지연 시간과 고가용성으로 데이터를 읽고 쓸 수 있게 합니다.

핵심 사항은 다음과 같습니다.

- **멀티 리전 복제:**
	글로벌 테이블은 선택한 AWS 리전 전반에 데이터를 자동으로 복제합니다. 즉, 한 리전에서 데이터가 쓰이면 그 변경 사항은 다른 리전의 복제본 테이블로 비동기적으로 전파됩니다.

- **멀티 액티브 쓰기:**
	글로벌 테이블이 배포된 모든 리전에서 쓰기 작업을 수행할 수 있습니다. 트랜잭션의 ACID 보장은 소스 리전 내에서만 적용되지만, 멀티 액티브 쓰기는 로컬의 낮은 지연 시간 쓰기와 향상된 가용성을 가능하게 합니다.

- **고가용성과 재해 복구:**
	데이터가 지리적으로 분산된 여러 리전에 복제되기 때문에, 글로벌 테이블은 전체 AWS 리전이 일시적으로 접근 불가능해지더라도 애플리케이션이 계속 사용 가능하도록 보장하는 데 도움을 줍니다.

- **매끄러운 통합:**
	글로벌 테이블은 표준 테이블과 동일한 DynamoDB API를 사용하므로, 애플리케이션 코드를 변경하지 않고도 멀티 리전 복제를 활성화할 수 있습니다. 또한 암호화를 위한 AWS KMS 같은 다른 AWS 서비스와도 통합되어 데이터가 안전하게 유지되도록 보장합니다.

- **리전 간 최종 일관성:**
	글로벌 테이블은 원본 리전 내에서는 ACID 트랜잭션을 제공하지만, 다른 리전으로의 복제는 비동기적으로 이루어집니다. 즉, 트랜잭션이 성공한 직후 일부 리전은 업데이트가 전파될 때까지 일시적으로 이전 버전의 데이터를 볼 수 있습니다.


글로벌 테이블은 전 세계적인 사용자 기반을 가진 애플리케이션이나, 데이터를 사용자 위치에 가깝게 유지함으로써 향상된 복원력과 낮은 지연 시간이 필요한 애플리케이션에 이상적입니다.

## 12. DynamoDB Streams

DynamoDB Streams는 DynamoDB 테이블의 데이터 수정 이벤트를 캡처하는 선택적 기능입니다. 이 이벤트에 대한 데이터는 거의 실시간으로, 이벤트가 발생한 순서대로 스트림에 나타납니다.

각 이벤트는 _스트림 레코드_로 표현됩니다. 테이블에 스트림을 활성화하면 DynamoDB Streams는 다음 이벤트 중 하나가 발생할 때마다 스트림 레코드를 씁니다.

- 테이블에 새 항목이 추가됨: 스트림은 모든 속성을 포함한 전체 항목의 이미지를 캡처합니다.
- 항목이 업데이트됨: 스트림은 항목에서 수정된 모든 속성의 "이전"과 "이후" 이미지를 캡처합니다.
- 항목이 테이블에서 삭제됨: 스트림은 삭제 전 전체 항목의 이미지를 캡처합니다.

각 스트림 레코드는 테이블 이름, 이벤트 타임스탬프, 기타 메타데이터도 포함합니다. 스트림 레코드의 수명은 24시간이며, 그 이후에는 스트림에서 자동으로 제거됩니다.

DynamoDB Streams를 AWS Lambda와 함께 사용해 _트리거_ — 스트림에 관심 있는 이벤트가 나타날 때마다 자동으로 실행되는 코드 — 를 만들 수 있습니다. 예를 들어 회사의 고객 정보를 담은 _Customers_ 테이블이 있다고 가정해봅시다. 새 고객마다 "환영" 이메일을 보내고 싶다고 가정합니다. 해당 테이블에 스트림을 활성화하고 그 스트림을 Lambda 함수와 연관시킬 수 있습니다. 이 Lambda 함수는 새로운 스트림 레코드가 나타날 때마다 실행되지만, _Customers_ 테이블에 추가된 새 항목만 처리합니다. `EmailAddress` 속성을 가진 모든 항목에 대해 Lambda 함수는 해당 주소로 이메일을 보내기 위해 Amazon Simple Email Service(Amazon SES)를 호출합니다.

## 13. Time to Live

DynamoDB의 Time to Live(TTL)는 지정된 만료 시간이 지나면 항목을 삭제하는 자동 메커니즘입니다. 동작 방식과 유용성은 다음과 같습니다.

- **만료 속성:**
    각 항목의 만료 시간을 나타내는 특정 속성(일반적으로 초 단위의 유닉스 에포크 타임스탬프를 저장)을 지정합니다. 현재 시간이 이 값을 초과하면 항목은 삭제 대상이 됩니다.

- **자동 삭제:**
    DynamoDB는 TTL 속성이 활성화된 항목을 지속적으로 모니터링합니다. 만료된 항목은 백그라운드에서 자동으로 제거되어, 수동 개입이나 추가 쓰기 용량 없이 테이블을 간결하게 유지하고 스토리지 비용을 줄이는 데 도움을 줍니다.

- **비용 효율성:**
    TTL 프로세스는 비동기적으로 작동하므로 삭제가 프로비저닝된 처리량을 소비하지 않습니다. 이는 세션 데이터, 로그, 임시 항목처럼 제한된 기간 동안만 관련이 있는 데이터를 관리하는 효율적인 방법입니다.

- **사용 사례:**
    TTL은 특정 기간이 지나면 데이터가 자연스럽게 쓸모없어지는 시나리오에 특히 유용합니다. 예를 들어 사용자 세션 정보, 캐시된 결과, 임시 토큰을 자동으로 정리할 수 있어 수동 유지보수나 복잡한 애플리케이션 로직의 필요성을 줄여줍니다.

- **설정과 관리:**
    테이블에서 TTL을 활성화하려면 만료 타임스탬프를 담고 있는 속성을 지정하기만 하면 됩니다. 활성화되면 DynamoDB는 만료된 항목을 자동으로 제거하지만, 삭제가 즉각적이지는 않으며 일반적으로 만료 후 48시간 이내에 발생한다는 점에 유의하세요.

## 14. Zero-ETL 통합

DynamoDB의 Zero-ETL 통합은 별도의 ETL(추출, 변환, 로드) 파이프라인을 구축하고 관리할 필요 없이 DynamoDB 데이터를 다른 AWS 서비스(분석을 위한 Amazon Redshift나 고급 검색을 위한 Amazon OpenSearch Service 등)와 매끄럽게 통합하는 기능을 말합니다. 이 통합은 "바로 사용 가능한" 방식으로 작동해 다음을 할 수 있게 합니다.

- **데이터를 직접 분석:**
    거의 실시간으로 DynamoDB 데이터를 쿼리하거나 분석할 수 있게 하는 통합(예: Amazon Redshift Spectrum이나 OpenSearch 사용)을 활용해, 데이터를 수동으로 추출, 변환한 다음 다른 시스템에 로드할 필요가 없습니다.

- **데이터 파이프라인 단순화:**
    DynamoDB를 분석과 검색 서비스에 직접 연결할 수 있으므로, 전통적인 ETL 프로세스와 관련된 복잡성, 지연 시간, 추가 비용을 피할 수 있습니다. 별도의 시스템으로 데이터를 전송하는 오버헤드가 프로덕션 워크로드에 영향을 주지 않습니다.

- **신선도와 효율성 유지:**
    Zero-ETL 통합을 사용하면 DynamoDB의 데이터 수정 사항이 (흔히 DynamoDB Streams나 내장 통합 기능을 통해) 즉시 다운스트림 시스템에서 사용 가능해져, 분석과 검색 애플리케이션이 항상 최신 데이터로 작동하도록 보장합니다.

## 15. 캐싱

AWS는 DynamoDB와 매끄럽게 작동하는 인메모리 캐시로서 DynamoDB Accelerator(DAX)를 제공합니다. 알아야 할 사항은 다음과 같습니다.

- **DynamoDB Accelerator(DAX):**
    DAX는 DynamoDB를 위해 특별히 설계된 완전관리형 인메모리 캐싱 서비스입니다. 읽기 쿼리의 결과를 캐싱해 애플리케이션이 밀리초가 아닌 마이크로초 단위로 데이터를 검색할 수 있게 합니다. write-through 방식이기 때문에 DynamoDB에서 데이터를 업데이트할 때마다 DAX는 캐시를 자동으로 업데이트(또는 무효화)해 이후의 읽기가 최신 데이터를 반환하도록 보장합니다.

- **성능 개선:**
    DAX는 읽기 집약적 워크로드의 응답 시간을 최대 10배까지 줄일 수 있어, 읽기 트래픽이 많거나 예측할 수 없는 급증을 경험하는 애플리케이션에 이상적입니다. 이 이점은 기반이 되는 DynamoDB 테이블을 반복적으로 쿼리하는 대신 자주 요청되는 항목을 메모리에서 직접 제공하기 때문에 발생합니다.

- **손쉬운 통합:**
    DAX는 DynamoDB와 API 호환되므로, 캐싱의 혜택을 누리기 위해 애플리케이션 코드를 크게 변경할 필요가 없습니다. 사용하고자 한다면 기존 DynamoDB SDK 호출을 DAX 클러스터를 통해 자동으로 라우팅할 수 있습니다.

- **일관성 고려 사항:**
    DAX는 최종 일관성 읽기를 지원합니다. 애플리케이션이 강력한 일관성 읽기를 요구한다면 DAX를 건너뛰고 DynamoDB에 직접 접근해야 합니다. 이 트레이드오프는 애플리케이션의 데이터 신선도 요구 사항에 따라 고려해야 할 중요한 사항입니다.

- **읽기 용량 소비 감소:**
    자주 사용되는 항목을 메모리에 캐싱함으로써 DAX는 DynamoDB 테이블에 도달하는 읽기 작업 수를 줄여, 비용을 낮추고 전체 처리량을 개선할 수 있습니다.


## 16. Amazon S3로 데이터 가져오기 및 내보내기

### 16.1. DynamoDB에서 Amazon S3로 데이터 내보내기

DynamoDB는 테이블의 데이터를 Amazon S3 버킷으로 직접 내보낼 수 있습니다. 이 내보내기는 테이블의 프로비저닝된 읽기 용량을 소비하지 않고 수행되며 DynamoDB의 특정 시점 복구(PITR) 기능과 통합되어 있습니다. 전체 테이블 데이터를 내보내거나 특정 시점부터의 증분 변경 사항을 DynamoDB JSON이나 Amazon Ion 같은 형식으로 내보낼 수 있습니다.

**사용 사례:**
- **분석:** Amazon Athena, Amazon EMR, AWS Glue 같은 AWS 서비스를 사용해 분석하기 위해 데이터를 Amazon S3로 내보냅니다.
- **데이터 아카이빙:** 규정 준수나 감사를 위한 과거 스냅샷을 유지합니다.
- **데이터 마이그레이션:** 계정 간 또는 리전 간 마이그레이션을 위해 테이블 데이터를 내보냅니다.

### 16.2. Amazon S3에서 DynamoDB로 데이터 가져오기

DynamoDB는 또한 Amazon S3의 데이터를 새 DynamoDB 테이블로 직접 가져오는 것도 지원합니다. 내보내기와 마찬가지로 이 프로세스는 완전관리형이며 DynamoDB JSON이나 Amazon Ion 같은 형식으로 내보낸 데이터를 활용합니다. 가져오기 프로세스는 S3 버킷의 데이터를 기반으로 새 테이블을 생성하며, 이는 데이터 마이그레이션이나 백업 복원에 특히 유용합니다.

**사용 사례:**
- **데이터 마이그레이션:** 한 테이블에서 S3로 내보낸 다음 다른 테이블로 가져와 계정이나 리전 간에 데이터를 마이그레이션합니다.
- **테스트와 개발:** 처음부터 데이터를 다시 수집할 필요 없이 새 테이블에 테스트 데이터를 빠르게 로드합니다.

## 17. 백업과 복원

### 17.1. 지속적인 백업과 특정 시점 복구

DynamoDB의 지속적인 백업 기능은 테이블 데이터의 변경 이력 전체를 자동으로 캡처하고 보존합니다. 테이블에서 특정 시점 복구(PITR)를 활성화하면 DynamoDB는 해당 테이블의 모든 쓰기, 업데이트, 삭제를 최대 35일까지 지속적으로 백업합니다.

- **동작 방식:**
    - **자동적이고 지속적:** 활성화되면 DynamoDB는 수동 개입이나 추가 용량 프로비저닝 없이 테이블을 지속적으로 백업합니다.
    - **복원 유연성:** 보존 기간 내의 특정 초 단위로 테이블을 복원할 수 있습니다. 즉, 데이터가 실수로 삭제되거나 손상된 경우 정확한 시점의 상태로 테이블을 복구할 수 있습니다.
    - **성능 영향 없음:** 백업 프로세스는 백그라운드에서 실행되며 테이블의 프로비저닝된 처리량을 소비하지 않습니다.
- **이점:**
    - **데이터 보호:** 정확한 복원을 통해 실수로 인한 쓰기, 삭제, 데이터 손상에 대한 안전장치를 제공합니다.
    - **운영 단순성:** AWS가 완전히 관리하므로 별도의 백업 시스템을 설정하거나 관리할 필요가 없습니다.

### 17.2. 온디맨드 백업과 복원

온디맨드 백업과 복원은 언제든지 DynamoDB 테이블의 전체 수동 백업을 생성할 수 있게 하는 기능입니다. 지속적인 백업(PITR)과 달리, 이 백업은 시작한 시점에 촬영된 스냅샷이며 삭제할 때까지 보존됩니다.

- **동작 방식:**
    - **수동 스냅샷:** 전체 테이블의 데이터를 캡처하기 위해 (AWS Management Console, CLI, 또는 API를 통해) 백업을 트리거합니다.
    - **복원 프로세스:** 백업을 사용해 테이블을 동일한 계정/리전 또는 다른 계정/리전의 새 테이블로 복원할 수 있으며, 이는 마이그레이션, 테스트, 데이터 복구에 유용합니다.
    - **용량 소비 없음:** 백업 프로세스는 테이블의 읽기·쓰기 용량을 소비하지 않으며 테이블의 성능에 영향을 주지 않고 작동합니다.
- **이점:**
    - **규정 준수와 아카이빙:** 규정 준수, 감사, 과거 분석을 위한 장기 데이터 보존에 유용합니다.
    - **유연성:** 언제 백업을 생성할지 통제할 수 있으며 필요한 만큼 보존할 수 있습니다.
    - **손쉬운 마이그레이션:** 복잡한 ETL 파이프라인 없이도 환경이나 계정 간 데이터 이동을 가능하게 합니다.

## 18. DynamoDB 가격 정책

Amazon DynamoDB 가격 정책은 세 가지 주요 구성 요소를 중심으로 구성됩니다.

- **용량:**
    예측 가능한 워크로드를 위해 (초당 설정된 RCU와 WCU) 프로비저닝된 용량, 또는 가변적인 트래픽을 위해 (요청당 지불) 온디맨드 용량 중에서 선택합니다.

- **스토리지:**
    테이블과 인덱스에 저장된 데이터에 대해 월별 GB당으로 계산되어 요금이 부과됩니다.

- **추가 기능:**
    비용에는 백업과 복원(온디맨드 또는 지속적인 PITR), 캐싱을 위한 DAX, 멀티 리전 복제를 위한 글로벌 테이블도 포함될 수 있습니다.

## 19. 보안

Amazon DynamoDB 보안은 저장 시와 전송 중 모두에서 데이터를 보호하는 데 도움을 주는 견고한 다층 프레임워크를 기반으로 구축되어 있습니다. 핵심 요소는 다음과 같습니다.

### 19.1. 공동 책임 모델

- **클라우드의 보안:** AWS는 물리적 인프라, 데이터센터, 네트워크, 하드웨어를 관리합니다.
- **클라우드 내 보안:** 사용자는 IAM 정책 설정, 암호화, VPC 엔드포인트를 포함해 데이터에 대한 접근을 구성하고 관리하는 책임이 있습니다.

### 19.2. 데이터 보호

- **저장 데이터 암호화:** DynamoDB에 저장된 모든 데이터(테이블, 인덱스, 스트림, 백업)는 AWS Key Management Service(KMS)의 키를 사용해 암호화됩니다. AWS 소유, AWS 관리형, 또는 고객 관리형 키 중에서 선택할 수 있습니다.
- **전송 중 암호화:** DynamoDB와의 모든 통신은 HTTPS(TLS)를 사용해 보안이 유지되어, 애플리케이션과 DynamoDB 사이를 이동하는 동안 데이터가 암호화되도록 보장합니다.

### 19.3. 접근 제어

- **IAM 정책:** AWS Identity and Access Management(IAM)를 사용해 세밀한 권한을 정의하고 DynamoDB 리소스에 대한 접근을 제어합니다.
- **리소스 기반 및 속성 기반 접근 제어:** DynamoDB 테이블에 직접 정책을 적용하고 특정 속성을 기반으로 접근을 제한하는 조건을 사용합니다.
- **VPC 엔드포인트:** Amazon VPC 내에서 DynamoDB에 접근하기 위해 VPC 엔드포인트를 사용함으로써 트래픽을 보안화해, 데이터가 퍼블릭 인터넷에 노출되지 않도록 합니다.

### 19.4. 규정 준수와 모니터링

- **규정 준수 인증:** DynamoDB는 여러 산업 표준과 규정 준수 프로그램(예: HIPAA, PCI DSS, GDPR)을 충족합니다.
- **모니터링과 로깅:** CloudTrail, Config, Security Hub 같은 AWS 서비스는 DynamoDB에 대한 접근을 모니터링하고 감사하는 데 도움을 주어, 지속적인 규정 준수와 보안을 보장합니다.

## 20. 결론

Amazon DynamoDB는 AWS의 NoSQL 제품군의 핵심으로서, 현대 애플리케이션 요구 사항에 최적화되고 완전관리형인, 고가용성이고 확장 가능하며 안전한 데이터베이스 솔루션을 제공합니다. 대규모에서 일관된 성능이 필요하든, 유연한 데이터 모델 지원이 필요하든, 다른 AWS 서비스와의 통합이 필요하든, DynamoDB는 분산 데이터베이스 관리의 많은 복잡성을 추상화하면서 이러한 요구를 충족하도록 설계되었습니다.

더 자세한 내용은 공식 [AWS 리소스](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Introduction.html)를 참고하세요.
