# Amazon EC2 - Fleets

## 1. 소개

**Amazon EC2 Fleet**과 **Spot Fleet**은 남는(Spot) 용량이나 Spot과 온디맨드 인스턴스의 조합을 사용해 대량의 인스턴스를 단일 API 호출로 시작하고 관리할 수 있게 하는 Amazon EC2의 기능입니다. 여러 인스턴스 유형, 가용 영역, 구매 옵션(Spot, 온디맨드, 또는 조합)을 지정할 수 있게 함으로써, 이 플릿들은 애플리케이션의 비용과 가용성을 모두 최적화하는 데 도움을 줍니다. 인스턴스 구성을 정의하기 위해 시작 템플릿이나 시작 파라미터를 사용하며, 대규모로 용량을 프로비저닝하는 데 높은 수준의 유연성을 제공합니다.

## 2. EC2 Fleet vs. Spot Fleet

**EC2 Fleet**과 **Spot Fleet** 모두 단일 API 호출로 대규모 EC2 인스턴스 그룹을 프로비저닝할 수 있게 하지만, 초점과 기능, 장기 로드맵에서 차이가 있습니다.
### 2.1. EC2 Fleet

EC2 Fleet은 정의된 목표 용량을 충족하기 위해 여러 인스턴스 유형과 구매 옵션(Spot, 온디맨드, 심지어 Reserved까지 조합)을 시작할 수 있게 합니다.

세 가지 요청 유형을 지원합니다.
- **Instant:** 인스턴스를 동기적으로 시작하고 즉시 결과를 반환합니다.
- **Request:** 용량에 대한 일회성 요청을 비동기적으로 배치합니다.
- **Maintain:** 플릿을 원하는 용량으로 지속적으로 유지하려 시도하며, 중단된 인스턴스를 교체합니다.

할당 전략(용량 최적화나 가격-용량 최적화 등), 인스턴스 가중치, 가용 영역·인스턴스 유형 전반의 다양화에 대해 세밀한 제어를 할 수 있습니다.

EC2 Fleet은 **API/CLI를 통해서만 사용 가능**하며(콘솔 기본 지원 없음), 새로운 배포를 위해 권장되고 활발히 유지 관리되는 서비스입니다.
### 2.2. Spot Fleet

Spot Fleet은 Spot 인스턴스 시작에 초점을 맞춘 **레거시 메커니즘**입니다. 다양한 Spot 풀에서 지정된 목표 용량을 요청할 수 있게 합니다.

두 가지 모드를 지원합니다.
- **Request:** 자동 보충 없는 일회성 요청입니다.
- **Maintain:** 중단된 Spot 인스턴스를 교체해 목표 용량을 계속 충족하려 시도합니다.

EC2 Fleet과 달리 Spot Fleet은 **AWS Management Console에서 지원**됩니다. 다만 이는 이전 API를 기반으로 하며 AWS의 향후 대규모 투자 계획이 없습니다. **콘솔 기반 관리가 필요할 때만 권장하는 것이 일반적입니다.**

## 3. 플릿 요청 유형

두 플릿 유형 모두 용량이 프로비저닝되고 유지되는 방식을 결정하는 요청 유형을 선택할 수 있게 합니다.

- **Maintain**: 플릿은 중단된 인스턴스를 자동으로 교체하려 시도해 목표 용량이 시간이 지나도 유지되도록 합니다.
- **Request**: 목표 용량에 대한 일회성 요청이 이루어집니다. 인스턴스가 중단되거나 용량을 즉시 사용할 수 없어도 자동 보충은 이루어지지 않습니다.
- **Instant**(EC2 Fleet에서만 사용 가능): 인스턴스를 즉시 시작하고 API 응답에 결과를 반환하는 동기적인 일회성 요청입니다.

## 4. 용량 풀이란?

Spot 용량 풀은 특정 구성을 공유하는 사용 가능한(사용되지 않은) EC2 인스턴스의 집합을 가리킵니다. 일반적으로 이 구성은 인스턴스 유형과 가용 영역 같은 요소로 정의됩니다. 예를 들어 특정 가용 영역(예: _us-east-1a_)의 모든 남는 _m5.large_ 인스턴스가 하나의 풀을 형성합니다. 플릿은 이 풀들을 사용해 서로 다른 조합에 걸쳐 용량을 할당하며, 이는 비용을 최적화하고 여러 풀에 분산시켜 중단 가능성을 줄이는 데 도움이 됩니다.
## 5. 할당 전략

사용 가능한 용량 풀에서 인스턴스를 시작할 때, 플릿은 할당 전략을 사용해 어느 용량 풀(인스턴스 유형과 가용 영역의 조합)에서 가져올지 선택합니다. 공식 AWS 문서는 여러 전략을 나열합니다.

- **최저가(Lowest Price)**(레거시, 권장하지 않음): 가장 저렴한 사용 가능 풀에서 인스턴스를 요청하지만, 중단률이 더 높을 수 있습니다.
- **가격-용량 최적화(Price Capacity Optimized)**(권장): 가격과 용량을 모두 고려해, 여유 용량이 최적이고 경쟁력 있는 가격을 가진 풀을 선택합니다.
- **용량 최적화(Capacity Optimized) / 용량 최적화 우선순위(Capacity Optimized Prioritized)**: 가용 용량이 가장 많은 풀에서 인스턴스를 시작하는 데 초점을 맞춰, 중단 가능성을 낮추는 데 도움이 됩니다.
- **다양화(Diversified)**: 지정된 풀에 걸쳐 인스턴스를 균등하게 분산시켜 위험을 더 줄입니다.

## 6. 주요 구성 옵션

플릿 요청(EC2 Fleet이든 Spot Fleet이든)을 설정할 때는 여러 핵심 파라미터를 구성할 수 있습니다.

- **목표 용량(Target Capacity)**: 시작하려는 인스턴스나 컴퓨팅 단위의 수입니다.
- **시작 템플릿/오버라이드**: 인스턴스 구성(AMI, 인스턴스 유형, 키 페어 등)을 정의하며, 다양화를 위한 여러 오버라이드를 포함할 수 있습니다.
- **인스턴스 가중치**: 컴퓨팅 용량을 기준으로 서로 다른 인스턴스 유형에 선택적으로 가중치를 할당합니다.
- **온디맨드와 Spot 조합**: 목표 용량 중 얼마를 온디맨드 인스턴스로, 얼마를 Spot 인스턴스로 충족할지 지정합니다.
- **클라이언트 토큰과 IAM 역할**: 멱등성을 보장하고 플릿이 여러분을 대신해 리소스를 관리할 권한을 부여합니다.
- **지출 한도와 최대 가격**: (Spot 인스턴스의 경우) 다만 중단을 줄이기 위해 최대 가격을 온디맨드 요율로 기본 설정하는 것이 일반적으로 권장됩니다.

추가 옵션으로는 초과 용량 처리 정책, 중단 시 종료 동작(예: 중지, 최대 절전, 종료), 리소스 관리를 위한 태깅 옵션도 있습니다.

## 7. 플릿 생명주기 단계

플릿의 생명주기는 인스턴스를 시작하는 요청을 제출하는 시점부터, 플릿이 용량을 능동적으로 관리하는 기간, 요청의 최종 수정이나 취소까지 모든 단계를 포함합니다.

![fleet-price](@site/docs/Compute/_assets/fleet-price.png)

### 7.1. 제출/생성

- **요청 제출:**
    EC2 Fleet이나 Spot Fleet API/CLI를 사용해 플릿 요청을 제출하는 것으로 시작합니다.
- **초기 평가:**
    요청이 제출되면 플릿은 평가 단계에 들어갑니다. 이 단계에서 AWS는 요청이 유효한지, 계정의 할당량을 충족하는지 확인합니다.
    - Spot Fleet의 경우 이 단계는 **"submitted"** 상태로 반영됩니다.
### 7.2. 활성 단계

- **프로비저닝과 실행:**
    승인되면 플릿 요청은 **"active"** 상태에 들어갑니다. 이 상태에서 AWS는 사용 가능한 용량 풀에서 요청된 인스턴스를 시작하려 능동적으로 시도합니다.
- **용량 유지(Maintain 유형):**
    - **"maintain"**으로 구성된 요청의 경우, 시작된 Spot 인스턴스가 용량 변화로 인해 중단되거나 종료되면 AWS는 목표 용량을 충족하기 위해 자동으로 교체를 시도합니다.
- **생명주기 모니터링:**
    활성 단계 전반에서 플릿은 인스턴스의 상태를 모니터링합니다. AWS는 중단을 선제적으로 관리하는 데 도움이 되는 신호(리밸런스 권장 등)를 제공할 수 있습니다.
### 7.3. 수정

- **플릿 구성 업데이트:**
    **maintain**으로 설정된 플릿의 목표 용량이나 다른 구성 세부 사항을 변경해야 한다면 요청을 수정할 수 있습니다. 이 기간 동안 플릿은 변경 사항이 완전히 처리될 때까지 **"modifying"** 상태에 있습니다.
### 7.4. 취소와 종료

- **취소 시작:**
    플릿 요청을 취소(또는 삭제)하기로 결정하면, 실행 중인 모든 인스턴스가 즉시 종료되지는 않습니다. 대신 요청은 취소 관련 상태로 전환됩니다.
- **취소 상태:**
    - **Cancelled_running:**
        - 요청이 취소되어 새 인스턴스는 시작되지 않지만, 이미 시작된 인스턴스는 계속 실행됩니다.
    - **Cancelled_terminating:**
        - 취소 과정에는 인스턴스 종료가 포함될 수 있습니다. 이 상태에서는 플릿이 실행 중인 인스턴스를 종료하는 과정에 있습니다.
    - **Cancelled:**
        - 모든 인스턴스가 종료되거나 자연스럽게 생명주기를 마치면, 요청은 최종 **"cancelled"** 상태에 들어갑니다.

이 상태들은 취소 후에도 실행 중인 인스턴스를 계속 유지할지, 자동으로 종료할지 관리하는 데 도움이 됩니다.
## 8. Spot 인스턴스의 사용 사례

- **데이터 분석:** 대규모 데이터 처리 작업을 여러 Spot 인스턴스에 분산시킬 수 있습니다. 일부 인스턴스가 회수되어도 작업은 나머지 또는 새로 시작된 Spot 인스턴스에서 계속됩니다.
- **렌더링과 배치 처리:** 영화 렌더링, 이미지 처리, CI(지속적 통합) 작업은 인스턴스가 간헐적으로 사라지는 것을 감내할 수 있다면 저비용 용량의 이점을 누릴 수 있습니다.
- **복원력 있는 웹 서비스:** 일부 마이크로서비스는 매끄럽게 확장하고 일시적인 컴퓨팅 용량을 처리할 수 있습니다. 특히 스테이트리스하고 적절히 오케스트레이션되어 있다면 더욱 그렇습니다.
## 9. 결론

Spot 인스턴스와 Spot 플릿은 특히 잠재적인 중단을 감내할 수 있는 워크로드에서 AWS 컴퓨팅 비용을 최적화하는 강력한 메커니즘을 제공합니다. 최대 가격 임계값을 설정함으로써 컴퓨팅 소비의 경제성에 대한 제어권을 유지할 수 있습니다.

Spot 인스턴스의 비용 최적화 원칙과 모범 사례에 대해 더 깊이 알아보려면 공식 AWS 백서 **[Amazon EC2 Spot 인스턴스 개요](https://docs.aws.amazon.com/pdfs/whitepapers/latest/cost-optimization-leveraging-ec2-spot-instances/cost-optimization-leveraging-ec2-spot-instances.pdf)**를 참고하세요. 이 백서는 Spot 인스턴스를 언제, 어떻게 효과적으로 사용할지, 모범 사례, 다른 AWS 서비스와의 통합을 자세히 다룹니다.
