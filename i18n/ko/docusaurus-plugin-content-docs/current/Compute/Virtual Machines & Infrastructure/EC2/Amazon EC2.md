# Amazon EC2

## 1. 소개

Amazon Elastic Compute Cloud(EC2)는 클라우드에서 크기를 조정할 수 있는 컴퓨팅 용량을 제공하는 Amazon Web Services(AWS)의 핵심 서비스입니다. 2006년에 도입된 EC2는 전 세계 어디서든 가상 서버를 빠르게 프로비저닝하고 확장 가능하게 배포할 수 있게 함으로써 개발자를 위한 웹 규모 컴퓨팅을 단순화하도록 설계되었습니다. 이런 유연성 덕분에 단순한 웹 호스팅부터 복잡하고 고성능인 컴퓨팅 워크로드까지 다양한 애플리케이션을 실행하는 기반 구성 요소로 자리 잡았습니다.

## 2. EC2 인스턴스 유형

Amazon EC2는 요구사항에 가장 잘 맞는 유형을 선택할 수 있도록 다양한 인스턴스 유형을 제공합니다. 인스턴스 유형은 _인스턴스 계열_과 _인스턴스 크기_를 기준으로 이름이 붙습니다. 인스턴스 계열의 첫 자리는 _시리즈_를 나타냅니다(예: `c`). 두 번째 자리는 _세대_를 나타냅니다(예: `7`). 세 번째 자리는 _옵션_을 나타냅니다(예: `gn`). 마침표(`.`) 뒤에는 `small`이나 `4xlarge` 같은 인스턴스 크기, 또는 베어메탈 인스턴스의 경우 `metal`이 옵니다.

- **R(메모리 최적화)**
    인메모리 캐시나 고성능 데이터베이스(예: 인메모리 분석) 같은 워크로드에 이상적입니다. 대용량 RAM에 중점을 둡니다.

- **C(컴퓨팅 최적화)**
    고성능 웹 서버, 머신 러닝 추론, 컴퓨팅 집약적 데이터베이스 같은 CPU 집약적 작업을 위해 설계되었습니다.

- **M(범용)**
    CPU와 메모리 측면에서 균형이 잡혀 있어 웹 애플리케이션, 애플리케이션 서버, 소규모·중간 규모 데이터베이스에 유용합니다.

- **I(스토리지 최적화)**
    인스턴스 스토어 볼륨으로 높은 로컬 I/O 처리량을 제공합니다. NoSQL 데이터베이스나 데이터 웨어하우징처럼 빠르고 낮은 지연 시간의 스토리지가 필요한 트랜잭션 워크로드에 적합합니다.

- **G(GPU 최적화)**
    그래픽 집약적 애플리케이션(예: 비디오 렌더링)과 머신 러닝 모델 학습을 위한 강력한 GPU를 갖추고 있습니다.

- **T(버스터블 인스턴스, 예: T2와 T3)**
    기본 CPU 성능을 제공하면서 짧은 기간 동안 CPU 사용량을 버스트할 수 있습니다. 수요가 간헐적이거나 예측 불가능하게 급증하는 애플리케이션에 훌륭합니다.

    - **T2/T3 Unlimited**: 장기간에 걸쳐 기준선을 초과하는 워크로드를 위해 지속적인 버스팅을 허용합니다.


> **시험 팁:** 시험 시나리오에서 빅데이터, 메모리 캐시, HPC를 언급한다면, 항상 인스턴스 계열이 그런 유형의 부하에 적합한지 확인하세요. 리소스가 맞지 않으면 불필요한 비용이나 성능 병목이 발생할 수 있습니다.

### 2.1. Graviton 프로세서

Amazon EC2 Graviton 프로세서는 클라우드 워크로드를 위해 최적화된 성능과 비용 효율성을 제공하도록 AWS가 설계한 커스텀 Arm 기반 프로세서입니다. 전통적인 x86 기반 인스턴스를 대체할 고성능이면서도 에너지 효율적인 대안을 제공하며, M6g, C6g, R6g, T4g를 포함한 다양한 EC2 인스턴스 계열에서 사용되어 범용, 컴퓨팅 최적화, 메모리 최적화, 버스터블 애플리케이션을 대상으로 합니다.

- **Graviton2**: 5세대 x86 대비 최대 ~40% 향상된 가격 대비 성능.
- **Graviton3**: Graviton2 대비 최대 3배 향상된 성능.
- **호환성**: 인기 있는 Linux 배포판(예: Amazon Linux 2, Ubuntu). Windows Server는 지원하지 않습니다.

가장 정확하고 최신인 정보는 [Amazon EC2 Graviton 프로세서](https://aws.amazon.com/ec2/graviton/)를 참고하세요.

### 2.2. 베어메탈 인스턴스

Amazon EC2 베어메탈 인스턴스는 AWS 서버의 기반이 되는 물리적 하드웨어에 직접 접근할 수 있게 합니다. 가상화된 인스턴스와 달리, 이 인스턴스들은 운영체제와 서버의 프로세서·메모리·스토리지 사이에 하이퍼바이저 없이 하드웨어에서 "네이티브"로 실행됩니다. 이 모델을 통해 저수준 하드웨어 기능이 필요하거나, 직접적인 성능 분석이 필요하거나, (예를 들어 라이선스나 레거시 제약으로 인해) 비가상화 환경이 필요한 애플리케이션을 실행하면서도, AWS 생태계 전체(Amazon VPC, Amazon EBS, Auto Scaling, CloudWatch 등)와 AWS Nitro System이 제공하는 보안·관리 기능을 그대로 누릴 수 있습니다.

더 기술적인 세부 사항은 [하드웨어에 직접 접근하는 Amazon EC2 베어메탈 인스턴스 소개](https://aws.amazon.com/blogs/aws/new-amazon-ec2-bare-metal-instances-with-direct-access-to-hardware/)를 참고하세요.

## 3. 관리형 인스턴스

Amazon EC2 관리형 인스턴스는 EKS Auto Mode를 통한 Amazon EKS 같은 지정된 서비스 공급자가 프로비저닝하고 관리하는 EC2 인스턴스입니다. 이 관리형 인스턴스들은 인스턴스의 운영 제어를 서비스 공급자에게 위임할 수 있게 해 Amazon EC2에서 컴퓨팅 워크로드를 실행하는 것을 단순화합니다. 위임된 제어가 관리형 인스턴스에 도입된 유일한 변화입니다. 기술 사양과 요금은 비관리형 EC2 인스턴스와 동일하게 유지됩니다.

### 3.1. 위임된 제어

인스턴스가 관리형일 때, 서비스 공급자는 인스턴스 프로비저닝, 소프트웨어 구성, 용량 확장, 인스턴스 장애 처리와 교체 같은 작업을 책임집니다. 관리형 인스턴스의 설정을 직접 수정할 수는 없지만, AWS 환경 안에서 분류하기 위해 태그를 추가·수정·제거할 수 있습니다. 구체적인 작업은 여러분과 서비스 공급자 간의 계약에 따라 결정됩니다.

### 3.2. 관리형 인스턴스 식별

관리형 인스턴스는 **Managed** 필드의 값이 **true**로 식별됩니다. 서비스 공급자는 (콘솔에서) **Operator** 필드나 (CLI에서) `Principal` 필드로 식별됩니다.

### 3.3. 관리형 인스턴스 요금

온디맨드 인스턴스, Reserved Instance, Spot 인스턴스, Savings Plans를 포함한 모든 Amazon EC2 구매 옵션을 관리형 인스턴스에도 사용할 수 있습니다. 컴퓨팅을 EC2에서 직접 조달한 다음 서비스 공급자에게 제공함으로써, 계정에 이미 적용된 Reserved Instance나 Savings Plans의 이점을 그대로 누릴 수 있어 가장 비용 효율적인 컴퓨팅 용량을 사용할 수 있습니다.

예를 들어 Amazon EKS Auto Mode를 사용할 때는 기반 인스턴스에 대해 표준 EC2 인스턴스 요율을 지불하고, 여러분을 대신해 인스턴스를 관리하는 것에 대해 Amazon EKS로부터 추가 요금이 부과됩니다. 이후 [Savings Plan](https://docs.aws.amazon.com/savingsplans/latest/userguide/what-is-savings-plans.html)에 가입하기로 결정하면, EC2 인스턴스 요율은 Savings Plan에 의해 낮아지지만 Amazon EKS의 추가 요금은 변하지 않습니다.

## 4. 요금과 구매 옵션

Amazon EC2 비용을 최적화하기 위해 다음 옵션을 사용할 수 있습니다.

- **온디맨드 인스턴스**: 시작한 인스턴스에 대해 초 단위로 요금을 지불합니다.
- **Savings Plans**: 1년 또는 3년 기간 동안 시간당 USD 기준의 일정한 사용량에 대해 약정함으로써 Amazon EC2 비용을 줄입니다.
- **Reserved Instance**: 1년 또는 3년 기간 동안 인스턴스 유형과 리전을 포함한 일정한 인스턴스 구성에 약정함으로써 Amazon EC2 비용을 줄입니다.
- **Spot 인스턴스**: 사용되지 않는 EC2 인스턴스를 요청해 Amazon EC2 비용을 크게 줄일 수 있습니다.
- **Dedicated Host**: 인스턴스 실행에 완전히 전용으로 사용되는 물리 호스트에 대해 요금을 지불하며, 기존의 소켓별·코어별·VM별 소프트웨어 라이선스를 가져와 비용을 줄일 수 있습니다.
- **Dedicated Instance**: 단일 테넌트 하드웨어에서 실행되는 인스턴스에 대해 시간당 요금을 지불합니다.
- **Capacity Reservation**: 특정 가용 영역에서 EC2 인스턴스를 위한 용량을 예약합니다.

### 4.1. 온디맨드 인스턴스

온디맨드 인스턴스에서는 장기 약정 없이 사용한 컴퓨팅 용량에 대해 초 단위(최소 60초)로 요금을 지불합니다. 이 옵션은 예측 불가능한 워크로드, 단기 프로젝트, 테스트에 이상적입니다.

AWS 계정별·리전별로 실행 중인 온디맨드 인스턴스 수에는 [할당량](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-on-demand-instances.html#ec2-on-demand-instances-limits)이 있습니다. 온디맨드 인스턴스 할당량은 인스턴스 유형과 무관하게, 실행 중인 온디맨드 인스턴스가 사용하는 _가상 중앙 처리 장치(vCPU) 수_로 관리됩니다. 각 할당량 유형은 하나 이상의 인스턴스 계열에 대한 최대 vCPU 수를 지정합니다.

Amazon EC2가 사용량에 따라 온디맨드 인스턴스 할당량을 자동으로 늘리지만, 필요하다면 할당량 증가를 요청할 수 있습니다. 예를 들어 현재 할당량보다 더 많은 인스턴스를 시작하려는 경우, [Amazon EC2 서비스 할당량](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-resource-limits.html)에서 설명하는 Service Quotas 콘솔을 사용해 할당량 증가를 요청할 수 있습니다.
### 4.1. Savings Plans

Savings Plans는 1년 또는 3년 기간 동안 일정한 사용량(시간당 USD로 측정)에 약정할 수 있게 하며, 온디맨드 요금에 비해 상당한 절감을 제공합니다.

Reserved Instance와 달리 Savings Plans는 할인된 요율을 유지하면서도 인스턴스 계열, 크기, 리전, 운영체제, 심지어 AWS 서비스(AWS Lambda나 Fargate 등)까지 변경할 수 있는 유연성을 제공합니다.
### 4.2. Reserved Instance(RI)

Reserved Instance는 1년 또는 3년 기간 동안 특정 인스턴스 구성에 약정하는 대가로 온디맨드 사용량에 대한 요금 할인을 제공합니다. 물리적 인스턴스가 아니라, 실행 중인 인스턴스가 예약의 속성과 일치할 때 적용되는 요금 메커니즘입니다. **AWS는 Reserved Instance보다 Savings Plans를 권장합니다**.

- **핵심 변수:**
    요금은 인스턴스 속성, 계약 기간, 선택한 결제 옵션에 따라 달라집니다.
* **인스턴스 속성**:
	* **인스턴스 유형**: 예를 들어 `m4.large`.
	- **리전**: Reserved Instance를 구매한 리전.
	- **테넌시**: 인스턴스가 공유(기본) 하드웨어나 단일 테넌트(전용) 하드웨어에서 실행되는지 여부.
	- **플랫폼**: 운영체제. 예를 들어 Windows나 Linux/Unix.
- **결제 옵션:**
    - **전액 선결제(All Upfront):** 구매 시 전체 비용을 지불해 가장 낮은 실질 시간당 요율을 받습니다.
    - **부분 선결제(Partial Upfront):** 일부를 선결제하고 나머지는 할인된 시간당 요율로 지불합니다.
    - **선결제 없음(No Upfront):** 계약 기간 동안 할인된 시간당 요율만 지불합니다.
- **오퍼링 클래스:**
    - **Standard RI:** 가장 큰 할인을 제공하지만 유연성이 낮습니다.
    - **Convertible RI:** 다소 낮은 할인율이지만 다른 구성으로 교환할 수 있는 능력을 제공합니다.

다음 다이어그램은 Reserved Instance를 구매하고 사용하는 기본적인 시나리오를 보여줍니다.

![reserved-instance](@site/docs/Compute/_assets/reserved-instance.png)

이 시나리오에서는 계정에 실행 중인 온디맨드 인스턴스(T2)가 있고, 현재 온디맨드 요율로 비용을 지불하고 있습니다. 실행 중인 인스턴스의 속성과 일치하는 Reserved Instance를 구매하면 요금 혜택이 즉시 적용됩니다. 다음으로 C4 인스턴스용 Reserved Instance를 구매합니다. 계정에는 이 Reserved Instance의 속성과 일치하는 실행 중인 인스턴스가 없습니다. 마지막 단계에서 C4 Reserved Instance의 속성과 일치하는 인스턴스를 시작하면 요금 혜택이 즉시 적용됩니다.
### 4.3. Spot 인스턴스

Spot 인스턴스는 온디맨드 가격보다 낮은 가격으로 사용 가능한 남는 EC2 용량을 사용하는 인스턴스입니다. Spot 인스턴스를 사용하면 큰 할인가로 사용되지 않는 EC2 인스턴스를 요청할 수 있어 Amazon EC2 비용을 크게 줄일 수 있습니다. Spot 인스턴스의 시간당 가격을 Spot 가격이라고 합니다. 각 가용 영역의 각 인스턴스 유형별 Spot 가격은 Amazon EC2가 설정하며, Spot 인스턴스에 대한 장기적인 공급과 수요에 따라 점진적으로 조정됩니다. Spot 인스턴스는 용량이 사용 가능할 때마다 실행됩니다.

애플리케이션이 언제 실행될지 유연하게 대응할 수 있고 중단을 감내할 수 있다면 Spot 인스턴스는 비용 효율적인 선택입니다. 예를 들어 Spot 인스턴스는 데이터 분석, 배치 작업, 백그라운드 처리, 선택적 작업에 적합합니다.

현재 Spot 가격을 확인하려면 [Amazon EC2 Spot 인스턴스 요금](https://aws.amazon.com/ec2/spot/pricing/)을 참고하세요.

### 4.4. Dedicated Host

Amazon EC2 Dedicated Host는 완전히 전용으로 사용할 수 있는 물리 서버입니다. 선택적으로 인스턴스 용량을 다른 AWS 계정과 공유할 수도 있습니다. 자세한 내용은 [계정 간 Amazon EC2 Dedicated Host 공유](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/dh-sharing.html)를 참고하세요.

Dedicated Host는 인스턴스 배치에 대한 가시성과 제어권을 제공하며 호스트 어피니티를 지원합니다. 즉 특정 호스트에 인스턴스를 시작하고 실행할 수 있고, 인스턴스가 특정 호스트에서만 실행되도록 보장할 수 있습니다.

Dedicated Host는 포괄적인 BYOL(Bring Your Own License) 지원을 제공합니다. Windows Server, SQL Server, SUSE Linux Enterprise Server, Red Hat Enterprise Linux, 또는 VM·소켓·물리 코어에 종속된 다른 소프트웨어 라이선스를 라이선스 조건에 따라 그대로 사용할 수 있습니다.

인스턴스가 전용 하드웨어에서 실행되어야 하지만 인스턴스 배치에 대한 가시성이나 제어가 필요하지 않고 소켓별·코어별 소프트웨어 라이선스도 필요하지 않다면, 대신 Dedicated Instance 사용을 고려할 수 있습니다.
### 4.5. Dedicated Instance

기본적으로 EC2 인스턴스는 공유 테넌시 하드웨어에서 실행됩니다. 즉 여러 AWS 계정이 동일한 물리적 하드웨어를 공유할 수 있습니다.

**Dedicated Instance는 단일 AWS 계정에 전용으로 지정된 하드웨어에서 실행되는 EC2 인스턴스입니다**. 즉 Dedicated Instance는 다른 AWS 계정에 속한 인스턴스로부터 호스트 하드웨어 수준에서 물리적으로 격리됩니다. 이는 그 계정들이 하나의 결제 계정에 연결되어 있어도 마찬가지입니다. **다만 Dedicated Instance는 동일한 AWS 계정에서 Dedicated Instance가 아닌 다른 인스턴스와는 하드웨어를 공유할 수 있습니다**.

Dedicated Instance는 **인스턴스 배치에 대한 가시성이나 제어권을 제공하지 않으며**, 호스트 어피니티도 지원하지 않습니다. Dedicated Instance를 중지하고 다시 시작하면 동일한 호스트에서 실행되지 않을 수 있습니다. 마찬가지로 인스턴스를 시작하거나 실행할 특정 호스트를 지정할 수 없습니다. 또한 Dedicated Instance는 BYOL(Bring Your Own License)에 대해 제한적인 지원만 제공합니다.

인스턴스 배치에 대한 가시성과 제어, 더 포괄적인 BYOL 지원이 필요하다면 대신 Dedicated Host 사용을 고려하세요. 다음 표는 Dedicated Instance와 Dedicated Host의 주요 차이점을 보여줍니다.

|                                               | Dedicated Host                                                                                  | Dedicated Instance                                               |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **전용 물리 서버**                 | ✅ 인스턴스 용량이 여러분의 사용에 완전히 전용인 물리 서버.                           | ✅ 단일 고객 계정에 전용인 물리 서버. |
| **인스턴스 용량 공유**                 | ✅ 다른 계정과 인스턴스 용량을 공유할 수 있음.                                              | ❌ 지원되지 않음                                                  |
| **요금**                                   | 호스트별 요금                                                                                | 인스턴스별 요금                                             |
| **소켓, 코어, 호스트 ID의 가시성** | ✅ 소켓 수와 물리 코어 수에 대한 가시성 제공                               | ❌ 가시성 없음                                                  |
| **호스트·인스턴스 어피니티**                | ✅ 시간이 지나도 인스턴스를 동일한 물리 서버에 일관되게 배포할 수 있음        | ❌ 지원되지 않음                                                  |
| **타깃 인스턴스 배치**               | ✅ 인스턴스가 물리 서버에 배치되는 방식에 대해 추가적인 가시성과 제어 제공 | ❌ 지원되지 않음                                                  |
| **자동 인스턴스 복구**               | ✅ 지원됨                                                                                     | ✅ 지원됨                                                      |
| **BYOL(Bring Your Own License)**             | ✅ 지원됨                                                                                     | 부분 지원                                                  |
| **Capacity Reservation**                     | ❌ 지원되지 않음                                                                                 | ✅ 지원됨                                                      |
### 4.6. Capacity Reservation

Capacity Reservation을 사용하면 특정 가용 영역에서 인스턴스를 위한 EC2 용량을 예약할 수 있습니다. 이를 통해 사용 가능한 용량의 변동과 무관하게 필요할 때 인스턴스를 시작할 수 있으며, 계속 온디맨드 요율로 요금이 부과됩니다.

이 옵션은 장기 요금에 약정하지 않으면서도 중요한 워크로드를 위해 보장된 용량이 필요할 때 유용합니다.

## 5. Amazon Machine Image

Amazon Machine Image(AMI)는 Amazon EC2 인스턴스를 설정하고 부팅하는 데 필요한 소프트웨어를 제공하는 이미지입니다. 인스턴스를 시작할 때는 AMI를 지정해야 합니다. **AMI는 인스턴스에 선택한 인스턴스 유형과 호환되어야 합니다.** AWS가 제공하는 AMI, 퍼블릭 AMI, 다른 누군가가 공유한 AMI, 또는 AWS Marketplace에서 구매한 AMI를 사용할 수 있습니다.

AMI는 다음에 특정됩니다.

- **리전**
- **운영체제**
- **프로세서 아키텍처**
- **루트 디바이스 유형:** Amazon EBS 기반 또는 인스턴스 스토어 기반.
- **가상화 유형:** 두 가지 가상화 유형 중 하나입니다. 파라버추얼(PV) 또는 하드웨어 가상 머신(HVM)
- **시작 권한:** AMI의 소유자는 시작 권한을 지정해 가용성을 결정합니다. 다음 중 하나일 수 있습니다.
	- **public**: 모든 AWS 계정
	- **explicit**: 특정 AWS 계정, 조직, 또는 조직 단위(OU)
	- **implicit**: AMI에 대한 암묵적 시작 권한.
### 5.1. AMI 생명주기

![ami-lifecycle](@site/docs/Compute/_assets/ami-lifecycle.png)
- **생성과 커스터마이징:**
    - Amazon은 미리 만들어진 AMI를 제공하거나, 자체 AMI를 만들 수 있습니다.
    - 기존 AMI에서 인스턴스를 시작해 커스터마이징한(예: 소프트웨어 설치, OS 설정 변경) 다음, 업데이트된 환경을 새 AMI로 저장할 수 있습니다.
    - 모든 커스터마이징이 저장되므로, 새 AMI에서 시작된 인스턴스는 이 변경 사항을 포함합니다.
- **복사:**
    - **AMI는 만들어진 AWS 리전에서만 사용할 수 있습니다**.
    - 동일한 구성을 여러 리전에서 사용하려면 원하는 각 리전으로 AMI를 복사해야 합니다.
- **비활성화 vs. 등록 해제:**
    - **비활성화:**
        - AMI를 새 인스턴스를 시작하는 데 사용하지 못하도록 일시적으로 막습니다.
        - 다시 활성화하면 가용성이 복원됩니다.
        - 비활성화는 이미 시작된 인스턴스에는 영향을 미치지 않습니다.
    - **등록 해제:**
        - AMI가 새 인스턴스를 시작하는 능력을 영구적으로 제거합니다.
        - 기존 인스턴스는 영향을 받지 않습니다.
- **Amazon Data Lifecycle Manager를 통한 자동화:**
    - Amazon EBS 기반 AMI와 그 스냅샷의 생성, 보존, 복사, 사용 중단, 등록 해제를 자동화합니다.

### 5.2. Amazon EventBridge로 AMI 이벤트 모니터링

Amazon Machine Image(AMI)의 상태가 변경되면 Amazon EC2는 Amazon EventBridge로 전송되는 이벤트를 생성합니다. 이벤트는 JSON 형식으로 기본 EventBridge 이벤트 버스로 전송됩니다. Amazon EventBridge를 사용해 이런 이벤트를 감지하고 대응할 수 있습니다.

### 5.3. AMI 비용

- **AMI 요금은 이미지 자체에 대한 "개별 항목" 요금이 아닙니다.** 비용은 스냅샷 저장(EBS 기반 이미지의 경우)이나 S3(인스턴스 스토어 이미지의 경우)에서 발생합니다.
- **Marketplace AMI**는 요금 모델(시간당 vs. 연간 구독)에 따라 추가 요금이 발생할 수 있으며, 이런 비용을 추적할 수 있도록 청구 메타데이터가 제공됩니다.

## 6. EC2 시작 템플릿

Amazon EC2 시작 템플릿은 EC2 인스턴스를 시작하는 데 필요한 파라미터를 저장할 수 있게 하는 구성 문서입니다. 동일한 설정(AMI ID, 인스턴스 유형, 키 페어, 보안 그룹, 스토리지 옵션, 네트워크 인터페이스, 사용자 데이터 등)을 반복해서 지정하는 대신, 시작 템플릿을 한 번 만들어 여러 인스턴스 시작에 재사용할 수 있습니다.

**핵심 이점:**
- **일관성과 재사용성:**
    선호하는 인스턴스 구성을 시작 템플릿에 저장함으로써, 그 템플릿을 사용해 시작되는 모든 인스턴스가 조직의 표준을 준수하도록 보장할 수 있습니다. 이는 인적 오류를 최소화하고 배포 속도를 높입니다.
- **버전 관리:**
    시작 템플릿은 버전 관리를 지원합니다. 서로 다른 파라미터 집합을 담은 여러 버전의 템플릿을 만들 수 있습니다. 인스턴스를 시작할 때 특정 버전을 선택할 수도 있고, AWS가 기본 버전을 사용하게 할 수도 있습니다. 이를 통해 변경 사항을 점진적으로 배포하고 필요하면 되돌리기도 쉬워집니다.
- **다른 서비스와의 통합:**
    시작 템플릿은 수동 인스턴스 시작뿐 아니라 다음과 같은 서비스에도 필수적으로 사용됩니다.
    - **Amazon EC2 Auto Scaling**(확장 그룹의 인스턴스 구성을 지정하기 위해)
    - **EC2 Fleet과 Spot Fleet**(다양한 인스턴스 유형과 구매 옵션을 관리하기 위해)
    - **AWS CloudFormation**(AWS::EC2::LaunchTemplate 리소스를 통해)
    이 통합은 AWS 서비스 전반에서 일관된 인스턴스 프로비저닝 접근 방식을 제공합니다.

## 7. 인스턴스에 연결하기

AWS는 EC2 인스턴스에 연결할 수 있는 여러 방법을 제공하며, 흔히 인스턴스의 운영체제, 네트워크 구성, 보안 요구사항에 따라 방법을 선택합니다.

| 연결 옵션             | 인스턴스 운영체제 | 인바운드 트래픽 규칙 | IAM 권한 | 인스턴스 프로필 역할 | 인스턴스의 소프트웨어 | 연결하는 시스템의 소프트웨어 | 키 페어 |
| ----------------------------- | ------------------------- | -------------------- | --------------- | --------------------- | -------------------- | ----------------------------- | -------- |
| SSH 클라이언트                    | Linux                     | ✅                    | ❌               | ❌                     | ❌                    | ✅                             | ✅        |
| EC2 Instance Connect          | Linux                     | ✅                    | ✅               | ❌                     | ✅                    | ❌                             | ❌        |
| PuTTY                         | Linux                     | ✅                    | ❌               | ❌                     | ❌                    | ✅                             | ✅        |
| RDP 클라이언트                    | Windows                   | ✅                    | ❌               | ❌                     | ❌                    | ✅                             | ✅        |
| Fleet Manager                 | Windows                   | ❌                    | ✅               | ✅                     | ✅                    | ❌                             | ✅        |
| Session Manager               | Linux, Windows            | ❌                    | ✅               | ✅                     | ✅                    | ❌                             | ❌        |
| EC2 Instance Connect Endpoint | Linux, Windows            | ✅                    | ✅               | ❌                     | ❌                    | ❌                             | ✅        |

* **SSH 클라이언트:** 프라이빗 키를 사용해 Linux/Unix 기반 EC2 인스턴스에 안전하게 연결하는 SSH 프로토콜을 사용하는 표준 명령줄 도구입니다.
* **EC2 Instance Connect:** 키를 수동으로 관리하지 않고 EC2 인스턴스에 안전하게 연결할 수 있도록 SSH 키를 임시로 프로비저닝하는, 브라우저 기반(CLI로도 접근 가능)의 서비스입니다.
* **PuTTY:** 프라이빗 키를 사용해 Linux/Unix 기반 EC2 인스턴스에 안전하게 연결할 수 있게 하는, Windows에서 널리 사용되는 무료 SSH·telnet 클라이언트입니다.
* **RDP 클라이언트:** Remote Desktop Protocol을 사용해 Windows 기반 EC2 인스턴스에 연결하는 클라이언트 애플리케이션으로, 그래픽 데스크톱 인터페이스를 제공합니다.
* **Fleet Manager:** EC2 인스턴스 플릿을 인벤토리화·관리하고 원격으로 연결할 수 있는 통합 웹 기반 인터페이스를 제공하는 AWS Systems Manager 기능입니다.
* **Session Manager:** 인바운드 포트를 열거나 SSH 키를 요구하지 않고도 EC2 인스턴스에 안전한 브라우저 또는 CLI 기반 셸 접근을 가능하게 하는 AWS Systems Manager의 기능입니다.
* **EC2 Instance Connect Endpoint:** VPC를 통해 Instance Connect로 EC2 인스턴스에 안전하고 프라이빗한 연결을 허용하는 관리형 엔드포인트로, 퍼블릭 IP가 필요 없어 보안이 강화됩니다.

### 6.1. 키 페어

키 페어는 공개 키와 비공개 키로 구성되며, Amazon EC2 인스턴스에 연결할 때 신원을 증명하는 데 사용하는 보안 자격 증명 집합입니다. Linux 인스턴스의 경우 비공개 키를 사용해 안전하게 인스턴스에 SSH 접속할 수 있습니다. Windows 인스턴스의 경우 관리자 비밀번호를 복호화하는 데 비공개 키가 필요하며, 그 비밀번호로 인스턴스에 연결합니다.

Amazon EC2는 공개 키를 인스턴스에 저장하고, 비공개 키는 아래 다이어그램에 나온 것처럼 사용자가 보관합니다. 비공개 키를 가진 사람은 누구든 그 키 페어를 사용하는 인스턴스에 연결할 수 있으므로 비공개 키를 안전한 곳에 보관하는 것이 중요합니다.

![ec2-key-pair](@site/docs/Compute/_assets/ec2-key-pair.png)

인스턴스를 시작할 때 [키 페어를 지정](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-instance-launch-parameters.html#liw-key-pair)할 수 있으며, 이를 통해 키 페어가 필요한 방법으로 인스턴스에 연결할 수 있습니다. 보안을 관리하는 방식에 따라 모든 인스턴스에 동일한 키 페어를 지정할 수도 있고, 서로 다른 키 페어를 지정할 수도 있습니다.

Linux 인스턴스의 경우, 인스턴스가 처음 부팅될 때 시작 시점에 지정한 공개 키가 `~/.ssh/authorized_keys` 안의 항목으로 Linux 인스턴스에 배치됩니다. SSH로 Linux 인스턴스에 연결할 때는 로그인하려면 그 공개 키에 대응하는 비공개 키를 지정해야 합니다.

## 7. EC2 인스턴스 상태

Amazon EC2 인스턴스는 시작되는 순간부터 종료되기까지 여러 상태를 거쳐 전환됩니다.

다음 그림은 인스턴스 상태 간의 전환을 나타냅니다.

![ec2-instance-state](@site/docs/Compute/_assets/ec2-instance-state.png)

인스턴스의 상태가 바뀌면 Amazon EC2는 `EC2 Instance State-change Notification` 이벤트를 Amazon EventBridge로 전송합니다.

다음 표는 각 인스턴스 상태에 대한 간략한 설명과, 인스턴스 사용에 요금이 부과되는지를 나타냅니다. Amazon EBS 볼륨이나 탄력적 IP 주소 같은 일부 AWS 리소스는 인스턴스의 상태와 무관하게 요금이 발생합니다.

| 인스턴스 상태  | 설명                                                                                                                                                                  | 요금 부과?                                                                                                                                              |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pending`       | 인스턴스가 `running` 상태로 진입하려 준비하고 있습니다. 인스턴스는 시작될 때나 `stopped` 상태에서 다시 시작될 때 `pending` 상태에 들어갑니다. | ❌                                                                                                                                                    |
| `running`       | 인스턴스가 실행 중이며 사용할 준비가 되었습니다.                                                                                                                                   | ✅                                                                                                                                                    |
| `stopping`      | 인스턴스가 중지되려 준비하고 있습니다.                                                                                                                                     | ❌<br /><br />**참고:** 인스턴스를 최대 절전 모드로 전환하면, `stopping` 상태에 있는 동안 요금이 부과됩니다.                                        |
| `stopped`       | 인스턴스가 종료되어 사용할 수 없습니다. 인스턴스는 언제든 다시 시작할 수 있습니다.                                                                                                       | ❌                                                                                                                                                    |
| `shutting-down` | 인스턴스가 종료되려 준비하고 있습니다.                                                                                                                                  | ❌                                                                                                                                                    |
| `terminated`    | 인스턴스가 영구적으로 삭제되어 다시 시작할 수 없습니다.                                                                                                             | ❌<br /><br />**참고:** 종료된 인스턴스에 적용된 Reserved Instance는 결제 옵션에 따라 계약 기간이 끝날 때까지 요금이 부과됩니다. |

## 8. EC2 인스턴스 최대 절전(Hibernate)

인스턴스를 최대 절전 모드로 전환하면 Amazon EC2는 운영체제에 최대 절전(디스크로 서스펜드)을 수행하도록 신호를 보냅니다. 최대 절전은 인스턴스 메모리(RAM)의 내용을 Amazon Elastic Block Store(Amazon EBS) 루트 볼륨에 저장합니다. Amazon EC2는 인스턴스의 EBS 루트 볼륨과 연결된 모든 EBS 데이터 볼륨을 유지합니다. 인스턴스가 다시 시작되면:

- EBS 루트 볼륨이 이전 상태로 복원됩니다
- RAM 내용이 다시 로드됩니다
- 인스턴스에서 이전에 실행되던 프로세스가 재개됩니다
- 이전에 연결된 데이터 볼륨이 다시 연결되고 인스턴스는 인스턴스 ID를 유지합니다

인스턴스는 [최대 절전이 활성화](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/enabling-hibernation.html)되어 있고 [최대 절전 전제조건](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/hibernating-prerequisites.html)을 충족할 때만 최대 절전 모드로 전환할 수 있습니다.

최대 절전 상태의 인스턴스가 `stopped` 상태에 있는 동안에는 인스턴스 사용에 대한 요금이 부과되지 않으며, RAM 내용이 EBS 루트 볼륨으로 전송될 때의 데이터 전송에도 요금이 부과되지 않습니다. RAM 내용의 저장을 포함한 EBS 볼륨 저장에는 요금이 부과됩니다.
### 8.1. 최대 절전 사용 사례

인스턴스나 애플리케이션이 완전히 생산적인 상태가 되기 위해 부트스트랩하고 메모리 사용 흔적을 구축하는 데 오랜 시간이 걸린다면, 최대 절전을 사용해 인스턴스를 미리 예열할 수 있습니다. 인스턴스를 예열하려면 다음과 같이 합니다.

1. 최대 절전을 활성화해 시작합니다.
2. 원하는 상태로 만듭니다.
3. 필요할 때 언제든 원하는 상태로 재개할 준비가 되도록 최대 절전 모드로 전환합니다.

## 9. EC2 인스턴스 메타데이터

**EC2 인스턴스 메타데이터**는 실행 중인 인스턴스에 대한 동적 정보를 인스턴스 자신이 사용할 수 있게 하는, AWS가 제공하는 서비스입니다. 인스턴스의 애플리케이션은 이 데이터를 사용해 인스턴스의 신원, 네트워킹 정보, 할당된 IAM 역할 같은 구성 세부 정보를 확인할 수 있습니다. 또한 이 서비스는 시작 시 제공한 정보(예: 시작 스크립트)인 사용자 데이터에 대한 접근도 제공합니다.

![ec2-metadata](@site/docs/Compute/_assets/ec2-metadata.png)

메타데이터는 특수 IP 주소 `169.254.169.254`로의 HTTP 요청을 통해 사용할 수 있습니다. 정보의 구조화된 계층(예: `latest/meta-data/`, `latest/user-data/`)을 제공합니다.

## 10. 스토리지

Amazon EC2는 다양한 성능, 내구성, 비용 요구사항을 충족하도록 설계된 풍부한 스토리지 옵션을 제공합니다.

1. **인스턴스 스토어(임시 스토리지):** 인스턴스 스토어는 EC2 인스턴스를 실행하는 호스트 머신에 물리적으로 연결된 임시 블록 수준 스토리지를 제공합니다. 이 스토리지는 "임시적"입니다. 데이터는 인스턴스의 수명 동안만 유지됩니다. **인스턴스가 중지, 최대 절전, 종료되면 인스턴스 스토어 볼륨의 데이터는 사라집니다.**

2. **Amazon Elastic Block Store(EBS):** Amazon EBS는 EC2 인스턴스에 연결할 수 있는 영구적인 블록 스토리지 볼륨을 제공합니다. 이 볼륨들은 인스턴스의 생명주기와 독립적으로 유지되며, 스냅샷, 암호화, 다운타임 없이 성능과 용량을 확장하는 기능 같은 특징을 제공합니다.

3. **Amazon Simple Storage Service(S3):** EC2 인스턴스에 블록 디바이스로 직접 "연결"되지는 않지만, Amazon S3는 AWS에서 광범위하게 사용되는 매우 내구성 있는 오브젝트 스토리지 서비스입니다. EC2는 S3를 사용해 AMI, EBS 스냅샷, 백업, 정적 자산을 저장합니다.

4. **Amazon Elastic File System(EFS):** Amazon EFS는 POSIX 호환 파일 시스템을 제공하는 완전관리형의 확장 가능한 파일 스토리지 서비스입니다. 여러 가용 영역에 걸쳐 여러 EC2 인스턴스(Linux만)가 동시에 마운트할 수 있습니다.

5. **Amazon FSx:** 인기 있는 파일 시스템을 기반으로 완전관리형 파일 스토리지를 제공합니다.
	- **FSx for Windows File Server:** 네이티브 SMB 지원을 갖춘 Windows 기반 애플리케이션용입니다.
	- **FSx for Lustre:** HPC와 머신 러닝 같은 컴퓨팅 집약적 워크로드에 최적화된 고성능 파일 시스템입니다.
	- **FSx for NetApp ONTAP와 FSx for OpenZFS:** 고급 스토리지 기능과 기존 온프레미스 환경과의 통합을 위한 것입니다.

6. **Amazon File Cache:** 파일 데이터를 위한 고성능 임시 캐싱 계층을 제공하도록 설계되었습니다. Amazon EFS나 S3 같은 시스템에 저장된 데이터를 위한 중간 캐시 역할을 하여 파일 처리를 가속화할 수 있습니다.

다음은 주요 EC2 스토리지 옵션의 핵심 특성을 정리한 비교표입니다.

| **스토리지 옵션**    | **유형**             | **지속성**                    | **이상적인 사용 사례**                                  | **핵심 기능**                                               |
| --------------------- | -------------------- | ---------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------- |
| **인스턴스 스토어**    | 🔗 블록(임시) | 임시(중지/종료 시 손실) | 🧰 캐싱, 스크래치 공간, 임시 데이터            | ⚡ 매우 낮은 지연 시간, 인스턴스에 포함됨, 로컬 스토리지      |

## 11. 결론

Amazon EC2는 많은 클라우드 아키텍처의 근간을 이루는 강력하고 다재다능한 서비스입니다. 광범위한 인스턴스 유형, 유연한 요금 모델, 견고한 보안 기능, 다른 AWS 서비스와의 깊은 통합을 통해 EC2는 기업과 개발자가 애플리케이션을 효율적으로 구축·확장·보호할 수 있게 합니다. 포괄적이고 최신인 정보는 항상 [공식 문서](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Instances.html)를 참고하세요.
