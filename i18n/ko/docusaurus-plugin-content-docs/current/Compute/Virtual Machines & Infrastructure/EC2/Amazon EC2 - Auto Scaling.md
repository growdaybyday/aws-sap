# Amazon EC2 - Auto Scaling

## 1. 소개

Amazon EC2 Auto Scaling은 애플리케이션의 수요에 따라 EC2 인스턴스를 자동으로 시작하거나 종료함으로써 애플리케이션 가용성을 유지하는 데 도움을 줍니다. 최소·최대·원하는 용량을 지정해 Auto Scaling 그룹을 정의하면, 이 서비스는 언제든 적절한 양의 컴퓨팅 용량을 갖도록 보장합니다. 인스턴스 상태를 모니터링하고 비정상 인스턴스를 교체해 애플리케이션이 복원력 있고 고가용성을 유지하도록 합니다.

## 2. 애플리케이션 아키텍처에서 Auto Scaling의 이점

Amazon EC2 Auto Scaling을 애플리케이션 아키텍처에 추가하는 것은 AWS 클라우드의 이점을 최대한 활용하는 하나의 방법입니다. Amazon EC2 Auto Scaling을 사용하면 애플리케이션은 다음과 같은 이점을 얻습니다.

- **더 나은 내결함성:** Amazon EC2 Auto Scaling은 인스턴스가 비정상 상태임을 감지하면 이를 종료하고 대체 인스턴스를 시작할 수 있습니다. 여러 가용 영역을 사용하도록 Amazon EC2 Auto Scaling을 구성할 수도 있습니다. 한 가용 영역을 사용할 수 없게 되면 Amazon EC2 Auto Scaling이 다른 영역에서 인스턴스를 시작해 이를 보완할 수 있습니다.

- **더 나은 가용성:** Amazon EC2 Auto Scaling은 애플리케이션이 현재 트래픽 수요를 처리할 수 있는 적절한 양의 용량을 항상 갖도록 보장하는 데 도움을 줍니다.

- **더 나은 비용 관리:** Amazon EC2 Auto Scaling은 필요에 따라 용량을 동적으로 늘리거나 줄일 수 있습니다. 사용한 EC2 인스턴스에 대해서만 요금을 지불하므로, 필요할 때 인스턴스를 시작하고 필요 없을 때 종료함으로써 비용을 절감할 수 있습니다.

## 3. 인스턴스 생명주기

Auto Scaling 그룹의 EC2 인스턴스는 다른 EC2 인스턴스와는 다른 경로, 즉 생명주기를 가집니다. 이 생명주기는 Auto Scaling 그룹이 인스턴스를 시작하고 서비스에 투입할 때 시작됩니다. 인스턴스를 종료하거나 Auto Scaling 그룹이 인스턴스를 서비스에서 제외하고 종료할 때 생명주기가 끝납니다.

다음 그림은 Amazon EC2 Auto Scaling 생명주기에서 인스턴스 상태 간의 전환을 보여줍니다.

![ec2-aut-scaling-lifecycle](@site/docs/Compute/_assets/ec2-aut-scaling-lifecycle.png)
- **확장(Scale Out)**
    수요가 증가하면 확장 이벤트가 새 EC2 인스턴스의 시작을 트리거합니다. 이 새 인스턴스들은 _Pending_ 상태로 시작되며, 완전히 구성되고 상태 확인을 통과하면(선택적으로 생명주기 후크 작업을 거친 후) Auto Scaling 그룹에 연결되어 _InService_ 상태로 전환됩니다.

- **서비스 중인 인스턴스**
    _InService_ 인스턴스는 활발하게 실행되며 애플리케이션 트래픽을 처리하는 인스턴스입니다. 축소 이벤트, 수동 분리, 또는 대기(standby) 상태로 전환되기 전까지 서비스 상태를 유지합니다.

- **축소(Scale In)**
    수요가 줄어들면 축소 이벤트가 종료 과정을 시작합니다. Auto Scaling 그룹은 종료 정책을 사용해 종료할 인스턴스를 선택하여 하나 이상의 인스턴스를 종료함으로써 용량을 줄입니다. 그룹이 로드 밸런서와 연결되어 있다면, 인스턴스는 종료되기 전에 자동으로 등록이 해제됩니다.

- **인스턴스 분리**
    인스턴스를 종료하지 않고 Auto Scaling 그룹에서 제거(분리)할 수 있습니다. 이를 통해 인스턴스를 독립적으로 관리하거나 나중에 다른 그룹에 연결할 수 있습니다.

- **인스턴스 연결**
    반대로, 특정 기준을 충족하는 기존의 실행 중인 EC2 인스턴스를 Auto Scaling 그룹에 연결할 수 있습니다. 연결되면 그 인스턴스는 그룹의 일부로 관리되며 원하는 용량에 기여합니다.

- **생명주기 후크**
    생명주기 후크는 인스턴스가 전환 중일 때 커스텀 작업을 수행할 수 있게 합니다. 예를 들어 확장 이벤트 중에는 후크가 인스턴스를 _Pending:Wait_ 상태에서 일시 정지시켜, _InService_ 상태에 진입하기 전에 커스텀 초기화 단계를 수행할 수 있게 할 수 있습니다. 마찬가지로 축소 이벤트 중에는 후크가 인스턴스를 _Terminating:Wait_ 상태로 옮겨 필요한 작업(예: 정상 종료 작업)이 완료될 때까지 종료를 지연시킬 수 있습니다.

- **대기 상태 진입과 종료**
    인스턴스를 _Standby_ 상태로 두어 일시적으로 활성 서비스에서 제외할 수 있습니다. 이 상태에서 인스턴스는 여전히 Auto Scaling 그룹의 일부이며(계속 모니터링됨) 트래픽은 제공하지 않습니다. 준비가 되면 다시 _InService_ 상태로 되돌릴 수 있습니다.

## 4. 시작 템플릿과 시작 구성

시작 구성(Launch Configuration)은 Auto Scaling 그룹의 일부로 새 EC2 인스턴스를 시작하는 방법을 지정하는 **레거시** 방식입니다. 본질적으로 인스턴스를 만드는 데 필요한 파라미터를 담은 "청사진"입니다.

시작 템플릿(Launch Template)은 인스턴스 구성을 정의하는 더 새롭고 발전된 방식입니다. 더 큰 유연성을 제공하며, 현재는 Auto Scaling 그룹, EC2 Spot, 온디맨드 시작에 대한 인스턴스 설정을 지정하는 권장 방식입니다.

오늘날 Auto Scaling 그룹을 만들 때 AWS는 다음과 같은 이유로 시작 템플릿 사용을 권장합니다.

- 여러 버전을 가진 단일 템플릿을 유지할 수 있어 업데이트가 단순해집니다.
- 최신 기능(인스턴스 메타데이터 옵션, 향상된 네트워킹 구성 등)을 활용할 수 있습니다.
- AWS 서비스 전반에 걸쳐 일관된 메커니즘을 제공해, 서로 다른 사용 사례를 위해 별도의 구성을 유지해야 하는 부담을 줄여 줍니다.

**시작 구성**과 **시작 템플릿**의 차이를 정리한 비교표입니다.

| **기능**                | **시작 구성** 🏗️                                 | **시작 템플릿** 🚀                                    |
|----------------------------|------------------------------------------------------------|-------------------------------------------------------------|
| **가변성**              | 🔄 **불변**(변경 시 새 구성을 만들어야 함).      | 🔄 **버전 관리**(기존 템플릿을 버전으로 업데이트). |
| **버전 관리**              | 🚫 **버전 관리 없음**(롤백 기능 없음).             | #️⃣ **버전 지원**(변경 사항을 손쉽게 추적/롤백). |
| **주요 파라미터**          | ✅ **기본**: AMI, 인스턴스 유형, 키 페어, 보안 그룹, 사용자 데이터. | ✅ **모든 기본 항목** + 🌟 **고급**: 메타데이터 옵션, 용량 예약, 태깅, 혼합 구매(Spot/온디맨드). |
| **유연성**             | 🚫 **제한적**(고급 네트워킹/스토리지 옵션 없음).   | 💪 **높음**(배치 그룹, 버스터블 인스턴스, 다중 인스턴스 유형). |
| **재사용성**             | 🔄 **단일 용도**(하나의 Auto Scaling 그룹에 종속).         | ♻️ **재사용 가능**(Auto Scaling, EC2, Spot Fleet 전반에서 동작). |
| **업데이트**                 | ⏳ **수동 교체**(변경마다 새 구성 필요).    | ⚡ **매끄러움**(템플릿 업데이트, 버전 보존).       |
| **AWS 권장 사항**      | 🚫 **레거시**(새 구성에는 피할 것).                      | 🏆 **권장**(미래 대응, 최신 기능 지원). |
| **사용 사례**               | 🏚️ **기존 구성**(아직 마이그레이션하지 않은 경우).             | 🏗️ **신규 프로젝트** + ☁️ **다중 서비스 워크플로**(EC2, Spot, ASG). |

## 5. Auto Scaling 그룹(ASG)

ASG는 하나의 단위로 관리되는 EC2 인스턴스의 논리적 집합입니다. 최소·최대·원하는 용량 같은 파라미터를 정의합니다. 이 그룹은 내결함성을 개선하기 위해 여러 가용 영역에 걸쳐 인스턴스를 분산시키는 것도 처리합니다.

Auto Scaling 그룹은 원하는 용량을 충족할 만큼의 인스턴스를 시작하는 것으로 시작합니다. 그룹 내 인스턴스에 대해 주기적인 상태 확인을 수행함으로써 이 수를 유지합니다. Auto Scaling 그룹은 인스턴스가 비정상 상태가 되어도 고정된 수의 인스턴스를 계속 유지합니다. 인스턴스가 비정상 상태가 되면 그룹은 그 인스턴스를 종료하고 대체 인스턴스를 시작합니다.

### 5.1. ASG 생성

시작 템플릿을 만들었다면, EC2 인스턴스의 구성 템플릿으로 그 시작 템플릿을 사용하는 Auto Scaling 그룹을 만들 수 있습니다. 시작 템플릿은 AMI ID, 인스턴스 유형, 키 페어, 보안 그룹, 블록 디바이스 매핑 같은 정보를 지정합니다.

### 5.2. ASG 업데이트

Auto Scaling 그룹의 대부분의 세부 정보를 업데이트할 수 있지만, Auto Scaling 그룹의 이름을 바꾸거나 AWS 리전을 변경할 수는 없습니다.

### 5.3. 인스턴스 유지 관리 정책

인스턴스 새로 고침이나 상태 확인 과정처럼 인스턴스가 교체되는 이벤트 동안 특정 용량 요구사항을 충족하도록, Auto Scaling 그룹에 인스턴스 유지 관리 정책을 구성할 수 있습니다.

다음 정책을 사용할 수 있습니다.

- **먼저 시작 후 종료** – 기존 인스턴스를 종료하기 전에 먼저 새 인스턴스를 프로비저닝해야 합니다. 비용 절감보다 가용성을 우선하는 애플리케이션에 좋은 선택입니다.

- **종료와 시작 동시 진행** – 기존 인스턴스가 종료되는 동시에 새 인스턴스가 프로비저닝됩니다. 가용성보다 비용 절감을 우선하는 애플리케이션에 좋은 선택입니다. 인스턴스를 교체할 때도 현재 사용 가능한 것보다 더 많은 용량을 시작해서는 안 되는 애플리케이션에도 좋은 선택입니다.

- **커스텀 정책** – 인스턴스를 교체할 때 사용 가능하게 유지하고 싶은 용량의 최소·최대 범위를 커스텀으로 설정할 수 있는 옵션입니다. 이 접근 방식은 비용과 가용성 사이의 적절한 균형을 이루는 데 도움이 됩니다.

### 5.4. Amazon EC2 Auto Scaling 생명주기 후크

Amazon EC2 Auto Scaling은 Auto Scaling 그룹에 생명주기 후크를 추가할 수 있는 기능을 제공합니다. 이 후크들은 Auto Scaling 인스턴스 생명주기의 이벤트를 인식하는 솔루션을 만들고, 해당 생명주기 이벤트가 발생할 때 인스턴스에 커스텀 작업을 수행할 수 있게 합니다. 생명주기 후크는 인스턴스가 다음 상태로 전환되기 전에 작업이 완료될 때까지 기다리는 지정된 시간(기본값 1시간)을 제공합니다.

Auto Scaling 인스턴스에서 생명주기 후크를 사용하는 예시입니다.

- 확장 이벤트가 발생하면 새로 시작된 인스턴스는 시작 시퀀스를 완료하고 대기 상태로 전환됩니다. 인스턴스가 대기 상태에 있는 동안, 애플리케이션에 필요한 소프트웨어 패키지를 다운로드하고 설치하는 스크립트를 실행해 트래픽을 받기 시작하기 전에 인스턴스가 완전히 준비되도록 보장합니다. 스크립트가 소프트웨어 설치를 마치면 계속하기 위해 **complete-lifecycle-action** 명령을 전송합니다.

- 축소 이벤트가 발생하면 생명주기 후크가 인스턴스를 종료하기 전에 일시 정지시키고 Amazon EventBridge를 사용해 알림을 보냅니다. 인스턴스가 대기 상태에 있는 동안 AWS Lambda 함수를 호출하거나 인스턴스에 연결해 로그나 다른 데이터를 다운로드한 후 인스턴스를 완전히 종료할 수 있습니다.

생명주기 후크의 흔한 사용 방식은 인스턴스가 Elastic Load Balancing에 등록되는 시점을 제어하는 것입니다. Auto Scaling 그룹에 시작 생명주기 후크를 추가하면, 부트스트랩 스크립트가 성공적으로 완료되고 인스턴스의 애플리케이션이 트래픽을 받을 준비가 된 것을 확인한 후, 생명주기 후크가 끝날 때 로드 밸런서에 등록되도록 보장할 수 있습니다.

### 5.5. 최소, 최대, 원하는 용량

- **최소 용량:**
    - **정의:** 그룹이 항상 실행해야 하는 최소 인스턴스 수입니다.
    - **목적:** 수요가 적을 때도 기본 수준의 용량을 보장합니다.
- **최대 용량:**
    - **정의:** 그룹이 확장할 수 있는 최대 인스턴스 수입니다.
    - **목적:** 무한 확장을 방지하고 리소스를 제한해 비용을 통제하는 데 도움을 줍니다.
- **원하는 용량:**
    - **정의:** ASG가 유지하려 노력하는 목표 인스턴스 수입니다.
    - **동작:**
        - 실제 인스턴스 수가 이 목표보다 낮아지면(예: 장애로 인해), ASG는 새 인스턴스를 시작합니다.
        - 확장 정책은 수요 변화에 맞춰 이 값을 (최소·최대 용량이 설정한 범위 내에서) 조정합니다.
- **고려사항:**
    이 세 값은 함께 작동해 애플리케이션의 확장 범위와 전체 용량을 제어합니다.

## 6. 인스턴스 새로 고침

인스턴스 새로 고침을 사용해 Auto Scaling 그룹의 인스턴스를 업데이트할 수 있습니다. 이 기능은 구성 변경으로 인스턴스를 교체해야 할 때, 특히 Auto Scaling 그룹에 많은 수의 인스턴스가 있을 때 유용할 수 있습니다.

인스턴스 새로 고침이 도움이 되는 상황의 예는 다음과 같습니다.

- **Auto Scaling 그룹 전체에 새로운 Amazon Machine Image(AMI)나 사용자 데이터 스크립트를 배포하는 경우.** 변경 사항이 담긴 새 시작 템플릿을 만들고 인스턴스 새로 고침을 사용해 업데이트를 즉시 배포할 수 있습니다.
- **최신 개선 사항과 최적화를 활용하기 위해 인스턴스를 새로운 인스턴스 유형으로 마이그레이션하는 경우.**
- **Auto Scaling 그룹을 시작 구성 사용에서 시작 템플릿 사용으로 전환하는 경우.** 시작 구성을 시작 템플릿으로 복사한 다음 인스턴스 새로 고침을 사용해 인스턴스를 새 템플릿으로 업데이트할 수 있습니다.

아직 진행 중인 인스턴스 새로 고침은 취소할 수 있습니다. 완료된 후에는 취소할 수 없습니다.

### 6.1. 인스턴스 새로 고침 취소

인스턴스 새로 고침을 취소해도 이미 교체된 인스턴스는 롤백되지 않습니다. 인스턴스의 변경 사항을 되돌리려면 대신 롤백을 수행해야 합니다.

### 6.2. 롤백으로 변경 사항 취소하기

아직 진행 중인 인스턴스 새로 고침은 롤백할 수 있습니다. 완료된 후에는 롤백할 수 없습니다. 다만 새 인스턴스 새로 고침을 시작해 Auto Scaling 그룹을 다시 업데이트할 수는 있습니다.

롤백할 때 Amazon EC2 Auto Scaling은 그때까지 배포된 인스턴스를 교체합니다. 새 인스턴스는 인스턴스 새로 고침을 시작하기 전 Auto Scaling 그룹에 마지막으로 저장된 구성과 일치합니다.

### 6.3. 인스턴스 새로 고침 체크포인트

인스턴스 새로 고침을 사용할 때는 인스턴스를 단계적으로 교체하도록 선택해, 진행하면서 인스턴스에 대한 검증을 수행할 수 있습니다. 단계적 교체를 하려면 체크포인트를 추가합니다. 체크포인트는 인스턴스 새로 고침이 일시 정지되는 시점입니다. 체크포인트를 사용하면 Auto Scaling 그룹을 업데이트하는 방식을 더 세밀하게 제어할 수 있습니다. 애플리케이션이 안정적이고 예측 가능한 방식으로 동작할지 확인하는 데 도움이 됩니다.

![instance-refresh-checkpoint](@site/docs/Compute/_assets/instance-refresh-checkpoint.png)

## 7. 확장 방식

Amazon EC2 Auto Scaling은 플릿의 용량을 조정하는 여러 방식을 제공합니다.

- **고정 용량**은 추가 확장 작업 없이 안정적인 상태를 보장합니다.
- **수동 확장**은 용량 변경을 직접 제어할 수 있게 합니다.
- **예약 확장**은 알려진 수요 패턴을 충족하도록 특정 시각에 용량 조정을 자동화합니다.
- **동적 확장**(목표 추적, 단계 확장, 단순 확장)은 애플리케이션 부하 변화에 실시간으로 반응합니다.
- **예측 확장**은 과거 트렌드를 사용해 미래를 예측하고 용량을 미리 준비합니다.

### 7.1. 고정 용량(확장 없음)

기본적으로 Auto Scaling 그룹은 지정한 "원하는 용량"으로 인스턴스 수를 유지합니다. 확장 정책이나 예약 작업이 연결되어 있지 않다면, 그룹은 단순히 이 목표를 충족할 만큼의 인스턴스를 시작하고 계속 실행합니다. 일부 인스턴스가 비정상 상태가 되어도(이 경우 교체됩니다) 마찬가지입니다.

워크로드가 상대적으로 일정하거나, 비정상 인스턴스의 자동 교체와 함께 기본 수준의 용량만 보장하고 싶을 때 유용합니다.

### 7.2. 수동 확장

수동 확장은 Auto Scaling 그룹의 원하는 용량을 직접 변경하는 것을 포함합니다(예: AWS Management Console, CLI, API를 통해). 인스턴스 수를 수동으로 늘리거나 줄일 수 있고, 특정 인스턴스를 연결하거나 분리할 수도 있습니다.

**핵심 사항:**
- 추가하거나 제거할 정확한 인스턴스 수를 직접 결정합니다.
- 현재 필요에 대한 직접적인 통찰이 있을 때 임시 변경에 유용합니다.

수동 확장은 정밀한 제어를 제공하지만 부하 변화에 자동으로 반응하지 않으므로, 일반적으로 다른 방식과 함께 사용되거나 단기적인 조정에 사용됩니다.

### 7.3. 예약 확장

예약 확장은 특정 날짜나 반복되는 시각에 발생하는 확장 작업을 정의할 수 있게 합니다. 그룹의 원하는 용량(선택적으로 최소·최대 용량도)을 조정하는 "예약 작업"을 설정합니다.

**핵심 사항:**
- 예측 가능한 부하 패턴(예: 평일 아침마다 트래픽이 많은 웹사이트, 또는 알려진 계절적 피크)에 이상적입니다.
- 시각(UTC나 로컬 시간대 사용)과 반복 주기(cron 표현식이나 단순 반복 패턴 사용)를 지정합니다.

이 방식은 부하 지표가 반응을 트리거하기를 기다리지 않고, 예상한 정확한 시점에 용량이 늘거나 줄도록 선제적으로 관리해 줍니다.

### 7.4. 동적 확장

동적 확장은 애플리케이션 수요의 변화에 따라 실시간으로 용량을 조정합니다. 여러 유형이 있습니다.
#### a. 목표 추적 확장

이 정책 유형은 목표 지표 값을 유지하도록 용량을 지속적으로 조정합니다(예: 평균 CPU 사용률을 50%로 유지). 온도 조절기와 매우 유사하게 동작합니다. 목표를 설정하면 시스템이 필요에 따라 확장하거나 축소합니다.

**이점:**
- 변화하는 부하에 자동으로 적응합니다.
- 커스텀 CloudWatch 경보가 필요 없어 구성이 단순해집니다.

#### b. 단계 확장

단계 확장 정책은 지표 초과 정도에 따라 여러 조정 수준("단계")을 정의할 수 있게 합니다. 예를 들어 CPU 사용률이 60%를 넘으면 인스턴스 1개를 추가하고, 80%를 넘으면 2개를 더 추가할 수 있습니다.

**이점:**
- 용량 변경에 대한 세밀한 제어를 제공합니다.
- 지표와 용량의 관계가 선형적이지 않을 때 유용합니다.

#### c. 단순 확장

단순 확장은 단일 조정을 사용하며 작업 사이에 쿨다운 기간을 둡니다. 예를 들어 CloudWatch 경보가 임계값을 초과하면 정책은 인스턴스 1개를 추가한 다음, 다른 확장 작업을 허용하기 전에 쿨다운 기간을 기다립니다.

**이점:**
- 조정 수준이 하나만 필요할 때는 단계 확장보다 구성이 쉽습니다.

### 7.5. 예측 확장

예측 확장은 머신 러닝을 사용해 과거 데이터를 분석하고 미래 부하를 예측합니다. 이 예측을 기반으로 부하가 실제로 증가하기 전에 용량이 선제적으로 조정됩니다. 규칙적이고 예측 가능한 패턴을 가진 워크로드에 특히 유용합니다.

![predictive-scaling](@site/docs/Compute/_assets/predictive-scaling.png)

**핵심 사항:**
- 일반적으로 14일간의 과거 지표를 검토해 다음 이틀간의 부하를 예측합니다.
- 그런 다음 시스템은 필요할 때 용량이 준비되도록 확장 작업을 미리 예약합니다.

**사용 시점:**
- 주기적이거나 예측 가능한 트래픽 패턴이 있을 때(예: 업무 시간 vs. 비업무 시간).
- 초기화 시간이 길어 용량을 미리 프로비저닝해야 하는 애플리케이션.

## 8. 상태 확인

Amazon EC2 Auto Scaling은 원하는 용량을 유지하기 위해 Auto Scaling 그룹 내 인스턴스의 상태를 지속적으로 모니터링합니다.

Amazon EC2 Auto Scaling은 다음 상태 확인 중 **하나 이상**을 사용해 `InService` 인스턴스의 상태를 판단할 수 있습니다.

| 상태 확인 유형                                   | 확인 내용                                                                                                                                                                                                              |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ***Amazon EC2 상태 확인과 예약된 이벤트*** | - 인스턴스가 실행 중인지 확인합니다.<br />- 인스턴스에 문제를 일으킬 수 있는 기반 하드웨어나 소프트웨어 문제를 확인합니다.<br /><br />Auto Scaling 그룹의 기본 상태 확인 유형입니다.                       |
| ***Elastic Load Balancing 상태 확인***          | - 로드 밸런서가 인스턴스를 정상으로 보고하는지 확인해, 인스턴스가 요청을 처리할 수 있는지 확인합니다.<br /><br />이 상태 확인 유형을 실행하려면 Auto Scaling 그룹에서 활성화해야 합니다. |
| ***VPC Lattice 상태 확인***                     | - VPC Lattice가 인스턴스를 정상으로 보고하는지 확인해, 인스턴스가 요청을 처리할 수 있는지 확인합니다.<br /><br />이 상태 확인 유형을 실행하려면 Auto Scaling 그룹에서 활성화해야 합니다.       |
| ***Amazon EBS 상태 확인***                      | - EBS 볼륨에 도달 가능한지, I/O 상태 확인을 통과하는지 확인합니다.<br /><br />이 상태 확인 유형을 실행하려면 Auto Scaling 그룹에서 활성화해야 합니다.                                                            |
| ***커스텀 상태 확인***                          | - 커스텀 상태 확인에 따라 인스턴스 상태 문제를 나타낼 수 있는 다른 모든 문제를 확인합니다.                                                                                                         |

## 9. 결론

Amazon EC2 Auto Scaling은 수요에 따라 EC2 인스턴스 수를 동적으로 조정함으로써 애플리케이션을 사용 가능하고 복원력 있으며 비용 효율적으로 유지하도록 설계된 필수적인 AWS 서비스입니다. 수동 조정, 예약 작업, 동적(반응형) 정책, 예측 확장 중 무엇을 사용하든, Auto Scaling은 플릿 관리를 자동화해 핵심 애플리케이션 로직에 집중할 수 있게 해줍니다.

더 자세한 정보는 [공식 문서](https://docs.aws.amazon.com/autoscaling/ec2/userguide/what-is-amazon-ec2-auto-scaling.html)를 참고하세요.
