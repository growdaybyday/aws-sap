# AWS Elastic Beanstalk

## 1. 소개

AWS Elastic Beanstalk는 웹 애플리케이션과 서비스를 배포·관리·확장하는 것을 단순화하는 완전관리형 PaaS(Platform as a Service)입니다. 인프라 프로비저닝의 복잡성을 추상화함으로써, Elastic Beanstalk는 용량 프로비저닝, 로드 밸런싱, 자동 확장, 애플리케이션 상태 모니터링을 자동으로 처리하는 동안 코드 작성에 집중할 수 있게 합니다. Java, .NET, PHP, Node.js, Python, Ruby, Go, Docker 등으로 작성된 애플리케이션을 지원합니다.

## 2. Elastic Beanstalk 개념

### 2.1. 애플리케이션

Elastic Beanstalk _애플리케이션_은 _환경_, _버전_, _환경 구성_을 포함한 Elastic Beanstalk 구성 요소의 논리적 집합입니다. Elastic Beanstalk에서 애플리케이션은 개념적으로 폴더와 유사합니다. AWS Elastic Beanstalk는 애플리케이션을 실행하는 모든 리소스를 _환경_으로 관리할 수 있게 합니다.

### 2.2. 애플리케이션 버전

Elastic Beanstalk에서 _애플리케이션 버전_은 웹 애플리케이션을 위해 배포 가능한 코드의 특정 라벨이 붙은 반복본을 가리킵니다. 애플리케이션 버전은 배포 가능한 코드(예: Java WAR 파일)를 담은 Amazon S3(Simple Storage Service) 오브젝트를 가리킵니다. 애플리케이션 버전은 애플리케이션의 일부입니다. 애플리케이션은 여러 버전을 가질 수 있고 각 애플리케이션 버전은 고유합니다. 실행 중인 환경에서는 이미 애플리케이션에 업로드한 버전 중 하나를 배포할 수도 있고, 새 애플리케이션 버전을 업로드해 즉시 배포할 수도 있습니다. 웹 애플리케이션의 한 버전과 다른 버전 간의 차이를 테스트하기 위해 여러 애플리케이션 버전을 업로드할 수도 있습니다.

### 2.3. 환경

_환경_은 애플리케이션 버전을 실행하는 AWS 리소스의 집합입니다. 각 환경은 한 번에 하나의 애플리케이션 버전만 실행하지만, 동일한 애플리케이션 버전이나 서로 다른 애플리케이션 버전을 여러 환경에서 동시에 실행할 수 있습니다. 환경을 만들면 Elastic Beanstalk가 지정한 애플리케이션 버전을 실행하는 데 필요한 리소스를 AWS 계정에 프로비저닝합니다.

### 2.4. 환경 계층

Elastic Beanstalk 환경을 시작할 때는 먼저 환경 계층을 선택합니다. 환경 계층은 그 환경이 실행하는 애플리케이션의 유형을 지정하고, Elastic Beanstalk가 이를 지원하기 위해 프로비저닝할 리소스를 결정합니다. HTTP 요청을 처리하는 애플리케이션은 웹 서버 환경 계층에서 실행됩니다. Amazon SQS(Simple Queue Service) 큐에서 작업을 가져오는 백엔드 환경은 워커 환경 계층에서 실행됩니다.

### 2.5. 환경 구성

_환경 구성_은 환경과 그에 연관된 리소스가 어떻게 동작할지 정의하는 파라미터와 설정의 집합을 식별합니다. 환경의 구성 설정을 업데이트하면 Elastic Beanstalk는 변경 유형에 따라 기존 리소스에 자동으로 변경을 적용하거나 새 리소스를 삭제 후 배포합니다.

### 2.6. 저장된 구성

_저장된 구성_은 고유한 환경 구성을 만들 때 시작점으로 사용할 수 있는 템플릿입니다. Elastic Beanstalk 콘솔, EB CLI, AWS CLI, API를 사용해 저장된 구성을 만들고 수정하며 환경에 적용할 수 있습니다. API와 AWS CLI는 저장된 구성을 _구성 템플릿_이라고 부릅니다.

### 2.7. 플랫폼

_플랫폼_은 운영체제, 프로그래밍 언어 런타임, 웹 서버, 애플리케이션 서버, Elastic Beanstalk 구성 요소의 조합입니다. 웹 애플리케이션을 설계할 때 특정 플랫폼을 대상으로 지정합니다. Elastic Beanstalk는 애플리케이션을 구축할 수 있는 다양한 플랫폼을 제공합니다.

## 3. 웹 서버 환경

AWS Elastic Beanstalk의 **웹 서버 환경**은 HTTP 요청을 처리하는 애플리케이션을 호스팅하도록 설계되었습니다. 이런 환경을 만들면 Elastic Beanstalk는 애플리케이션을 실행하는 데 필요한 AWS 리소스를 자동으로 프로비저닝하고 관리합니다. 이 리소스에는 다음이 포함됩니다.

- **Elastic Load Balancer(ELB):** 애플리케이션으로 트래픽을 라우팅하는 단일 퍼블릭 URL(CNAME)을 제공합니다. 환경의 URL(예: `myapp.us-west-2.elasticbeanstalk.com`)은 ELB DNS 이름을 가리키는 CNAME 별칭입니다.
- **Auto Scaling 그룹:** 애플리케이션을 실행하는 Amazon EC2 인스턴스 그룹을 관리합니다. Auto Scaling은 수요에 따라 인스턴스 수를 조정합니다. 부하가 높을 때는 인스턴스를 추가하고 수요가 줄면 종료하면서도 항상 최소 하나의 인스턴스가 실행되도록 보장합니다.
- **Amazon EC2 인스턴스:** 선택한 컨테이너 유형에 따라 미리 구성된 소프트웨어 스택으로 시작됩니다. 예를 들어 Apache Tomcat 컨테이너를 실행하는 환경은 Apache와 Tomcat이 설치된 Amazon Linux를 사용합니다.

![eb-web-server](@site/docs/Compute/_assets/eb-web-server.png)

### 3.1. 핵심 구성 요소

- **컨테이너 유형:** 기반이 되는 운영체제와 애플리케이션 서버 소프트웨어(예: Apache Tomcat, Node.js 등)를 결정합니다. 환경의 각 인스턴스는 선택한 플랫폼에 대응하는 컨테이너를 실행합니다.
- **호스트 관리자(HM):** 모든 EC2 인스턴스에서 실행되는 소프트웨어 구성 요소입니다. 담당하는 역할은 다음과 같습니다.
    - 애플리케이션 배포.
    - 이벤트, 지표, 인스턴스 수준 로그의 집계와 보고.
    - 애플리케이션과 서버 상태 모니터링.
    - 패치와 로그 순환, Amazon S3로의 로그 게시 포함.

### 3.2. 네트워킹과 보안

- **보안 그룹:** Elastic Beanstalk는 EC2 인스턴스에 기본 보안 그룹을 할당하며, 일반적으로 80번 포트(HTTP)의 인바운드 트래픽을 허용하도록 구성됩니다. 보안 요구사항에 맞게 이 설정을 커스터마이징할 수 있습니다.
- **DNS 관리:** Elastic Beanstalk가 제공하는 환경 URL은 Amazon Route 53으로 관리되며, 사용자 친화적인 CNAME을 ELB의 DNS 이름에 매핑합니다.

### 3.3. 추가 고려사항

- **모니터링과 관리:** 각 인스턴스의 호스트 관리자는 중요한 운영 데이터를 제공합니다. 지표, 오류, 이벤트는 Elastic Beanstalk 콘솔, API, 명령줄 도구를 통해 확인할 수 있습니다.
- **커스터마이징:** Elastic Beanstalk가 인프라 관리의 많은 부분을 추상화하지만, 인스턴스 구성, 보안 그룹, 확장 파라미터 같은 측면을 커스터마이징할 수 있는 능력은 그대로 유지됩니다.

## 4. 워커 환경

**워커 환경**은 백그라운드 작업을 비동기로 처리하는 애플리케이션을 위해 설계되었습니다. 웹 서버 환경처럼 HTTP 요청을 처리하는 대신, 워커 환경은 Amazon SQS(Simple Queue Service) 큐에서 메시지를 가져와 처리합니다.

![eb-worker](@site/docs/Compute/_assets/eb-worker.png)
### 4.1. 핵심 구성 요소

- **Auto Scaling 그룹과 EC2 인스턴스:**
    Elastic Beanstalk는 Auto Scaling 그룹으로 묶인 하나 이상의 EC2 인스턴스를 프로비저닝합니다. 이를 통해 최소 용량을 유지하면서 워크로드에 따라 인스턴스 수가 조정됩니다.

- **IAM 역할:**
    워커 환경과 연관된 IAM 역할이 생성됩니다. 이 역할은 환경이 다른 AWS 서비스(Amazon SQS, CloudWatch 등)와 상호작용하는 데 필요한 권한을 부여합니다.

- **Amazon SQS 큐:**
    이미 SQS 큐가 없다면, Elastic Beanstalk가 워커 환경을 위해 자동으로 하나를 만들고 프로비저닝합니다. 이 큐는 워커 환경이 사용하는 비동기 처리 모델의 핵심입니다.

- **워커 데몬:**
	각 EC2 인스턴스에서 Elastic Beanstalk는 사용하는 프로그래밍 언어에 맞춘 데몬을 설치합니다. 이 데몬은 새 메시지가 있는지 SQS 큐를 지속적으로 폴링합니다. 메시지를 받으면 그 메시지 데이터를 애플리케이션 코드로 전달해 처리합니다.

- **모니터링과 경보:**
    Amazon CloudWatch가 통합되어 워커 환경의 상태 모니터링과 경보를 제공해 성능을 추적하고 문제를 해결하는 데 도움을 줍니다.

### 4.2. 동작 방식

1. **메시지 수신:**
    외부 시스템이나 애플리케이션이 SQS 큐로 메시지를 보냅니다.

2. **폴링:**
    각 인스턴스의 워커 데몬이 SQS 큐를 지속적으로 폴링합니다. 모든 인스턴스가 동일한 큐를 공유하므로 메시지가 그들 사이에 분산됩니다.

3. **처리:**
    메시지를 가져오면 데몬이 이를 워커 애플리케이션으로 전달합니다. 그러면 애플리케이션이 작업을 비동기로 처리합니다.

4. **확장과 모니터링:**
    워크로드와 구성된 임계값에 따라 Auto Scaling이 EC2 인스턴스 수를 조정합니다. CloudWatch는 성능과 시스템 상태에 대한 통찰을 제공합니다.

## 5. 핵심 이점

- **관리 단순화:** 인프라를 수동으로 프로비저닝하거나 관리할 필요가 없습니다. 서비스가 대신 처리합니다.
- **확장성:** 자동 확장과 로드 밸런싱이 기본으로 내장되어 있어 애플리케이션이 가변적인 트래픽 부하를 처리할 수 있습니다.
- **유연성과 커스터마이징:** Elastic Beanstalk가 인프라 세부 사항을 추상화하지만, AWS 리소스에 대한 완전한 제어권은 그대로 유지되며 필요에 따라 설정을 커스터마이징할 수 있습니다.
- **컴플라이언스:** Elastic Beanstalk는 다양한 컴플라이언스 표준(ISO, PCI, SOC, HIPAA)을 충족하도록 설계되어 규제 대상 애플리케이션에도 적합합니다.
- **비용 효율성:** Elastic Beanstalk 자체에는 추가 요금이 없습니다. 기반이 되는 AWS 리소스에 대해서만 요금을 지불합니다.
