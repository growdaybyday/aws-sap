# AWS Lambda

## 1. 소개

AWS Lambda는 서버를 프로비저닝하거나 관리하지 않고도 코드를 실행할 수 있게 하는 Amazon Web Services의 서버리스, 이벤트 기반 컴퓨팅 서비스입니다. Lambda를 사용하면 함수로 구성된 코드를 업로드하기만 하면 되며, 서비스가 들어오는 이벤트에 대응해 애플리케이션을 실행하고 확장하는 데 필요한 모든 것을 자동으로 처리합니다. 사용한 컴퓨팅 시간에 대해서만 요금을 지불하므로 많은 워크로드에서 매우 비용 효율적인 옵션입니다.

## 2. 핵심 개념

### 2.1. Lambda 함수

Lambda 함수는 AWS Lambda의 기본 단위입니다. 이벤트에 대응해 실행되는, 자체적으로 완결된 코드 조각과 그 구성(메모리, 타임아웃, 환경 변수 등)을 나타냅니다. Lambda 함수를 만들 때는 코드를 업로드하거나(또는 컨테이너 이미지를 지정하고) AWS Lambda가 실행을 시작하기 위해 호출하는 메서드인 핸들러를 지정합니다. Lambda 함수는 들어오는 이벤트 비율에 따라 자동으로 확장되는 관리형 인프라에서 실행되며, 실제로 사용한 컴퓨팅 시간에 대해서만 요금이 부과됩니다.

### 2.2. Lambda 런타임

Lambda 런타임은 함수 코드가 실행되는 실행 환경을 제공합니다. 런타임에는 기반이 되는 운영체제, 언어 라이브러리, 핸들러를 로드하는 데 필요한 시작 루틴이 포함됩니다. AWS는 Node.js, Python, Java, Go, .NET, Ruby 등을 위한 다양한 관리형 런타임을 제공하므로, 런타임 환경을 관리하는 대신 코드 작성에 집중할 수 있습니다. 또한 언어나 프레임워크가 네이티브로 지원되지 않는다면 커스텀 런타임을 제공할 수도 있어, 개발 환경에 더 큰 유연성을 부여합니다.

### 2.3. 트리거와 이벤트 소스 매핑

AWS CLI(Command Line Interface)나 Lambda API를 사용해 Lambda 함수를 수동으로 호출할 수 있지만, 프로덕션 애플리케이션에서는 특정 이벤트에 대응해 다른 AWS 서비스가 함수를 호출하는 것이 더 일반적입니다. 예를 들어 Amazon DynamoDB 테이블에 항목이 추가될 때마다 함수를 실행하고 싶을 수 있습니다.

특정 이벤트에 대응해 실행되도록 함수를 구성하려면 **_트리거_**를 추가합니다. 트리거를 만들면 다른 AWS 서비스는 특정 이벤트가 발생할 때마다 이벤트 객체를 Lambda로 직접 밀어넣어 함수를 호출할 수 있습니다. 하나의 함수는 여러 트리거를 가질 수 있으며, 각 트리거는 독립적으로 함수를 호출합니다.

Amazon Kinesis나 Amazon Simple Queue Service(Amazon SQS) 같은 일부 유형의 스트림·큐 서비스는 트리거를 사용해 Lambda를 직접 호출할 수 없습니다. 이런 서비스에서는 대신 **_이벤트 소스 매핑_**을 만들어야 합니다. 이벤트 소스 매핑은 새 이벤트가 있는지 확인하기 위해 스트림이나 큐를 지속적으로 폴링하는 특수한 유형의 Lambda 리소스입니다. 예를 들어 이벤트 소스 매핑은 새 메시지가 추가되었는지 확인하기 위해 Amazon SQS 큐를 폴링할 수 있습니다. Lambda는 구성한 한도에 도달할 때까지 새 메시지를 하나의 페이로드로 배치 처리한 다음, 배치의 모든 레코드를 담은 단일 이벤트 객체로 함수를 호출합니다.

![lambda-event-source-mapping](@site/docs/Compute/_assets/lambda-event-source-mapping.png)

### 2.4. 이벤트 객체

Lambda 함수가 트리거되면 AWS Lambda는 이벤트 객체를 함수의 핸들러로 전달합니다. 이 객체는 트리거 이벤트에 대한 세부 정보를 담은 JSON 형식의 데이터 구조입니다. 그 내용은 소스에 따라 달라집니다. 예를 들어 S3 이벤트는 버킷과 오브젝트 세부 정보를 포함하고, API Gateway 트리거는 HTTP 요청 데이터를 포함합니다. 이벤트 객체를 통해 함수는 맥락을 이해하고 들어오는 데이터에 적절하게 대응할 수 있습니다.

### 2.5. Lambda 권한

Lambda 권한은 누가(또는 무엇이) Lambda 함수를 호출할 수 있는지 결정합니다. 이 권한은 AWS Identity and Access Management(IAM)와 Lambda 리소스 기반 정책으로 제어됩니다. 이를 통해 인가된 AWS 서비스, 사용자, 계정만 함수를 트리거할 수 있도록 보장합니다. 예를 들어 API Gateway에 함수 호출 권한을 부여하거나, 특정 프린시펄로만 호출을 제한할 수 있습니다. 이런 권한을 신중하게 정의함으로써 함수를 보호하고 서버리스 아키텍처에 대한 제어력을 유지할 수 있습니다.

### 2.6. Lambda 프로그래밍 모델

핵심적으로 Lambda는 개별 함수를 중심으로 구축됩니다. 각 Lambda 함수는 특정 로직의 일부를 캡슐화하며 이벤트에 대응해 실행됩니다. 함수는 코드와 구성(메모리 할당, 타임아웃 설정, 환경 변수 등)으로 정의됩니다.

함수가 호출되면 AWS Lambda는 진입점인 지정된 핸들러를 호출하며, 이 핸들러는 두 가지 핵심 파라미터를 받습니다.

1. **이벤트 객체:** 함수를 트리거한 이벤트에 대한 세부 정보를 담습니다(예: S3 오브젝트 업로드, 큐의 메시지, HTTP 요청).
2. **컨텍스트 객체:** 함수 이름, 로그 스트림 세부 정보, 남은 실행 시간을 가져오는 메서드 같은 런타임 정보를 제공합니다.

Lambda 함수의 각 호출은 스테이트리스합니다. 다만 실행 환경은 여러 호출에 걸쳐 재사용될 수 있습니다. 즉 핸들러 밖에서 객체나 연결을 초기화하면 이들이 유지되고 재사용되어, 이후 호출의 지연 시간을 줄일 수 있습니다.

AWS Lambda는 여러 런타임(Node.js, Python, Java, Go, .NET, Ruby 등)을 지원하므로, 애플리케이션의 요구에 가장 적합한 언어로 함수를 작성할 수 있습니다. 커스텀 런타임도 지원되어 네이티브로 지원되는 언어를 넘어서는 유연성을 제공합니다.

## 3. Lambda 실행 환경

AWS Lambda의 실행 환경은 함수 코드가 실행되는 관리형 런타임 컨테이너입니다. 이 컨테이너들은 경량화된 Linux 운영체제(주로 Amazon Linux나 Amazon Linux 2)를 기반으로 하며 Firecracker로 구동되는 microVM을 사용합니다. 이 격리는 컨테이너가 재사용되더라도 함수 호출 간 보안 경계를 제공합니다.

실행 환경에는 런타임(Node.js, Python, Java, Go, .NET, Ruby 등)과 AWS가 제공하는 다른 라이브러리가 미리 로드되어 있습니다. 이는 함수의 배포 패키지에서 필요한 작업을 최소화하면서 일관성과 빠른 시작을 보장합니다.

각 컨테이너는 임시 스토리지 디렉터리(일반적으로 `/tmp`, **기본 용량 512MB**)에 접근할 수 있으며, 이는 동일한 컨테이너에서 이루어지는 호출 간에는 유지되지만 컨테이너가 재활용되면 정리됩니다.

### 3.1. 실행 환경 생명주기

![lambda-lifecycle](@site/docs/Compute/_assets/lambda-lifecycle.png)

**1. 초기화(콜드 스타트)**

- **컨테이너 프로비저닝:**
    Lambda 함수가 처음 호출되거나, 사용 가능한 기존 환경이 없으면 새 컨테이너가 시작됩니다. 이는 리소스 프로비저닝, microVM 시작, 운영체제 초기화를 포함합니다.
- **런타임 초기화:**
    컨테이너가 준비되면 Lambda 런타임이 로드됩니다. 이 단계에서 함수의 코드가 메모리에 로드되고, 핸들러 밖(전역 스코프)의 초기화 코드가 실행됩니다. 이 과정을 흔히 "콜드 스타트"라고 부르며, 첫 호출에 지연 시간을 추가할 수 있습니다.
- **스냅샷(Lambda SnapStart):**
    Lambda SnapStart 같은 기능을 사용하면 AWS는 완전히 초기화된 실행 환경의 스냅샷을 찍을 수 있습니다. 이 스냅샷은 나중에 빠르게 복원할 수 있어, 이후 호출의 콜드 스타트 지연 시간을 크게 줄여 줍니다.

**2. 호출(웜 스타트)**

- **이벤트 처리:**
    실행 환경이 초기화되면 AWS Lambda는 이벤트 객체와 컨텍스트 객체를 전달해 함수의 핸들러를 호출합니다. 컨테이너가 이미 준비되어 있으므로, 동일한 컨테이너에서의 이후 호출은 "웜 스타트"로 간주되어 이전에 초기화된 코드와 구성된 네트워크 연결을 재사용하는 이점을 얻습니다.
- **리소스 재사용:**
    초기화 중에 만들어진 데이터베이스 연결이나 SDK 클라이언트 같은 전역 객체는 이후 호출에서도 계속 사용할 수 있어, 성능을 개선하고 지연 시간을 줄여 줍니다.

**3. 유휴와 재사용**

- **환경 재사용:**
	AWS Lambda는 웜 실행 환경을 재사용해 여러 호출을 처리합니다. 동일한 컨테이너가 일정 기간 유휴 상태가 되기 전까지 많은 요청을 순차적으로 처리할 수 있습니다.
- **스테이트리스 설계:**
    실행 환경이 캐시된 객체를 유지하고 재사용할 수는 있지만, Lambda 함수는 스테이트리스하게 설계되었습니다. 메모리에 저장된 상태가 컨테이너의 생명주기를 넘어 개별 호출 간에 유지된다고 가정해서는 안 됩니다.

**4. 종료와 재활용**

- **환경 종료:**
    실행 환경이 일정 기간(AWS가 공개적으로 밝히지 않지만 일반적으로 몇 분 단위) 유휴 상태로 유지되면 회수될 수 있습니다. 회수되면 컨테이너의 메모리나 임시 파일 시스템에 저장된 데이터는 사라집니다.
- **생명주기 관리:**
    AWS는 재활용 과정을 자동으로 관리해, 컨테이너가 결국 종료되어 리소스를 확보하고 격리를 유지하도록 보장합니다. 개발자는 호출 간 상태의 장기 유지에 의존하지 않도록 함수를 설계해야 합니다.

> **시험 팁:** 콜드 스타트(컨테이너 + 런타임 초기화) 동안 걸리는 시간은 일반적으로 실행 환경이 이미 초기화된 웜 스타트보다 더 길습니다. 프로비저닝된 동시성이나 SnapStart 같은 기법으로 콜드 스타트 지연을 완화할 수 있습니다.
## 4. 이벤트 기반 아키텍처

이벤트 기반 아키텍처에서는 각 Lambda 함수가 좁은 범위의 특정 명령을 수행하는 마이크로서비스로 취급됩니다.

### 4.1. 이벤트 기반 아키텍처의 이점

**1. 폴링과 웹훅 대체:**

![lambda-webhook](@site/docs/Compute/_assets/lambda-webhook.png)

폴링이나 웹훅 같은 전통적인 통합 방식은 비효율적이고 확장하기 어려울 수 있습니다. 이벤트 기반 아키텍처는 이를, 필터링되고 라우팅되어 소비자에게 전달되는 이벤트로 대체함으로써 지연 시간과 리소스 낭비를 줄입니다.

**2. 복잡성 감소:**

모놀리식 애플리케이션을 분리된 마이크로서비스로 나눔으로써 각 함수가 하나의 책임에 집중할 수 있습니다. 예를 들어 이커머스 애플리케이션은 주문 접수, 결제 처리, 재고 관리를 별도의 독립적으로 확장 가능한 서비스로 나눌 수 있습니다. 이런 분리는 서로 다른 속도로 동작하는 서비스 사이에 (예를 들어 Amazon SQS를 통한) 버퍼링도 가능하게 합니다.

![lambda-event-arch-example](@site/docs/Compute/_assets/lambda-event-arch-example.png)

**3. 확장성과 확장 용이성 개선:**

메시징 서비스(Amazon SNS, SQS, EventBridge 등)에 게시된 이벤트는 시스템이 갑작스러운 트래픽 급증을 처리할 수 있게 하는 탄력적인 버퍼를 만듭니다. 이벤트 생산자와 소비자 사이의 느슨한 결합은 기존 구성 요소를 수정하지 않고도 나중에 추가 서비스를 통합할 수 있게 합니다.

### 4.2. 이벤트 기반 아키텍처의 트레이드오프

- **가변적인 지연 시간:**
    아키텍처가 분리된 서비스 간 네트워크 통신에 의존하므로, 모든 구성 요소가 같은 메모리 공간에서 실행되는 모놀리식 시스템에 비해 지연 시간이 덜 예측 가능할 수 있습니다.

- **최종 일관성:**
    이벤트가 분산 시스템 전반의 개별적인 상태 변화를 나타내므로, 전체 시스템 상태는 흔히 최종적으로만 일관성을 갖습니다. 이는 엄격한 일관성이 필요할 때 (강력한 일관성 읽기나 트랜잭션 지원을 갖춘 DynamoDB 같은) 데이터베이스를 사용하는 등 특별한 설계 고려가 필요합니다.

- **호출자에게 값 반환:**
    비동기 이벤트 기반 시스템에서는 함수의 결과가 호출자에게 즉시 반환되지 않습니다. 대신 값을 직접 반환하는 대신 (흔히 데드 레터 큐로) 성공이나 실패를 추적합니다.

- **서비스 전반의 디버깅:**
    여러 서비스를 거치는 이벤트의 경로를 추적하는 것은 어려울 수 있습니다. AWS는 견고한 로깅, 서비스 전반에 걸친 트랜잭션 식별자 삽입, 분산 트랜잭션 추적을 위한 AWS X-Ray 같은 도구 사용의 중요성을 강조합니다.

### 4.3. Lambda 기반 이벤트 기반 애플리케이션의 안티패턴

- **Lambda 모놀리스:**
    기존 모놀리식 애플리케이션을 "그대로" 단일 Lambda 함수로 마이그레이션하면 배포 패키지가 비대해지고, 권한이 지나치게 광범위해지며, 코드를 테스트·유지·업그레이드하기 어려워질 수 있습니다. 권장되는 접근 방식은 애플리케이션을 더 작고 집중된 Lambda 함수(마이크로서비스)로 나누는 것입니다.
    ![lambda-microservice](@site/docs/Compute/_assets/lambda-microservice.png)

- **폭주 호출을 유발하는 재귀 패턴:**
    Lambda 함수가 결과적으로 자신을 트리거하는 이벤트를 쓰면(예: S3에 쓰고 S3 put 이벤트로 트리거되는 함수) 무한 루프가 생길 수 있습니다. 이런 재귀 루프를 감지하고 방지하는 것은 리소스 고갈을 피하는 데 매우 중요합니다.
	![lambda-recursive](@site/docs/Compute/_assets/lambda-recursive.png)

- **Lambda 함수가 다른 Lambda 함수를 동기적으로 호출하는 경우:**
    코드 재사용은 흔한 관행이지만, 하나의 Lambda 함수를 다른 함수에서 직접 호출하고(그 응답을 기다리면) 실행 시간과 비용이 늘어날 수 있습니다. 대신 메시징(예: 오케스트레이션을 위한 SQS나 AWS Step Functions)을 통한 분리가 확장성과 내결함성 측면에서 선호됩니다.
    ![lambda-calling-lambda](@site/docs/Compute/_assets/lambda-calling-lambda.png)

- **단일 Lambda 함수 안에서의 동기적 대기:**
    하나의 함수 안에서 순차적인 작업(예: S3에 쓴 다음 DynamoDB에 쓰기)을 결합하면 지연 시간이 누적될 수 있습니다. 작업을 이벤트로 통신하는 별도의 함수로 나누면 대기 시간을 줄이고 리소스 사용을 최적화할 수 있습니다.
	![lambda-sequential-lambda](@site/docs/Compute/_assets/lambda-sequential-lambda.png)

## 5. Lambda 메모리

Lambda는 구성된 메모리 양에 비례해 CPU 성능을 할당합니다. _메모리_는 런타임에 Lambda 함수가 사용할 수 있는 메모리 양입니다. **Memory** 설정을 사용해 함수에 할당되는 메모리와 CPU 성능을 늘리거나 줄일 수 있습니다. 메모리는 128MB에서 10,240MB까지 1MB 단위로 구성할 수 있습니다. 1,769MB에서 함수는 1개의 vCPU와 동등한 성능을 갖습니다(초당 1 vCPU초의 크레딧).

적절한 메모리 구성을 찾으려면 Amazon CloudWatch로 함수를 모니터링하고 메모리 사용량이 구성된 최댓값에 근접하면 경보를 설정하세요. 이는 메모리에 제약이 있는 함수를 식별하는 데 도움이 됩니다. CPU 바운드나 I/O 바운드 함수의 경우, 실행 시간을 모니터링하는 것도 통찰을 줄 수 있습니다. 이런 경우 메모리를 늘리면 컴퓨팅이나 네트워크 병목을 해결하는 데 도움이 될 수 있습니다.

오픈소스 [AWS Lambda Power Tuning](https://github.com/alexcasalboni/aws-lambda-power-tuning) 도구 사용도 고려할 수 있습니다. 이 도구는 AWS Step Functions를 사용해 서로 다른 메모리 할당으로 여러 개의 동시 버전의 Lambda 함수를 실행하고 성능을 측정합니다. 입력 함수는 실제 AWS 계정에서 실행되어 실제 HTTP 호출과 SDK 상호작용을 수행하며, 실제 프로덕션 시나리오에서의 예상 성능을 측정합니다. 이 도구를 사용해 배포하는 새 함수의 성능을 자동으로 측정하는 CI/CD 프로세스를 구현할 수도 있습니다.

## 6. 컨테이너 이미지로 Lambda 함수 만들기

AWS Lambda는 함수를 위한 대체 패키징 형식으로 컨테이너 이미지를 지원합니다. 이 기능을 통해 코드, 의존성, 심지어 커스텀 런타임까지 표준 컨테이너 이미지로 묶을 수 있으며, 이 이미지는 Amazon Elastic Container Registry(ECR)에 저장되어 함수 실행에 사용됩니다.

![lambda-docker](@site/docs/Compute/_assets/lambda-docker.png)

**이점과 사용 사례:**

- **익숙한 컨테이너 도구:**
    개발자는 기존 컨테이너 빌드와 CI/CD 파이프라인을 활용할 수 있어, Lambda를 컨테이너화된 워크플로에 더 쉽게 통합할 수 있습니다.
- **더 큰 의존성 지원:**
    늘어난 이미지 크기 제한 덕분에, 큰 바이너리, 복잡한 라이브러리, 비표준 런타임이 필요한 함수를 패키징할 수 있습니다.
- **커스터마이징 가능성:**
    컨테이너 이미지는 런타임 환경에 대한 더 큰 제어권을 제공해, 관리형 ZIP 배포로는 불가능한 특정 OS 수준 패키지나 커스텀 구성을 포함할 수 있게 합니다.

**모범 사례와 고려사항:**

- **이미지 크기 최적화:**
    제한이 10GiB이더라도 이미지를 최대한 가볍게 유지하면 콜드 스타트 시간을 줄이는 데 도움이 됩니다.
- **로컬에서 테스트:**
    Lambda에 배포하기 전에 Docker로 컨테이너 이미지를 로컬에서 테스트해 Lambda Runtime API 통합이 올바른지 확인하세요.
- **콜드 스타트 영향 모니터링:**
    웜 호출은 빠르지만 초기 콜드 스타트는 지연 시간을 추가할 수 있습니다. 애플리케이션이 낮은 지연 시간의 응답을 요구한다면 프로비저닝된 동시성 사용을 고려하세요.
- **보안 업데이트:**
    취약점을 최소화하기 위해 베이스 이미지와 의존성을 최신 상태로 유지하고, 컨테이너 보안에 대한 AWS 모범 사례를 따르세요.

## 7. 임시 스토리지

Lambda는 `/tmp` 디렉터리에서 함수를 위한 임시 스토리지를 제공합니다. 이 스토리지는 임시적이며 각 실행 환경에 고유합니다. **Ephemeral storage** 설정을 사용해 함수에 할당되는 임시 스토리지 양을 제어할 수 있습니다. **임시 스토리지는 512MB에서 10,240MB까지 1MB 단위로 구성할 수 있습니다.** `/tmp`에 저장된 모든 데이터는 AWS가 관리하는 키로 저장 시 암호화됩니다.

늘어난 임시 스토리지의 이점을 누리는 몇 가지 흔한 사용 사례입니다.

- **ETL(추출-변환-로드) 작업:** 코드가 중간 계산을 수행하거나 처리를 완료하기 위해 다른 리소스를 다운로드한다면 임시 스토리지를 늘리세요. 더 많은 임시 공간은 더 복잡한 ETL 작업을 Lambda 함수에서 실행할 수 있게 합니다.

- **머신 러닝(ML) 추론:** 많은 추론 작업은 라이브러리와 모델을 포함한 큰 참조 데이터 파일에 의존합니다. 임시 스토리지가 더 많으면 Amazon Simple Storage Service(Amazon S3)에서 더 큰 모델을 `/tmp`로 다운로드해 처리에 사용할 수 있습니다.

- **데이터 처리:** S3 이벤트에 대응해 Amazon S3에서 오브젝트를 다운로드하는 워크로드의 경우, `/tmp` 공간이 더 넓으면 인메모리 처리를 사용하지 않고도 더 큰 오브젝트를 처리할 수 있습니다. PDF를 만들거나 미디어를 처리하는 워크로드도 더 많은 임시 스토리지의 이점을 누립니다.

- **그래픽 처리:** 이미지 처리는 Lambda 기반 애플리케이션의 흔한 사용 사례입니다. 큰 TIFF 파일이나 위성 이미지를 처리하는 워크로드의 경우, 임시 스토리지가 더 많으면 라이브러리를 사용하고 Lambda에서 계산을 수행하기가 더 쉬워집니다.

## 8. 함수 타임아웃

Lambda는 타임아웃되기 전까지 정해진 시간 동안 코드를 실행합니다. _타임아웃_은 Lambda 함수가 실행될 수 있는 최대 시간(초)입니다. **이 설정의 기본값은 3초**이지만, 1초 단위로 최대 900초(15분)까지 조정할 수 있습니다.

## 9. 환경 변수

코드를 업데이트하지 않고도 함수의 동작을 조정하기 위해 환경 변수를 사용할 수 있습니다. 환경 변수는 함수의 버전별 구성에 저장되는 문자열 쌍입니다. Lambda 런타임은 환경 변수를 코드에서 사용할 수 있게 하고, 함수와 호출 요청에 대한 정보를 담은 추가 환경 변수도 설정합니다.

환경 변수는 함수 호출 전에 평가되지 않습니다. 정의한 값은 리터럴 문자열로 간주되며 확장되지 않습니다. 변수 평가는 함수 코드에서 수행하세요.

환경 변수를 사용해 테스트 환경과 프로덕션 환경에서 함수 동작을 커스터마이징할 수 있습니다. 예를 들어 코드는 동일하지만 구성이 다른 두 개의 함수를 만들 수 있습니다. 하나는 테스트 데이터베이스에 연결하고, 다른 하나는 프로덕션 데이터베이스에 연결합니다. 이 상황에서는 환경 변수를 사용해 데이터베이스의 호스트명과 다른 연결 세부 정보를 함수에 전달합니다.

다음 예시는 데이터베이스 호스트와 데이터베이스 이름을 환경 변수로 정의하는 방법을 보여줍니다.

![lambda-env](@site/docs/Compute/_assets/lambda-env.png)
### 9.1. 정의된 런타임 환경 변수

Lambda 런타임은 초기화 중에 여러 환경 변수를 설정합니다. 이 환경 변수의 대부분은 함수나 런타임에 대한 정보를 제공합니다. 이 환경 변수들의 키는 _예약되어_ 있어 함수 구성에서 설정할 수 없습니다. 이 변수들의 목록은 [여기](https://docs.aws.amazon.com/lambda/latest/dg/configuration-envvars.html#configuration-envvars-runtime)에서 확인할 수 있습니다.

## 10. Lambda 함수의 파일 시스템 접근

Amazon Elastic File System(Amazon EFS) 파일 시스템을 로컬 디렉터리에 마운트하도록 함수를 구성할 수 있습니다. Amazon EFS를 사용하면 함수 코드가 안전하게, 높은 동시성으로 공유 리소스에 접근하고 수정할 수 있습니다.

## 11. 함수 버전

버전을 사용해 함수 배포를 관리할 수 있습니다. 예를 들어 안정적인 프로덕션 버전의 사용자에게 영향을 주지 않고 베타 테스트를 위해 함수의 새 버전을 게시할 수 있습니다. Lambda는 함수를 게시할 때마다 새 버전을 만듭니다. 새 버전은 게시되지 않은 함수 버전의 복사본입니다. 게시되지 않은 버전은 `$LATEST`로 명명됩니다.

## 12. Lambda 별칭

Lambda 별칭은 본질적으로 Lambda 함수의 특정 버전을 가리키는 포인터나 참조입니다. 함수를 호출할 때 버전 번호 대신 사용할 수 있는 안정적이고 사용자 친화적인 이름(별칭)을 제공합니다.

별칭을 사용하면 함수 호출을 그 기반 버전으로부터 분리할 수 있습니다. 이 추상화는 별칭을 호출하는 클라이언트나 다른 서비스를 변경하지 않고도 별칭 뒤의 함수 버전을 업데이트할 수 있게 합니다.

![lambda-alias](@site/docs/Compute/_assets/lambda-alias.png)
### 12.1. Lambda 별칭 사용

각 별칭은 고유한 ARN을 가집니다. 별칭은 함수 버전만 가리킬 수 있으며 다른 별칭을 가리킬 수 없습니다. 별칭을 업데이트해 함수의 새 버전을 가리키게 할 수 있습니다.

Amazon Simple Storage Service(Amazon S3) 같은 이벤트 소스는 Lambda 함수를 호출합니다. 이 이벤트 소스들은 이벤트가 발생할 때 호출할 함수를 식별하는 매핑을 유지합니다. 매핑 구성에서 Lambda 함수 별칭을 지정하면, 함수 버전이 바뀌어도 매핑을 업데이트할 필요가 없습니다.

리소스 정책에서는 이벤트 소스가 Lambda 함수를 사용할 수 있는 권한을 부여할 수 있습니다. 정책에서 별칭 ARN을 지정하면, 함수 버전이 바뀌어도 정책을 업데이트할 필요가 없습니다.

### 12.2. 가중치 별칭

가중치 별칭을 사용해 동일한 함수의 두 서로 다른 버전 사이에 트래픽을 분산시킬 수 있습니다. 이 접근 방식을 사용하면 트래픽의 일부만으로 함수의 새 버전을 테스트하고, 필요하면 빠르게 되돌릴 수 있습니다. 이를 [캐너리 배포](https://docs.aws.amazon.com/whitepapers/latest/overview-deployment-options/canary-deployments.html)라고 합니다. 캐너리 배포는 모든 트래픽을 한 번에 전환하는 대신 새 버전을 일부 요청에만 노출한다는 점에서 블루/그린 배포와 다릅니다.

![lambda-weighted-alias](@site/docs/Compute/_assets/lambda-weighted-alias.png)

하나의 별칭은 최대 두 개의 Lambda 함수 버전을 가리킬 수 있습니다. 버전은 다음 기준을 충족해야 합니다.

- 두 버전 모두 동일한 [실행 역할](https://docs.aws.amazon.com/lambda/latest/dg/lambda-intro-execution-role.html)을 가져야 합니다.
- 두 버전 모두 동일한 [데드 레터 큐](https://docs.aws.amazon.com/lambda/latest/dg/invocation-async-retain-records.html#invocation-dlq) 구성을 가지거나, 데드 레터 큐 구성이 없어야 합니다.
- 두 버전 모두 게시되어 있어야 합니다. 별칭은 `$LATEST`를 가리킬 수 없습니다.

## 13. 응답 스트리밍

Lambda 함수 URL을 구성해 응답 페이로드를 클라이언트로 스트리밍할 수 있습니다. 응답 스트리밍은 첫 바이트까지의 시간(TTFB) 성능을 개선해 지연 시간에 민감한 애플리케이션에 도움이 될 수 있습니다. 이는 사용 가능해지는 대로 부분 응답을 클라이언트로 보낼 수 있기 때문입니다. 또한 응답 스트리밍을 사용해 더 큰 페이로드를 반환하는 함수를 만들 수도 있습니다. 응답 스트림 페이로드는 버퍼링된 응답의 6MB 제한에 비해 20MB의 소프트 제한을 갖습니다. 응답을 스트리밍하면 함수가 전체 응답을 메모리에 담을 필요도 없어집니다. 매우 큰 응답의 경우 이는 함수에 구성해야 하는 메모리 양을 줄일 수 있습니다.

## 14. 함수 호출하기

AWS Lambda 호출은 함수가 트리거되고 실행되는 방식입니다. 크게 동기와 비동기라는 두 가지 주요 유형이 있으며, 호출자가 함수와 상호작용하는 방식, 오류가 처리되는 방식, 호출의 전반적인 동작에서 차이가 있습니다.

### 14.1. 동기 호출

동기 호출에서는 호출자가 Lambda 함수가 처리를 완료하고 응답을 반환하기를 기다립니다. 클라이언트가 즉각적인 결과가 필요할 때 흔히 사용됩니다.

함수가 동기적으로 호출되면(호출 유형 `RequestResponse` 사용) AWS Lambda는 즉시 이벤트 데이터를 함수의 핸들러로 전달합니다. 호출자는 다음을 포함한 직접적인 응답을 받습니다.

- 상태 코드(예: 성공 시 200 OK)
- 함수가 반환한 페이로드(또는 함수가 실패한 경우 오류 세부 정보)

![lambda-sync](@site/docs/Compute/_assets/lambda-sync.png)

**사용 사례:**
- **웹 API와 마이크로서비스:** Amazon API Gateway 같은 서비스는 HTTP 요청을 처리하기 위해 Lambda 함수를 동기적으로 호출합니다.
- **실시간 데이터 처리:** 즉각적인 피드백이나 결과가 필요한 애플리케이션.
**오류 처리:**
* 실행 중 오류가 발생하면 그 오류는 즉시 호출자에게 전파됩니다. 재시도나 실패 로직을 오류 메시지에 따라 처리하는 것은 호출자의 책임입니다.

### 14.2. 비동기 호출

비동기 호출(호출 유형 `Event` 사용)에서는 호출자가 이벤트를 Lambda로 보내고 함수 실행이 완료되기를 기다리지 않습니다. 대신 Lambda는 즉시 이벤트가 수신되어 처리를 위해 큐에 들어갔음을 나타내는 응답을 반환합니다.

![lambda-async](@site/docs/Compute/_assets/lambda-async.png)

**동작 방식:**
- 이벤트는 내부 큐에 놓입니다.
- 그런 다음 AWS Lambda는 그 이벤트를 독립적으로 처리합니다.
- 호출자는 즉시 HTTP 202(Accepted) 상태를 받습니다.
- 함수가 실패하면 AWS Lambda는 (지수 백오프와 함께) 자동으로 처리를 재시도하며, 선택적으로 실패한 이벤트를 데드 레터 큐(DLQ)로 보내거나 Lambda Destinations를 사용해 성공·실패 결과를 처리할 수 있습니다.

**사용 사례:**
- **이벤트 기반 워크로드:** 즉각적인 응답이 필요하지 않은 파일 처리, 알림, 데이터 변환 같은 애플리케이션.
- **배치 처리:** 호출자를 처리 지연이나 실패로부터 분리하고 싶을 때.

**오류 처리:**
* 오류는 Lambda의 재시도 메커니즘에 의해 내부적으로 처리됩니다. 함수가 반복적으로 실패하면 이벤트를 DLQ로 보낼 수 있어, 나중에 문제를 분석하고 해결할 수 있습니다. 비동기 모델은 처리 결과를 호출자에게 즉시 반환할 필요가 없을 때 이상적입니다.

#### Lambda Destinations

Lambda Destinations를 사용하면 비동기 호출의 결과(성공이든 실패든)를 어디로 보낼지 지정할 수 있습니다. 함수를 비동기 호출용으로 구성할 때 두 개의 별도 대상을 설정할 수 있습니다.

![lambda-destinations](@site/docs/Compute/_assets/lambda-destinations.png)

- **성공 시:**
    성공적인 응답(또는 그에 대한 메타데이터)을 SNS 토픽, SQS 큐, Lambda 함수, EventBridge 버스 같은 대상으로 보낼 수 있습니다. 이를 통해 함수가 성공적으로 완료되면 후속 처리, 알림, 추가 작업이 가능해집니다.

- **실패 시:**
    마찬가지로 함수가 이벤트 처리에 실패하면(자동 재시도가 있다면 그 후에) 분석, 경고, 복구 처리를 위해 실패 세부 정보를 다른 대상(또는 동일한 대상)으로 보낼 수 있습니다. 이 메커니즘은 보완 작업이나 오류 처리 워크플로를 트리거하는 데도 사용할 수 있습니다.

## 15. Lambda 함수 상태

Lambda 함수에는 배포와 업데이트 상태를 반영하는 내부 상태가 있습니다. 이 상태들은 함수가 요청을 처리할 준비가 되었는지, 아니면 주의가 필요한 문제가 있는지 이해하는 데 도움이 됩니다. Lambda의 런타임 환경(컨테이너)도 생명주기 단계(콜드 스타트, 웜 스타트, 유휴, 종료)를 갖지만, 여기서는 함수의 구성 상태에 초점을 맞춥니다.

### 15.1. Pending

Lambda 함수를 만들거나 업데이트하면 처음에는 _Pending_ 상태에 들어갑니다. 이 상태는 AWS Lambda가 실행 환경을 프로비저닝하고 코드와 구성 변경을 적용하는 과정에 있음을 나타냅니다.

- **의미:**
    - 함수는 아직 호출할 수 없습니다.
    - 이 기간 동안 호출을 시도하면 함수가 활성 상태로 전환될 때까지 큐에 쌓이거나 오류가 발생합니다.
    - 초기화가 완료되면(성공한 경우) 상태는 자동으로 Active로 전환됩니다.
### 15.2. Active

_Active_ 상태의 함수는 완전히 배포되어 호출을 처리할 준비가 되어 있습니다. 이는 Lambda 함수의 정상적인 운영 상태입니다.

- **의미:**
    - 함수가 즉시 이벤트를 받고 처리할 수 있습니다.
    - 첫 호출(콜드 스타트) 동안 수행된 전역 초기화가 이미 완료되어, 이후 호출의 지연 시간을 줄이는 데 도움이 됩니다.
    - 대부분의 프로덕션 호출은 함수가 이 상태에 있을 때 발생합니다.
### 15.3. Failed

배포 중이나 함수의 구성·코드를 업데이트하는 중에 오류가 발생하면 함수는 _Failed_ 상태에 들어갑니다.

- **의미:**
    - 오류가 해결되기 전까지 함수를 호출할 수 없습니다.
    - AWS Lambda는 실패 원인을 파악하는 데 도움이 되는 추가 진단 필드(`StateReason`, `StateReasonCode` 등)를 제공합니다.
    - 개발자는 근본적인 문제(예: 문법 오류, 잘못된 구성, 리소스 권한 문제)를 해결하고 함수를 다시 배포해야 합니다.

## 16. 재귀 루프 감지

함수를 호출하는 것과 동일한 서비스나 리소스로 출력하도록 Lambda 함수를 구성하면 무한 재귀 루프가 만들어질 수 있습니다. 예를 들어 Lambda 함수가 Amazon Simple Queue Service(Amazon SQS) 큐에 메시지를 쓰고, 그 메시지가 같은 함수를 다시 호출할 수 있습니다. 이 호출은 함수가 큐에 다른 메시지를 쓰게 하고, 이는 다시 함수를 호출합니다.

의도치 않은 재귀 루프는 AWS 계정에 예상치 못한 요금이 청구되는 결과를 낳을 수 있습니다. 루프는 또한 Lambda가 확장되어 계정에서 사용 가능한 모든 동시성을 소진하게 할 수 있습니다. 의도치 않은 루프의 영향을 줄이기 위해 Lambda는 특정 유형의 재귀 루프를 발생 직후 감지합니다. 기본적으로 Lambda가 재귀 루프를 감지하면 함수 호출을 중단하고 알립니다. 설계상 재귀 패턴을 의도적으로 사용한다면, 함수의 기본 구성을 변경해 재귀적으로 호출되도록 허용할 수 있습니다.

Lambda는 현재 함수들 사이, Amazon SQS, Amazon S3, Amazon SNS 사이의 재귀 루프를 감지합니다. 다음 다이어그램은 Lambda가 감지할 수 있는 루프의 몇 가지 예를 보여줍니다.

![lambda-recursion](@site/docs/Compute/_assets/lambda-recursion.png)

Amazon DynamoDB 같은 다른 AWS 서비스가 루프의 일부를 형성하는 경우, Lambda는 현재 이를 감지하고 중단할 수 없습니다.

## 17. 함수 URL

함수 URL은 Lambda 함수를 위한 전용 HTTP(S) 엔드포인트입니다. Lambda 콘솔이나 Lambda API를 통해 함수 URL을 만들고 구성할 수 있습니다.

함수 URL을 만들면 Lambda는 자동으로 고유한 URL 엔드포인트를 생성합니다. 함수 URL을 만들면 그 URL 엔드포인트는 절대 바뀌지 않습니다. 함수 URL 엔드포인트는 다음과 같은 형식을 가집니다.

```html
https://<url-id>.lambda-url.<region>.on.aws
```

함수 URL은 듀얼 스택을 지원해 IPv4와 IPv6를 모두 사용할 수 있습니다. 함수에 함수 URL을 구성한 후에는 웹 브라우저, curl, Postman, 또는 다른 HTTP 클라이언트를 통해 HTTP(S) 엔드포인트로 함수를 호출할 수 있습니다.

## 18. Lambda 함수 확장

**동시성**은 AWS Lambda 함수가 동시에 처리하고 있는 진행 중인 요청의 수입니다. 각 동시 요청마다 Lambda는 실행 환경의 별도 인스턴스를 프로비저닝합니다. 함수가 더 많은 요청을 받으면 Lambda는 계정의 동시성 한도에 도달할 때까지 실행 환경 수의 확장을 자동으로 처리합니다. 기본적으로 Lambda는 AWS 리전 안의 모든 함수에 걸쳐 총 1,000개의 동시 실행이라는 동시성 한도를 계정에 제공합니다. 특정 계정 요구를 지원하기 위해 할당량 증가를 요청하고, 중요한 함수가 스로틀링을 겪지 않도록 함수 수준의 동시성 제어를 구성할 수 있습니다.

함수가 더 많은 동시 요청을 받으면 Lambda는 이에 대응해 실행 환경 인스턴스 수를 확장합니다. 다음 애니메이션은 시간에 따른 동시 요청 수를 보여줍니다.

![lambda-concurrency](@site/docs/Compute/_assets/lambda-concurrency.png)
예를 들어 시각 `t1`에는 세 개의 동시 요청을 처리하는 세 개의 활성 환경이 있습니다. 이 시뮬레이션에서 동시 요청의 최댓값은 시각 `t4`에 발생하며, 이때 여섯 개의 활성 환경이 여섯 개의 동시 요청을 처리합니다.

### 18.1. 예약된 동시성과 프로비저닝된 동시성

기본적으로 계정은 리전 안의 모든 함수에 걸쳐 1,000개의 동시 실행이라는 동시성 한도를 갖습니다. 함수들은 이 1,000개의 동시성 풀을 온디맨드 방식으로 공유합니다. 사용 가능한 동시성이 소진되면 함수는 스로틀링을 겪습니다(즉 요청을 거부하기 시작합니다).

일부 함수는 다른 함수보다 더 중요할 수 있습니다. 결과적으로 중요한 함수가 필요한 동시성을 확실히 받을 수 있도록 동시성 설정을 구성하고 싶을 수 있습니다. 사용할 수 있는 두 가지 유형의 동시성 제어가 있습니다. 예약된 동시성과 프로비저닝된 동시성입니다.

**1. 예약된 동시성:**

함수를 위해 언제든 일정량의 동시성을 확보하고 싶다면 예약된 동시성을 사용하세요.

예약된 동시성은 함수에 할당하고 싶은 동시 인스턴스의 최대 수입니다. 함수에 예약된 동시성을 전용으로 지정하면 다른 함수는 그 동시성을 사용할 수 없습니다. 즉 예약된 동시성을 설정하면 다른 함수가 사용할 수 있는 동시성 풀에 영향을 줄 수 있습니다. 예약된 동시성이 없는 함수는 나머지 예약되지 않은 동시성 풀을 공유합니다.

예약된 동시성을 더 잘 이해하기 위해 다음 다이어그램을 살펴보세요.

![lambda-reserved](@site/docs/Compute/_assets/lambda-reserved.png)
이 다이어그램에서, 이 리전의 모든 함수에 대한 계정 동시성 한도는 기본 한도인 1,000입니다. `function-blue`와 `function-orange`라는 두 개의 중요한 함수가 있고, 이들이 일상적으로 높은 호출량을 받는다고 가정해 봅시다. `function-blue`에는 400 단위의 예약된 동시성을, `function-orange`에는 400 단위의 예약된 동시성을 부여하기로 결정합니다. 이 예에서는 계정의 다른 모든 함수가 나머지 200 단위의 예약되지 않은 동시성을 공유해야 합니다.

**2. 프로비저닝된 동시성:**

예약된 동시성은 Lambda 함수를 위해 예약된 실행 환경의 최대 수를 정의하는 데 사용합니다. 다만 이 환경들 중 어느 것도 미리 초기화되어 있지 않습니다. 결과적으로 함수 호출은 더 오래 걸릴 수 있는데, Lambda가 함수를 호출하기 위해 사용하기 전에 새 환경을 먼저 초기화해야 하기 때문입니다. Lambda가 호출을 수행하기 위해 새 환경을 초기화해야 할 때 이를 콜드 스타트라고 합니다. 콜드 스타트를 완화하려면 프로비저닝된 동시성을 사용할 수 있습니다.

프로비저닝된 동시성은 함수에 할당하고 싶은, 미리 초기화된 실행 환경의 수입니다. 함수에 프로비저닝된 동시성을 설정하면 Lambda는 그 수만큼의 실행 환경을 초기화해 함수 요청에 즉시 응답할 준비를 갖춥니다.

## 19. Lambda SnapStart

Lambda SnapStart는 함수 코드를 변경하지 않고도 1초 미만의 시작 성능을 제공할 수 있습니다. SnapStart는 리소스를 프로비저닝하거나 복잡한 성능 최적화를 구현하지 않고도 매우 응답성 있고 확장 가능한 애플리케이션을 구축하기 쉽게 만들어 줍니다.

시작 지연(흔히 콜드 스타트 시간이라고 불림)에 가장 크게 기여하는 요소는 Lambda가 함수를 초기화하는 데 걸리는 시간으로, 여기에는 함수의 코드 로드, 런타임 시작, 함수 코드 초기화가 포함됩니다. SnapStart를 사용하면 Lambda는 함수 버전을 게시할 때 함수를 초기화합니다. Lambda는 초기화된 [실행 환경](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)의 메모리와 디스크 상태에 대한 [Firecracker microVM](https://aws.amazon.com/blogs/opensource/firecracker-open-source-secure-fast-microvm-serverless/) 스냅샷을 찍고, 스냅샷을 암호화하고, 가져오기 지연 시간을 최적화하도록 지능적으로 캐시합니다.

복원력을 보장하기 위해 Lambda는 각 스냅샷의 여러 사본을 유지합니다. Lambda는 스냅샷과 그 사본들에 최신 런타임과 보안 업데이트를 자동으로 패치합니다. 함수 버전을 처음 호출할 때, 그리고 호출이 확장될 때, Lambda는 처음부터 초기화하는 대신 캐시된 스냅샷에서 새 실행 환경을 재개해 시작 지연 시간을 개선합니다.

Lambda SnapStart는 모듈 의존성이나 프레임워크 로드 같은 일회성 초기화 코드로 인한 지연 시간 변동성을 해결하도록 설계되었습니다. 이런 작업은 최초 호출 중에 완료까지 몇 초가 걸릴 수 있습니다. 최적의 시나리오에서 SnapStart를 사용하면 이 지연 시간을 몇 초에서 1초 미만으로 줄일 수 있습니다.

## 20. Lambda 권한

AWS Identity and Access Management(IAM)를 사용해 AWS Lambda의 권한을 관리할 수 있습니다. Lambda 함수로 작업할 때 고려해야 할 권한에는 크게 두 가지 범주가 있습니다.

- Lambda 함수가 API 작업을 수행하고 다른 AWS 리소스에 접근하는 데 필요한 권한
- 다른 AWS 사용자와 엔티티가 Lambda 함수에 접근하는 데 필요한 권한

Lambda 함수에 필요한 권한은 실행 역할이라는 특수한 IAM 역할에서 정의합니다. 이 역할에는 함수가 다른 AWS 리소스에 접근하고 이벤트 소스에서 읽는 데 필요한 모든 권한을 정의하는 정책을 연결할 수 있습니다. 모든 Lambda 함수는 실행 역할을 가져야 합니다. 최소한 실행 역할은 Amazon CloudWatch에 대한 접근 권한을 가져야 하는데, Lambda 함수가 기본적으로 CloudWatch Logs에 로그를 기록하기 때문입니다. 이 요구사항을 충족하기 위해 실행 역할에 [`AWSLambdaBasicExecutionRole` 관리형 정책](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AWSLambdaBasicExecutionRole.html)을 연결할 수 있습니다.

## 21. Lambda 레이어

Lambda 레이어는 보조 코드나 데이터를 담은 .zip 파일 아카이브입니다. 레이어에는 일반적으로 라이브러리 의존성, 커스텀 런타임, 또는 구성 파일이 포함됩니다.

레이어를 사용하는 데는 여러 이유가 있습니다.

- **배포 패키지 크기를 줄이기 위해.** 모든 함수 의존성을 함수 코드와 함께 배포 패키지에 포함하는 대신, 레이어에 넣으세요. 이는 배포 패키지를 작고 정돈된 상태로 유지합니다.
- **핵심 함수 로직을 의존성에서 분리하기 위해.** 레이어를 사용하면 함수 코드와 독립적으로 함수 의존성을 업데이트할 수 있고, 그 반대도 가능합니다. 이는 관심사의 분리를 촉진하고 함수 로직에 집중할 수 있게 돕습니다.
- **여러 함수에서 의존성을 공유하기 위해.** 레이어를 만든 후에는 계정 내 원하는 수의 함수에 적용할 수 있습니다. 레이어가 없다면 각 개별 배포 패키지에 동일한 의존성을 포함해야 합니다.
- **Lambda 콘솔 코드 편집기를 사용하기 위해.** 코드 편집기는 소규모 함수 코드 업데이트를 빠르게 테스트하는 데 유용한 도구입니다. 다만 배포 패키지 크기가 너무 크면 편집기를 사용할 수 없습니다. 레이어를 사용하면 패키지 크기가 줄어들어 코드 편집기 사용이 가능해질 수 있습니다.

다음 다이어그램은 의존성을 공유하는 두 함수 사이의 상위 수준 아키텍처 차이를 보여줍니다. 하나는 Lambda 레이어를 사용하고 다른 하나는 사용하지 않습니다.

![lambda-layers](@site/docs/Compute/_assets/lambda-layers.png)

함수에 레이어를 추가하면 Lambda는 함수의 실행 환경 안에 있는 `/opt` 디렉터리에 레이어 콘텐츠를 압축 해제합니다. 네이티브로 지원되는 모든 Lambda 런타임은 `/opt` 디렉터리 안의 특정 디렉터리에 대한 경로를 포함합니다. 이를 통해 함수가 레이어 콘텐츠에 접근할 수 있습니다.

함수당 최대 5개의 레이어를 포함할 수 있습니다. 또한 레이어는 [.zip 파일 아카이브로 배포된](https://docs.aws.amazon.com/lambda/latest/dg/configuration-function-zip.html) Lambda 함수에서만 사용할 수 있습니다. [컨테이너 이미지로 정의된](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html) 함수의 경우, 컨테이너 이미지를 만들 때 선호하는 런타임과 모든 코드 의존성을 패키징하세요.

## 22. Lambda 확장(Extensions)

Lambda 확장은 AWS Lambda 프로그래밍 모델에 추가된 기능으로, 함수 코드를 수정하지 않고도 모니터링, 보안, 로깅, 거버넌스 같은 추가 기능을 함수의 실행 환경에 직접 통합할 수 있게 합니다.

![lambda-extensions](@site/docs/Compute/_assets/lambda-extensions.png)

확장은 Lambda 함수와 함께 추가 프로세스를 실행해 일반적으로 비즈니스 로직과 직교하는 작업을 수행할 수 있게 합니다. 흔한 사용 사례는 다음과 같습니다.

- **모니터링과 관측성:** 커스텀 지표나 로그를 수집하고, 서드파티 모니터링 솔루션과 통합합니다.
- **보안:** 위협을 모니터링하거나 정책을 강제하는 보안 에이전트를 실행합니다.
- **거버넌스:** 구성을 관리하거나 추가적인 런타임 텔레메트리를 수집합니다.

확장은 함수와 동일한 실행 환경 안에서 별도의 프로세스로 실행됩니다. 생명주기 이벤트(초기화, 호출, 종료 등)를 구독할 수 있어 다음을 할 수 있습니다.

- 함수가 실행되기 전에 리소스를 초기화합니다.
- 호출 중에 데이터를 처리하거나 환경을 수정합니다.
- 함수 실행이 완료된 후 정리나 로깅을 수행합니다.

확장은 함수 코드와 함께 실행됩니다. 이는 다음을 의미합니다.

- 동일한 컨테이너를 공유하며 공유 라이브러리와 파일이 있는 `/opt` 디렉터리에 접근할 수 있습니다.
- 독립적으로 동작하지만 필요하다면 로그를 읽거나 성능 지표를 모니터링하는 등의 방법으로 함수와 통신할 수 있습니다.
- Lambda 함수 구성을 통해 등록되며, 일반적으로 별도의 실행 파일로 작성됩니다.

자체 확장을 만들거나 AWS 파트너가 제공하는 확장을 사용할 수 있습니다. 개발이 완료되면 확장은 함수 배포와 함께 패키징되거나(또는 별도로 참조되어) AWS Lambda가 실행 환경의 일부로 관리합니다.

## 23. VPC 안의 Lambda

Lambda 함수를 VPC 안에서 실행하도록 구성하면, 실질적으로 함수의 실행 환경을 프라이빗 네트워크 안에 배치하는 것입니다. 이 통합을 통해 함수는 Lambda의 서버리스, 자동 확장, 사용량 기반 요금 모델의 이점을 그대로 누리면서도 퍼블릭으로 접근할 수 없는 다른 VPC 리소스와 통신할 수 있습니다.

![lambda-in-vpc](@site/docs/Compute/_assets/lambda-in-vpc.png)
### 23.1. 동작 방식

#### 1. **Lambda의 VPC 구성**

- **서브넷과 보안 그룹:**
    함수 구성에서 하나 이상의 VPC 서브넷과 보안 그룹을 지정합니다. Lambda는 이 설정을 사용해 VPC 안에 Elastic Network Interface(ENI)를 만듭니다. 이 ENI들은 AWS가 자동으로 관리하며, Lambda 실행 환경과 VPC 리소스 사이의 다리 역할을 합니다.

- **ENI 프로비저닝:**
    VPC 접근을 위해 구성된 Lambda 함수가 호출되면 AWS는 함수의 실행 환경에 ENI를 만들고 연결합니다. 이 ENI들은 지정한 서브넷에서 프라이빗 IP 주소를 받아, 함수가 VPC 내 다른 리소스와 통신할 수 있도록 보장합니다.

#### 2. **네트워킹 고려사항**

- **프라이빗 리소스 접근:**
    VPC 안에 들어가면 Lambda 함수는 프라이빗 IP 주소 지정 체계를 사용해 그 VPC 내 사용 가능한 모든 리소스(RDS 데이터베이스, EC2 인스턴스, ElastiCache 클러스터 등)에 접근할 수 있습니다. 이는 백엔드 데이터베이스나 내부 API와의 안전한 통신이 필요한 애플리케이션에 이상적입니다.

- **인터넷 접근:**
    기본적으로 VPC 안에서 실행되는 Lambda 함수는 인터넷에 직접 접근할 수 없습니다. 인터넷 연결이 필요하다면(예: 외부 API 호출) 퍼블릭 서브넷에 NAT 게이트웨이나 NAT 인스턴스를 구성하고 프라이빗 서브넷의 라우팅 테이블을 그에 맞게 조정해야 합니다.

#### 3. **성능과 콜드 스타트**

- **콜드 스타트 영향:**
    콜드 스타트 중 ENI를 프로비저닝하면 추가 지연 시간이 발생할 수 있습니다. VPC에서 실행되는 Lambda 함수를 위해 새 컨테이너가 시작되면 AWS는 ENI를 할당해야 하며, 이는 초기 호출을 느리게 할 수 있습니다. 시간이 지나 컨테이너가 재사용되면(웜 스타트) 이 오버헤드는 최소화됩니다.

- **콜드 스타트 최적화:**
    프로비저닝된 동시성처럼 지정된 수의 실행 환경을 미리 초기화 상태로 유지하는 전략을 사용하거나, 초기화 중 의존성을 최소화하도록 함수를 설계함으로써 콜드 스타트 영향을 완화할 수 있습니다.

### 23.2. 고려사항과 트레이드오프

- **복잡성 vs. 보안:**
    VPC에서 Lambda 함수를 실행하면 리소스를 격리해 보안 계층을 추가하지만, 구성에 복잡성이 추가되고(예: 인터넷 접근을 위한 NAT 게이트웨이 설정) 콜드 스타트 지연 시간이 늘어날 수 있습니다.

- **리소스 제한:**
    VPC와 계정의 ENI 제한을 알아 두세요. 고동시성 시나리오에서 많은 Lambda 함수가 VPC에서 실행되고 있다면, 사용 가능한 ENI의 한도에 도달해 성능에 영향을 줄 수 있습니다.

- **비용 영향:**
    VPC에서 Lambda 함수를 실행해도 추가적인 Lambda 요금은 발생하지 않지만, NAT 게이트웨이 사용과 ENI 사용 증가는 더 높은 네트워킹 비용을 초래할 수 있습니다.

## 24. Lambda 함수 모니터링

### 24.1. CloudWatch 지표

AWS Lambda는 다음과 같은 다양한 지표를 Amazon CloudWatch에 자동으로 게시합니다.

- **Invocations:** 함수가 호출된 횟수.
- **Duration:** 각 함수 실행이 지속된 시간.
- **Errors:** 실패한 호출 수(타임아웃과 예외 포함).
- **Throttles:** 동시성 한도로 인해 스로틀링된 호출 시도 수.
- **IteratorAge(스트림 기반 트리거의 경우):** 스트림 이벤트 처리 지연을 측정합니다.

이 지표들은 함수의 성능과 사용 패턴을 이해하는 데 도움이 됩니다. 지표가 미리 정의한 임계값을 초과할 때 알리도록 CloudWatch 경보를 설정할 수 있어 문제를 선제적으로 감지할 수 있습니다.
### 24.2. CloudWatch Logs와 Logs Insights

모든 Lambda 호출은 자동으로 CloudWatch Logs로 전송되는 로그를 출력할 수 있습니다. 이 로그 안에서 다음을 할 수 있습니다.

- **진단 메시지 기록:** 코드에 로깅 문을 사용해 실행 흐름을 추적하거나, 변수 값을 캡처하거나, 오류를 보고합니다.
- **로그 데이터 분석:** CloudWatch Logs Insights는 로그 데이터를 검색하고 분석할 수 있는 강력한 질의 엔진을 제공합니다. 트렌드를 파악하고, 오류 메시지를 짚어내고, 특정 호출 세부 사항까지 파고들 수 있습니다.

### 24.3. AWS Lambda Insights

Lambda Insights는 Lambda 함수를 위한 추가적인 모니터링 기능을 제공하는 CloudWatch의 기능입니다. 다음을 제공합니다.

- **향상된 지표와 대시보드:** CPU와 메모리 사용량, 함수 실행 시간 등에 대한 상세한 가시성.
- **이상 감지:** 비정상적인 동작이나 성능 문제를 자동으로 강조합니다.
- **통합된 문제 해결:** 함수 성능을 다른 AWS 서비스 지표와 연관 지을 수 있게 돕습니다.

### 24.4. 분산 추적을 위한 AWS X-Ray

AWS X-Ray는 Lambda와 통합되어 여러 서비스에 걸친 요청의 종단 간 추적을 제공합니다. X-Ray는 다음을 할 수 있습니다.

- **실행 경로 추적:** 분산 시스템의 다양한 구성 요소를 거쳐 요청이 어떻게 흐르는지 시각화합니다.
- **병목 지점 식별:** 함수나 그 하위 호출의 지연 시간 문제나 오류를 짚어냅니다.
- **추적 주석 추가:** 주석과 메타데이터를 사용해 더 상세한 분석을 위해 추적 데이터를 보강합니다.

### 24.5. AWS CloudTrail

CloudTrail은 Lambda 함수 호출과 구성 변경을 포함해 AWS 계정에서 이루어진 API 호출을 기록합니다. 이는 다음에 유용할 수 있습니다.

- **보안 감사:** 인가되지 않은 변경이나 호출을 감지합니다.
- **운영 가시성:** 누가(또는 무엇이) Lambda 함수를 호출하고 있는지 이해합니다.

## 25. Lambda 함수 문제 해결

### 25.1. 오류와 실패 분석

- **CloudWatch Logs 검토:** 함수가 실패하면 오류 메시지와 스택 트레이스가 CloudWatch Logs에 기록됩니다. 이 로그를 사용해 오류가 발생한 이유를 이해하세요.
- **CloudWatch 지표 확인:** 오류와 스로틀 지표를 모니터링해 프로덕션의 문제를 빠르게 식별하세요.
- **Lambda Destinations와 데드 레터 큐(DLQ) 사용:** 비동기 호출의 경우, 반복적으로 실패하는 이벤트를 캡처하도록 DLQ를 구성하세요. Lambda Destinations는 성공·실패 결과를 다른 AWS 서비스로 라우팅해 추가 처리나 경고를 할 수 있게 합니다.

### 25.2. 성능 문제 진단

- **콜드 스타트:** 콜드 스타트로 인한 지연 시간 급증을 조사하세요. 프로비저닝된 동시성이나 Lambda SnapStart 같은 기법이 이를 완화하는 데 도움이 될 수 있습니다.
- **리소스 구성:** 메모리 크기, 타임아웃, 동시성 설정이 적절히 구성되어 있는지 확인하세요. 메모리가 부족하면 실행 시간이 길어질 수 있고, 타임아웃 설정이 낮으면 함수가 조기에 종료될 수 있습니다.
- **X-Ray 활용:** AWS X-Ray를 사용해 실행 흐름을 추적하고 시각화하세요. X-Ray는 함수의 어느 부분(또는 다른 서비스와의 통합)이 지연이나 오류에 기여하고 있는지 식별하는 데 도움이 됩니다.

### 25.3. 문제 해결을 위한 모범 사례

- **구조화된 로깅:** 특정 오류 패턴을 파싱하고 검색하기 쉽게 하기 위해 구조화된(JSON) 로그를 사용하세요.
- **상관관계 ID:** 여러 서비스에 걸친 요청의 경로를 따라가기 위해 로그와 추적에 고유한 트랜잭션이나 상관관계 ID를 삽입하세요.
- **분석 자동화:** CloudWatch와 X-Ray와 통합되는 자동화 도구나 서드파티 모니터링 솔루션을 사용해 더 깊은 통찰과 더 빠른 문제 감지를 고려하세요.
- **정기적인 테스트와 상태 확인:** 트래픽을 시뮬레이션하고 함수가 예상대로 동작하는지 확인하기 위해 정기적인 테스트와 모니터링 스크립트를 배포하세요.

## 26. 결론

AWS Lambda는 서버 관리를 없애면서 자동 확장, 유연한 배포 옵션(ZIP 아카이브나 컨테이너 이미지), 다른 AWS 서비스와의 견고한 통합을 제공함으로써 애플리케이션 개발을 단순화하는 강력한 서버리스 컴퓨팅 서비스입니다. 이벤트 기반 모델과 프로비저닝된 동시성, Lambda 레이어, 확장, VPC 통합 같은 기능에 대한 내장 지원은 현대적이고 확장 가능한 마이크로서비스 아키텍처를 구축하는 데 이상적입니다. Lambda의 동작 방식과 모범 사례에 대한 더 자세한 내용은 [AWS Lambda 개발자 가이드](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html)를 참고하고 [AWS Lambda 보안 개요 백서](https://docs.aws.amazon.com/whitepapers/latest/security-overview-aws-lambda/security-overview-aws-lambda.html)를 살펴보세요.
