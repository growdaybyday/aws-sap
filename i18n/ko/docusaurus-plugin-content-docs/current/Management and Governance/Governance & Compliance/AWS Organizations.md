# AWS Organizations

## 1. 소개

대규모 클라우드 도입은 기업이 IT 운영을 구조화하는 방식을 재편했습니다. 단일 거대한 AWS 계정에 의존하는 대신, 현대 조직은 서로 다른 팀, 프로젝트, 환경을 위해 격리된 계정을 활용하는 멀티 계정 전략을 채택합니다. AWS Organizations는 모든 회원 계정에 걸쳐 중앙화된 관리, 정책 강제, 통합 결제를 가능하게 함으로써 이 접근 방식을 위한 필수적인 프레임워크를 제공합니다.

![aws-org-capability](@site/docs/Management%20and%20Governance/_assets/aws-org-capability.png)

AWS Organizations를 도입함으로써 기업은 다음을 할 수 있습니다.

- **보안 강화:** 한 계정의 침해가 다른 계정에 영향을 미치지 않도록 워크로드를 별도의 계정으로 격리합니다.
- **거버넌스 강화:** 서비스 제어 정책(SCP)과 다른 중앙화된 정책을 통해 규정 준수와 보안 표준을 중앙에서 강제합니다.
- **비용 최적화:** 볼륨 할인을 위해 사용량을 통합하고, 계정 간 예약 용량을 공유하고, 통합 결제를 사용해 지출을 모니터링합니다.
- **운영 간소화:** 계정 프로비저닝과 기준선 구성을 자동화해 신속한 확장과 애자일 배포를 가능하게 합니다.

## 2. 멀티 계정 패러다임

여러 AWS 계정을 사용하는 개념은 격리의 원칙에 뿌리를 두고 있습니다. 워크로드, 팀, 프로젝트를 개별 계정으로 세분화함으로써 조직은 보안 사고의 "폭발 반경"을 제한하고, 잠재적인 잘못된 구성을 최소화하며, 명확한 비용 소유권을 할당할 수 있습니다. 이 격리는 다음에 근본적입니다.

- **보안과 규정 준수:** 한 계정에서 보안 취약점이 악용되면 피해는 그곳에 국한됩니다. 게다가 민감한 워크로드를 분리해 규제 요구 사항을 충족할 수 있습니다.
- **운영 자율성:** 서로 다른 팀은 어느 정도 독립적으로 운영할 수 있습니다 — 자신의 전용 환경에만 영향을 미치는 정책과 구성을 수정합니다.
- **비용 관리:** 각 계정이 하나의 팀이나 프로젝트에 연결되면 비용 추적과 귀속이 훨씬 더 간단해집니다.

AWS Organizations는 이 별도의 계정들을 하나의 중앙화된 관리 우산 아래 통합하면서도 그 자율성을 계속 보존합니다. 멀티 계정 접근 방식은 널리 모범 사례로 간주되며 운영 우수성, 보안, 신뢰성, 비용 최적화 같은 범주에서 AWS Well-Architected Framework의 기둥입니다.

## 3. 핵심 개념과 구조

AWS Organizations의 핵심에는 계정을 계층적 트리로 조직화하는 개념이 있습니다. 이 구조는 몇 가지 기본 개념 위에 구축됩니다.

### 3.1. 조직과 그 루트

AWS Organization은 모든 AWS 계정을 위한 논리적 컨테이너입니다. 계층 구조의 최상단에는 **루트**가 있습니다. 루트는 전체 조직을 나타내며 모든 계정을 담고 있는 기본 컨테이너입니다. 일상적인 작업을 위해 루트와 직접 상호작용하지는 않을 수 있지만, 모든 정책과 설정이 궁극적으로 전파되는 단일 지점을 제공하기 때문에 매우 중요합니다.

### 3.2. 관리 계정 vs. 회원 계정

조직 내에서 계정은 두 가지 별개의 유형으로 나뉩니다.

- **관리 계정:** 이전에는 "마스터 계정"으로 알려졌던 이 계정은 조직을 생성하고 관리하는 계정입니다. 결제와 전체 정책 관리에 대한 책임을 집니다. 그 특권은 새 계정을 생성하고, 기존 계정을 초대하고, 조직 통제를 강제할 수 있게 합니다.
- **회원 계정:** 이 계정들은 실제 워크로드를 담고 있습니다 — 프로덕션 애플리케이션을 실행하든, 테스트 환경이든, 실험적인 샌드박스든 말입니다. 회원 계정은 기본적으로 서로 격리되어 있습니다. 명시적인 권한이 설정된 경우에만 상호작용할 수 있습니다.

![aws-org-example](@site/docs/Management%20and%20Governance/_assets/aws-org-example.png)
모범 사례는 관리 계정을 오로지 관리 기능만을 위해 예약하고 그곳에 워크로드를 배포하는 것을 피하는 것입니다. 이 분리는 관리 계정이 안전하게 유지되고 실수로 인한 변경이나 결제 혼동의 위험을 최소화하도록 보장합니다.

### 3.3. 조직 단위(OU)

조직 단위, 즉 OU는 조직 내의 하위 컨테이너입니다. 비즈니스 단위, 환경(예: 프로덕션 vs. 개발), 또는 규제 요구 사항 같은 공통 특성으로 계정을 그룹화할 수 있게 합니다. OU는 최대 5단계 깊이까지 중첩될 수 있어, 조직 구조를 유연하게 반영할 수 있습니다. 정책은 어떤 OU 수준에서든 적용할 수 있어 모든 자식 계정이 설정을 상속하도록 합니다. 이 계층적 설계는 관련 계정 전반에 걸쳐 거버넌스 통제를 적용하는 작업을 크게 단순화합니다.

### 3.4. AWS Organizations의 정책

AWS Organizations의 가장 강력한 기능 중 하나는 여러 계정에 걸쳐 정책을 강제하는 능력입니다. 이 정책들은 여러 유형으로 제공됩니다.

- **서비스 제어 정책(SCP):** 이 JSON 정책은 회원 계정에 대한 최대 권한을 설정합니다. 계정 내 개별 IAM 정책과 관계없이 작업을 제한하는 가드레일 역할을 합니다. 예를 들어 SCP는 특정 고위험 서비스의 사용을 방지하거나 승인된 AWS 리전으로 리소스 생성을 제한할 수 있습니다.
- **태그 정책:** 이는 계정 전반에 걸쳐 리소스가 태깅되는 방식을 표준화하는 데 도움을 줍니다. 일관된 태깅을 강제하는 것은 비용 할당, 리소스 관리, 규정 준수에 매우 중요합니다.

:::tip

태그 정책은 거버넌스와 보고만 제공합니다; 실제로 규정을 준수하지 않는 리소스가 생성되는 것을 차단하지는 않습니다. 태그의 존재를 강제하려면 SCP를 사용해야 합니다.

:::

- **백업 정책:** AWS Backup을 Organizations와 함께 사용하는 경우 모든 계정이나 선택한 OU에 자동으로 적용되는 백업 일정과 보존 규칙을 중앙에서 정의할 수 있습니다.
- **AI 서비스 옵트아웃 정책:** 개인정보 보호나 규제 우려가 있는 조직을 위해, 이 유형의 정책은 콘텐츠가 AWS AI 서비스 개선에 사용되는 것을 거부하는 데 사용할 수 있습니다.

이 정책들을 신중하게 설계하고 적용함으로써 솔루션 아키텍트는 조직 내 모든 계정에 걸쳐 강력한 보안 태세와 거버넌스 표준을 강제할 수 있습니다.

## 4. 기능 세트: 통합 결제 vs. 전체 기능 모드

AWS Organization을 생성할 때는 **통합 결제**나 **전체 기능** 중 하나의 기능 세트를 선택해야 합니다. 두 옵션 모두 집계된 결제를 가능하게 하지만, 관리와 거버넌스 기능 측면에서 크게 다릅니다.

### 4.1. 통합 결제 모드

통합 결제 모드에서 조직은 주로 결제 집계에 초점을 맞춥니다. 모든 회원 계정은 결제 목적으로 연결되어, 사용량을 통합하고 볼륨 할인과 공유된 예약 인스턴스 할인을 활용할 수 있게 합니다. 다만 이 모드는 AWS Organizations의 고급 보안 및 관리 기능을 제공하지 않습니다. 추가 기능 없이는 SCP를 강제하거나, 중앙화된 접근 관리를 위해 AWS Single Sign-On을 사용하거나, 여러 AWS 보안 서비스와 자동으로 통합할 수 없습니다.

### 4.2. 전체 기능 모드

전체 기능 모드는 AWS Organizations의 전체 잠재력을 잠금 해제합니다. 통합 결제 외에도 다음을 활용할 수 있습니다.

- **조직 정책:** SCP, 태그 정책, 백업 정책을 계정이나 OU에 연결합니다.
- **계정 간 통합:** CloudTrail, Config, IAM Identity Center(이전 AWS SSO), AWS Resource Access Manager(RAM) 같은 AWS 서비스와 매끄럽게 통합합니다.
- **위임된 관리:** 특정 서비스에 대해 위임된 관리자 계정을 지정해, 선택된 팀이 중앙화된 지침을 계속 따르면서도 자신의 계정 내 리소스를 관리할 수 있게 합니다.

전체 기능 모드는 강화된 거버넌스와 보안을 지원하기 때문에 거의 모든 엔터프라이즈 시나리오에 강력하게 권장됩니다. 오늘날의 AWS 콘솔이나 CLI에서는 전체 기능 모드가 기본 옵션입니다. 처음에 통합 결제 모드로 조직을 설정했다면, 모든 회원 계정과 핸드셰이크 프로세스를 수행함으로써 나중에 전체 기능으로 업그레이드할 수 있습니다.

## 5. AWS 계정 마이그레이션과 병합

조직이 발전함에 따라 한 조직에서 다른 조직으로 AWS 계정을 마이그레이션하거나 독립형 계정을 기존 AWS Organization으로 가져와야 할 필요성을 발견하는 것이 일반적입니다. 이러한 마이그레이션은 인수합병(M&A) 중, 회사가 유기적으로 성장해 개별 프로젝트를 위해 새 계정을 만들 때, 또는 회사가 레거시 계정에 대한 중앙화된 거버넌스를 구현하기로 결정할 때 발생할 수 있습니다.

### 5.1. 마이그레이션 전 고려 사항

계정을 마이그레이션하기 전에 몇 가지 핵심 전제 조건을 충족해야 합니다.

- **계정 연령:** 조직 내에서 생성된 새 계정은 마이그레이션되기 전에 최소 7일이 지나야 합니다. 이 규칙은 계정을 이동하기 전에 안정화되도록 보장하기 위한 것입니다.
- **권한:** 필요한 IAM 권한이 소스와 대상 조직 모두에 존재하는지 확인하세요. 소스 계정에서는 계정을 현재 조직에서 제거할 권한(예: `organizations:LeaveOrganization`)이 있어야 합니다. 대상 조직에서는 관리 계정이 `organizations:InviteAccountToOrganization` 같은 권한이 필요합니다.
- **IAM 역할과 SSO:** 계정이 조직의 일부인 경우 일반적으로 관리 계정이 접근할 수 있게 하는 특별한 역할(흔히 `OrganizationAccountAccessRole`로 명명됨)이 있습니다. 계정을 마이그레이션하는 경우 이전 조직으로부터의 의도치 않은 계정 간 접근을 방지하기 위해 이 역할을 검토하거나 제거하세요.
- **결제 정보:** 독립형 계정은 유효한 결제 정보가 필요합니다. 계정이 조직을 떠나면 다른 조직에 가입하지 않는 한 자체 신용카드로 직접 청구됩니다.
- **백업과 로깅:** 마이그레이션 전에 통합 결제 보고서나 조직 로그를 내보내세요. 계정이 현재 조직을 떠나면 일부 과거 데이터를 더 이상 사용할 수 없을 수 있습니다.

### 5.2. 마이그레이션 프로세스

마이그레이션 프로세스는 일반적으로 다음 단계를 따릅니다.

1. **소스 조직에서 계정 이탈:** 계정이 현재 조직에서 제거되어 독립형 AWS 계정이 됩니다.
2. **대상 조직으로의 초대:** 대상 조직의 관리 계정이 독립형 계정에 초대를 보냅니다.
3. **핸드셰이크 수락:** 계정 소유자는 AWS Organizations가 제공하는 핸드셰이크 메커니즘을 사용해 초대를 수락합니다.
4. **구성 업데이트:** 계정이 새 조직에 가입하면 이전 조직에 특화되었던 정책, 역할, 설정을 조정합니다.

예를 들어 AWS CLI를 사용하는 경우 다음과 같은 명령으로 계정을 초대할 수 있습니다.

```bash
aws organizations invite-account-to-organization --target Id=<AccountId>,Type=ACCOUNT
```

그런 다음 마이그레이션되는 계정에서 핸드셰이크를 수락합니다.

```bash
aws organizations accept-handshake --handshake-id <HandshakeId>
```

이 과정 전반에서 AWS는 계정의 리소스 — EC2 인스턴스, S3 버킷 등 — 가 계속 정상적으로 작동하도록 보장합니다. 주된 영향은 결제, 계정 간 접근, 정책 강제에 있습니다.

### 5.3. 인수합병(M&A)

M&A 시나리오에서는 두 개의 별도 AWS 환경을 통합하는 것이 단일 계정을 마이그레이션하는 것보다 흔히 더 어렵습니다. 일반적인 전략은 한 조직을 프라이머리(일반적으로 인수하는 회사의 조직)로 선택한 다음 인수된 조직의 계정을 프라이머리로 마이그레이션하는 것입니다. 조율이 필수적입니다.

- **계획과 소통:** 마이그레이션 일정을 잡고 필요한 권한이 준비되어 있는지 확인하기 위해 계정 소유자와 긴밀하게 협력하세요.
- **SCP와 정책 검토:** 대상 조직의 보안과 거버넌스 정책이 마이그레이션되는 계정의 필수 작업을 의도치 않게 차단하지 않는지 확인하세요.
- **테스트 마이그레이션:** 프로덕션 계정을 이동하기 전에 마이그레이션 프로세스를 검증하기 위해 중요하지 않은 계정부터 시작하세요.

마이그레이션을 체계적으로 접근함으로써 기업은 결합된 조직 전반에서 결제, 보안, 관리 관행을 통합하면서도 최소한의 중단으로 AWS 환경을 병합할 수 있습니다.

## 6. 서비스 제어 정책(SCP): 계정을 위한 가드레일

서비스 제어 정책(SCP)은 AWS Organizations가 제공하는 아마도 가장 중요한 도구일 것입니다. SCP는 각 계정에서 수행할 수 있는 작업의 경계를 정의합니다 — 자체적으로 권한을 부여하는 것이 아니라 사용 가능한 최대 권한을 제한합니다. 사실상 SCP는 회원 계정의 IAM 정책이 지나치게 관대하더라도, 명시적으로 허용되지 않은 작업을 SCP가 차단할 것이라는 것을 보장하는 "안전망" 역할을 합니다.

### 6.1. SCP의 작동 방식

AWS Organization이 생성되면 모든 계정은 자동으로 `FullAWSAccess`라는 기본 SCP를 받습니다. 이 정책은 사실상 모든 AWS 작업을 허용합니다. 추가 SCP를 연결하면 기본 권한 위에 제한을 부과하는 것입니다. 기억해야 할 핵심 사항은 다음을 포함합니다.

- **경계 강제:** SCP는 계정 내 모든 사용자와 역할 — 심지어 루트 사용자까지 — 에 적용됩니다. SCP가 특정 작업을 거부하면 IAM 정책이 무엇을 허용하든 관계없이 해당 계정의 어떤 사용자나 역할도 그 작업을 수행할 수 없습니다.
- **비부여 특성:** SCP는 그 자체로 권한을 부여하지 않습니다. SCP가 서비스 작업을 허용하더라도 작업이 성공하려면 계정 내 IAM 정책도 이를 허용해야 합니다.
- **상속:** 계층 구조의 더 높은 수준(루트나 OU 등)에서 연결된 정책은 모든 자식 계정에 자동으로 적용됩니다. 이 상속은 하나의 정책이 한 번에 많은 계정을 거버넌스할 수 있도록 보장합니다.

### 6.2. SCP 사용에 대한 접근 방식

SCP를 설계할 때 두 가지 주요 전략이 있습니다.

#### 6.2.1. 거부 목록(블랙리스트) 전략

이 모델에서는 기본 모두 허용(`FullAWSAccess`)으로 시작한 다음 위험하거나 규정을 준수하지 않는 일련의 작업을 명시적으로 **거부**하는 추가 SCP를 연결합니다. 예를 들어 스토리지 리소스의 암호화를 비활성화하는 능력을 거부하거나 승인되지 않은 리전에서의 작업을 제한하는 SCP를 만들 수 있습니다. 거부 목록의 이점은 명시적으로 거부되지 않는 한 새로운 AWS 서비스가 기본적으로 허용되기 때문에 일반적으로 유지보수가 덜 필요하다는 것입니다.

#### 6.2.2. 허용 목록(화이트리스트) 전략

반대로 허용 목록 접근 방식은 훨씬 더 제한적입니다. 여기서는 기본 모두 허용 정책을 제거하고 특정 작업 집합만 명시적으로 **허용**하는 SCP를 만듭니다. 허용 목록에 없는 모든 것은 암묵적으로 거부됩니다. 이 제로 트러스트 접근 방식은 승인된 작업만 발생하도록 보장하지만, 변경이나 새로운 서비스를 수용하기 위해 지속적인 업데이트가 필요해 혁신을 늦출 수 있습니다.

#### 6.2.3. 하이브리드 접근 방식

많은 조직은 하이브리드 전략을 채택합니다: 대부분의 계정에는 광범위한 거부 목록을 사용하면서 특히 민감한 환경에는 더 제한적인 허용 목록을 적용합니다. 예를 들어 일반적인 워크로드 계정에는 더 관대한 거부 목록을 유지하면서 전문화된 인프라 OU에서는 네트워킹 관련 서비스만 허용할 수 있습니다.

### 6.3. SCP 설계와 테스트

SCP를 설계할 때:

- **중요한 작업 식별:** 오용될 경우 상당한 보안이나 운영상의 피해를 초래할 수 있는 작업(예: IAM 변경, 로깅 서비스 비활성화, 또는 승인되지 않은 리소스 유형 시작)에 초점을 맞추세요.
- **조건 사용:** SCP는 리소스 태그, 리전, 또는 서비스 주체를 기반으로 작업을 제한할 수 있는 조건을 지원합니다. 예를 들어 특정 조건이 충족되지 않는 한 `us-east-1`이나 `eu-west-1` 이외의 리전에서 EC2 인스턴스를 시작하는 것을 거부할 수 있습니다.
- **하위 환경에서 테스트:** 조직 전체에 SCP를 배포하기 전에 중요하지 않은 계정을 포함하는 OU에서 테스트하세요. CloudTrail 로그와 IAM 정책 시뮬레이터를 사용해 SCP가 의도치 않게 필수 작업을 차단하지 않는지 확인하세요.
- **의도 문서화:** 각 SCP가 달성하도록 설계된 것에 대한 명확한 문서를 항상 유지하세요. 이 문서는 감사와 향후 조정을 할 때 매우 유용할 것입니다.

암호화 없이 EC2 인스턴스를 시작하거나 EBS 볼륨을 생성하는 것을 방지하는 간단한 거부 스타일 SCP의 예시입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyUnencryptedVolumes",
      "Effect": "Deny",
      "Action": [
        "ec2:RunInstances",
        "ec2:CreateVolume"
      ],
      "Resource": "*",
      "Condition": {
        "Bool": { "aws:RequestPermanentVolumeEncryption": "false" }
      }
    }
  ]
}
```

이 예시에서 어떤 사용자가 암호화를 활성화하지 않고 인스턴스를 시작하거나 볼륨을 생성하려 시도하면, IAM 정책이 부여한 권한과 관계없이 이 조건이 거부를 트리거합니다.

## 7. 다른 AWS 서비스와의 통합

AWS Organizations는 고립되어 존재하지 않습니다 — 모든 회원 계정에 걸쳐 중앙화된 관리와 거버넌스를 가능하게 하기 위해 많은 다른 AWS 서비스와 깊이 통합됩니다. 다음 절에서는 통합된 관리 경험을 가능하게 하는 핵심 통합을 강조합니다.

### 7.1. AWS Resource Access Manager(RAM)

AWS Resource Access Manager(RAM)는 커스텀 계정 간 IAM 역할 없이도 계정 간 리소스 공유를 촉진합니다. RAM을 사용하면 VPC 서브넷, transit gateway, Route 53 resolver 규칙 같은 리소스를 조직 전반에 공유할 수 있습니다. AWS Organizations와 함께 사용하면 리소스 공유의 주체로 전체 OU나 심지어 전체 조직을 지정할 수 있습니다. 이는 모든 계정에 걸쳐 공유 네트워크 아키텍처나 중앙 관리형 서비스를 만드는 프로세스를 단순화합니다.

### 7.2. AWS IAM Identity Center(이전 AWS SSO)

AWS IAM Identity Center는 여러 AWS 계정에 걸친 접근을 단순화하는 중앙화된 신원 관리 서비스입니다. AWS Organizations와 통합되면 다음을 할 수 있습니다.

- **중앙에서 접근 관리:** 중앙 디렉터리에서 사용자와 그룹을 생성하고 관리합니다.
- **권한 집합 할당:** 사용자에게 여러 계정에 걸쳐 사전 정의된 IAM 역할(관리자나 읽기 전용 등)을 부여합니다.
- **매끄러운 SSO:** 사용자가 한 번 로그인해 별도의 자격 증명 없이도 계정 간에 전환할 수 있게 합니다.

이 통합은 모든 계정에서 별도의 IAM 사용자를 유지하는 관리 오버헤드를 없애고 신원과 접근 관리를 중앙화함으로써 보안을 강화합니다.

### 7.3. AWS CloudTrail과 AWS Config

**CloudTrail**은 감사와 포렌식 분석에 필수적입니다. 조직 전체 CloudTrail 트레일을 사용하면 모든 회원 계정의 모든 API 활동이 (일반적으로 전용 로그 아카이브 계정의) 중앙 S3 버킷으로 로깅됩니다. 이 중앙화된 로깅은 회원 계정의 누군가가 로깅을 비활성화하려 시도하더라도 조직 전체 구성이 이를 방지하도록 보장합니다.

**AWS Config**는 AWS 리소스의 상태를 지속적으로 기록하고 원하는 규정 준수 규칙에 대해 평가합니다. (조직 ID로 구성된) 중앙 집계기를 사용해 AWS Config 데이터를 집계함으로써 모든 계정에 걸친 모든 리소스의 구성 이력에 대한 완전한 가시성을 얻을 수 있습니다. 이는 규정 준수 감사와 사고 조사 모두에 매우 중요합니다.

### 7.4. AWS 비용 관리 도구

AWS Organizations를 통한 통합 결제는 모든 계정에 대한 하나의 청구서를 가능하게 하며, 이는 다시 AWS Cost Explorer와 AWS Budgets 같은 도구를 사용해 다음을 할 수 있게 합니다.

- **지출 분석:** 계정, 서비스, 리전, 또는 커스텀 비용 범주별로 비용을 분석합니다.
- **트렌드 추적:** 전체 조직에 걸친 지출 트렌드를 모니터링합니다.
- **차지백/쇼백 구현:** 리소스 사용에 기반해 적절한 팀이나 비즈니스 단위에 비용을 할당합니다.

예를 들어 여러 계정이 예약 인스턴스나 Savings Plan을 공유하면 AWS는 조직 전체에 걸쳐 자동으로 할인을 적용해, 비용 효율성을 극대화합니다.

### 7.5. AWS 보안 서비스: GuardDuty, Security Hub 등

AWS 보안 서비스는 Organizations와 통합될 때 계정 전반에서 작동하도록 설계되었습니다.

- **Amazon GuardDuty:** 조직 전체에서 활성화되면 GuardDuty는 모든 계정에서 의심스러운 활동을 지속적으로 모니터링합니다. 발견 사항은 중앙 보안 계정에 집계되어, 보안 팀이 전체 환경에 걸친 위협을 보고 조치할 수 있게 합니다.
- **AWS Security Hub:** Security Hub는 GuardDuty, AWS Config 규칙, 다른 보안 서비스의 발견 사항을 집계하고 정규화합니다. AWS Organizations와의 통합을 통해 Security Hub는 모든 계정에 걸친 통합 대시보드를 제공해, 규정 준수 모니터링과 사고 대응을 단순화합니다.
- **기타 서비스:** AWS Macie, Firewall Manager, IAM Access Analyzer 같은 서비스도 Organizations와의 통합의 혜택을 받아 위임된 관리와 균일한 구성을 가능하게 합니다.

## 8. 멀티 계정 환경에서의 비용 최적화 전략

비용 최적화는 AWS Organizations를 사용할 때 가장 매력적인 이점 중 하나입니다. 계정 전반의 결제를 중앙화하고 사용량을 통합함으로써 조직은 여러 비용 절감 메커니즘을 잠금 해제할 수 있습니다.

### 8.1. 통합 결제의 이점

모든 회원 계정이 결제를 위해 단일 관리 계정에 연결되면 여러 재정적 이점이 실현됩니다.

- **볼륨 할인:** 많은 AWS 서비스는 전체 사용량이 증가함에 따라 단위당 비용이 낮아지는 가격 티어를 제공합니다. 통합 결제는 모든 계정의 사용량을 집계해, 조직이 가장 높은 티어의 가격의 혜택을 받도록 보장합니다.
- **예약 인스턴스와 Savings Plan 공유:** 한 계정이 예약 인스턴스(RI)나 Savings Plan을 구매하면 할인을 모든 계정에 걸쳐 공유할 수 있습니다. 이는 활용도를 극대화하고 전체 비용을 줄이는 데 도움을 줍니다.
- **단일 결제와 간소화된 조정:** 하나의 통합된 청구서는 관리 오버헤드를 줄이고 재무 팀이 지출을 추적하고 내부적으로 비용을 할당하기 더 쉽게 만듭니다.

### 8.2. 비용 통제 구현

지출을 통제하기 위해 조직은 AWS Budgets와 AWS Cost Explorer를 사용할 수 있습니다.

- **AWS Budgets:** 계정이나 OU 수준에서 지출 임계값을 설정합니다. 예산은 임계값을 초과하면 팀 리더에게 알림을 보내거나 심지어 자동화된 작업(리소스 축소 등)을 트리거할 수 있습니다.
- **Cost Explorer:** 고급 필터링과 그룹화 옵션을 사용해 계정, 서비스, 또는 태그별로 지출을 분석합니다. 이 세밀한 가시성은 더 나은 차지백과 비용 할당 관행을 가능하게 합니다.

### 8.3. 비용 관리를 위한 조직적 거버넌스

기술을 넘어 좋은 거버넌스 관행은 비용 최적화에서 핵심적인 역할을 합니다.

- **태깅 전략:** 정확한 비용 할당과 보고를 촉진하기 위해 모든 계정에 걸쳐 일관된 태깅 정책을 강제하세요.
- **정책 강제:** 특정 계정(예: 샌드박스 계정에서 인스턴스 크기 제한)에서 비싸거나 필수적이지 않은 리소스의 배포를 방지하기 위해 SCP를 사용하세요.
- **정기 검토:** 지출이 허용 가능한 범위 내에 유지되도록 비용 보고서와 예산 알림을 주기적으로 검토하세요.

통합 결제와 세심한 거버넌스를 결합함으로써 기업은 높은 수준의 성능과 보안을 유지하면서도 클라우드 비용을 크게 줄일 수 있습니다.

## 9. 멀티 계정 환경에서의 자동화와 DevOps

수십 개 — 심지어 수백 개 — 의 AWS 계정을 수동으로 관리하는 것은 지속 가능하지 않습니다. 자동화는 멀티 계정 환경을 효율적으로 프로비저닝, 구성, 유지하는 열쇠입니다. AWS Organizations는 클라우드 환경을 코드로 취급하는 데 필요한 API와 통합 지점을 제공합니다.

### 9.1. 계정 프로비저닝 자동화

AWS 콘솔을 통해 수동으로 계정을 생성하는 대신 AWS Organizations API를 사용해 계정 생성을 자동화할 수 있습니다. 예를 들어 새 프로젝트가 승인되면 파이프라인이 새 계정을 생성하고, 이메일 주소를 할당하고, 이름을 설정하는 API 호출을 트리거할 수 있습니다.

```bash
aws organizations create-account \
    --email new_project_team@example.com \
    --account-name "New Project Account" \
    --role-name OrganizationAccountAccessRole
```

이 비동기 작업은 계정이 준비될 때까지 폴링할 수 있는 요청 ID를 반환합니다. 계정이 생성되면 적절한 OU로 이동시키고 AWS CloudFormation StackSets 같은 도구를 사용해 자동으로 기준선 인프라를 배포할 수 있습니다.

### 9.2. Infrastructure as Code(IaC)와 StackSets

AWS CloudFormation StackSets는 하나의 작업으로 여러 계정과 리전에 동시에 CloudFormation 템플릿을 배포할 수 있게 합니다. 이 기능은 VPC, IAM 역할, 로깅 구성, 심지어 SCP 설정 같은 기준선 구성을 조직 전체에 강제하는 데 매우 유용합니다. StackSets를 사용하면 모든 새 계정이 자동으로 다음으로 구성되도록 보장할 수 있습니다.

- **보안 기준선:** 로깅(CloudTrail, Config), GuardDuty 탐지기, 사전 구성된 IAM 역할.
- **네트워크 인프라:** 공유 VPC, 서브넷, 연결 설정.
- **운영 도구:** 중앙화된 모니터링, CI/CD 에이전트, 백업 구성.

IaC를 사용하면 전체 AWS 환경이 재현 가능하고, 버전 관리되며, 감사 가능하도록 보장합니다.

### 9.3. CI/CD 파이프라인과의 통합

현대 DevOps 관행은 여러 AWS 계정에 걸친 애플리케이션 배포로 확장됩니다. 중앙 CI/CD 파이프라인은 코드를 한 번 빌드한 다음 각 대상 계정에서 배포 역할을 수임함으로써 개발, 테스트, 프로덕션 같은 다양한 환경에 배포할 수 있습니다. AWS IAM Identity Center는 싱글 사인온 경험을 제공함으로써 이 프로세스를 더욱 간소화해, 수동 자격 증명 관리의 필요를 줄여줍니다.

### 9.4. AWS Control Tower: 견해가 있는 멀티 계정 프레임워크

많은 기업에게 AWS Control Tower는 멀티 계정 환경을 구축하기 위한 즉시 사용 가능한 솔루션을 제공합니다. Control Tower는 내부적으로 AWS Organizations를 활용해 기본 OU, SCP, 기준선 계정(로그 아카이브와 감사 계정 등)을 갖춘 사전 구성된 랜딩 존을 생성합니다. Control Tower는 견해가 있는 설정을 제공하지만, 자신만의 자동화된 멀티 계정 프레임워크를 커스터마이징할 수 있는 템플릿이나 시작점 역할을 할 수 있습니다.

### 9.5. AWS Organizations를 위한 GitOps

최첨단 관행은 AWS Organization 구성을 코드로 취급하는 것입니다. OU 구조, SCP, 기준선 인프라 템플릿을 버전 관리 저장소(예: Git)에 저장하세요. 그런 다음 자동화된 파이프라인을 사용해 조직 구성을 배포하고 업데이트하세요. 이 접근 방식은 수동 오류를 최소화할 뿐만 아니라 변경 이력도 제공해, 감사와 규정 준수 검토를 훨씬 더 간단하게 만듭니다.

## 10. 모니터링과 사고 대응

멀티 계정 환경에서는 중앙화된 모니터링과 잘 정의된 사고 대응 전략이 보안과 운영 복원력을 유지하는 데 필수적입니다.

### 10.1. 중앙화된 로깅

첫 단계 중 하나는 모든 계정의 로그가 중앙 저장소로 집계되도록 보장하는 것입니다. 이는 일반적으로 다음을 통해 달성됩니다.

- **AWS CloudTrail:** 모든 회원 계정에 걸친 모든 API 호출을 로깅하는 조직 전체 CloudTrail 트레일을 설정합니다. 이 로그는 일반적으로 변조로부터 보호되는 전용 로그 아카이브 계정의 S3 버킷으로 전달됩니다.
- **AWS Config:** AWS Config 집계기를 사용해 모든 계정으로부터 구성 스냅샷과 규정 준수 데이터를 수집합니다.
- **애플리케이션과 시스템 로그:** 많은 조직이 각 계정에서 CloudWatch Logs를 중앙 로그 분석 시스템(ELK 스택이나 SIEM 등)으로 전달해, 운영 문제와 보안 사고가 한 곳에서 보이도록 보장합니다.

### 10.2. 지표, 알람, 대시보드

AWS CloudWatch를 사용하면 모든 계정의 지표를 통합하는 대시보드를 만들 수 있습니다. 예를 들어:

- **계정 간 대시보드:** EC2 인스턴스 상태, Lambda 함수의 오류율, RDS 성능 지표 같은 핵심 성능 지표(KPI)를 표시하는 대시보드를 구성합니다.
- **CloudWatch 알람:** 보안 침해나 잘못된 구성을 나타낼 수 있는 API 오류 급증이나 예기치 않은 리소스 생성 같은 이상한 활동을 탐지하는 알람을 설정합니다.

### 10.3. 보안 모니터링과 사고 대응

AWS 보안 서비스는 Organizations와 통합될 때 잠재적인 위협에 대한 중앙화된 시각을 제공합니다.

- **Amazon GuardDuty:** 조직 전체에서 활성화되면 GuardDuty는 이상한 API 호출이나 의심스러운 네트워크 활동 같은 이상을 지속적으로 모니터링합니다. 모든 계정으로부터의 발견 사항은 중앙 보안 계정에 집계됩니다.
- **AWS Security Hub:** GuardDuty, AWS Config, 다른 보안 서비스로부터의 발견 사항을 집계해, 조직의 보안 태세에 대한 통합된 시각을 제공합니다.
- **자동화된 사고 대응:** AWS Lambda, Amazon EventBridge, AWS Systems Manager Automation을 활용해 특정 사고에 자동으로 대응할 수 있는 런북을 만듭니다 — 예를 들어 GuardDuty가 악성 행동을 탐지하면 EC2 인스턴스를 격리합니다.

### 10.4. 사고 대응을 위한 계정 간 접근

신속한 사고 대응을 보장하려면 보안 팀이 수임할 수 있는 전용 IAM 역할을 각 계정에 설정하는 것이 매우 중요합니다. 예를 들어 모든 계정에 "OrgSecurityAudit" 같은 역할을 만들면 중앙 보안 팀이 로그에 신속하게 접근하고, 포렌식 분석을 수행하고, 계정 전반의 문제를 개선할 수 있습니다. 이 역할들은 문제 해결에 필요한 최소한의 권한만 가져야 하며 다중 인증(MFA)으로 보호되어야 합니다.

## 11. 재해 복구와 백업 전략

멀티 계정 환경에서의 재해 복구(DR) 계획은 리전 복제를 넘어섭니다 — 데이터와 중요한 워크로드가 불리한 조건에서도 계속 사용 가능하도록 보장하기 위해 여러 계정에 걸친 조율된 전략을 포함합니다.

### 11.1. AWS Backup을 사용한 중앙화된 백업

AWS Backup은 EC2 볼륨, RDS 데이터베이스, DynamoDB 테이블을 포함한 다양한 AWS 리소스의 백업을 자동화하는 완전관리형 서비스입니다. AWS Organizations와 통합되면 다음을 할 수 있습니다.

- **조직 수준 백업 정책 정의:** 모든 계정이나 OU에 걸쳐 일관된 백업 일정과 보존 규칙을 적용합니다.
- **계정 간 백업 볼트:** 별도의 전용 계정에 백업 볼트를 구성해 백업이 프로덕션 환경으로부터 격리되도록 합니다. 이는 실수로 인한 또는 악의적인 삭제에 대한 추가적인 보호를 제공합니다.
- **Vault Lock:** AWS Backup Vault Lock을 사용해 백업에 Write-Once-Read-Many(WORM) 정책을 강제해, 보존 기간 동안 중요한 백업이 변경되거나 삭제될 수 없도록 보장합니다.

### 11.2. 멀티 리전과 계정 간 DR 전략

재해 복구 전략은 흔히 리전 전반이나 심지어 다른 AWS 계정 전반에 걸쳐 데이터와 워크로드를 복제하는 것을 포함합니다.

- **동일 계정, 리전 간 DR:** 많은 조직이 동일한 계정 내에서 다른 리전으로 리소스(RDS 복제본이나 S3 리전 간 복제 등)를 복제하기로 선택합니다.
- **별도의 DR 계정:** 또는 DR 목적으로 별도의 계정을 전용으로 사용할 수 있습니다. 예를 들어 프로덕션 워크로드는 Infrastructure as Code를 사용해 사전 프로비저닝된 대기 환경이 있는 "복구 OU"로 미러링될 수 있습니다. 위기 상황에서는 트래픽을 최소한의 다운타임으로 이 계정들로 재라우팅할 수 있습니다.
- **인프라 자동화:** CloudFormation StackSets나 Terraform을 사용해 DR 환경을 프로덕션과 동기화된 상태로 유지하세요. 이는 재해가 발생하면 필요한 인프라가 이미 준비되어 있어 신속하게 활성화될 수 있도록 보장합니다.
- **Route 53과 DNS 페일오버:** DNS 기반 페일오버를 위해 Amazon Route 53을 활용하세요. 상태 확인은 프라이머리 리전이나 계정을 사용할 수 없을 때를 감지하고 트래픽을 DR 사이트로 자동으로 재라우팅할 수 있습니다.

### 11.3. 테스트와 지속적인 개선

DR 계획은 마지막 성공적인 테스트만큼만 좋습니다. 백업 복원과 페일오버 프로세스를 정기적으로 테스트하세요.

- **시뮬레이션된 페일오버:** 백업 데이터가 접근 가능하고 자동화된 복구 프로세스가 올바르게 작동하는지 확인하기 위해 주기적으로 리전 장애나 계정 수준 사고를 시뮬레이션하세요.
- **정책 감사와 조정:** 백업 정책, 복원 시간, 전체 DR 전략을 세밀하게 조정하기 위해 테스트 결과를 사용하세요. 배운 교훈을 문서화하고 그에 따라 런북을 업데이트하세요.

## 12. 조직 할당량

AWS Organizations 자체는 다음을 포함해 특정 한도를 가집니다.

- **최대 계정 수:** 기본적으로 조직은 작은 한도(흔히 10개 계정)로 시작하지만, 수천 개의 계정을 지원하도록 늘릴 수 있습니다. 대기업의 경우 계정 성장을 계획하는 것이 매우 중요합니다.
- **조직 단위(OU):** 조직은 기본적으로 최대 1,000개의 OU를 가질 수 있으며 최대 5단계까지 중첩할 수 있습니다. 이는 일반적으로 복잡한 기업에게도 충분합니다.
- **정책 연결:** 단일 엔티티(계정이나 OU)에 연결할 수 있는 SCP, 태그 정책, 백업 정책의 수에는 제한이 있습니다.

## 13. 실제 시나리오와 사례 연구

이 개념들을 종합하기 위해 두 가지 상세한 실제 시나리오를 살펴보겠습니다: 하나는 엔터프라이즈 확장과 관련되고 다른 하나는 인수합병에 초점을 맞춥니다.

### 13.1. 엔터프라이즈 확장 사례 연구

**회사 배경:**
Acme Corp는 개발, 테스트, 프로덕션에 전용된 소수의 AWS 계정으로 클라우드 여정을 시작했습니다. 회사가 성장함에 따라 개별 제품 팀은 보안, 비용, 자율성을 더 잘 관리하기 위해 격리된 환경을 요청했습니다. 곧 Acme의 클라우드 발자국은 마이크로서비스 애플리케이션부터 네트워킹과 로깅을 위한 공유 인프라까지 모든 것을 아우르는 50개 이상의 계정으로 확장되었습니다.

**조직 구조:**
Acme Corp는 내부 구조를 반영하도록 AWS Organization을 설계했습니다.

- **루트 계정:** 관리 계정은 거버넌스와 결제만을 위해 예약되었습니다.
- **보안 OU:** 중앙화된 보안 운영을 위한 전용 계정 — Security Tooling 계정(GuardDuty, Security Hub, 다른 모니터링 도구 실행)과 Log Archive 계정(CloudTrail 로그, AWS Config 스냅샷, 다른 로그 중앙화)을 포함했습니다.
- **인프라 OU:** VPC와 Transit Gateway 관리를 위한 Network Account, CI/CD 도구와 Active Directory를 위한 Shared Services Account 같은 공유 서비스 계정을 호스팅했습니다.
- **워크로드 OU:** 프로덕션과 비프로덕션 OU로 나뉘었으며, 각 제품이나 비즈니스 단위는 자체 계정 세트를 가졌습니다(예: 프로덕션의 "Payments-Prod", "ShoppingCart-Prod"; 비프로덕션의 해당 개발 및 테스트 계정).
- **샌드박스 OU:** 개별 엔지니어가 프로덕션에 영향을 미치거나 예기치 않은 비용을 발생시키지 않고 안전하게 실험할 수 있는 격리된 환경을 제공했습니다.

**거버넌스와 정책:**
Acme는 서로 다른 OU에 걸쳐 엄격한 SCP를 강제했습니다.

- **루트에서:** 기준선 SCP는 어떤 회원 계정도 자체적으로 조직에서 이탈할 수 없도록 보장해, 무단 이탈로부터 보호했습니다.
- **비프로덕션 계정:** SCP는 비싼 서비스에 대한 접근을 제한하고 인스턴스 크기가 비용 효율적인 범위 내에 유지되도록 보장했습니다.
- **프로덕션 계정:** 더 엄격한 정책은 중요한 보안 구성에 대한 어떤 수정도 방지했습니다. 예를 들어 IAM 역할 변경이나 GuardDuty 비활성화는 엄격하게 통제되었습니다.
- **샌드박스 계정:** 가장 제한적인 SCP는 고비용 서비스에 대한 접근을 방지하고 승인된 작업만 수행될 수 있도록 보장해, 비용을 예측 가능하게 유지했습니다.

**자동화와 효율성:**
Acme는 자동화를 광범위하게 활용했습니다.

- **계정 벤딩:** 새 계정은 AWS Organizations API를 사용하는 자동화된 스크립트를 통해 프로비저닝되어, 각 새 계정이 자동으로 올바른 OU로 이동되고 기준선 CloudFormation 템플릿으로 구성되도록 보장했습니다.
- **StackSets:** 로깅 구성, 보안 설정, 네트워킹 파라미터 같은 기준선 인프라는 CloudFormation StackSets를 사용해 모든 계정에 배포되었습니다.
- **중앙화된 신원:** AWS IAM Identity Center는 계정 전반의 사용자 접근 관리를 단순화해, 직원이 한 번 로그인하고 매끄럽게 계정 간에 전환할 수 있게 했습니다.

**비용 관리:**
통합 결제를 사용해 Acme의 재무 팀은 다음을 할 수 있었습니다.

- AWS Cost Explorer를 사용해 모든 계정에 걸친 지출을 모니터링합니다.
- 상세한 태깅을 통해 개별 제품 팀에 비용을 다시 할당합니다.
- 계정 간 할인을 공유함으로써 예약 인스턴스 사용을 최적화해, 상당한 절감을 달성합니다.

**사고 대응과 모니터링:**
Security Tooling 계정은 GuardDuty와 Security Hub로부터의 발견 사항을 집계했으며, Log Archive 계정은 로그가 변조 방지되도록 보장했습니다. 개발 계정에서 보안 사고가 발생하면 중앙 보안 팀은 신속하게:

- 계정 간 IAM 역할을 사용해 영향받은 EC2 인스턴스를 격리했습니다.
- Log Archive 계정으로부터 CloudTrail 로그를 분석했습니다.
- 사고가 해결될 때까지 민감한 작업을 동결하기 위해 긴급 SCP를 적용했습니다.

Acme Corp의 사례는 잘 설계된 AWS Organization이 통제, 규정 준수, 비용 효율성을 유지하면서도 빠른 확장을 어떻게 지원할 수 있는지 보여줍니다.

### 13.2. 인수합병(M&A) 사례 연구

**시나리오:**
약 20개의 AWS 계정을 가진 중견 기업인 BetaCo는 100개 이상의 AWS 계정을 가진 더 큰 기업인 MegaCorp에 인수되었습니다. 목표는 통합 결제, 중앙화된 보안, 일관된 거버넌스를 달성하기 위해 BetaCo의 클라우드 환경을 MegaCorp의 AWS Organization으로 병합하는 것이었습니다.

**마이그레이션 전 계획:**
두 회사 모두 AWS 환경에 대한 철저한 감사를 수행했습니다. 주요 준비 단계는 다음을 포함했습니다.

- **이메일과 계정 검증:** BetaCo의 계정이 MegaCorp와 충돌하는 이메일 주소를 가지고 있지 않은지 확인.
- **연령 검증:** 모든 BetaCo 계정이 마이그레이션 자격을 갖추기 위한 최소 연령 요구 사항(7일)을 충족하는지 확인.
- **정책 조정:** BetaCo의 SCP를 MegaCorp의 것과 비교하고 매끄러운 전환을 보장하기 위한 조정을 계획.
- **결제와 로그 데이터 백업:** 마이그레이션 중 데이터 손실을 피하기 위해 BetaCo의 조직으로부터 결제 보고서와 CloudTrail 로그를 내보내기.

**마이그레이션 프로세스:**
마이그레이션은 덜 중요한 계정부터 시작해 점진적으로 수행되었습니다.

1. **BetaCo의 조직에서 제거:** 각 BetaCo 계정은 먼저 원래 AWS Organization에서 제거되어 독립형 계정이 되었습니다.
2. **MegaCorp로의 초대:** MegaCorp의 관리 계정이 독립형 계정에 초대를 보냈습니다.
3. **수락과 OU 할당:** 계정이 초대를 수락하면 MegaCorp의 조직 내 지정된 "BetaCo" OU로 이동되었습니다.
4. **재구성:** 계정의 로깅, 보안, 접근 구성이 MegaCorp의 정책을 따르도록 업데이트되었습니다. 예를 들어 기존 GuardDuty 탐지기는 MegaCorp의 중앙화된 GuardDuty 인스턴스로 통합되거나 중복을 피하기 위해 폐기되었습니다.
5. **사용자와 접근 전환:** BetaCo의 IAM 사용자는 매끄러운 사인온 경험을 보장하기 위해 MegaCorp의 AWS IAM Identity Center로 전환되었습니다.

**마이그레이션 후 통합:**
모든 BetaCo 계정이 통합된 후:

- **통합 결제:** BetaCo의 지출은 이제 MegaCorp의 통합 청구서의 일부가 되어, 공유 예약 인스턴스 사용 같은 비용 최적화를 가능하게 했습니다.
- **중앙화된 보안:** Security Hub와 GuardDuty가 BetaCo의 계정으로부터 발견 사항을 집계하기 시작해, 중앙 보안 팀에게 완전한 가시성을 제공했습니다.
- **운영 일관성:** MegaCorp가 BetaCo의 팀을 기능이나 환경에 기반해 기존 OU로 통합함에 따라 OU 구조가 시간이 지남에 따라 조정되었습니다.

**결과:**
합병은 실행 중인 애플리케이션에 최소한의 중단으로 대체로 성공적이었습니다. IAM 역할 이름 충돌 같은 신속한 해결이 필요한 몇 가지 사소한 문제가 발생했지만, 전반적으로 이 마이그레이션은 AWS Organizations가 서로 다른 AWS 환경을 하나의 응집력 있고 중앙에서 관리되는 생태계로 매끄럽게 통합할 수 있다는 것을 입증했습니다.

## 14. 결론

AWS Organizations는 현대 엔터프라이즈 클라우드 아키텍처의 초석입니다. 격리되고 자율적인 계정의 필요와 중앙화된 통제, 통합 보안, 통합 결제의 이점 사이의 균형을 맞출 수 있게 하는 구조화된 프레임워크를 제공합니다. 이 장에서 설명한 개념을 이해하고 적용함으로써 안전하고 확장 가능하며 비용 효율적인 멀티 계정 환경을 설계할 수 있습니다.
