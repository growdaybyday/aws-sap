# AWS Systems Manager
## 1. 소개

AWS Systems Manager는 AWS에서 실행되든, 온프레미스에서 실행되든, 멀티클라우드 환경에서 실행되든 관계없이 노드를 보고, 관리하고, 운영할 수 있는 중앙화된 방법을 제공합니다. 통합된 콘솔 경험을 통해 AWS 계정과 리전 전반에서 일반적인 노드 작업을 단순화하는 포괄적인 도구 모음에 접근할 수 있습니다.

Systems Manager가 작동하려면 노드가 _관리형_이어야 합니다. 즉, SSM 에이전트가 설치되어 있고 Systems Manager 서비스와 통신할 수 있어야 합니다. 연결 문제를 진단하고 해결하는 데 도움을 주기 위해 Systems Manager는 원클릭 에이전트 진단과 개선 런북을 제공합니다. 이 자동화된 기능은 네트워킹 잘못된 구성 같은 이유로 노드가 관리형으로 보고되지 않는 이유를 식별하고 정의한 일정에 따라 이 문제를 해결하기 위한 권장 런북을 제공합니다.

통합 콘솔에는 노드에 대한 고수준 개요를 제공하는 강력한 대시보드도 포함되어 있습니다. (구식 운영체제 버전 같은) 상세한 인사이트로 세부 조사하고 (OS, OS 버전, AWS 리전, 계정, SSM Agent 버전 같은) 메타데이터를 기반으로 한 고급 필터를 사용할 수 있습니다. 이 기능은 조직 전반의 계정과 애플리케이션 수준 모두에서 관련 정보를 신속하게 검색할 수 있게 합니다.

## 2. Systems Manager는 내 운영에 어떤 이점을 줄 수 있는가?

AWS Systems Manager는 인프라 관리를 간소화하고 보안을 강화하는 여러 운영상의 이점을 제공합니다.

- **인프라 전반의 강화된 가시성**
    모든 AWS 계정과 리전에 걸친 노드에 대한 중앙화된 시각을 얻으세요. ID, 이름, OS 세부 사항, 에이전트 버전 같은 상세한 인스턴스 정보에 즉시 접근하세요. 예를 들어 글로벌 운영 팀은 구식 소프트웨어를 실행하는 인스턴스를 신속하게 식별해 취약점을 선제적으로 개선할 수 있습니다.

- **자동화를 통한 향상된 운영 효율성**
    시간을 절약하고 오류를 줄이기 위해 일상적인 관리 작업을 자동화하세요. Systems Manager를 사용하면 배스천 호스트, SSH, 또는 원격 PowerShell 세션 없이도 대규모로 안전하게 노드를 관리할 수 있습니다. 몇 번의 클릭만으로 수백 개의 인스턴스에 걸쳐 레지스트리 업데이트, 사용자 관리, 또는 패치 설치를 자동화하는 것을 상상해보세요.

- **다양한 환경 전반의 단순화된 노드 관리**
    노드가 AWS에 있든, 온프레미스에 있든, 멀티클라우드 환경에 걸쳐 있든, Systems Manager는 관리를 간소화합니다. SSM Agent 문제를 자동으로 진단하고 원클릭 런북을 사용해 개선할 수 있습니다. 노드가 관리형으로 구성되면 전통적인 원격 관리 방법의 복잡성 없이 보안 패치 적용이나 로깅된 세션 시작 같은 중요한 작업을 원격으로 실행할 수 있습니다.

## 3. 누가 Systems Manager를 사용해야 하는가?

AWS Systems Manager는 IT 운영 관리자, DevOps 엔지니어, 보안 및 규정 준수 전문가, IT 이사와 CIO 같은 임원급 리더를 위해 설계되었습니다. 다음과 같은 조직에 이상적입니다.

- **대규모 관리와 보안을 강화해야 함:**
    인프라의 감독과 보호를 개선하고자 하는 조직은 Systems Manager의 중앙화되고 자동화된 도구의 혜택을 받을 수 있습니다.

- **더 큰 가시성과 운영 민첩성을 원함:**
    다양한 환경에 걸쳐 실시간 인사이트와 운영 문제에 신속하게 대응할 수 있는 능력이 필요하다면 Systems Manager의 대시보드와 보고 기능은 필수 불가결합니다.

- **운영 효율성을 높이는 것을 목표로 함:**
    일상적인 작업을 자동화하고 수동 개입을 줄이고자 하는 회사를 위해 Systems Manager는 프로세스를 간소화하고 사람의 실수와 관련된 위험을 최소화합니다.

## 4. Systems Manager 서비스 이름 이력

AWS Systems Manager는 이전에 "Amazon Simple Systems Manager(SSM)"와 "Amazon EC2 Systems Manager(SSM)"로 알려졌었습니다. 서비스 이름의 진화에도 불구하고 약어 "SSM"은 다양한 AWS 리소스와 서비스 콘솔에 계속 나타납니다. 예를 들면:

- **Systems Manager 에이전트:** SSM Agent로 지칭됨
- **Systems Manager 파라미터:** 흔히 SSM 파라미터로 알려짐
- **서비스 엔드포인트:** `ssm.<region>.amazonaws.com` 형식으로 지정됨
- **CloudFormation 리소스 유형:** `AWS::SSM::Document`로 식별됨
- **AWS Config 규칙 식별자:** `EC2_INSTANCE_MANAGED_BY_SSM` 같은 것
- **CLI 명령:** 예를 들어 `aws ssm describe-patch-baselines`
- **IAM 관리형 정책:** 예를 들어 `AmazonSSMReadOnlyAccess`
- **리소스 ARN:** `arn:aws:ssm:<region>:<account-id>:patchbaseline/pb-07d8884178EXAMPLE` 형식으로 지정됨

이 레거시 명명은 AWS 서비스 전반에 걸친 SSM의 깊은 통합을 강조합니다.

## 5. 통합 콘솔이란?

통합 Systems Manager 콘솔은 여러 AWS 계정과 리전에 걸쳐 — 또는 단일 계정과 리전 내에서 — 일반적인 노드 관리 작업을 수행하는 데 도움이 되는 다양한 도구를 하나로 모은 통합 인터페이스입니다. 노드가 EC2 인스턴스든, 하이브리드 서버든, 멀티클라우드 환경의 일부든, 통합 콘솔은 포괄적인 인사이트와 관리 기능을 제공합니다.

![ssm-unified-console-1](@site/docs/Management%20and%20Governance/_assets/ssm-unified-console-1.png)

콘솔 내에서 다음을 할 수 있습니다.

- 노드 상태와 구성에 대한 상세한 보고서를 생성합니다.
- 노드가 관리형으로 인식되지 못하게 하는 연결 문제 같은 문제를 진단하고 개선합니다.
- 소프트웨어 인벤토리와 패치 상태 같은 특정 세부 사항을 봅니다.

![ssm-unified-console-2](@site/docs/Management%20and%20Governance/_assets/ssm-unified-console-2.png)

예를 들어 여러 리전에 걸쳐 운영하는 회사는 통합 콘솔을 사용해 문제가 있는 인스턴스를 신속하게 세부 조사하고, OS 버전이나 SSM Agent 버전 같은 기준으로 노드를 필터링하고, 하나의 응집력 있는 대시보드에서 시정 조치를 실행할 수 있습니다. AWS가 통합 콘솔을 계속 강화함에 따라 더 많은 노드 관리 작업이 통합되어, 효율적이고 효과적인 인프라 관리를 위한 권장 인터페이스가 되고 있습니다.

## 6. AWS Systems Manager Resource Groups

Resource Groups는 공통 기준에 기반해 여러 AWS 리소스(EC2 인스턴스, S3 버킷, RDS 데이터베이스 등)를 논리적으로 조직화할 수 있게 합니다.

50개의 EC2 인스턴스에 걸쳐 웹 애플리케이션을 실행하는 조직을 상상해보세요. 이 인스턴스들을 (예를 들어 `Environment=Production`과 `App=WebPortal`로) 태깅함으로써 동적 리소스 그룹을 만듭니다. 배치 업데이트나 패치 작업을 실행할 때가 되면 전체 그룹을 하나의 명령으로 대상으로 삼을 수 있습니다. 새 EC2 인스턴스가 시작되어 자동으로 태깅되면 그룹에 추가되며 — SSM Agent가 설치되어 있다면 — 즉시 동일한 업데이트를 받습니다.

### 6.1. 리소스 그룹 생성하기

태그 기반 또는 CloudFormation 기반 방법을 사용해 리소스 그룹을 생성할 수 있습니다. 태그 기반 그룹화는 동적입니다 — 새 리소스가 태깅되면 자동으로 그룹에 가입합니다 — 반면 CloudFormation 기반 그룹화는 정의된 스택에서 가져옵니다.

한 회사는 마이크로서비스 아키텍처를 배포하기 위해 CloudFormation 스택을 사용할 수 있습니다. 해당 스택의 모든 리소스를 그룹화하면 운영 팀이 전체 애플리케이션에 걸쳐 유지보수 작업을 신속하게 실행할 수 있습니다. 이는 일관성을 보장하고 수동 개입을 최소화합니다.

### 6.2. 동적 vs. 정적 리소스 그룹

동적 그룹은 태그에 기반해 자동으로 업데이트되어, SSM Agent가 설치된 모든 새 인스턴스가 수동 업데이트 없이 포함되도록 보장함으로써 오버헤드를 줄여줍니다. 반면 (CLI나 CloudFormation 템플릿을 사용해) 특정 리소스 ARN을 수동으로 나열함으로써 "정적" 그룹도 만들 수 있습니다 — 하지만 태그 기반(동적) 그룹은 환경이 성장함에 따라 유지하기 더 쉽습니다.

## 7. Systems Manager Documents(SSM Documents)

SSM Document는 관리형 인스턴스에서 실행할 일련의 작업 — 흔히 런북이라고 불림 — 을 정의하는 JSON이나 YAML 파일입니다. Document는 단순한 셸 명령부터 복잡한 다단계 워크플로까지 모든 것을 캡슐화할 수 있습니다.

AWS는 일반적인 시나리오를 다루는 100개 이상의 사전 생성된 **Amazon 소유 문서**(`AWS-RunShellScript`, `AWS-RunPatchBaseline` 등의 접두사로 명명됨)를 제공합니다. 필요에 맞춘 **커스텀 SSM Document**를 만들 수도 있습니다.

개발자가 인스턴스 함대에서 구성 파일을 업데이트해야 하는 시나리오를 생각해보세요. 파일을 업데이트하는 셸 스크립트를 실행하는 커스텀 SSM Document를 만들고 모든 인스턴스에 SSM Agent가 설치되어 있는지 확인함으로써, 운영 팀은 최소한의 위험으로 100개의 인스턴스에 걸쳐 이 변경을 동시에 실행할 수 있습니다.

### 7.1. SSM Document의 유형

주요 문서 유형은 다음을 포함합니다.

- **명령 문서(Command documents):** **Run Command**, State Manager, Maintenance Windows와 함께 사용되어 인스턴스에서 명령이나 스크립트를 실행합니다. 예시: `AWS-RunShellScript`는 Linux 인스턴스에서 셸 명령을 실행하는 명령 문서입니다. 명령 문서는 흔히 하나 이상의 대상에 대한 구성이나 자동화 작업을 위한 단순한 단일 단계나 다단계 지침입니다.

- **자동화 런북(자동화 문서):** 다단계 워크플로를 위해 **Systems Manager Automation**과 함께 사용됩니다(State Manager나 Maintenance Windows를 통해서도 호출할 수 있음). 자동화 문서는 분기, 오류 처리, AWS API와의 통합을 갖춘 복잡한 시퀀스를 허용합니다. 예를 들어 `AWS-CreateImage`(자동화 런북)는 인스턴스를 중지하고, AMI를 생성하고, 인스턴스를 재시작하는 단계를 조율합니다. 이 런북들은 하나 또는 여러 리소스에 적용될 수 있으며 흔히 유지보수와 배포 작업에 사용됩니다.

- **정책 문서:** 덜 사용되는 유형으로, 역사적으로 **인벤토리 수집이나 구성 정책**을 위한 것이었습니다. 예를 들어 `AWS-GatherSoftwareInventory`는 Inventory가 사용하는 정책 문서입니다; State Manager는 데이터 수집을 위해 이를 적용할 수 있습니다. 일반적으로 AWS는 이제 정책을 강제하기 위해 명령이나 자동화 문서를 사용할 것을 권장하지만, 정책 유형 문서는 특정 목적을 위해 여전히 존재합니다(일반적으로 특정 상태를 보장하거나 정보를 수집함).

- **세션 문서:** **Session Manager**가 세션의 파라미터를 정의하는 데 사용됩니다. 예를 들어 `AWS-StartSSHSession`이나 `AWS-StartPortForwardingSession`은 어떤 종류의 Session Manager 연결이 수립되는지 제어하는 세션 문서입니다. 일반적으로 사용자가 편집하지 않습니다; AWS는 포트 포워딩, 대화형 셸 등의 기능을 지원하기 위해 이를 제공합니다.

- **패키지(Distributor) 문서:** **Distributor**의 패키지를 나타내며, 설치와 제거 지침을 포함하고 소프트웨어 페이로드와 연관됩니다. 예를 들어 패키지 문서는 사내 에이전트를 배포하기 위해 만들어질 수 있으며, 서로 다른 OS 플랫폼에서 해당 소프트웨어를 설치/제거하는 명령을 포함합니다.

- **자동화 및 변경 캘린더, CloudFormation 템플릿 등:** Incident Manager의 **사고 후 분석** 템플릿도 또 다른 유형이며, AWS AppConfig는 애플리케이션 구성 데이터를 저장하기 위해 특화된 문서 유형(`ApplicationConfiguration`과 `ApplicationConfigurationSchema`)을 사용합니다. AWS는 이러한 사용 사례를 위한 미리 정의된 문서를 제공합니다(예: 예정된 이벤트를 위한 변경 캘린더 문서, 버전 관리를 위한 CloudFormation 템플릿을 SSM 문서로).

### 7.2. 문서 생성과 버전 관리

콘솔(_Documents_ 편집기 사용), AWS CLI(`aws ssm create-document`), 또는 Infrastructure as Code(CloudFormation은 SSM 문서 생성을 지원함)를 통해 커스텀 SSM 문서를 만들 수 있습니다. 문서를 업데이트할 때마다 새 버전이 생성되어, 필요한 경우 테스팅과 롤백을 가능하게 합니다.

데이터베이스 백업 절차를 위한 중요한 자동화를 업데이트할 때, 버전 1을 프로덕션 기본값으로 유지하면서 문서의 버전 2를 출시할 수 있습니다. 비프로덕션 시스템에서 철저히 테스트한 후 최소한의 중단으로 프로덕션을 버전 2로 전환할 수 있습니다.

### 7.3. 계정 간 문서 공유

기본적으로 커스텀 SSM 문서는 AWS 계정에 비공개입니다. 다만 다른 AWS 계정과 문서를 공유하거나 심지어 퍼블릭으로 만들 수도 있습니다. **SSM 문서를 공유**하려면 특정 계정과 그 권한을 수정하고 접근이 허용된 AWS 계정 ID를 지정합니다.

## 8. AWS Systems Manager Parameter Store

Parameter Store는 AWS Systems Manager가 제공하는 구성 데이터와 시크릿을 위한 안전하고 계층적인 저장소입니다. 평문 구성 문자열, 데이터베이스 연결 문자열, 라이선스 키, 비밀번호, 기타 시크릿 같은 키-값 쌍을 저장하고 애플리케이션이나 스크립트에서 런타임에 검색할 수 있게 합니다.

### 8.1. 파라미터 유형과 계층 구조

Parameter Store 파라미터에는 **티어**와 **유형**이 있습니다. 두 가지 티어의 파라미터가 있습니다.

* **표준 파라미터:** 무료로 사용할 수 있으며, 계정당 최대 10,000개의 값을 지원하고, 값은 최대 4KB이며, 기본적으로 더 높은 처리량 한도를 갖습니다.
* **고급 파라미터:** 더 큰 값(최대 8KB)을 허용하고 (자동 만료나 순환하는 값 같은) 파라미터 정책 같은 추가 기능을 지원합니다. 고급 파라미터는 파라미터당 월별로 소액의 비용이 발생하며 10,000개 이상의 파라미터가 필요하거나 TTL 같은 메타데이터를 연결하고 싶을 때 유용할 수 있습니다. 기본 티어를 구성하거나 파라미터별로 지정할 수 있습니다; 파라미터가 고급이 되면 크기나 기능이 표준 한도를 초과하면 표준으로 되돌릴 수 없다는 점에 유의하세요.

파라미터를 생성할 때 **유형**에는 세 가지 주요 유형이 있습니다.

- **String:** 평문 값.
- **StringList:** 쉼표로 구분된 문자열 목록(IP 목록이나 배열 같은 구성에 유용).
- **SecureString:** 민감한 데이터를 위한 암호화된 값.

파라미터 이름에 슬래시(`/`) 구분자를 사용해 **계층 구조**로 배열할 수 있습니다. 이는 사실상 파라미터에 대한 디렉터리 같은 구조를 만듭니다. 예를 들어 `/Prod/DB/Password`와 `/Dev/DB/Password`를 두 개의 파라미터로 가질 수 있습니다. 계층 구조는 파라미터를 조직화하고 접근을 통제하는 데 도움을 줍니다. 경로 아래의 모든 파라미터를 검색하는 것 같은 대량 작업도 할 수 있습니다.

계층 구조는 몇 가지 한도를 강제합니다(최대 15단계 깊이, 각 단계는 슬래시로 구분). 이는 이름 충돌 가능성을 크게 줄이고 IAM 정책을 적용하기 더 쉽게 만듭니다 — 예를 들어 역할이 `/Dev/`로 접두사가 붙은 파라미터만 읽을 수 있도록 허용해 경로별로 접근 범위를 효과적으로 지정할 수 있습니다.
### 8.2. SecureString 파라미터

**SecureString** 파라미터는 민감한 데이터(비밀번호, 시크릿)를 암호화된 형태로 저장하는 데 사용됩니다. Parameter Store는 저장 시 SecureString 값을 암호화하기 위해 AWS Key Management Service(KMS)를 사용합니다. SecureString을 생성할 때는 Systems Manager를 위한 기본 AWS 관리형 키(계정에 자동으로 생성되며 일반적으로 `aws/ssm` KMS 키로 알려짐)를 사용하거나 암호화를 위한 자체 고객 관리형 KMS 키를 지정할 수 있습니다.

내부적으로 Parameter Store는 SecureString을 넣을 때 값을 암호화하고 검색 시 복호화하기 위해 KMS를 호출합니다. 표준 티어 SecureString(`<=4KB`)은 요청당 KMS 키로 직접 암호화되는 반면, 고급 티어 SecureString은 (더 큰 크기를 처리하고 키 사용을 추적하기 위해) AWS Encryption SDK를 통한 봉투 암호화 메커니즘을 사용합니다.

AWS는 **평문을 저장하지 않습니다**; 암호문과 메타데이터만 저장합니다. 즉, SecureString의 보안은 KMS와 연결되어 있습니다 — 적절한 역할만 복호화를 위해 KMS 키를 사용할 접근 권한을 갖도록 보장해야 합니다.

Parameter Store에는 자동 시크릿 순환이 없습니다(이를 위해서는 AWS Secrets Manager를 사용하거나 Lambda와 파라미터 정책을 통해 순환을 구현할 수 있습니다). 다만 SecureString에 파라미터 정책을 연결해 특정 시간 후 만료된 것으로 표시할 수 있으며, 이는 순환 전략의 일부가 될 수 있습니다(Lambda가 새 시크릿을 생성하고, 파라미터를 업데이트하고, 이전 것이 만료된 것으로 표시되는 것 등). 또한 Parameter Store 자체는 표준의 경우 무료이지만, **SecureString 사용은 암호화/복호화를 위한 API 호출에 대해 KMS 비용을 실제로 발생시킨다**는 점에 유의하세요(복호화가 포함된 각 GetParameter는 KMS 복호화 호출입니다).
### 8.3. 다른 서비스와의 통합

Parameter Store는 Lambda, CloudFormation, CodeBuild 등과 통합되어, 파라미터를 동적으로 참조할 수 있게 합니다.

**예시:**
CloudFormation 템플릿에서는 `{{resolve:ssm:parameter-name:version}}` 문법을 사용해 Parameter Store에 저장된 파라미터 값을 참조할 수 있습니다. 이를 통해 템플릿은 수동 업데이트 없이 최신 구성으로 배포할 수 있습니다.

## 9. AWS Systems Manager Run Command

**Run Command**는 SSH나 RDP를 통해 로그인할 필요 없이 관리형 인스턴스(EC2 인스턴스나 SSM에 등록된 온프레미스 서버)에서 원격으로 명령이나 스크립트를 실행할 수 있게 하는 AWS Systems Manager의 기능입니다. 임시 작업을 실행하기 위한 중앙화되고 안전한 방법을 제공합니다. 예를 들어 인스턴스 함대에서 서비스를 재시작하거나, 로그를 가져오거나, 빠른 구성 변경을 적용하는 데 Run Command를 사용할 수 있습니다.

Run Command는 각 인스턴스의 SSM Agent를 통해 작동하기 때문에 인바운드 포트를 열 필요가 없습니다 — 명령은 SSM 서비스와 에이전트의 안전한 채널을 통해 전송됩니다. 이는 프라이빗 서브넷에 있거나 방화벽 뒤에 있는 관리형 인스턴스에 특히 유용합니다. (Linux용 셸 명령, Windows용 PowerShell 등) **임시 스크립트**를 실행하거나 일련의 명령을 캡슐화하는 사전 정의된 SSM 문서를 사용할 수 있습니다.

이 기능은 EC2에만 국한되지 않습니다 — Systems Manager에서 _하이브리드 관리형 인스턴스_로 구성된 온프레미스 서버나 VM도 대상으로 할 수 있습니다. SSM 에이전트를 갖추고 계정에서 활성화된 후에는 그 인스턴스들이 EC2 인스턴스와 마찬가지로 Run Command 작업을 받을 수 있습니다. 이는 Run Command를 하이브리드 클라우드 관리 도구로 만듭니다.

### 9.1. 인스턴스 타겟팅

Run Command는 유연한 타겟팅을 제공합니다. **인스턴스 ID**, **태그**, 또는 **리소스 그룹**으로 특정 관리형 노드를 타겟팅할 수 있습니다. 가장 단순한 경우는 명령을 실행할 인스턴스 ID 목록을 지정하는 것입니다(적은 수의 알려진 인스턴스에 유용). 다만 대규모 또는 동적 환경의 경우 **태그**로 타겟팅할 수 있습니다 — 예를 들어 `App=WebServer` 태그를 가진 모든 인스턴스에서 명령을 실행합니다.

### 9.2. SSM 문서로 작업하기

명령을 실행할 때는 흔히 기존 SSM **문서**를 사용하게 됩니다. 임시 작업을 위한 일반적인 내장 문서는 `AWS-RunShellScript`(Linux용)나 `AWS-RunPowerShellScript`(Windows용)입니다. 이는 인스턴스에서 주어진 셸이나 PowerShell 명령을 단순히 실행하는 AWS가 제공하는 명령 유형 SSM 문서입니다. 예를 들어 모든 Linux 서버의 디스크 사용량을 수집하려면 `AWS-RunShellScript` 문서로 Run Command를 호출하고 명령을 전달할 수 있습니다: `df -h > /tmp/diskusage.txt`.

### 9.3. 모니터링과 로깅

Run Command는 각 명령 실행에 대한 상세한 피드백을 제공합니다. Systems Manager 콘솔에서는 각 대상 인스턴스에 대한 명령 호출 상태(예: 진행 중, 성공, 실패)를 볼 수 있습니다. 각 인스턴스에 대한 명령의 출력(stdout과 stderr)도 특정 크기 한도까지 볼 수 있습니다. 더 오래 실행되는 명령이나 더 큰 출력의 경우 S3나 CloudWatch 로깅을 활성화하는 것이 일반적입니다. 명령을 보낼 때는 출력이 업로드될 S3 버킷 이름과 접두사, 그리고/또는 출력을 스트리밍할 CloudWatch Logs 그룹을 지정하는 옵션이 있습니다. 구성되면 Systems Manager는 각 인스턴스의 명령 출력을 거의 실시간으로 S3 경로나 CloudWatch 로그로 전달합니다.

## 10. AWS Systems Manager Session Manager

Session Manager는 **SSH 키나 열린 인바운드 포트 없이도** EC2 인스턴스(와 온프레미스 관리형 인스턴스)에 안전하고 대화형인 셸 접근을 제공하는 AWS Systems Manager의 구성 요소입니다. Session Manager를 사용하면 AWS 콘솔이나 CLI에서 세션을 시작하고 SSM Agent를 통해 인스턴스에서 셸을 얻을 수 있습니다. 인스턴스의 보안 그룹에서 포트 22(SSH)나 RDP 포트를 열 필요가 없어, 공격 표면을 줄임으로써 보안 태세를 크게 개선합니다.

인증은 IAM을 통해 처리됩니다 — 즉, IAM 정책을 사용해 누가 인스턴스에 세션을 시작할 수 있는지 통제할 수 있으며, 모든 연결은 암호화되고 로깅됩니다. 이는 SSH 키 페어나 배스천 호스트를 관리할 필요를 없애줍니다. Session Manager는 또한 AWS 프라이빗 네트워크를 통해 작동하므로, SSM Agent를 갖추고 SSM 엔드포인트와 통신할 수 있는 한 퍼블릭 IP가 없는 인스턴스도(인터넷이나 VPC 엔드포인트를 통해) 도달할 수 있습니다.

워크플로 관점에서, Session Manager를 사용하려면 인스턴스의 IAM 역할이 적절한 SSM 세션 권한(관리형 정책 AmazonSSMManagedInstanceCore가 이를 포함함)을 가지고 있고 사용자/역할이 세션을 시작할 권한(인스턴스에 대한 ssm:StartSession)을 가지고 있는지 확인하세요.

### 10.1. 세션 시작과 관리

**AWS Systems Manager 콘솔**(브라우저 기반 터미널을 엽니다)을 통해서나 **AWS CLI**/PowerShell(Session Manager Plugin을 사용해 터미널에서 로컬 SSH와 유사한 경험을 만듭니다)을 통해 세션을 시작할 수 있습니다. 콘솔에서는 _Session Manager_로 이동해 접근 권한이 있는 인스턴스 목록을 보고 "Start session"을 클릭합니다 — 터미널 인터페이스가 있는 새 브라우저 탭이 열립니다. 이는 명령을 실행할 수 있는 대화형 셸입니다. 여러 세션을 동시에 열 수 있습니다. 조직이 AWS Console에 싱글 사인온을 사용한다면, 콘솔 로그인과 IAM 정책만으로 서버에 접근할 수 있다는 것을 의미합니다 — 별도의 키나 VPN이 필요 없습니다.

**세션 관리** 기능에는 콘솔에서 **세션을 종료**하는 능력도 포함됩니다. 무단이거나 오래 실행되는 세션을 발견하면 적절한 권한을 가진 관리자가 이를 종료할 수 있습니다. 콘솔에서나 `aws ssm describe-sessions`로 모든 활성 세션을 나열하고 누가 연결되어 있는지 감사할 수 있습니다. 모든 세션 시작/종료는 CloudTrail 이벤트를 생성하므로 _누가 어떤 인스턴스에 언제 연결했는지_에 대한 감사 추적을 가집니다. 이는 규정 준수("모든 대화형 접근이 로깅됨")에 도움이 됩니다.

### 10.2. 포트 포워딩과 SSH 통합

Session Manager는 대화형 셸 세션에만 국한되지 않습니다; **포트 포워딩**도 지원하며 필요한 경우 전통적인 SSH를 위한 프록시로도 사용할 수 있습니다. 포트 포워딩은 Session Manager 연결을 통해 원격 인스턴스의 포트로 트래픽을 안전하게 터널링할 수 있게 합니다. 예를 들어 프라이빗 서브넷의 EC2 인스턴스에서 데이터베이스가 실행 중이라고 가정해보세요. Session Manager를 사용해 로컬 포트(예: localhost:5432)를 데이터베이스의 포트(인스턴스의 5432)로 터널링하는 포트 포워딩 세션을 설정할 수 있으며, DB 서버를 퍼블릭하게 노출하지 않습니다.

**실제 예시:**
개발자가 프라이빗 서브넷의 데이터베이스에 연결해야 합니다. 직접 연결을 여는 대신 Session Manager의 포트 포워딩을 사용해 localhost에서 데이터베이스에 안전하게 접근함으로써 데이터베이스가 퍼블릭 인터넷으로부터 격리된 상태를 유지하도록 보장합니다.

## 11. AWS Systems Manager Automation

**Systems Manager Automation**은 복잡한 운영 작업을 자동화된 워크플로(_런북_이라고 불림)로 조율할 수 있게 하는 기능입니다. 본질적으로 IT 프로세스나 유지보수 작업을 반복 가능하고 감사 가능한 시퀀스로 인코딩하는 방법입니다.

Automation의 일반적인 사용 사례는 다음을 포함합니다.

* **일상적인 유지보수:** 예를 들어 순서대로 서버 함대를 재시작하거나 정기적인 EBS 스냅샷 촬영
* **AMI 패치와 업데이트:** Automation은 임시 인스턴스를 시작하고, 업데이트하고, AMI를 생성함으로써 "골든" 이미지를 만들 수 있습니다 — 모두 자동으로
* **사고 개선:** 비정상적인 인스턴스를 자동으로 재시작하거나 특정 알람이 트리거될 때 리소스를 정리하는 것 같은
* **일반적으로 사람의 개입이나 여러 스크립트를 순서대로 실행하는 것이 필요한 다른 다단계 워크플로**

Automation은 흔히 일반적인 IT 작업을 위한 "무인" 운영이나 **셀프 서비스**를 가능하게 하는 것으로 설명됩니다. 예를 들어 개발자에게 직접 접근을 부여하지 않고도 개발 환경을 설정하거나 서비스를 재설정하는 사전 정의된 자동화를 트리거할 수 있는 권한을 부여할 수 있습니다 — 자동화 런북이 통제된 방식으로 이를 수행합니다.

### 11.1. 자동화 워크플로 생성하기

자동화 워크플로는 일련의 단계를 포함하는 **자동화 문서**(런북이라고도 불림)로 정의됩니다. 각 단계는 특정 Systems Manager **자동화 작업 유형**(예를 들어 스크립트 실행, AWS API 호출, 승인 대기 등)을 사용해 작업을 수행합니다. 커스텀 런북을 만들려면 자동화 문서 스키마를 따라 YAML이나 JSON으로 작성할 수 있습니다. AWS는 또한 원시 JSON을 작성하지 않고도 이를 구축하는 데 도움이 되는 "Automation Document Builder"(그리고 콘솔의 더 새로운 **시각적 워크플로 디자이너**)도 제공합니다.

런북을 설계할 때는 `mainSteps` 섹션 내의 단계로 절차를 나눕니다. 각 단계는 이름, 작업(`aws:runCommand`, `aws:executeAwsApi`, `aws:waitForResourceSignal`, `aws:approve` 등), 해당 작업을 위한 파라미터, 선택적 출력을 가집니다.

### 11.2. AWS 서비스와의 통합

Automation은 EventBridge, CloudWatch, 또는 Config로부터의 이벤트에 의해 트리거될 수 있으며, 커스텀 작업을 위해 Lambda 함수도 호출할 수 있습니다.

## 12. AWS Systems Manager State Manager

**State Manager**는 인스턴스(그리고 일부 다른 리소스)를 **원하는 상태**로 유지하는 프로세스를 자동화하는 Systems Manager 기능입니다. 본질적으로 _구성 기준선이나 정책_을 (_연관_이라고 불리는 SSM 문서를 사용해) 정의하면 State Manager는 인스턴스가 이 설정을 지속적으로 충족하도록 보장하며, 드리프트가 감지되면 개선을 적용합니다.

이는 Chef/Puppet이나 Ansible 같은 구성 관리 도구와 pull 모드에서 유사합니다 — 하지만 변경을 적용하기 위해 SSM Agent를 사용합니다. 일반적인 사용 사례로는 특정 소프트웨어가 설치되어 있는지(또는 설치되어 있지 않은지) 확인하거나, 특정 설정이나 서비스가 구성되어 있는지 확인하거나, 규정 준수를 강제하기 위해 스크립트가 일정에 따라 실행되는지 확인하는 것이 있습니다. 예를 들어 "Amazon SSM Agent가 모든 인스턴스에서 실행 중이고 최신 상태여야 한다"나 "커스텀 모니터링 에이전트가 모든 서버에 존재하고 부팅 시 시작되어야 한다"는 기준선을 가질 수 있습니다. State Manager를 사용하면 에이전트를 주기적으로 확인/설치하는 문서를 실행하는 **연관**을 만듦으로써 이를 강제할 수 있습니다.

### 12.1. 연관 문서

State Manager의 **연관**은 본질적으로 특정 파라미터와 일정을 가진 대상 집합에 문서를 연결하는 것입니다. 문서는 일반적으로 명령 문서나 자동화 문서일 수 있습니다. AWS는 특히 **소프트웨어가 설치되고 실행 중인지 보장하는 것** 같은 것에 State Manager를 사용할 것을 명시적으로 언급합니다.

예를 들어 "안티바이러스가 모든 인스턴스에 설치되고 실행 중이어야 한다"는 고전적인 요구 사항입니다. 다음을 통해 이를 충족할 수 있습니다.

- AV의 존재를 확인하고 없으면 설치하고, 중지되어 있으면 서비스를 시작하는 SSM 문서를 사용합니다.
- 해당 문서를 모든 인스턴스(또는 특정 유형/태그의 모든 인스턴스)에 연결해 아마도 매시간 또는 인스턴스가 시작될 때 실행되도록 합니다.

### 12.2. 예약 및 이벤트 기반 연관

State Manager는 cron 작업과 마찬가지로 cron이나 rate 표현식을 사용한 유연한 예약을 허용합니다. 고정 간격(시간별, 일별 등)이나 특정 일정(예: "매주 일요일 오전 2시")으로 연관을 실행할 수 있습니다. 기본적으로 새 연관을 생성하면 State Manager는 즉시 적용한 다음 설정한 간격으로 적용할 수 있습니다.

EventBridge 통합을 사용해 **이벤트 기반 연관**을 만들 수도 있습니다. 예를 들어 State Manager는 특정 이벤트(인스턴스 시작 등)에 반응할 수 있습니다. 실제로 한 가지 미묘한 기능이 있습니다: 연관에 대해 "trigger type"을 `OnBoot`으로 설정할 수 있어(에이전트를 통해), 인스턴스가 부팅될 때마다 문서가 실행됩니다(시작 시 기준선 보장). 추가로 언급한 대로 EventBridge는 자동화를 트리거할 수 있습니다(State Manager와 함께, 일반적으로 이벤트보다는 SM 내에서 직접 cron 일정을 사용하지만, 유사한 강제 작업을 수행하는 자동화를 시작하는 데 이벤트를 사용할 수 있습니다).

## 13. Systems Manager Patch Manager

**Patch Manager**는 EC2 인스턴스나 온프레미스 관리형 인스턴스에서 운영체제(와 일부 애플리케이션)를 패치하는 프로세스를 자동화하는 Systems Manager 기능입니다. **패치 기준선**을 정의할 수 있게 합니다 — 본질적으로 어떤 패치가 승인되거나 거부되는지 결정하는 규칙과 목록입니다 — 그런 다음 온디맨드로나 (흔히 Maintenance Windows를 통해) 일정에 따라 패치를 적용해 인스턴스를 보안 및 중요 업데이트로 최신 상태로 유지합니다.

일반적인 패치 관리 전략은 심각도나 중요도에 따라 패치를 분리하는 것을 포함합니다. 예를 들어 중요한 보안 패치는 가능한 한 빨리 자동 승인하면서 덜 중요한 업데이트는 테스트를 위해 지연시킬 수 있습니다. Patch Manager는 자동 승인 지연을 지정할 수 있게 함으로써 이를 촉진합니다(예: 중요한 업데이트는 0일 후, 다른 것은 7일 후 승인).

### 13.1. 패치 기준선과 그룹

**패치 기준선**은 주어진 OS에 설치가 승인된 패치를 결정하는 일련의 패치 규칙과 목록입니다. AWS는 사용하거나 복제할 수 있는 각 OS(Amazon Linux, Ubuntu, Windows 등)에 대한 기본 기준선을 제공합니다. 이들은 일반적으로 기본적으로 특정 시간 후 중요하고 보안 관련 패치를 자동 승인합니다. 더 많은 통제를 위해 **커스텀 패치 기준선**을 만들 수 있습니다.

Patch Manager는 서로 다른 서버에 서로 다른 기준선을 쉽게 할당할 수 있게 하는 **패치 그룹** 개념을 가지고 있습니다. **패치 그룹**은 단순히 인스턴스에 붙이는 태그(태그 키 `Patch Group`이나 `PatchGroup`)로, 패치를 위해 이들에 레이블을 붙입니다. 예를 들어 일부 인스턴스에는 `Patch Group=ProdServers`를, 다른 인스턴스에는 `Patch Group=DevServers`를 태깅합니다. 패치 기준선 설정에서는 패치 그룹에 기준선을 등록할 수 있습니다(예: "Prod 기준선"이 `ProdServers` 그룹에 적용됨). Patch Manager가 실행되면 어떤 기준선을 사용할지 결정하기 위해 인스턴스의 Patch Group 태그를 확인합니다. 이 메커니즘은 **올바른 패치가 올바른 노드 집합에 적용되도록** 보장합니다. 또한 dev용 기준선으로 실수로 prod를 패치하는 것도 방지합니다. AWS는 환경과 일정을 분리하기 위해 패치 그룹을 사용할 것을 강조합니다.

### 13.2. 스캐닝과 패치 워크플로

Patch Manager는 두 가지 주요 작업을 지원합니다: **스캔**과 **설치**(때때로 "스캔 후 설치"라고 불림). **스캔** 작업은 인스턴스의 SSM 에이전트가 기준선의 어떤 패치가 인스턴스에서 누락되었는지 확인하고 규정 준수를 보고한다는 것을 의미합니다(하지만 실제로 아무것도 설치하지 않습니다). 이는 시스템을 변경하지 않고도 패치 규정 준수 보고서를 얻는 데 유용합니다. **패치 스캔**은 누락된 패치 목록을 출력하고 Patch Manager의 뷰에서 인스턴스를 규정 준수 또는 규정 미준수로 표시합니다.

**설치** 작업은 실제로 누락된 승인된 패치를 다운로드하고 인스턴스에 설치한 다음 필요한 경우 재부팅합니다(재부팅 동작을 제어할 수 있습니다: 기본적으로 Windows는 필요하면 재부팅할 수 있습니다; Linux에서는 많은 Linux 업데이트가 즉시 재부팅을 강제하지 않기 때문에 지시하지 않는 한 자동으로 재부팅하지 않을 수 있습니다 — 하지만 커널 업데이트는 전체 효과를 위해 재부팅이 필요합니다). Patch Manager는 결과를 로깅하며, 설치 후에는 일반적으로 규정 준수 정보를 업데이트하기 위해 스캔을 수행합니다.

## 14. AWS Systems Manager Distributor

**Distributor**는 소프트웨어나 스크립트를 패키징해 대규모로 관리형 인스턴스에 배포할 수 있게 하는 Systems Manager 기능입니다. SSM Agent가 사용할 수 있는 자체 소프트웨어 저장소와 설치 프로그램을 만드는 AWS의 메커니즘으로 생각하세요. Distributor를 사용하면 설치 지침과 함께 소프트웨어를 ZIP이나 TAR로 번들링한 다음, Systems Manager(State Manager나 Run Command를 통해)를 사용해 함대에 이 패키지를 푸시하고 설치할 수 있습니다.

일반적인 사용 사례에는 에이전트(예: 보안 에이전트, 모니터링 에이전트), 내부 도구, 또는 인스턴스에 일관되게 롤아웃하고자 하는 스크립트 배포가 포함됩니다. 예를 들어 AWS 자체가 AmazonCloudWatchAgent 같은 패키지를 제공하기 위해 Distributor를 사용합니다(CloudWatch 에이전트는 Distributor 패키지로 사용할 수 있어 인스턴스에서 쉽게 설치/업데이트할 수 있습니다).

Distributor는 소프트웨어의 **버전 관리**에 도움을 줍니다. 소프트웨어를 설치하기 위해 단순히 임의의 스크립트를 실행하는 대신, 이름과 버전 번호를 가진 패키지를 만듭니다.
### 14.1. 패키지 생성과 배포

패키지를 만들려면 매니페스트와 필요한 스크립트와 함께 소프트웨어를 ZIP 파일로 번들링합니다. 이 패키지는 안전하게 저장되며 여러 플랫폼에 걸쳐 버전 관리되고 배포될 수 있습니다.
### 14.2. 버전 관리와 검증

Distributor는 게시하는 각 패키지의 **버전**을 본질적으로 관리합니다. 버전을 추가할 때마다 시스템은 이전 버전을 (삭제하지 않는 한) 계속 사용 가능하게 유지합니다 — 특정 인스턴스에 어떤 버전을 설치할지 선택할 수 있습니다. 기본적으로 버전을 지정하지 않고 "패키지 X 설치"라고만 말하면 최신 승인된 버전을 가져옵니다. 또는 특정 버전을 지정해 고정할 수 있습니다.

## 15. AWS Systems Manager Maintenance Windows

Maintenance Windows는 정의된 기간 동안 (패치나 백업 같은) 작업을 예약할 수 있게 합니다. 예를 들어 한 소매업체는 비피크 시간인 매주 일요일 오전 3시에 모든 서버를 패치하는 Maintenance Window를 예약합니다. 이는 영업 시간 동안 고객 거래를 방해하지 않으면서 중요한 업데이트가 적용되도록 보장합니다.

### 15.1. 작업 우선순위와 동시성

Maintenance Window 내에서 작업은 시스템 과부하를 피하기 위해 우선순위가 매겨지고 동시성이 제한됩니다. 예를 들어 예약된 백업 창 동안 한 회사는 먼저 서버 팜에서 트래픽을 배출한 다음 백업 스크립트를 실행하고 마지막으로 서버를 다시 온라인 상태로 전환하는 작업을 설정합니다. 동시성을 통제함으로써 특정 시점에 서버의 일부만 오프라인 상태가 되도록 보장해 서비스 가용성을 유지합니다.

### 15.2. Run Command와 Automation과의 통합

Maintenance Windows는 Run Command, Automation, Lambda, 또는 Step Functions에 정의된 작업을 실행합니다. 이 통합은 복잡하고 순차적인 워크플로를 자동화하고 예약할 수 있게 합니다.

## 16. 구성 규정 준수

규정 준수는 Patch Manager와 State Manager의 데이터를 중앙화된 대시보드로 집계합니다.

![ssm-compliance](@site/docs/Management%20and%20Governance/_assets/ssm-compliance.png)

### 16.1. 규정을 준수하지 않는 리소스 개선하기

규정 준수 모니터링의 목표는 일반적으로 무언가 규정을 준수하지 않을 때 개선을 트리거하는 것입니다. 개선은 State Manager 연관, Maintenance Windows, 또는 Automation 런북을 사용해 달성됩니다.

**규정 준수 UI**에서 인스턴스가 패치에 대해 규정을 준수하지 않으면 콘솔은 흔히 "지금 패치" 또는 "개선"이라는 버튼을 제공합니다. 마찬가지로 연관 규정 미준수의 경우 연관으로 이동하거나 즉시 실행할 수 있습니다. 솔루션 아키텍트는 규정 준수 데이터를 CI/CD나 CMDB 파이프라인에 통합할 수도 있습니다. 예를 들어 인스턴스가 X시간 넘게 규정을 준수하지 않은 채로 남아 있으면 에스컬레이션하는 등입니다.

## 17. AWS Systems Manager OpsCenter

**OpsCenter**는 다양한 소스로부터의 운영 문제(OpsItem이라고 불림)를 집계하고 표준화해 IT 엔지니어를 위한 하나의 창으로 만드는 Systems Manager의 구성 요소입니다.

이는 본질적으로 여러 AWS 서비스로부터의 알림과 문제를 볼 수 있고 그 생명주기(조사 -> 개선 -> 해결)를 관리할 수 있는 운영 대시보드입니다. OpsCenter는 한 곳에서 맥락과 도구를 제공함으로써 평균 해결 시간을 줄이도록 설계되었습니다. 예를 들어 CloudWatch 알람, Config 규칙 위반, Security Hub 발견 사항, 그리고 Systems Manager 자체(규정 준수나 자동화 실패 같은)가 모두 OpsCenter에서 OpsItem을 만들 수 있습니다. CloudWatch, Config 등 사이를 오가는 대신 OpsCenter는 세부 사항이 있는 문제 목록을 보여주며, 각 OpsItem에 대해 **맥락 데이터**를 가져옵니다: 관련된 리소스에 대한 정보, 관련 AWS Config 변경, CloudTrail 로그, CloudWatch 지표 그래프, 심지어 관련 런북이나 과거 유사한 OpsItem에 대한 링크까지 포함합니다.


![ssm-ops-center](@site/docs/Management%20and%20Governance/_assets/ssm-ops-center.png)

### 17.1. OpsItem 생성과 관리하기

**OpsItem**은 OpsCenter에서 단일 운영 문제나 이벤트를 나타내는 객체입니다. 일반적으로 대부분의 OpsItem을 수동으로 생성하지는 않습니다; 트리거나 다른 서비스에 의해 생성됩니다. 다만 필요하다면(예를 들어 자동으로 탐지되지 않은 것을 추적하기 위해) 수동으로 만들 수 있습니다.

### 17.2. Automation과의 통합

이미 언급했듯이 OpsCenter는 개선을 위해 SSM Automation과 크게 통합됩니다. **OpsCenter가 제안하는 런북**을 사용하거나 심지어 일부 OpsItem이 자동으로 개선되도록 **OpsItem을 Automation과 연관**시키는 것이 일반적입니다. 후자의 경우, 자동화를 충분히 신뢰한다면 이론적으로 이벤트가 도착하는 즉시 EventBridge가 자동화를 트리거하도록 하고, 자동화가 실패한 경우에만 OpsItem을 생성할 수 있습니다. 하지만 인간을 루프에 넣고 싶다면 OpsCenter와 수동 런북 실행이 더 낫습니다.

## 18. Incident Manager

AWS Incident Manager(Systems Manager의 일부)는 탐지부터 사고 후 분석까지 사고 생명주기를 자동화함으로써 중요한 사고에 대한 대응을 간소화합니다. 다음은 그 워크플로에 대한 개요입니다.

- **탐지:** 대응 계획에 연결된 고심각도 알림(예: CloudWatch 알람, EventBridge 이벤트)으로부터 자동으로 사고를 트리거하거나, 운영 엔지니어가 수동으로 사고를 선언할 수 있게 합니다.
- **대응자 참여:** 사전 정의된 에스컬레이션 계획에 따라 여러 채널(전화, SMS, 이메일, Slack/Chime)을 통해 즉시 대기 중인 대응자에게 알립니다. PagerDuty와 유사합니다.
- **협업:** 실시간 협업을 위해 자동으로 "War Room"(예: Slack 채널이나 Chime 브리지)을 설정하며, 모든 통신이 기록됩니다.
- **런북을 통한 완화:** 사고 시작 시 로그 수집, 서버 확장, 또는 페일오버 같은 작업을 수행하기 위해 자동화 런북을 실행하며, 진행 상황은 사고 타임라인에서 추적됩니다.
- **타임라인 추적:** 대응자에게 정보를 제공하고 사고 후 분석을 지원하기 위해 핵심 이벤트(탐지, 알림, 런북 실행, 메모, 해결)를 기록합니다.
- **해결과 종료:** 자동화된 런북과 수동 작업을 모두 사용해 대응자가 문제를 완화하는 데 도움을 준 다음 사고를 해결됨으로 표시하고 MTTR 같은 지표를 계산합니다.
- **사고 후 분석:** 타임라인, 근본 원인 분석, 후속 조치를 갖춘 사후 보고서 작성을 안내하며, 향후 개선을 위해 인사이트를 저장합니다.
- **지속적인 개선:** 대응 시간과 일반적인 실패 패턴에 대한 인사이트를 제공해 대기 일정을 개선하고 런북을 업데이트합니다.

전반적으로 Incident Manager는 알림, 페이징, 협업, 자동화를 AWS에 직접 통합해, AWS 생태계 내에서 전용 사고 관리 도구와 유사한 기능을 제공합니다.

### 18.1. 사고 대응 계획 생성하기

대응 계획은 사고 심각도, 트리거 알람, 에스컬레이션 경로, 알림 채널, 연관된 자동화 런북을 정의합니다. 사전 구성된 계획은 사고가 발생할 때 참여부터 완화까지 모든 단계가 가능한 한 자동화되도록 보장합니다.

예를 들어 금융 서비스 회사는 서비스 중단에 대한 사고 대응 계획을 만듭니다. 이 계획은 서비스가 다운되면 Incident Manager가 즉시 대기 팀을 참여시키고, 전용 채팅 채널을 만들고, 트래픽을 페일오버하는 런북을 실행한다는 것을 지정합니다 — 모든 작업이 SSM Agent를 갖춘 인스턴스에서 수행됩니다.

### 18.2. 사고 후 분석

사고를 해결한 후 Incident Manager는 배운 교훈을 캡처하고 향후 대응을 개선하기 위해 구조화된 사고 후 분석을 촉진합니다. (SSM Agent를 통해 실행된 자동화 런북 결과를 포함해) 수집된 타임라인과 데이터는 이 분석에 매우 중요합니다.

## 19. 모범 사례 요약

- Resource Groups와 패치/유지보수 타겟팅을 활용하기 위해 리소스를 일관되게 태깅하세요.
- 관리 작업을 코드화하기 위해 SSM Documents를 사용하고, 적절히 공유/버전 관리하세요.
- 시크릿/구성을 Parameter Store에 저장하고 이를 참조하세요 — 하드코딩을 피하세요.
- 더 나은 보안과 감사를 위해 SSH/RDP 대신 Run Command와 Session Manager를 사용하세요.
- 핵심 구성을 강제하기 위해 State Manager를 사용하세요(예: 중요한 서비스가 항상 실행 중인지 보장).
- 서버를 안전하게 유지하기 위해 적절한 기준선과 유지보수 창을 갖춘 Patch Manager를 설정하세요.
- 모든 인스턴스가 필요한 도구를 갖추도록 표준 소프트웨어(에이전트 등)를 롤아웃하기 위해 Distributor를 사용하세요.
- 사람의 실수를 줄이고 안전한 시간에 발생하도록 임시가 아닌 Maintenance Windows로 일상적인 작업(백업, 패치)을 예약하세요.
- 규정 준수 대시보드를 정기적으로 확인하거나 규정 미준수에 대한 알림을 설정하고, 규정 준수를 보안 운영(예: Security Hub)과 통합하세요.
- 더 작은 문제에 대한 중앙 분류로 OpsCenter를 사용하세요(필요에 따라 기존 티켓 시스템과 통합).
- 주요 중단의 경우 Incident Manager 계획을 정의하세요: 누구를 호출할지, 어떤 자동화를 실행할지, 어떤 채팅에 모일지. 게임 데이나 시뮬레이션을 통해 이 계획들을 테스트하세요. 연락처와 런북이 최신 상태인지 확인하세요. 실제 사고 후에는 모니터링, 런북 업데이트, 또는 새로운 자동화 추가나 일정 조정에 교훈을 반영하세요.
- 근본 원인과 예방 조치를 식별하기 위해 Incident Manager나 다른 방법을 통해 사고 후 분석(이상적으로는 비난 없는 사후 분석)을 수행하세요.
- SSM 작업을 보안화하세요: 모든 SSM 작업에 최소 권한 IAM 역할을 사용하세요(예를 들어 승인된 문서만 실행되도록 Run Command를 제한하고, 누가 인스턴스를 종료하거나 패치를 업데이트할 수 있는지 제한하는 등). 변경을 감사하기 위해 로깅(CloudTrail, 세션 로그)을 사용하세요.

## 20. 결론

AWS Systems Manager는 클라우드와 온프레미스 환경에 대한 강화된 가시성과 통제를 원하는 모든 조직을 위한 강력한 솔루션입니다. 서버 함대 패치부터 안전한 인스턴스 접근과 운영 사고의 중앙화된 관리까지, 운영을 간소화하는 데 필수적인 역할을 합니다.
