# Amazon EKS

## 1. 소개

Amazon EKS는 AWS에서 Kubernetes를 사용하는 컨테이너화된 애플리케이션의 배포, 관리, 확장을 단순화하도록 설계된 완전관리형 Kubernetes 서비스입니다. 인증된 Kubernetes 준수 서비스이므로 코드를 수정할 필요 없이 표준 Kubernetes 애플리케이션을 실행할 수 있습니다. EKS는 확장성, 가용성, 패치를 포함해 Kubernetes 컨트롤 플레인 운영의 복잡함을 처리해주므로 애플리케이션 구축에 집중할 수 있습니다.

## 2. Amazon EKS의 일반적인 사용 사례

Amazon EKS는 광범위한 컨테이너화된 애플리케이션 시나리오를 다루도록 설계되었습니다.

### 2.1. 애플리케이션과 마이크로서비스 아키텍처 현대화

- **컨테이너화와 분리:**
    EKS를 사용하면 모놀리식 애플리케이션을 더 작고 독립적인 마이크로서비스로 분해해 개발, 배포, 확장이 더 쉬워집니다. 이 컨테이너화된 접근 방식은 팀이 전체 시스템에 영향을 주지 않고 개별 서비스를 업데이트하고 배포할 수 있게 해줍니다.

- **복원력과 확장성:**
    Kubernetes의 오케스트레이션 기능을 활용하면 장애로부터 자동으로 복구되고 수요에 따라 수평으로 확장되는 시스템을 설계할 수 있습니다. 이는 고가용성과 내결함성이 필요한 애플리케이션에 특히 중요합니다.

### 2.2. 배치 처리와 머신 러닝 워크로드

- **효율적인 리소스 관리:**
    Kubernetes는 배치 처리 작업을 위한 강력한 스케줄링 기능을 제공해, 데이터 처리와 머신 러닝 작업에 이상적인 플랫폼이 됩니다. 작업을 병렬로 실행하고 비용과 성능을 최적화하기 위해 리소스 할당을 자동으로 관리할 수 있습니다.

- **데이터 서비스와의 통합:**
    EKS는 AWS 데이터 저장 및 분석 서비스(Amazon S3와 Amazon EMR 등)와 원활하게 통합되어 복잡한 데이터 파이프라인과 머신 러닝 워크플로를 더 쉽게 구축하고 확장할 수 있습니다.

### 2.3. 지속적 통합과 지속적 배포(CI/CD)

- **동적이고 임시적인 환경:**
    EKS는 현대적인 CI/CD 파이프라인에 매우 적합합니다. Kubernetes를 사용하면 테스트를 실행하고 빌드를 배포하기 위한 임시적이고 격리된 환경을 즉시 만들 수 있습니다. 이는 각 변경 사항이 프로덕션과 유사한 환경에서 승격되기 전에 테스트되도록 보장합니다.

- **자동화와 확장성:**
    (CodePipeline과 CodeBuild 같은) AWS 서비스와 (Jenkins나 GitLab 같은) 인기 있는 서드파티 도구와 통합함으로써 소프트웨어 전달 프로세스를 자동화하고 빌드 및 테스트 인프라를 효율적으로 확장할 수 있습니다.

### 2.4. 하이브리드와 멀티 클라우드 배포

- **환경 전반의 일관성:**
    EKS는 온프레미스, 하이브리드, 멀티 클라우드 환경 전반에서 컨테이너화된 워크로드를 관리하는 중앙 플랫폼 역할을 할 수 있습니다. 이 일관성은 조직이 완전한 재작성 없이 애플리케이션을 현대화할 수 있게 해주어, 환경 간 더 원활한 전환을 가능하게 합니다.

- **원활한 통합:**
    Kubernetes의 기본 인프라 추상화는 EKS와 다른 Kubernetes 환경에서 유사한 워크로드를 실행할 수 있음을 의미합니다. 이 유연성은 특정 워크로드는 온프레미스에 남아 있고 다른 워크로드는 클라우드로 이동하는 시나리오를 지원합니다.

### 5. AWS Fargate를 사용한 서버리스 컨테이너 배포

- **인프라 관리 불필요:**
    EKS와 AWS Fargate의 통합을 사용하면 EC2 인스턴스를 관리하지 않고도 컨테이너를 실행할 수 있습니다. 이 서버리스 컴퓨팅 모델은 가변적이거나 예측할 수 없는 리소스 요구가 있는 워크로드에 특히 유용해, 기본 인프라 관리의 운영 오버헤드와 복잡함을 줄여줍니다.
    
- **비용 효율성과 단순함:**
    EKS와 함께 Fargate를 사용하면 사용한 컴퓨팅 시간에 대해서만 비용을 지불할 수 있어, 많은 프로덕션과 개발 시나리오에서 비용 효율적인 옵션이 됩니다.

## 3. 실제로 작동하는 Kubernetes

아래 다이어그램은 Kubernetes 클러스터를 생성하고 사용하기 위해 Kubernetes 관리자나 애플리케이션 개발자로서 수행할 핵심 활동을 보여줍니다. 이 과정에서 기본 클라우드 제공자의 예로 AWS 클라우드를 사용해 Kubernetes 구성 요소들이 서로 어떻게 상호 작용하는지 보여줍니다.

![kubernetes-in-action](@site/docs/Containers/_assets/kubernetes-in-action.png)

Kubernetes 관리자는 클러스터가 구축될 제공자 유형에 특화된 도구를 사용해 Kubernetes 클러스터를 생성합니다. 이 예시는 관리형 Kubernetes 서비스인 Amazon EKS를 제공하는 AWS 클라우드를 제공자로 사용합니다. 관리형 서비스는 클러스터를 위한 두 개의 새로운 Virtual Private Cloud(Amazon VPC) 생성, 네트워킹 설정, 클라우드 자산 관리를 위해 새 VPC에 Kubernetes 권한을 직접 매핑하는 것을 포함해 클러스터를 생성하는 데 필요한 리소스를 자동으로 할당합니다. 관리형 서비스는 또한 컨트롤 플레인 서비스가 실행될 위치를 확보하고 워크로드 실행을 위한 Kubernetes 노드로 0개 이상의 Amazon EC2 인스턴스를 할당합니다. AWS는 컨트롤 플레인을 위해 하나의 Amazon VPC를 직접 관리하고, 다른 VPC에는 워크로드를 실행하는 고객 노드가 포함됩니다.

Kubernetes 관리자의 향후 많은 작업은 `kubectl` 같은 Kubernetes 도구를 사용해 수행됩니다. 그 도구는 클러스터의 컨트롤 플레인에 직접 서비스 요청을 보냅니다. 클러스터에 쿼리하고 변경하는 방식은 어떤 Kubernetes 클러스터에서든 하는 방식과 매우 유사합니다.

이 클러스터에 워크로드를 배포하려는 애플리케이션 개발자는 여러 작업을 수행할 수 있습니다. 개발자는 애플리케이션을 하나 이상의 컨테이너 이미지로 빌드한 다음, 그 이미지들을 Kubernetes 클러스터가 접근할 수 있는 컨테이너 레지스트리에 푸시해야 합니다. AWS는 이 목적을 위해 Amazon Elastic Container Registry(Amazon ECR)를 제공합니다.

애플리케이션을 실행하기 위해 개발자는 레지스트리에서 어떤 컨테이너를 가져올지, 그 컨테이너들을 Pod로 어떻게 감쌀지를 포함해 클러스터에 애플리케이션 실행 방법을 알려주는 YAML 형식의 구성 파일을 만들 수 있습니다. 컨트롤 플레인(스케줄러)은 컨테이너를 하나 이상의 노드에 스케줄링하고, 각 노드의 컨테이너 런타임이 실제로 필요한 컨테이너를 가져와 실행합니다. 개발자는 또한 각 노드에서 실행 중인 사용 가능한 컨테이너로 트래픽을 분산하기 위해 애플리케이션 로드 밸런서를 설정하고, 애플리케이션을 퍼블릭 네트워크에서 외부 세계에 사용 가능하도록 노출할 수 있습니다. 이 모든 것이 완료되면 애플리케이션을 사용하려는 사람이 애플리케이션 엔드포인트에 연결해 접근할 수 있습니다.

## 4. 워커 노드

![eks-workers](@site/docs/Containers/_assets/eks-workers.png)

- **EC2와 Fargate 옵션:** Kubernetes 워커 노드를 (관리형 노드 그룹을 사용해) Amazon EC2 인스턴스에서 실행하거나, 기본 인프라 관리를 추상화하는 AWS Fargate로 서버리스 컴퓨팅을 선택할 수 있습니다.
- **AWS 서비스와의 통합:** 워커 노드는 네트워킹을 위한 Amazon VPC, 인증과 권한 부여를 위한 AWS IAM, 스토리지를 위한 Amazon EBS 같은 다른 AWS 서비스와 원활하게 통합됩니다.

## 5. Amazon EKS Distro

Amazon Elastic Kubernetes Service(EKS)는 AWS가 빌드하고 유지 관리하는 Kubernetes 배포판인 Amazon EKS Distro를 사용합니다. Amazon EKS Distro는 신뢰할 수 있고 안전한 클러스터를 더 쉽게 만들 수 있게 해줍니다.

![eks-distro](@site/docs/Containers/_assets/eks-distro.png)

**사용 사례:**

* **온프레미스와 클라우드에서 일관되게 배포**
	Amazon EKS를 구동하는 것과 동일한 안전하고, 검증되고, 테스트된 Kubernetes 구성 요소를 AWS, 온프레미스, 다른 클라우드의 자체 관리형 인프라 내에서 실행합니다.

* **온프레미스 애플리케이션 현대화**
	업스트림 Kubernetes와 보안 패치를 따라잡아야 할 필요성을 없애 핵심 비즈니스에 집중할 수 있습니다.

* **기존 하드웨어 투자 활용**
	Kubernetes 워크로드를 실행하기 위해 자체 하드웨어와 데이터 센터 투자를 계속 사용합니다.

자세한 내용과 배포판 탐색은 [Amazon EKS Distro 문서](https://aws.amazon.com/eks/eks-distro/)를 참고하세요.

## 6. Amazon EKS Anywhere

Amazon EKS Anywhere는 자체 온프레미스 인프라에서 Kubernetes 클러스터를 생성, 운영, 유지 관리할 수 있게 해주는 Amazon EKS의 확장입니다. 관리형 Amazon EKS 서비스를 구동하는 것과 동일한 일관된 업스트림 Kubernetes 경험을 제공하지만 AWS 클라우드 외부에서 실행됩니다. 이는 익숙한 AWS 도구와 모범 사례를 활용하면서 자체 데이터 센터, 베어 메탈, 또는 가상화된 환경에 Kubernetes 클러스터를 배포할 수 있음을 의미합니다.

자세한 내용은 공식 [Amazon EKS Anywhere 문서](https://aws.amazon.com/eks/eks-anywhere/)를 참고하세요.

## 7. EKS vs ECS

다음은 **Amazon ECS**와 **Amazon EKS**의 차이를 요약한 비교표입니다.

| **기능**               | **Amazon ECS**                                                                                                                                 | **Amazon EKS**                                                                                                                                 |
|---------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|
| **서비스 유형**          | AWS 네이티브 독점 컨테이너 오케스트레이션 서비스.                                                                                        | 관리형 Kubernetes 서비스(CNCF 인증, 업스트림 Kubernetes와 호환).                                                              |
| **생태계**             | AWS 서비스(IAM, CloudWatch, VPC)와 긴밀하게 통합됨. AWS 도구로 제한됨.                                                           | 더 넓은 Kubernetes 생태계(서드파티 도구, Helm 차트, 오퍼레이터, 커뮤니티 확장) 활용.                              |
| **통합**           | 즉시 사용 가능한 원활한 AWS 통합(예: ALB, ECR). 최소한의 구성 필요.                                                     | AWS 통합을 위한 설정이 필요하지만 Kubernetes 네이티브 도구(예: Prometheus, Istio, Knative) 지원.                                  |
| **제어와 커스터마이징** | 의견이 반영된 단순화된 구성. 커스터마이징 옵션이 적음. 단순한 AWS 중심 워크플로에 최적.                            | Kubernetes API, CRD, 컨트롤러를 통한 높은 커스터마이징. 고급 네트워킹, 스토리지, 스케줄링 구성 지원.           |
| **관리 복잡성** | 낮은 운영 오버헤드. 관리형 컨트롤 플레인과 더 단순한 추상화(파드/배포 대신 태스크/서비스).                 | Kubernetes 아키텍처로 인한 더 높은 복잡성(예: 파드, 노드, 커스텀 컨트롤러 관리). AWS는 컨트롤 플레인만 관리.     |
| **가격 정책 모델**          | ECS 자체에 대한 추가 비용 없음. EC2/Fargate 리소스에 대해서만 지불.                                                                          | EKS 컨트롤 플레인은 클러스터당 시간당 $0.10 + EC2/Fargate 리소스.                                                                        |
| **사용 사례**             | - AWS 통합 앱의 신속한 배포.<br />- Fargate를 사용한 서버리스 컨테이너.<br />- Kubernetes 복잡성을 피하려는 팀.                  | - 멀티 클라우드/하이브리드 클라우드 워크로드.<br />- Kubernetes 네이티브 도구 필요.<br />- 고급 오케스트레이션이나 기존 Kubernetes 전문성.       |
| **이식성**           | AWS로 제한됨. AWS 외부로 워크로드를 마이그레이션하려면 재아키텍처링이 필요.                                                                          | 높은 이식성(Kubernetes 워크로드는 온프레미스나 다른 클라우드를 포함해 준수하는 모든 클러스터에서 실행 가능).                               |
| **학습 곡선**         | AWS 사용자에게 더 쉬움. Kubernetes 지식이 필요하지 않음.                                                                                        | 더 가파른 학습 곡선(Kubernetes 전문성 필요).                                                                                        |

## 8. 결론

Amazon EKS는 Kubernetes 운영과 관련된 복잡성의 상당 부분을 추상화하는 견고하고 프로덕션에 적합한 관리형 Kubernetes 서비스입니다. AWS 생태계와의 깊은 통합, 고가용성, 보안 기능, Kubernetes 표준 준수를 통해 EKS는 현대적인 컨테이너화된 애플리케이션을 규모에 맞게 실행하는 데 적합합니다.

더 자세한 내용과 특정 주제에 대한 심층 탐구는 [공식 자료](https://docs.aws.amazon.com/eks/latest/userguide/what-is-eks.html)를 참고하세요.
