# Amazon ECS

## 1. 소개

Amazon Elastic Container Service(Amazon ECS)는 컨테이너화된 애플리케이션을 손쉽게 배포, 관리, 확장할 수 있게 해주는 완전관리형 컨테이너 오케스트레이션 서비스입니다. 완전관리형 서비스로서 Amazon ECS는 AWS 구성과 운영 모범 사례가 내장되어 있습니다. Amazon Elastic Container Registry 같은 AWS 도구와 Docker 같은 서드파티 도구 모두와 통합되어 있습니다. 이 통합 덕분에 팀은 환경이 아니라 애플리케이션 구축에 집중할 수 있습니다. 컨트롤 플레인을 관리하는 복잡함 없이 클라우드의 AWS 리전과 온프레미스 전반에서 컨테이너 워크로드를 실행하고 확장할 수 있습니다.

## 2. 핵심 구성 요소

- **클러스터:**
    클러스터는 태스크와 서비스가 실행되는 컨테이너 인스턴스(EC2든 ECS Anywhere를 통한 온프레미스든)의 논리적 그룹입니다. 컨테이너 워크로드를 위한 중앙화된 관리 지점을 제공합니다.

- **태스크 정의:**
    JSON으로 작성된 청사진으로, 하나 이상의 컨테이너, 사용할 Docker 이미지, 리소스 할당(CPU와 메모리), 네트워킹 모드, 데이터 볼륨, 로깅 구성, IAM 역할을 지정합니다. 각 태스크 정의는 버전 관리되어 시간이 지남에 따라 애플리케이션 구성을 반복적으로 개선할 수 있습니다. 아래는 샘플 태스크 정의입니다.

```json
{
    "family": "sample-fargate", 
    "networkMode": "awsvpc", 
    "containerDefinitions": [
        {
            "name": "fargate-app", 
            "image": "public.ecr.aws/docker/library/httpd:latest", 
            "portMappings": [
                {
                    "containerPort": 80, 
                    "hostPort": 80, 
                    "protocol": "tcp"
                }
            ], 
            "essential": true, 
            "entryPoint": [
                "sh",
		"-c"
            ], 
            "command": [
                "/bin/sh -c \"echo '<html> <head> <title>Amazon ECS Sample App</title> <style>body {margin-top: 40px; background-color: #333;} </style> </head><body> <div style=color:white;text-align:center> <h1>Amazon ECS Sample App</h1> <h2>Congratulations!</h2> <p>Your application is now running on a container in Amazon ECS.</p> </div></body></html>' >  /usr/local/apache2/htdocs/index.html && httpd-foreground\""
            ]
        }
    ], 
    "requiresCompatibilities": [
        "FARGATE"
    ], 
    "cpu": "256", 
    "memory": "512"
}
```

- **태스크와 서비스:**
    - **태스크:** 태스크는 태스크 정의의 실행 인스턴스입니다.
    - **서비스:** 서비스는 지정된 개수의 태스크 인스턴스를 실행하고 유지할 수 있게 합니다. 태스크 상태를 모니터링하고 실패 시 자동으로 태스크를 교체해 고가용성을 보장합니다.

- **컨테이너 에이전트와 최적화된 AMI:**
    ECS 컨테이너 인스턴스(일반적으로 ECS 최적화 AMI를 사용하는 Amazon EC2 인스턴스)는 ECS 컨트롤 플레인과 통신해 태스크 스케줄링과 인스턴스 상태를 관리하는 ECS 에이전트를 실행합니다.


## 3. 실행 유형

Amazon ECS는 컨테이너화된 애플리케이션을 실행하는 여러 방법을 제공하며, 각각 고유한 이점, 트레이드오프, 제어 수준을 가지고 있습니다. 실행 유형과 배포 옵션 선택은 운영 요구 사항, 원하는 인프라 관리 수준, 워크로드 특성에 따라 달라집니다.

### 3.1. Amazon EC2 실행 유형

EC2 실행 유형에서는 ECS 클러스터를 구성하는 EC2 인스턴스(또는 컨테이너 인스턴스)를 프로비저닝, 구성, 관리할 책임이 있습니다. 이는 인스턴스 유형(컴퓨팅 최적화, GPU 지원, 메모리 최적화 등) 선택과 커스텀 또는 특수화된 운영체제(Amazon ECS 최적화 AMI나 Bottlerocket 등) 실행 기능을 포함해 기본 하드웨어에 대한 완전한 제어를 제공합니다.

특정 성능이나 규정 준수 요구를 충족하도록 클러스터를 맞춤화할 수 있습니다. 예를 들어 향상된 네트워킹이나 최적화된 스토리지 옵션을 갖춘 인스턴스를 사용할 수 있습니다. EC2 클러스터는 특정 인스턴스 특성이 필요한 워크로드나 호스트 수준 접근이 필요한 레거시 시스템과 통합해야 할 때 적합합니다.

EC2 기반 클러스터는 Auto Scaling 그룹과 통합될 수 있으며, ECS Capacity Provider를 사용하면 클러스터의 인스턴스 수를 자동으로 조정하는 전략을 정의할 수 있습니다. Capacity Provider를 사용하면 가용한 리소스를 기반으로 태스크 배치 정책을 설정해, 서로 다른 인스턴스 유형 간에 부하를 분산하거나 심지어 단일 클러스터 내에서 EC2와 Fargate 용량을 결합할 수 있습니다.

#### 3.1.1. EC2 실행 유형을 위한 태스크 배치 전략

EC2 실행 유형에서 실행되는 태스크의 경우 Amazon ECS는 태스크를 어디에 실행할지 결정하기 위해 2단계 프로세스를 사용합니다. 먼저 태스크의 리소스 요구 사항(CPU, 메모리, GPU, 포트 가용성 등)이나 사용자 정의 배치 제약 조건을 충족하지 않는 컨테이너 인스턴스를 걸러냅니다. 그런 다음 배치 전략을 사용해 남은 후보들 중에서 "최적"의 인스턴스를 정렬하고 선택합니다. 다음은 EC2 실행 유형에서 사용 가능한 주요 배치 전략입니다.

- **Random(무작위)**
    - **동작:**
        정의된 제약 조건을 여전히 충족하면서 태스크가 컨테이너 인스턴스에 무작위로 배치됩니다.
    - **사용 사례:**
        특정 인스턴스 선호가 없고 배치 로직을 지나치게 복잡하게 만들지 않으면서 시간이 지남에 따라 태스크를 고르게 분산하고 싶은 시나리오에 가장 적합합니다.
- **Binpack**
    - **동작:**
        Binpack은 사용되지 않는 리소스를 최소화하는 방식으로 인스턴스에 태스크를 배치합니다. CPU나 메모리를 기준으로 최적화할지 선택합니다. 가능한 한 적은 수의 인스턴스에 태스크를 채워, 리소스 활용을 극대화하고 활용도가 낮은 컨테이너 인스턴스를 줄임으로써 비용을 절감하는 데 도움이 됩니다.
    - **사용 사례:**
        인스턴스 효율성을 극대화하고 실행 중인 컨테이너 인스턴스 수를 잠재적으로 줄이고 싶은 비용에 민감한 환경에 이상적입니다.
- **Spread**
    - **동작:**
        Spread 전략은 정의된 "빈(bin)" 집합에 태스크를 고르게 분산합니다. 빈은 다음이 될 수 있습니다.
        - **인스턴스 ID:** 모든 컨테이너 인스턴스에 걸쳐 태스크가 고르게 분산되도록 보장합니다.
        - **속성:** 예를 들어 `attribute:ecs.availability-zone`을 사용하면 가용 영역 전반에 태스크를 고르게 분산합니다.
    - **사용 사례:**
        고가용성이 중요할 때 유용합니다. 서로 다른 가용 영역이나 인스턴스에 태스크를 분산함으로써 한 영역이나 인스턴스의 장애가 모든 태스크에 영향을 미칠 위험을 줄입니다.

### 3.2. AWS Fargate 실행 유형

![aws-fargate](@site/docs/Containers/_assets/aws-fargate.png)

AWS Fargate는 기본 컴퓨팅 인프라를 추상화합니다. 태스크 정의에 컨테이너의 리소스 요구 사항(CPU, 메모리, 네트워킹 설정)만 정의하면 Fargate가 런타임에 적절한 인프라를 자동으로 프로비저닝합니다. 이는 EC2 인스턴스 관리와 관련된 확장, 패치, 유지보수 작업의 부담을 없애줍니다.

Fargate 태스크는 할당된 리소스에 대해 초 단위로 요금이 청구되며, 이는 산발적이거나 예측할 수 없는 워크로드에 특히 비용 효율적일 수 있습니다. 이 모델은 과도한 프로비저닝의 필요성을 없애고 사용한 만큼만 지불하도록 보장함으로써 비용을 최적화하는 데 도움이 됩니다.

각 Fargate 태스크는 전용 컴퓨팅, 메모리, 네트워킹 리소스를 가진 자체 격리된 런타임 환경에서 실행됩니다. 이 격리는 별도의 호스트 인스턴스를 관리할 필요 없이 달성되며, 태스크 간 상호 간섭 가능성을 줄여 보안을 강화합니다.

태스크 배치 전략과 제약 조건은 Fargate 실행 유형을 사용하는 태스크에서는 지원되지 않습니다. Fargate는 접근 가능한 가용 영역에 걸쳐 태스크를 최대한 분산하려고 시도합니다.
### 3.3. ECS Anywhere

ECS Anywhere는 ECS의 기능을 AWS 클라우드 너머로 확장합니다. ECS Anywhere를 사용하면 동일한 ECS 컨트롤 플레인과 API를 사용해 온프레미스 서버나 심지어 다른 클라우드의 리소스를 등록하고 관리할 수 있습니다. 이는 클라우드와 온프레미스 환경 전반에서 일관된 관리 경험을 제공합니다.

상당한 온프레미스 투자를 하고 있거나 특정 데이터 상주 또는 지연 시간 요구 사항을 충족해야 하는 조직은 새로운 도구나 프로세스를 배울 필요 없이 다양한 환경 전반에서 컨테이너화된 애플리케이션을 오케스트레이션하기 위해 ECS Anywhere를 사용할 수 있습니다.
## 4. 태스크 vs. 서비스 배포

(`run-task` API 호출을 사용해) 태스크를 직접 실행하면 이는 짧게 지속되는 일회성 작업을 위한 것입니다. 연속적인 가용성이 필요하지 않은 배치 처리, 임시 테스트, 일회성 작업에 이상적입니다.

반면 ECS 서비스는 지정된 개수의 태스크 인스턴스를 지속적으로 실행하고 유지하는 데 사용됩니다. 태스크가 실패하거나 예기치 않게 중지되면 ECS 서비스 스케줄러가 자동으로 이를 교체해 원하는 태스크 수가 유지되도록 보장합니다. 서비스는 로드 밸런서(Application 또는 Network Load Balancer)와 통합되어 태스크 전반에 걸쳐 들어오는 트래픽을 분산할 수 있어, 프로덕션 웹 애플리케이션과 API에 적합합니다.

단순히 태스크를 실행하는 것을 넘어 ECS는 롤링 업데이트, 블루/그린 배포(종종 AWS CodeDeploy 통합 사용) 같은 고급 배포 전략을 지원하며, ECS Capacity Provider를 활용해 서로 다른 유형의 인프라 전반에 태스크를 분산할 수 있습니다. 이러한 전략들은 다운타임을 최소화하고 업데이트 중 애플리케이션 안정성을 유지하는 데 도움이 됩니다.

## 5. Capacity Provider와 실행 유형 결합

Capacity Provider를 사용하면 단일 ECS 클러스터 내에서 둘 이상의 실행 유형을 사용할 수 있습니다. 예를 들어 EC2와 Fargate Capacity Provider를 모두 사용하는 서비스를 만들어 태스크를 어떻게 분산할지 전략을 정의할 수 있습니다. 이는 EC2의 완전한 제어와 Fargate의 사용 편의성 사이에서 워크로드 요구에 따라 균형을 맞출 수 있어 확장과 비용 관리에 유연성을 제공합니다.

ECS 서비스를 Capacity Provider와 연결하면 실시간 사용 지표를 기반으로 기본 리소스(EC2 인스턴스든 Fargate 태스크든)를 자동으로 확장할 수 있습니다. 이는 리소스 활용을 최적화하고 수동 개입 없이 애플리케이션이 트래픽 변동을 처리할 수 있도록 보장하는 데 도움이 됩니다.

## 6. ECS 네트워킹

Amazon ECS는 컨테이너가 내부적으로 그리고 외부 시스템과 어떻게 통신하는지를 결정하는 다양한 네트워킹 옵션을 제공합니다. 네트워크 모드 선택은 격리, 보안, 포트 관리 방식 같은 측면에 영향을 미칩니다. 아래는 ECS 태스크에 사용 가능한 네트워킹 옵션에 대한 상세 설명입니다.

### 6.1. Amazon EC2에서 ECS 태스크를 위한 네트워크 모드

(Fargate와 달리) Amazon EC2 인스턴스에서 ECS 태스크를 실행할 때는 여러 Docker 네트워크 모드 중에서 선택할 수 있습니다.

#### **a. awsvpc(VPC 네트워킹)**

`awsvpc` 모드를 사용하면 각 태스크는 VPC 내에서 자체 elastic network interface(ENI)를 할당받습니다. 이는 EC2 인스턴스와 마찬가지로 태스크에 고유한 프라이빗 IP 주소(그리고 선택적으로 IPv6 주소)를 부여합니다. 이 ENI들은 ECS가 관리하며, EC2 콘솔에서 확인할 수 있습니다. 듀얼 스택(IPv4와 IPv6), 보안 그룹, 네트워크 트래픽 모니터링을 위한 VPC 흐름 로그 같은 기능을 지원합니다.

- **이점:**
    - **격리:** 태스크는 자체 네트워크 스택으로 작동해 태스크 간 강력한 격리를 제공합니다.
    - **보안:** 태스크에 직접 보안 그룹을 할당할 수 있어 인바운드와 아웃바운드 트래픽에 대한 세밀한 제어가 가능합니다.
    - **통합:** 로드 밸런서(Application과 Network Load Balancer)와 직접 호환되며 포트 충돌 없이 동적 포트 매핑을 지원합니다.
- **사용 사례:**
    예측 가능한 네트워크 성능과 견고한 보안 제어가 필요한 애플리케이션에 권장됩니다. 이 모드는 Fargate의 태스크에도 필요합니다.

#### **b. Bridge**

특정 네트워크 모드가 정의되지 않았을 때 Linux 컨테이너의 기본 Docker 네트워킹 모드입니다. 이 설정에서는 모든 컨테이너가 호스트의 내부 Docker 브리지 네트워크를 공유합니다.

- **이점:**
    - **단순함:** 컨테이너는 내부 네트워크를 통해 통신하며, Docker 포트 매핑을 사용해 특정 컨테이너 포트를 호스트에 노출할 수 있습니다.
- **제한 사항:**
    - **격리:** 모든 컨테이너가 동일한 브리지를 공유하므로 `awsvpc`에 비해 네트워크 격리가 덜 됩니다.
    - **포트 관리:** 같은 호스트의 여러 태스크가 동일한 호스트 포트를 사용하려고 할 수 있으므로 포트 충돌을 수동으로 관리해야 합니다.
- **사용 사례:**
    같은 호스트 내에서 컨테이너 간 통신으로 충분한 레거시 애플리케이션이나 단순한 배포에 적합합니다.

#### **c. Host**

호스트 모드에서는 컨테이너가 Docker의 가상 네트워크를 우회하고 호스트의 네트워크 스택을 직접 사용합니다. 이는 컨테이너가 호스트와 동일한 IP 주소를 공유한다는 것을 의미합니다.

- **이점:**
    - **성능:** 네트워크 변환 오버헤드를 제거해 네트워크 집약적인 애플리케이션에서 성능을 개선할 수 있습니다.
- **제한 사항:**
    - **포트 충돌:** 컨테이너가 호스트의 네트워크를 공유하므로 여러 컨테이너가 동시에 동일한 포트를 사용할 수 없습니다.
    - **보안과 격리:** 컨테이너와 호스트 사이에 네트워크 격리가 없어 네트워크 기반 공격의 잠재적 영향이 커집니다.
- **사용 사례:**
    매우 높은 네트워크 성능이 필요하거나 컨테이너가 특정 호스트 수준 네트워킹 기능을 사용해야 할 때 가장 적합합니다.

#### **d. None**

`none` 모드에서는 컨테이너가 외부 네트워크 연결 없이 시작됩니다. 어떤 네트워크에서도 완전히 격리되지만 localhost를 통해 동일한 태스크 내 다른 컨테이너와는 여전히 통신할 수 있습니다.

- **이점과 사용 사례:**
	네트워크 통신이 필요하지 않은 격리된 태스크(특정 배치 작업이나 테스트 시나리오 등)를 실행하는 데 유용합니다.

### 6.2. Windows 컨테이너를 위한 네트워크 모드

Windows 기반 컨테이너의 경우 네트워킹 옵션이 약간 다릅니다.

- **기본값(NAT 모드):**
    Amazon ECS에서 실행되는 Windows 컨테이너의 경우 기본 네트워크 모드는 `default`이며, 이는 Windows NAT 드라이버(일반적으로 `nat` 네트워크 모드로 불림)를 사용합니다.
    - **동작:**
        컨테이너는 가상화된 네트워크 인터페이스 뒤로 네트워킹을 추상화하는 NAT 기반 네트워크를 공유합니다. Linux의 `bridge` 모드와 달리 Windows `default` 모드는 Linux에서 사용 가능한 일부 고급 Docker 네트워킹 기능을 지원하지 않습니다.
- **제한 사항:**
    - `awsvpc` 모드는 EC2에서 실행되는 Windows 컨테이너에서는 사용할 수 없어, 각 컨테이너에 자체 ENI를 할당할 수 없습니다.

### 6.3. Fargate 태스크의 네트워킹 고려 사항

AWS Fargate에서 실행되는 태스크의 경우 `awsvpc` 네트워크 모드가 유일하게 지원되는 옵션입니다. 각 태스크는 자체 ENI를 할당받아 태스크 수준 격리, 보안 그룹, VPC 네트워킹과의 직접 통합의 이점을 제공합니다.

Fargate를 사용할 때는 태스크나 서비스 실행 시 `NetworkConfiguration`을 지정해야 합니다. 여기에는 다음이 포함됩니다.

- **서브넷:**
	태스크 ENI가 배치될 위치(접근 요구 사항에 따른 퍼블릭 또는 프라이빗 서브넷).
- **보안 그룹:**
	각 태스크의 ENI에 직접 적용되어 트래픽을 제어합니다.
- **퍼블릭 IP 할당:**
	선택적으로 태스크가 직접 인터넷 접근이 필요한 경우 퍼블릭 IP 주소를 할당할 수 있습니다.

### 6.4. ECS 네트워킹 모범 사례

AWS는 ECS 네트워킹을 위한 일련의 모범 사례를 제공합니다.

- **awsvpc 모드 사용:**
    가능한 한, 특히 프로덕션 워크로드의 경우 향상된 보안과 성능을 포함한 VPC 네트워킹의 모든 이점을 활용하기 위해 `awsvpc` 모드를 사용하세요.
- **서브넷 계획:**
    태스크가 퍼블릭 서브넷(직접 인터넷 접근용)에서 실행되어야 할지 아니면 NAT 게이트웨이가 있는 프라이빗 서브넷(향상된 보안용)에서 실행되어야 할지 결정하세요.
- **보안 그룹을 적절히 구성:**
    필요한 트래픽만 태스크로 오가도록 허용해 최소 권한 원칙을 적용하세요.
- **네트워크 트래픽 모니터링:**
    VPC 흐름 로그와 CloudWatch 지표를 활용해 네트워크 성능을 모니터링하고 문제를 해결하세요.

## 7. 태스크 라이프사이클

아래 순서도는 태스크 라이프사이클 흐름을 보여줍니다.

![ecs-task-lifecycle](@site/docs/Containers/_assets/ecs-task-lifecycle.png)


* **PROVISIONING**
	Amazon ECS가 태스크가 시작되기 전에 추가 단계를 수행해야 합니다. 예를 들어 `awsvpc` 네트워크 모드를 사용하는 태스크의 경우 elastic network interface를 프로비저닝해야 합니다.

* **PENDING**
	이는 Amazon ECS가 컨테이너 에이전트의 추가 조치를 기다리는 전환 상태입니다. 태스크에 사용 가능한 리소스가 있을 때까지 태스크는 pending 상태로 유지됩니다.

* **ACTIVATING**
	이는 Amazon ECS가 태스크가 시작된 후 하지만 태스크가 `RUNNING` 상태로 전환되기 전에 추가 단계를 수행해야 하는 전환 상태입니다. 이는 Amazon ECS가 컨테이너 이미지를 풀링하고, 컨테이너를 생성하고, 태스크 네트워킹을 구성하고, 로드 밸런서 타겟 그룹을 등록하고, 서비스 디스커버리를 구성하는 상태입니다.

* **RUNNING**
	태스크가 성공적으로 실행되고 있습니다.

* **DEACTIVATING**
	이는 Amazon ECS가 태스크가 중지되기 전에 추가 단계를 수행해야 하는 전환 상태입니다. 예를 들어 Elastic Load Balancing 타겟 그룹을 사용하도록 구성된 서비스의 일부인 태스크의 경우 이 상태 동안 타겟 그룹 등록 해제가 발생합니다.

* **STOPPING**
	이는 Amazon ECS가 컨테이너 에이전트의 추가 조치를 기다리는 전환 상태입니다.
	Linux 컨테이너의 경우 컨테이너 에이전트는 애플리케이션이 종료되어야 함을 알리기 위해 `SIGTERM` 신호를 보낸 다음, 태스크 정의에 설정된 `StopTimeout` 기간을 기다린 후 `SIGKILL`을 보냅니다.

* **DEPROVISIONING**
	Amazon ECS가 태스크가 중지된 후 하지만 태스크가 `STOPPED` 상태로 전환되기 전에 추가 단계를 수행해야 합니다. 예를 들어 `awsvpc` 네트워크 모드를 사용하는 태스크의 경우 elastic network interface를 분리하고 삭제해야 합니다.

* **STOPPED**
	태스크가 성공적으로 중지되었습니다.

* **DELETED**
	이는 태스크가 중지될 때의 전환 상태입니다. 이 상태는 콘솔에 표시되지 않지만 `describe-tasks`에는 표시됩니다.

## 8. 가격 정책

Amazon ECS 자체는 추가 요금을 부과하지 않습니다 — 컨테이너화된 애플리케이션이 소비하는 기본 컴퓨팅, 스토리지, 다른 AWS 서비스에 대해서만 비용을 지불합니다. 다음은 세부 내역입니다.

- **ECS는 무료입니다:**
    Amazon ECS를 서비스로 사용하는 데 추가 요금이 없습니다. ECS가 제공하는 오케스트레이션과 관리는 추가 비용 없이 제공됩니다.
    
- **EC2 실행 유형:**
    EC2 인스턴스에서 태스크를 실행할 때는 EC2 인스턴스, 스토리지(EBS 등), 데이터 전송, 사용하는 다른 추가 AWS 서비스(예: 로깅을 위한 CloudWatch)에 대해 요금이 청구됩니다. 본질적으로 비용은 컨테이너를 호스팅하고 지원하는 개별 AWS 리소스의 가격 정책을 반영합니다.
    
- **AWS Fargate:**
    Fargate 실행 유형을 사용하는 태스크의 경우 가격 정책은 태스크 정의에 지정한 vCPU와 메모리 리소스를 기반으로 합니다. 실행 중인 태스크에 할당된 리소스에 대해 초 단위(최소 1분)로 요금이 청구됩니다. 이 모델은 기본 인스턴스를 관리할 필요 없이 컴퓨팅 용량에 대한 세밀한 청구를 제공합니다.
    
- **ECS Anywhere:**
    ECS Anywhere를 사용해 자체 서버나 다른 환경에서 태스크를 실행할 때는 오케스트레이션 서비스 자체에 대해서는 요금이 부과되지 않습니다. 다만 사용하는 추가 AWS 서비스(예: 에이전트 관리를 위한 AWS Systems Manager나 모니터링을 위한 CloudWatch)에 대해서는 계속 비용을 지불하며, 온프레미스 인프라 비용에 대해서도 책임이 있습니다.

## 9. 결론

Amazon ECS는 컨테이너화된 애플리케이션을 관리하기 위한 견고하고, 확장 가능하고, 안전한 플랫폼입니다. 자체 EC2 인스턴스를 관리하는 유연성을 선택하든, 서버리스 Fargate의 편의성을 선택하든, ECS Anywhere로 온프레미스 환경까지 ECS를 확장하든, 이 서비스는 AWS의 풍부한 도구와 서비스 생태계와 원활하게 통합되도록 설계되었습니다.

더 자세한 내용과 특정 주제에 대한 심층 탐구는 [공식 자료](https://docs.aws.amazon.com/ecs/latest/developerguide/Welcome.html)를 참고하세요.
