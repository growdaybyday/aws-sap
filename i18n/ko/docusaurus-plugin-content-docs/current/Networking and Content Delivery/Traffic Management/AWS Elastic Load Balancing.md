# AWS Elastic Load Balancing

## 1. 소개

현대 웹 애플리케이션의 발전은 네트워크 인프라가 견고하고 확장성 있으며 내결함성을 갖추기를 요구합니다. 이런 요구사항의 핵심에는 로드 밸런싱이라는 개념이 있습니다. 이는 들어오는 네트워크 트래픽을 여러 백엔드 서버나 리소스로 분산시키는 기법입니다. AWS Elastic Load Balancing은 들어오는 애플리케이션 트래픽을 자동으로 분산시키고 백엔드 대상의 장애를 매끄럽게 처리함으로써 이 개념을 구현합니다.

## 2. ELB 기초

고급 구성과 사용 사례로 넘어가기 전에 Elastic Load Balancing의 기초를 이해하는 것이 필수적입니다. 이 절에서는 ELB의 개요, 핵심 기능, AWS에서 제공하는 다양한 로드 밸런서 유형에 대한 분석을 종합적으로 살펴봅니다.

### 2.1 ELB 개요: 목적과 주요 기능

본질적으로 로드 밸런서는 들어오는 네트워크 트래픽을 여러 백엔드 대상(EC2 인스턴스, 컨테이너, 심지어 온프레미스 서버까지)으로 분산시키는 서버(또는 서버 집합)입니다. 로드 밸런서의 주된 목적은 다음과 같습니다.

- **트래픽을 균등하게 분산:** 인스턴스가 세 개든 서른 개든, 로드 밸런서는 사용자 요청을 분산시켜 특정 인스턴스가 병목이 되지 않도록 보장합니다.
- **내결함성 개선:** 내장된 상태 확인 기능으로 ELB는 비정상 인스턴스를 자동으로 감지해, 복구될 때까지 트래픽 라우팅을 중단할 수 있습니다.
- **클라이언트 연결 단순화:** 클라이언트는 단일 엔드포인트에 연결하므로 기반 서버 인프라의 복잡성이 추상화됩니다.
- **보안 강화:** ELB는 SSL 종료 같은 작업을 대신 처리할 수 있으며, 보안 그룹 연결과 관리형 인증서 같은 기능으로 통합된 보안을 제공합니다.
- **AWS와의 매끄러운 통합:** AWS가 ELB의 기반 인프라(업그레이드, 유지 관리, 확장 포함)를 관리해 운영 부담을 줄여 줍니다.

높은 수준에서 보면 AWS ELB의 아키텍처는 세 가지 핵심 계층으로 이루어집니다.

![elb](@site/docs/Networking%20and%20Content%20Delivery/_assets/elb.png)

1. **클라이언트에서 로드 밸런서로:** 클라이언트는 HTTP, HTTPS, TCP, 심지어 UDP 같은 프로토콜을 사용해 로드 밸런서와 연결을 수립합니다.
2. **로드 밸런서 처리:** 로드 밸런서는 들어오는 요청을 처리합니다. 상태 확인, 라우팅 알고리즘, 보안 정책(예: SSL 종료, 헤더 삽입)을 적용합니다.
3. **로드 밸런서에서 백엔드 대상으로:** 마지막으로 로드 밸런서는 요청을 등록된 하나 이상의 백엔드 대상으로 전달합니다. 이 대상들은 Auto Scaling 그룹, Amazon ECS 같은 컨테이너 서비스, 또는 Lambda 함수일 수 있습니다.

ELB를 사용하는 이점은 단순히 부하를 분산하는 것에 그치지 않습니다. 세션 스티키니스, 연결 드레이닝, 고급 라우팅 알고리즘 같은 기능을 통합함으로써, AWS ELB는 단순한 웹 애플리케이션부터 복잡한 마이크로서비스 아키텍처까지 지원하는 견고한 플랫폼을 제공합니다.

### 2.2 로드 밸런서 유형

AWS는 서로 다른 사용 사례, 프로토콜, 성능 특성에 맞춰진 여러 유형의 로드 밸런서를 제공합니다. 주요 변형은 Classic Load Balancer(CLB), Application Load Balancer(ALB), Network Load Balancer(NLB)입니다(주로 네트워크 계층에서 동작하는 Gateway Load Balancer(GWLB)도 있지만, 여기서는 대부분의 워크로드와 관련된 세 가지 주요 유형에 초점을 맞춥니다).

![elb-types](@site/docs/Networking%20and%20Content%20Delivery/_assets/elb-types.png)

#### 2.2.1 Classic Load Balancer(CLB): 레거시 사용 사례

Classic Load Balancer는 AWS 로드 밸런싱 기술의 첫 세대를 나타냅니다. 현재는 레거시로 간주되어 더 현대적인 솔루션으로 대체되고 있지만, CLB는 AWS에서 로드 밸런싱이 발전하는 데 중요한 역할을 했습니다.

**CLB의 주요 특성:**

- **프로토콜 지원:**
    CLB는 HTTP, HTTPS, TCP, SSL(Secure TCP로도 알려짐)을 포함한 여러 프로토콜을 지원합니다. 이런 다양성 덕분에 사용자는 다양한 애플리케이션에 맞춰 로드 밸런서를 구성할 수 있었습니다.

- **상태 확인:**
    CLB의 상태 확인은 정상 상태인 백엔드 인스턴스만 트래픽을 받도록 보장하는 데 매우 중요합니다. CLB는 HTTP, HTTPS, TCP 상태 확인을 지원합니다. 일반적인 구성에서는 CLB가 인스턴스 상태를 확인하는 데 사용할 포트와 URL 경로(예: `/health`)를 지정합니다. 백엔드 인스턴스가 허용 가능한 상태 코드(주로 HTTP 200)로 응답하지 않으면 비정상으로 표시되고 더 이상 트래픽이 전달되지 않습니다.

- **리스너 아키텍처:**
    CLB에서 리스너는 로드 밸런서가 들어오는 트래픽을 받는 프로토콜과 포트를 정의합니다. 리스너는 클라이언트와의 연결을 수립한 다음, 트래픽을 적절한 백엔드 인스턴스로 전달하는 역할을 합니다. CLB는 암호화된(HTTPS/SSL) 연결과 암호화되지 않은(HTTP/TCP) 연결을 모두 지원합니다.

- **백엔드 인스턴스 등록:**
    CLB에서는 백엔드 인스턴스가 로드 밸런서에 직접 등록됩니다. AWS 로드 밸런싱이 발전하면서 나중에 도입된 "타깃 그룹" 같은 추상화 계층이 없습니다. 이 직접 등록 방식이 CLB가 레거시로 분류되는 요인 중 하나입니다.

- **EC2-Classic 네트워크:**
    CLB는 원래 지금은 사용이 중단된 네트워크 모델인 EC2-Classic 네트워크와 함께 동작하도록 설계되었습니다. CLB를 VPC 안에서도 사용할 수 있지만, 원래 설계는 보안 수준이 낮은 플랫 네트워크 아키텍처를 위한 것이었습니다.

- **보안과 SSL 종료:**
    CLB는 SSL 종료(로드 밸런서가 들어오는 HTTPS 트래픽을 복호화한 다음 암호화되지 않은 HTTP 트래픽을 백엔드로 전달하는 방식)를 지원하지만, 신중한 구성이 필요합니다. 종단 간 암호화(SSL 종료가 백엔드에서 이루어지는 경우)를 위해서는 각 EC2 인스턴스에 인증서를 설치해야 합니다.

- **운영상의 제약:**
    1세대 로드 밸런서로서 CLB는 ALB와 NLB에서 제공하는 여러 고급 기능이 없습니다. 예를 들어 URL 경로나 호스트명 기반의 고급 라우팅, 컨테이너 환경을 위한 동적 포트 매핑, WebSocket이나 HTTP/2의 현대적 처리를 지원하지 않습니다.


**사용 사례와 레거시 고려사항:**

AWS는 사용자에게 ALB나 NLB로 마이그레이션할 것을 권장하지만, CLB는 여전히 레거시 애플리케이션이나 원래 EC2-Classic으로 구축된 아키텍처에서 사용되고 있습니다. 시험이나 역사적 맥락에서는 CLB의 동작, 특히 SSL 종료 처리, 연결 라우팅, 타깃 그룹의 부재를 이해하는 것이 중요합니다.

#### 2.2.2 Application Load Balancer(ALB): 레이어 7 라우팅

Application Load Balancer는 OSI 모델의 애플리케이션 계층(레이어 7)에서 동작하는, 기능이 풍부한 현대적 로드 밸런싱 솔루션입니다. ALB는 HTTP/HTTPS 애플리케이션과 마이크로서비스 아키텍처의 요구를 충족하기 위해 도입되었습니다.

**ALB의 주요 특성:**

- **레이어 7 인텔리전스:**
    레이어 7에서 동작하는 ALB는 HTTP와 HTTPS 프로토콜을 상세히 이해합니다. 이를 통해 URL 경로, HTTP 헤더, 쿼리 파라미터, 심지어 호스트 헤더 같은 요청 내용을 기반으로 라우팅 결정을 내릴 수 있습니다.

- **다중 리스너와 규칙:**
    ALB는 서로 다른 포트(예: HTTP는 80, HTTPS는 443)에 여러 리스너를 구성할 수 있습니다. 각 리스너는 트래픽을 어떻게 라우팅할지 정의하는 하나 이상의 규칙을 가질 수 있습니다. 규칙은 순서대로 평가되며, 각 규칙은 조건(경로 패턴이나 쿼리 문자열 등)과 그에 연관된 동작(주로 타깃 그룹으로의 전달)을 지정할 수 있습니다.

- **타깃 그룹:**
    CLB와 달리 ALB는 타깃 그룹을 사용해 백엔드 엔드포인트를 추상화합니다. 타깃 그룹에는 하나 이상의 타깃(EC2 인스턴스, IP 주소, Lambda 함수, ECS에서 실행되는 컨테이너 등)이 포함됩니다. 상태 확인은 타깃 그룹 수준에서 구성되며, 타깃은 서로 다른 규칙 사이에서 공유될 수 있습니다.

- **동적 포트 매핑:**
    ALB는 동적 포트 매핑을 지원해 컨테이너화된 애플리케이션에 이상적입니다. 이 기능으로 ALB는 ECS 태스크에서 정의한 대로 EC2 인스턴스의 임의 포트에서 실행되는 컨테이너로 트래픽을 라우팅할 수 있습니다.

- **프로토콜 지원과 고급 기능:**
    ALB는 HTTP, HTTPS, WebSocket, HTTP/2, gRPC를 지원합니다. 특히 gRPC 지원은 현대적인 HTTP/2 프로토콜을 활용해 마이크로서비스 아키텍처에서 효율적인 통신을 가능하게 합니다.

- **세션 스티키니스:**
    ALB는 스티키 세션(세션 어피니티로도 불림)을 지원합니다. 활성화하면 ALB는 쿠키(로드 밸런서가 생성하거나 애플리케이션이 생성)를 사용해 같은 클라이언트의 이후 요청이 동일한 타깃으로 라우팅되도록 보장합니다.

- **SSL/TLS 오프로딩과 SNI:**
    ALB에서는 SSL/TLS 종료가 로드 밸런서에서 이루어질 수 있습니다. 즉 들어오는 HTTPS 트래픽이 ALB에서 복호화되어 HTTP로(또는 종단 간 암호화를 위해 재암호화되어) 백엔드 타깃으로 전달됩니다. ALB는 SNI(Server Name Indication)도 지원해, 하나의 로드 밸런서에서 여러 SSL 인증서를 제공할 수 있습니다.

- **콘텐츠 기반 라우팅:**
    ALB의 가장 강력한 기능 중 하나는 요청 내용을 기반으로 트래픽을 라우팅하는 능력입니다. 예를 들어 `/user/*`로의 요청은 한 타깃 그룹으로, `/admin/*`로의 요청은 다른 타깃 그룹으로 라우팅할 수 있고, 요청된 도메인 이름을 기준으로 트래픽을 안내하는 호스트 기반 라우팅도 사용할 수 있습니다.

- **커스텀 HTTP 응답과 리디렉션:**
    ALB는 커스텀 HTTP 응답(예: 고정된 404 응답)을 생성하거나 HTTP 요청을 HTTPS로 자동 리디렉션할 수 있어 보안과 사용자 경험을 모두 개선합니다.

**ALB의 사용 사례:**

ALB는 고급 라우팅이 필요한 현대적인 웹 애플리케이션과, 단일 인스턴스나 컨테이너 집합에서 서로 다른 서비스가 실행되는 마이크로서비스 아키텍처에 특히 적합합니다. Amazon ECS와 Lambda 함수와의 통합은 서버리스와 컨테이너화된 배포로 활용 범위를 더욱 확장합니다.

#### 2.2.3 Network Load Balancer(NLB): 초저지연

Network Load Balancer는 고성능과 초저지연을 위해 설계되었습니다. 전송 계층(레이어 4)에서 동작하는 NLB는 극단적인 성능과 초당 수백만 건의 요청을 처리할 수 있는 능력이 필요한 사용 사례에 이상적입니다.

**NLB의 주요 특성:**

- **레이어 4 동작:**
    NLB는 레이어 4에서 동작하며, TCP, UDP, TLS 프로토콜을 직접 다룹니다. HTTP 요청의 내용을 검사하는 ALB와 달리, NLB는 더 낮은 수준에서 동작해 더 빠르고 지연 시간에 민감한 애플리케이션에 더 적합합니다.

- **고정 IP 주소와 ENI:**
    NLB가 배포된 각 가용 영역(AZ)에는 로드 밸런서와 연결된 고정 IP 주소가 있습니다. 이 IP 주소들은 NLB의 수명 동안 고정된 상태로 유지되는 Elastic Network Interface(ENI)에 할당됩니다. 인터넷 대면 구성에서는 방화벽에서 화이트리스트 등록을 더 쉽게 하기 위해 탄력적 IP를 할당할 수도 있습니다.

- **높은 처리량과 낮은 지연 시간:**
    NLB는 성능에 최적화되어 있습니다. 분당 수십만 개의 동시 연결을 처리할 수 있어 높은 처리량이 필요한 애플리케이션에 이상적입니다. NLB의 일반적인 지연 시간은 수백 밀리초 수준으로, ALB보다 훨씬 낮습니다.

- **TCP, TLS, UDP, TCP_UDP 지원:**
    NLB는 광범위한 프로토콜을 지원합니다. 이는 게임 서버, VoIP 서비스, 커스텀 TCP/UDP 애플리케이션처럼 HTTP/HTTPS를 사용하지 않을 수 있는 애플리케이션에 다재다능한 선택지가 되게 합니다.

- **클라이언트 IP 주소 보존:**
    NLB의 중요한 기능 중 하나는 원본 클라이언트 IP 주소를 보존하는 능력입니다. 백엔드 타깃이 인스턴스 ID로 등록되면 타깃은 클라이언트의 IP 주소를 직접 받습니다. 타깃이 IP 주소로 등록된 경우 일부 프로토콜(TCP나 TLS)에서는 원본 IP 정보를 전달하기 위해 Proxy Protocol이 필요할 수 있습니다.

- **Proxy Protocol 지원:**
    기본적으로 클라이언트 IP가 보존되지 않는 상황에서는 NLB가 Proxy Protocol을 지원합니다. 이 프로토콜은 발신 클라이언트의 IP 주소와 포트 번호를 담은 헤더를 TCP 페이로드 앞에 붙여, 백엔드 타깃이 연결의 원본 출처를 파악할 수 있게 합니다.

- **존 단위와 리전 단위 DNS 이름:**
    NLB는 활성화된 모든 AZ의 노드 IP로 해석되는 리전 단위 DNS 이름과, 클라이언트가 특정 AZ를 대상으로 지정할 수 있게 하는 존 단위 DNS 이름을 모두 제공합니다. 이는 AZ 간 데이터 전송을 최소화하는 것이 중요한 애플리케이션에서 특히 유용할 수 있습니다.

- **고급 사용 사례:**
    전통적인 백엔드 인스턴스를 처리하는 것 외에도, NLB는 컨테이너화된 워크로드(동적 포트 매핑 활용)와 리전 간·VPC 간 배포에서도 사용할 수 있습니다. 다만 NLB는 원시 성능과 저수준 프로토콜 처리에 초점을 맞추므로 ALB에서 제공하는 일부 고급 기능(콘텐츠 기반 라우팅 등)은 지원하지 않는다는 점에 유의해야 합니다.


**NLB를 사용해야 할 때:**

NLB는 초저지연, 극도로 높은 처리량, HTTP/HTTPS를 넘어서는 프로토콜이 필요한 애플리케이션에 가장 좋은 선택입니다. 예를 들어 커스텀 TCP 기반 애플리케이션이나 UDP 통신이 필요한 서비스는 NLB의 아키텍처로부터 큰 이점을 얻을 수 있습니다. 또한 로깅이나 보안을 위해 클라이언트 IP 보존이 중요할 때는 NLB의 기능이 이상적인 선택입니다.

## 3. 구성과 연결 관리

가변적인 워크로드에서도 로드 밸런서가 최적으로 동작하도록 하려면 연결에 대한 적절한 구성과 관리가 매우 중요합니다. 이 절에서는 연결 생명주기 관리, 라우팅 전략, 존 간 트래픽 분산의 세부 사항을 살펴봅니다.

### 3.1 연결 생명주기: 유휴 타임아웃과 연결 드레이닝

연결이 얼마나 오래 열려 있을지 관리하고, 백엔드 타깃의 제거를 매끄럽게 처리하는 것은 애플리케이션 응답성을 유지하고 리소스 효율성을 보장하는 데 핵심입니다.

#### 3.1.1 연결 유휴 타임아웃

연결 유휴 타임아웃은 연결이 닫히기 전에 비활성 상태로 유지될 수 있는 기간입니다. 이 설정은 로드 밸런싱 아키텍처의 두 지점에 적용됩니다.

- **클라이언트와 로드 밸런서 사이:**
    지정된 기간(ALB와 CLB의 기본값은 일반적으로 60초) 동안 클라이언트와 로드 밸런서 사이에 데이터 전송이 없으면 연결이 닫힙니다. 이는 리소스를 확보하고 걸려 있는 연결을 방지하는 데 도움이 됩니다.
- **로드 밸런서와 백엔드 타깃 사이:**
    마찬가지로 로드 밸런서와 EC2 인스턴스(또는 다른 타깃) 사이에 동일한 기간 동안 데이터 교환이 없으면 해당 연결도 종료됩니다.

애플리케이션의 동작에 맞춰 유휴 타임아웃을 조정하는 것이 중요합니다. 예를 들어 대용량 파일 업로드나 장기간 유지되는 세션을 포함하는 애플리케이션은 유휴 타임아웃을 늘려 조기 연결 종료를 방지하는 것이 유리할 수 있습니다. 반대로 단기간 유지되는 연결이라면 타임아웃을 낮춰 리소스를 절약할 수 있습니다.

_참고:_ Network Load Balancer의 경우 유휴 타임아웃 설정이 약간 다릅니다. NLB의 TCP 연결은 일반적으로 350초로 고정되어 있고, UDP 연결의 기본값은 120초입니다. NLB는 ALB나 CLB와 같은 수준으로 유휴 타임아웃을 구성할 수 있게 하지는 않습니다.

#### 3.1.2 연결 드레이닝(등록 해제 지연)

연결 드레이닝은 ALB와 NLB 맥락에서 "등록 해제 지연(deregistration delay)"으로 불리며, 인스턴스가 서비스에서 제거되기 전에 진행 중인 요청을 마무리할 수 있게 하는 메커니즘입니다. 이 기능은 다음과 같은 상황에서 매우 중요합니다.

- **인스턴스 종료:**
    인스턴스가 서비스에서 제외될 때(예: Auto Scaling 이벤트의 일부로), 연결 드레이닝은 활성 연결이 갑자기 종료되는 대신 작업을 완료할 수 있도록 보장합니다.
- **타깃 그룹 재구성:**
    백엔드 타깃이 비정상으로 표시되거나 교체되는 경우, 연결 드레이닝은 새 연결이 정상 상태인 타깃으로 리디렉션되기 전에 기존 세션이 처리를 마칠 수 있도록 유예 기간(1초에서 3,600초까지 구성 가능)을 제공합니다.

등록 해제 지연 동안 로드 밸런서는 드레이닝 중인 인스턴스로 새 요청을 보내지 않습니다. 하지만 이미 수립된 연결에 대한 요청은 정의된 타임아웃에 도달하거나 연결이 자연스럽게 닫힐 때까지 계속 전달합니다.

연결 드레이닝을 올바르게 구성하는 것은 특히 요청 처리 시간이 긴 애플리케이션에서 중요한 트랜잭션이 중간에 끊기지 않도록 보장하는 데 필요합니다.

### 3.2 라우팅 전략

로드 밸런서가 백엔드 타깃으로 트래픽을 라우팅하는 방식은 구성된 라우팅 알고리즘과 전략에 따라 결정됩니다. 이 절에서는 부하를 분산하는 데 사용되는 방법과, 필요할 때 세션 어피니티를 유지하는 메커니즘을 모두 살펴봅니다.

#### 3.2.1 요청 라우팅 알고리즘

들어오는 요청을 효율적으로 분산시키기 위해 다양한 라우팅 알고리즘을 사용할 수 있습니다.

- **라운드 로빈:**
    라운드 로빈 알고리즘에서는 요청이 순환 순서로 백엔드 타깃 사이에 균등하게 분배됩니다. 예를 들어 타깃이 세 개라면 첫 번째 요청은 타깃 1로, 두 번째는 타깃 2로, 세 번째는 타깃 3으로 가고 그다음 다시 순환합니다. 이 방법은 단순하며, 모든 타깃의 용량이 동일할 때 균등한 분산을 보장합니다.

- **가장 적은 처리 중 요청:**
    이 알고리즘은 새 요청을 현재 처리 중(대기 중이거나 완료되지 않은)인 요청이 가장 적은 백엔드 인스턴스로 보냅니다. 각 인스턴스의 부하를 동적으로 평가함으로써, 특히 요청 처리 시간이 가변적일 때 더 균형 잡힌 분산을 이끌어낼 수 있습니다.

- **플로 해시:**
    주로 NLB에서 사용되는 플로 해시 알고리즘은 연결의 여러 요소(프로토콜, 소스·대상 IP 주소와 포트, 심지어 TCP 시퀀스 번호까지)를 고려해 해시 값을 계산합니다. 이 해시는 어느 타깃이 연결을 처리할지 결정하여, 특정 TCP나 UDP 연결이 전체 기간 동안 항상 같은 백엔드 타깃으로 라우팅되도록 보장합니다. 이는 상위 계층의 세션 어피니티를 지원하지 않는 프로토콜에서 세션 상태를 유지하는 데 매우 중요합니다.

각 알고리즘은 애플리케이션의 특성과 워크로드 패턴에 따라 선택됩니다. 예를 들어 라운드 로빈은 동질적인 환경에서 효과적이고, 백엔드 인스턴스의 성능 특성이 서로 다를 때는 가장 적은 처리 중 요청 방식이 선호됩니다.

#### 3.2.2 세션 어피니티: 스티키 세션 구성

세션 어피니티(스티키 세션)는 같은 클라이언트의 이후 요청이 동일한 백엔드 인스턴스로 라우팅되도록 보장합니다. 이는 세션 상태가 공유 저장소가 아니라 백엔드에 로컬로 유지될 때 특히 중요합니다.

**스티키 세션의 동작 방식:**

![ELB Sticky Sessions](@site/docs/Networking%20and%20Content%20Delivery/_assets/elb_sticky_sessions.png)

- **쿠키 기반 메커니즘:**
    스티키 세션이 활성화되면 로드 밸런서는 쿠키를 사용해 클라이언트의 최초 요청을 처리한 백엔드 인스턴스를 "기억"합니다. 두 가지 유형의 쿠키가 있습니다.
    - **로드 밸런서가 생성한 쿠키:**
        로드 밸런서가 자동으로 생성하며(로드 밸런서 유형에 따라 AWSALB나 AWSELB 같은 이름을 가짐), 만료 시간을 구성할 수 있습니다. 쿠키가 설정되면 클라이언트의 이후 요청에 이 쿠키가 포함되어, 로드 밸런서가 연결을 동일한 타깃으로 라우팅할 수 있게 됩니다.
    - **애플리케이션 기반 쿠키:**
        또는 애플리케이션이 세션 정보를 담은 자체 쿠키를 생성할 수도 있습니다. 이 경우 로드 밸런서를 구성해 커스텀 쿠키 이름을 인식하도록 해야 합니다.
- **구성과 만료:**
    스티키 세션이 활성 상태로 유지되는 기간은 구성 가능합니다. 기간을 짧게 설정하면 시간이 지남에 따라 더 균등한 부하 분산으로 이어질 수 있고, 기간을 길게 설정하면 사용자가 애플리케이션과 상호작용하는 동안 세션 상태가 일관되게 유지됩니다.

특정 백엔드가 불균형적으로 많은 사용자에게 "고정"되면 스티키 세션이 부하 불균형을 초래할 수 있습니다. 따라서 애플리케이션의 동작을 분석해 쿠키 만료 설정을 적절하게 조정하는 것이 매우 중요합니다.

### 3.3 존 간 로드 밸런싱: 트래픽 분산 최적화

존 간 로드 밸런싱은 로드 밸런서가 서로 다른 가용 영역(AZ)에 위치한 백엔드 타깃으로 트래픽을 균등하게 분산시키는 능력을 가리킵니다. 이 기능은 특히 AZ별 인스턴스 수가 다를 수 있는 환경에서 트래픽이 의도치 않게 단일 AZ에 집중되지 않도록 보장하는 데 필수적입니다.

**존 간 로드 밸런싱의 동작 방식:**
![elb-cross-zone](@site/docs/Networking%20and%20Content%20Delivery/_assets/elb-cross-zone.png)
- **균등한 트래픽 분산:**
    존 간 로드 밸런싱이 활성화되면, 특정 AZ의 로드 밸런서 인스턴스는 그 존에 위치하는지와 무관하게 모든 사용 가능한 타깃에 걸쳐 트래픽을 분산합니다. 예를 들어 두 AZ에 총 10개의 인스턴스(한 AZ에 2개, 다른 AZ에 8개)가 있다면, 각 로드 밸런서 노드는 로컬의 두 타깃에만 분산을 제한하지 않고 10개 인스턴스 전체에 걸쳐 트래픽을 균등하게 전달합니다.

- **구성 시 고려사항:**

    - **ALB:**
        Application Load Balancer는 기본적으로 존 간 로드 밸런싱이 활성화되어 있습니다. ALB에서는 특정 로드 밸런서 노드가 들어오는 트래픽의 50%를 받더라도, 등록된 모든 타깃에 걸쳐 그 트래픽을 균등하게 분산합니다.
    - **NLB와 GWLB:**
        Network Load Balancer와 Gateway Load Balancer는 기본적으로 존 간 로드 밸런싱이 비활성화되어 있습니다. 활성화할 수는 있지만, 트래픽이 AZ 경계를 넘을 수 있어 추가 데이터 전송 요금이 발생할 수 있습니다.
    - **CLB:**
        Classic Load Balancer는 기본적으로 존 간 로드 밸런싱이 비활성화되어 있지만, 원한다면 활성화할 수 있습니다. 활성화하면 CLB는 모든 AZ의 모든 인스턴스에 걸쳐 들어오는 트래픽을 균등하게 분산합니다.
- **데이터 전송 비용에 미치는 영향:**
    AWS에서는 가용 영역 간 데이터 전송에 추가 요금이 발생할 수 있습니다. 존 간 로드 밸런싱을 구성할 때는 이런 비용 영향을 이해하는 것이 중요합니다. ALB의 경우 존 간 로드 밸런싱이 기본적으로 활성화되어 있지만, 트래픽이 관리되는 방식 때문에 AZ 간 데이터 전송 요금은 적용되지 않습니다. 반면 NLB와 GWLB에서는 존 간 로드 밸런싱을 활성화하면 트래픽이 AZ 경계를 넘어가면서 요금이 발생할 수 있습니다.

**존 간 로드 밸런싱의 이점:**

- **리소스 활용 개선:**
    모든 백엔드 타깃이 자신의 용량에 비례해 트래픽을 받도록 보장하면 리소스 활용이 더 효율적이 되고 전반적인 성능이 개선됩니다.
- **내결함성 강화:**
    한 AZ에 문제가 발생해도 로드 밸런서는 다른 존의 타깃으로 트래픽을 계속 라우팅할 수 있어 고가용성이 유지됩니다.

## 4. 트래픽 처리와 프로토콜 지원

다양한 트래픽 유형과 프로토콜을 처리하는 능력은 AWS Elastic Load Balancing의 가장 큰 강점 중 하나입니다. 이 절에서는 ELB가 안전한 연결을 관리하고, HTTP 헤더를 처리하고, 클라이언트 IP 정보를 보존하며, gRPC 같은 고급 프로토콜을 지원하는 방법을 다룹니다.

### 4.1 SSL/TLS 종료: 인증서 관리와 암호화

보안은 모든 웹 애플리케이션에서 무엇보다 중요합니다. ELB는 계산 비용이 큰 SSL/TLS 암호화·복호화 작업을 백엔드 서버에서 대신 처리할 수 있습니다. SSL/TLS 종료라고 불리는 이 과정은 클라이언트 연결의 보안을 보장하면서도 백엔드 인스턴스가 암호화 연산의 부담에서 벗어날 수 있게 합니다.

#### 4.1.1 로드 밸런서에서의 SSL/TLS 종료

![elb-TLS Termination](@site/docs/Networking%20and%20Content%20Delivery/_assets/elb-tls_termination.png)

로드 밸런서에서 SSL/TLS 종료가 구성되면 다음과 같이 동작합니다.

- **클라이언트 연결:**
    클라이언트가 로드 밸런서와 HTTPS 연결을 수립합니다.
- **ELB에서의 복호화:**
    로드 밸런서는 설치된 SSL/TLS 인증서를 사용해 들어오는 요청을 복호화합니다.
- **백엔드로의 전달:**
    복호화된(또는 선택적으로 재암호화된) 트래픽이 백엔드 타깃으로 전달되며, 백엔드는 HTTP나 HTTPS로 트래픽을 받을 수 있습니다.

이 과정은 인증서 관리를 단순화할 뿐 아니라(인증서가 로드 밸런서에서 중앙집중식으로 관리되므로), 백엔드 서버의 암호화 부담을 줄여 성능도 개선합니다.

#### 4.1.2 AWS Certificate Manager(ACM)를 통한 인증서 관리

AWS Certificate Manager(ACM)는 로드 밸런서의 SSL/TLS 인증서를 관리하는 데 사용됩니다.

- **인증서 프로비저닝:**
    ACM에서 직접 퍼블릭 인증서를 무료로 요청하거나 자체 인증서를 가져올 수 있습니다.
- **자동 갱신:**
    ACM은 자신이 발급한 인증서를 자동으로 갱신할 수 있어 안전한 통신이 끊기지 않도록 보장합니다.
- **다중 도메인과 SNI:**
    Application Load Balancer와 Network Load Balancer는 SNI(Server Name Indication)를 사용해 여러 인증서를 지원합니다. SNI는 클라이언트가 요청한 호스트명에 따라 로드 밸런서가 올바른 인증서를 제시할 수 있게 합니다.

#### 4.1.3 보안 정책과 컴플라이언스

엄격한 컴플라이언스가 필요한 애플리케이션의 경우, 로드 밸런서는 미리 정의된 보안 정책을 지원합니다.

- **미리 정의된 보안 정책:**
    AWS는 지원되는 SSL/TLS 프로토콜, 암호, 서버 순서 선호도를 지정하는 여러 보안 정책(예: ELBSecurityPolicy-2016-08, ELBSecurityPolicy-FS)을 제공합니다.
- **커스텀 정책:**
    경우에 따라 조직은 내부 보안 표준을 충족하기 위해 커스텀 정책이 필요할 수 있습니다. 이런 정책은 로드 밸런서에 구성해 준수하는 연결만 허용되도록 할 수 있습니다.


### 4.2 HTTP 헤더: X-Forwarded-For와 X-Forwarded-Proto 사용

로드 밸런서가 SSL/TLS를 종료하거나 HTTP 트래픽을 프록시하는 경우, 백엔드 서버가 원본 클라이언트 정보를 파악할 수 있도록 보장해야 합니다. AWS ELB는 이를 위해 커스텀 HTTP 헤더를 사용합니다.

- **X-Forwarded-For:**
    이 헤더에는 원본 클라이언트의 IP 주소가 담겨 있습니다. 백엔드 서버는 요청이 로드 밸런서의 프라이빗 IP에서 오는 것으로 보지만, 이 헤더를 통해 클라이언트의 퍼블릭 IP 정보가 손실되지 않습니다.
- **X-Forwarded-Proto:**
    이 헤더는 클라이언트가 로드 밸런서에 연결할 때 사용한 프로토콜(HTTP 또는 HTTPS)을 나타냅니다. 이는 로드 밸런서가 SSL/TLS를 종료하고 트래픽을 HTTP로 전달할 때 특히 유용합니다.
- **X-Forwarded-Port:**
    일부 구성에서는 클라이언트가 로드 밸런서에 연결할 때 사용한 포트가 이 헤더에 포함됩니다.

이 헤더들을 사용해 백엔드 서버는 정확한 클라이언트 정보를 로그에 남기고, 프로토콜별 동작을 강제하며, 원본 연결 파라미터를 기반으로 보안 검사를 수행할 수 있습니다.

### 4.3 Proxy Protocol: 클라이언트 IP 정보 보존(레이어 4)

Network Load Balancer 같은 레이어 4에서 동작하는 로드 밸런서에서는, 로드 밸런서가 애플리케이션 계층 처리를 수행하지 않으므로 원본 클라이언트 IP 주소를 보존하는 것이 간단하지 않을 수 있습니다. 이를 해결하기 위해 AWS는 Proxy Protocol을 제공합니다.

#### 4.3.1 Proxy Protocol의 동작 방식

- **헤더 삽입:**
    Proxy Protocol이 활성화되면 로드 밸런서는 TCP 페이로드 앞에 작은 헤더를 붙입니다. 이 헤더에는 클라이언트의 IP 주소, 포트 번호, 기타 연결 세부 정보가 포함됩니다.
- **백엔드에서의 파싱:**
    백엔드 타깃은 클라이언트 정보를 추출하기 위해 Proxy Protocol 헤더를 파싱하도록 구성되어야 합니다. 추출되면 애플리케이션은 클라이언트의 IP를 로그에 남기고 이를 기반으로 라우팅이나 보안 결정을 내릴 수 있습니다.

#### 4.3.2 버전과 사용 사례

- **Proxy Protocol v1 vs. v2:**
    Classic Load Balancer와 Network Load Balancer는 서로 다른 버전의 Proxy Protocol을 사용합니다. 예를 들어 CLB는 버전 1을, NLB는 버전 2를 사용합니다.
- **활성화해야 할 때:**
    TCP나 TLS 연결에서 백엔드 타깃이 인스턴스 ID가 아니라 IP 주소로 등록되어 있다면, 원본 클라이언트 IP를 보존하기 위해 Proxy Protocol이 필수적입니다. UDP나 TCP_UDP 같은 프로토콜에서는 클라이언트 IP가 기본적으로 보존됩니다.

Proxy Protocol을 활용하면 순수한 레이어 4 환경에서도 백엔드 애플리케이션이 로깅, 모니터링, 보안 목적에 필요한 중요한 클라이언트 연결 세부 정보에 접근할 수 있습니다.

### 4.4 고급 프로토콜 지원: ALB의 gRPC

현대적인 마이크로서비스 아키텍처는 전송 계층으로 HTTP/2를 사용하는 고성능 오픈소스 범용 RPC 프레임워크인 gRPC를 점점 더 많이 채택하고 있습니다. Application Load Balancer는 gRPC 트래픽을 네이티브로 지원하도록 강화되었습니다.

#### 4.4.1 gRPC 개요

gRPC는 다음을 위해 설계되었습니다.

- **효율적인 통신:**
    gRPC는 요청 멀티플렉싱, 헤더 압축, 양방향 스트리밍을 지원하는 HTTP/2를 사용합니다. 이는 특히 마이크로서비스에서 상당한 성능 개선을 이끌어냅니다.
- **강한 타입의 계약:**
    Protocol Buffers를 인터페이스 정의 언어로 사용함으로써 gRPC는 서비스 계약이 명확하게 정의되고 엄격하게 강제되도록 보장합니다.
- **스트리밍 기능:**
    gRPC는 다양한 유형의 스트리밍(클라이언트, 서버, 양방향)을 지원해, 지속적인 통신이 필요한 애플리케이션에 실시간 데이터 교환을 가능하게 합니다.

#### 4.4.2 ALB와 gRPC의 통합

ALB의 gRPC 지원은 여러 이점을 가져옵니다.

- **네이티브 HTTP/2 지원:**
    gRPC가 HTTP/2에 의존하므로 ALB의 네이티브 HTTP/2 지원은 gRPC 트래픽을 라우팅하는 데 이상적인 선택입니다.
- **고급 라우팅:**
    콘텐츠 기반 라우팅 기능을 통해 ALB는 요청 메타데이터를 기반으로 gRPC 요청을 적절한 백엔드 서비스로 안내할 수 있습니다.
- **통합된 상태 확인:**
    ALB는 HTTP/HTTPS 타깃과 마찬가지로 gRPC 엔드포인트에도 상태 확인을 수행할 수 있어, 정상 상태인 마이크로서비스만 트래픽을 받도록 보장합니다.

이런 고급 프로토콜 지원은 AWS에서 마이크로서비스 아키텍처를 배포하는 과정을 단순화해, 개발자가 고성능이고 확장 가능하며 복원력 있는 애플리케이션을 구축할 수 있게 합니다.

## 5. 고급 배포 시나리오

조직이 IT 인프라를 발전시키면서, 온프레미스 데이터센터와 AWS 클라우드 환경을 연결하는 하이브리드 환경이 점점 더 흔해지고 있습니다. 이 절에서는 하이브리드 연결과 다중 VPC 아키텍처를 포함해 AWS Elastic Load Balancer를 고급 시나리오에서 배포하는 방법을 살펴봅니다.

### 5.1 하이브리드 연결: 온프레미스와 AWS 워크로드 연결하기

하이브리드 배포 시나리오는 온프레미스 환경을 AWS와 연결해, 조직이 레거시 시스템과 클라우드 네이티브 서비스를 모두 매끄럽게 활용할 수 있게 합니다. ELB는 이런 아키텍처에서 핵심적인 역할을 합니다.

#### 5.1.1 연결 수립하기

하이브리드 배포를 위해서는 먼저 온프레미스 데이터센터와 AWS 사이에 안전한 연결을 수립해야 합니다. 이는 다음을 통해 이루어질 수 있습니다.

- **VPN 연결:**
    VPN(Virtual Private Network)을 사용해 공용 인터넷을 통해 온프레미스 네트워크를 Amazon VPC에 안전하게 연결할 수 있습니다.
- **AWS Direct Connect:**
    더 높은 대역폭과 낮은 지연 시간을 원한다면 AWS Direct Connect가 온프레미스 데이터센터와 AWS 사이의 전용 네트워크 연결을 제공합니다.

연결이 수립되면 다음 단계는 온프레미스 워크로드를 AWS 로드 밸런싱과 통합하는 것입니다.

#### 5.1.2 온프레미스 서버를 위한 타깃 그룹 구성

하이브리드 시나리오에서 Application Load Balancer를 사용할 때는 다음을 고려합니다.

- **프라이빗 IP 타깃:**
    온프레미스 서버의 백엔드 타깃은 프라이빗 IP 주소로 등록해야 합니다. 이렇게 하면 트래픽이 데이터센터와 AWS 사이에 수립된 안전한 프라이빗 연결을 통해 라우팅되도록 보장됩니다.
- **하이브리드 환경 전반의 상태 확인:**
    온프레미스 서버의 가용성을 모니터링하도록 상태 확인을 구성할 수 있습니다. 그러면 로드 밸런서는 정상 상태인 엔드포인트로만 트래픽을 지능적으로 라우팅할 수 있습니다.
- **라우팅 고려사항:**
    지연 시간과 성능 요구에 따라 온프레미스 워크로드와 AWS 기반 워크로드를 위한 별도의 타깃 그룹을 만들 수 있습니다. 그런 다음 고급 라우팅 규칙으로 트래픽을 적절히 안내해 매끄러운 사용자 경험을 제공할 수 있습니다.

#### 5.1.3 VPC 피어링과 리전 간 연결

온프레미스와의 하이브리드 연결 외에도 AWS는 다중 VPC와 리전 간 배포도 지원합니다.

- **VPC 피어링:**
    VPC 피어링을 사용하면 두 개 이상의 VPC가 마치 같은 네트워크에 있는 것처럼 통신할 수 있습니다. 한 VPC의 Application Load Balancer가 피어링된 다른 VPC의 EC2 인스턴스로 트래픽을 라우팅해야 할 때는, 그 인스턴스들의 프라이빗 IP 주소로 타깃 그룹을 정의합니다.
- **리전 간 로드 밸런싱:**
    더 복잡하지만, Route 53과 Global Accelerator 같은 서비스를 사용해 AWS 리전 전반에 걸친 로드 밸런싱을 구성할 수도 있습니다. 이를 통해 사용자가 가장 가까운 사용 가능한 리전으로 안내되어 지연 시간이 줄어듭니다. 자세한 내용은 [이 AWS 문서](https://docs.aws.amazon.com/whitepapers/latest/real-time-communication-on-aws/cross-region-dns-based-load-balancing-and-failover.html)를 참고하세요.

    ![Cross-Region Load balancing](@site/docs/Networking%20and%20Content%20Delivery/_assets/cross-region-load-balancing.png)


#### 5.1.4 인터넷 대면 로드 밸런서 vs. 내부 로드 밸런서

하이브리드 솔루션을 설계할 때는 인터넷 대면 로드 밸런서와 내부 로드 밸런서의 차이를 이해하는 것이 중요합니다.

- **인터넷 대면 로드 밸런서:**
    이 로드 밸런서들은 퍼블릭 IP 주소를 가지며 퍼블릭 서브넷에 배포됩니다. 인터넷에서 오는 트래픽을 처리하는 데 사용되며, 흔히 프라이빗 서브넷에 있는 백엔드 인스턴스로 트래픽을 라우팅합니다.
- **내부 로드 밸런서:**
    내부 로드 밸런서는 프라이빗 서브넷에 배포되며 인터넷에서 직접 접근할 수 없습니다. AWS 네트워크 내부의 애플리케이션 사이, 또는 AWS와 온프레미스 환경 사이의 트래픽을 라우팅하는 데 사용됩니다.
- **듀얼 스택 지원:**
    인터넷 대면 로드 밸런서는 듀얼 스택(IPv4와 IPv6) 엔드포인트로 구성할 수 있습니다. 클라이언트 연결이 IPv6를 사용할 수 있지만, 백엔드로의 트래픽은 IPv4로 유지되어 레거시 시스템과의 호환성이 보장됩니다.

## 6. 보안과 네트워크 제어

안전하고 잘 관리된 네트워크는 모든 프로덕션 환경의 근간입니다. 이 절에서는 보안 그룹, 아웃바운드 규칙, 관리형 프리픽스 목록 사용을 포함해 AWS Elastic Load Balancing에 필수적인 보안 조치를 살펴봅니다.

### 6.1 ELB 보호: 인바운드/아웃바운드 트래픽을 위한 보안 그룹

보안 그룹은 로드 밸런서와 백엔드 인스턴스를 포함한 AWS 리소스의 인바운드·아웃바운드 트래픽을 제어하는 가상 방화벽 역할을 합니다.

#### 6.1.1 로드 밸런서용 보안 그룹 구성

- **ELB 인바운드 규칙:**
    인터넷 대면 로드 밸런서의 경우, 보안 그룹은 일반적으로 모든 IP 주소(0.0.0.0/0)에서 80번(HTTP)과 443번(HTTPS) 포트로의 인바운드 트래픽을 허용하도록 구성됩니다. 이는 어디서든 클라이언트가 애플리케이션에 접근할 수 있도록 보장합니다.
- **ELB 아웃바운드 규칙:**
    아웃바운드 규칙은 로드 밸런서가 트래픽을 어디로 보낼 수 있는지 결정합니다. 기본적으로 이 규칙들은 모든 목적지로의 트래픽을 허용할 수 있습니다. 다만 보안을 강화하려면 아웃바운드 트래픽을 특정 CIDR 블록이나 목적지(예: Amazon S3 엔드포인트)로 제한할 수 있습니다.

#### 6.1.2 백엔드 인스턴스 보호

- **트래픽 출처 제한:**
    백엔드 EC2 인스턴스는 로드 밸런서의 보안 그룹에서 오는 트래픽만 허용하는 보안 그룹으로 구성해야 합니다. 이는 인스턴스가 공용 인터넷에 직접 노출되지 않도록 보장합니다.
- **계층화된 보안:**
    로드 밸런서와 백엔드 인스턴스 모두 엄격한 규칙을 가진 보안 그룹으로 보호되는 계층화된 보안 접근 방식을 채택하면 전반적인 보안 태세가 크게 강화됩니다.

#### 6.1.3 모범 사례

- **최소 권한 원칙:**
    필요한 최소한의 트래픽만 허용하도록 보안 그룹을 구성하세요. 예를 들어 백엔드 인스턴스가 로드 밸런서로부터의 트래픽만 받아야 한다면, 로드 밸런서의 보안 그룹을 유일한 소스로 지정하세요.
- **정기적인 감사:**
    보안 그룹 규칙을 정기적으로 검토하고 업데이트해 변화하는 보안 요구사항과 모범 사례를 준수하도록 하세요.

### 6.2 관리형 프리픽스 목록: IP 허용 목록 관리 단순화

보안 그룹과 라우팅 테이블에서 IP 주소 범위를 수동으로 관리하는 것은 특히 대규모 환경에서는 번거롭고 오류가 발생하기 쉽습니다. AWS 관리형 프리픽스 목록은 IP 허용 목록 관리와 네트워크 관리를 단순화하는 해법을 제공합니다.

#### 6.2.1 프리픽스 목록이란?

프리픽스 목록은 일련의 IP 주소를 나타내는 CIDR 블록의 집합입니다. AWS는 두 가지 유형의 프리픽스 목록을 제공합니다.

- **AWS 관리형 프리픽스 목록:**
    이 목록들은 AWS 서비스(예: Amazon S3, Amazon CloudFront, DynamoDB)의 IP 범위를 담고 있습니다. 사용자가 수정할 수는 없지만 보안 그룹 규칙에서 참조할 수 있습니다.
- **고객 관리형 프리픽스 목록:**
    자체 프리픽스 목록을 만들고 관리할 수 있어, 자주 사용하는 CIDR을 묶어 여러 보안 그룹과 라우팅 테이블에서 참조할 수 있습니다. 이런 중앙집중화는 네트워크 관리를 단순화하고 일관성을 보장합니다.

#### 6.2.2 프리픽스 목록 사용의 이점

- **관리 단순화:**
    각 보안 그룹 규칙에 여러 개별 CIDR 블록을 지정하는 대신 하나의 프리픽스 목록을 참조할 수 있습니다.
- **중앙집중식 업데이트:**
    프리픽스 목록이 업데이트되면 이를 참조하는 모든 보안 그룹이 자동으로 변경 사항을 반영해 관리 부담이 줄어듭니다.
- **보안 강화:**
    프리픽스 목록을 사용하면 특정 IP 범위로부터의 트래픽을 허용하거나 거부하는 명확하고 관리하기 쉬운 방법을 제공해 엄격한 네트워크 분리와 접근 제어를 강제하는 데 도움이 됩니다.

#### 6.2.3 구현 시 고려사항

- **계정 간 공유:**
    고객 관리형 프리픽스 목록은 여러 AWS 계정 간에 공유할 수 있습니다. 이는 일관된 네트워크 정책을 적용해야 하는 다중 계정 조직에서 특히 유용합니다.
- **AWS 서비스와의 통합:**
    관리형 프리픽스 목록은 보안 그룹 구성, VPC 라우팅 테이블, 기타 네트워크 관련 설정에서 지원되어, 네트워크 보안 관리를 위한 일관된 메커니즘을 제공합니다.

## 7. 결론

이 장에서는 AWS Elastic Load Balancing의 폭과 깊이를 살펴보았습니다. 기본 개념부터 연결 관리의 세부 사항, 고급 프로토콜 지원, 하이브리드 배포 시나리오까지, AWS ELB는 현대적인 애플리케이션 아키텍처를 위한 다재다능하고 강력한 도구임을 확인할 수 있었습니다.
