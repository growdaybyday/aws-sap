# AWS Direct Connect

## 1. 소개

오늘날 클라우드 컴퓨팅 시대에 많은 조직이 중요한 워크로드와 데이터를 온프레미스 데이터센터와 클라우드 환경으로 나누는 하이브리드 전략을 채택하고 있습니다. AWS Direct Connect는 공용 인터넷을 거치지 않는 전용 물리 네트워크 링크를 제공함으로써 이 전략에서 핵심적인 역할을 합니다. 이 장에서는 하이브리드 연결의 중요성을 소개하고, Direct Connect의 고유한 특성을 설명하며, 현대 엔터프라이즈 아키텍처에서 그 역할을 다룹니다.

Direct Connect는 콘솔에서 그냥 만들어낼 수 있는 "가상" 서비스가 아닙니다. 물리적인 네트워크 포트, 광케이블 연결, 서드파티 콜로케이션 시설과의 조율이 필요합니다. VPC 생성 같은 많은 클라우드 서비스가 소프트웨어로 정의되는 것과 달리, Direct Connect는 실체가 있는 물리적 인프라를 다룹니다. 지연 시간과 안정적인 대역폭이 성능에 결정적인 오늘날의 경쟁적인 시장에서, 전용 링크가 주는 이점은 상당합니다. 지연 시간 감소, 데이터 전송 비용 절감, 네트워크 안정성 향상입니다.

이어지는 절에서는 Direct Connect 배포를 계획하기 전에 이해해야 할 개념과 절차를 자세히 설명합니다. 기술적 요구사항을 설명하고, 사용 가능한 연결 유형(전용 vs. 호스팅)을 다루며, 물리적 배선과 크로스커넥트부터 가상 인터페이스와 라우팅 메커니즘까지 모든 측면을 살펴봅니다.

## 2. 핵심 개념과 요구사항

AWS Direct Connect는 잘 정립된 네트워킹 원칙을 기반으로 합니다. 이 절에서는 Direct Connect가 하이브리드 환경에서 매끄럽게 동작하도록 하는 기본 요구사항을, 물리 계층부터 네트워크 프로토콜까지 다룹니다.

### 2.1 AWS Direct Connect 소개: 사용 사례와 이점

AWS Direct Connect는 조직의 기업 데이터센터와 AWS 클라우드 사이에 프라이빗한 전용 연결을 만드는 데 사용됩니다. 주요 이점은 다음과 같습니다.

- **일관된 대역폭과 낮은 지연 시간:** 공용 인터넷의 변동성을 피함으로써 Direct Connect는 예측 가능한 성능을 보장합니다.
- **비용 절감:** Direct Connect를 통한 데이터 전송 요금은 일반적으로 표준 인터넷 데이터 전송 요금보다 낮으며, 이는 대규모 또는 대용량 데이터 이동에서 특히 중요합니다.
- **보안 강화:** 연결이 프라이빗하므로 인터넷에 노출된 링크와 관련된 위험이 줄어듭니다.
- **하이브리드 아키텍처 지원:** 온프레미스 시스템이 AWS 서비스(S3 같은 퍼블릭 서비스와 VPC 내부의 프라이빗 리소스 모두)에 안정적으로 연결되어야 하는 시나리오에서 Direct Connect는 필수적입니다.

이런 이점들 덕분에 Direct Connect는 예측 가능한 성능과 보안이 무엇보다 중요한 모든 하이브리드 네트워크 설계에서 필수적인 구성 요소가 됩니다.

### 2.2 Direct Connect의 네트워크 요구사항

Direct Connect를 프로비저닝하기 전에 조직은 여러 기술적 전제조건을 충족해야 합니다.

- **물리적 연결:** 데이터센터에서 AWS Direct Connect 위치까지 전용 광케이블 링크를 프로비저닝해야 합니다. 이 연결은 단일 모드 광케이블을 사용하며, 정확한 케이블 유형은 포트 속도(예: 1Gbps, 10Gbps, 100Gbps)에 따라 결정됩니다.
- **레이어 2 고려사항:** 연결은 레이어 2에서 이더넷을 사용합니다. 특히 VLAN 태깅을 위한 802.1Q 표준으로 트래픽을 분리합니다. VLAN 태그는 하나의 물리 링크를 여러 논리적 인터페이스(가상 인터페이스, VIF)로 나눌 수 있게 합니다.
- **포트 구성:** 1Gbps보다 빠른 연결에서는, 양쪽 엔드포인트가 속도와 듀플렉스 모드에 합의하도록 포트의 자동 협상(auto-negotiation)을 비활성화해야 합니다.
- **IP와 BGP 요구사항:** 유효한 IP 주소 지정 체계가 마련되어 있어야 합니다. AWS는 BGP(Border Gateway Protocol)를 사용해 온프레미스 라우터와 AWS 디바이스 간에 경로를 교환합니다. 여러분의 장비는 추가 보안을 위한 MD5 인증을 포함해 BGP를 지원해야 합니다. 선택적으로 빠른 장애 감지를 위해 BFD(Bidirectional Forwarding Detection)를 활성화할 수도 있습니다.
- **라우팅 프로토콜:** BGP는 경로 교환뿐 아니라 경로 선택(AS_PATH, MED, local preference 같은 속성 사용)에도 사용됩니다. Direct Connect를 구성하고 문제를 해결하려면 이런 개념에 익숙해야 합니다.

### 2.3 BGP 기초: 자율 시스템(AS)과 ASN

BGP는 Direct Connect에서 핵심적인 역할을 합니다. BGP 용어에서 자율 시스템(AS)은 공통 라우팅 정책 하에 있는 IP 프리픽스의 집합입니다. ASN(Autonomous System Number)은 AS를 고유하게 식별합니다. 주요 사항입니다.

- **퍼블릭 vs. 프라이빗 ASN:** 퍼블릭 ASN은 IANA가 할당하며 전역적으로 유일합니다. Direct Connect에서는 이미 보유한 퍼블릭 ASN을 사용할 수도 있고, 프라이빗 ASN을 사용할 수도 있습니다. 이 선택은 경로가 광고되고 필터링되는 방식에 영향을 줄 수 있습니다.
- **16비트 vs. 32비트 ASN:** 역사적으로 ASN은 16비트였지만, 현재는 32비트 ASN도 지원됩니다. AWS는 특정 인터페이스에서 사용할 수 있는 범위에 제약을 둘 수 있습니다.
- **BGP 피어링:** VIF를 만들면 라우터와 AWS 엔드포인트 사이에 BGP를 사용해 피어링 세션을 수립합니다. ASN을 올바르게 구성하는 것은 BGP 경로가 안정적으로 교환되도록 하는 데 매우 중요합니다.

### 2.4 AWS 퍼블릭 IP 범위: `ip-ranges.json` 사용

AWS는 자사의 퍼블릭 IP 범위를 기계가 읽을 수 있는 JSON 파일([ip-ranges.json](https://ip-ranges.amazonaws.com/ip-ranges.json))로 게시합니다. 이 파일은 AWS 서비스가 사용하는 모든 퍼블릭 IP 프리픽스를 나열하며, 다음과 같은 이유로 매우 중요합니다.

- **방화벽 구성:** 온프레미스 네트워크에서 AWS 서비스로의 접근(또는 그 반대)을 제한하려면 ip-ranges.json을 사용해 정확한 방화벽 규칙을 구성할 수 있습니다.
- **경로 필터링:** 이 파일은 Direct Connect 연결을 통해 어떤 AWS IP 범위에 접근할 수 있는지 필터링하는 데 도움이 되어, 지역별 또는 서비스별 연결 정책을 강제할 수 있게 합니다.
- **동적 업데이트:** AWS가 인프라를 확장하면서 ip-ranges.json도 업데이트됩니다. 자동화(예: SNS 알림과 Lambda 함수 사용)를 통해 네트워크 정책을 최신 상태로 유지할 수 있습니다.

## 3. Direct Connect 연결 유형과 설정

물리 계층과 프로토콜 요구사항을 이해했다면, 이제 Direct Connect 연결을 어떻게 프로비저닝할지 결정해야 합니다. 크게 전용 연결과 호스팅 연결, 두 가지 옵션이 있습니다.

### 3.1 연결 유형: 전용 연결 vs. 호스팅 연결

#### 전용 연결

전용 연결은 AWS Direct Connect 위치에서 여러분에게 할당된 물리적 포트입니다. 주요 특성은 다음과 같습니다.

- **대역폭 옵션:** 전용 연결은 표준 용량(일반적으로 1Gbps, 10Gbps, 100Gbps)으로 제공됩니다.
- **물리 포트 소유:** 전용 연결을 신청하면 실질적으로 AWS Direct Connect 라우터의 포트를 예약하게 됩니다.
- **주문 절차:** AWS Direct Connect 콘솔에서 요청을 시작합니다. AWS는 선택한 위치에 포트를 프로비저닝하고 LOA-CFA(Letter of Authorization and Connecting Facility Assignment)를 제공합니다. 이 문서는 여러분(또는 선택한 네트워크 공급자)이 콜로케이션 시설에서 물리적 크로스커넥트를 완료하는 데 필요합니다.
- **설정 시간:** 물리적 포트 프로비저닝과 크로스커넥트가 필요하므로 완료까지 몇 주(일반적으로 4~12주)가 걸릴 수 있습니다.
- **VIF 유연성:** 전용 연결에서는 여러 가상 인터페이스(연결당 최대 50개)를 만들 수 있습니다. 즉 연결을 논리적으로 퍼블릭, 프라이빗, 트랜짓 VIF로 세분화해 다양한 연결 요구를 충족할 수 있습니다.

#### 호스팅 연결

호스팅 연결은 1Gbps 미만(예: 50Mbps, 100Mbps, 또는 다른 소규모 단위)의 연결을 제공합니다. 주요 특징은 다음과 같습니다.

- **간접 프로비저닝:** 기반이 되는 물리 연결을 소유하지 않습니다. 대신 AWS Direct Connect 파트너("호스트")가 자신의 전용 연결에서 대역폭을 할당해 여러 고객에게 나눠 줍니다.
- **단일 VIF 제한:** 각 호스팅 연결은 하나의 가상 인터페이스만 지원할 수 있습니다. 여러 VIF가 필요하다면 추가 호스팅 연결을 요청해야 합니다.
- **요금 모델:** 호스팅 연결은 공유되므로, AWS는 할당된 대역폭을 초과하지 않도록 트래픽 폴리싱을 적용합니다.
- **적합한 사용 사례:** 호스팅 연결은 높은 대역폭이 필요하지 않거나, 전용 연결의 비용이나 준비 기간 없이 Direct Connect를 테스트해 보고 싶은 조직에 이상적입니다.

### 3.2 단계별 가이드: Direct Connect 연결 프로비저닝

전용 연결이든 호스팅 연결이든, 프로비저닝 과정은 몇 가지 핵심 단계를 따릅니다.

1. **AWS 리전과 Direct Connect 위치 선택:**
    연결할 AWS 리전을 결정하고, 기업 데이터센터에서 가장 가까운 Direct Connect 위치를 선택합니다. 이 선택은 지연 시간과 비용에 영향을 미칩니다.

2. **연결 요청 시작:**
    전용 연결의 경우 AWS Direct Connect 콘솔에 로그인해 위치, 포트 속도, 기타 파라미터를 지정하여 새 연결을 요청합니다. 호스팅 연결의 경우 12자리 AWS 계정 번호와 필요한 대역폭을 가지고 Direct Connect 파트너에게 연락합니다.

3. **LOA-CFA 수신(전용 연결의 경우):**
    AWS가 포트를 프로비저닝하고 LOA-CFA를 제공합니다. 이 문서에는 AWS 디바이스의 포트와 경계 정보 같은 세부 사항이 담겨 있습니다. 크로스커넥트를 설정하려면 이 LOA-CFA를 콜로케이션 공급자나 네트워크 서비스 파트너에게 전달해야 합니다.

4. **물리적 크로스커넥트 완료:**
    Direct Connect 위치에서 여러분의 장비(또는 파트너의 장비)와 AWS 라우터 사이에 크로스커넥트가 구성됩니다. 이미 해당 시설에 입주해 있다면 직접 크로스커넥트를 수행할 수 있고, 그렇지 않다면 Direct Connect 파트너가 도와줄 수 있습니다.

5. **신호와 연결 확인:**
    크로스커넥트가 완료되면 올바른 Tx(송신)와 Rx(수신) 광신호를 받고 있는지 확인합니다. 이 신호는 일반적으로 dBm(밀리와트당 데시벨) 단위로 측정되며, 허용 범위(예: -18에서 -25dBm) 안에 있어야 합니다.

6. **가상 인터페이스(VIF) 생성:**
    물리적 연결이 구성되면 AWS 콘솔에 다시 로그인해 하나 이상의 가상 인터페이스를 만듭니다. VIF가 퍼블릭인지, 프라이빗인지, 트랜짓인지 지정하고, 고유한 VLAN 태그를 할당하며, BGP 파라미터(피어 IP 주소, ASN, 선택적 MD5 인증 등)를 구성합니다.

7. **BGP와 라우팅 구성:**
    라우터와 AWS 엔드포인트 사이에 BGP 피어링 세션을 수립합니다. 올바른 경로가 교환되는지, 예상되는 프리픽스 수(퍼블릭 VIF는 최대 1,000개, 프라이빗 VIF는 최대 100개)가 수신되는지 확인합니다.

8. **연결 테스트:**
    BGP 세션이 활성화되고 VIF가 프로비저닝되면, 온프레미스 네트워크에서 AWS 리소스로의 연결을 테스트합니다. 라우팅 테이블과 성능 지표를 모니터링해 설정이 요구사항을 충족하는지 확인합니다.

9. **데이터 전송 시작과 요금 모니터링:**
    테스트가 성공하면 프로덕션에서 Direct Connect 연결을 사용하기 시작합니다. 연결이 활성화되는 즉시(포트 시간과 나가는 데이터 전송량 기준으로) 요금이 부과된다는 점을 기억하세요.

## 4. 가상 인터페이스(VIF)

물리적인 Direct Connect 연결은 데이터센터에서 AWS까지 이어지는 기반 "파이프"를 제공합니다. 하지만 이를 효과적으로 사용하려면 그 위에 논리적 인터페이스를 만들어야 합니다. 이 가상 인터페이스(VIF)는 여러분의 환경과 AWS 사이에서 네트워크 트래픽이 어떻게 라우팅될지를 정의합니다. 이 절에서는 VIF 개념, 구성 파라미터, 사용 가능한 세 가지 VIF 유형을 다룹니다.

### 4.1 Direct Connect 가상 인터페이스(VIF) 소개

가상 인터페이스는 Direct Connect 연결의 논리적 분할입니다. 두 가지 주요 목적을 수행합니다.

- **트래픽 세분화:** 서로 다른 VLAN 태그를 서로 다른 VIF에 매핑함으로써 서로 다른 목적의 트래픽을 분리할 수 있습니다(예: AWS 퍼블릭 서비스로의 접근과 VPC로의 프라이빗 연결을 분리).
- **다양한 엔드포인트로의 라우팅:** VIF는 여러분의 트래픽이 퍼블릭 엔드포인트(예: S3, DynamoDB)에 도달할지, VPC로 라우팅될지(Virtual Private Gateway를 통해), 아니면 대규모 VPC 상호 연결을 위해 Transit Gateway로 전달될지를 결정합니다.

### 4.2 VIF 구성 파라미터

VIF를 만들 때는 다음과 같은 주요 파라미터를 제공해야 합니다.

- **연결 연결:** VIF를 만들 기반 Direct Connect 연결(또는 LAG)을 선택합니다.
- **VIF 유형:** VIF가 퍼블릭, 프라이빗, 트랜짓 중 어느 것인지 선택합니다.
- **VIF 이름과 소유자:** 사용자 친화적인 이름을 할당하고 VIF를 소유할 AWS 계정을 지정합니다(다중 계정이나 호스팅 시나리오에서는 한 계정이 VIF를 만들고 다른 계정에서 "호스팅"할 수 있습니다).
- **VLAN 태그:** 고유한 802.1Q VLAN ID(1에서 4094 사이)를 지정합니다. 전용 연결에서는 이 값을 직접 선택하고, 호스팅 연결에서는 일반적으로 Direct Connect 파트너가 미리 할당합니다.
- **BGP 파라미터:** 다음을 포함한 BGP 세션 설정을 구성합니다.
    - BGP 피어 IP 주소(IPv4 또는 IPv6). 퍼블릭 VIF의 경우 AWS가 퍼블릭 IP 주소(주로 /30 또는 /31 블록)를 할당합니다. 프라이빗 VIF의 경우 일반적으로 169.254.0.0/16 범위에서 주소를 선택합니다.
    - 연결의 여러분 쪽 ASN(Autonomous System Number). 이는 소유하고 있다면 퍼블릭일 수도, 프라이빗일 수도 있습니다.
    - BGP용 MD5 인증 키(선택 사항).
    - 경로 광고 제한 같은 추가 파라미터(프라이빗 VIF는 100개 프리픽스, 퍼블릭 VIF는 1,000개 프리픽스).
- **MTU와 점보 프레임:** 점보 프레임을 활성화할지 결정합니다. 퍼블릭 VIF는 점보 프레임을 지원하지 않지만, 프라이빗과 트랜짓 VIF는 더 큰 MTU를 지원합니다(프라이빗 VIF는 최대 9,001바이트, 트랜짓 VIF는 최대 8,500바이트).

### 4.3 VIF의 유형

Direct Connect 연결 위에 만들 수 있는 가상 인터페이스에는 세 가지 유형이 있습니다.

![VIF](@site/docs/Networking%20and%20Content%20Delivery/_assets/vif.png)

#### 4.3.1 퍼블릭 VIF: AWS 퍼블릭 서비스 접근

퍼블릭 VIF는 온프레미스 네트워크가 전용 프라이빗 라우팅을 사용해 AWS 퍼블릭 엔드포인트(예: S3, DynamoDB, AWS 리소스의 퍼블릭 IP 주소)에 접근할 수 있게 합니다. 주요 사항입니다.

- **글로벌 도달 범위:** Direct Connect 연결이 물리적으로는 한 시설에 위치하지만, 퍼블릭 VIF는 여러 리전에 걸친 모든 AWS 퍼블릭 IP 범위에 대한 접근을 제공합니다.
- **BGP 경로 교환:** 고객의 퍼블릭 IP 프리픽스를 광고해야 하며, AWS는 자신의 퍼블릭 IP 범위를 광고합니다. AWS는 여러분이 광고하는 프리픽스가 실제로 소유한 것인지 검증합니다.
- **프리픽스 광고 제한:** 퍼블릭 VIF를 통해 최대 1,000개의 프리픽스를 광고할 수 있습니다.
- **점보 프레임 미지원:** 퍼블릭 VIF는 퍼블릭 엔드포인트로의 트래픽을 위해 설계되었으므로 점보 프레임을 지원하지 않습니다.

#### 4.3.2 프라이빗 VIF: Virtual Private Gateway(VGW)를 통한 VPC 연결

프라이빗 VIF는 VPC 내부의 리소스에 접근하는 데 사용됩니다. Virtual Private Gateway(VGW)에 직접 연결되거나, 여러 VGW에 연결되는 Direct Connect Gateway를 통해 간접적으로 연결됩니다. 중요한 고려사항입니다.

- **리전 범위:** 프라이빗 VIF는 연결 종단점과 동일한 AWS 리전의 VPC에 종속됩니다(리전 간 연결을 위해 Direct Connect Gateway를 사용하지 않는 한).
- **BGP 세션:** 온프레미스 라우터와 VGW 사이에 BGP 경로를 교환합니다. 고객 측에서는 일반적으로 최대 100개의 경로를 광고합니다.
- **MTU/점보 프레임:** 기반이 되는 Direct Connect 연결이나 LAG가 그에 맞게 구성되어 있다면, 프라이빗 VIF는 점보 프레임(최대 9,001바이트)을 지원합니다.
- **보안과 라우팅:** 프라이빗 VIF를 통한 트래픽은 공용 인터넷 트래픽과 분리되어 유지됩니다. 경로 전파가 활성화되어 있으면 BGP로 학습한 경로가 VPC 라우팅 테이블에 자동으로 전파될 수 있습니다.

#### 4.3.3 트랜짓 VIF: Transit Gateway(TGW)와의 통합

![Transit VIF](@site/docs/Networking%20and%20Content%20Delivery/_assets/transit_vif.png)

트랜짓 VIF는 Direct Connect 연결과 AWS Transit Gateway 사이의 연결에 사용됩니다. Transit Gateway는 수백에서 수천 개의 VPC를 연결하고, 심지어 서로 다른 리전의 온프레미스 네트워크를 상호 연결할 수 있게 합니다. 특징은 다음과 같습니다.

- **간접 연결:** 트랜짓 VIF는 Direct Connect Gateway에 연결되며, 이 Direct Connect Gateway는 다시 하나 이상의 Transit Gateway에 연결됩니다. 이 구성은 확장성 있는 대규모 VPC 간 통신을 가능하게 합니다.
- **라우팅과 집계:** 트랜짓 VIF는 Transit Gateway를 통해 여러 VPC 경로를 집계할 수 있게 해 효율적인 경로 관리를 지원합니다.
- **MTU/점보 프레임:** 트랜짓 VIF는 점보 프레임(최대 8,500바이트)을 지원하며, 이는 대량의 데이터를 전송할 때 유용합니다.
- **설계 유연성:** 하나의 트랜짓 VIF에 여러 Transit Gateway(Direct Connect Gateway당 최대 6개)를 연결할 수 있어, 중복성과 다중 리전 연결을 제공합니다.

## 5. Direct Connect 라우팅 정책과 BGP 커뮤니티

Direct Connect를 통한 라우팅은 어떤 경로가 선택되는지를 결정하는 BGP 프로토콜 파라미터부터, 퍼블릭과 프라이빗 연결을 구분하기 위해 AWS가 적용하는 구체적인 정책까지 여러 계층의 의사결정을 포함합니다. 이 절에서는 이런 라우팅 정책을 깊이 살펴봅니다.

### 5.1 퍼블릭 VIF 라우팅 정책과 시나리오

퍼블릭 VIF의 경우 라우팅 결정은 주로 BGP 속성과 최장 프리픽스 일치 원칙에 기반합니다. 온프레미스 네트워크와 AWS 퍼블릭 엔드포인트 사이로 트래픽이 흐를 때 다음을 고려해야 합니다.

- **최장 프리픽스 일치:** BGP는 항상 가장 구체적인(가장 긴) 프리픽스를 선택합니다. 동일한 목적지에 대해 /24와 /28을 모두 광고하면 /28이 선호됩니다.
- **정적 경로 vs. 전파된 경로:** 많은 시나리오에서 BGP로 학습한 AWS 경로는 자동으로 라우팅 테이블에 "전파"됩니다. 다만 여러분이 수동으로 구성한 정적 경로가 동적으로 학습된 경로보다 우선합니다.
- **BGP 속성:** AS_PATH, MED(Multi-Exit Discriminator), local preference 같은 속성이 경로 선택에 영향을 줍니다. 예를 들어 동일한 목적지로 가는 두 경로가 있다면, AS_PATH가 더 짧은 경로가 일반적으로 선호됩니다.
- **BGP 커뮤니티를 활용한 트래픽 엔지니어링:** 퍼블릭 VIF에서는 BGP 커뮤니티 태그로 경로 전파의 범위를 제어할 수 있습니다. 예를 들어 경로에 태그를 붙여 특정 AWS 리전이나 대륙 안에서만 광고되도록 할 수 있습니다. AWS는 커뮤니티 태그(예: 7224:9100 계열)를 사용해 경로가 Direct Connect 위치에 국한되는지, 특정 대륙에 국한되는지, 글로벌로 광고되는지를 나타냅니다.
- **인바운드 필터링:** 온프레미스 라우터에서 AWS로 경로를 보낼 때는, 광고하는 IP 프리픽스가 실제로 소유한 것인지 확인해야 합니다. AWS는 다른 고객이 잘못 광고한 경로가 수락되지 않도록 필터링을 사용합니다.
- **아웃바운드 선호도:** AWS에서 시작되어 온프레미스 네트워크로 향하는 트래픽의 경우, 여러 경로가 존재할 때(예: 액티브-액티브나 액티브-패시브 구성) 어느 Direct Connect 연결을 사용할지는 광고된 경로의 BGP 속성(AS_PATH 길이, MED, local preference 등)에 따라 결정됩니다.

### 5.2 퍼블릭 VIF BGP 커뮤니티

BGP 커뮤니티는 퍼블릭 VIF와 함께 사용되어 경로 전파를 더 세밀하게 조정합니다. 흔한 시나리오는 다음과 같습니다.

- **범위 제어:**
    - "local" 커뮤니티(예: 7224:9100)로 경로에 태그를 붙이면, 해당 AWS Direct Connect 리전 안에서만 경로가 광고되도록 보장할 수 있습니다.
    - 또는 "대륙 수준" 커뮤니티(예: 7224:9200)로 같은 대륙의 모든 AWS 리전까지 경로 광고를 확장할 수 있습니다.
    - 기본 동작(주로 7224:9300으로 표현됨)은 경로를 전역적으로 광고하는 것입니다.
- **인바운드와 아웃바운드 정책:**
    - 인바운드에서는 라우터가 AWS로 경로를 보낼 때, AWS가 이 경로를 의도한 범위 밖으로 전파하지 않도록 지시하는 커뮤니티 태그를 설정할 수 있습니다.
    - 아웃바운드에서는 AWS가 온프레미스 네트워크로 광고하는 경로에 커뮤니티 태그를 붙입니다. 에지 라우터에서 이 태그를 사용해 어떤 경로를 받아들일지 결정하거나 자체 라우팅 정책을 적용할 수 있습니다.
- **액티브-액티브 vs. 액티브-패시브:**
    - 여러 퍼블릭 VIF가 있다면, 커뮤니티 태그, local preference, AS_PATH 조작을 통해 BGP 속성을 조정해 로드 밸런싱(액티브-액티브)을 강제하거나 주·백업 링크(액티브-패시브)를 지정할 수 있습니다.

### 5.3 프라이빗 VIF 라우팅 정책과 BGP 커뮤니티

프라이빗 VIF(그리고 유사하게 트랜짓 VIF)의 경우, 초점은 VPC와 온프레미스 네트워크로 가는 경로만 교환되도록 보장하는 데 있습니다. 주요 사항입니다.

- **최장 프리픽스 일치:**
    - 동일한 기본 원칙이 적용됩니다. 가장 구체적인 프리픽스가 항상 선택됩니다.
- **리전 관련 고려사항:**
    - Virtual Private Gateway(VGW)나 Direct Connect Gateway에 연결할 때, 경로 전파가 활성화되어 있다면 AWS가 학습한 경로가 VPC의 라우팅 테이블에 자동으로 전파됩니다.
- **프리픽스 광고 제한:**
    - AWS는 프라이빗 VIF를 통해 광고할 수 있는 경로 수를 100개로 제한합니다. 이 제한을 초과해 광고하면 BGP 세션이 실패합니다.
- **경로 선택에 영향 주기:**
    - 여러 프라이빗 VIF가 존재하는 경우(예: 같은 리전 내 서로 다른 Direct Connect 위치에서), 기본 선택은 AWS 리전에서 Direct Connect 위치까지의 "거리"를 기준으로 이루어집니다. 이것이 충분하지 않다면 BGP 속성(예: AS_PATH)을 사용하고 광고하는 경로에 BGP 커뮤니티 태그를 설정해 결정에 더 영향을 줄 수 있습니다.
- **프라이빗 VIF의 BGP 커뮤니티:**
    - 프라이빗 VIF는 퍼블릭 VIF와 같은 수준의 범위 제어가 필요하지 않지만, BGP 커뮤니티를 여전히 사용해 경로 선택에 영향을 줄 수 있습니다(예: 액티브-패시브 구성을 강제하기 위해). 예를 들어 커뮤니티 태그로 한 VIF에 더 높은 local preference를 할당해 주 경로로 지정할 수 있습니다.

## 6. 확장성과 복원력

고가용성은 모든 엔터프라이즈 네트워크에서 매우 중요한 고려사항입니다. AWS Direct Connect는 연결이 복원력 있고 확장성 있으며 장애로부터 빠르게 회복할 수 있도록 여러 메커니즘을 제공합니다.

### 6.1 Link Aggregation Group(LAG): 연결 결합하기

![Link Aggregation Groups](@site/docs/Networking%20and%20Content%20Delivery/_assets/link_aggregation_groups.png)

Link Aggregation Group(LAG)은 여러 Direct Connect 연결을 하나의 논리적 연결로 결합할 수 있게 합니다. 두 가지 주요 이점이 있습니다.

- **대역폭 증가:** 예를 들어 네 개의 1Gbps 연결을 결합하면 4Gbps의 처리량을 갖는 하나의 유효한 파이프를 만들 수 있습니다.
- **복원력 향상:** LAG의 한 구성원에 장애가 발생해도 나머지 링크가 트래픽을 계속 처리합니다. LAG가 "정상"으로 간주되는 조건(예: 최소 활성 링크 수)을 정의할 수 있습니다.

LAG를 만들 때는 다음을 기억하세요.

- LAG의 모든 연결은 동일한 속도여야 합니다(예: 모두 1Gbps 또는 모두 10Gbps).
- 동일한 AWS Direct Connect 위치(이상적으로는 동일한 디바이스)에서 종단되어야 합니다.
- LAG는 전용 연결에서만 지원되며, 호스팅 연결에서는 지원되지 않습니다.
- LACP(Link Aggregation Control Protocol)를 사용해 그룹을 관리해, 트래픽이 균등하게 분산되고 장애가 신속하게 감지되도록 합니다.

### 6.2 연결 복원력: 고가용성을 위한 설계

다운타임을 최소화하려면 Direct Connect 아키텍처를 복원력 있게 설계해야 합니다. 옵션은 다음과 같습니다.

- **단일 위치의 이중 연결:**
    데이터센터에서 동일한 Direct Connect 위치로 두 개의 Direct Connect 연결을 프로비저닝하되, 서로 다른 AWS 디바이스에서 종단되게 합니다. 이는 단일 디바이스 장애로부터 보호합니다.
- **여러 Direct Connect 위치:**
    더 큰 복원력을 위해서는 지리적으로 분리된 Direct Connect 위치에 연결을 배포합니다. 이렇게 하면 한 위치에 장애(예: 광케이블 절단이나 전원 장애)가 발생해도 다른 위치의 백업 연결이 계속 동작합니다.
- **중복 가상 인터페이스:**
    전용 연결에서는 여러 VIF를 만들 수 있습니다. 액티브-패시브 구성에서는 하나의 VIF를 주 경로로 지정하고, 주 경로에 장애가 발생하면 보조 VIF가 그 역할을 대신할 수 있습니다. BGP 속성(예: 더 긴 AS_PATH나 더 낮은 local preference)을 사용해 백업 경로의 우선순위를 낮출 수 있습니다.
- **백업으로서의 VPN:**
    비용이 걱정되거나 최소한의 복원력만 필요하다면 VPN 연결을 백업으로 구성할 수 있습니다. VPN 트래픽은 공용 인터넷을 거치므로 일반적으로 지연 시간이 더 높지만, 추가적인 중복성 계층을 제공합니다.

### 6.3 BFD(Bidirectional Forwarding Detection)를 활용한 장애 감지

BFD는 1초 이내에 링크 장애를 감지할 수 있는 경량 프로토콜입니다. Direct Connect 인터페이스에서 BFD를 활성화하면 다음과 같습니다.

- **빠른 페일오버:**
    주 연결에 장애가 발생하면 BFD가 거의 즉시 장애를 감지해 백업 경로로의 페일오버를 유발할 수 있습니다.
- **가동 시간 향상:**
    BFD를 도입하면 Direct Connect 아키텍처가 일시적인 장애에 더 강해져 애플리케이션의 가용성이 유지됩니다.

## 7. 게이트웨이 통합

많은 조직에서 어려운 점은 AWS에 연결하는 것뿐만이 아니라, 여러 리전에 걸쳐(때로는 서로 다른 사업부가 소유한) 여러 VPC에 연결하는 것입니다. AWS는 Direct Connect를 대규모 네트워크에 통합하는 데 도움이 되는 두 가지 주요 게이트웨이 솔루션, 즉 Direct Connect Gateway와 Transit Gateway를 제공합니다.

### 7.1 Direct Connect Gateway: 프라이빗 VIF와 VGW 아키텍처

Direct Connect Gateway(DXGW)는 여러분의 Direct Connect 연결을 VPC에 연결된 하나 이상의 Virtual Private Gateway(VGW)에 연결할 수 있게 하며, 이는 그 VPC들이 서로 다른 리전에 있어도 가능합니다. 주요 사항입니다.

- **글로벌 연결:**
    DXGW는 글로벌 리소스입니다. 프라이빗 VIF를 DXGW에 연결하면 여러 AWS 리전의 VGW를 연결할 수 있습니다(단, VPC CIDR이 중복되지 않아야 합니다).
- **관리 단순화:**
    각 VPC마다 별도의 프라이빗 VIF를 만드는 대신, DXGW에 연결하는 하나의 VIF만 만들면 됩니다. 이 DXGW가 여러 VPC에 연결됩니다.
- **BGP 세션:**
    온프레미스 라우터와 DXGW 사이에 BGP 세션이 있습니다. VPC의 경로(각 VGW를 통해)는 이 세션을 통해 교환됩니다.
- **제약:**
    DXGW에 연결된 VPC들은 CIDR이 중복되지 않아야 합니다. 또한 DXGW는 여러 VPC로의 연결을 가능하게 하지만, 그 VPC들 사이의 전이적 라우팅은 지원하지 않습니다.

### 7.2 Transit Gateway 통합: 트랜짓 VIF와 TGW 아키텍처

AWS Transit Gateway(TGW)는 VPC와 온프레미스 네트워크를 연결하는 리전 단위 허브입니다. Direct Connect와 결합하면 아키텍처는 다음과 같습니다.

- **트랜짓 VIF 생성:**
    먼저 Direct Connect 연결에 트랜짓 VIF를 만듭니다. 이 트랜짓 VIF는 Direct Connect Gateway에 연결됩니다.
- **Direct Connect Gateway에서 TGW로:**
    이 DXGW는 다시 하나 이상의 Transit Gateway와 연결됩니다. 이를 통해 온프레미스 네트워크가 Transit Gateway에 연결된 여러 VPC와 통신할 수 있습니다.
- **확장성과 유연성:**
    Transit Gateway는 수백 개의 VPC 어태치먼트를 지원하며, 리전 간 연결을 위해 Transit Gateway를 리전 간에 피어링할 수도 있습니다.
- **비용 고려사항:**
    Transit Gateway는 추가적인 GB당 데이터 처리 요금이 발생한다는 점에 유의하세요. 처리량이 높은 환경에서는 이런 비용이 누적될 수 있으므로 신중한 아키텍처 설계가 필요합니다.

### 7.3 Direct Connect SiteLink: 다중 사이트 연결 단순화

![Direct Connect SiteLink](@site/docs/Networking%20and%20Content%20Delivery/_assets/direct_connect_sitelink.png)

Direct Connect SiteLink는 다중 사이트 연결을 간소화하는 비교적 새로운 기능입니다.

- **목적:**
    AWS 리전을 거치지 않고도 AWS의 글로벌 백본 네트워크를 통해 여러 온프레미스 위치를 상호 연결할 수 있게 합니다.
- **동작 방식:**
    Direct Connect VIF(프라이빗 또는 트랜짓)에서 SiteLink가 활성화되면, 지리적으로 분산된 사이트 간의 트래픽이 Direct Connect 위치를 거쳐 AWS 백본을 통해 흐를 수 있습니다. 이는 지연 시간을 줄이고 네트워크 설계를 단순화할 수 있습니다.
- **유연성:**
    SiteLink는 포트 속도나 연결 소유 방식(전용 vs. 호스팅)이 다르더라도 다양한 연결 유형에서 동작합니다.
- **비용 영향:**
    SiteLink는 아키텍처를 단순화하지만 추가적인 시간당 요금과 데이터 전송 요금이 발생합니다. 대용량, 저지연의 사이트 간 연결이 필요한 조직에 가장 적합합니다.

## 8. 보안과 성능

중요한 온프레미스 시스템을 클라우드에 연결할 때는 보안과 성능이 항상 최우선입니다. 이 절에서는 사용 가능한 암호화 옵션과 성능 최적화를 설명합니다.

### 8.1 Direct Connect 보안과 암호화

Direct Connect는 프라이빗 네트워크 링크를 제공하지만, 기본적으로 트래픽은 암호화되지 않습니다. 추가적인 보안 계층이 필요한 조직에는 몇 가지 선택지가 있습니다.

#### 암호화 옵션

- **레이어 4 암호화(Direct Connect 위의 VPN):**
    Direct Connect 연결 위에서 IPsec VPN을 운영할 수 있습니다. 이 경우 트래픽은 네트워크 계층(레이어 3/4)에서 암호화됩니다. 암호화가 필요하지만 Direct Connect의 성능 이점도 원할 때 흔히 사용됩니다. VPN은 퍼블릭 IP 주소를 사용해 Virtual Private Gateway나 Transit Gateway에서 종단됩니다.
- **레이어 2 암호화(MACSec):**
    MAC Security(MACSec)는 데이터 링크 계층(레이어 2)에서 암호화를 제공하는 IEEE 802.1 표준입니다. MACSec을 사용하면 전용 연결에 진입하는 순간부터 트래픽이 암호화됩니다. MACSec은 전용 연결에서만(선택된 Direct Connect 위치에서만) 사용할 수 있으며, AWS 엔드포인트와 온프레미스 라우터 모두 MACSec을 지원해야 할 수 있습니다.
- **애플리케이션 계층 보안:**
    많은 경우 애플리케이션 계층 프로토콜(예: TLS/SSL)을 사용해 종단 간 암호화를 달성할 수도 있습니다. 네트워크 링크 자체를 보호하지는 않지만, 민감한 데이터가 네트워크를 거치는 동안 암호화되도록 보장합니다.

#### 보안 모범 사례

- **엄격한 ACL과 방화벽 정책 구현:**
    ip-ranges.json 파일을 사용해 승인된 AWS 퍼블릭 서비스로 향하는 트래픽만 허용하도록 방화벽을 구성하세요.
- **BGP MD5 인증:**
    여러분과 AWS 엔드포인트 양쪽에서 항상 MD5 인증과 함께 BGP를 구성하세요. 이는 BGP 세션 하이재킹과 경로 스푸핑을 방지합니다.
- **네트워크 세분화:**
    VLAN 태깅을 사용해 트래픽을 논리적으로 분리하세요. 퍼블릭 VIF는 AWS 퍼블릭 엔드포인트로 향하는 트래픽만, 프라이빗 VIF는 내부 트래픽만 전달해야 합니다.
- **모니터링과 경보:**
    CloudWatch 경보를 설정해 이상 징후(예상치 못한 BGP 세션 플랩이나 비정상적인 오류율 등)를 모니터링하고 인시던트 대응 계획과 통합하세요.

### 8.2 성능 최적화: MTU와 점보 프레임 지원

특히 대량의 데이터를 전송하는 환경에서는 성능 최적화가 매우 중요합니다. 중요한 파라미터 중 하나가 MTU(Maximum Transmission Unit)입니다.

- **표준 MTU:**
    기본적으로 Direct Connect의 MTU는 1,500바이트입니다.
- **점보 프레임:**
    AWS는 현재(2018년 이후) Direct Connect 연결에서 점보 프레임을 지원합니다. 점보 프레임은 더 큰 패킷(프라이빗 VIF는 최대 9,001바이트, 트랜짓 VIF는 최대 8,500바이트)을 허용해 오버헤드를 줄입니다. 이는 라우터의 CPU 오버헤드를 줄이고 처리량을 늘립니다.
- **구성 요구사항:**
    온프레미스 장비와 기반이 되는 Direct Connect 연결(또는 LAG) 모두 점보 프레임을 지원하도록 구성되어 있는지 확인하세요. 퍼블릭 VIF는 점보 프레임을 지원하지 않습니다.
- **라우팅 관련 고려사항:**
    전파된 경로(BGP로 학습한 경로)만 점보 프레임을 지원하며, 정적 경로는 일반적으로 기본 1,500바이트 MTU를 사용합니다.

## 9. 모니터링, 요금, 문제 해결

운영 우수성에는 견고한 네트워크 설계뿐 아니라 모니터링, 비용 관리, 빠른 문제 해결 능력도 필요합니다. 이 절에서는 CloudWatch 지표, Direct Connect 요금 모델, 문제 진단을 위한 모범 사례를 다룹니다.

### 9.1 Amazon CloudWatch로 모니터링

Amazon CloudWatch는 Direct Connect 연결과 그에 연결된 가상 인터페이스의 상태와 성능을 모니터링하는 데 도움이 되는 여러 지표를 제공합니다.

- **ConnectionState:**
    물리적 연결이 정상(1)인지 비정상(0)인지 나타냅니다. 이 지표에 경보를 설정하면 장애를 즉시 알 수 있습니다.
- **트래픽 지표(BPS와 PPS):**
    - **인그레스와 이그레스 BPS:** 인바운드·아웃바운드 트래픽의 초당 비트 수를 측정합니다.
    - **초당 패킷 수(PPS):** 초당 패킷 수를 추적해 혼잡이나 성능 문제를 진단하는 데 도움이 됩니다.
- **오류 지표:**
    오류 수를 모니터링해 물리 계층 문제나 BGP 세션의 장애를 감지합니다.
- **광신호 레벨:**
    LightLevelTx와 LightLevelRx 같은 지표는 광케이블 연결의 상태에 대한 통찰을 제공합니다.
- **암호화 상태:**
    MACSec이 활성화되어 있다면, ConnectionEncryptionState 지표는 트래픽이 예상대로 암호화되고 있는지 나타냅니다.

CloudWatch에서 상세한 대시보드와 경보를 설정하면 Direct Connect 연결의 성능을 선제적으로 모니터링하고 이상 징후에 빠르게 대응할 수 있습니다.

### 9.2 Direct Connect 요금 모델: 비용 고려사항

AWS Direct Connect 요금은 크게 두 가지 범주로 나뉩니다.

#### 포트 시간 요금

- **정의:**
    Direct Connect 포트의 용량에 대해 시간당 요금이 부과됩니다. 데이터가 실제로 흐르는지 여부와 무관하게 이 요금이 발생합니다.
- **전용 vs. 호스팅:**
    시간당 요율은 포트 속도(예: 1Gbps, 10Gbps, 100Gbps)와 전용 연결인지 호스팅 연결인지에 따라 달라집니다(요금은 지리적 리전에 따라 다를 수 있습니다. 예를 들어 일본의 요율은 다른 리전과 다를 수 있습니다).
- **요금 시작 시점:**
    전용 연결의 경우 연결이 "사용 가능" 상태가 되면 요금이 시작됩니다. 호스팅 연결의 경우 AWS 계정에서 연결을 수락하는 순간부터 요금이 시작됩니다.

#### 나가는 데이터 전송(DTO) 요금

- **정의:**
    AWS에서 온프레미스 네트워크로 흐르는 데이터(나가는 데이터 전송)에 요금이 부과됩니다. AWS로 들어오는 데이터(인그레스)에는 요금이 부과되지 않습니다.
- **위치에 따른 차이:**
    DTO 요금은 데이터가 전송되는 AWS 리전과 Direct Connect 위치에 따라 달라집니다. 예를 들어 미국 기반 리전에서 미국의 Direct Connect 위치로 데이터를 전송하면 GB당 $0.02가 들 수 있고, 더 먼 리전에서의 전송은 더 비쌀 수 있습니다.
- **책임 소재:**
    다중 계정 환경에서는 일반적으로 리소스(예: S3 버킷이나 EC2 인스턴스)를 소유한 계정이 DTO 요금을 부담합니다.

### 9.3 Direct Connect 문제 해결: 레이어 1부터 레이어 4까지

가장 잘 설계된 네트워크도 문제를 겪습니다. Direct Connect 문제를 해결하려면 여러 계층을 확인해야 합니다.

#### 물리 계층(레이어 1)

- **크로스커넥트 확인:**
    콜로케이션 시설의 크로스커넥트가 Direct Connect 공급자에 의해 올바르게 완료되었는지 확인하세요.
- **광신호 레벨:**
    Tx(송신)와 Rx(수신) 광신호가 허용 범위 안에 있는지 확인하세요. 큰 편차가 있다면 광케이블 손상이나 하드웨어 문제를 의미할 수 있습니다.
- **하드웨어 확인:**
    온프레미스 라우터와 AWS 라우터가 모두 전원이 켜져 있고 올바르게 구성되어 있는지 확인하세요.

#### 데이터 링크 계층(레이어 2)

- **VLAN 태깅:**
    올바른 802.1Q VLAN 태그가 구성되어 있는지, 충돌이 없는지 확인하세요. 여러 VIF가 동일한 물리 연결을 공유한다면 각각 고유한 VLAN ID를 가져야 합니다.
- **자동 협상 설정:**
    1Gbps보다 빠른 연결에서 일관된 포트 설정을 위해 자동 협상이 비활성화되어 있는지 확인하세요.

#### 네트워크 계층(레이어 3)

- **BGP 세션:**
    BGP 세션의 상태를 확인하세요. BGP 피어 IP 주소, ASN, MD5 인증 키가 올바르게 구성되어 있는지 확인하세요.
- **프리픽스 광고:**
    올바른 개수의 프리픽스가 광고되고 있는지 확인하세요(프라이빗 VIF는 최대 100개, 퍼블릭 VIF는 최대 1,000개). 과도한 광고는 세션 플랩을 유발할 수 있습니다.
- **라우팅 테이블 일관성:**
    정적 경로와 BGP로 동적으로 학습한 경로가 올바른지, 의도한 최장 프리픽스 일치가 적용되고 있는지 확인하세요.

#### 전송 계층(레이어 4)

- **TCP 179번 포트:**
    BGP에 필요한 TCP 179번 포트를 방화벽이 차단하고 있지 않은지 확인하세요.
- **연결 타이밍:**
    TCP 세션을 방해할 수 있는 패킷 조각화나 지연 문제가 없는지 확인하세요.

각 계층에서의 문제 해결 단계로도 문제가 해결되지 않는다면, CloudWatch 로그를 검토하고 AWS Support나 Direct Connect 공급자에게 문의하는 것을 고려하세요.

## 10. 확장성 있고 복원력 있는 설계를 위한 모범 사례

AWS Direct Connect로 아키텍처를 설계할 때는 다음과 같은 모범 사례를 고려하세요.

- **중복성을 갖춘 설계:**
    항상 서로 다른 위치나 서로 다른 AWS 디바이스에 최소 두 개의 Direct Connect 연결을 프로비저닝하세요. 미션 크리티컬한 워크로드라면 최대 복원력 옵션(예: 두 개의 서로 다른 Direct Connect 위치에 이중 연결)을 고려하세요.
- **더 큰 대역폭과 복원력을 위해 LAG 사용:**
    LAG를 사용해 여러 전용 연결을 결합하면 더 높은 처리량을 달성하고 물리 계층에서 중복성을 제공할 수 있습니다.
- **트래픽 유형 분리:**
    서로 다른 트래픽 유형에는 서로 다른 VIF를 사용하세요. 예를 들어 퍼블릭 트래픽(AWS 퍼블릭 서비스 접근용)과 프라이빗 트래픽(VPC 리소스 접근용)을 분리하세요. 이는 잘못된 라우팅의 위험을 최소화하고 문제 해결을 단순화합니다.
- **BGP 커뮤니티와 경로 엔지니어링 활용:**
    BGP 속성(local preference, AS_PATH 조작, MED)과 커뮤니티 태그를 사용해 라우팅을 제어하고, 필요에 따라 액티브-액티브나 액티브-패시브 구성을 구현하세요.
- **지속적인 모니터링:**
    포괄적인 CloudWatch 대시보드와 경보를 설정하세요. 물리 계층(광신호 강도, 오류 수)과 논리 계층(BGP 세션 상태, 트래픽 지표)을 선제적으로 모니터링하세요.
- **성장을 고려한 계획:**
    미래의 확장을 염두에 두고 네트워크를 설계하세요. Direct Connect Gateway와 Transit Gateway를 사용해 새 VPC나 AWS 계정을 추가하는 과정을 단순화하세요.
- **보안 모범 사례 통합:**
    BGP 세션에서 항상 MD5 인증을 강제하고, ip-ranges.json 기반 필터링으로 경로 광고를 제한하세요. 암호화가 필요하다면 적절한 보호 계층을 선택하세요(레이어 3/4는 Direct Connect 위의 VPN, 레이어 2는 MACSec).
- **철저히 문서화하고 테스트:**
    프로덕션으로 전환하기 전에 사전 프로덕션 환경에서 광범위하게 테스트하세요. BFD와 액티브-패시브 구성을 사용해 페일오버 시나리오를 검증하고, 향후 문제 해결을 위해 구성을 문서화하세요.

## 11. 결론

AWS Direct Connect는 온프레미스 네트워크와 AWS 클라우드 사이에 안전하고 고성능인 하이브리드 연결을 가능하게 하는 강력한 서비스입니다. 전용 광케이블 연결과 VLAN 태깅부터 BGP 라우팅, VIF 구성, 게이트웨이 통합까지 물리적·논리적 구성 요소를 이해함으로써, 조직은 성능과 보안 요구사항을 모두 충족하는 견고한 아키텍처를 설계할 수 있습니다.
