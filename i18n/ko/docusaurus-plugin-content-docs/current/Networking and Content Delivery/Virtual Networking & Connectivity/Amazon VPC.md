# AWS Virtual Private Cloud (VPC)

## 1. 소개

Amazon VPC는 AWS에서 이루어지는 거의 모든 네트워크 배포의 기반입니다. AWS 환경 안에 여러분만의 격리된 "프라이빗 클라우드"를 제공합니다. 이 장에서는 기본 개념과 아키텍처부터 고급 구성, 보안, 연결 기능까지 VPC 기술을 종합적으로 살펴봅니다.

## 2. VPC 핵심 아키텍처

### 2.1 Amazon VPC란?

Amazon Virtual Private Cloud(VPC)는 AWS 클라우드 안에서 논리적으로 격리된 영역으로, 여러분이 직접 정의한 가상 네트워크 안에서 AWS 리소스를 실행할 수 있게 합니다. 자체 물리적 데이터센터를 구축하는 것과 비슷하게, VPC는 IP 주소 범위 선택, 서브넷 생성, 라우팅 테이블 구성, 네트워크 게이트웨이 등 가상 네트워크 환경에 대한 제어권을 제공합니다. VPC 안에서는 여러분만의 프라이빗 네트워킹 공간을 갖게 되어, Amazon EC2 인스턴스, RDS 데이터베이스, 그 외 다양한 서비스를 안전하고 통제된 방식으로 실행할 수 있습니다.

본질적으로 VPC는 전통적인 네트워크의 아키텍처를 모방하도록 설계되었습니다.

- **격리:** 각 VPC는 다른 모든 VPC 및 다른 AWS 고객으로부터 논리적으로 분리되어 있습니다.
- **커스터마이징:** IP 주소 지정(CIDR 표기법 사용)을 선택하고, 여러 AZ에 걸쳐 하나 이상의 서브넷을 만들고, 트래픽 흐름을 결정하는 라우팅 규칙을 설계합니다.
- **연결성:** VPC를 사용하면 AWS 환경을 온프레미스 데이터센터에 연결하거나 다른 VPC와 피어링할 수 있으며, 이 모든 트래픽은 프라이빗하게 유지됩니다.

### 2.2 범위와 경계: AWS 계정, 리전, 가용 영역

VPC가 전체 AWS 아키텍처 안에서 어떻게 위치하는지 이해하는 것이 중요합니다. AWS의 최상위 경계는 AWS 계정이며, 이를 통해 여러 AWS 리전에 접근할 수 있습니다. 각 리전은 여러 가용 영역으로 구성된 독립된 지리적 영역입니다. VPC를 만들 때는 특정 리전 안에서 생성하게 됩니다. VPC 자체는 그 리전에 국한되므로, 다른 리전에서도 비슷한 연결이 필요하다면 별도의 VPC를 만들어야 합니다.

한 리전 안에서 각 가용 영역은 독립적인 전원, 냉각, 네트워킹을 갖춘 독립된 데이터센터를 나타냅니다. 고가용성과 내결함성을 설계할 때는 서브넷을 여러 AZ에 분산시킬 수 있습니다. 예를 들어 세 개의 서로 다른 AZ에 걸친 세 개의 서브넷에 EC2 인스턴스를 실행하면, 한 AZ를 사용할 수 없게 되어도 나머지 영역을 통해 애플리케이션에 계속 접근할 수 있습니다.

핵심 사항입니다.

- **AWS 계정:** 리소스를 담는 최상위 컨테이너입니다.
- **리전:** VPC가 생성되는 지리적 영역(예: 미국 동부, EU 서부)입니다.
- **가용 영역(AZ):** 격리와 고가용성을 제공하는, 리전 내 물리적으로 분리된 위치입니다.
- **VPC 배치:** VPC는 리전 안에서 생성되며, 서브넷은 특정 AZ와 연결됩니다.

### 2.3 VPC 구성 요소

![vpc-core](@site/docs/Networking%20and%20Content%20Delivery/_assets/vpc-core.png)

VPC를 구성하는 기본 요소들은 물리적 네트워크의 요소와 유사합니다.

- **IP 주소 범위:** VPC를 만들 때 CIDR(Classless Inter-Domain Routing) 표기법(예: 10.0.0.0/16)으로 IP 주소 범위를 할당합니다. 이 범위가 프라이빗 IP 주소를 할당하는 풀이 됩니다.
- **서브넷:** 서브넷은 VPC의 IP 주소 범위를 나눈 세그먼트입니다. VPC를 하나 이상의 서브넷으로 나누며, 각 서브넷은 특정 AZ와 연결됩니다. 서브넷은 퍼블릭(인터넷에 직접 접근 가능)이나 프라이빗(인터넷에 직접 노출되지 않음)으로 지정할 수 있습니다.
- **라우팅 테이블:** 라우팅 테이블은 아웃바운드·인바운드 트래픽의 경로를 정의해 VPC 내부의 트래픽 흐름을 제어합니다. 모든 VPC에는 기본적으로 메인 라우팅 테이블이 생성되지만, 세밀한 제어를 위해 커스텀 라우팅 테이블을 만들 수도 있습니다.
- **인터넷 게이트웨이(IGW):** IGW는 수평 확장이 가능하고 중복성을 갖춘 고가용성 VPC 구성 요소로, VPC 내 인스턴스와 인터넷 간 통신을 가능하게 합니다.
- **NAT 디바이스:** 프라이빗 서브넷에서 아웃바운드 인터넷 접근을 허용하려면 NAT(Network Address Translation) 디바이스(NAT 게이트웨이 또는 NAT 인스턴스)를 사용합니다.
- **보안 메커니즘:** 보안 그룹(인스턴스 수준, 스테이트풀 방화벽)과 네트워크 ACL(서브넷 수준, 스테이트리스 필터)은 네트워크의 서로 다른 계층에서 보안 정책을 강제합니다.
- **DNS와 DHCP:** 모든 VPC에는 내장된 DNS 리졸버(Amazon이 제공하는 DNS 서버, Route 53 리졸버로도 불림)와, 인스턴스에 IP 구성 정보를 자동으로 할당하는 DHCP 옵션 세트가 포함되어 있습니다.

정리하면, VPC의 핵심 아키텍처는 전통적인 온프레미스 네트워크의 많은 측면을 그대로 재현하면서도, AWS 클라우드의 확장성·안정성·유연성을 갖춘 완전하고 커스터마이징 가능한 가상 네트워크를 정의할 수 있게 합니다.

## 3. IP 주소 지정과 서브넷 설계

### 3.1 CIDR 기초: VPC IP 범위 설계

VPC를 계획할 때 가장 먼저 결정해야 할 사항 중 하나는 IP 주소 범위를 어떻게 할당할지입니다. CIDR 표기법(예: 10.0.0.0/16)은 네트워크의 크기를 정의하는 데 사용됩니다. CIDR에서 "/16"은 처음 16비트가 네트워크 부분에 사용되고 나머지 비트가 호스트 주소로 남는다는 의미입니다. /16 네트워크에서는 최대 2^16(65,536)개의 주소를 가질 수 있습니다. 이후 서브넷을 만들 때는 VPC 전체 CIDR 블록에서 더 작은 범위를 떼어냅니다.

예를 들어

- CIDR이 10.0.0.0/16인 VPC는 65,536개의 주소를 제공합니다.
- 이후 10.0.1.0/24 같은 CIDR 블록으로 서브넷을 만들면 서브넷당 256개의 주소를 제공합니다.

AWS는 내부 네트워킹 목적으로 각 서브넷에서 5개의 IP 주소(처음 4개와 마지막 1개)를 예약한다는 점을 기억하세요. 따라서 실제 사용 가능한 주소 수는 이론적인 최댓값보다 약간 적습니다.

트레이드오프를 이해해야 합니다.

- 더 큰 CIDR 블록(예: /16)을 사용하면 많은 서브넷을 만들 여유가 생깁니다.
- 서브넷당 IP 주소가 몇 개만 필요할 때는 더 작은 서브넷 크기(예: /28)를 사용할 수 있지만, 최소한 총 16개의 주소(사용 가능한 주소는 11개)가 필요합니다.
- 향후 성장을 미리 계획하고, 특히 다중 VPC나 하이브리드 환경에서 IP 범위가 중복되지 않도록 하는 것이 매우 중요합니다.

### 3.2 IPv4 vs. IPv6: 듀얼 스택 지원과 사용 사례

IPv4가 여전히 널리 사용되고 있지만 주소 공간에는 한계가 있습니다. AWS는 VPC에서 IPv4와 IPv6를 모두 지원합니다.

- **IPv4:** 32비트 주소(예: 10.0.0.0/16)를 사용합니다. 대부분의 내부 통신과 많은 레거시 시스템에서 사용됩니다.
- **IPv6:** 128비트 주소를 사용해 상상할 수 없을 정도로 넓은 주소 공간을 제공합니다. AWS에서 IPv6 주소는 전역적으로 유일하며, 방대한 주소 공간이 필요한 인터넷 대면 애플리케이션에 주로 사용됩니다.

AWS는 인스턴스가 IPv4와 IPv6 주소를 모두 가질 수 있는 듀얼 스택 환경을 허용합니다. 이는 특히 다음과 같은 경우에 유용합니다.

- 네트워크를 미래 지향적으로 준비하는 경우.
- IPv6를 요구하는 시스템과의 호환성을 확보해야 하는 경우.
- 대량의 고유 주소 풀이 필요한 애플리케이션.

다만 IPv4는 프라이빗과 퍼블릭 주소를 모두 지원하지만, AWS에서 IPv6는 기본적으로 퍼블릭으로 설계되어 있다는 점에 유의하세요(보안 그룹으로 접근성을 제어할 수는 있습니다).

### 3.3 IP 주소 유형: 프라이빗, 퍼블릭, 탄력적 IP

AWS에는 서로 다른 역할을 하는 여러 유형의 IP 주소가 있습니다.

- **프라이빗 IP 주소:** VPC의 CIDR 블록에서 할당되며, VPC 내부 통신에 사용됩니다. 고정되어 있으며 인터넷에서 직접 접근할 수 없습니다. 전역적으로 인정되는 다음 범위에서 할당됩니다.

	- `10.0.0.0` ~ `10.255.255.255`(CIDR `10.0.0.0/8`)
	- `172.16.0.0` ~ `172.31.255.255`(CIDR `172.16.0.0/12`)
	- `192.168.0.0` ~ `192.168.255.255`(CIDR `192.168.0.0/16`)

	이 범위 밖에 있는 모든 IP 주소는 퍼블릭으로 간주됩니다.

- **퍼블릭 IP 주소:** 퍼블릭 접근 가능한 상태로 인스턴스를 시작할 때 Amazon의 풀에서 할당되는 주소입니다. 직접적인 인터넷 접근을 허용하지만, 기본적으로는 임시적이어서 인스턴스를 중지하고 다시 시작하면 바뀝니다.

- **탄력적 IP 주소(EIP):** 계정에 할당할 수 있는 고정된 퍼블릭 IP 주소입니다. 인스턴스에 연결되면 인스턴스를 중지하고 다시 시작해도 그대로 유지됩니다. 일정한 퍼블릭 엔드포인트가 필요한 애플리케이션에 유용합니다.

네트워크를 설계할 때는 사용 사례에 맞는 적절한 IP 주소 유형을 선택하는 것이 중요합니다. 예를 들어 데이터베이스와 내부 애플리케이션 서버는 일반적으로 프라이빗 IP 주소만 사용하는 반면, 인터넷을 대면하는 웹 서버는 안정성과 일관성을 위해 탄력적 IP를 사용할 수 있습니다.

## 4. 라우팅과 트래픽 제어

### 4.1 라우팅 테이블: 트래픽 경로 구성

라우팅 테이블은 VPC 설계의 핵심입니다. VPC 내부와 외부 목적지로 향하는 네트워크 트래픽이 어떻게 흘러갈지를 결정하기 때문입니다. 자세히 살펴보겠습니다.

- **기본 라우팅 테이블 생성:**
    VPC를 만들면 AWS가 자동으로 메인(기본) 라우팅 테이블을 생성합니다. 커스텀 라우팅 테이블과 명시적으로 연결되지 않은 모든 서브넷은 이 메인 테이블을 사용합니다. 이 테이블에는 VPC의 CIDR 블록 내 모든 리소스 간 트래픽이 흐를 수 있게 하는, 변경할 수 없는 "로컬" 경로가 항상 포함되어 있습니다.

- **커스텀 라우팅 테이블:**
    더 세밀한 제어를 위해 커스텀 라우팅 테이블을 만들어 특정 서브넷에 연결할 수 있습니다. 예를 들어 웹 서버가 있는 퍼블릭 서브넷은 인터넷 게이트웨이(IGW)로의 경로를 갖게 하고, 데이터베이스가 있는 프라이빗 서브넷은 인터넷에 직접 접근하지 못하도록 격리할 수 있습니다.
	![custom-route-table](@site/docs/Networking%20and%20Content%20Delivery/_assets/custom-route-table.png)
    커스텀 라우팅 테이블을 만들 때는 다음을 수행해야 합니다.

    - VPC의 CIDR(로컬 경로)에 대한 경로를 추가합니다. 이 경로는 제거할 수 없습니다.
    - 추가 경로를 추가합니다. 예를 들어 퍼블릭 서브넷은 IGW를 대상으로 하는 0.0.0.0/0, 프라이빗 서브넷은 NAT 디바이스를 대상으로 하는 경로를 추가합니다.

- **세밀한 라우팅:**
	커스텀 라우팅 테이블을 사용하면 각 서브넷에서 나가는 트래픽의 흐름을 제어할 수 있습니다. 예를 들어 한 서브넷의 라우팅 테이블은 NAT 게이트웨이를 통해 아웃바운드 트래픽을 보내고, 다른 서브넷(DMZ나 웹 계층)은 트래픽을 IGW로 직접 보내도록 설계할 수 있습니다.

- **주요 고려사항:**
    - 라우팅 변경은 처리되는 모든 신규 트래픽에 즉시 적용됩니다.
    - 이후 메인 라우팅 테이블을 수정하면, 여전히 그 테이블을 사용하는 서브넷은 새 경로를 즉시 반영합니다.
    - 다중 계층 환경에서는 서로 다른 서브넷에 서로 다른 라우팅 테이블을 지정해 라우팅 규칙을 분리하면 워크로드를 격리하고 민감한 리소스를 보호하는 데 도움이 됩니다.

### 4.2 인터넷 접근을 위한 NAT 솔루션

프라이빗 서브넷의 인스턴스는 인터넷으로 가는 직접적인 경로가 없습니다. 이 인스턴스들이 인바운드 인터넷 트래픽에 노출되지 않으면서도 인터넷에 접근(예: 소프트웨어 업데이트 다운로드, 외부 API 호출)하려면 NAT 솔루션이 필요합니다. AWS는 두 가지 방식을 제공합니다.

#### 4.2.1 NAT 게이트웨이: 관리형 고가용성 아웃바운드 트래픽

- **개요:**
    NAT 게이트웨이는 프라이빗 서브넷의 인스턴스가 인터넷으로 아웃바운드 연결을 시작할 수 있게 하는 완전관리형 AWS 서비스입니다. 자체 NAT 솔루션을 관리하는 복잡성을 추상화해 줍니다.

    ![nat-gateway](@site/docs/Networking%20and%20Content%20Delivery/_assets/nat-gateway.png)
- **배포:**
    - **위치:** NAT 게이트웨이는 퍼블릭 서브넷에 실행되어야 합니다.
    - **탄력적 IP 요구사항:** 탄력적 IP 주소가 연결되어야 하며, 이 주소가 프라이빗 인스턴스에서 나가는 모든 아웃바운드 트래픽에 사용되는 퍼블릭 IP가 됩니다.
    - **라우팅 테이블 구성:** 프라이빗 서브넷의 라우팅 테이블에는 목적지 0.0.0.0/0(IPv4의 경우)이 NAT 게이트웨이를 가리키는 경로를 추가합니다. 이렇게 하면 모든 아웃바운드 인터넷 트래픽이 게이트웨이를 통해 나갑니다.

- **주요 기능:**
    - **고가용성:** NAT 게이트웨이는 특정 가용 영역 내에서 고가용성을 갖도록 설계되었습니다. 고가용성 설계에서는 각 AZ마다 NAT 게이트웨이를 하나씩 만듭니다.
    - **확장성:** 트래픽이 늘어나면 자동으로 확장되며, 부하에 따라 5Gbps에서 100Gbps까지 성능이 확장됩니다.
    - **단순성:** AWS가 NAT 게이트웨이를 관리하므로 패치, 로드 밸런싱, 장애 감지를 걱정할 필요가 없습니다.
    - **비용 고려사항:** NAT 게이트웨이는 시간당 요금과 데이터 처리 요금이 모두 발생합니다. 성능과 관리 단순성 덕분에 프로덕션 워크로드에 권장됩니다.
    - **보안:** NAT 게이트웨이는 보안 그룹을 지원하지 않으므로, 트래픽 필터링은 서브넷 수준에서 네트워크 ACL로 강제해야 합니다.

#### 4.2.2 NAT 인스턴스: EC2 기반 커스텀 NAT(레거시)

- **개요:**
    NAT 인스턴스는 NAT 디바이스로 구성한 EC2 인스턴스입니다. 레거시 방식으로 간주되지만 높은 수준의 커스터마이징을 제공합니다.

- **배포와 구성:**
    - **AMI 선택:** 커뮤니티에서 제공하는 NAT AMI를 실행하거나 자체 커스텀 이미지를 사용해야 합니다.
    - **퍼블릭 서브넷:** NAT 인스턴스는 퍼블릭 서브넷에 배치되어야 하고, 아웃바운드 연결을 위해 퍼블릭 IP 주소(또는 탄력적 IP)를 할당받아야 합니다.
    - **라우팅 테이블 변경:** 프라이빗 서브넷의 라우팅 테이블을 업데이트해 아웃바운드 인터넷 트래픽이 NAT 인스턴스로 라우팅되도록 합니다.
    - **소스/대상 확인:** 매우 중요한 점으로, NAT 인스턴스에서는 소스/대상 확인을 비활성화해야 합니다. 기본적으로 EC2 인스턴스는 자신의 IP를 목적지로 하는 트래픽만 받습니다. 이 확인을 비활성화하면 인스턴스가 자신에게 명시적으로 향하지 않은 트래픽도 전달할 수 있습니다.

- **주요 고려사항:**
    - **커스터마이징:** NAT 인스턴스는 필요에 따라 추가 소프트웨어(예: 침입 탐지 시스템)를 설치하거나 방화벽 규칙을 수정할 수 있게 합니다.
    - **관리 부담:** NAT 게이트웨이와 달리, NAT 인스턴스의 관리, 패치, 확장, 고가용성 확보는 사용자의 책임입니다.
    - **성능:** 관리형 NAT 게이트웨이에 비해 높은 부하에서는 성능이 떨어질 수 있습니다.
    - **사용 사례:** 트래픽이 적고 커스터마이징이 필요한 개발이나 테스트 환경에서는 NAT 인스턴스가 비용 효율적인 선택이 될 수 있습니다.

### 4.3 보조 CIDR로 VPC 주소 공간 확장하기

때로는 VPC의 기본 IP 주소 범위가 부족할 수 있습니다. 사용 가능한 주소를 다 써버렸거나, 온프레미스 네트워크와의 IP 중복을 피해야 하는 경우입니다. AWS는 기존 VPC에 보조 CIDR 블록을 추가할 수 있게 합니다.

- **목적과 사용 사례:**
    - **주소 고갈:** 현재 VPC(예: 10.0.0.0/16)의 사용 가능한 IP가 부족해질 때, 추가 CIDR 블록(예: 10.1.0.0/16)을 추가해 주소 공간을 확장할 수 있습니다.
    - **하이브리드 연결:** 온프레미스 네트워크가 VPC의 기본 CIDR과 중복되는 CIDR을 사용하는 경우, 중복되지 않는 범위의 보조 CIDR을 추가해 매끄러운 VPN이나 Direct Connect 통합을 구현할 수 있습니다.

- **규칙과 제약:**
    - **중복 불가 요구사항:** 보조 CIDR은 기본 CIDR이나 VPC에 이미 연결된 다른 보조 CIDR과 중복될 수 없습니다.
    - **RFC 1918 일관성:** RFC 1918 주소 공간(예: 10.x.x.x)을 사용 중이라면, 보조 CIDR도 다른 프라이빗 범위(예: 192.168.x.x나 172.16.x.x)가 아니라 동일한 범위에서 선택해야 합니다.
    - **라우팅 테이블 고려사항:** VPC(또는 "루트" 라우팅 테이블)에 정의된 경로는 새 CIDR 블록과 충돌해서는 안 됩니다. 예를 들어 VPC 내 특정 범위에 대한 경로가 이미 존재한다면, 그 경로보다 넓거나 중복되는 보조 CIDR을 추가할 수 없습니다.
    - **제한:** 하나의 VPC에는 최대 5개의 IPv4 CIDR 블록과 1개의 IPv6 CIDR 블록을 연결할 수 있습니다.

VPC 주소 공간을 적절히 확장함으로써 애플리케이션과 인프라 요구가 늘어나더라도 VPC를 다시 설계할 필요 없이 네트워크를 성장시킬 수 있습니다.

## 5. VPC 보안

보안은 AWS 네트워킹 아키텍처의 모든 계층에 내재되어 있습니다. 두 가지 주요 메커니즘인 보안 그룹과 네트워크 ACL이 VPC 방화벽 제어의 기반이 됩니다.

### 5.1 보안 그룹: 인스턴스용 스테이트풀 방화벽

![vpc-security-group](@site/docs/Networking%20and%20Content%20Delivery/_assets/vpc-security-group.png)

보안 그룹은 인스턴스(ENI) 수준에서 인바운드·아웃바운드 트래픽을 제어하는 가상 방화벽 역할을 합니다. **"허용" 규칙만 지원합니다.** 주요 내용입니다.

- **스테이트풀 특성:**
    - 보안 그룹은 스테이트풀합니다. 즉 인바운드 규칙이 트래픽(예: 80번 포트의 TCP 트래픽)을 허용하면, 이에 대응하는 아웃바운드 규칙 없이도 반환 트래픽이 자동으로 허용됩니다. 이는 규칙 관리를 단순화합니다.

- **규칙 구성:**
    - 프로토콜(TCP, UDP, ICMP), 포트 범위, 소스/대상 IP 주소 또는 CIDR 블록을 기준으로 규칙을 정의합니다.
    - 같은 VPC 안의 다른 보안 그룹도 참조할 수 있어, 다계층 아키텍처에서 유용합니다(예: 웹 서버가 애플리케이션 서버의 보안 그룹을 참조해 통신을 허용).

- **기본 동작:**
    - 기본적으로 보안 그룹은 모든 인바운드 트래픽을 거부하고 모든 아웃바운드 트래픽을 허용합니다. 이후 허용하려는 인바운드 트래픽에 대해 구체적인 허용 규칙을 추가합니다.

- **ENI와의 연결:**
    - 보안 그룹은 실제로는 인스턴스의 Elastic Network Interface(ENI)에 연결됩니다. 즉 인스턴스에 여러 ENI가 있다면 각 ENI가 자체적인 보안 그룹 규칙 집합을 가질 수 있습니다.

- **세밀함과 유연성:**
    - 네트워크 접근에 대한 세밀한 제어를 제공하며, 최소 권한 모델을 구현하는 데 필수적입니다.
    - 보안 그룹 규칙은 전체적으로 평가됩니다(즉 규칙에 순서가 없습니다). 어떤 규칙이든 트래픽을 허용하면 그 트래픽은 허용됩니다.

### 5.2 네트워크 ACL(NACL): 스테이트리스 서브넷 수준 보안

![network-acl](@site/docs/Networking%20and%20Content%20Delivery/_assets/network-acl.png)

네트워크 ACL은 서브넷 수준에서 추가적인 보안 계층을 제공합니다. **"허용"과 "거부" 규칙을 모두 지원합니다.** 보안 그룹과 몇 가지 측면에서 다릅니다.

- **스테이트리스 필터링:**
    - 보안 그룹과 달리 NACL은 스테이트리스합니다. 즉 인바운드와 아웃바운드 규칙을 모두 지정해야 합니다. 반환 트래픽이 자동으로 허용되지 않으므로 응답을 위한 별도의 규칙을 만들어야 합니다.

- **허용과 거부 규칙:**
    - NACL은 "허용"과 "거부" 규칙을 모두 지원합니다. 이를 통해 특정 IP 주소나 범위의 트래픽을 명시적으로 차단할 수 있는데, 이는 보안 그룹에는 없는 기능입니다.

- **규칙 평가 순서:**
    - NACL의 규칙은 규칙 번호에 따라 순서대로 평가됩니다. 처음으로 일치하는 규칙이 적용되고, 그 이후에는 평가가 중단됩니다. 따라서 규칙 번호 지정이 중요하며 새 규칙을 삽입할 때 신중한 계획이 필요합니다.

- **기본 동작:**
    - 서브넷의 기본 NACL은 모든 인바운드·아웃바운드 트래픽을 허용합니다. 다만 이를 수정하거나 커스텀 NACL을 만들어 필요에 따라 트래픽을 제한할 수 있습니다.

- **적용 범위:**
    - NACL은 서브넷 수준에서 적용되므로, 서브넷 안의 모든 리소스는 인스턴스별 보안 그룹 설정과 무관하게 동일한 ACL 규칙의 적용을 받습니다.

### 5.3 VPC 방화벽 모범 사례: SG vs. NACL 사용 사례

VPC를 보호하려면 계층화된 보안 접근이 필수적입니다. 보안 그룹과 NACL을 함께 최대한 활용하는 방법입니다.

- **보안 그룹(인스턴스 수준):**
    - 각 인스턴스에 필요한 특정 트래픽만 허용하도록 보안 그룹을 사용하세요. 스테이트풀한 특성과 세밀한 규칙 정의 덕분에 개별 워크로드를 보호하는 데 이상적입니다.
    - 보안 그룹은 거부 규칙을 지원하지 않으므로, 긍정적 접근 제어(positive access control)에 가장 적합합니다.

- **네트워크 ACL(서브넷 수준):**
    - 서브넷 수준에서 추가적인 보안 계층을 더하려면 NACL을 사용하세요. 알려진 악성 IP를 차단하거나, 서브넷 내 모든 인스턴스에 적용되는 광범위한 보안 정책을 강제하는 데 특히 유용합니다.
    - 스테이트리스하고 규칙 순서에 따라 동작하는 특성 때문에, 원치 않는 트래픽을 허용할 수 있는 잘못된 구성을 잡아내는 데도 사용할 수 있습니다.

- **계층화된 방어(심층 방어):**
    - 두 가지를 결합하세요. 보안 그룹은 세밀한 인스턴스 수준 필터링을, NACL은 광범위한 서브넷 전체 제한을 담당합니다. 이 접근은 잘못된 구성이 발생했을 때 영향 범위를 최소화합니다.

- **문제 해결:**
    - 연결 문제를 진단할 때는 보안 그룹 설정과 NACL 규칙을 모두 확인하세요. 예를 들어 보안 그룹 규칙이 허용하는데도 아웃바운드 트래픽이 차단되고 있다면, NACL에 반환 트래픽에 대응하는 규칙이 빠져 있을 수 있습니다.
## 6. 고급 네트워킹 구성 요소

AWS 환경이 복잡해질수록 유연성, 고가용성, 운영 효율성을 확보하기 위한 고급 네트워킹 구성 요소가 필수적입니다.

### 6.1 Elastic Network Interface(ENI): 다중 IP 구성과 사용 사례

![eni](@site/docs/Networking%20and%20Content%20Delivery/_assets/eni.png)
ENI는 EC2 인스턴스에 네트워크 연결을 제공하는 가상 네트워크 어댑터입니다. 다음과 같은 이유로 AWS 네트워킹의 근간을 이룹니다.

- **1차 ENI와 2차 ENI:**
    - 모든 EC2 인스턴스는 시작할 때 1차 ENI(일반적으로 eth0으로 표시)를 자동으로 받으며, 여기에는 인스턴스의 1차 프라이빗 IP 주소가 포함됩니다.
    - 두 번째 이상의 네트워크 인터페이스가 필요하면 추가(2차) ENI를 인스턴스에 연결할 수 있습니다. 이는 멀티호밍(듀얼 NIC 구성)이나, 동일 인스턴스에서 실행되는 여러 애플리케이션의 트래픽을 분리하는 데 사용할 수 있습니다.

- **다중 IP 주소:**
    - 각 ENI는 하나의 1차 IP 주소와 여러 개의 2차 프라이빗 IP 주소를 가질 수 있습니다. 이는 특히 파드가 ENI에서 IP 주소를 받는 컨테이너 환경(예: Kubernetes 사용 시)에서 유용합니다.

- **보안 그룹 연결:**
    - 보안 그룹은 ENI에 직접 연결됩니다. 즉 인스턴스에 적용되는 보안 설정은 그 인스턴스에 연결된 ENI에서 비롯됩니다.

- **이동성:**
    - 2차 ENI는 한 인스턴스에서 분리해 다른 인스턴스에 다시 연결할 수 있습니다. 이는 MAC 주소를 유지해 소프트웨어 라이선스를 보존하거나 빠른 페일오버를 구현하는 등 고가용성 설계에 유용합니다.

- **AZ 경계:**
    - ENI는 특정 가용 영역에 종속됩니다. ENI를 다른 AZ의 인스턴스로 이동시킬 수는 없습니다.

- **제한:**
    - ENI의 최대 개수와 ENI당 IP 주소 수는 인스턴스 유형에 따라 다릅니다. AWS 문서에서 인스턴스 유형별 제한을 확인할 수 있습니다.

- **소스/대상 확인:**
    - 특정 사용 사례(예: NAT 인스턴스 구성)에서는 ENI가 자신의 IP로 향하지 않는 트래픽도 전달할 수 있도록 소스/대상 확인을 비활성화해야 할 수 있습니다.
### 6.2 자체 IP 반입(BYOIP): 커스텀 IP 주소 관리

AWS는 여러분의 AWS 환경에 "자체 IP 반입(BYOIP)"을 허용합니다. 이는 다음과 같은 조직에게 특히 중요합니다.

- **확립된 IP 신뢰도가 있는 경우:** 서드파티와의 관계에서 강한 신뢰도나 화이트리스트 상태를 구축해 두었다면, 기존 IP 주소를 재사용함으로써 처음부터 다시 시작할 필요가 없습니다.
- **일관된 IP 주소 지정을 유지해야 하는 경우:** IP 주소가 하드코딩되어 있거나 쉽게 재구성할 수 없는 레거시 통합을 가진 애플리케이션은 기존 퍼블릭 IP 주소를 계속 사용함으로써 이점을 얻습니다.
- **하이브리드 배포:** 애플리케이션을 온프레미스에서 AWS로 마이그레이션할 때 동일한 퍼블릭 IP 주소를 유지하면 혼란을 최소화할 수 있습니다.

BYOIP의 주요 요구사항과 고려사항입니다.

- **IP 소유권:** IP 주소는 퍼블릭으로 라우팅 가능해야 하며 지역 인터넷 등록기관(ARIN, RIPE, APNIC 등)에 등록되어 있어야 합니다.
- **깨끗한 이력:** AWS는 해당 IP 주소가 악의적인 활동에 사용된 적이 없어야 한다는 요건을 둡니다(즉 신뢰도가 깨끗해야 합니다).
- **CIDR 블록 크기:** IPv4 BYOIP의 경우 허용되는 최소 블록은 일반적으로 /24입니다.
- **AWS 광고:** IP 주소를 AWS로 가져오면, AWS는 자체 ASN(Autonomous System Number)을 사용해 여러분을 대신해 이를 광고합니다.

BYOIP는 AWS 클라우드에서 네트워크 아이덴티티에 대한 추가적인 유연성과 제어권을 제공합니다.

## 7. VPC의 DNS와 DHCP

네트워킹은 라우팅과 방화벽만의 문제가 아니며, 올바른 도메인 이름 해석과 IP 구성에도 의존합니다. VPC 안에서 DNS와 DHCP 설정은 내부 리소스 검색과 외부 통신 모두에 매우 중요합니다.

### 7.1 DNS 기초: AWS에서 DNS가 동작하는 방식

도메인 이름 시스템(DNS)은 사람이 읽기 쉬운 도메인 이름을 IP 주소로 변환합니다. AWS의 맥락에서는 다음과 같습니다.

- **퍼블릭 DNS 해석:** 사용자가 URL(예: [www.example.com](http://www.example.com/))을 입력하면 DNS 시스템이 이를 퍼블릭 IP 주소로 해석합니다.
- **프라이빗 DNS 해석:** VPC 안에서 프라이빗 DNS 해석은 리소스가 IP가 아닌 이름으로 서로를 참조할 수 있게 합니다. AWS는 EC2 인스턴스에 프라이빗 DNS 이름을 자동으로 할당합니다(예: ip-10-0-1-15.region.compute.internal 형식).
- **캐싱과 재귀:** DNS 리졸버는 반복 질의 속도를 높이기 위해 결과를 캐시하고, 로컬에 호스팅되지 않은 도메인 이름을 해석하기 위해 재귀 조회를 수행합니다.

AWS는 모든 VPC에 내장 DNS 서버를 제공합니다. 이 Amazon 제공 DNS 서버(흔히 Route 53 리졸버라고 부름)는 VPC 기본 주소 + 2에서 실행됩니다(예: VPC의 CIDR이 10.0.0.0/16이면 DNS 서버는 10.0.0.2에 있습니다). 이 리졸버는 프라이빗 호스팅 영역과 퍼블릭 해석을 모두 지원합니다.

### 7.2 Route 53 Resolver: VPC DNS 구성

Route 53 Resolver는 VPC 안에서 사용되는 핵심 DNS 서비스입니다.

- **기본 구성:** 기본적으로 모든 VPC는 Route 53 Resolver를 통해 DNS 해석이 활성화되어 있습니다. 즉 인스턴스에서 보내는 DNS 질의는 VPC 기본 주소 + 2에 있는 리졸버로 향합니다.
- **프라이빗 호스팅 영역:** 내부 DNS 레코드(예: app.example.internal)를 관리하기 위해 Route 53 프라이빗 호스팅 영역을 만들 수 있습니다. 이 영역들은 VPC 내부에서만 해석되는 커스텀 도메인 이름을 정의할 수 있게 합니다.
- **DHCP와의 통합:** EC2 인스턴스가 부팅될 때 DNS 서버 IP를 포함한 DHCP 옵션을 받습니다. 일반적으로 이 옵션은 Route 53 Resolver를 가리킵니다.
- **DNS 해석 순서:** 도메인 이름을 해석할 때 리졸버는 먼저 프라이빗 호스팅 영역에서 일치하는 항목을 찾고, 그다음 VPC의 내부 DNS 레코드를 확인하며, 마지막으로 일치하는 항목이 없으면 퍼블릭 DNS 서버로 질의를 전달합니다.

### 7.3 Route 53 Resolver 엔드포인트를 활용한 하이브리드 DNS

VPN이나 AWS Direct Connect로 온프레미스 네트워크가 VPC에 연결된 하이브리드 환경에서는 경계를 넘어서는 DNS 해석이 필요할 수 있습니다.

![hybrid-dns](@site/docs/Networking%20and%20Content%20Delivery/_assets/hybrid-dns.png)

- **인바운드 리졸버 엔드포인트:** VPC 외부(예: 온프레미스 DNS 서버)에서 발생한 DNS 질의가 VPC 내부의 Route 53 Resolver로 전달될 수 있게 합니다.
- **아웃바운드 리졸버 엔드포인트:** VPC 내부에서 발생한 DNS 질의를 온프레미스 DNS 서버로 전달합니다.
- **양방향 DNS 해석:** 인바운드와 아웃바운드 엔드포인트를 모두 구성하면 하이브리드 DNS 해석을 구현할 수 있어, AWS와 온프레미스 네트워크 전반에서 일관된 이름 해석이 가능합니다.

이 기능은 하이브리드 아키텍처에서 매끄러운 통합을 위해 필수적입니다.

### 7.4 커스텀 DHCP: DHCP 옵션 세트 구성

모든 VPC에는 인스턴스가 부팅될 때 구성 파라미터를 제공하는 DHCP 옵션 세트가 있습니다.

![vpc-dhcp-option-set](@site/docs/Networking%20and%20Content%20Delivery/_assets/vpc-dhcp-option-set.png)

- **기본 옵션:** 기본 DHCP 옵션 세트는 Amazon이 제공하는 DNS 서버(Route 53 Resolver)를 1차 DNS로 할당합니다.
- **커스텀 도메인 이름:** DHCP 옵션을 커스터마이징해 프라이빗 도메인 이름(예: "finance.internal")을 정의할 수 있으며, 이는 EC2 인스턴스가 호스트명을 구성하는 방식에 영향을 줍니다.
- **추가 파라미터:** DHCP 옵션 세트는 NTP 서버, NetBIOS 설정 등도 지정할 수 있습니다.
- **VPC당 하나 규칙:** 각 VPC는 한 번에 하나의 DHCP 옵션 세트만 연결할 수 있습니다. 설정을 수정하려면 새 옵션 세트를 만들어 VPC에 연결해야 하며, 변경 사항은 각 인스턴스에서 DHCP 리스가 갱신된 후 적용됩니다.

DNS와 DHCP를 올바르게 구성하는 것은 애플리케이션이 서로를 안정적으로 찾고 통신할 수 있도록 하는 데 매우 중요합니다.

## 8. 모니터링, 분석, 문제 해결

운영 우수성은 네트워크의 성능과 동작에 대한 가시성에 달려 있습니다. AWS는 VPC 트래픽을 모니터링, 분석, 문제 해결하기 위한 여러 내장 도구를 제공합니다.
### 8.1 VPC Flow Logs: 보안과 감사를 위한 트래픽 캡처

![flow-logs](@site/docs/Networking%20and%20Content%20Delivery/_assets/flow-logs.png)

VPC Flow Logs는 VPC 내 네트워크 트래픽 메타데이터를 캡처하고 분석하는 핵심 도구입니다. 리소스로 들어오고 나가는 트래픽에 대한 통찰을 제공합니다.

- **범위와 수준:**
    - Flow Log는 VPC 수준(모든 ENI의 트래픽 캡처), 서브넷 수준, 또는 개별 ENI에서 활성화할 수 있습니다.

- **로그 내용:**
    - 각 Flow Log 레코드에는 다음과 같은 여러 필드가 포함됩니다.
        - **버전:** (예: 커스텀 형식의 경우 버전 2 또는 버전 5)
        - **계정 ID**와 **ENI ID**
        - **소스 IP 주소**와 **대상 IP 주소**
        - **소스 포트**와 **대상 포트**
        - **프로토콜:** (예: TCP는 "6"으로 표시)
        - **패킷과 바이트 수:** 플로 중 전송된 패킷과 바이트 수
        - **시작·종료 시각:** Flow Log 레코드의 타임스탬프
        - **동작:** 트래픽이 "ACCEPT"였는지 "REJECT"였는지 표시
        - **로그 상태:** (예: 로그 전달이 성공했음을 나타내는 "OK")
    - 커스텀(v5) 형식에서는 VPC ID, 서브넷 ID, 인스턴스 ID, 리전, 가용 영역, 그리고 NAT 시나리오에 유용한 원본 패킷 소스/대상 같은 추가 필드도 포함될 수 있습니다.

- **전달과 분석:**
    - VPC Flow Log는 실시간 모니터링·분석을 위해 CloudWatch Logs로 전달하거나, 보관과 추가 처리를 위해 Amazon S3로 전달할 수 있습니다.
    - CloudWatch Logs Insights 같은 도구를 사용하면 연결 문제를 해결하거나, 대역폭 사용량을 모니터링하거나, 악성 IP의 반복적인 접근 시도 같은 이상 징후를 탐지하기 위해 Flow Log 데이터를 질의·필터링·집계할 수 있습니다.

- **사용상 고려사항:**
    - Flow Log는 실제 패킷 페이로드를 캡처하지 않지만, 보안이나 성능 문제를 진단할 수 있는 충분한 메타데이터를 제공합니다.
    - 특정 유형의 트래픽(예: VPC 기본 주소 +2의 Amazon 제공 DNS 서버로 향하는 트래픽)은 로깅되지 않습니다.

#### 8.1. Flow Logs 예시

**허용된 트래픽과 거부된 트래픽**

- _허용된 SSH 트래픽:_
    다음 레코드는 IP 주소 172.31.16.139에서 네트워크 인터페이스(프라이빗 IP 172.31.16.21, ID `eni-1235b8ca123456789`)로 향하는 SSH 트래픽(TCP 22번 포트)이 허용되었음을 보여줍니다.

```yaml
2 123456789010 eni-1235b8ca123456789 172.31.16.139 172.31.16.21 20641 22 6 20 4249 1418530010 1418530070 ACCEPT OK
```

- _거부된 RDP 트래픽:_
    이 레코드에서는 동일한 네트워크 인터페이스로 향하는 RDP 트래픽(TCP 3389번 포트)이 거부되었습니다.

```yaml
2 123456789010 eni-1235b8ca123456789 172.31.9.69 172.31.9.12 49761 3389 6 20 4249 1418530010 1418530070 REJECT OK
```

**데이터 없음과 건너뛴 레코드**

- _데이터 없음:_
    집계 구간 동안 캡처된 트래픽이 없으면 로그는 다음과 같이 나타날 수 있습니다.

```yaml
2 123456789010 eni-1235b8ca123456789 - - - - - - - 1431280876 1431280934 - NODATA
```

- _건너뛴 레코드:_
    집계 구간 동안 로그 시스템이 용량을 초과하면 다음과 유사한 레코드가 생성됩니다.

```yaml
2 123456789010 eni-11111111aaaaaaaaa - - - - - - - 1431280876 1431280934 - SKIPDATA
```

**보안 그룹과 네트워크 ACL 규칙**

가정용 컴퓨터(203.0.113.12)에서 인스턴스(172.31.16.139)로 ping 명령을 실행하는 시나리오를 생각해 봅시다. 보안 그룹이 스테이트풀하므로, 보안 그룹이 인바운드 ICMP만 허용하더라도 최초의 ICMP 요청은 허용됩니다. 하지만 네트워크 ACL(스테이트리스)이 아웃바운드 ICMP를 허용하지 않으면 응답은 폐기됩니다. Flow Log 레코드는 다음과 같이 나타날 수 있습니다.

- _Ping 요청(허용됨):_

```yaml
2 123456789010 eni-1235b8ca123456789 203.0.113.12 172.31.16.139 0 0 1 4 336 1432917027 1432917142 ACCEPT OK
```

- _Ping 응답(NACL에 의해 거부됨):_

```yaml
2 123456789010 eni-1235b8ca123456789 172.31.16.139 203.0.113.12 0 0 1 4 336 1432917094 1432917142 REJECT OK
```

**IPv6 트래픽**

IPv6도 Flow Log 형식이 유사합니다. 예를 들어 다음 레코드는 IPv6 주소에서 22번 포트로 향하는 SSH 트래픽을 보여줍니다.

```yaml
2 123456789010 eni-1235b8ca123456789 2001:db8:1234:a100:8d6e:3477:df66:f105 2001:db8:1234:a102:3304:8879:34cf:4071 34892 22 6 54 8855 1477913708 1477913820 ACCEPT OK
```

**NAT 게이트웨이를 통한 트래픽**

프라이빗 서브넷의 인스턴스가 NAT 게이트웨이를 통해 인터넷에 접근할 때, Flow Log는 NAT 게이트웨이 인터페이스와 최종 목적지에 대해 서로 다른 주소를 캡처할 수 있습니다. 예를 들면 다음과 같습니다.

- _인스턴스에서 NAT 게이트웨이로의 트래픽:

	여기서 인스턴스(10.0.1.5)가 보낸 트래픽은 먼저 대상이 NAT 게이트웨이의 프라이빗 IP(10.0.0.220)로 나타나며, 패킷의 실제 목적지(pkt-dstaddr)는 퍼블릭 호스트(203.0.113.5)입니다.

```yaml
- eni-1235b8ca123456789 10.0.1.5 10.0.0.220 10.0.1.5 203.0.113.5
```

- _NAT 게이트웨이에서 인스턴스로의 응답 트래픽:_

```yaml
- eni-1235b8ca123456789 10.0.0.220 10.0.1.5 203.0.113.5 10.0.1.5
```

**Transit Gateway를 통한 트래픽**

Transit Gateway를 통해 VPC 간에 트래픽이 흐르는 경우, Flow Log 레코드는 Transit Gateway와 관련된 여러 ENI에서의 트래픽을 캡처합니다.

- _클라이언트로부터의 요청 트래픽:_

```yaml
3 eni-33333333333333333 123456789010 vpc-abcdefab012345678 subnet-22222222bbbbbbbbb i-01234567890123456 10.20.33.164 10.40.2.236 39812 80 6 3 IPv4 10.20.33.164 10.40.2.236 ACCEPT OK
```

- _서버로부터의 응답 트래픽:_

```yaml
3 eni-33333333333333333 123456789010 vpc-abcdefab012345678 subnet-22222222bbbbbbbbb i-01234567890123456 10.40.2.236 10.20.33.164 80 39812 6 19 IPv4 10.40.2.236 10.20.33.164 ACCEPT OK
```

Transit Gateway의 요청자 관리 인터페이스를 통과하는 트래픽의 경우, 인스턴스 ID 필드에 '-'가 표시되어 해당 인터페이스가 고객 인스턴스가 아니라 Transit Gateway에 속한다는 것을 나타내는 예시 레코드는 다음과 같습니다.

```yaml
3 eni-11111111111111111 123456789010 vpc-abcdefab012345678 subnet-11111111aaaaaaaaa - 10.40.1.175 10.40.2.236 39812 80 6 3 IPv4 10.20.33.164 10.40.2.236 ACCEPT OK
```
### 8.2 트래픽 미러링: 분석을 위한 심층 패킷 검사

![traffic-mirroring](@site/docs/Networking%20and%20Content%20Delivery/_assets/traffic-mirroring.png)

트래픽 미러링은 ENI에서 발생하는 네트워크 트래픽의 실시간 사본을 캡처해 지정된 모니터링 어플라이언스로 전송할 수 있는 기능입니다.

- **목적:**
    - 보안 모니터링(예: 침입 탐지 시스템)이나 문제 해결을 위한 심층 패킷 검사와 실시간 분석을 가능하게 합니다.
    - 미러링된 트래픽은 사본이므로, 실제 프로덕션 트래픽에는 영향을 주지 않습니다.

- **구성 요소:**
    - **미러 소스:** 트래픽을 미러링할 대상 ENI(예: 중요한 EC2 인스턴스의 ENI)입니다.
    - **미러 대상:** 미러링된 트래픽이 전송되는 목적지입니다. 다음 중 하나가 될 수 있습니다.
        - 다른 ENI(모니터링용 EC2 인스턴스에 연결됨), 또는
        - 하나 이상의 모니터링 어플라이언스로 트래픽을 보내는 Network Load Balancer(NLB).
    - **미러 필터:** 프로토콜, 포트 범위, CIDR 블록 같은 조건에 따라 어떤 트래픽을 미러링할지 정의할 수 있는 선택적 필터입니다. 예를 들어 HTTP/HTTPS 트래픽만 미러링하거나 특정 소스 IP 범위의 트래픽만 미러링하도록 선택할 수 있습니다.

- **배포 시 고려사항:**
    - 미러링 세션은 ENI별로 구성되며, 일정한 확장성과 요금 관련 고려사항이 적용됩니다.
    - NLB를 미러 대상으로 사용할 때는 VXLAN 캡슐화에 사용되는 UDP 4789번 포트가 열려 있어야 트래픽이 올바르게 전달됩니다.
    - 트래픽 미러링의 소스와 대상은 일반적으로 동일한 리전에 있어야 하지만, 일부 고급 아키텍처에서는 서로 다른 VPC(주로 VPC 피어링이나 Transit Gateway로 연결됨)에 있을 수도 있습니다.

### 8.3 VPC Reachability Analyzer: 네트워크 경로 진단

![VPC Reachability Analyzer](@site/docs/Networking%20and%20Content%20Delivery/_assets/vpc_reachability_analyzer.png)

VPC Reachability Analyzer는 VPC 내 지정된 소스와 대상 엔드포인트 사이에 트래픽이 흐를 수 있는지 확인하는 데 도움을 주는 도구입니다.

- **기능:** 라우팅 테이블, 보안 그룹, 네트워크 ACL, 기타 연결 구성 요소의 설정을 분석해 유효한 경로가 존재하는지 판단합니다.
- **시각화:** 분석기는 트래픽이 어떻게 흐르는지(또는 어디서 막히는지) 보여주는 단계별 "홉 단위" 경로를 생성합니다.
- **사용 사례:** 이 도구는 연결 문제 해결(예: 한 서브넷의 EC2 인스턴스가 다른 서브넷의 데이터베이스에 도달하지 못하는 경우), VPC 피어링 설정 검증, AWS와 온프레미스 네트워크 간 하이브리드 연결 테스트에 이상적입니다.
- **비침습적:** 중요한 점으로, Reachability Analyzer는 실제 트래픽을 보내지 않고 구성만 검사하므로 프로덕션 환경에서 안전하게 사용할 수 있습니다.

Flow Log와 트래픽 미러링과 함께, Reachability Analyzer는 네트워크 문제 해결과 컴플라이언스 검증을 위한 종합적인 도구 세트를 제공합니다.

## 9. 네트워크 연결과 하이브리드 시나리오

AWS는 민감한 리소스를 공용 인터넷에 노출하지 않으면서 VPC를 서로 연결하거나 외부 네트워크에 연결할 수 있는 다양한 옵션을 제공합니다.

### 9.1 VPC 피어링: VPC를 안전하게 연결하기

![VPC Peering](@site/docs/Networking%20and%20Content%20Delivery/_assets/vpc_peering.png)

VPC 피어링은 AWS 내부 네트워크를 통해 두 VPC 사이에 프라이빗 링크를 구성합니다. 두 VPC가 피어링되면 다음과 같습니다.

- 마치 같은 네트워크 세그먼트에 있는 것처럼 트래픽을 주고받을 수 있습니다.
- 유효한 피어링 연결을 형성하려면 각 VPC의 IPv4 또는 IPv6 CIDR이 중복되지 않아야 합니다.
- 피어링을 수립한 후에는 각 VPC의 라우팅 테이블을 업데이트해 각 서브넷이 상대 VPC의 CIDR 블록으로 가는 경로를 알 수 있도록 해야 합니다.

일반적인 사용 사례로는 서로 다른 VPC에 있는 여러 애플리케이션이나 마이크로서비스를 연결해, 최소한의 지연 시간으로 안전하고 직접적으로 통신할 수 있게 하는 것이 있습니다.

#### 9.1.1. 제약과 주요 특성

##### 9.1.1.1. CIDR 블록 중복 불가

두 VPC의 CIDR 범위가 어떤 부분이라도 겹치면 피어링이 허용되지 않습니다. 각 VPC에 여러 CIDR이 있고 그중 하나만 겹쳐도 피어링 연결을 수립할 수 없습니다. 이 규칙은 IPv4와 IPv6 모두에 적용됩니다. 따라서 특히 다중 계정이나 대규모 배포에서는 IP 주소 지정 체계를 신중하게 계획하는 것이 매우 중요합니다.

##### 9.1.1.2. 라우팅 테이블과 최장 프리픽스 일치

피어링된 VPC 사이에 트래픽을 보낼 때 AWS는 라우팅 테이블에서 가장 구체적인(가장 긴) 프리픽스를 찾습니다. 예를 들면 다음과 같습니다.

- VPC A의 라우팅 테이블에 동일한 범위(10.0.0.0/16)를 대상으로 하는 두 개의 경로가 있는데, 그중 하나가 특히 10.0.0.77/32와 일치한다고 가정해 봅시다.
- 10.0.0.77로 향하는 트래픽은 더 넓은 /16 경로보다 우선하여, 가장 길고 구체적인 프리픽스인 /32 경로를 따르게 됩니다.

여러 피어링 연결이 있고 정밀한 트래픽 라우팅이 필요할 때는 최장 프리픽스 일치를 이해하는 것이 매우 중요합니다.

##### 9.1.1.3. 전이적이지 않음

가장 중요한 제약 중 하나는 VPC 피어링이 전이적이지 **않다**는 점입니다. VPC A가 VPC B와 피어링되어 있고 VPC B가 VPC C와 피어링되어 있다고 해서, A가 B를 거쳐 C와 통신할 수 있다는 의미는 **아닙니다**. A와 C 사이에서 트래픽이 흐르려면 A와 C 사이에 직접적인 피어링 연결이 필요합니다.

시험 팁: 각 VPC가 다른 모든 VPC와 통신해야 하는 다중 VPC 토폴로지에서는 다음 중 하나가 필요합니다.

- 완전 메시 피어링 모델(각 VPC가 다른 모든 VPC와 피어링됨)을 구성하거나,
- 허브 앤 스포크 아키텍처를 위해 AWS Transit Gateway 같은 대안적 접근을 고려해야 합니다.

##### 9.1.1.4. 엣지 투 엣지 라우팅 불가

전이성이 없다는 점 외에도, 피어링된 VPC를 거쳐 "엣지 투 엣지" 라우팅을 할 수도 없습니다. 흔한 예시는 다음과 같습니다.

- VPC A의 Direct Connect나 VPN 연결을 통해 VPC B에서 온프레미스 네트워크로 트래픽을 라우팅할 수 없습니다.
- VPC A의 인터넷 게이트웨이나 NAT 게이트웨이를 통해 VPC B에서 인터넷으로 트래픽을 라우팅할 수 없습니다.
- 마찬가지로 피어링 연결을 통해 피어링된 VPC의 게이트웨이 엔드포인트(S3, DynamoDB 등)를 사용할 수도 없습니다.

이 제약은 하나의 VPC에 중앙집중식 NAT나 인터넷 게이트웨이를 만들어 다른 피어링된 VPC들이 공유하는 구조를 막습니다. 여러 VPC를 위한 중앙 이그레스/인그레스 지점을 제공하는 것이 목표라면, 다른 아키텍처(예: AWS Transit Gateway)를 검토해야 합니다.

##### 9.1.1.5. 리전과 계정을 넘나드는 피어링

VPC 피어링은 다음과 같이 동작할 수 있습니다.

- **리전 간**: 서로 다른 AWS 리전에 있는 VPC를 피어링할 수 있습니다.
- **계정 간**: 한 계정의 VPC가 다른 계정이 소유한 VPC와 피어링할 수 있습니다. 단, 소유자가 피어링 요청을 수락하고 CIDR이 중복되지 않아야 합니다.

보안 그룹은 계정 간 시나리오를 포함해 피어링된 VPC의 보안 그룹 ID를 참조할 수 있습니다. 이는 개별 IP 주소를 지정하는 대신 원격 리소스를 하나의 엔티티처럼 다룰 수 있게 해 보안 관리를 단순화합니다.

### 9.2 VPC 엔드포인트: 프라이빗 AWS 서비스 접근

VPC 엔드포인트는 공용 인터넷을 거치지 않고 VPC를 지원되는 AWS 서비스에 프라이빗하게 연결하는 방법을 제공합니다. 엔드포인트를 사용하면 특정 서비스 통신을 위해 인터넷 게이트웨이(IGW), NAT 게이트웨이, VPN, AWS Direct Connect가 필요하지 않을 수 있습니다. 이 접근은 보안을 강화하고 지연 시간을 줄이며 데이터 전송 비용을 낮출 수 있습니다.

핵심 사항입니다.

- **프라이빗 연결:** 엔드포인트는 VPC와 지원되는 AWS 서비스 사이의 트래픽이 AWS 네트워크 안에 머물도록 보장합니다.
- **보안·컴플라이언스 개선:** 트래픽이 AWS 백본을 벗어나지 않으므로 인터넷에 덜 노출되어 위험이 줄고 컴플라이언스 요구사항을 충족하는 데 도움이 됩니다.
- **비용 이점:** S3나 DynamoDB 같은 서비스에 프라이빗하게 접근할 때 NAT 게이트웨이와 관련된 시간당·GB당 요금을 피할 수 있습니다.
- **DNS 통합:** 엔드포인트는 AWS DNS와 통합됩니다. 예를 들어 인터페이스 엔드포인트를 만들면 AWS가 DNS 설정을 자동으로 업데이트해, 해당 서비스의 도메인 이름이 엔드포인트의 프라이빗 IP 주소로 해석되게 합니다.
- **엔드포인트 정책:** VPC 엔드포인트에 정책을 직접 연결할 수 있습니다. 이 정책을 통해 특정 리소스에 대해서만 접근을 제한할 수 있습니다(예: 하나의 S3 버킷이나 특정 DynamoDB 테이블에만 접근을 허용).

VPC 엔드포인트에는 두 가지 유형이 있습니다.

- **게이트웨이 엔드포인트:** 현재는 Amazon S3와 DynamoDB에만 제공됩니다.
- **인터페이스 엔드포인트(AWS PrivateLink):** 많은 AWS 서비스와 지원되는 서드파티 애플리케이션에 프라이빗 연결을 제공합니다.

#### 9.2.1 게이트웨이 엔드포인트(S3, DynamoDB)

![Gateway Endpoints](@site/docs/Networking%20and%20Content%20Delivery/_assets/gateway_endpoints.png)

게이트웨이 엔드포인트는 가장 단순한 형태의 VPC 엔드포인트로, VPC를 Amazon S3와 DynamoDB에 프라이빗하게 연결하기 위해 특별히 설계되었습니다.

**동작 방식:**

- **라우팅 테이블 통합:** 게이트웨이 엔드포인트를 만들면 VPC의 하나 이상의 라우팅 테이블에 새 경로가 추가됩니다. S3나 DynamoDB로 향하는 트래픽을 인터넷(또는 NAT)을 거쳐 보내는 대신, 이 경로가 트래픽을 엔드포인트로 안내합니다.
- **프리픽스 목록:** AWS는 대상 서비스(S3 또는 DynamoDB)가 사용하는 IP 주소 범위를 담은 프리픽스 목록을 관리합니다. 라우팅 테이블에서는 이 프리픽스 목록이 목적지로 지정됩니다. 이 메커니즘은 실제 IP 주소를 추상화해 라우팅 유지 관리를 더 쉽게 만듭니다.
- **추가 요금 없음:** 게이트웨이 엔드포인트는 추가 비용 없이 제공됩니다. 시간당 요금이나 데이터 처리 요금이 발생하지 않습니다.

**구성과 사용 사례:**

- **S3/DynamoDB 프라이빗 접근:** NAT 게이트웨이 없이도 프라이빗 서브넷의 인스턴스가 S3나 DynamoDB에 접근할 수 있게 합니다. 이는 트래픽을 AWS 네트워크 안에 유지해 보안을 개선할 뿐 아니라 비용도 절감합니다.
- **정책 제한:** 게이트웨이 엔드포인트에 엔드포인트 정책을 연결할 수 있습니다. 예를 들어 특정 S3 버킷이나 일부 DynamoDB 테이블만 엔드포인트를 통해 접근할 수 있도록 제한할 수 있습니다. 이는 추가적인 보안 계층과 세밀한 제어를 제공합니다.
- **라우팅 테이블 업데이트:** 게이트웨이 엔드포인트를 만든 후에는 접근이 필요한 서브넷의 라우팅 테이블을 업데이트해야 합니다. 새 경로는 프리픽스 목록을 목적지로 사용하고, 그 대상은 VPC 게이트웨이 엔드포인트입니다.
- **보안 그룹 고려사항:** 게이트웨이 엔드포인트는 Elastic Network Interface(ENI)를 요구하지 않지만, 커스텀 아웃바운드 규칙을 강제하고 있다면 인스턴스(또는 다른 리소스)의 보안 그룹 규칙이 AWS 관리 프리픽스 목록으로의 아웃바운드 트래픽을 허용하는지 확인해야 합니다.

**예시 시나리오:** 프라이빗 서브넷의 EC2 인스턴스에서 실행되는 애플리케이션이 S3 버킷에 데이터를 읽고 써야 합니다. 추가 비용이 발생하고 트래픽이 공용 인터넷에 노출되는 NAT 게이트웨이를 거치는 대신, S3용 게이트웨이 엔드포인트를 만듭니다. 그런 다음 S3 프리픽스 목록으로 향하는 트래픽이 이 엔드포인트를 통하도록 라우팅 테이블을 업데이트합니다. 선택적으로 엔드포인트에 정책을 연결해 특정 S3 버킷에 대한 작업만 허용할 수 있습니다. 이런 구성은 S3에 대한 안전하고 확장 가능하며 비용 효율적인 접근을 보장합니다.

#### 9.2.2 인터페이스 엔드포인트(AWS PrivateLink)

인터페이스 엔드포인트는 AWS PrivateLink 기술을 사용해 다양한 AWS 서비스와 지원되는 서드파티 애플리케이션에 프라이빗 연결을 제공합니다. S3와 DynamoDB에만 동작하는 게이트웨이 엔드포인트와 달리, 인터페이스 엔드포인트는 API Gateway, SQS, SNS, Kinesis 등 훨씬 많은 서비스에서 사용할 수 있습니다.

**동작 방식:**

- **Elastic Network Interface(ENI):** 인터페이스 엔드포인트를 만들면 AWS가 선택한 서브넷 안에 하나 이상의 ENI를 프로비저닝합니다. 이 ENI들은 VPC의 CIDR 범위에서 프라이빗 IP 주소를 할당받습니다.
- **DNS 구성:** AWS는 VPC DNS를 자동으로 업데이트해, 대상 서비스의 도메인 이름이 엔드포인트 ENI의 프라이빗 IP 주소로 해석되도록 합니다. 즉 애플리케이션이 서비스 엔드포인트를 호출하면 트래픽이 AWS 네트워크 안에 머무릅니다.
- **엔드포인트 정책:** 게이트웨이 엔드포인트와 마찬가지로, 인터페이스 엔드포인트에 엔드포인트 정책을 연결해 어떤 작업이나 리소스에 접근할 수 있는지 제어할 수 있습니다.
- **요금 모델:** 인터페이스 엔드포인트는 무료가 아닙니다. 엔드포인트에 대한 시간당 요금과, 엔드포인트가 처리한 데이터 양에 따른 데이터 처리 요금이 발생합니다. 그러나 많은 사용 사례에서 프라이빗 연결과 보안 개선의 이점이 이런 비용을 상회합니다.

**구성과 사용 사례:**

- **광범위한 서비스 지원:** 인터페이스 엔드포인트는 40개 이상(계속 증가 중)의 AWS 서비스와 AWS Marketplace를 통해 제공되는 일부 서드파티 서비스에서 사용할 수 있습니다.
- **애플리케이션 구성 요소를 위한 프라이빗 연결:** 게이트웨이 엔드포인트가 지원하지 않는 서비스에 접근할 때 이상적입니다. 예를 들어 프라이빗 서브넷의 EC2 인스턴스가 API Gateway의 API를 호출하거나 SQS에서 메시지를 가져와야 한다면 인터페이스 엔드포인트를 만들 수 있습니다.
- **보안 강화:** 트래픽이 공용 인터넷을 거치지 않으므로 외부 위협에 대한 노출이 줄어듭니다. 엔드포인트 정책을 사용해 접근을 더 제한할 수도 있습니다.
- **DNS와 라우팅:** 인터페이스 엔드포인트를 사용할 때는 라우팅 테이블을 수정하지 않습니다. 대신 AWS가 DNS로 리디렉션을 관리해, 서비스 도메인 이름에 대한 요청이 자동으로 엔드포인트의 프라이빗 IP로 해석됩니다.
- **하이브리드 환경:** 인터페이스 엔드포인트는 온프레미스 시스템(VPN이나 Direct Connect를 통해)이 AWS 서비스에 프라이빗하게 접근해야 하는 시나리오도 지원할 수 있습니다. DNS 해석이 프라이빗 IP 주소를 반환하도록 함으로써 가능합니다.

**예시 시나리오:** 마이크로서비스 아키텍처에서 여러 서비스(메시지 큐, API 엔드포인트, 데이터 스트림 등)가 공용 인터넷에 트래픽을 노출하지 않고 서로 안전하게 통신해야 합니다. NAT 게이트웨이를 통해 요청을 라우팅하는 대신, 필요한 각 AWS 서비스에 대해 인터페이스 엔드포인트를 만듭니다. VPC 내 DNS 해석은 이제 요청을 이 엔드포인트들의 ENI로 안내하며, 보안 팀은 엔드포인트 정책으로 접근을 더 세밀하게 조정할 수 있습니다. 인터페이스 엔드포인트에는 비용이 발생하지만, 지연 시간 감소와 보안 강화라는 이점 때문에 민감하거나 지연 시간에 민감한 애플리케이션에는 선호되는 선택입니다.

### 9.3 온프레미스 네트워크에서 VPC 엔드포인트 접근하기

VPC 게이트웨이 엔드포인트는 _VPC 내부_의 리소스(예: EC2 인스턴스)가 S3나 DynamoDB 같은 AWS 서비스에 프라이빗하게 연결할 수 있게 합니다. 하지만 **온프레미스 네트워크**(예: VPN이나 Direct Connect로 연결된 회사 서버)에서 이 엔드포인트에 접근하려고 하면 **동작하지 않습니다**. 그 이유는 다음과 같습니다.

1. **라우팅 규칙은 VPC 내부에만 적용됨**:

    - 게이트웨이 엔드포인트는 VPC의 라우팅 테이블에 특수한 경로(지름길과 같은)를 추가함으로써 동작합니다.
    - 이 지름길은 **VPC 내부에서 오는 트래픽에서만 동작합니다**(예: EC2 인스턴스).
    - 온프레미스 네트워크에서 오는 트래픽은 VPC로 들어오더라도 이 내부 지름길을 따르지 않습니다.

2. **온프레미스가 두드릴 "문"이 없음**:

    - 게이트웨이 엔드포인트는 VPC 안에 가상 네트워크 카드(ENI)를 만들지 않습니다. 단지 라우팅 지름길일 뿐입니다.
    - 네트워크 인터페이스가 없으므로, 온프레미스 시스템은 엔드포인트와 직접 대화할 방법이 없습니다.

3. **트래픽이 잘못된 경로를 탐**: S3/DynamoDB로 향하는 온프레미스 트래픽은
	- 공용 인터넷을 거치거나(위험하고 느림), 또는
	- Direct Connect를 사용하지만 VPC의 내부 지름길은 건너뜁니다.

온프레미스 네트워크를 S3/DynamoDB 같은 AWS 서비스에 프라이빗하게 연결하려면 두 가지 방법이 있습니다.

**방법 1: AWS PrivateLink(인터페이스 엔드포인트) 사용**
- VPC 안에 AWS 서비스로 향하는 프라이빗 문처럼 동작하는 "가상 네트워크 카드"(ENI)를 만듭니다.
- 온프레미스 네트워크가 이 문을 사용할 수 있습니다.
- **설정 방법**:
    - VPC에 S3/DynamoDB용 인터페이스 엔드포인트를 만듭니다.
    - 온프레미스 DNS가 이 엔드포인트의 프라이빗 주소를 가리키도록 업데이트합니다.
    - VPC의 보안 규칙에서 온프레미스 IP를 허용합니다.

**방법 2: VPC를 통해 트래픽을 라우팅**
- **예시**:
    - _VPC 내부에_ 프록시 서버나 NAT 게이트웨이를 설정합니다.
    - S3/DynamoDB로 향하는 모든 온프레미스 트래픽을 이 프록시를 통해 보냅니다.
    - 프록시가 VPC의 게이트웨이 엔드포인트를 사용하므로 트래픽이 프라이빗하게 유지됩니다.

## 10. 기본 VPC

모든 AWS 리전은 초기 배포를 단순화하고 새 계정에 즉시 네트워크 연결을 제공하기 위해 자동으로 기본 VPC를 프로비저닝합니다. 기본 VPC는 빠른 실험과 프로토타이핑을 위해 설계되었지만, 프로덕션 환경에서 사용할지 결정하기 전에 그 구조, 동작, 한계를 이해하는 것이 중요합니다.

### 10.1 목적과 동작

- **자동 프로비저닝:**
    AWS 계정을 만들면 모든 리전에 자동으로 구성된 하나의 기본 VPC가 함께 제공됩니다. 즉 VPC를 지정하지 않고 EC2 인스턴스를 실행하면 자동으로 기본 VPC에 배포됩니다.
- **즉시 연결:**
    기본 VPC는 미리 구성되어 있어, 그 안에서 실행된 인스턴스들이 서로 통신할 수 있고, 퍼블릭 IP 주소가 있다면 인터넷과도 통신할 수 있습니다. 이런 "플러그 앤 플레이" 기능은 초기 실험과 개발의 설정 시간을 줄여 줍니다.

### 10.2 기본 구성

- **CIDR 블록:**
    기본 VPC에는 고정된 프라이빗 IP 주소 범위(일반적으로 **172.31.0.0/16**)가 할당됩니다. 이 큰 주소 블록은 각 리전의 기본 VPC를 위해 전용으로 예약되어 있습니다.

- **가용 영역별 서브넷:**
    기본 VPC는 해당 리전의 각 가용 영역(AZ)마다 하나의 서브넷으로 자동으로 나뉩니다. 예를 들면 다음과 같습니다.

    - **뭄바이** 리전(AZ 3개)에는 기본적으로 3개의 서브넷이 만들어집니다.
    - **북부 버지니아** 리전(AZ 6개)에는 6개의 서브넷이 프로비저닝됩니다.

    이 서브넷들은 각각 **/20** CIDR 블록으로 만들어집니다. 이 구성은 각 서브넷에 다음을 제공합니다.

    - **서브넷당 4096개의 IP 주소**(/20의 경우 2^12 = 4096이므로),
    - 이 중 **5개의 주소가 예약**되어 있어(처음 4개와 마지막 IP는 할당할 수 없음), 서브넷당 **4091개의 사용 가능한 주소**가 남습니다.

- **인터넷 게이트웨이(IGW):**
    기본 VPC에는 자동으로 연결된 인터넷 게이트웨이 하나가 포함되어 있습니다. 기본 VPC의 메인 라우팅 테이블에는 목적지 **0.0.0.0/0**을 IGW로 라우팅하는 항목이 포함되어 있습니다. 이 구성 덕분에 기본 VPC의 모든 서브넷은 사실상 퍼블릭 서브넷이 됩니다.

- **라우팅 테이블:**
    각 서브넷마다 개별 라우팅 테이블을 만드는 대신, 기본 VPC는 모든 서브넷에 자동으로 연결되는 하나의 메인 라우팅 테이블을 제공합니다. 이 라우팅 테이블에는 VPC 내부 트래픽을 위한 로컬 경로와, 아웃바운드 트래픽을 IGW로 보내는 경로가 모두 포함되어 있습니다.

### 10.3 이점과 고려사항

- **사용 편의성:**
    기본 VPC는 수동 네트워크 설정 없이 EC2 인스턴스와 다른 리소스를 실행하는 과정을 단순화하도록 만들어졌습니다. 테스트, 학습, 빠른 배포에 이상적입니다.

- **프로덕션에서의 한계:**
    편리하지만 기본 VPC는 일률적인 구성입니다. 프로덕션 워크로드에는 특정 보안·성능·조직 요구에 맞는 커스텀 VPC를 설계하는 것이 모범 사례로 권장됩니다. 커스텀 VPC를 사용하면 IP 주소 지정, 서브넷 분할(퍼블릭·프라이빗), 보안 그룹 규칙, 라우팅 테이블, 연결 옵션(VPN, VPC 피어링 등)을 더 정밀하게 조정할 수 있습니다.

- **의도치 않은 삭제와 재생성:**
    기본 VPC를 의도치 않게 삭제할 수도 있습니다. 다행히 AWS는 필요할 경우 VPC 콘솔을 통해 기본 VPC를 다시 만들 수 있는 옵션을 제공합니다. 다만 그 설정이 고정되어 있고 AWS가 관리하므로, 미션 크리티컬한 애플리케이션에서 기본 VPC에 의존하는 것은 일반적으로 권장되지 않습니다.

### 10.4 기본 VPC를 사용해야 할 때

- **프로토타이핑과 테스트:**
    기본 VPC는 즉각적인 접근과 단순함이 중요한 빠른 실험, 초기 학습, 개발에 완벽합니다.
- **비중요 애플리케이션:**
    네트워크 구성에 대한 세밀한 제어나 강화된 보안 통제가 필요하지 않은 애플리케이션이라면 기본 VPC를 사용해 설정 부담을 줄일 수 있습니다.
- **커스텀 아키텍처로의 전환:**
    기본 VPC에서 시작하더라도 요구사항이 늘어난다면 커스텀 VPC로의 마이그레이션을 계획하는 것을 고려하세요. 장기적인 확장성과 보안을 위해서는 네트워크 아키텍처를 일찍부터 커스터마이징하는 것이 권장됩니다.

## 11. 결론

AWS Virtual Private Cloud(VPC)는 안전하고 확장성 있으며 커스터마이징 가능한 AWS 네트워킹 환경의 근간입니다. 격리된 네트워크를 설계하고, IP 주소 지정을 관리하고, 라우팅을 구성하며, 보안 그룹과 네트워크 ACL 같은 도구로 계층화된 보안을 강제할 수 있게 합니다. NAT 솔루션, VPC 엔드포인트, Route 53 Resolver를 활용한 하이브리드 DNS 같은 고급 구성 요소를 통합함으로써 내부·외부 연결을 모두 최적화하고, 리전과 온프레미스 시스템 전반에서 견고한 성능과 매끄러운 통합을 보장할 수 있습니다. 동시에 Flow Log, 트래픽 미러링, Reachability Analyzer 같은 모니터링 도구는 문제 해결과 컴플라이언스 유지에 필수적인 인사이트를 제공합니다.
