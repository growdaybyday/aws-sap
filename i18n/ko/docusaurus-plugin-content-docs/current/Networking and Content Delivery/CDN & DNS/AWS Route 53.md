# AWS Route 53

## **1. 소개**

AWS Route 53은 Amazon Web Services(AWS)가 제공하는 완전관리형의 고가용성·확장성 있는 도메인 이름 시스템(DNS) 서비스입니다. 권한 있는(authoritative) DNS 응답, 도메인 등록, 고급 라우팅 기능을 하나의 통합 솔루션으로 제공하기 때문에 많은 조직의 기반 서비스로 자리 잡았습니다. 이 장에서는 Route 53이 최종 사용자 요청을 AWS 또는 외부에 호스팅된 엔드포인트로 안정적으로 라우팅하는 방식을 깊이 살펴봅니다. 또한 각 기능을 어떻게 조합해 견고하고 안전하며 비용 효율적인 DNS 솔루션을 설계할 수 있는지 살펴봅니다.

## **2. DNS 기초**

### **2.1 DNS란?**

도메인 이름 시스템(DNS)은 인터넷이나 사설 네트워크에 연결된 컴퓨터, 서비스, 리소스를 위한 계층적·분산형 이름 체계입니다. _[www.example.com](http://www.example.com/)_ 처럼 사람이 읽기 쉬운 도메인 이름을, 컴퓨터가 네트워크에서 서로를 식별하는 데 사용하는 숫자 IP 주소(예: 192.0.2.1)로 변환합니다. DNS가 없다면 사용자는 기억하기 쉬운 이름 대신 복잡한 숫자 주소를 외워야 할 것입니다.

DNS는 인터넷 통신의 근간으로 동작하며, 트리 형태의 계층 구조를 기반으로 설계되었습니다. 이 계층의 최상단에는 점(".")으로 표현되는 루트 존이 있습니다. 루트 아래에는 .com, .org, .gov 같은 최상위 도메인(TLD)이 있고, 그 아래에 2단계 도메인(예: _example.com_)이, 다시 그 아래에 서브도메인(예: _[www.example.com](http://www.example.com/)_ 또는 _api.example.com_)이 위치할 수 있습니다.

![dns-structure](@site/docs/Networking%20and%20Content%20Delivery/_assets/dns-structure.png)

기억해야 할 핵심 사항입니다.

- **계층 구조:** 도메인 이름 계층은 위임과 관리에 매우 중요합니다. 계층의 각 단계는 서로 다른 조직이 관리할 수 있습니다.
- **변환 과정:** 클라이언트가 웹 브라우저에 도메인 이름을 입력하면 요청이 로컬 DNS 리졸버로 전달되고, 리졸버는 올바른 IP 주소를 얻을 때까지 루트 서버, TLD 서버, 권한 있는 네임서버에 차례로 질의합니다.
- **캐싱:** 지연 시간과 DNS 서버 부하를 줄이기 위해, 응답은 TTL(Time-to-Live) 값에 지정된 기간 동안 로컬 리졸버에 캐시됩니다.

### **2.2 핵심 DNS 개념: 존, 레코드, 네임서버**

AWS Route 53을 본격적으로 다루기 전에 DNS의 핵심 용어와 구성 요소를 이해해야 합니다.

- **도메인 등록 대행자(Registrar):** 도메인 이름을 등록하는 서비스입니다. Amazon Route 53, GoDaddy, Google Domains 같은 등록 대행자를 통해 도메인(예: _example.com_)을 확보할 수 있으며, 일반적으로 DNS 관리 도구도 함께 제공합니다.

- **DNS 레코드:** 도메인 이름을 IP 주소나 다른 도메인 이름에 매핑하는 항목입니다. 가장 일반적인 레코드 유형은 다음과 같습니다.

    - **A 레코드:** 도메인 이름을 IPv4 주소에 매핑합니다.
    - **AAAA 레코드:** 도메인 이름을 IPv6 주소에 매핑합니다.
    - **CNAME 레코드:** 한 도메인 이름을 다른 도메인 이름의 별칭으로 지정합니다.
    - **NS 레코드:** 도메인의 권한 있는 네임서버를 지정합니다.
    - **MX 레코드:** 이메일 전달을 위한 메일 교환 서버를 정의합니다.

- **존 파일(Zone File):** 특정 도메인 또는 존의 모든 DNS 레코드를 담은 파일입니다. 권한 있는 DNS 서버가 이 파일을 관리합니다.

- **네임서버:** 존 파일을 호스팅하고 DNS 질의에 응답하는 서버입니다. 도메인을 등록하면 등록 대행자가 해당 도메인의 DNS 질의를 처리할 네임서버를 제공합니다.

- **정규화된 도메인 이름(FQDN):** DNS 계층 내에서의 정확한 위치를 나타내는 완전한 도메인 이름입니다. 예를 들어 _api.[www.example.com](http://www.example.com/)._ 처럼 끝에 점을 붙여 루트를 표시합니다.

이러한 기본 개념을 이해하는 것이 중요한 이유는, Route 53이 이 DNS 작업들을 확장하고 자동화해 도메인 이름 관리와 질의 처리를 더 쉽게 만들어 주기 때문입니다.

## **3. Route 53 소개**

### **3.1 Route 53 개요: 관리형 DNS 그리고 그 이상**

AWS Route 53은 안정적인 라우팅과 도메인 등록을 제공하도록 설계된 고가용성·확장성 DNS 서비스입니다. 권한 있는 DNS 서비스이므로, Route 53에서 DNS 레코드를 업데이트하면 도메인 이름 해석에 대한 완전한 제어권을 갖게 됩니다. 이런 권한 있는 특성 덕분에 레코드를 빠르고 확실하게 변경할 수 있어, 사용자가 항상 올바른 엔드포인트에 연결되도록 보장할 수 있습니다.

Route 53의 장점은 다음과 같습니다.

- **DNS 레코드 전면 관리:** A, AAAA, CNAME, MX, TXT 등 다양한 레코드 유형을 관리할 수 있습니다.
- **도메인 등록:** Route 53을 도메인 등록 대행자로 사용해 등록과 DNS 레코드를 하나의 서비스에서 관리할 수 있습니다.
- **라우팅 기능:** 가중치 기반 라우팅, 지연 시간 기반 라우팅, 지리적 위치 라우팅, 페일오버 라우팅 등의 기능으로 애플리케이션 요구에 맞게 DNS 응답을 조정할 수 있습니다.
- **상태 확인(Health Check):** 통합된 상태 확인으로 리소스가 비정상 상태가 되면 자동으로 페일오버합니다.
- **보안:** DNSSEC(Domain Name System Security Extensions)과 DNS Firewall 같은 고급 보안 기능이 스푸핑과 캐시 포이즈닝 공격으로부터 DNS 인프라를 보호합니다.
- **AWS 생태계와의 통합:** AWS 서비스이므로 Elastic Load Balancing(ELB), CloudFront, S3, API Gateway 등 다른 AWS 제품과 매끄럽게 통합됩니다.

"Route 53"이라는 이름 자체가 DNS가 사용하는 잘 알려진 53번 포트를 가리키면서, 단순한 이름 해석을 넘어서는 라우팅 기능을 강조합니다.

### **3.2 Route 53 핵심 기능: 도메인 등록, 라우팅, 상태 확인**

Route 53의 기능은 몇 가지 핵심 영역으로 나뉩니다.

- **도메인 등록:** Route 53에서 직접 도메인 이름을 구매하고 관리할 수 있습니다. 도메인을 등록하면 해당 DNS 레코드를 관리할 호스팅 영역(hosted zone)이 자동으로 생성됩니다.
- **DNS 레코드 관리:** 호스팅 영역 안에서 다양한 DNS 레코드를 만들고 수정합니다. A, AAAA, CNAME 같은 표준 DNS 레코드 유형과 AWS 전용 별칭(alias) 레코드를 모두 사용할 수 있는 유연성은 트래픽 라우팅에 강력한 도구가 됩니다.
- **라우팅 정책:** Route 53은 DNS 질의에 응답하는 방식을 결정하는 여러 라우팅 정책을 지원합니다. 단순한 단일 값 응답, 로드 밸런싱을 위한 가중치 분배, 지리적 트래픽 제어 등 필요한 방식을 모두 다룰 수 있습니다.
- **상태 확인과 자동 페일오버:** 통합된 상태 확인 메커니즘이 엔드포인트를 모니터링해 정상 상태인 리소스만 DNS 응답에 포함되도록 보장합니다. 주(primary) 리소스를 사용할 수 없게 되면 Route 53이 자동으로 백업 리소스로 페일오버합니다.
- **확장성과 SLA:** Route 53은 고가용성을 목표로 설계되었으며 100% 가용성 SLA를 제공해 DNS 질의가 안정적으로 처리되도록 보장합니다.

이어지는 절에서는 DNS 레코드를 관리하고, 고급 라우팅 정책을 구성하며, Route 53으로 DNS 인프라를 보호하는 방법을 살펴봅니다.

## **4. Route 53 레코드 관리**

DNS 레코드는 도메인 이름이 IP 주소와 기타 리소스에 매핑되는 방식을 정의합니다. Route 53의 모든 레코드는 레코드 유형, 값, TTL, 그리고 해당하는 경우 라우팅 정책 같은 중요한 속성을 갖습니다. 이 절에서는 Route 53의 레코드 관리에서 유의할 점을 다룹니다.

### **4.1 TTL(Time-to-Live) 이해하기**

TTL은 "Time-to-Live"의 약자로, DNS 레코드가 리졸버에 얼마나 오래 캐시될지를 정의하는 중요한 파라미터입니다. 클라이언트가 도메인 이름을 요청하면 그 DNS 응답은 TTL에 지정된 기간 동안 캐시됩니다. TTL이 크면 DNS 질의 수가 줄어 비용과 Route 53의 부하가 감소하지만, DNS 레코드 변경이 전파되는 속도도 느려집니다. 반대로 TTL이 작으면 질의 빈도가 늘어나지만 변경이 더 빨리 반영됩니다.

주요 고려사항입니다.

- **캐싱 동작:** DNS 리졸버가 레코드를 캐시하면 TTL이 만료될 때까지 그 레코드를 계속 제공합니다. Route 53에서 레코드를 변경해도 캐시된 사본이 남아 있을 수 있습니다.
- **레코드 변경 전략:** 마이그레이션이나 업그레이드처럼 리소스가 자주 바뀔 수 있는 상황에서는 TTL을 일시적으로 낮춰 두면 전환을 매끄럽게 진행할 수 있습니다.
- **비용 영향:** AWS는 DNS 질의에 대해 요금을 부과하므로, TTL을 길게 설정하면 질의 빈도가 낮아져 비용을 줄일 수 있습니다.

실무적으로는 프로덕션 시스템에 적정 수준의 TTL을 설정하고, 계획된 업데이트나 마이그레이션 기간에만 TTL을 일시적으로 낮추는 것이 좋습니다.

### **4.2 레코드 유형: CNAME vs. Alias(AWS 전용 최적화)**

Route 53은 표준 DNS 레코드 유형과 AWS 전용 별칭 레코드를 모두 지원합니다.

- **CNAME 레코드:** 정규 이름(CNAME) 레코드는 한 도메인 이름을 다른 도메인 이름에 매핑합니다. 예를 들어 _app.example.com_ 을 _myapp.loadbalancer.amazonaws.com_ 의 별칭으로 지정할 수 있습니다. CNAME 레코드는 서브도메인에만 허용되며, 존 정점(zone apex, 루트 도메인)에는 사용할 수 없습니다.
- **Alias 레코드:** Alias 레코드는 Route 53 전용이며, 도메인 이름을 AWS 리소스(Application Load Balancer, CloudFront 배포, S3 웹사이트 엔드포인트 등)에 매핑할 수 있게 합니다. 다음과 같은 장점이 있습니다.
    - 존 정점에 생성할 수 있습니다.
    - 무료입니다(별칭 레코드에 대한 질의는 별도로 과금되지 않습니다).
    - 기반이 되는 AWS 리소스의 변경 사항이 자동으로 반영됩니다.
    - Alias 레코드의 TTL은 Route 53이 자동으로 관리합니다.

DNS 전략을 설계할 때 CNAME과 Alias 중 무엇을 선택할지는 구체적인 요구사항에 따라 달라집니다. AWS 리소스라면 기본 통합과 유연성 때문에 일반적으로 Alias 레코드가 선호됩니다.

## **5. 트래픽 관리를 위한 라우팅 정책**

Route 53은 애플리케이션 요구에 따라 DNS 질의 응답 방식을 제어할 수 있는 여러 라우팅 정책을 제공합니다. 이 절에서는 각 정책을 자세히 설명하고 언제 어떻게 사용해야 하는지 살펴봅니다.

### **5.1 단순 라우팅 정책(Simple)**

단순 라우팅 정책은 Route 53에서 사용할 수 있는 가장 기본적인 방식입니다. 이 정책에서는 하나의 DNS 레코드를 하나의 리소스에 연결합니다. 다만 하나의 레코드에 여러 값(예: 여러 IP 주소)을 지정할 수도 있습니다. 여러 값이 반환되는 경우, 클라이언트는 일반적으로 그중 하나를 무작위로 선택합니다.

단순 라우팅의 사용 사례입니다.

- 도메인 이름을 단일 리소스에 직접 매핑하는 경우.
- 리소스가 자주 변경될 것으로 예상되지 않는 경우.
- 상태 확인이 필요하지 않은 경우. 단순 레코드는 상태 확인 모니터링과 직접 연결할 수 없습니다.

### **5.2 가중치 기반 라우팅 정책(Weighted)**

가중치 기반 라우팅 정책은 할당된 가중치에 따라 여러 리소스에 트래픽을 분배합니다. 예를 들어 세 엔드포인트에 각각 70, 20, 10의 가중치를 할당하면 Route 53은 트래픽의 약 70%를 첫 번째, 20%를 두 번째, 10%를 세 번째 엔드포인트로 보냅니다.

![Weighted Routing Policy](@site/docs/Networking%20and%20Content%20Delivery/_assets/weighted_routing_policy.png)

주요 세부 사항입니다.

- **상대적 가중치:** 가중치는 상대적인 값이므로 합이 100이 될 필요는 없습니다. 각 레코드의 가중치를 전체 가중치 합으로 나누어 트래픽 비율이 계산됩니다.
- **상태 확인:** 가중치 레코드에 상태 확인을 연결하면 정상 상태인 리소스만 반환됩니다.
- **동적 조정:** 가중치 기반 라우팅은 A/B 테스트, 점진적 배포, 여러 리전에 걸친 로드 밸런싱에 유용합니다.

### **5.3 지연 시간 기반 라우팅 정책(Latency-Based)**

지연 시간 기반 라우팅은 사용자를 가장 낮은 지연 시간을 제공하는 AWS 엔드포인트로 보냅니다. 이는 사용자 위치와 사용 가능한 AWS 리전 사이의 네트워크 지연을 측정해 결정됩니다. 이 정책의 주된 이점은 성능과 사용자 경험 개선입니다.

![Latency-Based Routing Policy](@site/docs/Networking%20and%20Content%20Delivery/_assets/latency-based_routing_policy.png)

고려할 사항입니다.

- **사용자 위치:** 지연 시간 기반 라우팅은 사용자의 지리적 위치에 크게 의존합니다.
- **엔드포인트 상태:** 지연 시간이 주된 판단 기준이지만, 상태 확인을 함께 사용해 정상 상태인 엔드포인트로만 트래픽이 가도록 할 수 있습니다.

### **5.4 지리적 위치 라우팅 정책(Geolocation)**

지리적 위치 라우팅은 사용자의 지리적 위치를 기준으로 트래픽을 라우팅합니다. 대륙, 국가, 심지어 주 단위까지 지정할 수 있습니다. 예를 들어 스리랑카 사용자는 현지화된 버전의 웹사이트를 호스팅하는 서버로, 미국 사용자는 다른 엔드포인트로 보내도록 DNS를 구성할 수 있습니다.

![Geolocation Routing Policy](@site/docs/Networking%20and%20Content%20Delivery/_assets/geolocation_routing_policy.png)

중요한 점입니다.

- **기본 라우팅:** 모든 사용자 위치가 특정 지리적 위치 레코드와 일치하지는 않으므로, 일치하지 않는 위치를 처리할 기본(default) 레코드를 만들어 두어야 합니다.
- **콘텐츠 현지화:** 이 정책은 지역별 콘텐츠를 제공하고 규제·컴플라이언스 요구사항을 관리하는 데 이상적입니다.

### **5.5 지리적 근접성 라우팅 정책(Geoproximity, Traffic Flow)**

지리적 근접성 라우팅은 지리적 위치 라우팅과 유사하지만, "바이어스(bias)" 값을 사용해 제어 계층을 하나 더 추가합니다. 사용자와 각 엔드포인트 사이의 상대적 거리를 기준으로 트래픽 비중을 조정하고, 여기에 바이어스 값을 반영합니다. 특정 엔드포인트의 바이어스 값을 높이면 그 엔드포인트의 영향 범위가 사실상 "확장"되어 더 많은 트래픽이 그쪽으로 향합니다.

![Geoproximity Routing Policy](@site/docs/Networking%20and%20Content%20Delivery/_assets/geoproximity_routing_policy.png)

핵심 요소입니다.

- **바이어스 값:** 양수 바이어스는 해당 엔드포인트로 트래픽을 더 보내고, 음수 바이어스는 비중을 줄입니다.
- **고급 Traffic Flow:** 이 정책은 Route 53 Traffic Flow의 그래픽 편집기를 활용하므로 지리적 경계를 시각적으로 확인하고 조정하기 쉽습니다.

### **5.6 IP 기반 라우팅 정책(IP-Based)**

IP 기반 라우팅 정책은 클라이언트의 IP 주소를 기준으로 트래픽을 보내야 하는 상황을 위해 설계되었습니다. CIDR 블록을 정의하고 이를 특정 엔드포인트에 연결합니다. DNS 질의가 들어오면 클라이언트의 IP 주소를 정의된 CIDR과 비교해 적절한 대상을 결정합니다.

사용 사례입니다.

- **네트워크 최적화:** 클라이언트의 인터넷 서비스 공급자나 네트워크 세그먼트를 기준으로 트래픽을 특정 엔드포인트로 보냅니다.
- **비용 관리:** 특정 게이트웨이나 리전을 경유하도록 트래픽을 라우팅해 네트워크 비용을 최적화합니다.

### **5.7 다중 값 응답 라우팅 정책(Multi-Value Answer)**

다중 값 응답 라우팅은 하나의 DNS 질의에 대해 정상 상태인 여러 레코드를 반환합니다. 이 정책에서 Route 53은 연결된 상태 확인을 통과한 값에 대해 최대 8개의 IP 주소(또는 기타 값)를 반환합니다. 정상 상태인 엔드포인트만 제공하면서 클라이언트 측 로드 밸런싱을 구현하려는 경우에 특히 유용합니다.

![Multi-Value Answer Routing Policy](@site/docs/Networking%20and%20Content%20Delivery/_assets/multi-value_answer_routing_policy.png)

단순 라우팅과의 차이점입니다.

- **상태 확인이 적용된 응답:** 단순 라우팅과 달리 다중 값 라우팅은 비정상 엔드포인트를 걸러낼 수 있습니다.
- **클라이언트 측 로드 밸런싱:** 클라이언트가 여러 응답을 받아 그중 하나를 선택하므로, 외부 로드 밸런서 없이도 중복성을 확보할 수 있습니다.

### **5.8 페일오버 라우팅 정책(Failover, 액티브-패시브)**

페일오버 라우팅은 재해 복구를 위해 설계된 특수 정책입니다. 이 정책에서는 한 엔드포인트를 "주(primary)", 다른 엔드포인트를 "보조(secondary)"로 지정합니다. 주 엔드포인트에는 상태 확인이 필수입니다. 주 엔드포인트가 비정상 상태가 되면 Route 53이 자동으로 트래픽을 보조 엔드포인트로 보냅니다.

![Failover Routing Policy](@site/docs/Networking%20and%20Content%20Delivery/_assets/failover_routing_policy.png)

중요한 측면입니다.

- **상태 확인 의존성:** 정확한 페일오버를 위해 주 레코드에 상태 확인이 연결되어 있어야 합니다.
- **자동 복구:** 주 엔드포인트가 복구되면 구성된 TTL과 상태 확인 주기에 따라 트래픽이 원래대로 되돌아갑니다.

## **6. 트래픽 관리와 안정성**

최종 사용자 트래픽이 올바른 리소스로 안정적으로 전달되도록 하는 것은 모든 DNS 인프라의 최우선 과제입니다. AWS Route 53은 상태 확인을 도입하고 페일오버 과정을 자동화해 트래픽 관리를 강화합니다. 이 절에서는 상태 확인의 동작 방식과 라우팅 정책과의 통합을 자세히 설명합니다.

### **6.1 Route 53 상태 확인: 엔드포인트 가용성 모니터링**

상태 확인은 웹 서버, 로드 밸런서, API 엔드포인트 같은 엔드포인트의 가용성과 성능을 모니터링하는 데 사용됩니다. Route 53 상태 확인은 주기적으로 엔드포인트에 요청을 보내고, HTTP 상태 코드, 응답 시간, 콘텐츠 검증 같은 기준에 따라 응답을 평가합니다.

주요 기능입니다.

- **글로벌 상태 검사기:** Route 53은 전 세계에 배치된 상태 검사기 네트워크를 사용합니다. 여러 위치에서 엔드포인트를 검사하므로 평가가 포괄적으로 이루어집니다.
- **주기 설정:** 원하는 반응성에 따라 상태 확인을 일정 주기(예: 30초 또는 10초마다)로 실행하도록 구성할 수 있습니다.
- **프로토콜과 포트 지원:** 상태 확인은 HTTP, HTTPS, TCP를 지원하므로 다양한 유형의 엔드포인트를 모니터링할 수 있습니다.
- **텍스트 일치 검사:** HTTP/HTTPS 상태 확인에서는 응답의 처음 5,120바이트 안에 반드시 나타나야 하는 문자열을 지정할 수 있습니다. 이를 통해 가용성뿐 아니라 콘텐츠 무결성도 검증할 수 있습니다.
- **임계값 설정:** 엔드포인트를 정상 또는 비정상으로 표시하기 전에 연속으로 몇 번의 성공 또는 실패가 필요한지 정의할 수 있습니다.

### **6.2 상태 확인과 라우팅 정책의 통합**

상태 확인은 페일오버, 가중치 기반, 다중 값 응답 라우팅을 포함한 여러 Route 53 라우팅 정책의 핵심 구성 요소입니다. 레코드에 상태 확인이 연결되면 다음과 같이 동작합니다.

- DNS 응답에 정상 상태인 엔드포인트만 반환됩니다.
- 엔드포인트에 장애가 발생하면 Route 53이 자동으로 트래픽을 백업 리소스로 전환할 수 있습니다.
- 가중치 기반 라우팅에서는 비정상 엔드포인트가 트래픽 분배에서 제외되므로, 클라이언트는 사용 가능한 응답만 받게 됩니다.

예를 들어 페일오버 구성에서 네트워크 또는 애플리케이션 장애로 주 리소스에 접근할 수 없게 되면, 상태 확인이 이를 비정상으로 표시합니다. 그러면 Route 53이 자동으로 보조(백업) 리소스를 제공해 다운타임을 최소화하고 서비스 연속성을 보장합니다.

상태 확인은 시스템 성능에 대한 유용한 통찰도 제공합니다. CloudWatch를 통해 응답 시간과 실패율 같은 지표를 모니터링하면, 관리자가 최종 사용자 경험에 영향을 미치기 전에 문제를 선제적으로 처리할 수 있습니다.

## **7. Route 53으로 도메인 관리하기**

Route 53의 도메인 관리는 새 도메인 이름 등록뿐 아니라 DNS 레코드의 효율적인 마이그레이션과 위임까지 포함합니다. 이 절에서는 Route 53을 도메인 등록 대행자와 DNS 서비스 공급자로 함께 사용하는 방법을 설명합니다.

### **7.1 서드파티 도메인을 Route 53과 함께 사용하기**

GoDaddy나 Google Domains 같은 서드파티 등록 대행자에서 도메인을 등록했더라도, DNS 레코드 관리는 Route 53으로 할 수 있습니다. 절차는 다음과 같습니다.

- **퍼블릭 호스팅 영역 생성:** Route 53에서 해당 도메인(예: _example.com_)의 호스팅 영역을 만듭니다.
- **네임서버(NS) 레코드 업데이트:** 도메인 등록 대행자 설정에서 NS 레코드를 Route 53이 제공한 네임서버로 변경합니다.
- **DNS 레코드 관리:** 네임서버가 변경되면 Route 53이 해당 도메인의 DNS 해석에 대한 권한 있는 소스가 됩니다. 이후 Route 53 콘솔에서 직접 레코드(A, AAAA, CNAME 등)를 관리할 수 있습니다.

이런 유연성 덕분에 조직은 선호하는 도메인 등록 대행자를 계속 사용하면서도 Route 53의 고급 기능을 활용할 수 있습니다.

### **7.2 Route 53으로 DNS 마이그레이션: 전략과 권장 사항**

기존 DNS 서비스를 Route 53으로 마이그레이션할 때는 다운타임을 최소화하기 위해 몇 가지 단계를 신중하게 진행해야 합니다.

1. **현재 DNS 구성 내보내기:** 현재 공급자에서 기존 DNS 레코드를 모두 추출합니다.
2. **새 호스팅 영역 생성:** Route 53에서 도메인용 퍼블릭 호스팅 영역을 만들고, 모든 DNS 레코드를 가져오거나 수동으로 다시 만듭니다.
3. **TTL 낮추기:** 네임서버를 전환하기 전에 기존 레코드의 TTL 값을 낮춥니다. 이렇게 하면 DNS 리졸버가 변경 사항을 더 빨리 반영합니다.
4. **네임서버 변경:** 도메인 등록 대행자에서 NS 레코드를 Route 53 네임서버로 변경합니다.
5. **트래픽과 성능 모니터링:** CloudWatch와 Route 53 질의 로깅으로 DNS 질의가 올바르게 해석되는지 확인합니다.
6. **롤백 전략:** 마이그레이션 중 예상치 못한 문제가 발생할 경우를 대비해 항상 롤백 계획을 준비해 둡니다.

권장 사항으로는 스테이징 환경에서 새 구성을 충분히 테스트하고, 트래픽이 적은 시간대에 마이그레이션을 진행하는 것이 있습니다.

### **7.3 서브도메인 위임: 서브도메인용 호스팅 영역**

서브도메인 위임은 _acme.example.com_ 같은 서브도메인에 대한 권한을 다른 호스팅 영역이나 심지어 다른 AWS 계정에 할당하는 과정입니다. 여러 팀이 각자의 DNS 레코드를 독립적으로 관리하는 대규모 조직에서 특히 유용합니다.

서브도메인을 위임하려면 다음과 같이 합니다.

- **서브도메인용 새 호스팅 영역 생성:** 예를 들어 _acme.example.com_ 의 호스팅 영역을 만듭니다.
- **상위 영역에 NS 레코드 생성:** 상위 도메인(_example.com_)의 호스팅 영역에서, 해당 서브도메인 호스팅 영역의 네임서버를 가리키는 NS 레코드를 만듭니다.
- **보안·관리 측면의 이점:** 서브도메인을 위임하면 상위 도메인 전체를 노출하지 않고도 특정 팀이나 외부 파트너에게 개별 IAM 권한을 부여할 수 있습니다.

서브도메인 위임은 운영 유연성을 제공하며, 크고 복잡한 DNS 인프라의 관리를 단순화할 수 있습니다.

## **8. 고급 DNS 보안**

인터넷이 발전하면서 DNS 보안의 중요성이 점점 커졌습니다. 이 절에서는 Route 53에서 사용할 수 있는 DNSSEC과 DNS Firewall 등 고급 DNS 보안 수단을 살펴보고, 이들이 일반적인 공격을 어떻게 방어하는지 설명합니다.

### **8.1 DNSSEC: 도메인 이름 시스템 보안 확장**

DNSSEC(DNS Security Extensions)은 DNS에 추가 보안 계층을 더하는 프로토콜 집합입니다. DNS 응답을 디지털 서명할 수 있게 해 DNS 스푸핑과 캐시 포이즈닝을 방어합니다. DNSSEC의 동작은 다음과 같습니다.

- **데이터 무결성과 진정성:** 각 DNS 레코드는 프라이빗 키로 암호학적으로 서명되며, 리졸버는 대응하는 퍼블릭 키로 레코드가 변조되지 않았음을 검증합니다.
- **키 서명 키(KSK)와 존 서명 키(ZSK):** KSK는 고객이 관리하며 AWS Key Management Service(KMS)에 저장되고, ZSK는 Route 53이 관리합니다. 이 둘이 함께 DNS 레코드가 안전하게 서명되도록 보장합니다.
- **신뢰 체인:** DNSSEC은 루트 존에서 개별 호스팅 영역까지 이어지는 신뢰 체인을 구성합니다. 이는 하위 영역의 KSK 해시를 담은 위임 서명자(DS) 레코드를 상위 영역에 게시함으로써 확립됩니다.

Route 53에서 DNSSEC을 활성화하는 절차입니다.

1. **준비:** 호스팅 영역이 안정적인 상태인지 확인하고, 빠른 전파를 위해 TTL 값을 낮춥니다.
2. **키 생성:** KMS에서 KSK를 만들고 관리하며, Route 53 콘솔 또는 AWS CLI에서 DNSSEC 서명을 활성화합니다.
3. **DS 레코드 게시:** 리졸버가 DNS 응답의 진정성을 검증할 수 있도록 상위 도메인에 DS 레코드를 게시합니다.
4. **모니터링:** 내부 오류나 키 서명 문제 같은 DNSSEC 지표를 모니터링하도록 CloudWatch 경보를 설정합니다.

DNSSEC은 거짓 DNS 레코드를 주입하려는 공격을 방어하는 데 필수적이며, 최종 사용자가 항상 올바르고 신뢰할 수 있는 엔드포인트로 연결되도록 보장합니다.

### **8.2 Route 53 DNS Firewall: 악성 질의 필터링**

Route 53 DNS Firewall은 VPC에서 나가는 DNS 질의를 필터링하는 관리형 보안 기능입니다. 도메인 이름을 기준으로 질의를 차단하거나 허용하는 규칙을 정의할 수 있습니다. DNS Firewall로 할 수 있는 일은 다음과 같습니다.

- **블랙리스트와 화이트리스트 구현:** 악성으로 알려진 도메인에 대한 질의를 차단하거나, 신뢰하는 도메인에 대한 질의만 허용합니다.
- **데이터 유출 방지:** 의심스러운 DNS 질의를 걸러내 DNS 기반 데이터 유출을 차단합니다.
- **페일오버 모드 선택:** 방화벽을 "fail-close" 모드(방화벽을 사용할 수 없으면 질의를 차단)나 "fail-open" 모드(방화벽 장애 시 질의를 허용)로 구성할 수 있습니다. 어느 모드를 선택할지는 보안과 가용성 중 무엇을 우선하는지에 따라 달라집니다.
- **AWS Firewall Manager와 통합:** 조직 전반의 방화벽 규칙을 중앙에서 관리하고 배포합니다.

![Route 53 DNS Firewall](@site/docs/Networking%20and%20Content%20Delivery/_assets/route_53_dns_firewall.png)

DNS Firewall은 DNS 트래픽을 필터링해 네트워크의 전반적인 보안 태세를 강화하면서, 상세한 로깅과 보고 기능도 제공합니다.

## **9. 모니터링과 컴플라이언스**

효과적인 DNS 관리는 구성만으로 끝나지 않습니다. 컴플라이언스를 보장하고 문제를 조기에 발견하려면 지속적인 모니터링과 로깅이 필요합니다. 이 절에서는 Route 53이 AWS 모니터링 도구와 로깅 서비스와 어떻게 통합되는지 다룹니다.

### **9.1 Route 53 로깅: 질의 로그와 CloudWatch 통합**

Route 53은 DNS 질의에 대한 상세 정보를 수집할 수 있는 견고한 로깅 기능을 제공합니다.

- **DNS 질의 로깅:** 퍼블릭 호스팅 영역의 DNS 질의 데이터를 CloudWatch Logs로 기록할 수 있습니다. 로그 형식에는 타임스탬프, 호스팅 영역 ID, 질의 이름, 질의 유형, 응답 코드, 프로토콜 정보, 클라이언트의 EDNS 서브넷이 포함됩니다.
- **리졸버 질의 로깅:** VPC에서 발생한 질의(Route 53 Resolver 사용)는 CloudWatch Logs, Amazon S3, Amazon Kinesis Data Firehose로 기록할 수 있습니다. 감사와 포렌식 분석에 특히 유용합니다.
- **CloudWatch 통합:** CloudWatch와 통합하면 DNS 질의량, 실패율, 성능 지표를 모니터링하는 경보와 대시보드를 구성할 수 있습니다. 이런 정보는 잠재적 보안 문제나 잘못된 구성을 식별하는 데 도움이 됩니다.
- **중앙집중식 관리:** 다중 계정 환경에서는 AWS Resource Access Manager(RAM)로 질의 로깅 구성을 여러 계정에 공유해 중앙집중식 로깅 전략을 구현할 수 있습니다.

상세한 DNS 로그를 유지하는 것은 컴플라이언스, 문제 해결, DNS 인프라 성능 최적화에 필수적입니다.

## **10. 하이브리드 및 엔터프라이즈 DNS**

많은 조직이 온프레미스 데이터센터와 AWS 클라우드에 리소스가 분산된 하이브리드 환경에서 운영됩니다. AWS Route 53은 Route 53 Resolver를 통해 이 경계를 넘어 매끄러운 DNS 경험을 구성할 수 있는 도구를 제공합니다.

### **10.1 Route 53 Resolver: 온프레미스와 클라우드 DNS 연결**

Route 53 Resolver는 VPC와 온프레미스 또는 외부 네트워크 사이에서 DNS 질의를 해석할 수 있게 합니다. 두 가지 주요 구성 요소가 있습니다.

![hybrid-dns](@site/docs/Networking%20and%20Content%20Delivery/_assets/hybrid-dns.png)

- **인바운드 엔드포인트:** 외부 DNS 리졸버(예: 온프레미스 서버)가 DNS 질의를 Route 53 Resolver로 전달할 수 있게 합니다. 이를 통해 온프레미스 클라이언트가 프라이빗 호스팅 영역에 있는 AWS 리소스의 DNS 이름을 해석할 수 있습니다.
- **아웃바운드 엔드포인트:** VPC 내부에서 시작된 DNS 질의를 온프레미스 DNS 리졸버로 전달할 수 있게 합니다. AWS 리소스가 온프레미스에 호스팅된 서비스의 도메인 이름을 해석해야 할 때 유용합니다.

### **10.2 Route 53 Resolver 엔드포인트를 활용한 하이브리드 DNS 아키텍처**

하이브리드 DNS 아키텍처를 설계할 때는 다음과 같은 핵심 설계 고려사항을 반드시 반영해야 합니다.

- **고가용성:** 복원력을 위해 인바운드·아웃바운드 엔드포인트를 여러 가용 영역(AZ)에 구성합니다. 각 엔드포인트는 VPC 내 Elastic Network Interface(ENI)와 연결됩니다.
- **조건부 전달:** 리졸버 규칙으로 어떤 DNS 질의를 온프레미스 리졸버로 전달할지 지정합니다. 이 규칙은 매우 구체적으로 설정할 수 있어, 특정 도메인 질의만 로컬 DNS 인프라로 보낼 수 있습니다.
- **중앙집중식 관리:** 다중 계정 환경에서는 AWS RAM으로 리졸버 엔드포인트와 규칙을 공유합니다. 이렇게 하면 관리 부담이 줄고 조직 전반의 일관성이 확보됩니다.
- **보안과 접근 제어:** VPC 보안 그룹과 네트워크 ACL로 리졸버 엔드포인트에 대한 접근을 제한합니다. 신뢰할 수 있는 출처만 DNS 인프라에 질의할 수 있도록 해야 합니다.
- **성능과 확장성:** 각 리졸버 엔드포인트는 IP 주소당 초당 최대 10,000개의 질의를 처리할 수 있습니다. 용량이 더 필요하면 엔드포인트 구성에 IP 주소를 추가해 확장합니다.

Route 53 Resolver가 제공하는 하이브리드 DNS 솔루션은 AWS와 온프레미스 환경을 아우르는 통합 네임스페이스를 제공해, 내부·외부 사용자 모두에게 일관된 경험을 제공합니다.

## **11. 솔루션 아키텍처**

오늘날의 역동적인 IT 환경에서는 견고하고 유연한 DNS 아키텍처를 설계하는 것이 매우 중요합니다. 이 절에서는 Route 53의 기능 전반을 활용하는 대표적인 시나리오와 솔루션 아키텍처를 살펴봅니다.

### **11.1 일반적인 Route 53 시나리오**

Route 53이 특히 효과적인 대표적 시나리오입니다.

- **단일 리소스 매핑:** 단순 A 레코드로 도메인 이름을 EC2 인스턴스나 탄력적 IP에 매핑합니다. 가장 기본적인 DNS 구성입니다.
- **다중 리전 배포:** 가중치 기반 또는 지연 시간 기반 라우팅으로 여러 AWS 리전에 배포된 리소스에 트래픽을 분배합니다. 성능과 가용성을 함께 개선할 수 있습니다.
- **재해 복구(페일오버):** 주·보조 엔드포인트를 페일오버 라우팅으로 구성합니다. 상태 확인이 주 리소스 장애 시 트래픽을 백업 리소스로 자동 전환하도록 보장합니다.
- **콘텐츠 현지화:** 지리적 위치 라우팅으로 사용자 지역에 따라 다른 콘텐츠를 제공해 현지 규제나 언어 선호를 충족합니다.
- **클라이언트 측 로드 밸런싱:** 다중 값 응답 라우팅으로 정상 상태인 여러 IP 주소를 반환해 클라이언트 측 로드 밸런싱을 구현하고 내결함성을 높입니다.

### **11.2 DNS 솔루션 아키텍처**

다음 아키텍처들은 복잡한 배포에서 Route 53을 활용하는 방법을 보여 줍니다.

#### **엔터프라이즈 다중 리전 아키텍처**

다중 리전 아키텍처에서는 지연 시간 기반 및 가중치 기반 라우팅 정책으로 여러 AWS 리전에 트래픽을 분배합니다. 상태 확인이 각 엔드포인트를 모니터링하고, 장애 발생 시 트래픽을 자동으로 전환하도록 페일오버 구성이 준비되어 있습니다. 높은 성능과 복원력이 요구되는 글로벌 애플리케이션을 지원할 수 있는 아키텍처입니다.

핵심 구성 요소입니다.

- **글로벌 로드 밸런싱:** 지연 시간 기반 라우팅과 가중치 정책을 결합해 트래픽 흐름을 최적화합니다.
- **상태 모니터링:** 상태 확인을 페일오버 라우팅과 통합해 고가용성을 보장합니다.
- **중앙집중식 로깅:** CloudWatch로 실시간 모니터링과 질의 로깅을 수행해 운영 가시성을 유지합니다.

#### **하이브리드 DNS 아키텍처**

하이브리드 DNS 아키텍처는 온프레미스 데이터센터와 AWS 리소스를 통합합니다. Route 53 Resolver(인바운드·아웃바운드 모두)를 사용해 온프레미스 네트워크와 AWS 사이에서 DNS 질의가 매끄럽게 흐르게 합니다. 온프레미스에 레거시 시스템을 유지하면서 클라우드 서비스도 활용하는 조직에 이상적입니다.

핵심 구성 요소입니다.

- **인바운드 리졸버 엔드포인트:** 온프레미스 시스템이 AWS에 호스팅된 프라이빗 DNS 레코드를 해석할 수 있게 합니다.
- **아웃바운드 리졸버 엔드포인트:** AWS 리소스가 온프레미스 도메인 이름을 해석할 수 있게 합니다.
- **조건부 전달 규칙:** 도메인 이름에 따라 특정 DNS 질의를 적절한 리졸버로 보냅니다.

#### **다중 계정 DNS 관리**

대규모 조직에서 여러 AWS 계정에 걸친 DNS 관리는 흔한 과제입니다. 서브도메인 위임, AWS Resource Access Manager(RAM), 중앙집중식 리졸버 규칙을 활용하면, 각 계정이 자체 프라이빗 호스팅 영역을 관리하면서 중앙 계정이 공유 리소스와 전달 규칙을 총괄하는 다중 계정 DNS 아키텍처를 구현할 수 있습니다.

핵심 구성 요소입니다.

- **서브도메인 위임:** 통합된 도메인을 유지하면서 서브도메인 제어권을 각 계정에 위임합니다.
- **공유 리졸버 규칙:** AWS RAM으로 리졸버 규칙과 엔드포인트를 계정 간에 공유합니다.
- **일관된 정책:** 조직 전반에 동일한 보안·라우팅 정책을 적용해 관리를 간결하게 유지합니다.

#### **보안 강화 DNS 아키텍처**

이 솔루션에서는 DNS 보안이 최우선입니다. DNSSEC을 활성화하고 Route 53 DNS Firewall을 배포하며 포괄적인 로깅을 통합해, 스푸핑 등 각종 공격에 강한 DNS 인프라를 구성합니다. 금융 기관, 정부 기관, 또는 높은 수준의 보안을 요구하는 조직에 특히 중요합니다.

핵심 구성 요소입니다.

- **DNSSEC 서명:** 퍼블릭 호스팅 영역의 데이터 무결성과 진정성을 보장합니다.
- **DNS Firewall:** 악성 질의를 차단하고 데이터 유출을 방지합니다.
- **포괄적 로깅과 모니터링:** CloudWatch와 CloudTrail로 모든 DNS 활동을 추적하고 보안 사고에 신속하게 대응합니다.

이러한 솔루션 아키텍처들은 AWS Route 53의 활용 폭을 보여 주며, 다양한 애플리케이션과 엔터프라이즈 환경의 요구를 충족하기 위해 각 기능을 어떻게 조합할 수 있는지 잘 드러냅니다.

## **12. 결론**

이 장에서는 AWS Route 53과 그 다양한 기능을 폭넓게 살펴보았습니다. DNS의 기본 개념에서 출발해 Route 53 레코드 관리의 세부 사항을 깊이 다루었고, 트래픽 흐름을 세밀하게 제어할 수 있는 여러 라우팅 정책을 살펴보았으며, 상태 확인과 페일오버 메커니즘이 어떻게 고가용성과 안정성을 보장하는지 확인했습니다. 또한 마이그레이션과 서브도메인 위임을 포함한 도메인 관리 전략과, DNSSEC 및 DNS Firewall 같은 고급 DNS 보안 기능도 다루었습니다.
