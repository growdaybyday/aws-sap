# Amazon CloudFront

## 1. 소개

오늘날의 디지털 환경에서는 최종 사용자 경험이 무엇보다 중요합니다. 속도, 응답성, 보안은 현대적인 웹 애플리케이션에 필수적입니다. CDN(Content Delivery Network)은 사용자와 더 가까운 서버에서 콘텐츠를 캐시하고 전달함으로써 지연 시간을 줄이고 콘텐츠 전송 성능을 개선하는 오버레이 네트워크입니다. 사용자 요청이 중앙집중식 데이터센터까지 멀리 이동해야 하는 전통적인 모델은 지연을 늘리고 애플리케이션 응답성을 떨어뜨릴 수 있습니다. CloudFront는 콘텐츠를 여러 엣지 위치(Edge Location)에 분산시켜, 최종 사용자가 지리적 위치와 무관하게 데이터에 빠르고 효율적으로 접근할 수 있게 함으로써 이런 한계를 극복합니다.

CloudFront는 단순한 캐싱 메커니즘이 아니라, 다음을 제공하는 종합적인 솔루션입니다.

- **글로벌 배포:** 전 세계에 흩어진 수백 개의 엣지 위치를 통해, 최종 사용자와 가장 가까운 위치에서 콘텐츠를 제공함으로써 지연 시간을 최소화합니다.
- **확장성과 성능:** CloudFront는 AWS 인프라의 거대한 규모를 활용해 초당 수백만 건의 요청을 처리하면서도 높은 처리량을 유지합니다.
- **보안:** AWS Shield, AWS WAF와의 통합, Origin Access Control(OAC) 같은 기능을 통해 DDoS(분산 서비스 거부) 공격을 방어하고 인증된 요청만 오리진에 도달하도록 보장해 보안을 강화합니다.
- **유연성:** CloudFront는 Amazon S3 버킷, Application Load Balancer(ALB), 커스텀 HTTP 서버 등 다양한 오리진 유형을 지원하며 캐싱 동작을 세밀하게 제어할 수 있습니다.
- **비용 효율성:** 자주 접근되는 콘텐츠를 엣지에서 캐시함으로써 오리진의 부하를 줄여, 대역폭과 컴퓨팅 리소스 비용을 절감할 수 있습니다.

## 2. 핵심 개념

이 절에서는 Amazon CloudFront의 기본 요소를 깊이 살펴봅니다. 전체 아키텍처와 동작 흐름을 먼저 살펴보고, 이어서 CloudFront와 통합할 수 있는 다양한 오리진 유형을 다룹니다.

### 2.1 CloudFront 개요: 동작 방식

CloudFront는 전 세계 규모의 콘텐츠 전송을 최적화하도록 2단계 캐싱 계층을 중심으로 설계되었습니다. 이 동작 원리를 이해하려면 두 개의 주요 캐싱 계층, 즉 엣지 위치와 리저널 엣지 캐시(Regional Edge Cache)의 역할을 파악하는 것이 중요합니다.

#### 2.1.1 2단계 캐싱 아키텍처

![cloudfront-The Two-Tier Caching Architecture](@site/docs/Networking%20and%20Content%20Delivery/_assets/cloudfront-the_two-tier_caching_architecture.png)

- **엣지 위치:**
	최종 사용자에게 콘텐츠가 제공되는 첫 번째 지점입니다. 사용자가 이미지, 비디오, 웹 페이지 같은 파일을 요청하면, 네트워크 근접성과 지연 시간을 고려해 가장 가까운 엣지 위치로 요청이 라우팅됩니다. 요청한 오브젝트가 엣지 위치에 캐시되어 있으면 즉시 사용자에게 제공되어 빠른 응답 시간을 보장합니다. 캐시되어 있지 않으면 엣지 위치가 요청을 리저널 엣지 캐시로 전달합니다.

- **리저널 엣지 캐시:**
    리저널 엣지 캐시는 엣지 위치와 오리진 사이의 중간 계층 역할을 합니다. 더 큰 용량의 캐시를 유지하며, 자주 요청되지 않는 오브젝트도 더 오래 보관할 수 있습니다. 엣지 위치에서 오브젝트를 찾지 못하면 리저널 엣지 캐시에 질의합니다. 리저널 캐시에서도 찾지 못하면 요청이 오리진 서버(Amazon S3 버킷, Application Load Balancer, 또는 다른 HTTP 서버일 수 있습니다)로 전달됩니다. 오리진이 요청한 콘텐츠를 반환하면 리저널 엣지 캐시에 캐시된 다음 엣지 위치에도 캐시되고, 마지막으로 최종 사용자에게 전달됩니다.

이런 다단계 캐싱 계층은 동일한 캐시된 오브젝트로 여러 사용자에게 응답함으로써 오리진 서버의 부하를 줄이는 동시에, 가능한 가장 가까운 위치에서 콘텐츠를 제공해 지연 시간을 최소화합니다.

#### 2.1.2 요청의 흐름

![cloudfront-Flow of a Request](@site/docs/Networking%20and%20Content%20Delivery/_assets/cloudfront-flow_of_a_request.png)

1. 사용자가 웹사이트나 애플리케이션에 접속해 이미지 파일이나 HTML 파일 같은 오브젝트를 요청합니다.
2. DNS가 요청을 가장 잘 처리할 수 있는 CloudFront POP(엣지 위치)로 요청을 라우팅합니다. 일반적으로 지연 시간 기준으로 가장 가까운 CloudFront POP입니다.
3. CloudFront가 캐시에서 요청한 오브젝트를 확인합니다. 캐시에 있으면 사용자에게 바로 반환합니다. 캐시에 _없으면_ CloudFront는 다음을 수행합니다.
    1. CloudFront가 요청을 배포(distribution) 설정과 대조해, 해당 오브젝트에 대한 요청을 오리진 서버(예: Amazon S3 버킷 또는 HTTP 서버)로 전달합니다.
    2. 오리진 서버가 오브젝트를 엣지 위치로 반환합니다.
    3. 오리진에서 첫 바이트가 도착하는 즉시 CloudFront는 오브젝트를 사용자에게 전달하기 시작합니다. 동시에 다음번 요청을 위해 오브젝트를 캐시에 저장합니다.

이 과정은 모든 리전에서 반복되고 최적화되어, 인기 있는 콘텐츠가 네트워크의 여러 계층에 캐시되도록 합니다.

#### 2.1.3 CloudFront 아키텍처의 이점

2단계 캐싱 시스템은 다음과 같은 여러 이점을 제공합니다.

- **지연 시간 감소:** 최종 사용자에게 더 가까운 곳에서 콘텐츠를 캐시함으로써 콘텐츠 전달에 필요한 네트워크 홉 수를 크게 줄여 로드 시간을 개선합니다.
- **가용성 향상:** 분산 아키텍처 덕분에 한 리전이나 엣지 위치에 트래픽이 몰리거나 장애가 발생해도 다른 위치가 계속 콘텐츠를 제공할 수 있습니다.
- **오리진 부하 감소:** 반복적인 콘텐츠 전달을 엣지 위치와 리저널 캐시로 분산시킴으로써 오리진이 대량의 요청에 압도되지 않도록 보호합니다.
- **보안 강화:** 캐싱이 글로벌 네트워크 전반에 분산되어 있어 CloudFront는 DDoS 공격에 대한 방어막도 제공합니다. 오리진이 공격 대상이 되어도 많은 요청이 분산된 캐시에서 흡수됩니다.

#### 2.1.4 다른 AWS 서비스와의 통합

CloudFront는 다른 AWS 서비스와 깊이 통합되어 있어 전 세계에 분산된 애플리케이션을 매끄럽게 배포할 수 있습니다. 주요 통합은 다음과 같습니다.

- **Amazon S3:**
    CloudFront는 S3 버킷에 저장된 콘텐츠를 캐시하는 데 사용할 수 있으며, 정적 웹사이트 호스팅이든 파일의 안전한 저장이든 모두 가능합니다. Origin Access Control(OAC)과 함께 사용하면 CDN에서 오는 요청만 S3 버킷에 접근할 수 있게 되어 보안이 크게 강화됩니다.

- **Elastic Load Balancing(ELB):**
    CloudFront는 Application Load Balancer(ALB) 및 Classic Load Balancer(CLB)와 함께 동작해 동적 콘텐츠를 배포합니다. 이 통합을 통해 CDN이 동적 웹 페이지와 API 응답의 캐싱을 효율적으로 관리할 수 있습니다.

- **AWS Certificate Manager(ACM):**
    ACM으로 SSL/TLS 인증서를 관리하여, 뷰어와 CloudFront 사이, 그리고 CloudFront와 오리진 사이의 통신을 안전하게 보호할 수 있습니다.

- **AWS Shield와 AWS WAF:**
    AWS Shield 및 AWS WAF(Web Application Firewall)와의 통합으로 추가적인 보안 계층이 제공되어, DDoS 공격과 악성 트래픽으로부터 콘텐츠 전송 네트워크를 보호합니다.

정리하면, 엣지 위치와 리저널 엣지 캐시를 전략적으로 결합한 CloudFront의 핵심 아키텍처는 전 세계에 빠르고 안전하며 안정적으로 콘텐츠를 전달할 수 있게 합니다.

### 2.2 CloudFront 오리진: S3, ALB, 커스텀 오리진, 다중 오리진 구성

CloudFront의 유연성은 다양한 오리진 소스와 통합할 수 있는 능력에서 대부분 비롯됩니다. 이 절에서는 다양한 오리진 유형과 이를 구성하기 위한 모범 사례를 살펴봅니다.

#### 2.2.1 오리진으로서의 Amazon S3

Amazon S3(Simple Storage Service)는 CloudFront와 함께 가장 흔히 사용되는 오리진입니다. 정적 웹사이트, 다운로드 가능한 파일, 미디어 콘텐츠를 제공하는 데 있어 S3는 매우 확장성 있고 안정적입니다.

- **Origin Access Control로 보안 강화:**
    CloudFront는 Origin Access Control(OAC, 이전 명칭 Origin Access Identity/OAI)을 사용해 S3 버킷과 연동하도록 구성할 수 있습니다. 이 메커니즘은 S3에 저장된 오브젝트가 CloudFront를 통해서만 접근되도록 보장해, S3의 퍼블릭 엔드포인트를 통한 직접 접근을 막습니다. 일반적인 구성에서는 버킷 정책을 설정해 OAC가 GET 작업을 수행하도록 허용하고 모든 퍼블릭 접근 시도는 거부합니다.

- **정적 웹사이트 콘텐츠 전달:**
    S3로 정적 웹사이트를 호스팅할 때는 버킷에서 정적 웹사이트 호스팅을 활성화해야 합니다. 이후 CloudFront를 S3 웹사이트 엔드포인트 앞에 두어 안전하고 낮은 지연 시간으로 콘텐츠를 전달할 수 있습니다.

- **미디어 전송:**
    CloudFront는 VoD(주문형 비디오)와 AWS Media Services를 통한 라이브 스트리밍을 포함한 미디어 스트리밍 애플리케이션의 오리진으로도 S3를 지원합니다. CloudFront의 캐싱 기능은 버퍼링을 줄이고 매끄러운 시청 경험을 보장하는 데 필수적입니다.

#### 2.2.2 오리진으로서의 Application Load Balancer와 EC2

서버 측 처리가 필요한 동적 콘텐츠와 애플리케이션을 위해, CloudFront는 Application Load Balancer(ALB)와 EC2 인스턴스와 통합할 수 있습니다.

- **Application Load Balancer 사용:**
    ALB는 하나 이상의 가용 영역에 있는 여러 대상(예: EC2 인스턴스)에 들어오는 트래픽을 분산합니다. CloudFront가 ALB를 오리진으로 사용할 때는, CloudFront의 엣지 위치가 퍼블릭 IP 주소로 콘텐츠를 가져오므로 ALB가 퍼블릭에서 접근 가능해야 합니다. 또한 ALB의 보안 그룹이 알려진 CloudFront IP 주소 범위에서의 인바운드 요청을 허용하도록 구성해야 합니다.

- **EC2의 커스텀 HTTP 오리진:**
    CloudFront는 EC2 인스턴스나 온프레미스 서버에서 실행되는 커스텀 HTTP 서버의 콘텐츠도 제공할 수 있습니다. ALB와 마찬가지로 이 오리진들도 퍼블릭에서 접근 가능해야 합니다. 일반적인 보안 구성으로는 CloudFront IP 주소를 화이트리스트에 등록하고, CloudFront가 삽입하는 특정 헤더나 보안 토큰을 서버가 인식하도록 설정하는 것이 있습니다.

- **다중 오리진 구성:**
    정적 이미지, 동적 API 응답, 개인화된 웹 페이지처럼 서로 다른 유형의 콘텐츠가 서로 다른 오리진에 호스팅되는 경우가 많습니다. CloudFront는 URL 경로 패턴에 따라 다른 캐시 동작을 정의할 수 있게 하여 하나의 배포 안에서 여러 오리진을 구성할 수 있습니다. 예를 들어 `/images/*`로의 요청은 S3 버킷으로, `/api/*`로의 트래픽은 동적 콘텐츠를 제공하는 ALB로 라우팅할 수 있습니다. 이런 유연성 덕분에 콘텐츠 유형별로 캐싱과 보안 정책을 최적화할 수 있습니다.

#### 2.2.3 커스텀 오리진과 사용 사례

커스텀 오리진은 S3나 ALB 같은 네이티브 AWS 서비스가 아닌 모든 HTTP/HTTPS 서버를 가리킵니다. 다음과 같은 예가 있습니다.

- **온프레미스 서버:**
    레거시 시스템이나 특정 컴플라이언스 요구사항이 있는 조직은 자체 서버에 콘텐츠를 호스팅할 수 있습니다. CloudFront를 이런 온프레미스 오리진 앞에 CDN으로 배치하면 성능을 개선하고 추가적인 보안 기능을 제공할 수 있습니다.

- **서드파티 웹 서버:**
    AWS가 아닌 호스팅을 사용하더라도, CloudFront의 글로벌 엣지 위치 네트워크는 콘텐츠 전달을 가속화하고 지연 시간을 줄여 줍니다.

- **API 엔드포인트:**
    RESTful API나 GraphQL 엔드포인트를 배포할 때 커스텀 오리진을 사용하면 CloudFront의 캐싱과 보안 기능을 활용해 동적이고 캐시할 수 없는 콘텐츠를 효과적으로 처리할 수 있습니다.

#### 2.2.4 다중 오리진과 오리진 그룹

가용성과 복원력을 최대화하기 위해 CloudFront는 다중 오리진 구성과 오리진 그룹을 지원합니다.

- **경로 패턴에 따른 라우팅:**
    앞서 설명했듯이 CloudFront는 URL 경로 패턴을 기준으로 하나의 배포 안에서 여러 오리진을 정의할 수 있게 합니다. 이를 통해 특정 콘텐츠를 어느 오리진이 제공할지 세밀하게 제어할 수 있어, 캐시 동작과 보안 설정을 최적화할 수 있습니다.

- **오리진 페일오버:**
    미션 크리티컬 애플리케이션의 경우, 주 오리진과 하나 이상의 보조 오리진을 정의하는 오리진 그룹을 구성할 수 있습니다. 네트워크 문제, 장애, 내부 오류 등으로 주 오리진이 제대로 응답하지 못하면 CloudFront가 자동으로 백업 오리진으로 페일오버합니다. 이런 중복성은 고가용성을 유지하고 최종 사용자가 지역적 장애의 영향을 받지 않도록 하는 데 필수적입니다.

- **다중 리전 배포:**
    경우에 따라 여러 AWS 리전에 오리진을 배포하는 것이 유리할 수 있습니다. 예를 들어 한 리전의 S3 버킷을 주 오리진으로, 다른 리전의 S3 버킷을 백업으로 사용할 수 있습니다. 버킷 간 복제를 적절히 구성하면 CloudFront가 고가용성의 다중 리전 콘텐츠 전송 솔루션을 제공할 수 있습니다.

정리하면, 오리진을 구성하는 유연성은 CloudFront의 핵심 강점 중 하나입니다. S3 버킷의 정적 콘텐츠든, ALB의 동적 콘텐츠든, 온프레미스 서버의 커스텀 콘텐츠든, CloudFront의 아키텍처와 구성 옵션을 통해 성능·보안·안정성 요구에 맞게 전송 네트워크를 조정할 수 있습니다.

## 3. 오리진 구성과 보안

견고한 CloudFront 배포를 설계할 때 중요한 부분은 오리진이 성능만 최적화되는 것이 아니라 무단 접근으로부터도 보호받도록 하는 것입니다. 이 절에서는 헤더를 통한 오리진 동작 커스터마이징, Origin Access Control(OAC)과 AWS WAF로 오리진을 보호하는 방법, 고가용성을 위한 오리진 페일오버 구현 기법을 살펴봅니다.

### 3.1 헤더로 오리진 동작 커스터마이징

CloudFront는 CDN에서 오리진으로 전달되는 요청에 HTTP 헤더를 삽입하고 조작할 수 있습니다. 이 기능은 보안, 캐싱 최적화, 콘텐츠 개인화 등 여러 이유로 매우 중요합니다.

#### 3.1.1 커스텀 헤더의 역할

커스텀 헤더는 몇 가지 핵심 기능을 수행합니다.

- **인증과 인가:**
    비밀 헤더(예: `X-Origin-Verify`)를 삽입함으로써 CloudFront는 해당 요청이 CDN을 통해 검증되었음을 오리진에 알릴 수 있습니다. 오리진은 올바른 헤더와 값이 포함된 요청만 허용하도록 강제할 수 있어, 직접 접근 시도를 효과적으로 차단할 수 있습니다.
- **캐시 키 정규화:**
    커스텀 헤더는 CloudFront가 사용하는 캐시 키를 세밀하게 조정하는 데 사용할 수 있습니다. 예를 들어 특정 디바이스 유형별로 콘텐츠를 캐시하고 싶다면 사용자의 디바이스를 나타내는 헤더를 삽입해 CloudFront가 요청을 구분할 수 있게 합니다.
- **요청 라우팅:**
    여러 오리진이 구성되어 있을 때 커스텀 헤더로 라우팅 결정을 조정할 수 있습니다. 예를 들어 특정 헤더는 요청이 주 오리진에서 처리되어야 함을 나타내고, 다른 헤더는 보조 오리진으로 페일오버를 유발할 수 있습니다.

#### 3.1.2 커스텀 헤더의 실제 동작 방식

사용자가 CloudFront로 요청을 보내면 그 요청에는 이미 user-agent나 쿠키 같은 특정 HTTP 헤더가 포함되어 있을 수 있습니다. CloudFront는 요청이 오리진으로 전달되기 전에 고정된 값을 갖는 추가 헤더를 삽입할 수 있게 합니다. 이는 캐시 동작 구성의 일부로 헤더 이름과 값을 정의함으로써 이루어집니다. 오리진은 이 헤더들을 확인해 자체적인 보안이나 비즈니스 로직을 적용합니다.

예를 들어 오리진이 CloudFront에서 온 요청만 수락해야 하는 시나리오를 생각해 봅시다. CloudFront가 모든 오리진 요청에 커스텀 헤더(예: `X-CloudFront-Secure: true`)를 삽입하도록 구성할 수 있습니다. 그러면 ALB든 커스텀 HTTP 서버든 오리진 서버는 이 헤더가 없는 모든 요청을 거부하도록 프로그래밍됩니다. 이 2단계 보안 메커니즘은 CloudFront에서 검증된 트래픽만 오리진에 도달하도록 보장합니다.

#### 3.1.3 동적 헤더 vs. 고정 헤더

CloudFront는 두 가지 유형의 헤더 삽입을 지원합니다.

- **고정 헤더:**
    요청마다 값이 바뀌지 않는 미리 정해진 값입니다. 일관되게 유지되어야 하는 인증 토큰이나 비밀 키에 적합합니다.
- **동적 헤더:**
    뷰어 요청의 속성을 기반으로 생성되는 헤더도 있습니다. 예를 들어 CloudFront는 뷰어의 디바이스 유형, 지리적 위치(도시나 국가), 사용된 HTTP 버전을 나타내는 헤더를 전달할 수 있습니다. 오리진은 이런 동적 헤더를 사용해 응답을 조정하거나 특정 비즈니스 규칙을 적용할 수 있습니다.

#### 3.1.4 커스텀 헤더 삽입의 사용 사례

헤더를 커스터마이징할 수 있는 능력은 다양한 가능성을 엽니다.

- **CloudFront 트래픽 식별:**
    커스텀 헤더는 오리진이 정상적인 CloudFront 요청과 잠재적으로 악의적인 직접 요청을 구분하는 데 도움을 줍니다.
- **A/B 테스트 지원:**
    특정 사용자 세그먼트를 나타내는 헤더를 삽입함으로써 오리진이 다른 콘텐츠를 제공하거나 캐싱 전략을 달리할 수 있습니다.
- **캐시 성능 최적화:**
    특정 뷰어 특성을 식별하는 헤더는 더 세밀한 캐시 키를 만드는 데 도움이 되어, 캐싱 효율을 희생하지 않으면서도 개인화된 콘텐츠를 정확하게 전달할 수 있습니다.

결론적으로 커스텀 헤더는 CloudFront의 강력한 도구입니다. 인가된 트래픽만 오리진에 도달하도록 보안을 강화하는 동시에, 캐싱과 콘텐츠 전송 전략을 세밀하게 조정할 유연성도 제공합니다.

### 3.2 오리진 보호: Origin Access Control(OAC)과 AWS WAF 통합

글로벌 CDN을 배포할 때는 보안이 최우선입니다. 이 절에서는 두 가지 핵심 보안 메커니즘, 즉 Origin Access Control(OAC)과 AWS WAF(Web Application Firewall)를 살펴봅니다. 이 두 기능은 함께 동작하여, S3 버킷이든 커스텀 HTTP 서버든 오리진 리소스가 CloudFront를 통해서만 접근되도록 보장합니다.

#### 3.2.1 Origin Access Control(OAC)로 S3 오리진 보호하기

Amazon S3를 CloudFront의 오리진으로 사용할 때는 공용 인터넷에서 S3 오브젝트로의 직접 접근을 막는 것이 중요합니다. Origin Access Control(OAC)은 S3 버킷이 지정된 CloudFront 배포에서 오는 요청만 수락하도록 강제하는 메커니즘입니다.

- **OAC의 동작 방식:**
    OAC는 CloudFront 배포에 아이디(이전에는 Origin Access Identity/OAI로 불렸습니다)를 연결해 구현됩니다. 이후 S3 버킷 정책을 구성해 오직 그 아이디에만 읽기 권한을 부여합니다. 결과적으로 CloudFront를 우회해 S3 버킷에 직접 접근하려는 모든 시도는 거부됩니다.

- **보안 강화 이점:**
    이 구성은 S3 버킷을 무단 접근으로부터 보호할 뿐 아니라, 데이터 유출과 무단 콘텐츠 스크래핑의 위험도 줄여 줍니다. 모든 요청이 CloudFront의 캐싱, 로깅, 보안 메커니즘의 적용을 받도록 보장합니다.

#### 3.2.2 AWS WAF와 커스텀 헤더로 커스텀 오리진 보호하기

EC2 인스턴스나 온프레미스 서버에 호스팅된 커스텀 오리진에는 S3처럼 내장된 접근 제어가 없습니다. 이런 오리진을 보호하려면 두 가지 전략을 결합할 수 있습니다.

- **커스텀 헤더를 활용한 애플리케이션 계층 보안:**
    3.1절에서 설명했듯이 CloudFront는 요청에 커스텀 HTTP 헤더를 삽입할 수 있습니다. 오리진을 구성해 이런 헤더가 없는 요청을 거부하도록 하면 첫 번째 방어 계층이 만들어집니다.
- **AWS WAF를 활용한 네트워크 계층 보안:**
    AWS WAF(Web Application Firewall)는 Application Load Balancer에 직접 통합하거나 CloudFront 앞의 추가 계층으로 커스텀 오리진 앞에 배포할 수 있습니다. WAF는 IP 주소, HTTP 헤더, 쿼리 문자열 등 다양한 특성을 기준으로 트래픽을 차단하거나 허용하는 규칙을 정의할 수 있게 합니다. 예를 들어 올바른 커스텀 헤더가 포함된 요청만 허용하는 WAF 규칙을 만들 수 있습니다. 이 규칙은 악의적인 행위자가 오리진에 직접 접근하려는 모든 시도를 차단합니다.

#### 3.2.3 최대 보안을 위한 자동 키 교체

특히 인증에 커스텀 헤더를 사용할 때는 보안 강화를 위해 비밀 값을 주기적으로 교체하는 것이 모범 사례입니다. AWS Secrets Manager를 사용해 자동 교체 정책과 함께 이런 비밀 키를 저장할 수 있습니다. Lambda 함수(또는 다른 자동화 메커니즘)가 CloudFront 배포와 WAF 규칙 양쪽에서 커스텀 헤더 값을 갱신할 수 있어, 키가 항상 최신 상태로 안전하게 유지됩니다. 이런 교체는 공격자가 탈취한 키를 사용할 수 있는 시간대를 최소화합니다.

#### 3.2.4 오리진 보안 실무 요약

정리하면, CloudFront 구성에서 오리진을 보호하는 방법은 다음과 같습니다.

- **S3 오리진의 경우:**
    OAC를 사용해 CloudFront에서 오는 요청만 S3 버킷에 접근할 수 있도록 합니다.
- **커스텀 오리진의 경우:**
    커스텀 헤더 삽입과 AWS WAF 규칙을 조합해 접근 제한을 강제합니다.
- **추가 조치:**
    CloudFront IP 범위를 화이트리스트에 등록하는 네트워크 계층 보안을 구현하고, 키 교체를 자동화해 견고한 보안 태세를 유지합니다.

### 3.3 오리진 페일오버: 중요 워크로드를 위한 고가용성

미션 크리티컬 애플리케이션에서는 고가용성이 필수적입니다. CloudFront는 오리진 페일오버를 지원해, 주 오리진에 문제가 발생해도 애플리케이션이 계속 사용 가능하도록 보장합니다.

![cloudfront- Origin Failover](@site/docs/Networking%20and%20Content%20Delivery/_assets/cloudfront-_origin_failover.png)

#### 3.3.1 오리진 그룹 구성하기

오리진 그룹은 두 개 이상의 오리진이 페일오버 관계로 연결된 구성입니다.

- **주 오리진:**
    CloudFront가 콘텐츠를 가져올 때 사용하는 기본 오리진입니다.
- **보조 오리진:**
    주 오리진이 요청한 콘텐츠를 전달하지 못할 때(접근할 수 없거나 오류 상태 코드를 반환할 때) CloudFront가 자동으로 전환하는 백업 오리진입니다.

이렇게 오리진을 그룹으로 묶으면 지역적 장애나 국지적 문제를 견딜 수 있는 복원력 있는 콘텐츠 전송 솔루션을 구성할 수 있습니다.

#### 3.3.2 다중 리전·다중 공급자 구성

고가용성은 오리진을 여러 리전이나 심지어 다른 서비스 공급자에 배포함으로써 더욱 강화할 수 있습니다.

- **다중 리전 배포:**
    예를 들어 한 AWS 리전의 S3 버킷을 주 오리진으로, 다른 리전의 두 번째 S3 버킷을 백업으로 사용할 수 있습니다. 두 버킷 사이에 데이터 복제가 구성되어 있으면, 주 버킷을 사용할 수 없을 때 CloudFront가 백업으로 매끄럽게 전환할 수 있습니다.
- **서로 다른 오리진 유형 결합:**
    일부 아키텍처에서는 ALB 기반의 동적 오리진과 S3 기반의 정적 오리진을 결합할 수 있습니다. 이런 경우 동적 콘텐츠 서비스에 문제가 생기면 CloudFront가 ALB에서 S3 버킷으로 페일오버하도록 구성할 수 있습니다.

#### 3.3.3 페일오버 메커니즘과 상태 확인

CloudFront는 오리진 그룹 내 각 오리진의 가용성을 모니터링하기 위해 상태 확인을 사용합니다. 이 상태 확인은 주 오리진에 장애가 발생하면 시스템이 신속하게 문제를 파악해 정상 상태인 백업으로 트래픽을 라우팅하도록 보장합니다.

- **자동 페일오버:**
    상태 확인 결과 주 오리진이 오류를 반환하거나 응답하지 않는 것으로 나타나면, 별도의 수동 개입 없이 CloudFront가 자동으로 보조 오리진으로 전환합니다.
- **구성 가능한 기준:**
    연속으로 몇 번의 상태 확인이 실패해야 하는지, 어떤 HTTP 오류 코드를 기준으로 삼는지 같은 페일오버 기준은 애플리케이션 요구에 맞게 커스터마이징할 수 있습니다.

#### 3.3.4 고가용성을 위한 모범 사례

최대한의 복원력을 확보하려면 다음 모범 사례를 고려하세요.

- **중복성:**
    항상 최소 하나의 백업 오리진을 구성해 두세요. 중요한 워크로드라면 여러 개의 백업 오리진을 고려하세요.
- **정기적인 상태 확인 모니터링:**
    상태 확인 결과를 지속적으로 모니터링하고 이상 징후를 알리는 경보를 설정하세요.
- **지리적 분산:**
    지역적 장애의 영향을 줄이기 위해 여러 지리적 리전에 오리진을 배포하세요.
- **일관된 데이터 복제:**
    S3 기반 오리진의 경우, 콘텐츠 불일치 없이 페일오버가 일어날 수 있도록 리전 간 데이터가 일관되게 복제되도록 하세요.

오리진 페일오버 메커니즘을 활용하면 오리진에 지역적 장애가 발생해도 전 세계 사용자에게 끊김 없는 서비스를 유지할 수 있습니다.

## 4. 암호화와 안전한 전송

인터넷을 통해 콘텐츠를 전달할 때 보안은 근본적인 관심사입니다. CloudFront는 클라이언트와 오리진 사이의 연결이 안전하게 유지되도록 여러 메커니즘을 제공합니다. 이 절에서는 HTTPS를 강제하고 종단 간 암호화를 구성하는 데 필요한 실무와 기술을 살펴봅니다.

### 4.1 HTTPS 강제: SSL/TLS 인증서와 뷰어 프로토콜 정책

최종 사용자(뷰어)와 CloudFront 사이의 연결을 보호하는 것은 데이터 무결성과 기밀성을 보장하는 첫 단계입니다. HTTPS(SSL/TLS 사용)는 웹 트래픽을 보호하는 업계 표준입니다.

#### 4.1.1 뷰어 프로토콜 정책

CloudFront의 뷰어 프로토콜 정책은 뷰어의 브라우저가 엣지 위치와 통신하는 방식을 결정합니다.

- **모두 허용(Allow All):**
    HTTP와 HTTPS 요청을 모두 수락합니다. 이 정책은 최대한의 호환성을 제공하지만 필요한 수준의 보안을 보장하지는 못할 수 있습니다.
- **HTTP를 HTTPS로 리디렉션:**
    이 구성에서는 모든 HTTP 요청이 자동으로 HTTPS로 리디렉션되어 모든 트래픽이 암호화되도록 보장합니다.
- **HTTPS만 허용:**
    HTTPS 요청만 수락하고 HTTP 요청은 모두 거부합니다. 모든 연결이 암호화됨을 보장하므로 가장 높은 수준의 보안을 제공합니다.

민감한 데이터를 다루거나 규제 준수가 필요한 현대적인 애플리케이션이라면 일반적으로 HTTPS만 허용하는 정책을 권장합니다.

#### 4.1.2 오리진 프로토콜 정책

오리진 프로토콜 정책은 CloudFront가 오리진 서버와 통신하는 방식을 제어합니다.

- **HTTP만 사용:**
    암호화되지 않은 HTTP로 콘텐츠를 가져옵니다. 오리진을 신뢰할 수 있고 암호화가 걱정되지 않는 경우에만 권장됩니다.
- **HTTPS만 사용:**
    CloudFront가 HTTPS로 오리진과 안전한 연결을 구성합니다. 종단 간 암호화를 유지하기 위해 권장됩니다.
- **뷰어와 동일:**
    CloudFront가 뷰어가 사용한 것과 동일한 프로토콜로 오리진에 연결합니다. 뷰어의 요청에 따라 보안과 성능의 균형을 맞출 수 있는 유연한 선택지입니다.

#### 4.1.3 SSL/TLS 인증서와 대체 도메인 이름

HTTPS가 올바르게 동작하려면 유효한 SSL/TLS 인증서가 준비되어 있어야 합니다.

- **기본 CloudFront 인증서:**
    CloudFront는 기본 인증서(예: `*.cloudfront.net`)를 제공해 HTTPS를 빠르게 시작할 수 있게 합니다.
- **커스텀 인증서:**
    `www.example.com` 같은 자체 도메인 이름을 사용하려면 AWS Certificate Manager(ACM)로 인증서를 가져오거나 서드파티 인증서를 업로드할 수 있습니다. 커스텀 도메인 이름을 사용할 때는 CloudFront 배포에서 대체 도메인 이름(CNAME)을 구성해야 합니다.
- **전용 IP vs. SNI:**
    CloudFront는 SSL/TLS를 위해 SNI(Server Name Indication)와 전용 IP 주소 옵션을 모두 지원합니다. 대부분의 상황에서는 비용 효율적이고 확장성이 좋은 SNI가 권장됩니다.

#### 4.1.4 보안 정책과 암호 스위트

HTTPS 연결을 더 강화하기 위해 CloudFront는 다음을 정의하는 보안 정책을 지정할 수 있게 합니다.

- **최소 TLS 버전:**
    최신의 안전한 TLS 버전(예: TLS 1.2 또는 TLS 1.3)만 허용되도록 보장합니다.
- **암호 스위트:**
    허용할 암호 목록을 지정해 취약한 암호화 알고리즘이 사용되지 않도록 합니다.

이런 정책을 구성하면 사용 가능한 가장 강력한 암호화 방식으로 모든 연결이 보호되도록 보장할 수 있습니다.

### 4.2 종단 간 암호화: 오리진-뷰어 데이터 보안

뷰어와 CloudFront 사이의 HTTPS 강제는 중요하지만, 오리진 서버에서 뷰어까지 이르는 전체 데이터 경로가 암호화되는 것도 그만큼 중요합니다. 종단 간 암호화는 모든 단계에서 데이터가 보호되도록 보장합니다.

#### 4.2.1 종단 간 암호화가 필요한 이유

많은 애플리케이션에서 클라이언트와 오리진 사이에 민감한 정보가 전송될 수 있습니다. 종단 간 암호화는 공용 인터넷과 AWS 내부 네트워크를 포함한 여러 네트워크를 거치는 동안 데이터의 기밀성과 무결성이 유지되도록 보장합니다.

#### 4.2.2 종단 간 암호화 구성하기

종단 간 암호화를 달성하려면 다음이 필요합니다.

- **오리진 구성:**
    오리진이 HTTPS 연결을 수락하고 유효한 SSL/TLS 인증서를 제시하도록 구성해야 합니다. Application Load Balancer(ALB)나 커스텀 오리진의 경우, ACM 또는 신뢰할 수 있는 서드파티의 인증서를 설치해야 합니다.
- **인증서 일치:**
    CloudFront 오리진 구성에 지정된 호스트명이 오리진에 설치된 인증서의 CN(Common Name) 또는 SAN(Subject Alternative Name)과 일치해야 합니다.
- **자체 서명 인증서 처리:**
    EC2 인스턴스에서 자체 서명 인증서를 사용할 수는 있지만, 프로덕션 환경에는 권장되지 않습니다. 신뢰할 수 있는 인증 기관(CA)이 발급한 인증서를 사용하세요.

#### 4.2.3 어려움과 고려사항

종단 간 암호화를 구현할 때는 다음과 같은 어려움이 있을 수 있습니다.

- **인증서 관리:**
    인증서는 만료되기 전에 갱신하고 교체해야 합니다. AWS Certificate Manager(ACM)는 지원되는 도메인에 대해 이 과정을 자동화할 수 있습니다.
- **레거시 시스템:**
    일부 오래된 시스템은 최신 TLS 버전을 지원하지 않을 수 있어, 보안을 희생하지 않으면서 호환성을 유지하기 위한 신중한 계획이 필요합니다.
- **성능 영향:**
    암호화는 약간의 오버헤드를 발생시키지만, 보안 측면의 이점에 비하면 대개 무시할 만한 수준입니다. CloudFront의 최적화된 네트워크가 성능 저하를 완화하는 데 도움을 줍니다.

#### 4.2.4 암호화 모범 사례 요약

견고하고 안전한 CloudFront 배포를 위해 다음을 권장합니다.

- 뷰어와 CloudFront 사이에 HTTPS를 강제합니다.
- CloudFront와 오리진 사이의 연결에 HTTPS를 사용합니다.
- 최신 TLS 버전과 안전한 암호 스위트를 사용합니다.
- ACM이나 다른 인증서 관리 도구로 인증서를 선제적으로 관리합니다.

이런 실무를 적용하면 오리진과 뷰어 사이에서 교환되는 모든 데이터가 가로채기나 변조로부터 안전하게 유지되도록 보장할 수 있습니다.

## 5. 콘텐츠 커스터마이징과 접근 제어

Amazon CloudFront는 지리적 위치를 기준으로 콘텐츠 전달을 커스터마이징하고 접근을 제어하거나, 엣지 컴퓨팅을 통해 이를 수행할 수 있는 고급 기능을 제공합니다. 이 절에서는 지리적 제한과, CloudFront Functions 및 Lambda@Edge가 제공하는 엣지 컴퓨팅 기능을 살펴봅니다.

### 5.1 지리적 제한: 위치에 따른 트래픽 차단 또는 허용

지리적 제한은 뷰어의 위치를 기준으로 콘텐츠 접근을 제어할 수 있는 강력한 기능입니다. 법적 규제 준수, 콘텐츠 라이선싱 관리, 지역 비즈니스 정책 적용에 유용합니다.

#### 5.1.1 지리적 제한의 동작 방식

CloudFront는 뷰어의 IP 주소를 IP 범위와 국가를 매핑한 데이터베이스와 비교해 접근을 제한할 수 있습니다. 두 가지 주요 모드가 있습니다.

- **허용 목록(Allow List):**
    지정된 국가의 뷰어만 콘텐츠에 접근할 수 있습니다. 나머지 요청은 모두 차단됩니다.
- **차단 목록(Block List):**
    지정된 국가의 뷰어는 차단되고, 나머지는 모두 콘텐츠에 접근할 수 있습니다.

이 설정은 배포 전체에 적용되므로, CloudFront 배포에 구성된 모든 오리진과 캐시 동작에 영향을 미칩니다.

#### 5.1.2 지리적 제한의 사용 사례

지리적 제한은 다음과 같은 경우에 흔히 사용됩니다.

- **콘텐츠 라이선싱과 저작권 준수:**
    미디어 회사는 지역 라이선스 계약에 따라 콘텐츠 접근을 제한할 수 있습니다.
- **규제 준수:**
    규제 산업에 속한 조직은 현지 법률을 준수하기 위해 지역별 제한을 강제할 수 있습니다.
- **타겟 마케팅:**
    기업은 특정 지역에 맞춰 콘텐츠 전달을 조정해, 사용자가 자신의 지역과 관련된 콘텐츠만 보도록 할 수 있습니다.

#### 5.1.3 지리적 제한 구성과 관리

지리적 제한은 CloudFront 관리 콘솔, AWS CLI, 또는 API를 통해 구성할 수 있습니다. 관리자가 허용 또는 차단할 국가 목록을 지정하면, 이 설정이 전 세계 엣지 위치 네트워크에 자동으로 전파됩니다.

정리하면, 지리적 제한은 콘텐츠 접근을 통제하고 법적·비즈니스 요구사항을 준수하기 위한 간단하지만 효과적인 방법을 제공합니다.

### 5.2 엣지 컴퓨팅

엣지 컴퓨팅은 단순한 캐싱을 넘어 CloudFront의 기능을 확장합니다. 엣지에서 코드를 실행함으로써 HTTP 요청과 응답을 조작하고, 인증·인가를 수행하며, 실시간 콘텐츠 변환까지 수행할 수 있습니다. CloudFront는 엣지 컴퓨팅을 위한 두 가지 주요 모델, 즉 CloudFront Functions와 Lambda@Edge를 지원합니다.

![cloudfront-Edge Computing](@site/docs/Networking%20and%20Content%20Delivery/_assets/cloudfront-edge_computing.png)

#### 5.2.1 CloudFront Functions(엣지에서의 경량 JavaScript)

CloudFront Functions는 뷰어에게 가능한 가장 가까운 곳에서 실행되어야 하는, 고성능·지연 시간 민감 작업을 위해 설계되었습니다. 헤더 조작, URL 재작성, 캐시 키 정규화 같은 단순 작업을 위한 경량 실행 환경을 제공합니다.

##### 5.2.1.1 CloudFront Functions의 특징

- **초저지연:**
    CloudFront Functions는 밀리초 미만의 시작 시간을 가져, 처리 지연을 최소로 유지해야 하는 작업에 이상적입니다.
- **프로세스 기반 격리:**
    이 함수들은 엣지 위치 내에서 고도로 최적화된 격리 환경에서 실행됩니다.
- **제한된 실행 시간과 메모리:**
    최대 실행 시간 1밀리초, 메모리 제한 2MB라는 조건에서 경량 작업에 가장 적합합니다.
- **외부 네트워크 접근 불가:**
    CloudFront Functions는 자체 완결적으로 설계되어 있어 외부로 나가는 네트워크 호출을 할 수 없으며, 이를 통해 처리 속도와 예측 가능성이 보장됩니다.

##### 5.2.1.2 CloudFront Functions의 사용 사례

- **캐시 키 정규화:**
    요청 파라미터(헤더, 쿠키, 쿼리 문자열)를 조정해 최적의 캐시 키를 만듭니다.
- **요청 재작성과 리디렉션:**
    특정 조건에 따라 들어오는 URL을 수정하거나 요청을 리디렉션합니다.
- **토큰 검증:**
    요청 헤더에 담긴 인증 토큰(예: JWT)을 빠르게 검사해 엣지에서 인가를 강제합니다.

이 함수들은 일반적으로 뷰어 요청 또는 뷰어 응답 단계에서 배포되어, 요청이 오리진에 도달하기 전이나 응답이 클라이언트로 반환되기 전에 수정이 이루어지도록 합니다.

#### 5.2.2 Lambda@Edge(고급 워크플로를 위한 커스텀 코드 실행)

Lambda@Edge는 CloudFront 이벤트에 대응해 커스텀 코드를 실행하기 위한 더 강력한 솔루션입니다. CloudFront Functions와 달리, Lambda@Edge는 더 넓은 범위의 사용 사례를 지원하며 프로그래밍 언어, 실행 시간, 네트워크 접근 측면에서 더 큰 유연성을 제공합니다.

##### 5.2.2.1 Lambda@Edge의 특징

- **언어 지원:**
    함수는 Node.js나 Python으로 작성할 수 있어, 복잡한 로직과 서드파티 라이브러리를 활용할 수 있습니다.
- **확장된 실행 시간:**
    Lambda@Edge 함수는 뷰어 트리거 이벤트에서 최대 5초, 오리진 트리거 이벤트에서 최대 30초의 실행 시간을 허용합니다.
- **VM 기반 격리:**
    함수는 가상 머신 환경에서 실행되어 추가적인 보안성과 유연성을 제공합니다.
- **네트워크와 파일 시스템 접근:**
    Lambda@Edge 함수는 외부로 나가는 네트워크 호출을 수행하고 로컬 임시 저장소와 상호작용할 수 있어, 다른 AWS 서비스나 외부 API와의 통합이 가능합니다.
- **요청 본문 접근:**
    이 함수들은 전체 요청 페이로드를 검사하고 수정할 수 있어, 콘텐츠 변환이나 정교한 인증 워크플로 같은 작업에 이상적입니다.

##### 5.2.2.2 Lambda@Edge의 사용 사례

- **고급 인증과 인가:**
    복잡한 토큰을 검증하거나 외부 인증 서비스에 질의해 요청을 허용할지 결정합니다.
- **User-Agent 기반 콘텐츠 전달:**
    클라이언트의 디바이스 유형에 따라 응답을 커스터마이징합니다. 예를 들어 모바일 사용자를 저해상도 이미지로 리디렉션해 대역폭 사용을 최적화합니다.
- **동적 콘텐츠 개인화:**
    사용자 프로필이나 지리적 데이터를 기반으로 웹 페이지나 API 응답을 서버 측에서 개인화합니다.
- **백엔드 서비스와 통합:**
    DynamoDB나 API Gateway 같은 추가 AWS 서비스를 호출해 사용자에게 제공되는 콘텐츠를 풍부하게 만듭니다.

## 6. 성능과 고급 통합

콘텐츠 전송 네트워크의 성능을 최적화하는 것은 응답성 있고 효율적인 사용자 경험을 유지하는 데 매우 중요합니다. 이 절에서는 CloudFront의 성능을 한층 더 강화하는 AWS Global Accelerator와 캐시 최적화 전략을 살펴봅니다.

### 6.1 AWS Global Accelerator: 가용성과 지연 시간 개선

AWS Global Accelerator는 사용자 트래픽을 최적의 AWS 엣지 위치로 보내 애플리케이션의 가용성과 성능을 개선하도록 설계된 네트워킹 서비스입니다. AWS 글로벌 네트워크를 활용해 CloudFront와 함께 동작합니다.

#### 6.1.1 Global Accelerator의 동작 방식

Global Accelerator는 애니캐스트(Anycast) IP 주소를 사용해 사용자 요청이 가장 가까운 AWS 엣지 위치로 자동 라우팅되도록 보장합니다.

- **애니캐스트 IP:**
    여러 엣지 위치가 동일한 IP 주소를 공유합니다. 사용자가 요청을 보내면 글로벌 라우팅 시스템이 네트워크 성능 지표를 기준으로 가장 가까운 엣지 위치로 트래픽을 보냅니다.
- **최적화된 라우팅:**
    요청이 엣지 위치에 도달하면, 공용 인터넷을 거치지 않고 AWS 프라이빗 네트워크를 통해 애플리케이션 엔드포인트(예: ALB나 EC2 인스턴스)로 전달되어 지연 시간이 줄어듭니다.

#### 6.1.2 Global Accelerator의 이점

- **일관된 성능:**
    AWS 내부 네트워크를 통해 트래픽을 라우팅함으로써 Global Accelerator는 지연 시간과 패킷 손실을 최소화해, 사용자 위치와 무관하게 일관된 경험을 보장합니다.
- **고정 IP 주소:**
    Global Accelerator는 시간이 지나도 변하지 않는 두 개의 고정 애니캐스트 IP 주소를 제공합니다. 이는 특히 고정 IP 주소가 필요한 애플리케이션의 네트워크 구성과 DNS 관리를 단순화합니다.
- **빠른 페일오버:**
    애플리케이션 엔드포인트에 대한 지속적인 상태 확인을 통해, 장애가 발생하면 Global Accelerator가 자동으로 정상 상태인 엔드포인트로 트래픽을 재라우팅해 빠르고 투명한 페일오버를 제공합니다.
- **HTTP 이외 프로토콜 지원:**
    HTTP와 HTTPS에 최적화된 CloudFront와 달리, Global Accelerator는 TCP와 UDP 트래픽을 지원합니다. 이는 HTTP에만 의존하지 않는 게임, VoIP, IoT 등 지연 시간에 민감한 애플리케이션에 이상적인 선택입니다.

#### 6.1.3 Global Accelerator와 CloudFront 통합

Global Accelerator와 CloudFront는 서로 다른 사용 사례를 다루지만 상호 보완적으로 사용할 수 있습니다.

- **사용 사례 구분:**
    CloudFront는 정적·동적 웹 콘텐츠를 캐시하고 가속화하는 데 강점이 있고, Global Accelerator는 모든 TCP/UDP 기반 애플리케이션의 라우팅과 네트워크 성능 개선에 초점을 맞춥니다.
- **결합된 아키텍처:**
    일부 시나리오에서는 CloudFront로 콘텐츠를 캐시하면서 Global Accelerator를 사용해 애플리케이션이 여러 리전에 분산되어 있을 때 요청이 최소한의 지연 시간으로 오리진에 도달하도록 보장할 수 있습니다.

#### 6.1.4 Global Accelerator 사용 모범 사례

- **엔드포인트 상태 모니터링:**
    엔드포인트의 상태를 정기적으로 모니터링하고 페일오버를 위한 적절한 임계값을 구성합니다.
- **고정 IP 화이트리스트 등록:**
    Global Accelerator가 고정 IP 주소를 제공하므로, 방화벽이나 네트워크 구성을 업데이트해 이 주소들의 트래픽을 허용하세요.
- **애플리케이션 계층 중복성:**
    다중 리전 또는 다중 오리진 구성과 Global Accelerator를 결합해 애플리케이션의 가용성과 복원력을 더욱 강화하세요.

#### 6.1.5. Global Accelerator vs. CloudFront

| **기능**        | **AWS CloudFront**                                               | **AWS Global Accelerator**                                                        |
|--------------------|------------------------------------------------------------------|-----------------------------------------------------------------------------------|
| **사용 사례**       | HTTP 프로토콜                                                   | HTTP 및 비HTTP 프로토콜                                                       |
| **성능**    | 정적·동적 HTTP/S 콘텐츠 모두의 성능을 개선 | TCP나 UDP를 사용하는 광범위한 애플리케이션의 성능을 개선             |
| **고정 IP**     | 동적으로 변경되는 여러 IP 주소 집합을 사용         | 고정된 두 개의 정적 IP 주소 집합을 제공                                   |
| **엣지 위치** | 엣지 위치를 콘텐츠 캐싱에 사용                            | 가장 가까운 리저널 엔드포인트로의 최적 경로를 찾는 데 엣지 위치를 사용      |
| **요금**        | 데이터 전송량과 HTTP 요청 수를 기준으로 산정                    | 고정 시간당 요금과 데이터 전송 요금을 부과                                |
| **DDoS 방어**| AWS Shield로 DDoS 방어 제공                        | AWS Shield로 DDoS 방어 제공                                          |

### 6.2 캐시 최적화: TTL, 무효화, 캐시 정책

효율적인 캐싱은 고성능 CDN의 근간입니다. 이 절에서는 TTL(Time-to-Live) 설정, 캐시 무효화 전략, 커스텀 캐시 정책 구성을 포함한 캐시 최적화의 원칙을 다룹니다.

#### 6.2.1 TTL과 캐시 동작 이해하기

- **TTL(Time-to-Live):**
    TTL은 엣지 위치나 리저널 엣지 캐시에서 오브젝트가 캐시되는 기간을 정의합니다. TTL을 잘 구성하면 오리진으로의 요청 수를 줄이고 콘텐츠 전달 속도를 개선할 수 있습니다.
- **캐시 무효화:**
    콘텐츠가 변경되면 오래된 콘텐츠가 제공되지 않도록 캐시를 무효화해야 합니다. CloudFront는 수동 무효화 요청을 지원하지만, 빈번한 무효화가 필요하지 않도록 캐시 동작을 설계하는 것이 모범 사례입니다.
- **커스텀 캐시 정책:**
    CloudFront는 쿼리 문자열, 헤더, 쿠키를 캐시 키 구성에 어떻게 사용할지 지정하는 커스텀 캐시 정책을 정의할 수 있게 합니다. 이런 세밀함은 개인화된 콘텐츠를 필요할 때 제공하면서도 효과적으로 캐시할 수 있도록 보장합니다.

#### 6.2.2 캐시 최적화 전략

- **콘텐츠 세분화:**
    정적 이미지, 동적 API 응답 같은 서로 다른 유형의 콘텐츠는 서로 다른 캐싱 전략이 필요할 수 있습니다. 하나의 배포 안에서 여러 캐시 동작을 구성하면 각 콘텐츠 유형에 최적의 TTL과 캐시 키 정책을 적용할 수 있습니다.
- **캐시 키 정규화:**
    불필요한 쿼리 파라미터나 헤더를 제거해 캐시 키를 정규화하면 캐시 적중률을 최대화하는 데 도움이 됩니다. CloudFront Functions나 Lambda@Edge로 이를 구현할 수 있습니다.
- **자동화된 캐시 무효화:**
    콘텐츠가 자주 갱신되는 시나리오에서는 자동화된 캐시 무효화 전략을 도입해 수동 개입 없이 최종 사용자가 최신 콘텐츠를 받도록 하는 것을 고려하세요.

#### 6.2.3 캐시 성능 모니터링과 튜닝

- **지표와 로깅:**
    AWS CloudWatch 지표와 CloudFront 로그를 사용해 캐시 적중률, 지연 시간, 오리진 요청 빈도를 모니터링하세요. 이런 인사이트는 최적화가 필요한 영역을 파악하는 데 도움이 됩니다.
- **반복적인 튜닝:**
    캐시 최적화는 지속적인 과정입니다. 콘텐츠와 트래픽 패턴이 변화함에 따라 캐싱 계층이 계속 효율적으로 유지되도록, 성능 데이터를 정기적으로 검토하고 TTL, 캐시 정책, 무효화 전략을 조정하세요.

이런 캐시 최적화 전략을 적용하면 지연 시간을 크게 줄이고, 오리진의 부하를 낮추며, 콘텐츠 전송 네트워크의 전반적인 성능을 개선할 수 있습니다.

## 7. 모니터링: 로깅, 지표, 비용 경보

CloudFront 배포가 예상대로 동작하는지 확인하고 이상 징후를 조기에 발견하려면 견고한 모니터링이 필수적입니다. 이 절에서는 로깅과 지표부터 비용 경보 설정까지, CloudFront를 모니터링하기 위한 다양한 도구와 기법을 다룹니다.

### 7.1 CloudFront 접근 로그

- **상세한 요청 로깅:**
    CloudFront는 모든 사용자 요청에 대한 상세한 정보를 기록하는 접근 로그를 생성할 수 있습니다. 이 로그에는 요청자의 IP 주소, 요청 타임스탬프, HTTP 메서드, 응답 상태, 제공된 바이트 수 같은 데이터가 포함됩니다. 이 정보는 문제 해결, 성능 튜닝, 포렌식 분석에 매우 유용합니다.
- **로그 저장과 분석:**
    접근 로그는 Amazon S3 버킷에 저장할 수 있으며, Amazon Athena 같은 도구나 서드파티 로그 분석 솔루션으로 추가 분석할 수 있습니다. 이런 로그를 정기적으로 분석하면 트렌드를 파악하고, 비정상적인 트래픽 패턴을 감지하고, 사용자 행동을 이해하는 데 도움이 됩니다.

다음 다이어그램은 CloudFront가 오브젝트에 대한 요청 정보를 어떻게 로깅하는지 보여 줍니다. 이 예에서는 배포가 접근 로그를 Amazon S3 버킷으로 전송하도록 구성되어 있습니다.

![CloudFront Access Logs](@site/docs/Networking%20and%20Content%20Delivery/_assets/cloudfront_access_logs.png)

1. 이 예에서는 웹사이트 A와 B, 그리고 이에 대응하는 두 개의 CloudFront 배포가 있습니다. 사용자는 배포와 연결된 URL로 오브젝트를 요청합니다.

2. CloudFront는 각 요청을 적절한 엣지 위치로 라우팅합니다.

3. CloudFront는 각 요청에 대한 데이터를 해당 배포 전용 로그 파일에 기록합니다. 이 예에서 배포 A와 관련된 요청 정보는 배포 A의 로그 파일에, 배포 B와 관련된 요청 정보는 배포 B의 로그 파일에 기록됩니다.

4. CloudFront는 로깅을 활성화할 때 지정한 Amazon S3 버킷에 배포의 로그 파일을 주기적으로 저장합니다. 이후 CloudFront는 해당 배포의 이후 요청 정보를 새 로그 파일에 기록하기 시작합니다.

### 7.2 지표와 대시보드

- **AWS CloudWatch 통합:**
    CloudFront는 지표를 Amazon CloudWatch로 자동 게시하여, 캐시 적중률, 지연 시간, 오류율 같은 주요 성능 지표(KPI)를 모니터링할 수 있게 합니다. CloudWatch 대시보드를 커스터마이징해 배포 성능에 대한 실시간 인사이트를 얻을 수 있습니다.
- **커스텀 경보:**
    지표가 미리 정의한 임계값을 초과할 때 알림을 받도록 CloudWatch 경보를 설정하세요. 예를 들어 비정상적으로 높은 오류율이나 캐시 적중률의 급격한 하락에 대한 경보를 만들어 두면 잠재적인 문제에 빠르게 대응할 수 있습니다.

### 7.3 비용 모니터링과 경보

- **데이터 전송 비용 추적:**
    CloudFront의 글로벌 배포 특성상 데이터 전송 비용을 모니터링하는 것이 중요합니다. AWS Cost Explorer와 CloudWatch 지표를 활용하면 이 비용을 시간에 따라 추적해 예산 내에서 관리할 수 있습니다.
- **예산 경보:**
    지출이 특정 한도에 근접하거나 초과할 때 알림을 받도록 AWS Budgets를 구성하세요. 이런 선제적인 접근은 예상치 못한 요금을 방지하고, 비용을 통제하기 위해 배포 구성을 최적화할 수 있게 합니다.

### 7.4 모니터링 모범 사례

- **정기적인 감사:**
    성능 저하나 이상 징후를 파악하기 위해 CloudFront 로그, 지표, 비용 보고서를 주기적으로 검토하세요.
- **자동화된 보고:**
    성능과 비용 보고서 생성을 자동화해 관계자들에게 정보를 전달하고 콘텐츠 전송 네트워크의 선제적인 관리를 지원하세요.
- **인시던트 관리와의 통합:**
    CloudWatch 경보와 로그를 인시던트 관리 시스템이나 온콜 시스템과 통합해, 문제가 발생하면 신속하게 에스컬레이션되고 해결되도록 하세요.

포괄적인 모니터링·경보 체계를 구축하면 CloudFront 배포가 안정적이고 성능이 좋으며 비용 효율적으로 유지되도록 보장할 수 있습니다.

## 8. 결론

Amazon CloudFront는 대규모로 콘텐츠를 전달하기 위한 다재다능하고 견고한 솔루션입니다. 정적 웹사이트를 호스팅하든, 미디어를 스트리밍하든, 전 세계에 분산된 복잡한 애플리케이션을 배포하든, CloudFront는 콘텐츠를 빠르고 안전하며 안정적으로 전달하는 데 필요한 도구와 통합을 제공합니다.
