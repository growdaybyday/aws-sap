# AWS PrivateLink

## 1. 소개

AWS PrivateLink는 한 VPC에서 수천 개의 다른 VPC로 서비스를 비공개로 노출하기 위한, 매우 안전하고 확장성 있는 해법입니다. VPC 전체를 연결하고 라우팅 테이블 등 네트워크 설정 변경을 요구하는 기존 VPC 피어링과 달리, PrivateLink는 특정 서비스로만 접근을 격리합니다. 이 격리 덕분에 소비자(consumer)가 노출된 서비스 외의 리소스에 접근하지 못하게 되어 공격 표면이 최소화됩니다. 또한 PrivateLink는 인터넷 게이트웨이, NAT 디바이스, VPN 연결을 필요로 하지 않으므로 모든 데이터 트래픽이 Amazon 네트워크 내부에 머무릅니다. 이 장에서는 PrivateLink의 동작 메커니즘과, 이를 현대적인 분산·SaaS 기반 애플리케이션에 적합한 해법으로 만드는 아키텍처 상의 선택을 살펴봅니다.

## 2. AWS PrivateLink의 동작 방식

AWS PrivateLink는 몇 가지 핵심 AWS 네트워킹 구성 요소를 활용해 서비스 공급자(provider) VPC와 하나 이상의 소비자 VPC 사이의 보안 연결을 단순화합니다. 이 절에서는 기반 아키텍처, Network Load Balancer(NLB)의 역할, 그리고 고가용성과 내결함성을 달성하는 전략을 다룹니다.

### 2.1. 아키텍처 개요

AWS PrivateLink의 핵심에는 서비스 노출을 VPC 전체 연결과 분리한다는 개념이 있습니다. 일반적인 PrivateLink 아키텍처에서 서비스 공급자는 자체 VPC 안에서 애플리케이션 서비스를 호스팅합니다. 이 서비스는 직접 노출되지 않고, 전용 엔드포인트 서비스를 통해서만 접근할 수 있게 됩니다. 공급자는 애플리케이션 엔드포인트를 Network Load Balancer(NLB)에 등록합니다.

![AWS PrivateLink](@site/docs/Networking%20and%20Content%20Delivery/_assets/aws_privatelink.png)

소비자 측에서는 인터페이스 VPC 엔드포인트를 생성합니다. 이 엔드포인트는 소비자 VPC의 서브넷에 Elastic Network Interface(ENI)를 프로비저닝하고, 서비스 공급자의 애플리케이션으로 들어가는 진입점 역할을 하는 프라이빗 IP 주소를 제공합니다. 소비자와 공급자 사이의 모든 통신은 AWS 프라이빗 네트워크를 통해 이루어지므로 트래픽이 공용 인터넷과 격리됩니다. 이 아키텍처는 단일 AWS 환경은 물론, 온프레미스에 호스팅된 서비스를 Direct Connect로 엣지 VPC에 연결하고 그 앞에 PrivateLink용 NLB를 두는 하이브리드 시나리오도 지원합니다.

### 2.2. Network Load Balancer(NLB)의 역할

Network Load Balancer는 PrivateLink 아키텍처에서 매우 중요한 구성 요소로, 서비스 공급자의 애플리케이션 엔드포인트에 대한 관문 역할을 합니다. PrivateLink 배포에서 NLB의 핵심 기술적 측면은 다음과 같습니다.

- **서비스 엔드포인트 등록:** 공급자는 애플리케이션 인스턴스(또는 기타 컴퓨팅 리소스)의 IP 주소를 NLB 뒤에 등록합니다. 이 등록을 통해 실제 서비스 엔드포인트가 추상화되고, NLB가 트래픽을 효율적으로 라우팅할 수 있습니다.
- **프라이빗 연결:** NLB는 프라이빗 서브넷에 배치되며 인터넷에 노출되지 않습니다. 따라서 들어오는 모든 트래픽이 AWS 내부 네트워크를 통해 안전하게 라우팅됩니다.
- **확장성과 성능:** NLB는 대량의 트래픽을 낮은 지연 시간으로 처리하도록 설계되어, 수천 개의 소비자 VPC에 서비스를 노출하는 데 적합합니다.
- **보안 격리:** 트래픽을 NLB로 집중시킴으로써 공급자는 내부 네트워크 세부 정보의 노출을 제한합니다. PrivateLink를 통해서는 NLB에 등록된 특정 서비스 엔드포인트만 접근할 수 있습니다.

### 2.3. 고가용성과 내결함성

엔터프라이즈급 애플리케이션의 요구를 충족하기 위해 AWS PrivateLink는 고가용성과 내결함성을 갖추도록 설계되었습니다. 구성 요소나 가용 영역(AZ)에 장애가 발생해도 서비스가 계속 동작하도록 다음과 같은 설계 전략이 사용됩니다.

- **다중 AZ 배포:** 서비스 공급자는 애플리케이션 인스턴스와 Network Load Balancer를 여러 가용 영역에 걸쳐 배포할 수 있습니다. 이렇게 분산해 두면 한 AZ에 장애가 발생해도 나머지 AZ가 트래픽을 계속 처리합니다.
- **소비자 VPC의 다중 ENI:** 소비자 측에서 서로 다른 AZ의 서브넷에 인터페이스 엔드포인트를 만들면 중복성이 향상됩니다. 특정 ENI나 AZ를 사용할 수 없게 되어도 대체 ENI가 프라이빗 연결을 유지합니다.
- **내결함성 라우팅:** 기반이 되는 AWS 네트워킹 인프라와 NLB 자체의 복원력이 결합되어, 장애 지점을 우회해 트래픽이 자동으로 재라우팅되므로 서비스 가용성이 끊기지 않습니다.

## 3. PrivateLink로 서비스 노출하기

여러 소비자 VPC에 서비스를 안전하게 노출하려면 서비스 공급자와 소비자 양쪽에서 신중한 구성이 필요합니다. 이 절에서는 AWS PrivateLink를 효과적으로 배포하기 위한 기술적 단계와 설정을 정리합니다.

### 3.1. 서비스 공급자 구성(공급자 VPC)

서비스 공급자 입장에서 AWS PrivateLink는 VPC의 나머지 부분은 격리한 채 특정 애플리케이션 서비스만 노출하는 체계적인 방법을 제공합니다. 공급자 측 구성의 핵심 단계는 다음과 같습니다.

- **애플리케이션 서비스 호스팅:** 공급자는 자체 VPC 내에 애플리케이션을 배포하며, 서비스가 견고하고 확장 가능하도록 구성합니다.
- **Network Load Balancer 배포:** 애플리케이션 서비스의 프런트엔드 역할을 할 프라이빗 NLB를 설정합니다. NLB는 여러 인스턴스 또는 엔드포인트에 트래픽을 로드 밸런싱하는 역할을 맡습니다.
- **서비스 엔드포인트 등록:** 애플리케이션 인스턴스 또는 특정 IP 주소를 NLB에 등록합니다. 다중 AZ 구성에서는 엔드포인트를 서로 다른 서브넷에 분산해 가용성을 높입니다.
- **VPC 엔드포인트 서비스 생성:** 그다음 공급자는 애플리케이션을 PrivateLink를 통해 접근할 수 있게 하는 VPC 엔드포인트 서비스를 구성합니다. 이 엔드포인트 서비스는 소비자 VPC에 알려지며, 소비자는 이를 대상으로 인터페이스 엔드포인트를 만들어 서비스에 접근합니다.
- **하이브리드 연결 고려사항:** 애플리케이션이 온프레미스에 호스팅된 경우, 공급자는 NLB를 둔 엣지 VPC를 배포하고 AWS Direct Connect로 연결을 구성해 PrivateLink 아키텍처를 확장할 수 있습니다.

### 3.2. 소비자 VPC 설정과 ENI 관리

소비자 측에서 AWS PrivateLink를 통해 서비스에 접근하는 과정은 간결하며, 기존 VPC 구성을 크게 변경할 필요가 없습니다. 핵심 단계는 다음과 같습니다.

- **인터페이스 VPC 엔드포인트 생성:** 소비자는 공급자의 엔드포인트 서비스에 연결되는 VPC 인터페이스 엔드포인트를 만들어 설정을 시작합니다. 이 과정에서 소비자 VPC에 하나 이상의 ENI가 자동으로 프로비저닝됩니다.
- **ENI 프로비저닝:** 생성된 ENI는 소비자 서브넷에서 프라이빗 IP 주소를 받으며, 이로써 소비자와 공급자 간 모든 트래픽이 AWS 네트워크 내부에 유지됩니다.
- **매끄러운 통합:** 연결이 ENI를 통해 이루어지므로 소비자의 라우팅 테이블을 수정할 필요가 없고, 인터넷 게이트웨이나 NAT 디바이스도 필요하지 않습니다. 이는 구성 부담을 최소화하고 설정 오류 가능성을 줄여 줍니다.
- **단방향 연결:** 트래픽은 소비자 VPC에서 공급자 서비스로만 시작됩니다. 이 단방향 연결 모델은 공급자 VPC가 소비자 VPC 내의 다른 리소스에 접근할 수 없도록 보장해 보안을 강화합니다.

## 4. PrivateLink와 VPC 피어링 비교

AWS PrivateLink와 VPC 피어링 중 무엇을 선택할지는 애플리케이션의 구체적인 네트워크 요구사항과 보안 고려사항을 이해해야 결정할 수 있습니다. 주요 차이점과 판단 기준은 다음과 같습니다.

- **연결 범위:**
    - _VPC 피어링:_ 두 VPC 사이에 완전 메시(full-mesh) 네트워크 연결을 구성해 모든 리소스 간 양방향 통신을 허용합니다. 이렇게 열린 연결은 보안 측면에서 영향 범위가 넓어질 수 있습니다.
    - _PrivateLink:_ 연결을 특정 서비스로 제한해, 소비자 VPC에서는 노출된 엔드포인트만 접근할 수 있습니다. 이 격리는 공격 표면을 좁히고 전반적인 보안을 강화합니다.
- **보안 고려사항:**
    - _VPC 피어링:_ 피어링 연결이 수립되면 네트워크 전체에 접근할 수 있게 되므로 라우팅 테이블과 보안 그룹을 광범위하게 관리해야 합니다. 본질적으로 양방향이어서 두 VPC 모두 트래픽을 시작할 수 있습니다.
    - _PrivateLink:_ 소비자만 공급자 서비스로 연결을 시작할 수 있는 단방향 흐름을 강제합니다. 공급자가 소비자 VPC의 리소스에 접근할 필요가 없는 SaaS 애플리케이션에 이상적인 접근 제어 모델입니다.
- **확장성:**
    - _VPC 피어링:_ 피어링 연결 수(VPC당 최대 125개)에 제약이 있어, 수천 개의 VPC에 서비스를 노출해야 하는 상황에는 적합하지 않습니다.
    - _PrivateLink:_ 수천 개의 소비자 VPC를 지원하도록 설계되어, SaaS 공급자에게 상당한 확장성 이점을 제공합니다.
- **네트워크 복잡도:**
    - _VPC 피어링:_ 라우팅 테이블 변경은 물론 인터넷 게이트웨이나 NAT 디바이스 구성이 필요한 경우가 많아 복잡도가 늘어납니다.
    - _PrivateLink:_ 이런 변경 없이 동작하므로 프라이빗 연결을 구성하는 더 단순하고 간결한 방법을 제공합니다.
- **CIDR 중복:**
    - _VPC 피어링:_ CIDR 블록이 겹치는 VPC 사이에는 피어링을 구성할 수 없어, 특정 네트워크 설계에서는 제약이 됩니다.
    - _PrivateLink:_ CIDR 중복에 영향을 받지 않으므로 주소 공간이 충돌하는 상황에서도 유연하게 설계할 수 있습니다.

## 5. 결론

AWS PrivateLink는 클라우드에서 서비스를 안전하게 노출하고 소비하는 방식의 패러다임 전환을 보여 줍니다. 프라이빗 Network Load Balancer와 인터페이스 엔드포인트를 조합함으로써, 기존 VPC 피어링을 대체할 매우 안전하고 확장성 있으며 내결함성을 갖춘 대안을 제공합니다. 이 아키텍처는 노출하려는 특정 엔드포인트로만 서비스 접근을 격리해 보안 위험과 관리 부담을 크게 줄입니다. 또한 다중 AZ 배포와 수천 개의 소비자 연결을 지원하므로, 현대적인 SaaS 애플리케이션과 복잡한 네트워크 환경에 이상적입니다.
