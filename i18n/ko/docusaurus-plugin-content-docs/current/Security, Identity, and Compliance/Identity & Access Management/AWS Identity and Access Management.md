# AWS Identity and Access Management (IAM)

## 1. 소개

오늘날의 클라우드 우선 환경에서 인프라를 보호하는 것은 무엇보다 중요합니다. AWS Identity and Access Management(IAM)는 AWS 리소스에 대한 접근을 제어하기 위한 유연하고 강력한 메커니즘을 제공하는 AWS 보안의 초석입니다. 소규모 프로젝트를 관리하든 대규모 엔터프라이즈 환경을 관리하든, IAM은 누가(또는 무엇이) 리소스에 접근할 수 있는지, 어떻게 접근할 수 있는지, 어떤 조건 하에서 접근할 수 있는지를 정의할 수 있게 합니다.
## 2. IAM 핵심 개념

IAM의 핵심은 어떤 리소스에 대해 누가 무엇을 할 수 있는지 정의하는 능력에 있습니다. 이 절에서는 IAM 정책의 핵심 구성 요소와 AWS에서 사용 가능한 다양한 유형의 정책을 설명합니다. 고급 설계 고려 사항으로 넘어가기 전에 이 기본 사항을 깊이 이해하는 것이 필수적입니다.

### 2.1 IAM 정책: 구조와 문법

IAM 정책은 JSON으로 작성되며 권한을 정의하는 규칙을 나타냅니다. 모든 정책은 하나 이상의 명문으로 구성되며, 각 명문은 명확하게 정의된 요소 집합으로 만들어집니다. IAM 정책의 일반적인 구조는 다음과 같습니다.

1. **Version:**
    모든 정책은 정책 언어의 버전을 나타내는 버전 날짜로 시작합니다. 현재 버전은 `"2012-10-17"`이며, 모든 정책에 포함되어야 합니다.

2. **Id(선택 사항):**
    이 요소는 정책에 대한 고유 식별자나 이름을 제공하는 데 사용됩니다. 선택 사항이지만 문서와 문제 해결에서 정책을 참조하는 데 유용합니다.

3. **Statement:**
    이는 하나 이상의 개별 명문을 포함하는 배열입니다. 각 명문은 다음 요소를 포함할 수 있습니다.

    - **Sid(선택 사항):** 특정 명문을 추적하고 참조하는 데 사용되는 명문 식별자입니다.
    - **Effect:** `"Allow"` 또는 `"Deny"` 중 하나여야 하며, 명문이 접근을 허용하는지 거부하는지 결정합니다.
    - **Principal(해당하는 경우):** 정책이 적용되는 사용자, 계정, 또는 서비스를 지정합니다. 이 요소는 특히 신뢰 정책에서 사용됩니다.
    - **Action(또는 NotAction):** 허용되거나 명시적으로 허용되지 않는 AWS 서비스 작업(API 호출)을 나열합니다. 모든 작업을 나타내기 위해 `*` 같은 와일드카드를 사용하거나 접두사 패턴을 사용해 부분 집합을 나타낼 수 있습니다.
    - **Resource(또는 NotResource):** 작업이 적용되는 리소스를 식별합니다. 작업과 마찬가지로 ARN과 와일드카드를 사용해 제한할 수 있습니다.
    - **Condition(선택 사항):** 명문이 유효한 추가적인 제약 조건을 정의하는 키-값 맵입니다. 조건은 이 장 뒷부분에서 자세히 설명하는 다양한 연산자를 지원합니다.

S3 서비스에 대한 전체 접근을 허용하는 간단한 IAM 정책의 예를 살펴보겠습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowFullS3Access",
      "Effect": "Allow",
      "Action": "s3:*",
      "Resource": "*"
    }
  ]
}
```

위 정책에서는 모든 S3 작업이 모든 리소스에 대해 허용됩니다. 이 직관적인 구조는 조건, `NotAction`과 `NotResource` 같은 표기법 등을 통합하는 더 복잡한 정책의 기초를 형성합니다.

IAM 정책은 `NotAction` 요소도 사용할 수 있습니다. 예를 들어 IAM 서비스에 속하는 작업을 제외한 모든 작업을 허용하는 정책을 살펴보겠습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAllExceptIAM",
      "Effect": "Allow",
      "NotAction": "iam:*",
      "Resource": "*"
    }
  ]
}
```

이 예시에서 정책은 `NotAction`을 사용해(IAM 작업을 제외한 모든 것) 모든 작업을 명시적으로 허용하지만, IAM 작업을 "거부"하는 것은 아닙니다 — 대신 IAM 작업은 단순히 명시적으로 허용되지 않습니다. (나중에 자세히 다룰) IAM의 평가 로직에서, 명시적으로 허용되지 않은 모든 작업은 암묵적으로 거부됩니다.

IAM 정책의 구조와 문법을 이해하는 것은 안전하고 효율적인 정책을 설계하는 데 필수적입니다. 다음 절에서는 다양한 유형의 정책과 세밀한 접근 제어를 달성하기 위해 이 기본 구조를 확장하는 방법을 살펴봅니다.

### 2.2 정책 유형: ID 기반 vs. 리소스 기반 정책

AWS는 두 가지 주요 유형의 IAM 정책을 지원합니다: ID 기반 정책과 리소스 기반 정책입니다. 두 유형 모두 누가 리소스에 접근할 수 있는지 결정하는 데 중요한 역할을 하지만, 연결되고 평가되는 방식이 다릅니다.

#### ID 기반 정책

ID 기반 정책은 IAM 신원(사용자, 그룹, 역할)에 연결되며 이러한 신원이 AWS 리소스에서 수행할 수 있거나 없는 작업을 정의합니다. 사용자나 역할이 요청을 하면 AWS는 해당 신원에 적용되는 모든 ID 기반 정책을 평가합니다. 예를 들어 개발자가 DynamoDB 테이블에 접근할 수 있는 정책을 가지고 있고 그룹에 연결된 다른 정책이 더 넓은 접근을 부여한다면, 개발자가 할 수 있는 작업은 명시적 거부 규칙을 조건으로 그 권한들의 합집합입니다.

개발자를 위한 샘플 ID 기반 정책은 다음과 같을 수 있습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowReadAccessToDynamoDB",
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:Query",
        "dynamodb:Scan"
      ],
      "Resource": "arn:aws:dynamodb:us-east-1:123456789012:table/DevelopersTable"
    }
  ]
}
```

이 경우 개발자는 특정 DynamoDB 테이블에 대한 읽기 작업을 수행할 수 있습니다.

#### 리소스 기반 정책

반면 리소스 기반 정책은 S3 버킷, Lambda 함수, SQS 큐 같은 AWS 리소스에 직접 연결됩니다. 이 정책들은 어떤 주체(사용자, 역할, 계정)가 리소스에 접근할 수 있고 어떤 작업을 수행할 수 있는지 지정합니다. 일반적인 예로 어떤 AWS 계정이나 IAM 사용자가 버킷에 접근할 수 있는지 정의하는 S3 버킷 정책이 있습니다.

예시 S3 버킷 정책은 다음과 같을 수 있습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCrossAccountAccess",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::987654321098:root"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-bucket/*"
    }
  ]
}
```

이 정책은 외부 AWS 계정에 지정된 S3 버킷 내 오브젝트에 대한 읽기 접근을 부여합니다.

ID 기반 정책과 리소스 기반 정책은 접근 확인 중 함께 평가됩니다. 계정 간 요청이 이루어지면 요청 계정의 ID 기반 정책과 대상 리소스의 리소스 기반 정책이 모두 해당 작업을 허용해야 합니다. 그렇지 않으면 요청이 거부됩니다.

이 이중 모델은 유연한 제어를 가능하게 하여, 리소스 소유자가 자체 정책을 강제할 수 있으면서도 신원은 중앙에서 관리될 수 있도록 보장합니다. 많은 실제 시나리오에서 원하는 수준의 보안을 달성하기 위해 두 유형의 정책을 조합해 사용하게 됩니다.

## 3. 고급 정책 설계

정책 구조의 기본을 넘어 AWS는 접근 제어 정책을 세밀하게 조정할 수 있는 광범위한 기능 집합을 제공합니다. IAM에서의 고급 정책 설계는 조건 연산자, 전역 컨텍스트 키, 속성 기반 접근 제어(ABAC)를 사용해 매우 세밀한 보안을 제공하는 것을 중심으로 돌아갑니다.

### 3.1 IAM 조건 연산자: 세밀한 접근 제어

IAM 정책의 조건은 시간, IP 주소, 리소스 태그 같은 특정 속성을 기반으로 접근을 제한할 수 있게 합니다. 조건은 값이 비교되는 방식을 정의하는 연산자와 결합된 키-값 쌍으로 표현됩니다. 다음 연산자가 일반적으로 사용됩니다.

- **StringEquals / StringNotEquals:**
    이 연산자들은 대소문자를 구분하는 정확한 일치에 사용됩니다. 예를 들어 리소스의 태그 값이 지정된 문자열과 정확히 일치하는지 확인하기 위해 `StringEquals`를 사용할 수 있습니다.

- **StringLike / StringNotLike:**
    이 연산자들은 (`*`와 `?` 같은) 와일드카드 사용을 허용함으로써 정확한 일치를 확장합니다. 이 연산자는 Amazon Resource Name(ARN)을 비교하거나 부분 일치가 허용될 때 특히 유용합니다.

- **DateEquals / DateLessThan / DateGreaterThan:**
    이 연산자들은 날짜와 시간 값을 비교합니다. 특정 시간 창으로 접근을 제한하거나 토큰이 발급된 시간을 비교하는 것 같은 시간 조건을 강제하는 데 유용합니다.

- **ArnLike / ArnNotLike:**
    이 연산자들은 ARN 작업에 특화되어 있으며 부분 일치를 지원합니다. ARN을 비교할 때는 문자열 기반 연산자보다 `ArnLike`를 사용하는 것이 더 직관적인 경우가 많습니다.

- **Bool:**
    이 연산자는 불리언 조건을 테스트하는 데 사용됩니다. 예를 들어 `Bool`을 사용해 `aws:SecureTransport` 조건이 `true`인지 확인함으로써 안전한 전송이 활성화되어 있는지 확인할 수 있습니다.

- **IpAddress / NotIpAddress:**
    이 연산자들은 IP 주소를 기반으로 접근을 제한할 수 있게 합니다. CIDR 표기법을 지원하므로, IP 주소 범위로부터의 접근을 허용하거나 거부할 수 있습니다.


다음은 이 연산자들 중 일부를 사용하는 IAM 정책 명문 예시입니다.

```json
{
  "Sid": "DenyAccessWithoutMFA",
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "Bool": {
      "aws:MultiFactorAuthPresent": "false"
    }
  }
}
```

이 명문은 MFA를 포함하지 않는 모든 요청에 대해 모든 작업을 명시적으로 거부합니다. 모든 것을 MFA 없이 거부하지만, 다른 허용 명문과 결합되어 중요한 작업(또는 MFA로 수행된 작업)만 허용되도록 할 수 있다는 점에 주목하세요.

다른 예시는 IP 주소를 기반으로 접근을 제한하는 방법을 보여줍니다.

```json
{
  "Sid": "DenyAccessOutsideCorporateIP",
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "NotIpAddress": {
      "aws:SourceIp": "203.0.113.0/24"
    }
  }
}
```

이 정책에서는 지정된 회사 IP 범위 외부에서 발생하는 모든 요청이 거부됩니다.

서로 다른 연산자와 조건을 결합함으로써 높은 정밀도로 최소 권한 원칙을 강제하는 정책을 만들 수 있습니다.

### 3.2 전역 조건 컨텍스트 키: 환경별 규칙

전역 조건 컨텍스트 키는 모든 AWS 서비스에서 사용할 수 있으며 요청의 컨텍스트를 기반으로 조건을 만들 수 있게 합니다. 주요 컨텍스트 키는 다음을 포함합니다.

- **aws:RequestedRegion:**
    이 키는 API 호출이 이루어지는 리전을 나타냅니다. 특정 리전으로 접근을 제한하는 데 사용할 수 있습니다. 예를 들어 EU 리전에서만 작업을 허용하고 싶다면, `aws:RequestedRegion`이 `eu-west-1`, `eu-west-2`, 또는 `eu-west-3`과 같은지 확인하는 조건을 작성할 수 있습니다. 다만 항상 `us-east-1` 리전을 경유할 수 있는 전역 서비스(IAM이나 CloudFront 등)에는 주의하세요.

- **aws:PrincipalArn:**
    이 키는 요청을 하는 주체(사용자, 역할, 서비스)의 ARN을 제공합니다. 신원의 ARN에 의존하는 정책을 강제하는 데 유용합니다. 예를 들어 요청이 특정 IAM 역할에서 왔을 때만 작업을 허용할 수 있습니다.

- **aws:SourceArn:**
    이 키는 서비스 간 요청에서 사용됩니다. 예를 들어 S3 버킷이 SNS 알림을 트리거하면 SNS 토픽 정책은 요청의 소스가 S3 버킷의 ARN과 일치하는지 확인하는 조건을 포함할 수 있습니다.

- **aws:CalledVia:**
    이 키는 주체를 대신해 호출을 하는 중간 서비스를 식별합니다. CloudFormation, Athena, DynamoDB, KMS 같은 몇몇 서비스만 지원하며, 요청 체인에 여러 서비스가 포함될 때 특히 유용합니다.

- **aws:SourceVpc, aws:SourceVpce, aws:SourceIp:**
    이 키들은 퍼블릭과 프라이빗 네트워크 요청을 구분합니다. 요청이 퍼블릭 IP 주소에서 올 때는 `aws:SourceIp`가 적용됩니다. VPC 엔드포인트를 통한 프라이빗 요청의 경우 `aws:SourceVpc`와 `aws:SourceVpce`가 관련됩니다.


`aws:RequestedRegion` 키를 사용하는 샘플 정책은 다음과 같을 수 있습니다.

```json
{
  "Sid": "RestrictAccessToSpecificRegions",
  "Effect": "Deny",
  "NotAction": "iam:*",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:RequestedRegion": [
        "eu-west-1",
        "eu-west-2",
        "eu-west-3",
        "eu-central-1"
      ]
    }
  }
}
```

이 예시에서는 (전역인) IAM을 제외한 모든 작업이 지정된 유럽 리전 외부에서 요청되면 거부됩니다. 전역 서비스는 IAM과 함께 `NotAction`을 사용해 면제됩니다.

전역 컨텍스트 키는 운영 환경, 지리적 위치, 또는 기타 요청별 속성을 기반으로 접근 제어가 적용되도록 보장하는 환경별 규칙을 설계하는 데 도움을 줍니다.

### 3.3 속성 기반 접근 제어(ABAC): 태그 기반 정책

속성 기반 접근 제어(ABAC)는 IAM 주체와 AWS 리소스 모두와 연관된 태그와 속성을 사용해 권한을 관리하는 동적인 접근 방식입니다. 수많은 특정 정책을 만드는 대신 ABAC는 리소스나 신원을 설명하는 속성(또는 태그)을 기반으로 권한을 정의할 수 있게 합니다.

ABAC는 두 가지 유형의 태그를 활용합니다.

- **리소스 태그:**
    AWS 리소스(예: EC2 인스턴스, S3 버킷, RDS 인스턴스)에 적용되는 태그입니다. 이 태그들은 리소스를 설명합니다(예: `Project: DataAnalytics`).

- **주체 태그:**
    IAM 사용자나 역할과 연관된 태그입니다. 부서, 직무, 리전 같은 속성을 포함할 수 있습니다.


ABAC를 사용할 때 정책은 일반적으로 리소스 태그를 주체 태그와 비교하는 조건을 포함합니다. 예를 들어 다음 정책 명문은 리소스 태그 `Project`가 `DataAnalytics` 값을 가지고 주체 태그 `Department`가 `Data`와 같을 때만 EC2 인스턴스가 리소스에 작업을 수행할 수 있도록 허용합니다.

```json
{
  "Sid": "ABACExample",
  "Effect": "Allow",
  "Action": "ec2:*",
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "ec2:ResourceTag/Project": "DataAnalytics",
      "aws:PrincipalTag/Department": "Data"
    }
  }
}
```

이 경우 정책은 허용되는 모든 리소스를 명시적으로 나열하지 않습니다. 대신 리소스와 사용자 신원 모두에 연결된 태그를 기반으로 권한을 동적으로 평가합니다. 이 접근 방식은 대량의 리소스와 사용자가 있을 때 권한 관리를 단순화합니다.

ABAC는 리소스 구성과 팀 구조가 자주 변경되는 동적 환경을 가진 조직에서 특히 유용합니다. 수많은 정적 정책을 유지하는 관리 부담을 줄이고 태그가 변경될 때 권한이 자동으로 조정될 수 있게 합니다.

## 4. IAM 보안 경계

IAM 보안 경계는 사용자나 역할에 권한이 부여되었더라도 그 권한이 특정 한도를 초과하지 않도록 보장하는 데 도움을 줍니다. 이 절에서는 IAM 권한 경계와 AWS가 접근을 허용할지 거부할지 결정하는 뒤에 있는 평가 로직을 다룹니다.

### 4.1 IAM 권한 경계

IAM 권한 경계는 IAM 신원(사용자나 역할)이 가질 수 있는 최대 권한을 정의할 수 있게 하는 강력한 메커니즘입니다. 권한을 직접 부여하는 대신, 신원의 유효 권한은 ID 기반 정책과 권한 경계의 교집합으로 결정됩니다. 즉, ID 기반 정책이 광범위한 권한을 부여하더라도 경계는 이를 사전에 정의된 한도로 제한합니다.

권한 경계가 S3, CloudWatch, EC2에 대한 작업만 허용하도록 설정된 예를 살펴보겠습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PermissionBoundary",
      "Effect": "Allow",
      "Action": [
        "s3:*",
        "cloudwatch:*",
        "ec2:*"
      ],
      "Resource": "*"
    }
  ]
}
```

신원의 연결된 정책이 IAM 작업(예: `iam:CreateUser`)에 대한 권한도 포함한다면, 유효 권한은 두 정책의 교집합이 됩니다. 이 경우 ID 기반 정책이 `iam:CreateUser`를 명시적으로 허용하더라도, 권한 경계는 신원이 S3, CloudWatch, EC2에서만 작업하도록 제한합니다. 결과적으로 신원은 사용자를 만들 수 있는 권한을 갖지 못합니다.

권한 경계는 정책 관리를 관리자가 아닌 사용자에게 위임하는 시나리오에서 특히 유용합니다. 예를 들어 개발자가 자신의 권한을 관리할 수 있게 허용하면서도 조직의 보안 요구 사항에서 정의한 것을 넘어 특권을 상승시킬 수 없도록 보장할 수 있습니다.

권한 경계는 AWS Organizations의 서비스 제어 정책(SCP)과도 잘 작동합니다. SCP가 계정이나 조직 단위 수준에서 수행할 수 있는 작업을 제한하는 반면, 권한 경계는 그 경계 내에서도 신원이 의도하지 않은 특권을 획득할 수 없도록 보장합니다.

### 4.2 IAM 정책 평가 로직: AWS가 접근을 결정하는 방식

AWS는 요청을 허용해야 할지 거부해야 할지 결정하기 위해 정해진 순서로 정책을 평가합니다. 이 평가 로직을 이해하는 것은 접근 문제를 해결하고 조화롭게 함께 작동하는 정책을 설계하는 데 매우 중요합니다.

간소화된 평가 프로세스는 다음과 같습니다.

1. **기본 거부:**
    기본적으로 명시적인 허용이 지정되지 않으면 모든 요청은 암묵적으로 거부됩니다. 루트 사용자는 예외로, 기본적으로 전체 접근을 갖습니다.
2. **명시적 허용:**
    정책이 작업을 명시적으로 허용하면 그 권한이 기본 거부를 무효화합니다.
3. **명시적 거부:**
    어떤 정책이 작업을 명시적으로 거부하면, 다른 허용과 관계없이 요청은 즉시 거부됩니다.
4. **권한 경계, SCP, 세션 정책:**
    권한 경계, 서비스 제어 정책(SCP), 또는 세션 정책을 사용할 때는 ID 기반 정책이나 리소스 기반 정책의 명시적 허용만으로는 충분하지 않습니다 — 작업은 경계나 SCP에서도 허용되어야 합니다.

예를 들어 다음과 같은 정책 명문이 있는 시나리오를 살펴보겠습니다.

- `sqs:DeleteQueue`를 허용하는 ID 기반 정책
- `sqs:*`를 거부하는 리소스 기반 정책

ID 기반 정책이 큐 삭제를 명시적으로 허용하더라도, 리소스 기반 정책의 명시적 거부가 우선합니다. 따라서 `sqs:DeleteQueue`는 효과적으로 거부됩니다.

계정 간 접근이 관련될 때는 (요청자 계정의) ID 기반 정책과 (대상 리소스의) 리소스 기반 정책 모두가 작업을 명시적으로 허용해야 합니다. 둘 중 하나가 거부하거나 요청을 허용하지 못하면 최종 결정은 거부입니다.

## 5. IAM 역할과 자격 증명 관리

IAM 역할과 자격 증명은 AWS 서비스와 사용자에게 안전한 방식으로 권한을 위임할 수 있게 합니다. 이 절에서는 IAM 역할의 생성과 관리, `PassRole` 권한의 중요성, AWS 환경을 보호하는 데 있어 다중 인증(MFA)의 중요성을 다룹니다.

### 5.1 IAM 역할: 서비스에 권한 위임

IAM 역할은 권한 정책이 연결된 AWS 신원이라는 점에서 사용자와 유사합니다. 다만 역할은 AWS 서비스, 애플리케이션, 또는 심지어 다른 계정의 사용자 같은 신뢰할 수 있는 엔티티가 수임하도록 의도됩니다. 일반적인 사용 사례는 EC2 인스턴스에 IAM 역할을 할당해 다른 AWS 서비스와 안전하게 상호작용할 수 있게 하는 것입니다.

EC2 인스턴스가 IAM 역할을 수임하면 임시 보안 자격 증명이 인스턴스에 제공됩니다. 이는 인스턴스에 영구 자격 증명을 저장할 필요를 없애 보안을 강화합니다. 다른 일반적인 역할로는 Lambda 함수 역할, CloudFormation 스택을 위한 역할, 서드파티 애플리케이션을 위한 역할이 있습니다.

예를 들어 EC2 인스턴스를 위한 역할은 S3 버킷에서 읽을 수 있도록 허용하는 정책을 가질 수 있습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EC2S3ReadAccess",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::example-bucket",
        "arn:aws:s3:::example-bucket/*"
      ]
    }
  ]
}
```

이 역할은 그 후 EC2 인스턴스에 연결되어, 명시적인 자격 증명을 요구하지 않고도 S3와 상호작용할 수 있게 합니다.

### 5.2 `PassRole` 권한: 역할 할당 제어

AWS 서비스가 구성의 일부로 역할을 할당해야 할 때(예: EC2 인스턴스에 IAM 역할을 할당) 해당 서비스를 구성하는 사용자는 `iam:PassRole` 권한을 가지고 있어야 합니다. 이 권한은 승인된 사용자만 서비스에 역할을 전달할 수 있도록 보장해, 무단 특권 상승을 방지합니다.

예를 들어 사용자가 특정 역할을 EC2 인스턴스에 전달할 수 있게 허용하는 정책은 다음과 같을 수 있습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowPassSpecificEC2Role",
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::123456789012:role/EC2RoleFor*"
    }
  ]
}
```

이 정책에서 사용자는 `EC2RoleFor`로 시작하는 이름을 가진 역할만 전달할 수 있습니다. 이 제한은 사용자가 허용된 것보다 더 많은 특권을 가진 역할을 임의로 할당할 수 없도록 보장하는 데 매우 중요합니다.

`iam:PassRole` 권한 자체는 역할이 접근을 제공하는 리소스에 대한 어떤 권한도 부여하지 않는다는 점에 주의해야 합니다. 이는 단지 사용자가 역할을 AWS 서비스에 할당할 수 있도록 승인할 뿐입니다. 역할이 부여하는 실제 권한은 역할의 정책에 의해 결정됩니다.

### 5.3 IAM 다중 인증(MFA): 강력한 인증 강제

다중 인증(MFA)은 사용자가 비밀번호 외에 두 번째 형태의 인증을 제공하도록 요구함으로써 계정 보안을 크게 강화합니다. 비밀번호가 침해된 경우에도 MFA는 무단 접근을 방지할 수 있도록 보장합니다. AWS는 가상 MFA(스마트폰 앱 사용), 하드웨어 MFA 장치, 보안 키를 포함한 여러 유형의 MFA 장치를 지원합니다.

MFA는 민감한 작업에 특히 중요합니다. 예를 들어 정책은 특정 작업에 대해 MFA를 요구하는 조건을 포함할 수 있습니다. 일반적인 패턴은 MFA가 없으면 EC2 인스턴스의 종료나 중지를 거부하는 것입니다.

```json
{
  "Sid": "DenyStopTerminateWithoutMFA",
  "Effect": "Deny",
  "Action": [
    "ec2:StopInstances",
    "ec2:TerminateInstances"
  ],
  "Resource": "*",
  "Condition": {
    "Bool": {
      "aws:MultiFactorAuthPresent": "false"
    }
  }
}
```

MFA의 또 다른 고급 사용은 MFA 인증의 나이를 기반으로 작업을 제한하는 `aws:MultiFactorAuthAge` 조건과 함께입니다. 예를 들어 MFA 인증이 300초보다 오래되지 않았을 때만 접근을 허용할 수 있습니다.

```json
{
  "Sid": "AllowShortTermMFAUsage",
  "Effect": "Allow",
  "Action": "ec2:RebootInstances",
  "Resource": "*",
  "Condition": {
    "NumericLessThan": {
      "aws:MultiFactorAuthAge": "300"
    }
  }
}
```

MFA는 민감한 IAM 작업을 보호하는 데도 매우 중요합니다. 가상 MFA 장치를 삭제하는 것과 관련된 알려진 엣지 케이스가 있는데, 권한이 올바른 것처럼 보여도 사용자가 오류를 받을 수 있습니다. 이러한 경우 관리자는 비활성화된 MFA 장치를 제거하기 위해 AWS CLI나 API를 통해 개입해야 할 수 있습니다.

MFA를 강제함으로써 견고한 IAM 전략에 필수적인 추가적인 보안 계층을 더할 수 있습니다.

## 6. AWS Security Token Service (STS)

AWS Security Token Service(STS)는 사용자와 서비스에 임시적이고 제한된 특권 자격 증명을 부여하는 기반입니다. STS는 페더레이션, 계정 간 접근, 임시 자격 증명을 통한 강화된 보안을 가능하게 합니다. 이 절에서는 STS가 어떻게 작동하는지, 그 버전 간의 차이, 외부 ID의 사용, 임시 자격 증명을 취소하는 기법을 살펴봅니다.

### 6.1 STS 개요: 임시 자격 증명과 페더레이션

STS는 제한된 기간 동안 AWS 리소스에 대한 접근을 부여하는 임시 보안 자격 증명을 발급할 수 있게 합니다. 이 자격 증명은 장기 자격 증명이 위험을 초래하는 시나리오에 이상적입니다. STS는 다음 경우에 널리 사용됩니다.

- **AssumeRole:**
    사용자나 서비스가 역할을 수임해야 할 때 `AssumeRole` API가 호출됩니다. 이는 제한된 수명을 가진 임시 자격 증명을 반환해, 자격 증명이 침해되더라도 그 유용성이 제한되도록 보장합니다.

- **AssumeRoleWithSAML:**
    이 작업은 SAML 호환 신원 공급자에 의해 인증된 페더레이션 사용자가 임시 자격 증명을 얻을 수 있게 합니다.

- **AssumeRoleWithWebIdentity:**
    이 방법은 OpenID Connect(OIDC)를 사용하는 서드파티 신원 공급자(예: Google이나 Facebook)를 통한 인증을 지원합니다. AWS는 이제 더 통합된 솔루션으로 Amazon Cognito 사용을 권장한다는 점에 유의하세요.

- **GetSessionToken:**
    이 작업은 이미 MFA를 사용해 인증한 사용자를 위한 임시 자격 증명을 얻는 데 사용됩니다. 고위험 작업의 보안을 강화하는 단기 토큰을 제공합니다.


예를 들어 EC2 인스턴스가 S3에 접근해야 할 때 임시 자격 증명을 얻기 위해 `AssumeRole`을 호출할 수 있습니다. 이 자격 증명은 만료될 때까지 API 호출에 사용되며, 만료되면 새 자격 증명을 생성해야 합니다.

### 6.2 STS 버전: v1과 v2 비교

AWS STS는 두 가지 형식으로 토큰을 발급합니다: 버전 1과 버전 2입니다. 호환성과 성능을 위해 그 차이를 이해하는 것이 중요합니다.

- **STS 버전 1 토큰:**
    이 토큰은 (일반적으로 `us-east-1`에 있는) 전역 STS 엔드포인트가 발급합니다. 오랫동안 사용되어 왔지만, 특히 새로운 AWS 리전에서 일부 제한이 있습니다.

- **STS 버전 2 토큰:**
    버전 2 토큰은 리전별 STS 엔드포인트가 발급합니다. 낮은 지연 시간, 증가된 세션 기간, 새로운 리전(예: `me-south-1`)에 대한 더 나은 지원 같은 이점을 제공합니다. 리전별 엔드포인트에서 얻더라도 버전 2 토큰은 모든 AWS 리전에서 유효합니다.


AWS는 특히 지리적으로 분산된 아키텍처에서 강화된 성능과 신뢰성을 제공하기 때문에 가능한 곳에서는 STS 버전 2 토큰을 사용할 것을 권장합니다.

### 6.3 STS 외부 ID: 계정 간 접근 보호

계정 간 접근을 활성화할 때는 confused deputy 문제의 위험이 발생합니다. 이 시나리오에서는 서드파티("대리인")가 소유자의 의도 없이 계정 내 리소스에 접근하도록 속을 수 있습니다. 이 위험을 완화하기 위해 신뢰 정책에서 외부 ID를 요구할 수 있습니다.

외부 ID는 `AssumeRole` API 호출에서 제공되어야 하는 고유한 값입니다. 요청의 외부 ID가 역할의 신뢰 정책에 정의된 것과 일치할 때만 요청이 수락됩니다. 이 메커니즘은 서드파티 벤더나 서비스 제공업체에 AWS 리소스에 대한 접근을 부여할 때 특히 유용합니다.

외부 ID를 강제하는 신뢰 정책은 다음과 같을 수 있습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "TrustWithExternalID",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::987654321098:root"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "56789"
        }
      }
    }
  ]
}
```

이 예시에서 IAM 역할은 외부 ID `56789`를 포함하는 호출만 신뢰합니다. 이는 무단 당사자가 신뢰 관계를 악용하는 것을 방지합니다.

### 6.4 임시 자격 증명 취소: 긴급 접근 통제

임시 자격 증명은 일시적으로 설계되었습니다. 다만 침해된 경우 즉시 취소할 수 있는 메커니즘이 필수적입니다. AWS는 자격 증명이 지정된 시간 이전에 발급되었다면 모든 작업을 명시적으로 거부하는 인라인 정책을 적용해 임시 자격 증명의 취소를 강제하는 방법을 제공합니다.

예를 들어 보안 침해가 임시 자격 증명을 잠재적으로 노출시켰을 가능성이 있는 시나리오를 살펴보겠습니다. 관리자는 현재 시간 이전에 발급된 토큰을 가진 모든 세션에 대한 접근을 취소하기 위해 IAM 역할에 다음과 유사한 정책을 연결할 수 있습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RevokeOlderSessions",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "DateLessThan": {
          "aws:TokenIssueTime": "2025-03-09T12:00:00Z"
        }
      }
    }
  ]
}
```

이 정책에서 지정된 타임스탬프 이전에 발급된 모든 자격 증명은 명시적으로 접근이 거부됩니다. 이 메커니즘은 새로운 세션이 계속 작동할 수 있도록 허용하면서도 침해된 자격 증명을 즉시 취소할 수 있게 합니다.

임시 자격 증명을 취소하는 능력은 IAM 도구 모음에서 중요한 긴급 대응 도구로, 침해가 발생하더라도 손상을 최소화할 수 있도록 보장합니다.

## 7. IAM 모니터링과 감사

IAM 활동을 모니터링하고 감사하는 것은 안전한 AWS 환경을 유지하는 데 필수적입니다. AWS는 이 목적을 위해 IAM Access Analyzer, IAM Access Advisor, IAM Credentials Report를 포함한 여러 도구를 제공합니다. 각 도구는 잠재적인 보안 격차를 식별하고 권한이 모범 사례와 일치하도록 보장하는 데 고유한 역할을 합니다.

### 7.1 IAM Access Analyzer: 리소스 노출 식별

![IAM Access Analyzer](@site/docs/Security,%20Identity,%20and%20Compliance/_assets/iam_access_analyzer.png)

IAM Access Analyzer는 외부 엔티티와 공유된 리소스를 식별하는 데 도움을 주는 서비스입니다. 이 도구는 (S3 버킷, IAM 역할, KMS 키, Lambda 함수, SQS 큐, Secrets Manager 시크릿에 연결된) 리소스 정책을 검토해 의도하지 않은 접근을 탐지합니다.

예를 들어 외부 계정으로부터의 접근을 허용하는 S3 버킷 정책을 실수로 구성한 경우, IAM Access Analyzer는 이를 잠재적인 보안 위험으로 플래그합니다. 이는 "신뢰 영역"(일반적으로 여러분의 AWS 계정이나 조직)을 수립하며, 그 영역 외부의 모든 접근은 발견 사항으로 보고됩니다.

노출을 식별하는 것 외에도 IAM Access Analyzer는 정책 검증 기능도 제공합니다. 정책을 모범 사례와 AWS 정책 문법에 대해 검사해 경고, 오류, 실행 가능한 권장 사항을 제시합니다. 또한 CloudTrail에 기록된 API 호출 활동을 기반으로 정책을 생성할 수 있어, 생성된 정책이 정당한 접근을 여전히 허용하면서도 가능한 한 제한적이도록 보장합니다.

### 7.2 IAM Access Advisor: 서비스 권한 검토

![IAM Access Advisor](@site/docs/Security,%20Identity,%20and%20Compliance/_assets/iam_access_advisor.png)

IAM Access Advisor는 또 다른 중요한 도구이지만, 개별 사용자 수준에서 작동합니다. 특정 IAM 사용자가 접근한 AWS 서비스와 마지막 접근의 타임스탬프에 대한 상세한 정보를 제공합니다. 이 세밀함은 사용되지 않는 권한을 식별하고 최소 권한 원칙에 따라 사용자의 권한을 줄일 수 있게 합니다.

예를 들어 사용자의 IAM Access Advisor가 40개 서비스에 대한 권한을 가지고 있지만 몇 개만 접근한 것으로 나타난다면, 그 사용자의 권한을 강화하는 것을 선택할 수 있습니다. Advisor의 데이터를 검토함으로써 관리자는 불필요한 접근을 제거하고 잠재적인 공격 표면을 줄일 수 있습니다.

IAM Access Advisor는 IAM 정책이 실제로 어떻게 사용되고 있는지에 대한 실행 가능한 인사이트를 제공하기 때문에 지속적인 운영 보안에 특히 유용합니다. 이는 모든 IAM 사용자가 필요한 권한만 가지도록 보장하는 데 도움을 줍니다.

### 7.3 IAM Credentials Report: 사용자와 역할 키 감사

![IAM Credentials Report](@site/docs/Security,%20Identity,%20and%20Compliance/_assets/iam_credentials_report.png)

IAM Credentials Report는 계정 내 모든 IAM 사용자와 그 자격 증명 상태에 대한 개요를 제공하는 포괄적인 CSV 파일입니다. 이 보고서는 다음과 같은 세부 사항을 포함합니다.

- 사용자의 생성 날짜
- 비밀번호 상태(활성화 또는 비활성화)
- 액세스 키에 대한 정보(생성 날짜, 마지막 사용, 순환 세부 사항)
- 각 사용자의 MFA 상태

관리자는 AWS Management Console, API, 또는 CLI를 통해 이 보고서를 다운로드할 수 있습니다. 이 보고서는 예정된 일정(일반적으로 4시간마다)으로 생성되지만, 휴면 자격 증명을 식별하고, 순환 정책을 강제하고, 모든 사용자가 보안 모범 사례를 준수하도록 보장하는 중요한 감사 도구로 작용합니다.

예를 들어 보고서에 특정 사용자의 액세스 키가 90일 넘게 순환되지 않은 것으로 나타난다면, AWS Config 규칙(예: `access-key-rotated`)을 트리거해 사용자에게 알림을 보내거나 심지어 자동으로 키를 순환함으로써 이를 개선할 수 있습니다.

IAM 자격 증명을 정기적으로 감사하는 것은 무단 접근을 방지하고 보안 정책이 전체 계정에서 강제되도록 보장하는 데 필수적입니다.

## 8. 결론

이 장에서는 IAM 정책의 기본 사항부터 고급 보안 조치와 감사 도구까지 광범위한 주제를 다루며 AWS Identity and Access Management(IAM)에 대한 심층적인 탐구를 제공했습니다.
