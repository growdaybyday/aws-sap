# AWS Certificate Manager
## 1. 소개

AWS Certificate Manager는 클라우드에서 네트워크 통신을 보호하기 위한 SSL/TLS 인증서의 프로비저닝, 관리, 배포를 단순화하는 완전관리형 서비스입니다. ACM의 핵심은 SSL 인증서 관리에서 가장 어려운 측면 중 하나인 수동 인증서 갱신과 설치를 다룹니다. 인증서 발급과 갱신을 자동화함으로써 ACM은 안전한 연결을 유지하는 것과 전통적으로 관련된 운영 부담을 줄여주며, 많은 AWS 서비스와 매끄럽게 통합됩니다.

이 서비스는 브라우저와 외부 클라이언트가 신뢰하는 퍼블릭 인증서와 내부 통신을 위한 프라이빗 인증서를 모두 지원합니다. ACM은 AWS Trust Services CA가 암호적으로 서명하거나 관리하는 프라이빗 CA가 발급한 인증서를 제공함으로써 진위성, 무결성, 개인정보 보호의 원칙을 활용해, 클라이언트가 서버의 신원을 안전하게 검증할 수 있도록 보장합니다.

## 2. 핵심 기능과 통합

ACM의 기능은 핵심 기능과 AWS 관리형 서비스와의 깊은 통합을 중심으로 구축되어 있어, 간소화된 배포와 보안을 보장합니다.

### 2.1. 퍼블릭 vs. 프라이빗 인증서

- **퍼블릭 인증서:**
    ACM은 AWS가 유지하는 신뢰할 수 있는 인증 기관(CA)이 발급한 퍼블릭 SSL/TLS 인증서를 자동으로 프로비저닝할 수 있습니다. 이 인증서들은 대부분의 최신 브라우저와 클라이언트 장치에서 본질적으로 신뢰되므로, 인터넷에 노출된 애플리케이션을 보호하는 데 이상적입니다.

- **프라이빗 인증서:**
    퍼블릭 인증서 외에도 ACM은 내부 애플리케이션을 위한 프라이빗 인증서를 지원합니다. AWS Private CA를 사용하면 조직은 통제된 환경 내에서만 신뢰되는 내부 X.509 인증서를 발급할 수 있습니다. 이 인증서들은 기업이 내부 통신, API 보안, IoT 장치 인증, 클라이언트 VPN 접근을 위한 견고한 공개 키 인프라(PKI)를 구축할 수 있게 합니다.

### 2.2. SSL 종료

SSL 종료는 중간 장치(일반적으로 로드 밸런서)가 암호화되지 않은 요청을 백엔드 서버로 전달하기 전에 수신되는 SSL/TLS 트래픽을 복호화하는 과정을 말합니다. ACM이 프로비저닝한 인증서는 Application Load Balancer(ALB) 같은 서비스에 배포되어 SSL 종료를 촉진합니다. 이는 백엔드 인스턴스로부터 계산 오버헤드를 오프로드하고, CPU 집약적인 암호화와 복호화 프로세스가 네트워크 엣지에서 처리되도록 함으로써 전체 성능을 최적화합니다.

### 2.3. 지원되는 서비스

ACM은 다양한 AWS 서비스와 통합되어 인증서 배포를 단순화합니다. 주요 통합은 다음을 포함합니다.

- **Elastic Load Balancing(ELB):**
    인증서를 로드 밸런서에 직접 연결할 수 있으며, 그러면 로드 밸런서가 SSL 종료를 수행합니다.

- **CloudFront 배포:**
    글로벌 콘텐츠 전송을 위해 CloudFront는 (일반적으로 US East[N. Virginia] 리전에서 프로비저닝된) ACM 인증서를 사용해 HTTPS 트래픽을 보호합니다.

- **API Gateway와 Elastic Beanstalk:**
    이 서비스들은 ACM을 활용해 보안 통신 엔드포인트를 구축할 수 있어, 모든 외부 요청이 암호화되고 신뢰되도록 보장합니다.

ACM이 이 서비스들과 통합되어 있다는 것은, 인증서가 발급되면 대상 AWS 리소스에 자동으로 적용될 수 있어 환경 전반에서 배포와 관리를 단순화한다는 것을 의미합니다.

## 3. 인증서 프로비저닝

ACM은 각각 다른 운영 시나리오에 맞는 여러 인증서 프로비저닝 접근 방식을 지원합니다.

### 3.1. 퍼블릭 인증서

ACM에서 퍼블릭 인증서를 요청하는 것은 자동화된 프로세스를 통해 간소화됩니다. 퍼블릭 인증서를 요청하면 ACM은 DNS나 이메일을 통해 도메인의 소유권이나 통제를 검증합니다. 검증되면 ACM은 인증서를 발급하며, 이 인증서는 (검증 방법에 따라) 자동으로 유지되고 갱신되며 13개월 동안 유효합니다. 이 자동화된 프로세스는 수동 갱신의 필요를 없애고 만료된 인증서로 인한 다운타임 위험을 줄여줍니다.

### 3.2. 프라이빗 인증서

내부용이나 비퍼블릭 사용 사례를 위해 AWS Private CA를 사용해 프라이빗 인증서를 발급할 수 있습니다. 이 기능은 루트와 하위 CA를 포함해 자체 인증 기관 계층 구조를 만들고 관리해 최종 엔티티 X.509 인증서를 생성할 수 있게 합니다. 프라이빗 인증서는 내부 애플리케이션, API, IoT 통신을 보호하기 위해 엔터프라이즈 환경 내에서 사용됩니다. 퍼블릭 인증서와 달리 프라이빗 인증서의 신뢰 체인은 조직 내에서 수립되어야 하며, 모든 내부 시스템이 프라이빗 CA를 명시적으로 신뢰해야 합니다.

### 3.3. 외부 인증서 가져오기

ACM은 외부에서 획득한 인증서를 가져오는 것도 허용합니다. 다른 유명한 CA로부터 인증서를 획득한 경우 관련된 프라이빗 키와 함께 ACM에 업로드할 수 있습니다. 다만 외부에서 가져온 인증서는 자동 갱신의 혜택을 받지 못합니다. 대신 만료가 가까워지면 수동 갱신과 재가져오기가 필요합니다. 이 옵션은 조직이 외부 인증 기관과 기존 관계를 가지고 있거나 ACM의 자동화된 발급 프로세스에서 제공되지 않는 커스텀 인증서 속성이 필요할 때 유용합니다.

## 4. 검증과 갱신

도메인 소유권을 검증하고 인증서를 갱신하는 과정은 안전한 통신을 유지하는 데 매우 중요합니다. ACM은 별도의 갱신 프로세스와 함께 두 가지 주요 검증 방법을 지원합니다.

### 4.1. DNS 검증

DNS 검증은 ACM에서 퍼블릭 인증서에 선호되는 방법입니다. 이 프로세스 중 ACM은 도메인의 DNS 구성에 추가해야 하는 고유한 CNAME 레코드를 제공합니다. DNS 레코드가 감지되면 ACM은 도메인 소유권을 확인하고 인증서 발급을 진행합니다. DNS 검증은 매우 자동화되어 있어 관리 부담을 줄이고 매끄러운 인증서 갱신을 가능하게 합니다.

### 4.2. 이메일 검증

또는 ACM은 (WHOIS 레코드에서 확인된) 도메인의 등록된 연락처 주소로 확인 이메일을 보내 도메인 소유권을 검증할 수 있습니다. 수신자는 소유권을 확인하기 위해 링크를 따라가야 하며, 그 후 ACM이 인증서를 발급합니다. 효과적이지만 이 방법은 초기 발급과 이후 갱신 모두에서 수동 개입이 필요해, 완전한 자동화의 혜택을 받는 환경에는 덜 바람직합니다.

### 4.3. 자동 vs. 수동 갱신

- **자동 갱신:**
    DNS 검증을 사용해 ACM이 직접 프로비저닝한 인증서는 자동으로 갱신됩니다. ACM은 인증서의 유효 기간을 모니터링하고 — 일반적으로 만료 45일 전에 — 갱신 프로세스를 시작해 사람의 개입 없이 지속적인 보안을 보장합니다.

- **수동 갱신:**
    외부 소스에서 가져왔거나 이메일을 통해 검증된 인증서의 경우, 갱신 프로세스는 수동 단계가 필요합니다. 관리자는 갱신 알림에 응답하고 필요한 조치(DNS 레코드 업데이트나 이메일을 통한 확인 등)를 취해 인증서가 재발급되고 유효한 상태를 유지하도록 보장해야 합니다. EventBridge와 AWS Config는 인증서 만료와 갱신 준수 여부를 모니터링하기 위해 알림을 생성하거나 자동화된 워크플로를 트리거하도록 구성할 수 있습니다.

## 5. 리전별 배포

ACM은 본질적으로 리전별 서비스이며, 전역 애플리케이션에는 그 배포 모델을 이해하는 것이 필수적입니다.

### 5.1. 멀티 리전 전략

ACM 인증서는 발급된 AWS 리전에 종속되므로, 여러 리전에 애플리케이션을 배포하는 조직은 각 리전에 인증서를 프로비저닝해야 합니다. 즉, 여러 리전에 걸친 애플리케이션의 경우 각 리전별 엔드포인트(예: 로드 밸런서)에는 자체 ACM 발급 인증서가 필요합니다. 멀티 리전 전략을 채택하면 모든 배포가 리전별 서비스 경계를 준수해 보호되도록 보장합니다.

### 5.2. CloudFront 전역 예외

CloudFront는 ACM이 부과하는 리전 제약의 예외입니다. 전역 콘텐츠 전송 네트워크로서 CloudFront는 배포를 보호하는 데 사용되는 인증서가 US East(N. Virginia) 리전에서 프로비저닝되어야 합니다. 이 예외는 다른 AWS 서비스가 계속 리전 제한을 준수하는 동안에도 CloudFront가 ACM 인증서를 전역적으로 활용할 수 있게 합니다.

## 6. 프라이빗 인증 기관(CA)

퍼블릭 인증서 관리를 넘어 AWS는 프라이빗 PKI가 필요한 조직을 위한 전용 솔루션인 AWS Private CA 서비스를 제공합니다. AWS Private CA를 사용하면 다음을 할 수 있습니다.

- **인증서 계층 구조 수립:**
    자체 루트와 하위 CA를 생성하고 관리해 조직 내에서 인증서를 발급하고 취소할 수 있습니다.

- **최종 엔티티 인증서 발급:**
    내부 사용자, 애플리케이션, API, IoT 장치를 인증하기 위해 인증서를 배포합니다. 이 최종 엔티티 인증서는 통제된 환경 내에서 안전한 TLS 통신을 보장합니다.

- **커스텀 PKI 관리:**
    유효 기간, 취소 목록, 커스텀 확장 같은 인증서 속성에 대한 세밀한 제어를 누릴 수 있으며, 이는 엔터프라이즈 규정 준수와 보안 요구 사항을 충족하는 데 매우 중요합니다.


AWS Private CA 서비스는 퍼블릭 신뢰가 필요하지 않지만 견고한 내부 보안 인프라가 필요한 시나리오에 특히 유익합니다.

## 7. 모니터링과 모범 사례

ACM 배포의 지속적인 보안과 운영 효율성을 보장하려면 적절한 모니터링을 구현하고 모범 사례를 준수하는 것이 필수적입니다.

### 7.1. 만료 알림

ACM은 인증서 만료에 대한 선제적 알림을 제공합니다. ACM이 관리하는 인증서의 경우 갱신 알림은 일반적으로 만료 45일 전에 발급됩니다. 가져온 인증서의 경우 관리자는 EventBridge, Lambda 함수, 또는 SNS 알림을 사용해 모니터링을 설정해 시기적절한 알림을 받고 만료된 인증서로 인한 서비스 중단을 방지해야 합니다.

### 7.2. CNAME/TXT 충돌 방지

DNS 구성은 인증서의 성공적인 발급과 갱신에서 핵심적인 역할을 합니다. DNS 검증을 사용할 때는 제공된 CNAME 레코드가 DNS 제공업체에 의해 수정되지 않고 정확하게 삽입되었는지 확인하세요. 중복 레코드(예: 동일한 이름을 가진 TXT 레코드)가 존재하면 충돌이 발생할 수 있습니다. 적절한 검증과 발급 워크플로를 유지하려면 충돌하는 레코드를 확인하고 필요한 경우 제거하는 것이 중요합니다.

### 7.3. SSL 종료 비용 최적화

로드 밸런서와 다른 AWS 관리형 서비스로 SSL 종료를 오프로드함으로써 백엔드 EC2 인스턴스의 CPU 부담을 줄일 수 있습니다. 이는 성능을 향상시킬 뿐만 아니라 ALB와 CloudFront 같은 서비스와의 ACM 통합을 활용함으로써 운영 비용도 낮춥니다. 네트워크 엣지에서 SSL 종료가 관리되도록 보장하는 것은, 특히 트래픽이 많은 환경에서 효율성과 확장성을 최대화합니다.

## 8. 결론

AWS Certificate Manager는 다양한 AWS 서비스 전반에서 인증서 발급, 갱신, 배포를 자동화함으로써 SSL/TLS 인증서 관리를 크게 단순화합니다. 퍼블릭 애플리케이션이든 내부 통신이든 보호하려는 경우 ACM은 디지털 인증서를 관리하기 위한 견고한 프레임워크를 제공합니다. 로드 밸런서, CloudFront, API Gateway, 그리고 다른 AWS 서비스와의 통합과 퍼블릭 및 프라이빗 인증서 모두에 대한 지원이 결합되어, 안전한 네트워크 통신을 유지하는 데 필수적인 도구가 됩니다.
