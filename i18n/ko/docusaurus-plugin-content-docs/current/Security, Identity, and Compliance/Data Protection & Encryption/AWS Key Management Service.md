# AWS Key Management Service (KMS)

## 1. 소개

AWS에서 암호화를 이야기할 때는 즉시 AWS KMS를 고려해야 합니다. 이 서비스는 암호화 키를 관리하는 데 관련된 많은 복잡성을 추상화하면서 Amazon S3, Amazon EBS, Amazon RDS, Amazon Redshift, AWS Systems Manager 등 다른 AWS 서비스와의 견고한 통합을 제공합니다. AWS Management Console, 명령줄 인터페이스(CLI), 또는 소프트웨어 개발 키트(SDK)를 통해 접근하든, AWS KMS는 암호화 키와 상호작용하기 위한 일관된 인터페이스를 제공합니다.

AWS KMS는 인가를 위해 AWS Identity and Access Management(IAM)와 통합함으로써 암호화 프로세스를 단순화해, 적절한 권한을 가진 사용자나 역할만 암호화 작업을 수행할 수 있도록 보장합니다. 이 서비스는 또한 AWS CloudTrail을 통한 광범위한 감사 기능도 제공해, 조직이 규정 준수와 보안 목적으로 키의 모든 사용을 추적할 수 있게 합니다.

이 장에서는 AWS KMS의 구체적인 사항을 자세히 살펴보며, 다양한 구성 요소를 살펴보고 이들이 어떻게 상호작용해 안전하고 확장 가능한 키 관리 솔루션을 제공하는지 설명합니다. 대칭과 비대칭 키의 기본 개념부터 봉투 암호화와 속성 기반 접근 제어(ABAC) 같은 고급 주제까지 모든 것을 다룹니다.

## 2. 핵심 개념

AWS KMS는 안전한 키 관리의 기반을 형성하는 여러 핵심 개념을 기반으로 구축되어 있습니다. 이 개념들을 이해하는 것은 안전한 시스템을 설계하는 것과 전문 자격증 시험을 준비하는 것 모두에 필수적입니다.

### 2.1. 대칭 vs. 비대칭 키

암호화 시스템의 핵심에는 두 가지 근본적인 암호화 키 유형이 있습니다: 대칭 키와 비대칭 키입니다.

#### 대칭 키

대칭 암호화는 암호화와 복호화 모두에 사용되는 하나의 암호화 키를 포함합니다. 이 접근 방식은 본질적으로 빠르고 효율적이어서, 성능이 주된 관심사인 데이터를 암호화하는 데 이상적입니다. AWS KMS에서 대칭 키는 원래의 제공 형태였으며 많은 통합 서비스에서 여전히 가장 일반적으로 사용되는 키 유형입니다.

AWS KMS의 대칭 키의 주요 특성은 다음과 같습니다.

- **단일 키 사용:** 하나의 키가 데이터를 암호화하고 복호화합니다.
- **봉투 암호화:** 많은 AWS 서비스는 대칭 키를 활용해 봉투 암호화를 구현합니다. 이때 데이터 키가 생성되어 클라이언트 측 암호화에 사용되고, 그 다음 마스터 키로 암호화됩니다.
- **API 전용 접근:** 암호화되지 않은 키 자재는 KMS를 절대 벗어나지 않습니다. 모든 암호화 작업은 API 호출을 통해 수행됩니다. 즉, 사용자나 애플리케이션은 원시 키에 직접 접근하지 않습니다.
- **성능 효율성:** 대칭 키 알고리즘은 일반적으로 더 빠르기 때문에 대량 데이터 암호화를 처리하는 데 적합합니다.

#### 비대칭 키

반면 비대칭 암호화는 퍼블릭 키와 프라이빗 키로 구성된 키 쌍을 사용합니다. 퍼블릭 키는 공개적으로 공유할 수 있지만 프라이빗 키는 비밀로 유지됩니다. 이 키 쌍 메커니즘은 키의 역할이 구별되는 암호화와 복호화를 촉진합니다.

AWS KMS의 비대칭 키의 주요 특성은 다음과 같습니다.

- **키 쌍 구조:** 퍼블릭 키는 데이터를 암호화하거나 서명을 검증하며, 프라이빗 키는 데이터를 복호화하거나 서명을 생성합니다.
- **외부 사용 사례:** 비대칭 키는 데이터가 AWS 외부에서 암호화되어야 하거나 외부 당사자와 안전하게 통신해야 하는 시나리오에서 특히 유용합니다.
- **다운로드 가능한 퍼블릭 키:** AWS KMS는 퍼블릭 키의 다운로드를 허용해, 외부 애플리케이션이 복호화를 위해 KMS로 보내기 전에 데이터를 암호화할 수 있게 합니다.
- **제한된 직접 접근:** 비대칭 키를 사용하더라도 프라이빗 키는 절대 암호화되지 않은 형태로 제공되지 않습니다. 프라이빗 키가 필요한 모든 작업은 KMS API를 통해 수행되어야 합니다.

대칭 키와 비대칭 키 중 선택은 사용 사례에 따라 달라집니다. 대칭 키는 높은 성능과 단순성이 필요할 때 선호되는 반면, 비대칭 키는 안전한 키 교환이나 디지털 서명 작업이 필요할 때 사용됩니다.

### 2.2. 키 관리 유형

AWS KMS는 각각 고유한 관리 특성과 사용 사례를 가진 여러 유형의 키를 지원합니다. 이 키 유형들은 키가 어떻게 생성되고 관리되는지뿐만 아니라 누가 생명주기와 순환을 책임지는지도 결정합니다.

#### 2.2.1. 고객 관리형 키

고객 관리형 키(CMK)는 고객이 생성, 관리, 사용합니다. 이 키들은 높은 수준의 통제와 유연성을 제공합니다.

- **생성과 관리:** 고객은 AWS KMS에서 직접 CMK를 생성하고 그 생명주기 전체에 걸쳐 관리할 수 있습니다.
- **순환 정책:** CMK는 일반적으로 매년 자동 순환하도록 구성하거나 온디맨드로 순환할 수 있습니다. 순환이 활성화되면 이전 키는 복호화에 계속 사용 가능하고, 새로운 백업 키가 이후 작업에 사용됩니다.
- **키 정책과 감사 가능성:** 고객은 어떤 사용자와 역할이 키에 접근할 수 있는지 지정하는 커스텀 키 정책을 정의할 수 있습니다. 이 키를 사용하는 모든 작업은 CloudTrail을 통해 감사할 수 있어, 사용에 대한 완전한 가시성을 제공합니다.
- **봉투 암호화에서의 사용:** CMK는 데이터 암호화 키(DEK)가 생성되고 CMK로 랩핑되는 봉투 암호화에서 마스터 키로 흔히 사용됩니다.

CMK는 완전히 고객의 통제 아래 있기 때문에 엄격한 보안 통제와 키 사용의 완전한 추적성이 필요한 애플리케이션에 이상적입니다.

#### 2.2.2. AWS 관리형 키

AWS 관리형 키는 AWS가 자동으로 생성, 관리, 순환합니다. 이 키들은 AWS 서비스에서만 배타적으로 사용됩니다.

- **서비스별 키:** KMS와 통합되는 AWS 서비스(예: Amazon S3나 Amazon EBS)를 사용할 때 그 서비스는 일반적으로 AWS 관리형 키를 사용합니다.
- **자동 순환:** AWS 관리형 키는 매년 자동으로 순환되어, 고객 개입의 필요를 없애줍니다.
- **제한된 커스터마이징:** 키 메타데이터를 보고 사용을 감사할 수 있지만, 키 정책을 수정하거나 순환 일정을 변경할 수는 없습니다.
- **운영 단순성:** AWS 관리형 키는 심층적인 키 관리 지식 없이도 암호화가 투명하게 처리되도록 보장하는 "설정하고 잊어버리는" 솔루션을 제공합니다.

이 키들은 수동으로 키를 관리하는 오버헤드 없이 견고한 암호화를 원하는 고객에게 가장 적합합니다.

#### 2.2.3. AWS 소유 키

AWS 소유 키는 여러 고객을 대신해 AWS가 배타적으로 생성, 관리, 사용합니다.

- **내부 사용 전용:** 이 키들은 AWS 서비스가 리소스를 보호하는 데 사용하지만 고객의 AWS 계정 내에서는 보이거나 접근할 수 없습니다.
- **직접 통제 없음:** 고객은 AWS 소유 키를 보거나, 관리하거나, 추적하거나, 감사할 수 없습니다. AWS는 그 존재와 보안에 대한 보증을 제공하지만 모든 운영 측면은 AWS의 관할 아래 둡니다.
- **계정 간 유틸리티:** AWS 소유 키는 여러 계정에 걸친 리소스를 보호할 수 있지만, 고객은 이 키들과 직접적인 상호작용이 없습니다.
- **운영 투명성:** 이 키들은 고객의 관리 인터페이스에서 완전히 추상화되어, 개별 키 관리가 필요하지 않은 시나리오의 작업을 단순화합니다.

AWS 소유 키는 일반적으로 AWS가 고객 개입 없이 서비스를 보호하기 위해 키의 전체 생명주기를 관리하는 시나리오에서 사용됩니다.

## 3. 키 생성과 자재 출처

KMS 키를 생성할 때 가장 먼저 결정해야 할 사항 중 하나는 키 자재 — 암호화 키를 구성하는 원시 비트 — 가 어떻게 생성되고 관리되는지입니다. 이 결정은 주어진 키에 대해 영구적이며 보안, 규정 준수, 운영 통제에 영향을 미칩니다.

### 3.1. KMS 생성 키

기본 운영 모드에서 AWS KMS는 키 자재를 내부적으로 생성합니다.

- **자동화된 생성:** AWS는 자동으로 암호화 키 자재를 안전한 키 스토어 내에서 생성, 저장, 관리합니다.
- **높은 보안:** 키 자재가 강화되고 감사된 환경 내에서 생성되기 때문에 고객은 키 자재가 외부에 노출되지 않는다는 것을 보장받을 수 있습니다.
- **단순화된 관리:** KMS 생성 키를 사용하면 고객이 외부 키 자재를 관리할 필요가 없습니다. 생성부터 순환과 삭제까지 전체 생명주기를 AWS가 처리합니다.
- **암호화 통합:** 이 키들은 봉투 암호화 패턴과 매끄럽게 작동하도록 설계되어, 생성된 키가 GenerateDataKey API를 통해 생성된 데이터 키를 랩핑하는 마스터 키로 작동합니다.

이 모델은 고객이 AWS의 보안 통제를 신뢰하고 키 생성과 안전한 저장의 복잡성을 오프로드하는 것을 선호하는 대부분의 애플리케이션에 이상적입니다.

### 3.2. 외부 키 자재

특정 시나리오에서는 고객이 AWS KMS 외부에서 키 자재를 생성해야 할 수도 있습니다. "Bring Your Own Key"(BYOK)라고 불리는 이 모델은 추가적인 통제를 제공합니다.

- **수동 가져오기:** 고객은 자체 암호화 시스템을 사용해 외부에서 키 자재를 생성한 다음 AWS KMS로 가져옵니다.
- **통제와 규정 준수:** 엄격한 규제나 규정 준수 요구 사항이 있는 조직은 AWS로 가져오기 전에 통제된 환경에서 키 자재를 생성하는 것을 선호할 수 있습니다.
- **제한된 순환:** 외부에서 생성된 키 자재를 사용할 때는 고객이 그 생명주기 관리를 책임집니다. 자동 순환은 사용할 수 없으므로 키는 온디맨드로 순환해야 합니다.
- **사용 사례:** 이 접근 방식은 조직이 이미 견고한 암호화 인프라를 갖추고 있거나 보안 정책이 가져오기 전에 특정 하드웨어 보안 모듈(HSM) 환경에서 키를 생성하도록 요구할 때 흔히 사용됩니다.

외부 키 자재를 사용하면 조직이 암호화 신뢰 루트에 대한 통제를 유지하면서도 AWS KMS를 기존 보안 아키텍처에 통합할 수 있습니다.

### 3.3. AWS CloudHSM을 사용한 커스텀 키 스토어

키 자재를 저장하는 하드웨어에 대한 직접적인 통제가 필요한 고객을 위해 AWS는 AWS CloudHSM을 지원하는 커스텀 키 스토어를 사용하는 옵션을 제공합니다.

- **전용 하드웨어 보안:** AWS CloudHSM은 고객이 통제하는 전용 하드웨어 보안 모듈을 제공합니다. CloudHSM 클러스터를 KMS에 연결함으로써 고객은 키 자재가 자신이 관리하는 하드웨어에서 생성되고 저장되도록 보장합니다.
- **커스텀 키 스토어 구성:** 고객은 먼저 고가용성을 위해 여러 가용 영역에 걸쳐 CloudHSM 클러스터를 설정합니다. 그런 다음 이 클러스터는 커스텀 키 스토어 구성을 통해 AWS KMS에 연결됩니다.
- **운영 통합:** 키 자재는 고객이 통제하는 HSM 내에 저장되지만, AWS KMS는 계속 키 메타데이터를 관리하고, 정책을 강제하고, 암호화 작업을 로깅합니다.
- **강화된 보안과 규정 준수:** 이 옵션은 엄격하게 규제되는 산업이나 엄격한 내부 보안 요구 사항을 가진 조직에 특히 유용하며, 키 저장에 사용되는 하드웨어에 대한 실질적인 통제를 제공합니다.
- **성능 고려 사항:** 커스텀 키 스토어에 저장된 키를 포함하는 암호화 작업은 KMS 생성 키를 사용하는 작업과 다른 성능 특성을 가질 수 있습니다. 다만 보안과 규정 준수 측면의 이점이 종종 이러한 고려 사항을 능가합니다.

AWS CloudHSM을 사용한 커스텀 키 스토어를 선택함으로써 고객은 AWS KMS의 운영 단순성의 혜택을 계속 누리면서도 암호화 작업을 엄격한 규제 요구 사항에 맞출 수 있습니다.

## 4. Multi-Region 키

조직이 점점 전역적이고 멀티 리전 환경에서 운영됨에 따라, 리전 전반에 복제할 수 있는 키의 필요성이 중요해지고 있습니다. AWS KMS는 리전 간 암호화와 복호화 워크플로를 단순화하는 multi-region 키를 생성할 수 있는 능력을 제공합니다.

![KMS-Multi-Region Keys](@site/docs/Security,%20Identity,%20and%20Compliance/_assets/kms-multi-region_keys.png)

Multi-region 키는 데이터를 재암호화하거나 리전 간 API 호출을 발생시키지 않고도 한 리전에서 암호화되고 다른 리전에서 복호화될 수 있는 시나리오를 위해 설계되었습니다.

- **키 자재의 복제:** multi-region 키가 생성되면 그 키 자재와 키 ID는 여러 AWS 리전에 걸쳐 복제됩니다. 서로 다른 리전에 있음에도 키는 동일한 키 ID와 속성을 유지합니다.
- **프라이머리와 리플리카 모델:** multi-region 키는 프라이머리/리플리카 모델을 따릅니다. 한 리전이 프라이머리 키를 호스팅하고 추가 리전이 리플리카 키를 호스팅합니다. 각 키를 독립적으로 관리할 수 있지만, 이들은 기능적으로 동일하며 동일한 기반 암호화 자재를 공유합니다.
- **재해 복구와 전역 애플리케이션:** multi-region 키는 애플리케이션의 데이터가 한 리전에 저장되지만 다른 리전에서 접근 가능해야 하는 재해 복구 시나리오에 특히 유용합니다. 또한 여러 리전에서 저지연 복호화를 가능하게 하는 전역 클라이언트 측 암호화 워크플로도 지원합니다.
- **자동 순환:** 프라이머리 키에서 자동 순환이 활성화되면 업데이트된 백업 키가 모든 리플리카 키로 복제되어, 리전 전반에서 일관된 키 관리를 보장합니다.
- **운영 고려 사항:** multi-region 키는 리전 간 암호화와 복호화의 편리함을 제공하지만, "전역" 키는 아니라는 점에 유의해야 합니다. 대신 각 키는 특정 리전에 종속되므로, multi-region 아키텍처를 설계할 때 적절한 계획과 관리가 필요합니다.

multi-region 키를 활용함으로써 조직은 전역적으로 분산된 애플리케이션에서 데이터 보호를 간소화하고, 지연 시간을 줄이고, 재해 복구 시나리오에서 키 관리를 단순화할 수 있습니다.

## 5. 봉투 암호화

AWS KMS는 직접 암호화할 수 있는 데이터의 크기에 제한(최대 4킬로바이트)을 부과하기 때문에, AWS는 더 큰 데이터셋에는 봉투 암호화를 사용할 것을 권장합니다. 봉투 암호화는 AWS KMS와 클라이언트 측 암호화를 모두 활용하는 하이브리드 접근 방식입니다.

### 5.1. GenerateDataKey API

GenerateDataKey API는 봉투 암호화 프로세스의 핵심입니다.

![kms-GenerateDataKey](@site/docs/Security,%20Identity,%20and%20Compliance/_assets/kms-generatedatakey.png)

- **두 부분으로 된 출력:** GenerateDataKey API가 호출되면 AWS KMS는 고유한 데이터 암호화 키(DEK)를 생성합니다. 이 API는 (클라이언트 측 암호화에 즉시 사용하기 위한) DEK의 평문 복사본과 (고객 마스터 키 또는 CMK로 랩핑된) DEK의 암호화된 복사본을 모두 반환합니다.
- **사용 패턴:** 평문 DEK는 클라이언트 측에서 대용량 파일이나 데이터 페이로드를 암호화하는 데 사용되며, 암호화된 DEK는 "봉투"라고 불리는 것 안에 암호문과 함께 저장됩니다.
- **보안 고려 사항:** 평문 DEK는 클라이언트 측에서 일시적으로만 사용 가능하고 안전한 환경 외부로 저장되거나 전송되지 않기 때문에, 키 노출의 위험이 최소화됩니다.
- **성능 이점:** 대량 데이터 암호화를 클라이언트로 오프로드함으로써 봉투 암호화는 AWS KMS가 키 관리와 API 작업에 집중할 수 있게 해, 지연 시간과 비용을 줄여줍니다.
- **대안 API:** AWS KMS는 평문 키가 클라이언트 애플리케이션에 즉시 노출되어서는 안 되는 시나리오를 위해 GenerateDataKeyWithoutPlaintext API도 제공합니다. 다만 즉각적인 암호화가 필요한 봉투 암호화 워크플로에서는 GenerateDataKey API가 선호됩니다.

GenerateDataKey API는 직접 KMS 암호화가 부과하는 4킬로바이트 제한을 초과하는 데이터에 대해 효율적이고 안전한 암호화를 촉진하도록 설계되었습니다.

### 5.2. 클라이언트 측 암호화 워크플로

DEK가 생성되면 클라이언트 측 암호화 워크플로는 다음과 같이 진행됩니다.

![kms-Client-Side Encryption](@site/docs/Security,%20Identity,%20and%20Compliance/_assets/kms-client-side_encryption.png)

- **데이터 암호화:** 클라이언트 애플리케이션은 평문 DEK를 사용해 대용량 파일이나 데이터 스트림을 암호화합니다. 이 과정은 일반적인 대칭 암호화 알고리즘을 사용해 완전히 클라이언트 측에서 수행됩니다.
- **봉투 생성:** 암호화 후 클라이언트는 암호문(암호화된 데이터)과 암호화된 DEK를 모두 포함하는 "봉투"를 생성합니다. 봉투는 데이터와 이를 복호화하는 데 필요한 키를 함께 묶는 안전한 컨테이너 역할을 합니다.
- **저장과 전송:** 봉투는 하나의 단위로 저장되거나 전송됩니다. 암호화된 DEK가 봉투의 일부이기 때문에, 이후의 모든 복호화 작업은 이를 참조할 수 있습니다.

![kms- Client-Side Dec](@site/docs/Security,%20Identity,%20and%20Compliance/_assets/kms-_client-side_dec.png)

- **복호화 프로세스:** 데이터를 복호화해야 할 때 클라이언트는 봉투를 검색하고 암호화된 DEK를 추출합니다. 이 암호화된 DEK는 복호화 API를 통해 AWS KMS로 전송됩니다. KMS가 평문 DEK를 반환하면 클라이언트는 이를 사용해 로컬에서 데이터를 복호화할 수 있습니다.
- **비용과 지연 시간 트레이드오프:** 봉투 암호화는 추가적인 단계가 필요하지만, AWS KMS에 대한 API 호출 수를 크게 줄여, 처리량이 높은 환경에서 운영 비용을 낮추고 지연 시간을 줄여줍니다.
- **데이터 키 캐싱:** 성능을 더욱 최적화하기 위해 AWS Encryption SDK를 포함한 많은 구현이 데이터 키 캐싱을 지원합니다. 이 경우 DEK는 정의된 보안 경계 내에서 여러 암호화 작업에 재사용될 수 있어, AWS KMS에 대한 전체적인 호출 빈도를 줄여줍니다.

봉투 암호화는 중앙화된 키 관리의 보안과 클라이언트 측 암호화의 성능 및 확장성 사이의 균형을 맞추는 강력한 기법입니다. AWS 서비스 전반에서 널리 사용되며 아키텍트와 보안 전문가 모두에게 중요한 개념입니다.

## 6. 키 생명주기 관리

효과적인 키 관리는 생성과 암호화를 넘어섭니다. 순환, 삭제, 복구를 포함한 키의 전체 생명주기를 포괄합니다. AWS KMS는 키의 수명 동안 관리를 돕기 위한 일련의 기능을 제공합니다.

### 6.1. 키 순환

암호화 키의 정기적인 순환은 침해 위험을 줄이기 위한 모범 사례입니다. AWS KMS는 고객 관리형 대칭 키에 대해 자동과 온디맨드 키 순환을 모두 지원하며, AWS 관리형 키는 자동으로 순환됩니다.

#### 6.1.1. 자동 및 온디맨드 순환

자동 키 순환은 AWS KMS가 백업 키를 연간 단위로 순환할 수 있게 하는 기능입니다.

![kms-rotation-Automatic](@site/docs/Security,%20Identity,%20and%20Compliance/_assets/kms-rotation-automatic.png)

- **연간 순환:** 기본적으로 고객 관리형 대칭 키는 365일마다 자동으로 순환하도록 구성할 수 있으며, 순환 간격은 90일에서 2,560일 사이로 커스터마이징할 수 있습니다.
- **매끄러운 전환:** 키가 자동으로 순환되면 이전 백업 키는 복호화 작업에 계속 사용 가능합니다. 이는 이전 버전의 키로 암호화된 데이터를 계속 복호화할 수 있도록 보장합니다.
- **온디맨드 순환:** 자동 순환 외에도 고객은 온디맨드 순환을 트리거할 수 있습니다. 온디맨드 순환은 전체 키 식별자(CMK ID)를 변경하지 않고도 새로운 백업 키를 생성할 수 있게 하여, 클라이언트 애플리케이션에서 매끄러운 전환을 보장합니다.
- **보안 고려 사항:** 키를 순환하면 단일 키 침해가 광범위한 데이터 노출로 이어질 위험을 줄여줍니다. 다만 키 순환은 성능에 영향을 줄 수 있는 과도한 키 재사용을 피하기 위해 운영 요구 사항과 균형을 맞춰야 합니다.

자동 및 온디맨드 키 순환은 운영 단순성과 견고한 보안 사이의 균형을 제공하도록 설계되어, 진행 중인 작업을 중단시키지 않으면서 암호화 키가 신선하게 유지되도록 보장합니다.

#### 6.1.2. 별칭을 사용한 수동 순환

비대칭 키나 더 빈번한 순환이 필요한 경우처럼 자동 순환 대상이 아닌 키의 경우 수동 순환이 해결책입니다.

![kms-Manual Rotation](@site/docs/Security,%20Identity,%20and%20Compliance/_assets/kms-manual_rotation.png)

- **새 키 생성:** 수동 순환 시나리오에서는 다른 키 ID를 가진 새 키가 생성됩니다.
- **별칭을 사용해 변경 사항 숨기기:** 키를 참조하는 애플리케이션을 방해하지 않기 위해 AWS KMS는 별칭 사용을 지원합니다. 별칭은 특정 키 ID를 가리키는 친숙한 이름입니다. 수동 순환이 수행되면 별칭이 새 키를 참조하도록 업데이트됩니다.
- **운영상의 영향:** 이전 키는 이전 키로 암호화된 데이터가 계속 복호화될 수 있도록 활성 상태로 유지됩니다. 애플리케이션은 계속 별칭을 참조해, 순환이 최종 사용자에게는 투명합니다.
- **수동 순환을 사용해야 할 때:** 수동 순환은 비대칭 키나 규제 요구 사항이 표준 순환 기간보다 더 빈번한 키 변경을 요구하는 상황에서 특히 유용합니다.

수동 순환은 더 많은 관리 노력을 요구하지만, 특정 운영이나 규정 준수 요구 사항에 키 순환 일정을 맞출 수 있는 유연성을 제공합니다.

### 6.2. 키 삭제와 복구

키를 폐기하는 과정은 그것을 생성하는 것만큼 중요합니다. AWS KMS는 키를 비활성화하고, 삭제를 예약하고, 경우에 따라 삭제가 실수였다면 복구할 수 있는 메커니즘을 제공합니다.

#### 6.2.1. 대기 중인 삭제 기간

AWS KMS 내에서 생성된 키의 경우 즉시 삭제는 허용되지 않습니다. 대신 키는 "대기 중인 삭제" 상태로 들어갑니다.

- **예약된 삭제:** 키가 삭제 대상으로 표시되면 AWS KMS는 7일에서 30일의 대기 기간을 강제합니다. 이 기간 동안 키는 암호화 작업에 사용할 수 없습니다.
- **취소 옵션:** 삭제 예정인 키가 다시 필요하다면, 대기 기간이 만료되기 전에 삭제 프로세스를 취소할 수 있습니다.
- **감사 가능성:** 대기 중인 삭제 상태에서도 키 사용 시도는 AWS CloudTrail을 통해 로깅됩니다. 이 로깅은 규정 준수와 감사 목적에 필수적입니다.
- **보안상의 함의:** 대기 기간은 실수로 인한 삭제에 대한 안전장치를 제공하며, 관리자가 중요한 프로세스가 해당 키에 종속되어 있지 않은지 확인할 수 있게 합니다.

대기 중인 삭제 메커니즘은 되돌릴 수 없는 데이터 손실을 초래할 수 있는 갑작스러운 키 제거를 방지하는 중요한 안전장치입니다.

#### 6.2.2. 계정 간 고려 사항

계정 간에 사용되는 키를 다룰 때 — 예를 들어 암호화된 RDS 스냅샷의 계정 간 공유 — 삭제 프로세스에는 특별한 주의가 필요합니다.

- **조율된 삭제:** multi-region 키나 계정 간 시나리오에서 사용되는 키의 경우, 다른 계정의 모든 리플리카 또는 종속 키가 삭제될 때까지 프라이머리 키는 삭제할 수 없습니다.
- **리플리카 키의 승격:** 경우에 따라 프라이머리 키를 삭제해야 하지만 리플리카가 남아 있어야 한다면, 삭제가 이루어지기 전에 리플리카를 새로운 프라이머리 키로 승격시킬 수 있습니다.
- **알림과 모니터링:** AWS CloudTrail, CloudWatch, Amazon SNS와의 통합은 키가 사용 중일 때 삭제가 시도되면 관리자에게 알림을 받을 수 있게 합니다. 이러한 알림은 의도치 않은 데이터 접근 불가를 방지하기 위한 시기적절한 개입을 가능하게 합니다.
- **운영 워크플로:** 계정 간 시나리오에서의 삭제 프로세스는 일반적으로 더 복잡한데, 여러 계정에 걸쳐 삭제 단계를 수동으로 확인하고 신중하게 순서를 정해야 할 수 있기 때문입니다.

효과적인 키 삭제와 복구 관행은 암호화 키가 오용되거나 조기에 파괴되지 않도록 보장하면서 운영 연속성을 유지하는 데 필수적입니다.

## 7. 보안과 접근 제어

권한이 있는 사용자와 서비스만 암호화 키에 접근할 수 있도록 보장하는 것은 모든 안전한 시스템의 초석입니다. AWS KMS는 IAM과 통합되며 접근을 제어하기 위한 자체 네이티브 메커니즘(키 정책과 그랜트 등)을 제공합니다.

### 7.1. 키 정책

키 정책은 개별 KMS 키에 대한 접근을 제어하는 JSON 기반 리소스 정책입니다. 어떤 주체(사용자, 역할, 계정)가 키에 대한 암호화 작업을 수행할 권한을 가지는지 정의하는 주요 메커니즘입니다.

#### 7.1.1. 기본 vs. 커스텀 정책

키가 생성되면 AWS KMS는 AWS 계정의 루트 사용자에게 전체 접근을 부여하는 기본 키 정책을 생성합니다. 다만 고객은 이 기본 정책을 커스텀 키 정책으로 수정하거나 교체할 수 있습니다.

- **기본 키 정책:** 기본 정책은 단순하도록 설계되어 있어, 루트 사용자에게 전체 통제를 부여하지만 더 세밀한 권한을 위해 IAM에 의존합니다. 명시적으로 부여되지 않는 한 기본적으로 접근을 허용하지 않습니다.
- **커스텀 키 정책:** 커스텀 키 정책은 관리자가 암호화, 복호화, 재암호화, 데이터 키 생성 등의 특정 암호화 작업에 대해 어떤 사용자나 역할이 접근할 수 있는지 지정할 수 있게 합니다. 커스텀 정책은 계정 간 접근을 포함하는 시나리오에 특히 유용합니다.
- **IAM으로의 위임:** 키 정책은 IAM 정책에 권한을 위임할 수 있어, 사용자가 자신의 IAM 자격 증명을 통해 접근할 수 있게 합니다. 이 모델에서 키 정책은 게이트키퍼 역할을 하며 키 접근에 대한 신뢰 경계를 수립합니다.
- **보안 모범 사례:** 키 정책은 최소 권한의 원칙을 따라, 각 주체가 필요한 작업을 수행하는 데 필요한 권한만 부여하는 것이 권장됩니다.

기본 정책과 커스텀 정책 중 선택은 조직의 보안 요구 사항과 접근 제어 모델의 복잡성에 따라 달라집니다.

### 7.2. 그랜트와 임시 권한

키 정책 외에도 AWS KMS는 임시 권한을 위임하는 "그랜트"라는 메커니즘을 제공합니다.

- **그랜트의 목적:** 그랜트는 키 소유자가 키 정책을 수정할 필요 없이 특정 IAM 주체에게 키로 특정 작업을 수행할 권한을 부여할 수 있게 합니다.
- **사용 사례:** 그랜트는 AWS 서비스가 사용자를 대신해 일회성 작업을 수행해야 할 때처럼 임시 권한에 특히 유용합니다.
- **그랜트 생명주기:** 더 이상 필요하지 않으면 그랜트를 명시적으로 취소해야 합니다. 자동으로 만료되지 않으므로, 남아 있는 권한을 피하기 위해 적절한 생명주기 관리가 필요합니다.
- **구현:** 그랜트는 API 호출을 통해 생성되며 키 ID, 그랜트를 받는 주체, 허용된 작업(암호화, 복호화, 서명, 검증 등), 추가적인 제약 조건을 지정합니다.

그랜트는 키 정책이나 IAM 정책을 계속 수정하는 오버헤드 없이 임시 또는 일회성 접근을 허용함으로써 유연성을 제공합니다.

### 7.3. 계정 간 접근 방법

KMS 키에 대한 계정 간 접근을 가능하게 하는 여러 방법이 있습니다.

- **키 정책 수정:** 키 소유자는 다른 AWS 계정의 주체를 포함하도록 키 정책을 수정해, 그들에게 키에 대한 접근을 부여할 수 있습니다.
- **대상 계정의 IAM 정책:** 접근을 받는 계정에서는 원격 키에 대한 필요한 KMS 작업을 허용하도록 IAM 정책을 구성해야 합니다.
- **그랜트 사용:** 외부 계정이 임시 접근이 필요한 시나리오의 경우, 키 정책을 영구적으로 수정하는 대신 그랜트를 사용할 수 있습니다.
- **IAM 역할 수임:** 계정 간 접근 전략은 키를 소유한 계정에서 IAM 역할을 수임하는 것을 포함할 수 있습니다. 이 역할이 수임되면 암호화 작업을 수행하는 데 필요한 권한을 제공합니다.

계정 간 접근은 멀티 테넌트 환경과 조직 경계를 넘어 암호화된 리소스(RDS 스냅샷 등)를 공유할 때 매우 중요합니다.

### 7.4. 인가 프로세스

요청된 작업에 접근을 부여할지 AWS KMS가 평가하는 프로세스는 복잡하며 여러 계층의 점검을 포함합니다. 다음 단계는 일반적인 인가 흐름을 보여줍니다.

#### 7.4.1. SCP, IAM, 키 정책 평가

1. **명시적 거부 확인:** 평가는 키 정책이나 관련 정책(서비스 제어 정책(SCP) 등)에 명시적인 "거부" 명문이 있는지 확인하는 것부터 시작합니다. 명시적 거부가 발견되면 요청은 즉시 거부됩니다.
2. **서비스 제어 정책(SCP):** 명시적 거부가 없다면 시스템은 다음으로 접근을 제한할 수 있는 SCP를 평가합니다. SCP가 해당 작업을 허용하지 않으면 접근이 거부됩니다.
3. **VPC 엔드포인트 정책 확인:** VPC 엔드포인트를 사용하는 프라이빗 접근 시나리오의 경우, 다음으로 엔드포인트 정책이 확인됩니다. 정책이 접근을 허용하지 않으면 요청은 거부됩니다.
4. **키 정책 평가:** 그다음 키 정책을 검토해 호출자에게 필요한 권한을 명시적으로 부여하는지 확인합니다. 키 정책이 접근을 부여하면 프로세스가 계속됩니다.
5. **그랜트 평가:** 키 정책에 호출자에 대한 명시적인 허용이 없더라도 시스템은 해당 작업을 허용할 수 있는 그랜트가 있는지 확인합니다.
6. **IAM 정책으로의 위임:** 키 정책이 접근 제어를 IAM에 위임하면 호출자의 신원과 연관된 IAM 정책이 평가됩니다.
7. **계정 간 고려 사항:** 마지막으로 키가 계정 간에 접근되고 있다면, 소유자 계정의 키 정책과 호출자 계정의 IAM 정책 모두가 요청된 작업을 승인하는지 확인하는 추가적인 점검이 이루어집니다.

이 다단계 평가 프로세스는 적절히 승인된 요청만 KMS 키를 사용할 수 있도록 보장해, 견고한 심층 방어 메커니즘을 제공합니다.

### 7.5. 조건 키(kms:ViaService, kms:CallerAccount)

AWS KMS는 접근을 더욱 제한하기 위해 키 정책 내에서 사용할 수 있는 특별한 조건 키도 지원합니다.

- **kms:ViaService:** 이 조건 키는 관리자가 특정 AWS 서비스만 키를 사용할 수 있도록 지정할 수 있게 합니다. 예를 들어 키가 Amazon EC2나 RDS만 사용할 수 있도록 제한할 수 있습니다. 이는 서비스별 암호화 정책을 강제하는 데 도움을 줍니다.
- **kms:CallerAccount:** 이 조건 키는 키 사용을 특정 AWS 계정의 주체로 제한합니다. 신뢰할 수 있는 계정의 신원만 키에 대한 작업을 수행할 수 있도록 보장하기 위해 계정 간 시나리오에서 특히 유용합니다.

이 조건 키들을 사용하면 키가 어떻게, 어디서 사용될 수 있는지에 대한 정밀한 통제를 허용함으로써 추가적인 보안 계층을 제공합니다.

## 8. 비대칭 암호화와 서명

대칭 키가 AWS KMS의 많은 암호화 시나리오를 지배하지만, 비대칭 키는 안전한 키 교환, 디지털 서명, 공개 키 인프라(PKI)에 필수 불가결한 기능을 제공합니다.

### 8.1. 키 쌍과 사용 사례

비대칭 암호화는 퍼블릭 키와 프라이빗 키로 구성된 키 쌍의 사용을 포함합니다.

- **퍼블릭 키:** 퍼블릭 키는 암호화나 디지털 서명 검증에 사용됩니다. 공개적으로 공유할 수 있기 때문에 외부 당사자에게 배포되거나 애플리케이션에 내장되는 경우가 많습니다.
- **프라이빗 키:** 프라이빗 키는 복호화나 데이터 서명에 사용됩니다. 이 키는 매우 민감하며 AWS KMS 외부에서 평문으로 노출되지 않습니다.
- **사용 사례:** 비대칭 키는 암호화 작업이 AWS 외부에서 수행될 수 있는 데이터를 암호화하거나, 데이터 무결성을 보장하기 위한 디지털 서명, 안전한 키 교환이 필요한 시나리오에 사용됩니다.
- **지원되는 알고리즘:** AWS KMS는 암호화/복호화와 서명/검증 모두를 위한 RSA, 서명과 검증을 위한 타원 곡선 암호(ECC), 그리고 중국 리전의 경우 SM2 키를 포함한 여러 비대칭 알고리즘을 지원합니다.
- **보안 모델:** 프라이빗 키는 복호화나 서명에 사용되더라도 AWS KMS의 안전한 경계를 암호화되지 않은 형태로 절대 벗어나지 않습니다. 프라이빗 키가 필요한 모든 작업은 API 호출을 통해 AWS KMS 내에서 수행됩니다.

비대칭 키는 공개 키 암호화가 필요한 외부 시스템 및 애플리케이션과의 안전한 상호작용을 가능하게 함으로써 AWS KMS의 유연성을 확장합니다.

### 8.2. 디지털 서명 워크플로

디지털 서명은 데이터의 진위성과 무결성을 검증하는 데 사용되는 암호화 기법입니다.

- **다이제스트 생성:** 대용량 파일이나 문서에 디지털 서명을 하려면 클라이언트는 먼저 데이터의 다이제스트(암호화 해시)를 계산합니다. 다이제스트는 파일 내용을 고유하게 나타내는 고정 크기 문자열입니다.
- **다이제스트 서명:** 그런 다음 클라이언트는 AWS KMS를 사용해 다이제스트에 서명합니다. 이 과정에서 AWS KMS가 보유한 프라이빗 키가 디지털 서명을 생성하는 데 사용됩니다. 디지털 서명은 나중에 파일이 변경되지 않았음을 검증하는 데 사용할 수 있는 암호적으로 안전한 토큰입니다.
- **서명된 데이터 배포:** 파일은 디지털 서명과 함께 수신자에게 전송됩니다. 수신자는 (다운로드 가능한) 퍼블릭 키를 사용해 서명을 검증합니다.
- **검증 프로세스:** 수신자는 수신한 파일의 다이제스트를 계산하고 AWS KMS의 verify API를 사용해 계산된 다이제스트를 서명과 비교합니다. 일치하면 파일의 무결성과 진위성이 확인됩니다.
- **애플리케이션:** 디지털 서명은 문서 전자 서명, 안전한 메시징, 인증 토큰, 그리고 데이터 무결성이 무엇보다 중요한 다른 많은 시나리오에서 사용됩니다.

디지털 서명과 검증에 대한 견고한 지원을 제공함으로써 AWS KMS는 통신을 보호하고 전송 중 데이터가 변조되지 않았음을 보장하는 데 중요한 역할을 합니다.

## 9. 성능과 최적화

AWS KMS가 데이터를 보호하는 데 있어 수행하는 중요한 역할을 감안할 때, 서비스의 성능 특성과 보안, 비용, 지연 시간의 균형을 맞추기 위해 사용할 수 있는 최적화 전략을 이해하는 것이 중요합니다.

### 9.1. API 제한과 스로틀링

AWS KMS는 시스템의 안정성과 성능을 보장하기 위해 서비스 한도를 강제합니다.

- **요청 한도:** AWS KMS에 초당 만들 수 있는 API 요청 수에는 한도가 있습니다. 이 한도를 초과하면 스로틀링이 발생할 수 있어 애플리케이션 성능에 영향을 줄 수 있습니다.
- **비용상의 함의:** AWS KMS에 대한 각 호출은 요금이 부과됩니다. 빈번한 호출은 — 특히 처리량이 높은 애플리케이션에서 — 상당한 비용을 초래할 수 있습니다.
- **완화 전략:** 스로틀링 위험을 완화하기 위해 애플리케이션은 암호화 작업의 배치 처리, 키 생성 호출 빈도 최적화, 클라이언트 측 캐싱 기법 사용 같은 전략을 고려해야 합니다.
- **모니터링:** AWS CloudWatch와 CloudTrail은 KMS 사용과 관련된 상세한 지표와 로그를 제공합니다. 이 도구들은 API 사용을 모니터링하고, 스로틀링 이벤트를 감지하고, 애플리케이션 성능을 최적화하는 데 사용할 수 있습니다.

API 한도를 이해하고 관리하는 것은 AWS KMS에 크게 의존하는 환경에서 성능과 비용 효율성을 모두 유지하는 데 필수적입니다.

### 9.2. 데이터 키 캐싱 전략

데이터 키 캐싱은 AWS KMS에 대한 API 호출 수를 줄이는 데 사용되는 강력한 기법입니다.

- **데이터 키 재사용:** 모든 암호화 작업마다 새 데이터 키를 생성하는 대신, 데이터 키 캐싱은 구성 가능한 기간, 바이트 수, 또는 메시지 수만큼 데이터 키를 재사용할 수 있게 합니다.
- **성능 이점:** 데이터 키를 캐싱함으로써 애플리케이션은 GenerateDataKey API에 대한 빈번한 호출과 관련된 지연 시간과 비용을 크게 줄일 수 있습니다.
- **보안 트레이드오프:** 데이터 키를 재사용하면 성능을 개선할 수 있지만, 일부 보안 트레이드오프도 발생합니다. 더 긴 기간 동안 또는 더 큰 볼륨의 데이터를 암호화하기 위해 키를 재사용하면 키가 침해될 위험이 증가합니다.
- **구현:** AWS Encryption SDK를 비롯한 다른 라이브러리는 로컬 암호화 자재 캐시를 통해 데이터 키 캐싱을 지원합니다. 이 캐시는 새 데이터 키를 가져오기 전에 최대 나이, 최대 암호화 바이트 수, 또는 최대 암호화 작업 수를 지정하는 정책으로 구성할 수 있습니다.
- **균형 잡기:** 데이터 키를 캐싱할지 여부에 대한 결정은 애플리케이션의 특정 보안 및 성능 요구 사항에 기반해 내려져야 합니다. 목표는 API 호출 감소의 이점이 데이터의 전체적인 보안을 저해하지 않는 최적의 균형을 찾는 것입니다.

데이터 키 캐싱은 강력한 보안 통제를 유지하면서도 처리량이 높은 환경에서 암호화 성능을 최적화하는 가장 효과적인 방법 중 하나입니다.

## 10. 속성 기반 접근 제어(ABAC)

속성 기반 접근 제어(ABAC)는 고정된 신원이 아니라 속성(또는 태그)을 기반으로 리소스에 대한 접근을 관리하는 방법입니다.

- **개념 개요:** ABAC를 사용하면 KMS 키를 사용할 권한을 리소스 태그를 기반으로 부여할 수 있습니다. 예를 들어 "environment:prod"로 태그된 키는 IAM 정책이 프로덕션 키로 작업할 수 있다고 지정한 사용자만 접근할 수 있습니다.
- **확장성:** ABAC는 대규모 접근 관리를 단순화합니다. 각 개별 키나 사용자마다 상세한 정책을 정의하는 대신, 조직은 태그 기반 정책을 활용해 접근을 부여하거나 제한할 수 있습니다.
- **KMS에서의 구현:** AWS KMS에서 ABAC는 키 정책이 KMS 키의 특정 태그 값을 확인하는 조건을 포함할 수 있게 함으로써 구현됩니다. 마찬가지로 IAM 정책은 이 태그를 참조하도록 작성할 수 있어, 일치하는 속성을 가진 키에 대해서만 승인된 사용자가 암호화 작업을 수행할 수 있도록 보장합니다.
- **이점:** ABAC는 명시적인 사용자나 역할 기반 권한을 유지하는 관리 부담을 줄여 보안을 강화합니다. 또한 키가 재분류되거나 환경 간에 이동될 때 같은 변경 사항에 적응하기 더 쉽게 만들어줍니다.
- **보안 고려 사항:** 다른 접근 제어 메커니즘과 마찬가지로 ABAC 정책의 신중한 설계와 테스트가 매우 중요합니다. 정책은 의도한 사용자만 접근을 부여받도록 정확해야 하며 최소 권한의 원칙을 따라야 합니다.

ABAC는 복잡하고 동적인 환경에서 암호화 키 관리를 크게 단순화할 수 있는 현대적이고 유연한 접근 제어 방식입니다.

## 11. 결론

요약하면, AWS KMS는 단순한 키 관리 서비스를 넘어 — 다양한 암호화 시나리오와 보안 요구 사항을 지원하는 포괄적인 플랫폼입니다. S3의 민감한 저장 데이터를 암호화하든, EBS 볼륨을 보호하든, RDS 데이터베이스를 보안하든, 리전 간 애플리케이션의 무결성을 보장하든, AWS KMS는 클라우드에서 데이터를 보호하는 데 필요한 도구와 기능을 제공합니다.
