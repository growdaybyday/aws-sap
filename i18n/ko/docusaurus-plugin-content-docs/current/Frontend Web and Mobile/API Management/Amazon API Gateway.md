# Amazon API Gateway

## 1. 소개

Amazon API Gateway는 개발자가 **어떤 규모로든 API를 생성, 게시, 유지 관리, 모니터링, 보호**할 수 있게 해주는 완전관리형 서비스입니다. AWS Lambda 함수, 컨테이너화된 마이크로서비스, 또는 전통적인 웹 애플리케이션 같은 백엔드 서비스로부터 데이터, 비즈니스 로직, 또는 기능에 접근하기 위한 애플리케이션의 "정문" 역할을 합니다. 트래픽 관리, 권한 부여, 모니터링, 버전 관리 같은 작업을 대신 처리하면서 수십만 건의 동시 API 호출을 처리하도록 설계되었습니다.

## 2. API Gateway의 아키텍처

다음 다이어그램은 API Gateway 아키텍처를 보여줍니다.

![api-gateway-arch](@site/docs/Frontend%20Web%20and%20Mobile/_assets/api-gateway-arch.png)

이 다이어그램은 Amazon API Gateway에서 구축한 API가 여러분이나 개발자 고객에게 AWS 서버리스 애플리케이션을 구축하기 위한 통합되고 일관된 개발자 경험을 어떻게 제공하는지 보여줍니다. API Gateway는 수십만 건의 동시 API 호출을 수락하고 처리하는 것과 관련된 모든 작업을 처리합니다. 이 작업들에는 트래픽 관리, 권한 부여와 접근 제어, 모니터링, API 버전 관리가 포함됩니다.

API Gateway는 Amazon Elastic Compute Cloud(Amazon EC2)에서 실행되는 워크로드, AWS Lambda에서 실행되는 코드, 모든 웹 애플리케이션, 또는 실시간 통신 애플리케이션 같은 백엔드 서비스로부터 데이터, 비즈니스 로직, 또는 기능에 접근하기 위한 애플리케이션의 "정문" 역할을 합니다.

## 3. 지원되는 API 유형

API Gateway는 다양한 사용 사례를 충족하기 위해 여러 API 스타일을 지원합니다.
### 3.1. REST API

REST API는 리소스와 표준 HTTP 메서드를 중심으로 엔드포인트를 구성함으로써 웹 서비스를 구축하는 견고하고 다재다능한 접근 방식을 제공합니다. 고유한 URL 경로로 표현되는 각 리소스는 GET, POST, PUT, PATCH, DELETE 같은 메서드로 조작될 수 있습니다. 이 리소스 기반 구조는 실제 데이터 엔터티와 작업을 모델링하기 쉽게 만들어줍니다 — 예를 들어 새 소득 레코드를 추가하기 위한 `/incomes`로의 POST나 지출 데이터를 검색하기 위한 `/expenses`로부터의 GET을 허용합니다. REST API는 또한 클라이언트로부터 기본 복잡성을 추상화하면서 AWS Lambda, DynamoDB, 또는 다른 HTTP 엔드포인트 같은 백엔드 서비스와의 상세한 통합을 용이하게 합니다.

이러한 API는 요청/응답 변환, 상세한 오류 처리, 스키마 검증을 포함한 포괄적인 API 관리 기능이 필요할 때 이상적입니다. 풍부한 문서, SDK 생성, 프론트엔드와 백엔드 간 상호 작용에 대한 정밀한 제어가 필요한 시나리오에 특히 유용합니다. 재무 데이터나 사용자 프로필 관리 같은 비즈니스 로직이 특정 리소스 작업과 밀접하게 연결된 애플리케이션에서 REST API는 필요한 세분성과 통합 유연성을 제공합니다.

### 3.2. HTTP API

HTTP API는 더 낮은 지연 시간과 비용 효율성에 최적화된, REST API에 대한 간소화되고 고성능인 대안을 제공합니다. 핵심 기능에 집중해 API 개발을 단순화하고 AWS Lambda 함수나 공개적으로 라우팅 가능한 모든 HTTP 엔드포인트와 원활하게 통합됩니다. OpenID Connect와 OAuth 2.0 같은 현대적인 웹 보안 표준을 지원하고, 자동 배포와 교차 출처 리소스 공유(CORS) 같은 내장 기능과 함께, HTTP API는 필수적인 보안과 접근성을 희생하지 않으면서 속도가 필요한 애플리케이션에 잘 맞습니다.

주요 요구 사항이 빠른 응답 시간과 최소한의 처리 오버헤드일 때 HTTP API가 선호되는 선택입니다. 광범위한 요청/응답 변환이나 복잡한 라우팅 규칙 없이 백엔드 서비스로 요청을 신속하게 전달하는 것이 API의 역할인 시나리오에 완벽합니다. 예를 들어 최소한의 지연 시간으로 실시간 사용자 상호 작용이나 데이터 검색을 처리하는 서버리스 백엔드를 구축하고 있다면, HTTP API를 활용하는 것이 더 효율적이고 비용 효과적인 솔루션으로 이어질 수 있습니다.

### 3.3. WebSocket API

WebSocket API는 지속적인 연결을 유지함으로써 클라이언트와 서버 간의 실시간, 양방향 통신을 가능하게 합니다. 이를 통해 양측이 언제든지 메시지를 보낼 수 있어, 즉각적인 데이터 교환이 필요한 대화형 애플리케이션에 훌륭한 선택입니다. 전통적인 요청-응답 모델과 달리 WebSocket API는 지속적인 데이터 스트림을 지원하며, 이는 폴링의 지연이 성능을 저해하는 라이브 채팅, 실시간 대시보드, 또는 협업 도구 같은 애플리케이션에 매우 중요합니다.

이 API들은 사용자에게 라이브 업데이트를 푸시하는 시스템을 구축해야 할 때 특히 유리해, 정보가 가용해지는 즉시 전달되도록 보장합니다. 예를 들어 채팅 애플리케이션은 연결된 모든 클라이언트에게 즉시 메시지를 브로드캐스트할 수 있고, 실시간 주식 시세는 반복적인 HTTP 요청 없이도 최신 시장 정보로 사용자를 업데이트할 수 있습니다. WebSocket API를 활용함으로써 개발자는 여러 동시 연결과 동적이고 실시간인 상호 작용을 효율적으로 처리하는 확장 가능하고 반응성 있는 시스템을 만들 수 있습니다.

#### 3.3.1. 연결

- **연결 ID:** 클라이언트가 WebSocket 연결을 설정하면 API Gateway는 고유한 연결 ID를 할당합니다. 이 ID는 후속 상호 작용에 사용되며 (예를 들어 데이터베이스에 연결 메타데이터를 저장함으로써) 상태를 외부적으로 관리하는 데 필수적입니다.
- **라이프사이클 관리:** API Gateway는 각 연결의 라이프사이클을 관리해, 클라이언트가 연결하거나 연결을 끊을 때 특정 라우트를 호출합니다.
#### 3.3.2. 라우트와 라우트 선택

![api-gateway-websocket](@site/docs/Frontend%20Web%20and%20Mobile/_assets/api-gateway-websocket.png)
- **내장 라우트:**
    - **$connect:** 클라이언트가 연결을 시작할 때 트리거됩니다. 종종 초기 인증이나 설정을 수행하는 데 사용됩니다.
    - **$disconnect:** 클라이언트가 연결을 끊을 때 호출되어 정리 작업을 가능하게 합니다.
    - **$default:** 특정 커스텀 라우트와 일치하지 않는 모든 메시지를 캐치합니다.
- **커스텀 라우트:**
    개발자는 메시지 콘텐츠를 기반으로 추가 라우트를 정의할 수 있습니다. 각 라우트는 _라우트 키_ — API Gateway가 라우팅 선택 표현식을 사용해 들어오는 메시지와 일치시키는 문자열 — 로 결정됩니다. 이는 메시지 처리에 대한 세밀한 제어를 제공합니다.

## 4. 엔드포인트 유형

![api-gateway-endpoint-types](@site/docs/Frontend%20Web%20and%20Mobile/_assets/api-gateway-endpoint-types.png)

API Gateway를 사용하면 엔드포인트 유형을 정의함으로써 API가 접근되는 방식을 선택할 수 있습니다. 간단히 말해 엔드포인트 유형은 API의 호스트명과 네트워크 라우팅을 결정합니다. 사용 사례와 클라이언트가 위치한 곳에 따라 다음 중 하나를 선택할 수 있습니다.

- **Edge-optimized:** 전 세계에 분산된 클라이언트로부터의 REST API 요청을 서비스하도록 설계되었습니다.
- **Regional:** 클라이언트가 단일 AWS 리전 내 또는 그 근처에 있는 API에 이상적입니다.
- **Private:** API 접근을 Amazon Virtual Private Cloud(VPC) 내 리소스로 제한합니다.

이 엔드포인트 유형들이 두 API 제품 간에 다르게 지원된다는 점에 유의하는 것이 중요합니다.

- **REST API**는 세 가지 유형(Edge-optimized, Regional, Private) 모두를 지원합니다.
- **HTTP API**는 Regional 엔드포인트 유형만 지원합니다.

### 4.1. Edge-optimized API 엔드포인트

Edge-optimized 엔드포인트는 지리적으로 분산된 사용자의 지연 시간을 줄이기 위해 가장 가까운 Amazon CloudFront Point of Presence(POP)를 통해 들어오는 요청을 라우팅합니다. 이 설정은 CloudFront의 글로벌 분산을 활용해 성능을 최적화합니다. 그러나 Edge-optimized 엔드포인트는 REST API 전용으로 사용 가능하며 HTTP API에서는 지원되지 않습니다. 또한 Edge-optimized REST API에 커스텀 도메인 이름을 할당하면 모든 리전에 걸쳐 전역적으로 적용됩니다.

### 4.2. Regional API 엔드포인트

Regional 엔드포인트는 API 클라이언트가 배포된 API와 동일한 리전 내에 위치한 시나리오를 위한 것입니다. 이는 연결 오버헤드를 최소화하며 동일 리전 내 EC2 인스턴스 같은 AWS 리소스에서 애플리케이션을 실행할 때 특히 유리합니다. Regional 엔드포인트의 경우:

- **REST API**는 이를 지원해, (필요하면 여러 리전에 걸쳐 동일한 도메인 이름을 재사용할 수 있지만) 각 리전에 특화된 커스텀 도메인 이름을 구성하는 유연성을 제공합니다.
- **HTTP API**도 Regional 엔드포인트만 독점적으로 사용합니다.
- 모든 HTTP 헤더 이름을 변경 없이 통과시켜, 클라이언트의 헤더가 보존되도록 보장합니다.

Regional 엔드포인트를 (원한다면) 자체 CloudFront 배포와 결합함으로써, Edge-optimized 엔드포인트와 연관된 내장 CloudFront 배포를 사용하지 않고도 다양한 지리적 위치의 클라이언트에게 전달을 최적화할 수 있습니다.

### 4.3. Private API 엔드포인트

Private 엔드포인트는 VPC 내에서만 접근 가능해야 하는 내부 API를 위해 설계되었습니다. Private REST API를 생성할 때는 인터페이스 VPC 엔드포인트(VPC 내의 Elastic Network Interface)를 설정함으로써 하며, 이는 API 접근을 프라이빗 네트워크로 제한합니다. 이 엔드포인트 유형은 HTTP API에서는 사용할 수 없습니다. Regional 엔드포인트와 마찬가지로 Private 엔드포인트는 제공된 모든 헤더 이름을 그대로 전달해 HTTP 요청의 무결성을 유지합니다.

### 5.1. 상호 TLS 인증

![api-gateway-mutual-tls](@site/docs/Frontend%20Web%20and%20Mobile/_assets/api-gateway-mutual-tls.png)

상호 TLS 인증은 양방향 검증 프로세스를 확립하는 견고한 보안 메커니즘입니다. 클라이언트와 서버 모두 신원을 확인하기 위해 X.509 인증서를 제시해야 하며, 신뢰할 수 있는 당사자만 통신을 시작할 수 있도록 보장합니다. 이 프로토콜은 강력한 신원 보증이 필요한 사물 인터넷(IoT) 네트워크와 기업 간(B2B) 상호 작용 같은 시나리오에 특히 중요합니다.

API Gateway 내에서 상호 TLS는 원활하게 통합됩니다. 클라이언트가 상호 TLS를 사용해 연결하면 API Gateway는 제시된 인증서를 Lambda 권한 부여자와 백엔드 통합으로 전달해 추가 처리합니다. 이 기능을 구현하려면 커스텀 도메인 이름을 사용하고, AWS Certificate Manager를 통해 최소 하나의 인증서를 프로비저닝하고, Amazon S3에 truststore를 설정해야 합니다. 또한 기본 `execute-api` 엔드포인트를 비활성화하면 클라이언트가 오직 커스텀 도메인을 통해서만 API에 접근하도록 보장해 보안을 강화합니다.

**실제 사용 사례:**
- **IoT 배포:** 장치가 데이터를 전송하기 전에 인증서를 사용해 안전하게 인증합니다.
- **B2B 통합:** 파트너가 서로의 신원을 검증해 민감한 비즈니스 데이터를 안전하게 교환합니다.

### 5.2. 백엔드 인증을 위한 인증서

백엔드 인증을 위한 인증서는 백엔드 시스템이 들어오는 요청이 실제로 API Gateway에서 발생했는지 검증할 수 있는 메커니즘을 제공합니다. 이는 API Gateway가 SSL 인증서를 생성하고 공개 키를 노출함으로써 달성되며, 백엔드는 이를 사용해 요청의 출처를 확인할 수 있습니다.

REST API의 경우 API Gateway는 자체 서명된 SSL 인증서를 생성할 수 있어, 백엔드 시스템이 검증에 사용할 수 있도록 공개 키를 제공합니다. 이 프로세스는 백엔드가 공개적으로 접근 가능하더라도 신뢰할 수 있는 소스로부터의 요청만 처리하도록 보장하는 데 도움을 줍니다. 반면 HTTP API는 이 인증서 생성을 네이티브로 지원하지 않습니다.

**HTTP API를 위한 대안:**
HTTP API의 경우 인증서 기반 검사를 모방하는 서명이나 토큰을 검증하기 위해 (예를 들어 Lambda 권한 부여자를 사용해) 커스텀 검증을 구현할 수 있어, 네이티브 지원 없이도 유사한 보안을 보장합니다.

**실제 사용 사례:**
- **민감한 데이터 전송:** 백엔드는 요청의 진위를 확인해 데이터 교환이 API Gateway를 통해서만 일어나도록 보장할 수 있습니다.
- **퍼블릭 서비스 엔드포인트:** 백엔드 서비스가 공개적으로 노출될 때 인증서 검증은 무단 접근에 대한 추가적인 보안 계층 역할을 합니다.

### 5.3. AWS WAF

![api-gateway-waf](@site/docs/Frontend%20Web%20and%20Mobile/_assets/api-gateway-waf.png)

AWS WAF(Web Application Firewall)는 SQL 인젝션, 크로스 사이트 스크립팅(XSS), 다른 악의적인 공격 같은 일반적인 웹 공격으로부터 API를 보호하도록 설계되었습니다. IP 주소, 요청 패턴, 속도 제한 같은 기준을 기반으로 원하지 않는 트래픽을 필터링하거나 차단하는 커스터마이징 가능한 규칙을 정의할 수 있게 해줍니다.

API Gateway에서 AWS WAF는 REST API와 통합되어 첫 번째 방어선 역할을 합니다. 활성화되면 WAF는 다른 접근 제어(리소스 정책이나 IAM 권한 등)가 적용되기 전에 정의된 규칙에 대해 들어오는 요청을 평가합니다. 이 통합은 엣지에서 악의적인 트래픽을 차단함으로써 공격을 완화하는 데 도움을 줍니다. 그러나 HTTP API는 AWS WAF에 대한 네이티브 지원을 제공하지 않습니다.

**HTTP API를 위한 대안:**
HTTP API를 보호하려면 AWS WAF와 통합되는 Amazon CloudFront 배포로 앞단을 구성하거나 (Lambda 함수 같은) 커스텀 보안 솔루션을 배포해 유사한 규칙을 시행할 수 있습니다.

**실제 사용 사례:**
- **퍼블릭 대면 API:** 그렇지 않으면 가용성이나 성능에 영향을 미칠 수 있는 자동화된 공격과 웹 공격으로부터 API 엔드포인트를 보호합니다.
- **엔터프라이즈 애플리케이션:** WAF를 사용해 엄격한 보안 정책을 시행하고 악의적인 소스로부터의 트래픽을 차단해 정당한 사용자를 위한 신뢰할 수 있는 서비스를 보장합니다.

### 6.1. IAM 권한 부여

IAM 권한 부여는 API에 대한 접근을 제어하기 위해 AWS Identity and Access Management(IAM)를 활용합니다. IAM 정책을 사용하면 어떤 사용자, 그룹, 또는 역할이 API를 관리하거나 호출할 권한을 가지는지 정의할 수 있어, 승인된 신원만 리소스와 상호 작용할 수 있도록 보장합니다.

API Gateway에서 IAM은 두 가지 별개의 시나리오에서 사용됩니다.
- **관리 접근:** REST API의 경우 개발자는 API 리소스를 생성, 배포, 관리하기 위한 올바른 IAM 권한을 가지고 있어야 합니다.
- **실행 접근:** REST와 HTTP API 모두 클라이언트가 API를 호출하기 전에 `execute-api` 권한을 포함하는 유효한 자격 증명으로 요청에 서명해야 합니다(HTTP API의 경우 SigV4 사용).
    이 이중 모델은 API를 관리할 수 있는 사람과 호출할 수 있는 사람에 대한 세밀한 제어를 가능하게 합니다.

**실제 사용 사례:**
- **내부 애플리케이션:** 엄격한 IAM 정책을 시행해 내부 대시보드와 관리 인터페이스를 보호합니다.
- **서비스 간 통신:** 백엔드 서비스가 필요한 IAM 자격 증명을 가지고 있을 때만 API를 호출하도록 보장해, 민감한 작업을 무단 접근으로부터 보호합니다.

### 6.2. 리소스 정책

리소스 정책은 API에 직접 첨부되는 JSON 정책 문서로, 어떤 principal, IP 범위, 또는 VPC가 API에 접근할 수 있는지 정의합니다. API 리소스 수준에서 네트워크와 신원 제한을 부과함으로써 추가적인 보안 계층을 더합니다.

REST API의 경우 리소스 정책을 사용하면 소스 IP, AWS 계정, VPC, 또는 VPC 엔드포인트를 기반으로 API에 대한 접근을 명시적으로 허용하거나 거부할 수 있습니다. 이 세밀한 제어는 Private API에 특히 유용합니다. 그러나 HTTP API는 리소스 정책을 네이티브로 지원하지 않습니다.

**HTTP API를 위한 대안:**
HTTP API의 경우 IAM 권한 부여를 외부 네트워크 수준 제어(예: AWS WAF를 사용하는 CloudFront)와 결합하거나 유사한 제한을 달성하기 위해 커스텀 권한 부여자를 구현할 수 있습니다.

**실제 사용 사례:**

- **Private API:** 특정 VPC나 IP 범위로 접근을 제한해 신뢰할 수 있는 엔터티만 API 엔드포인트에 도달할 수 있도록 보장합니다.
- **다중 테넌트 환경:** 리소스 정책을 사용해 서로 다른 클라이언트나 사업 단위 간 접근을 분리해 엄격한 경계를 시행합니다.
### 6.3. Amazon Cognito

![api-gateway-cognito](@site/docs/Frontend%20Web%20and%20Mobile/_assets/api-gateway-cognito.png)

Amazon Cognito는 관리형 사용자 인증을 제공해, 사용자 풀을 통해 API에 대한 접근을 제어할 수 있게 해줍니다. 신원과 접근 토큰을 사용해 사용자가 가입하고, 로그인하고, 세션을 관리할 수 있는 안전한 방법을 제공합니다.

API Gateway는 REST와 HTTP API 모두에 대해 Amazon Cognito와 통합됩니다. REST API의 경우 Cognito 사용자 풀 권한 부여자를 생성해 API 메서드에 첨부합니다. HTTP API는 일반적으로 Cognito가 발급한 토큰을 검증하는 JWT 권한 부여자를 활용합니다. 두 경우 모두 사용자가 인증되면 (신원 또는 접근) 토큰이 API 요청을 승인하는 데 사용됩니다.
두 API 유형 모두 이 통합을 지원하므로 특별한 대안이 필요하지 않습니다 — 다만 HTTP API는 JWT 권한 부여자를 통한 구성이 필요합니다.

**실제 사용 사례:**
- **소비자 애플리케이션:** 확장 가능하고 즉시 사용 가능한 사용자 관리 시스템으로 모바일과 웹 애플리케이션을 보호합니다.
- **소셜 로그인 통합:** 사용자가 Cognito와 통합된 인기 있는 신원 공급자를 통해 인증할 수 있게 해, 접근 제어를 간소화합니다.

### 6.4. AWS Lambda 함수를 사용한 커스텀 권한 부여

![api-gateway-lambda-auth](@site/docs/Frontend%20Web%20and%20Mobile/_assets/api-gateway-lambda-auth.png)

AWS Lambda 함수(Lambda 권한 부여자)를 사용한 커스텀 권한 부여는 특정 비즈니스 로직에 맞춤화된 맞춤형 인증과 접근 제어 전략을 구현할 수 있게 해줍니다. Lambda 함수는 들어오는 요청을 처리하고, 토큰이나 파라미터를 검증하고, 접근을 허용할지 거부할지 지시하는 IAM 정책을 반환합니다.

REST와 HTTP API 모두 커스텀 Lambda 권한 부여자를 지원합니다. REST API에서는 권한 부여자가 요청이 백엔드 통합에 도달하기 전에 접근을 관리하기 위해 직접 통합됩니다. HTTP API에서는 Lambda 권한 부여자가 요청 헤더, 쿼리 문자열, 다른 신원 소스의 유연한 처리를 제공합니다. 일반적인 워크플로는 권한 부여자가 요청 세부 사항을 받고, (필요하면 외부 신원 공급자 호출을 포함해) 검증을 수행하고, API Gateway가 시행하는 정책을 반환하는 것을 포함합니다.

**실제 사용 사례:**
- **비표준 인증:** (Cognito나 IAM 같은) 기본 메커니즘이 요구를 충족하지 못할 때 — 예를 들어 레거시 시스템과 통합하거나 커스텀 토큰을 처리할 때 — Lambda 권한 부여자는 필요한 유연성을 제공합니다.
- **서드파티 통합:** 접근을 부여하기 전에 외부 신원 공급자나 데이터베이스에 대한 검증이 필요한 API를 보호합니다.

### 6.5. JSON Web Token(JWT) 권한 부여

JWT 권한 부여는 압축되고 URL에 안전한 형식으로 인증 클레임을 전달하기 위해 JSON Web Token을 사용합니다. 이 접근 방식은 OpenID Connect(OIDC)와 OAuth 2.0 같은 현대적인 인증 프레임워크에서 인기 있으며, 서버 측 세션을 유지하지 않고도 클라이언트 신원의 상태 비저장(stateless) 검증을 가능하게 합니다.

API Gateway의 HTTP API는 JWT 권한 부여를 네이티브로 지원합니다. 라우트가 JWT 권한 부여자로 구성되면 API Gateway는 구성에 대해 토큰의 서명과 클레임(발급자, 대상, 만료, 범위 등)을 자동으로 검증합니다. 반면 REST API는 내장 JWT 지원을 제공하지 않습니다.

**REST API를 위한 대안:**
JWT 기반 보안이 필요한 REST API의 경우 JWT를 디코딩하고 검증하는 Lambda 권한 부여자를 구현해, HTTP API에서 발견되는 네이티브 동작을 모방할 수 있습니다.

**실제 사용 사례:**

- **현대적인 웹과 모바일 앱:** JWT는 토큰 기반 사용자 세션에 의존하는 애플리케이션의 인증을 단순화해, 상태 저장 서버 관리의 필요성을 줄여줍니다.
- **마이크로서비스 아키텍처:** JWT를 통한 상태 비저장 토큰 검증은 각 서비스가 독립적으로 클라이언트 신원을 검증하는 확장 가능하고 분산된 API 생태계를 가능하게 합니다.

### 7.1. 커스텀 도메인

커스텀 도메인 이름을 사용하면 기본으로 자동 생성된 API Gateway 엔드포인트(예: `https://api-id.execute-api.region.amazonaws.com/stage`)를 `https://api.example.com/myservice` 같은 브랜드화되고 기억하기 쉬운 URL로 대체할 수 있습니다. 이는 사용자 경험을 개선하고 API의 아이덴티티를 강화합니다.

API를 배포한 후 커스텀 도메인과 기본 경로를 API 엔드포인트에 매핑할 수 있습니다. API Gateway는 Edge-optimized와 Regional 커스텀 도메인을 모두 지원합니다. 커스텀 도메인을 사용하지 않고 API에 접근하려고 시도하면 클라이언트가 `403 Forbidden` 오류를 받도록 기본 엔드포인트를 비활성화할 수도 있습니다. 추가 구성에는 DNS 레코드 업데이트와 TLS 통신을 위한 보안 정책 선택이 포함됩니다. 사실상 무제한 개수의 서브도메인을 지원하기 위한 와일드카드 커스텀 도메인 이름도 사용할 수 있습니다.

**실제 사용 사례:**

- **브랜드화된 서비스:** 기업들은 전문적인 외관을 제공하고 사용자 신뢰를 개선하기 위해 커스텀 도메인을 사용합니다.
- **다중 테넌트 플랫폼:** 와일드카드 도메인(예: `*.example.com`)은 서비스 제공자가 각 테넌트나 고객에 대해 고유한 서브도메인으로 트래픽을 라우팅할 수 있게 해줍니다.

**추가 고려 사항:**

- 커스텀 도메인 이름은 모든 계정에 걸쳐 AWS 리전 내에서 고유해야 합니다.
- 사전 조건에는 (Route 53이나 다른 등록 기관을 통한) 도메인 등록과 AWS Certificate Manager(ACM)의 SSL/TLS 인증서 또는 API Gateway로 가져온 인증서가 포함됩니다.
- Edge-optimized와 Regional 엔드포인트 간 마이그레이션이 지원됩니다 — 다만 퍼블릭과 프라이빗 커스텀 도메인은 서로 교환할 수 없다는 점에 유의하세요.

### 7.2. API 키

API 키는 API가 어떻게 사용되는지 추적하고 제어할 수 있게 해주는 영숫자 식별자입니다. 애플리케이션 개발자에게 배포되어 접근을 제한하고 스로틀링과 할당량 제한이 있는 사용 계획을 적용합니다.

REST API의 경우 API 키는 사용 계획과 통합됩니다. 개별 API 메서드가 API 키를 요구하도록 구성하고, 키를 생성하거나 가져와서, 스로틀링 속도와 할당량 제한을 정의하는 사용 계획에 첨부할 수 있습니다. 이를 통해 사용량을 모니터링하고, 제한을 시행하고, 심지어 API를 제품화된 서비스로 제공할 수 있습니다. 그러나 HTTP API는 API 키를 네이티브로 지원하지 않습니다.

**HTTP API를 위한 대안:**
HTTP API에서 유사한 기능이 필요하다면 애플리케이션이 생성하는 토큰을 검증하기 위한 (예를 들어 Lambda 권한 부여자를 사용한) 커스텀 권한 부여 구현이나 사용 정책을 외부적으로 시행하는 서드파티 API 관리 솔루션을 고려하세요.

**실제 사용 사례:**

- **API 제품화:** API 키를 사용하면 접근과 사용량을 제어하면서 파트너나 고객에게 API를 제공할 수 있습니다.
- **사용량 모니터링:** 소비 지표를 추적하고 속도 제한 같은 비즈니스 규칙을 시행할 수 있습니다.

### 7.3. 클라이언트별 속도 제한

클라이언트별 속도 제한을 사용하면 단일 클라이언트가 주어진 기간 내에 만들 수 있는 API 요청 수를 제한하는 스로틀링 규칙을 설정할 수 있습니다. 이는 어느 한 클라이언트에 의해 API가 압도되지 않도록 보호합니다.

REST API에서 클라이언트별 속도 제한은 사용 계획의 일부로 구성되며 클라이언트와 연결된 API 키를 기반으로 적용됩니다. API Gateway는 정상 상태 요청 속도와 버스트를 모두 관리하기 위해 토큰 버킷 알고리즘을 사용합니다. HTTP API는 API 키 지원이 없으므로 네이티브 클라이언트별 속도 제한을 제공하지 않습니다.

**HTTP API를 위한 대안:**
HTTP API의 경우 다음을 통해 속도 제한을 구현할 수 있습니다.

- 클라이언트 요청 속도를 추적하는 Lambda 권한 부여자 배포, 또는
- 클라이언트별 제한을 시행하기 위한 외부 솔루션(예: CloudFront나 서드파티 API 관리 도구) 사용.

**실제 사용 사례:**

- **공정한 사용 시행:** 어느 한 클라이언트가 API 리소스를 독점하지 못하도록 방지해 모든 사용자를 위한 서비스 품질을 보장합니다.
- **비용 관리:** 과다 사용을 제한함으로써 리소스 사용을 제어하고 예상치 못한 요금을 피하는 데 도움을 줍니다.

### 7.4. 클라이언트별 사용량 스로틀링

클라이언트별 사용량 스로틀링을 사용하면 클라이언트별로 스로틀링 한도(토큰이 보충되는 속도)와 할당량(허용되는 최대 요청 수)을 모두 정의할 수 있습니다. 이 세밀한 제어는 부하를 관리하고 각 클라이언트가 허용 가능한 한도 내에 머물도록 보장하는 데 필수적입니다.

REST API에서 사용 계획은 API 키가 API 스테이지 전반에서 요청 수를 집계하는 데 사용되는 클라이언트별 스로틀링을 지원합니다. 이를 통해 서로 다른 클라이언트나 제품에 맞게 속도 제한과 할당량을 맞춤화할 수 있습니다. HTTP API의 경우 API 키와 사용 계획이 네이티브로 사용 가능하지 않으므로 클라이언트별 사용량 스로틀링은 즉시 사용 가능한 상태로 지원되지 않습니다.

**HTTP API를 위한 대안:**
HTTP API에서 클라이언트별 사용량 스로틀링을 모방하려면 다음을 할 수 있습니다.

- 클라이언트 요청을 검사하고 카운트하기 위해 커스텀 Lambda 권한 부여자 사용, 또는
- 추가적인 속도 제한 기능을 지원하는 CloudFront와 API 통합, 또는
- 사용 제한을 시행하기 위한 외부 API 관리 서비스 활용.

**실제 사용 사례:**

- **고객 계층화:** 서로 다른 클라이언트나 구독 계획에 다양한 할당량과 스로틀링 임계값을 제공할 수 있습니다.
- **API 수익화:** 더 높은 계층이 더 높은 한도를 누리는 유료 서비스 계층을 시행할 수 있게 해줍니다.

### 8.1. CORS 구성

교차 출처 리소스 공유(CORS)는 서버의 리소스가 서로 다른 도메인 전반에서 어떻게 공유되는지 제어하는 브라우저 보안 표준입니다. 한 도메인에 호스팅된 웹 애플리케이션이 엄격한 보안 제어를 유지하면서 다른 도메인의 리소스를 안전하게 요청할 수 있도록 보장합니다.

API Gateway에서는 API 수준에서 CORS를 활성화해 다른 출처로부터 엔드포인트가 호출될 수 있게 할 수 있습니다. REST API의 경우 일반적으로 목업 통합으로 `OPTIONS` 메서드를 구성하거나 필요한 응답 헤더를 자동으로 생성하는 AWS Management Console의 내장 CORS 활성화를 사용합니다. HTTP API에서는 CORS를 라우트에서 더 직접적으로 구성할 수 있어 프로세스가 단순화됩니다. 두 경우 모두 프록시든 비프록시든 통합이 `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` 같은 적절한 헤더를 반환하도록 보장해야 합니다.

**실제 사용 사례:**
- **웹 애플리케이션:** 한 도메인에 호스팅된 브라우저 기반 애플리케이션이 안전하게 API를 소비할 수 있게 합니다.
- **모바일 백엔드 서비스:** 모바일 앱이 클라우드 호스팅 API에 연결할 때 크로스 도메인 요청을 가능하게 합니다.

### 8.2. 테스트 호출

테스트 호출을 사용하면 개발자가 API Gateway 콘솔 내에서 API 호출을 시뮬레이션할 수 있습니다. 이 기능은 API를 외부적으로 배포하지 않고도 디버깅과 메서드 구성 검증에 특히 유용합니다.

REST API의 경우 API Gateway 콘솔에는 쿼리 파라미터, 헤더, 요청 본문을 지정할 수 있는 테스트 호출 기능이 포함되어 있습니다. 그런 다음 콘솔은 상태 코드, 헤더, 본문을 포함한 전체 응답을 시뮬레이션된 CloudWatch 로그 출력과 함께 표시합니다. 반면 HTTP API는 내장 테스트 호출을 지원하지 않습니다. 대신 HTTP API 엔드포인트를 검증하기 위해 Postman, curl, 또는 자동화된 테스트 스크립트 같은 외부 도구를 사용해야 합니다.

**실제 사용 사례:**
- **빠른 디버깅:** 개발 중 메서드나 통합 설정 변경을 신속하게 테스트합니다.
- **통합 검증:** 백엔드가 올바른 파라미터를 받고 응답 형식이 기대치와 일치하는지 확인합니다.

### 8.3. 캐싱

![api-gateway-cache](@site/docs/Frontend%20Web%20and%20Mobile/_assets/api-gateway-cache.png)

API Gateway의 캐싱은 통합의 응답을 일시적으로 저장함으로써 백엔드 부하를 줄이고 응답 시간을 개선하는 데 도움을 줍니다. 캐시된 응답은 클라이언트에게 직접 제공되어 지연 시간을 줄이고 비용을 낮춥니다.

REST API의 경우 전용 캐시 인스턴스를 프로비저닝함으로써 스테이지 수준 캐싱을 활성화할 수 있습니다. 메서드별로 캐싱 동작을 세밀하게 조정하고 (헤더나 쿼리 문자열 같은) 파라미터를 캐시 키로 사용할 수 있습니다. 그러나 HTTP API는 네이티브 캐싱 지원을 제공하지 않습니다.

**대안:**
HTTP API의 경우 Amazon CloudFront로 API의 앞단을 구성해 캐싱 기능을 활용하거나 백엔드 서비스에서 캐싱을 구현하는 것을 고려하세요.

**실제 사용 사례:**
- **정적이거나 자주 변경되지 않는 데이터:** 모든 요청에서 변경되지 않는 데이터를 반환하는 엔드포인트의 성능을 개선합니다.
- **비용 최적화:** 트래픽이 많은 기간 동안 백엔드 서비스로의 호출 수를 줄입니다.

### 8.4. 사용자 제어 배포

사용자 제어 배포는 API 변경 사항이 언제 어떻게 라이브로 전환되는지 관리하는 완전한 권한을 제공합니다. `dev`, `test`, `prod` 같은 스테이지에 API 구성을 매핑하는 배포를 생성해, 엄격한 버전 관리와 통제된 롤아웃을 가능하게 합니다.

REST와 HTTP API 모두 사용자 제어 배포를 지원합니다. REST API의 경우 기존 스테이지를 업데이트하거나 새 스테이지를 만들기 위해 변경 사항을 수동으로 다시 배포합니다. HTTP API도 유사한 접근 방식을 따라, 명명된 스테이지에 배포하고 클라이언트가 올바른 기본 URL을 사용하도록 보장할 수 있습니다.

**실제 사용 사례:**
- **버전 관리:** 여러 API 버전을 동시에 관리하고 검증되면 테스트 스테이지에서 프로덕션으로 변경 사항을 승격합니다.
- **변경 관리:** 중요한 업데이트의 롤아웃을 제어해 완전히 테스트된 변경 사항만 최종 사용자에게 릴리스되도록 보장합니다.

### 8.5. 자동 배포

자동 배포는 수동 재배포 없이도 API에 대한 변경 사항을 즉시 게시함으로써 개발 프로세스를 간소화합니다. 이 접근 방식은 수동 업데이트의 다운타임과 운영 오버헤드를 줄여줍니다.

HTTP API는 구성 변경이 즉시 기본 스테이지에 적용되는 자동 배포를 지원합니다. 반면 REST API는 업데이트 후 수동 재배포가 필요해, 더 세밀한 제어를 제공하지만 추가적인 운영 단계도 필요로 합니다.

**REST API를 위한 대안:**
변경 시 재배포를 자동화하기 위해 배포 프로세스를 CI/CD 파이프라인(예: AWS CodePipeline 사용)과 통합하는 것을 고려하세요.

**실제 사용 사례:**
- **신속한 반복:** 더 빠른 피드백 루프를 위해 테스트 환경에 사소한 변경 사항을 자동으로 배포합니다.
- **지속적 통합:** 더 빠른 롤아웃과 롤백 기능을 위해 API 배포를 자동화된 워크플로에 통합합니다.

### 8.6. 커스텀 게이트웨이 응답

커스텀 게이트웨이 응답을 사용하면 요청이 실패할 때 API Gateway가 반환하는 오류 메시지와 HTTP 상태 코드를 맞춤화할 수 있습니다. 더 많은 맥락이나 사용자 친화적인 오류 메시지를 제공하기 위해 응답 헤더와 페이로드를 수정할 수 있습니다.

REST API는 API Gateway 콘솔이나 REST API를 통해 사전 정의된 응답 유형(예: `Missing Authentication Token`)을 구성함으로써 커스텀 게이트웨이 응답을 지원합니다. HTTP API는 커스텀 게이트웨이 응답에 대한 네이티브 지원을 제공하지 않습니다.

**HTTP API를 위한 대안:**
HTTP API에서 커스텀 응답을 모방하려면 클라이언트에 도달하기 전에 오류 메시지를 가로채고 포맷하기 위해 Lambda 권한 부여자나 백엔드 오류 처리를 사용할 수 있습니다.

**실제 사용 사례:**
- **향상된 개발자 경험:** API 소비자를 위해 명확하고 실행 가능한 오류 메시지를 제공해 디버깅 시간을 줄입니다.
- **브랜드 일관성:** 조직의 스타일과 로깅 요구 사항에 맞게 오류 형식을 커스터마이징합니다.

### 8.7. 카나리 릴리스 배포

카나리 릴리스 배포를 사용하면 새 API 버전을 점진적으로 롤아웃할 수 있습니다. 트래픽의 작은 비율이 업데이트된 버전으로 향하는 동안 대부분은 계속 안정적인 프로덕션 릴리스를 사용해 위험을 최소화합니다.

REST API에서는 카나리 설정을 배포 스테이지에 적용해 새 버전으로 라우팅되는 트래픽의 비율을 제어할 수 있습니다. HTTP API는 현재 내장된 카나리 릴리스 기능을 지원하지 않습니다.

**HTTP API를 위한 대안:**
HTTP API의 경우 (Route 53이나 CloudFront와 함께) AWS Lambda를 통한 가중치 기반 라우팅을 활용하거나 스테이지 변수와 별도의 배포를 통해 트래픽 분할을 수동으로 제어함으로써 카나리 릴리스를 시뮬레이션할 수 있습니다.

**실제 사용 사례:**
- **위험 완화:** 전체 롤아웃 전에 성능과 사용자 피드백을 모니터링할 수 있도록 새 기능을 사용자의 일부에게 점진적으로 노출합니다.
- **A/B 테스트:** 대다수 사용자에게 영향을 주지 않고 프로덕션에서 두 API 버전 간 동작을 비교합니다.

### 8.8. 요청 검증

API Gateway의 요청 검증을 사용하면 요청이 처리되기 전에 들어오는 API 요청이 (null이 아닌 파라미터나 JSON 스키마 준수 같은) 사전 정의된 요구 사항을 충족하는지 확인할 수 있습니다. 이는 초기에 오류를 잡는 데 도움을 주고 불필요한 백엔드 호출을 줄입니다.

REST API의 경우 모델과 필수 파라미터에 대해 쿼리 문자열, 헤더, 본문 콘텐츠를 확인하는 요청 검증자를 정의할 수 있습니다. HTTP API는 내장 요청 검증을 제공하지 않으므로 필요하면 백엔드나 Lambda 함수를 통해 검증을 구현해야 합니다.

**실제 사용 사례:**
- **오류 방지:** 잘못된 형식의 요청을 조기에 잡아 백엔드 시스템의 부하를 줄입니다.
- **개발자 안내:** API 소비자에게 요청에서 기대되는 것에 대한 명확한 피드백을 제공합니다.

### 8.9. 요청 파라미터 변환

요청 파라미터 변환을 사용하면 백엔드에 도달하기 전에 들어오는 API 요청을 수정할 수 있습니다. 이는 백엔드 기대치를 충족하거나 추가적인 맥락을 더하기 위해 헤더, 쿼리 문자열, 또는 경로 변수를 변경하는 것을 포함할 수 있습니다.

REST API의 경우 요청 파라미터를 변환하기 위해 Velocity Template Language(VTL)로 작성된 매핑 템플릿을 사용합니다. HTTP API는 VTL이 필요 없이 (헤더, 쿼리 문자열, 경로에 대한) 변환 규칙을 직접 지정할 수 있는 더 간단한, 선언적인 파라미터 매핑 메커니즘을 제공합니다.

**실제 사용 사례:**
- **백엔드 적응:** 외부 API 형식을 레거시 백엔드가 기대하는 형식으로 변환합니다.
- **보안과 정규화:** 처리 전에 민감한 헤더를 제거하거나 파라미터 이름을 표준화합니다.

### 8.10. 요청 본문 변환

요청 본문 변환을 사용하면 클라이언트에서 보낸 페이로드가 통합 백엔드에 도달하기 전에 형식이나 구조를 변경할 수 있습니다. 이 변환은 클라이언트 측 데이터 형식과 백엔드 기대치 간의 차이를 조화시키는 데 도움을 줄 수 있습니다.

REST API에서는 요청 본문을 재형식화하거나 재구성하기 위해 (VTL을 사용해) 매핑 템플릿을 정의할 수 있습니다. 이는 JSON 데이터 구조 변환이나 모델 스키마를 기반으로 특정 값 추출을 포함할 수 있습니다. HTTP API는 네이티브 요청 본문 변환을 지원하지 않습니다.

**HTTP API를 위한 대안:**
HTTP API의 경우 Lambda 통합에서 변환 로직을 구현하거나 여러 데이터 형식을 직접 처리하도록 백엔드를 조정할 수 있습니다.

**실제 사용 사례:**
- **레거시 통합:** 클라이언트가 데이터 형식을 변경하도록 강요하지 않고 들어오는 요청을 오래된 백엔드 시스템이 요구하는 형식에 맞춥니다.
- **데이터 강화:** 처리 전에 요청 페이로드의 데이터 필드를 자동으로 추가, 제거, 또는 수정합니다.

### 9.1. Amazon CloudWatch 지표

Amazon CloudWatch 지표는 API 실행을 모니터링하는 거의 실시간에 가까운 데이터를 제공합니다. 1분 간격의 자동 수집과 15개월의 과거 데이터 보존을 통해, 이 지표들은 API 성능, 응답성, 리소스 활용에 대한 상세한 뷰를 제공합니다.

REST와 HTTP API 모두 CloudWatch 지표와 통합됩니다. API Gateway는 **Latency**, **IntegrationLatency**, **CacheHitCount**, **CacheMissCount** 같은 핵심 성능 지표를 기록합니다. 이 지표들은 백엔드 응답성과 전체적인 API 효율성을 짚어내는 데 도움을 주어, 캐싱, 확장, 문제 해결 전략에서 데이터 기반 조정을 할 수 있게 해줍니다.

**실제 사용 사례:**
- **성능 튜닝:** 지연 시간 지표를 모니터링해 느린 통합을 식별하고 그에 따라 구성을 조정합니다.
- **용량 계획:** 과거 데이터를 활용해 트래픽 추세를 예측하고 확장을 준비합니다.
- **운영 통찰:** 캐시 히트/미스 통계를 사용해 리소스 사용을 최적화하고 응답 시간을 개선합니다.

### 9.2. CloudWatch Logs로의 접근 로그

CloudWatch Logs로의 접근 로깅은 클라이언트 신원, 요청 경로, 응답 세부 사항을 포함한 API 호출에 대한 상세한 정보를 캡처합니다. 이 로그들은 디버깅, 보안 감사, 규정 준수 모니터링에 매우 중요합니다.

API Gateway는 두 가지 로깅 유형을 지원합니다.

- **실행 로깅:** 오류 메시지, 요청/응답 세부 사항, Lambda 권한 부여자의 추적을 기록하는 자동으로 관리되는 로그.
- **접근 로깅:** 누가 API에 접근했고 어떻게 했는지 기록하는 커스터마이징 가능한 로그. [$context](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-mapping-template-reference.html#context-variable-reference) 변수를 사용해 형식(예: CLF, JSON, XML, CSV)을 정의할 수 있습니다.
    REST와 HTTP API 모두 이 로그를 CloudWatch로 보낼 수 있으며, 민감한 세부 사항(인증 헤더와 API 키 등)은 자동으로 마스킹됩니다.

**실제 사용 사례:**
- **디버깅:** 로그를 분석해 오류와 비정상적인 요청 패턴을 신속하게 식별합니다.
- **규정 준수:** 규제와 보안 표준을 충족하기 위해 감사 추적을 유지합니다.
- **사용량 분석:** 클라이언트 접근 추세를 모니터링하고 그에 따라 API 성능 설정을 조정합니다.

### 9.3. Amazon Data Firehose로의 접근 로그

Amazon Data Firehose로의 로깅을 사용하면 API 로그를 Firehose로 직접 스트리밍할 수 있어, 데이터 웨어하우스, 분석 플랫폼, 또는 시각화 도구로 거의 실시간에 가깝게 수집될 수 있습니다.

REST API의 경우 API Gateway는 구성된 Firehose 전달 스트림으로 접근 로그를 직접 보낼 수 있습니다. 이는 고급 로그 분석과 비즈니스 인텔리전스 도구와의 원활한 통합을 용이하게 합니다. 반면 HTTP API는 Data Firehose로의 로깅을 네이티브로 지원하지 않습니다.

**대안:**
HTTP API의 경우 접근 세부 사항을 CloudWatch Logs에 로깅한 다음 CloudWatch에서 로그를 가져오도록 Firehose 전달 스트림을 설정할 수 있습니다. 이 간접적인 접근 방식은 직접적인 Firehose 통합을 복제합니다.

**실제 사용 사례:**
- **실시간 분석:** 로그 데이터를 분석 시스템으로 스트리밍해 운영 이상 징후를 즉시 식별하고 대응합니다.
- **중앙화된 로깅:** 통합 모니터링과 장기 추세 분석을 위해 여러 소스의 로그를 집계합니다.
- **자동화된 알림:** 스트리밍된 데이터를 사용해 비정상적인 패턴이나 오류가 감지되면 알림을 트리거합니다.

### 9.4. AWS X-Ray 추적

AWS X-Ray 추적은 API와 그 백엔드 서비스를 통과하는 요청의 전체 여정을 시각화하는 분산 추적을 제공합니다. 이 추적 기능은 마이크로서비스와 통합 전반에서 성능 문제를 진단하고 병목 현상을 짚어내는 데 필수적입니다.

REST API의 경우 API Gateway는 다양한 서비스 전반에서 요청을 추적하기 위해 X-Ray와 네이티브로 통합되어, API 성능에 대한 엔드투엔드 뷰를 제공합니다. X-Ray의 서비스 맵은 지연 시간 문제를 식별하고 백엔드 상태를 모니터링하는 데 도움을 줍니다. 그러나 HTTP API는 네이티브 X-Ray 통합이 없습니다.

**대안:**
HTTP API로 유사한 추적을 달성하려면 Lambda 통합을 통한 커스텀 계측을 구현하거나 트레이스 데이터를 X-Ray로 전달하는 클라이언트 측 추적 라이브러리를 사용하는 것을 고려하세요.

**실제 사용 사례:**

- **지연 시간 분석:** 성능을 최적화하기 위해 요청 흐름에서 느린 구간을 식별합니다.
- **마이크로서비스 모니터링:** 서로 다른 서비스가 어떻게 상호 작용하고 어디서 지연이 발생하는지에 대한 통찰을 얻습니다.
- **근본 원인 분석:** 상세한 트레이스 데이터를 사용해 백엔드 문제를 신속하게 조사하고 해결합니다.

## 10. REST API 통합 유형

API Gateway REST API는 API 메서드를 다양한 백엔드 엔드포인트에 연결하기 위해 여러 통합 유형을 지원합니다. 통합 유형 선택은 백엔드의 특성(예: Lambda 함수, HTTP 엔드포인트, 또는 AWS 서비스)과 API Gateway와 통합 엔드포인트 간에 데이터가 전달되는 방식에 따라 달라집니다.

아래는 지원되는 통합 유형, 그 엔드포인트 대상, 매핑 요구 사항, 핵심 특성을 개괄하는 요약 표입니다.

|통합 유형|대상 엔드포인트|매핑 필요?|핵심 특성|
|---|---|---|---|
|**AWS**|AWS 서비스 작업(Lambda 커스텀 포함)|예|AWS 서비스 작업을 노출; 요청과 응답의 커스텀 매핑 필요.|
|**AWS_PROXY**|Lambda 함수(프록시 통합)|아니오|Lambda 함수와의 간소화된 직접 통합; 전체 클라이언트 요청을 직접 전달. 대부분의 Lambda 사용 사례에 권장됨.|
|**HTTP**|HTTP 엔드포인트(커스텀 통합)|예|데이터 형식을 변환하기 위한 통합 요청/응답 매핑 구성 필요.|
|**HTTP_PROXY**|HTTP 엔드포인트(프록시 통합)|아니오|HTTP 엔드포인트와의 직접적인 통과 통합; 최소한의 구성.|
|**MOCK**|시뮬레이션된 엔드포인트|해당 없음|요청을 전달하지 않고 응답을 생성; 테스트, CORS 지원, 시뮬레이션에 유용.|

### 10.1. AWS 통합(Lambda 커스텀 통합 포함)

이 통합 유형은 API Gateway를 통해 AWS 서비스 작업을 노출하는 데 사용됩니다. 메서드 요청과 백엔드 서비스 요청 간을 변환하고 백엔드 응답을 클라이언트로 다시 매핑하는 매핑 템플릿으로 통합 요청과 통합 응답 모두를 구성해야 합니다.

**Lambda 커스텀 통합:**
통합 엔드포인트가 Lambda 함수의 호출 작업인 AWS 통합의 특수한 경우입니다. 이 접근 방식은 유사한 입력과 출력 데이터 형식을 공유하는 여러 엔드포인트 전반에서 구성된 매핑 템플릿의 재사용을 가능하게 합니다. 커스텀 데이터 변환이 필요한 고급 애플리케이션 시나리오에 가장 적합합니다.

**프로그래밍 방식 구성:**
Integration 리소스의 `type` 속성을 `AWS`로 설정합니다.

### 10.2. AWS_PROXY(Lambda 프록시 통합)

AWS_PROXY는 Lambda 함수와의 통합을 위한 간소화된 설정을 제공합니다. 이 통합을 사용하면 API Gateway는 (헤더, 경로 변수, 쿼리 문자열 파라미터, 본문을 포함한) 전체 클라이언트 요청을 자동으로 Lambda 함수로 직접 전달합니다. Lambda 함수는 입력을 처리하고 적절하게 형식화된 응답을 반환할 책임이 있습니다.

**핵심 이점:**
- 별도의 매핑 템플릿을 설정할 필요가 없어 최소한의 구성.
- API Gateway 설정 변경 없이도 통합이 백엔드와 함께 진화할 수 있게 해줍니다.
- 대부분의 Lambda 함수 통합에 강력히 권장됩니다.

**프로그래밍 방식 구성:**
`type` 속성을 `AWS_PROXY`로 설정합니다.

### 10.3. HTTP 통합(HTTP 커스텀 통합)

이 통합 유형은 클라이언트 요청과 백엔드 간에 데이터가 변환되는 방식에 대한 제어가 필요한 HTTP 엔드포인트에 연결하는 데 사용됩니다. HTTP(커스텀) 통합을 사용하면 매핑 템플릿을 정의함으로써 통합 요청과 통합 응답 모두를 구성해야 합니다. 이를 통해 특정 요구 사항에 따라 데이터 형식을 맞춤화할 수 있습니다.

**프로그래밍 방식 구성:**
`type` 속성을 `HTTP`로 설정합니다.

### 10.4. HTTP_PROXY(HTTP 프록시 통합)

HTTP_PROXY는 HTTP 엔드포인트와의 직접적이고 간소화된 통합을 제공합니다. 이 모드에서는 API Gateway가 전체 클라이언트 요청을 백엔드 HTTP 엔드포인트로 직접 전달하고 매핑 구성 없이 응답을 클라이언트로 다시 전달합니다. 이 간소화된 접근 방식은 백엔드가 들어오는 요청 형식을 네이티브로 처리할 수 있을 때 이상적입니다.

**프로그래밍 방식 구성:**
`type` 속성을 `HTTP_PROXY`로 설정합니다.

### 10.5. MOCK 통합

MOCK 통합을 사용하면 API Gateway가 백엔드로 요청을 보내지 않고도 응답을 생성할 수 있습니다. 이는 다음과 같은 경우에 특히 유용합니다.

- 백엔드 비용을 발생시키지 않고 API 구성을 테스트하는 경우.
- 협업 개발 중 API 동작을 시뮬레이션하는 경우.
- 프리플라이트 요청에 대해 CORS 관련 헤더나 기본 응답(예: OPTIONS 메서드)을 반환하는 경우.

**프로그래밍 방식 구성:**
`type` 속성을 `MOCK`으로 설정합니다.

## 11. 한도와 할당량

### 11.1. 스로틀 할당량

- **한도:** 리전당 각 계정은 최대 **5,000건**의 버스트 용량으로 **초당 10,000건의 요청**을 처리할 수 있습니다. 일부 리전(예: 아프리카(케이프타운), 유럽(밀라노))은 더 낮은 기본값(2,500 RPS와 1,250 버스트)을 가진다는 점에 유의하세요.
- **대안:**
    - **트래픽 분산:** 더 높은 한도를 활용하기 위해 여러 리전에 트래픽을 분산하는 것을 고려하세요.
    - **캐싱 전략:** API Gateway의 부하를 줄이기 위해 (예: Amazon CloudFront와) 캐싱을 사용하세요.
    - **속도 제한과 백오프:** 클라이언트 측 스로틀링과 지수 백오프 전략을 구현하세요.

### 11.2. 권한 부여된 메서드에 대한 ARN 길이 제한

- **한도:** 권한 부여가 활성화되면 메서드의 ARN은 **1,600바이트**를 초과할 수 없습니다. 이 한도를 초과하면(종종 긴 경로 파라미터로 인해) `414 Request URI too long` 오류가 발생합니다.
- **대안:**
    - **명명 규칙 최적화:** ARN의 전체 길이를 줄이기 위해 리소스 이름과 경로 파라미터를 단축하세요.
    - **API 재구성:** 리소스를 더 효율적으로 그룹화하도록 API 경로를 재설계해 세그먼트 수나 길이를 줄이세요.
    - **파라미터 처리:** 가능한 경우 길이가 긴 데이터를 URI에서 헤더나 요청 본문으로 이동하는 것을 고려하세요.

### 11.3. API 유형별 특정 한도

#### 11.3.1 HTTP API

- **API당 라우트 수:**
    - **한도:** 최대 **300개 라우트**.
    - **대안:** 설계에 300개 이상의 라우트가 필요하면 기능별로 논리적으로 그룹화된 여러 API로 분할하는 것을 고려하세요.

- **통합 타임아웃:**
    - **한도:** 최대 **30초**.
    - **대안:**
        - 이 지속 시간을 초과하는 작업에는 비동기 처리나 백그라운드 작업 시스템(예: AWS Lambda)을 사용하세요.
        - 장기 실행 태스크를 별도의 백엔드 서비스로 오프로드하세요.

- **페이로드 크기:**
    - **한도:** 요청당 최대 **10MB**.
    - **대안:**
        - 더 큰 데이터 전송의 경우 페이로드를 Amazon S3에 업로드하고 API에 S3 URL을 전달하세요.
        - 매우 큰 파일에는 멀티파트 업로드를 활용하세요.

- **API당 스테이지 수:**
    - **한도:** **10개 스테이지**(요청 시 확장 가능).
    - **대안:**
        - 허용된 스테이지 내에서 여러 환경이나 버전을 통합하세요.
        - 추가 스테이지가 필요하면 AWS에 늘려달라고 요청하세요.

#### 11.3.2 WebSocket API

- **새 연결:**
    - **한도:** 초당 최대 **500개의 새 연결**(지원 요청을 통해 조정 가능).

- **통합 타임아웃:**
    - **한도:** **50밀리초에서 29초** 범위.
    - **대안:**
        - 타임아웃 내에 머물도록 비동기 메시징을 사용하거나 워크플로를 더 작고 관리하기 쉬운 상호 작용으로 분해하세요.

- **유휴 연결 타임아웃:**
    - **한도:** **10분**으로 고정됨.
    - **대안:**
        - 지속적인 연결성이 필요하면 연결을 유지하기 위해 킵얼라이브 메시지나 주기적인 하트비트를 구현하세요.

- **URL 길이:**
    - **한도:** **4096자**로 제한됨.
    - **대안:**
        - URL 경로를 단축하고 파라미터를 효율적으로 인코딩하세요.
        - 길이가 긴 데이터를 전달하기 위해 쿼리 파라미터나 요청 본문 사용을 고려하세요.

#### 11.3.3 REST API

- **API 정의 파일 크기:**
    - **한도:** 가져온 정의의 경우 최대 **6MB**.
    - **대안:**
        - 큰 API를 더 작고 관리하기 쉬운 구성 요소로 나눠 API 정의를 모듈화하세요.
        - 전체 파일 크기를 줄이기 위해 가능하면 외부 참조를 활용하세요.

- **API당 리소스 수:**
    - **한도:** 최대 **300개 리소스**.
    - **대안:**
        - 이 리소스 한도에 근접하면 큰 API를 여러 API로 분할하세요.
        - 가능하면 관련 리소스를 결합하도록 API 설계를 최적화하세요.

- **API당 스테이지 수:**
    - **한도:** **10개 스테이지**.
    - **대안:**
        - 여러 스테이지를 통합하기 위해 효율적인 버전 관리 전략을 사용하세요.
        - 운영 모델에 필요하면 추가 스테이지를 요청하세요.

- **API 키:**
    - **한도:** 계정당 최대 **10,000개**.
    - **대안:**
        - 키 순환과 재사용 전략을 구현하세요.
        - 필요한 키 수를 최소화하도록 접근 제어 정책을 설계하세요.

- **클라이언트 인증서:**
    - **한도:** 계정당 최대 **60개**.
    - **대안:**
        - 보안 정책이 허용하는 경우 API 간에 인증서를 공유해 인증서 사용을 최적화하세요.
        - 용량을 확보하기 위해 사용하지 않는 인증서를 모니터링하고 폐기하세요.

- **사용 계획:**
    - **한도:** 계정당 최대 **300개 사용 계획**.
    - **대안:**
        - 한도에 도달하지 않도록 가능하면 사용 계획을 통합하세요.
        - 유사한 사용 계층이나 접근 패턴을 기반으로 계획을 정리하세요.

- **통합 타임아웃:**
    - **한도:** 기본 범위 **50밀리초에서 29초**(일부 Regional API는 전체 스로틀 할당량에 영향을 미치는 확장을 제공).
    - **대안:**
        - HTTP API와 유사하게 비동기 처리를 사용하거나 장기 실행 태스크를 백그라운드 워크플로로 분리하세요.

## 12. 비용 최적화 전략

Amazon API Gateway를 활용하면서 비용을 최적화하려면 다음 모범 사례를 고려하세요.

- **적절한 API 유형 선택:**
    - **HTTP API**는 비용 효율성과 낮은 지연 시간을 위해 설계되어, REST API의 고급 기능이 필요하지 않다면 이상적입니다. 단순화된 기능 집합은 요청당 더 낮은 비용으로 이어집니다.
    - 복잡한 변환, 커스텀 권한 부여자, 또는 깊은 통합 기능 같은 광범위한 기능이 필요할 때만 **REST API**를 사용하세요.

- **캐싱을 현명하게 활용:**
    - 자주 접근하는 리소스에 캐싱을 활성화해 백엔드 서비스에 도달하는 호출 수를 줄이세요. 이는 지연 시간을 줄여 성능을 개선할 뿐만 아니라 컴퓨팅 비용도 절감합니다.
    - 캐시 메모리를 과도하게 프로비저닝하지 않도록 캐시 TTL(수명) 설정을 세밀하게 조정하고 적절한 캐시 크기를 선택하세요. 이는 불필요한 요금으로 이어질 수 있습니다.

- **스로틀링과 사용 계획:**
    - 트래픽을 제어하고 갑작스러운 API 호출 급증으로 인한 예상치 못한 비용 급증을 방지하기 위해 스로틀링을 구현하세요.
    - API 키당 요청 수를 제한하는 사용 계획을 만들어 사용량 — 그리고 그에 따라 비용 — 을 예측 가능한 범위 내로 유지하는 데 도움을 주세요.

- **모니터링과 최적화:**
    - API 사용량, 지연 시간, 오류율을 추적하기 위해 CloudWatch 같은 AWS 모니터링 도구를 사용하세요. 이 정보는 축소할 수 있는 비효율적인 엔드포인트나 활용도가 낮은 기능을 식별하는 데 도움이 될 수 있습니다.
    - API 사용 패턴을 정기적으로 검토하고 성능 요구와 예산 제약에 맞춰 구성을 조정하세요.

비용 최적화 전략에 대한 더 자세한 안내는 공식 [AWS API Gateway 모범 사례](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-best-practices.html) 문서를 참고하세요.
## 13. 결론

Amazon API Gateway는 AWS에서 현대적인 서버리스 아키텍처를 만드는 데 핵심적인 요소입니다. 보안, 확장, 요청 처리에 대한 고급 제어를 제공하면서 API의 간소화된 개발과 유지 관리를 가능하게 합니다.

더 포괄적인 세부 사항은 [공식 문서](https://docs.aws.amazon.com/apigateway/latest/developerguide/welcome.html)를 참고하세요.
